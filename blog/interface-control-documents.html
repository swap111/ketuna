Interface control documents: agreeing on the boundary before building

Systems & product engineering Intermediate 27 Nov 2026 5 min read By Ketuna

An interface control document writes down the signals, protocol, timing, connectors and ownership at a boundary between two teams, so each can build its side in parallel and integration holds no surprises.

Integration is where projects discover that two teams understood the same arrow on a block diagram differently. One side sent 16-bit readings in millivolts, the other expected tenths of a degree; one side's connector numbered pins clockwise, the other's anticlockwise; one side assumed the sensor was ready 10 ms after power-up, the other found it needed 100. An interface control document (ICD) prevents this by turning the arrow into an agreement, written and owned, before either side builds its half.

What an ICD is for

An ICD describes one boundary between two parts of a system: two boards, a board and a cable harness, firmware and an FPGA, a device and a phone app. It has three jobs:

  • Let teams work in parallel. The firmware engineer can write and test a driver against the ICD while the board is still being laid out.
  • Make integration a check, not a discovery. Each side verifies its half against the ICD; joining them then confirms what is already expected.
  • Control change. A boundary that changes silently breaks the other side. The ICD has an owner and a change process, so changes are proposed, reviewed and agreed.

An ICD is not a design document for either side. It says what crosses the boundary and how, not how each side achieves it.

What goes in it

The running example is a small sensor head connected by a 1 m cable to a main controller board. Each is designed by a different team. A useful ICD covers these areas, and the values below are made up for illustration.

Identification and ownership. Which two items, the document version, the owner (one person, usually from the systems role, not either side), and the approvers from each team.

Mechanical and connector. Connector part on each side, mating part, keying, cable length and type, and the pinout, written from one agreed viewpoint:

Pin Signal Direction (head view) Notes
1 VSUP in 3.3 V ± 5 %, 20 mA max
2 GND — Return for VSUP and signals
3 SDA bidirectional I2C data, pull-up on controller
4 SCL in I2C clock, pull-up on controller
5 INT_N out Open drain, active low, pull-up on controller
6 GND — Second ground, beside SCL

State whose view the pin numbers use, as seen looking into the connector on the head, for example. Mirror-image errors are among the most common integration faults.

Electrical. Voltage levels, input thresholds, maximum current, which side provides pull-ups and what value, ESD protection responsibility, and what happens if the cable is hot-plugged.

Protocol and data. Bus type and speed (I2C at up to 100 kHz over the 1 m cable), the device address, the register map, byte order, and units and scaling of every value: "TEMP register, signed 16-bit, two's complement, units of 0.01 °C".

Timing. Power-up sequence ("head ready for I2C 50 ms after VSUP reaches 3.0 V"), sample rate, maximum latency from a measurement to INT_N asserting, and timeouts.

Behaviour on errors. What the head does on a bus error, what the controller does if INT_N is stuck low or the head stops responding, and how a fault is reported.

Verification. How each side proves compliance: a test harness that emulates the other side, a loopback test, measurements at the connector.

Make the ICD executable where you can

Text that people re-type into code is a source of errors. Where possible, generate or share artefacts directly from the ICD so both sides use the same definitions. For a register map, a single header both teams include is a good start:

/* sensor_head_icd.h -- generated from ICD-SH-01 rev C. Do not edit. */
#ifndef SENSOR_HEAD_ICD_H
#define SENSOR_HEAD_ICD_H

#define SH_I2C_ADDR         0x48u   /* 7-bit address */
#define SH_READY_MS         50u     /* after VSUP >= 3.0 V */

#define SH_REG_ID           0x00u   /* read-only, reads 0xA5 */
#define SH_REG_STATUS       0x01u   /* bit0 DATA_RDY, bit1 FAULT */
#define SH_REG_TEMP_H       0x02u   /* signed 16-bit, 0.01 degC/LSB */
#define SH_REG_TEMP_L       0x03u
#define SH_REG_CTRL         0x10u   /* bit0 START, bits3:1 RATE */

#define SH_ID_VALUE         0xA5u
#define SH_TEMP_LSB_mC      10      /* 0.01 degC = 10 milli-degC */

#endif

The head's firmware or RTL implements these registers; the controller's driver reads them. A script can also generate the register table in the ICD and a test that reads every register and checks its reset value, so the document, the code and the test cannot drift apart.

Ownership and change control

The ICD needs one owner who is not on either side, because each side will naturally want the other to absorb changes. A workable process:

  1. A change request states what changes, why, and the impact on each side.
  2. Both sides review it and agree, or escalate to the project lead.
  3. The ICD revision increments, the change log records it, and generated artefacts are regenerated.
  4. Each side updates its implementation and reruns its compliance tests against the new revision.

Version the ICD in the same repository as the code and design files, so the revision a board or firmware build was made against is always known.

Common mistakes

  • Arrows labelled "data" on a block diagram, and nothing more. Every question that matters at integration is hidden.
  • Units and scaling left implicit. A value without units is a bug waiting for a meeting.
  • Pinouts without a stated viewpoint.
  • No error behaviour. Teams test the happy path and discover the failure path in the field.
  • Changes agreed in a hallway. If it is not in the ICD revision, it did not happen.

Try it yourself

  1. Pick a boundary in a project you know, such as a sensor module to a microcontroller, and write a one-page ICD covering pinout, electrical levels, protocol, units and timing.
  2. Write a small Python script that reads the register table from a CSV and generates both the C header above and a Markdown table for the document.
  3. Write a cocotb testbench or a C test that emulates one side of the interface and checks the other side against the ICD's timing and register values, and run it with Icarus Verilog or GCC.
