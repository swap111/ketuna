Testing an APB register block with pyuvm, from sequence to scoreboard

Verification Advanced 27 Nov 2026 5 min read By Ketuna

A walk-through of a pyuvm environment for a four-register APB slave, with a spec-derived register model, a wait-state-aware driver, reset-value checks and a scoreboard that predicts side effects.

Register blocks look like the easiest thing on a chip to verify, and that is why they ship with bugs. Every field has an access policy, a reset value, a width and sometimes a side effect, and the bugs live in exactly those details: a read-only field that accepts writes, a byte strobe ignored on one register, a counter that increments on an error response. This walk-through builds a pyuvm environment for a small APB slave and concentrates on the part that does the real work, the register model that predicts every response.

The block and its spec

The design is an APB slave with one wait state on reads and none on writes:

Address Register Access Behaviour
0x00 CTRL RW 8 bits; upper 24 read as 0
0x04 DATA RW byte strobes honoured
0x08 STATUS RO [31:16] fixed ID, [15:0] count of accepted writes
0x0C SCRATCH RW byte strobes honoured

Unmapped addresses and any write to STATUS complete with pslverr = 1 and change nothing. All registers reset to zero except the ID field.

Two lines in that table hide most of the interesting cases. "Accepted writes" means a write with an error response must not increment the counter. And "changes nothing" on an error means the counter, the target register and every other register stay put.

The register model is the reference

The model knows the spec and nothing about pins or timing. It holds a mirror of every register and, for each transfer, returns the predicted prdata and pslverr while updating its mirror the way the design should.

class ApbRegModel:
    ID = 0x0A51
    RW = {0x00: 0x0000_00FF, 0x04: 0xFFFF_FFFF, 0x0C: 0xFFFF_FFFF}

    def __init__(self):
        self.reset()

    def reset(self):
        self.mirror = {a: 0 for a in self.RW}
        self.wr_count = 0

    @staticmethod
    def strobe_mask(pstrb):
        return sum(0xFF << (8 * i) for i in range(4) if pstrb >> i & 1)

    def predict(self, write, addr, wdata=0, pstrb=0xF):
        """Return (prdata, pslverr); update the mirror as the spec says."""
        if addr == 0x08:
            if write:
                return 0, 1                       # STATUS is read-only
            return (self.ID << 16) | (self.wr_count & 0xFFFF), 0
        if addr not in self.RW:
            return 0, 1                           # unmapped
        if not write:
            return self.mirror[addr], 0
        m = self.strobe_mask(pstrb) & self.RW[addr]
        self.mirror[addr] = (self.mirror[addr] & ~m) | (wdata & m)
        self.wr_count += 1
        return 0, 0

Notice what the model encodes explicitly: the field mask for CTRL, strobe merging, the error rule, and the counter's dependence on success. Each of those is a line a reviewer can hold against the spec. Write it from the table, not from the RTL. If you transcribe the RTL's case statement, the model inherits whatever the RTL got wrong, and the scoreboard agrees with it forever.

One subtlety: with pstrb = 0 on a mapped register, this model counts the write as accepted while changing no data. Whether that is right is a spec question. Raise it with the designer and record the answer, rather than letting either the model or the RTL decide silently.

Driver and monitor on a protocol with wait states

The driver turns an item into APB phases. Because reads take a wait state, it must loop on pready rather than assume a fixed length. Driving on the falling edge keeps the setup and access phases clear of the rising edge where the slave samples.

class ApbDriver(uvm_driver):
    def start_of_simulation_phase(self):
        self.dut = cocotb.top

    async def run_phase(self):
        d = self.dut
        while True:
            it = await self.seq_item_port.get_next_item()
            await FallingEdge(d.pclk)                    # setup phase
            d.psel.value, d.penable.value = 1, 0
            d.pwrite.value, d.paddr.value = it.write, it.addr
            d.pwdata.value, d.pstrb.value = it.wdata, it.pstrb
            await FallingEdge(d.pclk)                    # access phase
            d.penable.value = 1
            while True:
                await ReadOnly()                 # settled bus values
                done = d.pready.value == 1
                await RisingEdge(d.pclk)         # slave samples here
                if done:
                    break
            await FallingEdge(d.pclk)
            d.psel.value, d.penable.value = 0, 0
            self.seq_item_port.item_done()

The monitor is independent of the driver. On each rising edge where psel, penable and pready are all high, it builds a transaction from the bus, including the observed prdata and pslverr, and calls self.ap.write(txn). It never reads the sequence item, so a driver bug that sends the wrong strobe is observed as what it really was.

The scoreboard predicts and compares

The scoreboard is a uvm_subscriber connected to the monitor's analysis port. For each observed transfer it asks the model what should have happened and compares.

class ApbScoreboard(uvm_subscriber):
    def build_phase(self):
        self.model = ApbRegModel()
        self.seen, self.errors = 0, []

    def write(self, t):
        exp_rdata, exp_err = self.model.predict(
            t.write, t.addr, t.wdata, t.pstrb)
        self.seen += 1
        if t.pslverr != exp_err or (not t.write and t.prdata != exp_rdata):
            self.errors.append(f"{t}: expected rdata={exp_rdata:#x} "
                               f"err={exp_err}")

    def check_phase(self):
        assert self.seen > 0, "scoreboard saw no transfers"
        assert not self.errors, "\n".join(self.errors[:10])

This is implicit prediction: the mirror updates from what the monitor saw, not from what the sequence intended. It is the right choice here because it keeps the scoreboard valid for any stimulus, including traffic that does not come from your sequences.

Reset checks deserve their own sequence

Reset values are part of the spec and are often wrong in quiet ways. A dedicated sequence reads every register straight after reset, before any write. If reset is applied again mid-test, the scoreboard must call model.reset() at the same moment, which means something in the environment has to observe the reset pin. A reset monitor that broadcasts reset events is cleaner than having the test call the model directly, because it also works when reset comes from another source.

A sensible sequence set for this block:

  • Reset values: read all four registers, plus one unmapped address
  • Write then read: each RW register with full and partial strobes
  • Error paths: writes to STATUS and to unmapped addresses, each followed by a STATUS read to prove the counter did not move
  • Random: random address, direction, data and strobes, biased towards the four valid addresses

Mutations this environment should catch

Before trusting the environment, break the RTL deliberately and check that each mutation fails:

  • increment the counter on error responses
  • ignore pstrb[3] on SCRATCH
  • let CTRL keep bits above 7
  • return the wrong ID

If one survives, the gap is in stimulus or in the model, and you now know where. An environment that has never caught a seeded bug has not been shown to catch anything.

Try it yourself

  1. Write the four-register APB slave in Verilog from the table above, without looking at any reference implementation.
  2. Build the environment with pyuvm and cocotb on Icarus Verilog: item, the four sequences, driver, monitor, scoreboard, agent, env and test; run it and confirm check_phase passes.
  3. Apply the four mutations one at a time and confirm each produces scoreboard errors.
  4. Add a coverage subscriber with bins for each register × direction × error outcome, and use the holes to decide which sequence needs more weight.
