Crossing a multi-bit value between clock domains: handshake, mux recirculation or FIFO

Digital & VLSI design Advanced 27 Nov 2026 6 min read By Ketuna

Synchronizing bus bits one by one can produce values that never existed. Compare the three safe structures for multi-bit crossings, what each assumes, what it costs, and how to choose.

A configuration word written by a processor on one clock, a timestamp read by a block on another, a stream of samples from an ADC interface: sooner or later every SoC moves multi-bit values between unrelated clocks. The one thing you must not do is put a two-flop synchronizer on each bit. There are three standard safe structures, and choosing among them is a matter of answering two questions about the data: how often it changes, and who guarantees it stays still while it crosses.

Why per-bit synchronizers fail

A synchronizer resolves one bit, at some cycle, to either its old or new value. With eight separately synchronized bits, each bit makes that choice independently. On the cycle where the source changes from 0x3F to 0x40, seven bits are changing. The destination can capture any mix of old and new bits, for example 0x7F or 0x00, values the source never held. Routing skew makes this worse: the bits do not even arrive at the same moment.

All three safe structures share one principle: the data bits are never sampled while they change. A single control signal crosses through a synchronizer, and the data is only captured once that control signal says it is stable. Only one bit is ever resolved by a synchronizer; the bus is sampled long after it has settled.

Structure 1: the request/acknowledge handshake

The source places a value on a data register and holds it. It then toggles a request signal. The request crosses into the destination through a two-flop synchronizer. When the destination sees the toggle, it captures the data, which has been stable for at least two destination cycles, and toggles an acknowledge back. The source sees the acknowledge through its own synchronizer and only then may change the data.

// source side (clk_s)
always_ff @(posedge clk_s or negedge rst_s_n)
  if (!rst_s_n) begin
    req_t <= 1'b0; busy <= 1'b0;
  end else if (!busy && send) begin
    data_s <= value;              // load and hold
    req_t  <= ~req_t;             // toggle request
    busy   <= 1'b1;
  end else if (busy && (ack_t_sync == req_t)) begin
    busy   <= 1'b0;               // destination has the value
  end

// destination side (clk_d): req_t_sync is req_t through 2 flops
always_ff @(posedge clk_d or negedge rst_d_n)
  if (!rst_d_n) begin
    req_seen <= 1'b0; ack_t <= 1'b0;
  end else begin
    req_seen <= req_t_sync;
    if (req_t_sync != req_seen) begin
      data_d <= data_s;           // stable for 2+ cycles: safe
      ack_t  <= req_t_sync;       // toggle acknowledge back
    end
  end

This is a two-phase (toggle) handshake: each transfer is one toggle each way. A four-phase version raises and then lowers both signals, which is simpler to reason about but takes twice the round trips.

What it costs: latency and throughput. Take, for illustration, a 100 MHz source and a 25 MHz destination. The request needs about three destination cycles to be seen and acted on (120 ns), and the acknowledge about three source cycles to return (30 ns): roughly 150 ns per word, so at most about 6.7 million words per second. That is fine for configuration and occasional status values, and far too slow for a data stream.

What it assumes: nothing about the clock frequencies. It works whether the destination is faster or slower, because each side waits for the other.

Structure 2: mux recirculation (data plus qualifier)

Sometimes the source can guarantee by design that the data stays still for a known time after it changes, for example a control register that firmware updates rarely, or a value that only changes once per long frame. Then you can drop the acknowledge.

The source updates the data bus and toggles a single "new data" qualifier. The qualifier crosses through a two-flop synchronizer and an edge detector. The destination register has a mux in front of it that recirculates its own value, holding it, until the detected edge selects the bus instead. Hence the name.

What it costs: almost nothing: one synchronizer and a mux per bit, and about three destination cycles of latency.

What it assumes: that the data is held stable for longer than the qualifier's synchronization delay plus margin, measured in the slowest destination clock. That assumption lives outside the circuit, so it must be written into the design documentation and, ideally, checked with an assertion in simulation. If a later change makes the source update faster, the structure silently breaks.

Structure 3: the asynchronous FIFO

For a continuous stream, such as ADC samples or packets, neither of the above keeps up. The asynchronous FIFO crosses only Gray-coded pointers through synchronizers, and data is written into and read from a dual-port memory. The pointer synchronization tells each side which entries are safe to touch; the memory contents are only read after the write pointer that covers them has crossed, so they are always stable when sampled.

What it costs: a memory or register array, pointer logic, and a few cycles of flag latency. It is the largest of the three structures.

What it gives: full throughput, one word per cycle on each side, limited only by the slower clock, plus buffering for bursts.

Choosing among them

Situation Structure
Occasional value, no timing guarantee from the source Handshake
Rare updates, source holds data for a known long time Mux recirculation
Continuous stream or bursts Asynchronous FIFO
Counter that changes by one per cycle Gray code plus per-bit synchronizers

The last row is the one exception to "never synchronize bits individually": a Gray-coded counter changes exactly one bit per step, so a per-bit synchronizer can only show the old or the new value.

Constraints and checking

The data bits in all three structures are deliberately not timed against the destination clock in the normal way. But declaring them a false path entirely is risky: if the bits arrive with a large skew, longer than the qualifier's synchronization delay, the destination could capture before they settle. A common practice is a max-delay constraint on the data bits, set below the qualifier's latency, so that place and route keeps them reasonably aligned. Then run a structural CDC check, which looks for unsynchronized crossings, reconvergence and missing qualifiers, in addition to simulation.

Try it yourself

  1. Complete the handshake code into two modules with the synchronizers, and simulate it in Icarus Verilog with clocks at 10 ns and 37 ns periods. Measure the cycles per transfer and compare with your estimate.
  2. Write a per-bit synchronized 8-bit bus next to the handshake version, and in the testbench add small random delays to each data bit. Count how often the per-bit version captures a value the source never sent.
  3. Add an assertion to the mux recirculation version that the source data does not change within N destination cycles of a qualifier toggle, and see it fire when you shorten the source's update interval.
