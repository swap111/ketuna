Layering a testbench: stimulus, driver, monitor and checker

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Split a testbench into what to send, how to send it, what was observed and whether it was right. A plain cocotb example shows why this layering pays off even without a methodology library.

Most first testbenches are one long function. It sets an input, waits a clock, checks an output, sets the next input, and so on for two hundred lines. It works until the second test, when you copy the function and change a few lines, and the third, when the interface timing changes and you have to edit every copy. Professional testbenches avoid this with a simple idea that does not need any library: separate the jobs, and give each job its own piece of code.

Four jobs, four layers

Every testbench does four different things, whether or not they are separated:

  • Stimulus: deciding what to send. "Send these five values", or "send 1,000 random values with occasional pauses".
  • Driving: deciding how to send it. Which pins to set, in which cycle, and how to wait for the design to accept it.
  • Monitoring: watching the design's pins and turning activity back into values or transactions, without caring who caused it.
  • Checking: deciding whether what was observed is correct, usually by comparing it with a model.

The key rule is that information flows one way through each path. The checker never asks the stimulus what it meant to send; it relies on the input monitor, which reports what actually reached the pins. That keeps the checker honest even if the driver has a bug.

A layered cocotb testbench

Take a block with a simple valid/ready input stream and a valid output stream: each accepted input byte comes out doubled, modulo 256, some cycles later. Here are the layers as small classes.

import cocotb, random
from cocotb.triggers import RisingEdge, ReadOnly

class Driver:
    """How to send: valid/ready handshake on the input."""
    def __init__(self, dut):
        self.dut = dut
        dut.in_valid.value = 0

    async def send(self, value):
        d = self.dut
        d.in_data.value = value
        d.in_valid.value = 1
        while True:
            await ReadOnly()                  # settled values
            accepted = d.in_ready.value == 1
            await RisingEdge(d.clk)           # transfer happens here
            if accepted:
                break
        d.in_valid.value = 0

class Monitor:
    """What happened: report every cycle where valid (and ready) is high."""
    def __init__(self, clk, valid, data, ready=None, callback=None):
        self.clk, self.valid, self.data = clk, valid, data
        self.ready, self.callback = ready, callback

    async def run(self):
        while True:
            await RisingEdge(self.clk)
            await ReadOnly()
            ok = self.valid.value == 1 and (
                self.ready is None or self.ready.value == 1)
            if ok:
                self.callback(int(self.data.value))

class Checker:
    """Was it right: compare outputs with the model, in order."""
    def __init__(self):
        self.expected, self.errors, self.matched = [], [], 0

    def on_input(self, value):
        self.expected.append((value * 2) % 256)     # the model

    def on_output(self, value):
        exp = self.expected.pop(0) if self.expected else None
        if value == exp:
            self.matched += 1
        else:
            self.errors.append(f"got {value}, expected {exp}")

A test now only deals with stimulus. It builds the layers, starts the monitors, sends values, and asks the checker at the end.

async def run_test(dut, values):
    chk = Checker()
    drv = Driver(dut)
    cocotb.start_soon(Monitor(dut.clk, dut.in_valid, dut.in_data,
                              dut.in_ready, chk.on_input).run())
    cocotb.start_soon(Monitor(dut.clk, dut.out_valid, dut.out_data,
                              callback=chk.on_output).run())
    for v in values:
        await drv.send(v)
    for _ in range(20):                 # let the pipeline drain
        await RisingEdge(dut.clk)
    assert not chk.errors, chk.errors[:5]
    assert not chk.expected, "outputs missing"
    assert chk.matched == len(values)

A directed test calls run_test(dut, [0, 1, 127, 128, 255]). A random test calls it with [random.getrandbits(8) for _ in range(1000)]. Neither test knows anything about handshakes or pipeline latency. (Clock and reset setup are left out to keep the example short.)

What the layering buys you

Protocol changes touch one class. If the input interface gains a last signal or a wait state, only Driver and the input Monitor change. Every test keeps working.

New tests are a few lines. A test is just a list of values, or a function that generates them. Writing the twentieth test costs the same as the second.

One checker serves every test. Directed, random and corner-case tests are all checked by the same model, so no test can quietly skip checking.

Monitors are reusable. The same Monitor class watches both the input and output streams. At a higher level, where your block's input is driven by another block instead of your driver, the monitors and checker still work unchanged.

Failures are easier to locate. If the checker reports a mismatch, you know the design or the model is wrong. If the driver hangs, you know the handshake is at fault. Separate pieces fail in recognisable ways.

Growing the layers as the design grows

The same structure stretches a long way before you need anything more formal.

  • Transactions instead of integers. When the interface carries more than one field, such as an address, data and a write flag, pass a small Python dataclass between layers instead of a bare number. Drivers, monitors and the checker then agree on one definition of "a transfer".
  • More listeners on a monitor. Let a monitor call a list of callbacks rather than one. A coverage collector becomes just another listener, counting which values and gaps occurred, with no change to the checker.
  • Stimulus as generators. A Python generator function that yields values, with a seeded random source, can produce directed lists, random streams or corner-biased mixes. The test picks one and hands it to the driver.

When these pieces start repeating across blocks, a methodology library such as pyuvm gives them standard names and connection rules. The layers stay the same; only the plumbing becomes shared.

Common mistakes

  • Checking inside the driver. The driver knows what it sent, so it is tempting to check there. It hides driver bugs and makes the check disappear when the driver is replaced.
  • Feeding the model from the stimulus. If the checker learns inputs from the test instead of the input monitor, an input that never reached the design still produces an expected output, and the error message points the wrong way.
  • No end-of-test check. Without checking that nothing is left in expected, a design that swallows inputs passes.

Try it yourself

  1. Write the doubling block in Verilog with a two-stage pipeline and a ready that drops every third cycle.
  2. Put the classes above in a cocotb test file, add clock and reset, and run directed and random tests on Icarus Verilog.
  3. Change the design's input protocol to add a wait state and update only the Driver; confirm both tests still pass.
  4. Break the design so it drops one byte when ready is low, and check which assertion catches it.
