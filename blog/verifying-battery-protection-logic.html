Verifying battery-protection logic: over-voltage, under-voltage and fault latching

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Assertions and directed corner tests for a battery protection block, covering thresholds, debounce, latched faults and safe reset states, where a single missed case can leave a cell unprotected.

In this article
  1. The block under test
  2. State the safety rules as assertions
  3. Directed tests for every boundary
  4. A reference model for the sample-by-sample behaviour
  5. What to cover
  6. Try it yourself

A battery protection block decides when to disconnect a lithium-ion cell from its charger or its load. If it trips too eagerly, the product shuts down for no reason. If it fails to trip, a cell can be overcharged or over-discharged, which damages it and in the worst case creates a fire risk. That asymmetry changes how you verify it: you are not just checking that it works, you are hunting for any input sequence in which it fails to protect. Assertions that state the safety rules directly, plus directed tests aimed at every boundary, are the core of the job.

A note on scope: this article is about verifying digital decision logic. Real battery protection also depends on analog measurement accuracy, independent hardware protection and the cell manufacturer's limits. Design and test of real battery systems should follow the applicable safety standards and be reviewed by qualified engineers.

The block under test

Consider a simplified protection block for one cell. Every sample period, an ADC delivers the cell voltage in millivolts, and a current sensor delivers a signed current. The thresholds below are made up for illustration; real values come from the cell's datasheet.

Rule Condition Action
Over-voltage (OV) voltage ≥ 4250 mV for 4 consecutive samples Turn off charge FET
OV recovery voltage ≤ 4150 mV (100 mV hysteresis) Charge FET may turn back on
Under-voltage (UV) voltage ≤ 2800 mV for 4 consecutive samples Turn off discharge FET
Over-current (OC) current beyond the limit on any sample Turn off both FETs, latch the fault
OC clear software clear command and current back in range Release the latch
Reset any reset Both FETs off until the first valid sample

Even this small table encodes several distinct mechanisms: thresholds, debounce counts, hysteresis, latching and a safe default. Each is a source of bugs.

State the safety rules as assertions

Write the rules that must never be broken first, before any test. These assertions run in every simulation, so they check the random tests and the directed tests alike.

module bms_props (input logic clk, rst_n, sample_valid,
                  input logic ov_flag, uv_flag, oc_latched,
                  input logic chg_en, dsg_en, clear_cmd, oc_now);
  default clocking cb @(posedge clk); endclocking
  default disable iff (!rst_n);

  // Safety: no FET is on while its fault is active
  a_no_chg_in_ov:  assert property (ov_flag    |-> !chg_en);
  a_no_dsg_in_uv:  assert property (uv_flag    |-> !dsg_en);
  a_oc_both_off:   assert property (oc_latched |-> !chg_en && !dsg_en);

  // Latching: an over-current fault stays latched until cleared
  // with the current back in range
  a_oc_holds: assert property (oc_latched && !(clear_cmd && !oc_now)
                               |=> oc_latched);

  // Outputs are never unknown outside reset
  a_known: assert property (!$isunknown({chg_en, dsg_en}));

  // Reset default: both FETs off while reset is asserted.
  // The explicit disable iff (1'b0) overrides the default above.
  a_reset_safe: assert property (disable iff (1'b0)
                                 !rst_n |-> !chg_en && !dsg_en);
endmodule

The reset assertion overrides the module's default disable iff, because it is precisely the behaviour during reset that it checks. The flags in the properties are internal decisions of the design; checking them against the FET outputs catches wiring and priority mistakes. The timing of the flags, for example that OV is declared after exactly four samples, is better checked by a model in the testbench, because it depends on counting samples.

Directed tests for every boundary

Random voltages spread uniformly across the ADC range will rarely land exactly on 4250 mV, and almost never four times in a row. The boundaries need directed tests. A useful list for this block:

  1. Exact threshold. Four samples at 4250 mV must trip OV; four at 4249 mV must not.
  2. Debounce count. Three samples at 4300 mV followed by one at 4200 mV must not trip; the count must restart.
  3. Debounce exactly met. Four samples over the threshold trip on the fourth, not the third or fifth.
  4. Hysteresis. After OV, a sample at 4151 mV must keep the charge FET off; 4150 mV allows recovery.
  5. Chatter. A voltage alternating between 4249 and 4251 mV each sample must not trip, because no four consecutive samples exceed the threshold.
  6. UV mirror. The same five tests at the UV threshold, with inequalities in the other direction.
  7. OC latch. A single over-current sample turns both FETs off; the latch holds after the current returns to normal.
  8. Clear with fault still present. A clear command while the current is still beyond the limit must not release the latch.
  9. Clear with fault gone. A clear command after the current has returned to range releases it.
  10. Fault during reset release. An over-current on the first sample after reset must still latch.

Tests 1 and 4 are where off-by-one errors in comparisons show up: > written instead of >=, or hysteresis applied in the wrong direction. Test 5 catches debounce counters that count total samples above threshold instead of consecutive ones.

A reference model for the sample-by-sample behaviour

For random and long tests, a small Python model in the testbench predicts the FET states after each sample. It is deliberately written from the table above, not from the RTL.

OV_MV, OV_CLR_MV, UV_MV, UV_CLR_MV, N = 4250, 4150, 2800, 2900, 4

class BmsModel:
    def __init__(self):
        self.ov = self.uv = self.oc = False
        self.ov_cnt = self.uv_cnt = 0

    def sample(self, mv, oc_now, clear):
        self.ov_cnt = self.ov_cnt + 1 if mv >= OV_MV else 0
        self.uv_cnt = self.uv_cnt + 1 if mv <= UV_MV else 0
        if self.ov_cnt >= N: self.ov = True
        elif mv <= OV_CLR_MV: self.ov = False
        if self.uv_cnt >= N: self.uv = True
        elif mv >= UV_CLR_MV: self.uv = False
        if oc_now: self.oc = True
        elif clear: self.oc = False
        chg = not (self.ov or self.oc)
        dsg = not (self.uv or self.oc)
        return chg, dsg

Writing the model raised a question the table did not answer: what is the UV recovery voltage? The model assumes 2900 mV by symmetry, but that is a guess. It must be confirmed with the spec owner before the model is trusted.

What to cover

Functional coverage confirms that the dangerous situations actually occurred. Useful bins: each fault type entered and exited; debounce runs of length 1, 3, 4 and more; samples exactly at each threshold and each recovery level; clear commands with and without the fault present; and a fault arriving on the first sample after reset. Any bin left empty is a protection case nobody has exercised.

Try it yourself

  1. Write the protection block in Verilog from the table, with a sample strobe, debounce counters, hysteresis and the OC latch.
  2. Build a cocotb testbench on Icarus Verilog that drives samples, runs the model above alongside the design, and implements the ten directed tests.
  3. Plant three bugs, one at a time: > instead of >= for OV, a debounce counter that does not reset, and a clear that ignores oc_now. Confirm each is caught, and note which test or assertion catches it.
  4. Bind the property module with Verilator's --assert and run a long random test with voltages biased towards the thresholds.
