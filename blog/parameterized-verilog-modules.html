Writing reusable Verilog with parameters and generate blocks

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

Width parameters, localparam, generate loops and generate-if let one module serve many sizes. Learn the patterns and the elaboration errors beginners hit most often, with fixes.

In this article
  1. Parameters and localparams
  2. Generate loops
  3. Generate if

  7. Try it yourself

The first time you need a 16-bit version of an 8-bit counter you wrote last week, you copy the file and change the numbers. The second time, you copy it again. By the third copy, a bug fixed in one version is still alive in the other two. Parameters and generate blocks let one module describe a whole family of circuits, and they are simple to use once you know the few rules that trip people up.

Parameters and localparams

A parameter is a constant that the instantiating module may override. A localparam is a constant derived inside the module that nobody outside can change.

module shift_reg #(
  parameter WIDTH = 8,          // data width, overridable
  parameter DEPTH = 4           // number of stages, overridable
) (
  input  wire             clk,
  input  wire             en,
  input  wire [WIDTH-1:0] din,
  output wire [WIDTH-1:0] dout
);
  localparam AW = (DEPTH > 1) ? $clog2(DEPTH) : 1;  // derived, fixed

  reg [WIDTH-1:0] stage [0:DEPTH-1];
  integer i;
  always @(posedge clk)
    if (en) begin
      stage[0] <= din;
      for (i = 1; i < DEPTH; i = i + 1)
        stage[i] <= stage[i-1];
    end
  assign dout = stage[DEPTH-1];
endmodule

The ports use WIDTH, so the interface itself changes size. AW is a localparam because it must always agree with DEPTH; letting a user override it separately would only allow inconsistent settings. AW is not used in this small example, but it is the typical pattern for an address width.

$clog2(N) returns the number of bits needed to index N items: $clog2(4) is 2, $clog2(5) is 3. Watch the edge case: $clog2(1) is 0, and a [0-1:0] vector is a bug. That is why the localparam above clamps the width to at least 1.

Overriding parameters

Always override by name:

shift_reg #(.WIDTH(16), .DEPTH(8)) u_delay (
  .clk(clk), .en(en), .din(sample), .dout(sample_d8)
);

Positional overrides, #(16, 8), work but break silently if someone later reorders or adds a parameter. The older defparam statement lets you change a parameter from anywhere in the hierarchy; avoid it, because it makes a module's configuration impossible to see at the instance.

Generate loops

A for loop inside an always block describes repeated behaviour. A generate loop describes repeated structure: instances, assign statements or whole always blocks.

module full_adder (
  input  wire a, b, ci,
  output wire s, co
);
  assign s  = a ^ b ^ ci;
  assign co = (a & b) | (ci & (a ^ b));
endmodule

module ripple_add #(parameter N = 8) (
  input  wire [N-1:0] a, b,
  input  wire         cin,
  output wire [N-1:0] s,
  output wire         cout
);
  wire [N:0] c;
  assign c[0] = cin;
  genvar k;
  generate
    for (k = 0; k < N; k = k + 1) begin : g_bit
      full_adder u_fa (
        .a(a[k]), .b(b[k]), .ci(c[k]),
        .s(s[k]), .co(c[k+1])
      );
    end
  endgenerate
  assign cout = c[N];
endmodule

Each iteration creates a named scope, g_bit[0], g_bit[1] and so on, so the instances have hierarchical names like g_bit[3].u_fa. Those names appear in waveforms, synthesis reports and timing paths, which is why the block label matters.

Generate if

A generate if picks between structures at elaboration time, based on parameters:

generate
  if (REGISTER_OUT) begin : g_reg
    always @(posedge clk) y_q <= y_comb;
    assign y = y_q;
  end else begin : g_comb
    assign y = y_comb;
  end
endgenerate

Only one branch exists in the elaborated design. This is how one module can offer an optional pipeline stage, an optional parity bit or a choice of implementation without duplicating the file. The generate and endgenerate keywords are optional in Verilog-2005 and later, but many teams keep them for readability.

The errors beginners hit most often

These show up at elaboration, the step after parsing where the tool computes parameter values and builds the hierarchy.

  • Using a genvar outside a generate loop, or an integer as a generate index. The loop variable of a generate for must be a genvar; a behavioural for inside always uses an integer or int.
  • Unnamed generate blocks. Tools accept them and invent names such as genblk1, which change when code is edited. Name every generate block.
  • Parameter-dependent widths that become zero or negative. [$clog2(DEPTH)-1:0] with DEPTH = 1 gives [-1:0], which is a 2-bit vector rather than the empty one you might expect, and some tools reject it outright. Clamp derived widths.
  • Overriding a localparam. The tool will reject or ignore it. If users need to set it, it should be a parameter.
  • Width mismatches at the instance. Changing WIDTH on an instance but connecting a fixed-width signal truncates or zero-pads silently. Lint tools warn about this; read those warnings.
  • Non-constant expressions in a parameter or generate condition. Parameters and generate conditions must be computable at elaboration. A signal value cannot choose a generate branch.

Parameters, not macros

Beginners sometimes reach for `define WIDTH 8 instead of a parameter. A macro is a text substitution done by the preprocessor before the compiler sees the code. It has no scope: once defined, it applies to every file compiled after it, in compile order. Two modules that each want a different WIDTH cannot both have one, and the value a module sees can change when someone reorders the file list. A parameter belongs to one module, can differ on every instance, and shows up in the elaborated hierarchy where you can inspect it. Keep macros for things that genuinely are global, such as include guards or a simulation-only switch, and use parameters for anything that describes the size or shape of hardware.

Checking every configuration

A parameterized module is really many modules, and each configuration you intend to support needs to be elaborated and tested. A good habit is a small script that elaborates the module with every interesting parameter combination, including the edge cases such as width 1 and depth 1, and runs a short test on each.

Try it yourself

  1. Elaborate shift_reg with several settings using Icarus Verilog, overriding parameters from the command line with -P, for example iverilog -g2012 -Pshift_reg.DEPTH=1 -o sim shift_reg.v (parameters of the root module can be overridden this way).
  2. Run verilator --lint-only -Wall on ripple_add with an unnamed generate block, then name it and compare the warnings.
  3. Synthesise ripple_add with Yosys using chparam -set N 16 ripple_add before synth, and look for the g_bit instance names in the netlist.
