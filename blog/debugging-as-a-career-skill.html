Debugging as a career skill: hypotheses, experiments and notes

Careers & skills Intermediate 27 Nov 2026 5 min read By Ketuna

Treat every bug as a small experiment: state a hypothesis, predict the result, change one thing, and record what happened in a debugging journal. The method works for RTL, firmware and boards alike.

In this article

  3. Change one thing at a time

Ask experienced engineers what separates a strong junior from a weak one and many will mention debugging before they mention any language or tool. Debugging is where most engineering time goes, in verification, firmware and board bring-up alike, and it is rarely taught as a skill in its own right. The good news is that it is learnable. It is mostly the scientific method applied to a misbehaving system, plus the discipline to write things down.

A bug is a gap in your model

When a system surprises you, the system is not being mysterious. It is doing exactly what it was built to do, and your mental model of it is wrong somewhere. Debugging is the process of finding where.

That framing changes how you work. Instead of hunting for "the bug", you look for the first place where reality and your expectation disagree. A test reports a wrong value at cycle 900; the real question is the earliest cycle at which any signal differed from what you expected, because everything after that is a consequence. In firmware, the crash in a print function is usually a symptom; the cause is whatever corrupted the buffer earlier.

It also explains why the same bug can take one engineer ten minutes and another a day. The fast engineer is not luckier. They narrow the gap systematically, while the slow one changes things at random and hopes.

The experiment loop

Each step of a good debugging session is a small experiment with four parts.

  1. Observe. Reproduce the failure exactly: same test, same seed, same commit, same tool version, same board. Record the precise symptom. A failure you cannot reproduce cannot be fixed with confidence.
  2. Hypothesise. Propose one specific, testable cause: "the read pointer advances when the FIFO is empty", not "something is wrong with the FIFO".
  3. Predict. Before running anything, write what you expect to see if the hypothesis is true. "If I force empty high and pulse rd_en, rd_ptr will increment."
  4. Change one thing. Run the experiment, changing a single variable. Compare the result with the prediction.

If the prediction holds, you have narrowed the gap. If it fails, you have learned something just as valuable: your model was wrong in a place you had not suspected. Either way, the next hypothesis is better informed. The step people skip is the prediction, and it is the one that turns poking into learning. Without it, any result looks like progress.

Change one thing at a time

When you are frustrated, it is tempting to change three things at once: bump the stack size, add a delay and swap the cable. If the problem disappears, you do not know which change fixed it, whether the others introduced new problems, or whether the fault simply became intermittent. You have traded a known bug for an unknown one.

Changing one variable per run feels slower and is almost always faster. It also makes bisection possible: when a design worked at one point and fails now, halve the distance between them repeatedly. With Git, git bisect does this over commits; with a long test, cut it in half until the shortest failing case remains; with a board, remove half the peripherals. Each halving takes one experiment, so even a large search space shrinks quickly.

Keep a debugging journal

Write each experiment down as you go: time, hypothesis, prediction, what you changed, what happened. A plain text file per bug is enough.

BUG: uart_rx test loses bytes after ~450 bytes, 115200
14:05 Repro: tb seed 77, first loss at byte 451. Repeats.
14:20 H1: baud counter drifts. Predict: sample point moves
      later each byte. Result: sample point stable. False.
14:40 H2: FIFO overflow. Predict: overflow flag set just
      before byte 451. Result: flag set. Consistent.
14:55 Why? tb reader takes 1 byte per 90 us; bytes arrive
      every 86.8 us. Backlog grows 1 byte per ~28 bytes,
      so 16 entries fill after ~450. Reader too slow.
15:10 Fix: tb reader takes 1 byte per 80 us. 20 seeds pass.
      Added assertion: overflow never set in normal test.

The journal does several jobs at once. It stops you repeating experiments you have already done, which is surprisingly common after a long afternoon. It makes asking for help easy, because you can show exactly what you tried. It becomes the root-cause note for the bug report. And over months it is a record of real problems you solved, which is the raw material for a strong interview answer about a hard bug.

Notice also that the example's culprit was the testbench, not the design. Checking the stimulus and the checker against the spec, before blaming the RTL or the firmware, is part of good method.

Close the loop

A bug is not fixed when the symptom disappears. It is fixed when you can explain the cause, the fix addresses that cause, and a test exists that fails on the old code and passes on the new. Confirm the test really fails before the fix; a test that never fails proves nothing. AI assistants can be useful for suggesting hypotheses from a log, but each suggestion is just another hypothesis to put through the same loop.

Try it yourself

  1. Take a small RTL module, plant a bug in it (for example remove the !empty guard on a FIFO read pointer) and ask a friend to find it using the loop, writing a journal entry for every run in Icarus Verilog or Verilator.
  2. On your next real bug, write the prediction before every run. Count how many predictions failed and what each taught you.
  3. Practise bisection: in a Git repository with a known good tag, run git bisect start, mark git bisect bad and git bisect good <tag>, and let git bisect run drive your test script.
  4. After fixing, write a regression test and confirm with git stash that it fails on the unfixed code.
