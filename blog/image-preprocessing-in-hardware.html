Image preprocessing in hardware: downscaling, normalisation and windowing

Edge AI Advanced 27 Nov 2026 5 min read By Ketuna

A streaming pixel pipeline crops, downscales and normalises camera data for a small network without ever storing a frame. Line buffers, a verified 2x2 downscaler in Verilog, and the rounding details that matter.

In this article

A camera sensor delivers far more pixels than a small vision network wants, in a format the network was not trained on. Doing the conversion in software means storing the frame first, and a 320 × 240 frame is 76,800 bytes in grayscale, often a large slice of a microcontroller's RAM, plus the processor time to touch every pixel. A hardware pipeline between the sensor interface and memory can crop, shrink and normalise the image as the pixels stream past, so only the small network input ever lands in RAM. The tool that makes this possible is the line buffer.

The streaming constraint

A typical sensor interface delivers pixels in raster order, left to right along a line, then line after line, at up to one pixel per clock, qualified by a valid signal and with gaps between lines. A streaming pipeline must accept each pixel as it arrives, keep only what later pixels will need, and emit results in raster order too.

Operations that use one pixel at a time, such as a gain, an offset or a lookup table, are trivial: a register stage or two. Anything that combines pixels from different lines, such as averaging a 2 × 2 block or applying a 3 × 3 filter, has to remember earlier lines, because the pixel directly above the current one arrived a whole line ago. The memory that holds those lines is a line buffer: one row of storage per remembered line, usually a small on-chip SRAM.

Sliding windows from line buffers

To produce a 3 × 3 window around every pixel, you keep two previous lines in line buffers and the current line arriving live. Each clock, the three vertically aligned pixels (two read from the buffers, one fresh) shift into a 3 × 3 array of registers. The newest pixel is written into the buffer, replacing the oldest, so the buffers always hold the last two lines.

For a 320-pixel-wide image the two buffers hold 640 bytes, against 76,800 for the frame. The general rule: a K × K neighbourhood costs K − 1 line buffers plus K × K registers, independent of the image height.

A 2 × 2 downscaler, verified

Halving width and height by averaging each 2 × 2 block is the most common first step, because it also reduces noise. It needs less than one line of memory: on even rows, store the sum of each horizontal pair (W / 2 entries of 9 bits); on odd rows, add the new pair sum to the stored one and output the rounded mean.

module down2x2 #(parameter W = 320) (
  input  wire       clk,
  input  wire       rst,
  input  wire       in_valid,
  input  wire [7:0] in_pix,     // raster order, W pixels per line
  output reg        out_valid,
  output reg  [7:0] out_pix
);
  localparam XW = $clog2(W);
  reg [XW-1:0] x;               // column of the incoming pixel
  reg          odd_row;
  reg [7:0]    left;            // previous pixel on this row
  reg [8:0]    line [0:W/2-1];  // pair sums saved from the even row
  wire [8:0]   pair  = left + in_pix;
  wire [9:0]   total = line[x >> 1] + pair;

  always @(posedge clk) begin
    out_valid <= 1'b0;
    if (rst) begin
      x       <= 0;
      odd_row <= 1'b0;
    end else if (in_valid) begin
      if (!x[0])
        left <= in_pix;                      // first of a pair
      else if (!odd_row)
        line[x >> 1] <= pair;                // even row: save pair sum
      else begin
        out_pix   <= (total + 10'd2) >> 2;   // odd row: 2x2 mean
        out_valid <= 1'b1;
      end
      if (x == W - 1) begin
        x       <= 0;
        odd_row <= ~odd_row;
      end else
        x <= x + 1'b1;
    end
  end
endmodule

The widths matter: a pair sum reaches 510 and needs 9 bits, the four-pixel total reaches 1,020 and needs 10. Adding 2 before shifting right by 2 rounds to nearest instead of truncating. The golden model is one numpy line, (a.reshape(H//2, 2, W//2, 2).sum(axis=(1, 3)) + 2) >> 2, and the testbench should compare every output pixel with it while driving in_valid with random gaps, which is how real sensors behave between lines. Repeating the block gives 4× and 8× reductions.

For non-integer scale factors, a phase accumulator steps through the source coordinates and selects (nearest neighbour) or interpolates (bilinear, needing one line buffer and a few multipliers) the source pixels. The rule stays the same: whatever resampling the hardware does, the training pipeline must do identically.

Cropping and normalisation

Cropping, selecting a region of interest, is the cheapest stage of all: compare the column and row counters against start and end registers and drop pixels outside. Making the window registers writable by firmware lets software move the region, for example to track a gauge that is mounted slightly differently on each installation.

Normalisation converts 8-bit pixels into whatever the network's int8 input tensor expects, which is its scale s and zero point z. If the network was trained on p / 255 and its input was quantized with s = 1/255 and z = −128, the conversion is q = p − 128, which for 8-bit values is just inverting the top bit. Other trainings use (p − mean) / std; then q = round(p × a + c) for constants a and c, which hardware does as a fixed-point multiply, an add, a rounding shift and a clamp to [−128, 127]. Derive a and c from the model's quantization parameters with a script, never by hand, and check with the golden model that every one of the 256 possible input values maps to the same q in both.

Pitfalls

  • training on images resized with a library's default filter while the hardware averages 2 × 2 blocks, so the network sees slightly different inputs in the field
  • truncating instead of rounding, which darkens the image by half a level on average at each stage
  • assuming the sensor never pauses mid-line, and losing pixels when in_valid drops
  • sizing a line buffer for the cropped width while it receives the full sensor width

Try it yourself

  1. Simulate down2x2 with Icarus Verilog using a small width such as W = 8, feed a random image from a hex file with $readmemh, and compare the outputs with the numpy model.
  2. Add random gaps in in_valid to the testbench and confirm the outputs do not change.
  3. Write a 3 × 3 box-filter module with two line buffers and verify it the same way, deciding how to treat the border pixels.
  4. Synthesise both with Yosys and check that the line buffers map to memory rather than thousands of flip-flops; look at the stat output.
