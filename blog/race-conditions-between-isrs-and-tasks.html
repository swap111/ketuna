Race conditions in firmware: shared variables between interrupts and tasks

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

Why a 64-bit tick counter read on a 32-bit core can jump 49 days into the future, how read-modify-write loses updates, and the critical sections, retry loops and atomics that make shared data safe.

An interrupt can arrive between any two instructions of your main loop or task. Most of the time that is harmless. But when the interrupt handler and the interrupted code share a variable, there are instruction boundaries where an interruption produces a value that never existed, or loses an update. These races depend on timing to the instruction, so they pass every bench test and appear in the field as a counter that jumps, a timeout that fires early or an event that is never handled. This article shows the three common shapes and the tools that fix each one.

Shape one: the torn read

A system tick counter is a classic. A timer interrupt increments a 64-bit count every millisecond, and the rest of the firmware reads it to measure time. A 64-bit count at 1 kHz will not overflow in any product's lifetime, which is why people choose it.

static volatile uint64_t ticks;        /* incremented by timer ISR */

void timer_isr(void) { ticks++; }

uint64_t now_ms(void) { return ticks; }   /* broken on a 32-bit core */

On a 32-bit core, reading ticks takes two load instructions, one for each half. With GCC for RV32, the low word is loaded first. Now suppose ticks is 0x0000_0000_FFFF_FFFF:

  1. The reader loads the low half: 0xFFFF_FFFF.
  2. The timer interrupt fires and increments ticks to 0x0000_0001_0000_0000.
  3. The reader loads the high half: 0x0000_0001.

The function returns 0x0000_0001_FFFF_FFFF, a value that was never stored. It is 232 ticks ahead of the truth, about 49.7 days at 1 kHz. Any timeout computed from it expires at once, or a "last seen" timestamp makes a device look offline. The window is one instruction wide and opens only when the low half wraps, once every 49.7 days of uptime, which is why no test finds it.

volatile does not help. It guarantees both loads happen; it says nothing about what happens between them. The same problem hits 32-bit variables on 8-bit and 16-bit cores, and any structure of several fields that must be read as a set.

Shapes two and three: lost updates and stale decisions

The lost update

static volatile uint32_t pending;      /* ISR adds, task subtracts */

void rx_isr(void)  { pending++; }
void task(void)    { if (pending) { pending--; handle_one(); } }

pending-- is load, subtract, store. If the receive interrupt runs between the load and the store, its increment is overwritten when the task stores its stale value minus one. One event is silently lost. The same happens with reg |= bit on a register that an interrupt also modifies.

Check, then act

if (buffer_count < SIZE) {             /* check */
    buffer[buffer_count++] = item;     /* act */
}

If an interrupt adds an item between the check and the action, the code acts on a condition that is no longer true and writes past the end. Any time a decision is based on shared state, the decision and the action must be one indivisible step.

Fix one: a short critical section

The general remedy is to make the sequence indivisible by masking interrupts around it. Save the previous state and restore it, rather than blindly enabling interrupts afterwards, so the function is safe to call from code that already had them disabled. On RISC-V, one instruction clears the global enable bit and returns its old value:

#include <stdint.h>

#define MSTATUS_MIE (1u << 3)

static inline uint32_t irq_save(void)
{
    uint32_t old;
    __asm__ volatile ("csrrc %0, mstatus, %1"
                      : "=r"(old) : "r"(MSTATUS_MIE) : "memory");
    return old & MSTATUS_MIE;
}

static inline void irq_restore(uint32_t was_enabled)
{
    if (was_enabled)
        __asm__ volatile ("csrs mstatus, %0"
                          :: "r"(MSTATUS_MIE) : "memory");
}

uint64_t now_ms(void)
{
    uint32_t s = irq_save();
    uint64_t t = ticks;
    irq_restore(s);
    return t;
}

The "memory" clobber is essential: it stops the compiler from moving the read of ticks outside the protected region. Keep critical sections to a few instructions. Every cycle spent with interrupts masked adds to the worst-case latency of every interrupt in the system.

Fix two: read until consistent

When the writer is hardware or an interrupt you would rather not delay, read the halves in a loop until they agree. The RISC-V machine timer is the textbook case: on RV32, the 64-bit mtime register must be read as two 32-bit halves while it keeps counting:

uint64_t mtime_read(volatile uint32_t *lo_reg, volatile uint32_t *hi_reg)
{
    uint32_t hi, lo;
    do {
        hi = *hi_reg;
        lo = *lo_reg;
    } while (hi != *hi_reg);           /* high half moved: try again */
    return ((uint64_t)hi << 32) | lo;
}

If the high half is the same before and after reading the low half, no carry happened in between, so the pair is consistent. Retry loops never block the writer. They work when updates are rare compared with how long one read takes, which is true for a counter.

Fix three: atomics and single-writer design

C11 <stdatomic.h> gives operations that the compiler guarantees are indivisible, such as atomic_fetch_add and atomic_fetch_sub. On RISC-V cores with the A extension, these become single atomic memory instructions. On cores without it, check what your toolchain generates, since it may fall back to library calls that themselves need a critical section. A 64-bit atomic on a 32-bit core is usually not lock-free either.

Often the cleanest fix is structural: give every shared variable exactly one writer. Instead of one pending counter that both sides modify, keep an added count written only by the interrupt and a handled count written only by the task; the work outstanding is added - handled. This is the principle behind the single-producer, single-consumer ring buffer described in Writing an interrupt-safe ring buffer for UART receive.

Finding races before the field does

  • List shared variables. For every variable touched by an interrupt, note its width, who writes it and who reads it. Anything wider than the core's natural word, or written by both sides, needs one of the fixes above.
  • Force the bad interleaving in a test. On the host, call the interrupt handler from inside the reader at the worst point, through a test hook, and assert that the result is still valid.
  • Start counters near the wrap. Initialise ticks to just below 0xFFFF_FFFF in test builds so the rare case happens in the first second.

Try it yourself

  1. Compile return ticks; for RV32 with riscv64-unknown-elf-gcc -O2 -S and find the two loads. Mark where an interrupt causes the torn value.
  2. On the host, simulate the torn read by splitting the read into two halves with a call to timer_isr() between them, starting ticks at 0xFFFFFFFF, and print the result. Then apply each fix and show that the test passes.
  3. On QEMU's RISC-V virt machine, where mtime sits at 0x0200BFF8 and counts at 10 MHz, read it with the retry loop. Then work out how often its low half wraps (about every 7 minutes) and explain why a naive two-load read can pass a long test run and still fail in the field.
