The load-use hazard: why one bubble remains even with forwarding

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

A load's data arrives at the end of the memory stage, one cycle too late to forward into the next instruction's ALU. Learn why, how the pipeline detects it and stalls, and how compilers hide the bubble.

In this article

  2. Detecting the hazard
  3. A store after a load is a special case
  4. How the compiler hides the bubble

  6. Try it yourself

Forwarding removes almost every data hazard in a five-stage pipeline: an ALU result can be sent straight back to the next instruction without waiting for write-back. There is one exception that every in-order pipeline of this shape keeps. When an instruction uses the result of a load immediately after it, the data simply does not exist yet at the moment it is needed, and no wire can fix that. The pipeline must wait one cycle. This article shows why, how the hardware detects the case, and how software makes the wait disappear most of the time.

Why forwarding cannot reach

Recall the stages: IF, ID (register read), EX (ALU), MEM (data memory) and WB. An ALU instruction has its result at the end of EX. A load has its result only at the end of MEM, because the address is computed in EX and the memory is read in the following cycle.

Now put a dependent instruction straight after the load:

lw   x1, 0(x2)      # x1 arrives at the end of MEM
add  x3, x1, x4     # needs x1 at the start of its EX

Without a stall, the add would be in EX in the same cycle that the load is in MEM. The add needs x1 at the start of that cycle to feed its ALU; the load produces x1 at the end of that cycle. Forwarding moves data between stages within a cycle boundary; it cannot send a value backwards in time. The only fix is to delay the add by one cycle so that it reaches EX when the load reaches WB, and then forward from the MEM/WB register as usual.

Instruction C1 C2 C3 C4 C5 C6 C7
lw x1, 0(x2) IF ID EX MEM WB
add x3, x1, x4 IF ID ID (stall) EX MEM WB
next instruction IF IF (stall) ID EX MEM

In C4 a bubble, an empty slot that does nothing, enters EX in place of the add. In C5 the add is in EX and the loaded x1 is forwarded from MEM/WB. The cost is exactly one cycle.

Detecting the hazard

The check is made when the consumer is in ID and the load is one stage ahead in EX. That is the last moment to hold the consumer back before it would read a wrong operand.

// Stall if the instruction in EX is a load whose destination
// is a source of the instruction in ID.
wire uses_rs1 = dec_uses_rs1;   // from the decoder
wire uses_rs2 = dec_uses_rs2;   // false for I-type, U-type, J-type

assign load_use_stall =
    idex_memread && (idex_rd != 5'd0) &&
    ((uses_rs1 && idex_rd == ifid_ins[19:15]) ||
     (uses_rs2 && idex_rd == ifid_ins[24:20]));

The uses_rs2 term is worth the few extra gates. An addi x3, x1, 8 has an immediate in bits 24 to 20, not a register number. Without the term, those bits can match the load's destination by accident and cause a stall that is not needed. It does not break correctness, but it costs cycles for no reason.

When load_use_stall is high, three things happen together:

  1. The PC does not advance, so the instruction in IF is fetched again.
  2. The IF/ID register holds, so the consumer stays in ID.
  3. The control bits entering ID/EX are cleared, so EX receives a bubble with no register write and no memory access.

All three must happen in the same cycle. Freezing the PC but not IF/ID skips an instruction; freezing IF/ID but not the PC duplicates one. Clearing only the register-write bit but not the memory-write bit lets a ghost store through.

A store after a load is a special case

lw  x1, 0(x2)
sw  x1, 0(x5)

The store needs x1 only as data to write, and it needs it in MEM, not in EX. If the core adds a forwarding path from MEM/WB into the store-data input of the MEM stage, this pair runs without a stall. The simple stall logic above, which only knows "rs2 is used", will still stall here. Whether the extra path is worth it depends on how often your code copies memory word by word; it is a design choice to make with measurements, not a rule.

How the compiler hides the bubble

The stall is architectural only in the sense that the hardware must handle it. Software can often move an independent instruction into the gap. Take a loop that sums an array:

loop: lw   t1, 0(a0)
      add  t0, t0, t1     # uses t1 immediately: stall
      addi a0, a0, 4
      addi a1, a1, -1
      bnez a1, loop

Each iteration issues five instructions and loses one cycle to the load-use stall, so ignoring branch costs it takes 6 cycles. Reorder it:

loop: lw   t1, 0(a0)
      addi a0, a0, 4      # independent: fills the slot
      addi a1, a1, -1
      add  t0, t0, t1     # t1 is ready now
      bnez a1, loop

The result is identical, because neither addi touches t0 or t1. Each iteration now takes 5 cycles. Over 100 iterations that is 600 cycles against 500 for the same work. Optimising compilers do this routinely when they schedule instructions for a pipeline, which is one reason the same C code can run faster at -O2 than at -O0. When you write assembly by hand, the job is yours.

Common mistakes

  • Checking for the hazard too late. By the time the consumer is in EX it has already used a wrong operand; detect in ID.
  • Ignoring x0. A load into x0 is legal and its result is discarded; it must not trigger a stall or a forward.
  • Stalling without the bubble. Holding IF and ID but letting the consumer's control bits into EX executes it twice.
  • Assuming the cost is fixed. On cores with longer memory pipelines or caches, the load-to-use distance can be two or more cycles, and a cache miss stalls far longer.

Try it yourself

  1. Write both versions of the summing loop in assembly and count cycles by hand with a timing table like the one above.
  2. Run both on a pipelined RV32I core in Verilator or Icarus Verilog with a cycle counter in the testbench, and confirm the one-cycle difference per iteration.
  3. Compile a C loop with a RISC-V GCC cross-compiler at -O0 and at -O2 (add -S), and find where the compiler placed an independent instruction after each load.
