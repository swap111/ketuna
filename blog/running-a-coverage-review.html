Running a coverage review: which holes to close and which to waive

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

How to triage coverage holes into missing stimulus, unreachable cases and spec questions, write waivers that a reviewer can check, and decide with evidence when a block's verification is done.

In this article

  2. Four kinds of hole

Near the end of a block's verification, the coverage report shows a number short of 100% and a list of holes. Two bad responses are common. One is to keep running random seeds and hope. The other is to exclude whatever is left until the number turns green. A coverage review is the disciplined middle path: a meeting, with the designer present, where every hole gets a decision and a reason, and the team agrees on what "done" means for this block.

Prepare before the meeting

A review goes quickly when the inputs are ready and merged.

  • Merged coverage from all regression runs, all seeds, all tests. Holes in a single run are not holes.
  • The verification plan, with each coverage item linked to a plan item.
  • The code coverage report, read for holes, not percentages.
  • The open bug list for the block.
  • A first-pass triage of every hole by the verification engineer, so the meeting confirms decisions instead of making them from scratch.

Four kinds of hole

Every coverage hole falls into one of four categories, and each has a different fix.

Category Meaning Action
Missing stimulus Reachable and important, but tests never got there Add a constraint, bias or directed test
Unreachable by design Cannot happen given how the RTL is built Exclude, with the reason and evidence
Not interesting Reachable but adds no verification value Waive, with the reason
Spec question Nobody knows whether it should happen Ask the spec owner; then reclassify

The hard part is telling the first two apart. "Our tests never reached it" and "it cannot be reached" look identical in a coverage report. The difference must be shown, not assumed: by reading the RTL with the designer, by a formal cover check that fails to find a trace, or by a structural reason such as a tied-off parameter.

A worked triage

Suppose a timer block's merged report shows these holes:

  1. Cross bin: one-shot mode × LOAD = 0. Random LOAD values rarely produce zero. Reachable and listed in the plan. Missing stimulus: add a directed test and bias the generator towards 0.
  2. Code coverage: default branch of the mode decode. The mode field is two bits and all four values are decoded explicitly, so default can never execute. Unreachable: exclude, citing the decode. Better still, add an assertion that it is never reached, so the exclusion is checked in every run.
  3. Toggle coverage: upper 8 bits of LOAD never toggled 1→0. Tests write large values but never reduce them. Each bit is stored the same way, but toggle holes on a register's storage can hide stuck bits. Missing stimulus: cheap to close with one write sequence.
  4. Bin: clear and zero event on the same cycle. Reachable and important, because the spec says the event wins. Random timing made it rare. Missing stimulus: a directed test that lines up the write.
  5. Bin: auto-reload with interrupt disabled and LOAD at maximum. Reachable, but the three features are independent in the RTL and each pair is already covered. Not interesting: waive, with the reason.
  6. Bin: LOAD write during the cycle the counter reaches zero. The spec does not say which value the reload uses. Spec question: assign to the designer and spec owner; reclassify after the answer.

Of six holes, three need new stimulus, two need written decisions, and one waits on a spec answer. That is a typical picture: most holes are cheap to close once someone has looked at them.

Waivers that survive scrutiny

A waiver is a claim that a hole does not matter. It needs to be checkable by someone who was not in the room.

Each waiver should record:

  • the coverage item, exactly as named in the report
  • the category: unreachable or not interesting
  • the reason in a sentence or two, citing the spec section or RTL line
  • the evidence where it exists: an assertion, a formal result, a parameter value
  • who agreed to it, so questions have an owner

Keep waivers in a text file in the repository, next to the plan, so they are reviewed like code and re-applied automatically. A short script can merge them with the coverage report and list anything still open:

import csv

def open_holes(holes, waiver_csv):
    """Return coverage holes that have no waiver."""
    with open(waiver_csv, newline="") as f:
        waived = {row["item"]: row for row in csv.DictReader(f)}
    for h in holes:
        if h not in waived:
            yield h
        elif not waived[h]["reason"].strip():
            yield f"{h} (waiver has no reason)"

holes = ["x_mode_load.one_shot.zero", "cp_mode.default",
         "x_all.reload.irq0.max"]
for h in open_holes(holes, "timer_waivers.csv"):
    print("OPEN:", h)

Revisit waivers when the RTL changes. A branch that was unreachable last month may be reachable after a feature is added, and the exclusion would then hide new, untested behaviour. Tying unreachable waivers to assertions guards against this automatically.

Deciding when verification is done

Coverage is one input to sign-off, not the whole of it. A defensible "done" for a block usually means all of the following:

  • Every plan item has a check, and its coverage goal is met or waived with a recorded reason.
  • Code coverage holes are explained, and none points at untested functionality.
  • The regression passes across many seeds, and failures are all understood.
  • The rate of new bugs found has fallen off, and recent bugs were in corners rather than in main features.
  • The testbench has been shown to catch seeded bugs, so a green result means something.
  • Open spec questions are answered and reflected in the spec.

When those hold, write a short sign-off note listing the evidence, the waivers and any known limitations. A reviewer, or you in six months, can then see exactly what was verified and what was not.

Try it yourself

  1. Take a block you have verified with cocotb on Icarus Verilog or Verilator, merge its coverage from several seeds, and list every hole.
  2. Classify each hole into the four categories, and for any you mark unreachable, try to prove it with an assertion or a SymbiYosys cover.
  3. Write a waiver CSV with reasons, run the script above, and close the remaining holes with stimulus.
  4. Ask a classmate to act as designer and challenge each waiver, and record which ones survived.
