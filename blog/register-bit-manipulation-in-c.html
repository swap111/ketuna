Setting, clearing and testing register bits safely in C

Embedded systems Beginner 27 Nov 2026 5 min read By Ketuna

Masks and shifts for single bits and multi-bit fields, why read-modify-write can silently undo another write, and how set/clear registers and write-1-to-clear flags change the code you should write.

In this article
  1. Masks, shifts and the four operations
  2. Multi-bit fields
  3. Hazard one: read-modify-write meets an interrupt
  4. Hazard two: bits that react to being written
  5. Pitfalls checklist
  6. Try it yourself

Almost every line of a low-level driver changes a few bits in a 32-bit register and leaves the rest alone. The C operators for this are simple, and that is the danger: REG |= BIT looks like one action but is three, and on real hardware those three steps can collide with an interrupt or with bits that react to being written. This article covers the idioms, then the two hazards that break them, and the register designs that make them safe.

Masks, shifts and the four operations

Name every bit with a mask built from an unsigned shift:

#define UART_CTRL_TXEN   (1u << 0)
#define UART_CTRL_RXEN   (1u << 1)

The u matters. 1 << 31 shifts a 1 into the sign bit of a signed int, which is undefined behaviour in C; the optimiser is allowed to assume it never happens. 1u << 31 is well defined.

With a mask m the four operations are:

Goal Code Why it works
Set bits reg |= m; OR with 1 forces a 1; OR with 0 keeps the bit
Clear bits reg &= ~m; AND with 0 forces a 0; AND with 1 keeps the bit
Toggle bits reg ^= m; XOR with 1 flips; XOR with 0 keeps
Test a bit (reg & m) != 0 Non-zero only if the bit is set

Write the test as != 0 rather than == m unless you really mean "all of these bits". For a single-bit mask they agree; for a multi-bit mask they do not.

Multi-bit fields

Many registers pack small numbers into fields: a 3-bit mode, an 8-bit divider. Describe each field by a shift and a mask, and write it in two steps, clear then insert:

/* A made-up control register: bit 0 EN, bits 6:4 MODE, bits 15:8 DIV */
#define CTRL_EN          (1u << 0)
#define CTRL_MODE_SHIFT  4u
#define CTRL_MODE_MASK   (0x7u << CTRL_MODE_SHIFT)
#define CTRL_DIV_SHIFT   8u
#define CTRL_DIV_MASK    (0xFFu << CTRL_DIV_SHIFT)

static inline uint32_t field_set(uint32_t reg, uint32_t mask,
                                 uint32_t shift, uint32_t val)
{
    return (reg & ~mask) | ((val << shift) & mask);
}

static inline uint32_t field_get(uint32_t reg, uint32_t mask,
                                 uint32_t shift)
{
    return (reg & mask) >> shift;
}

The final & mask in field_set stops an out-of-range value from spilling into the neighbouring field: writing 9 into a 3-bit field gives 1, not a corrupted divider. Starting from 0xA5A5A5A5, setting MODE to 3, DIV to 0x10 and EN gives 0xA5A510B5; you can check by hand that the upper 16 bits are untouched.

When writing a real register, read it once into a local, apply all the field changes to the local, and write it back once. Each access to a volatile register is a real bus transaction, and some peripherals act on every write.

Hazard one: read-modify-write meets an interrupt

GPIO_OUT |= LED compiles to a load, an OR and a store. Suppose a timer ISR toggles a different pin in the same register:

  1. Main loop loads GPIO_OUT = 0b0000.
  2. The timer interrupt fires. The ISR sets bit 2: the register becomes 0b0100.
  3. Main loop ORs bit 0 into its stale copy and stores 0b0001.

The ISR's change to bit 2 is gone, and nothing reports an error. This is not fixed by volatile: volatile guarantees the load and store happen, not that nothing happens between them. It shows up only when the interrupt lands in a window of two or three instructions, so it can survive weeks of testing.

There are three fixes, in order of preference:

  • Use the hardware's set and clear registers. Many GPIO and interrupt blocks provide separate addresses where writing a 1 sets (or clears) that bit and writing 0 does nothing. GPIO_SET = LED; is a single store with no read, so nothing can slip in between.
  • Use an atomic instruction. On RISC-V, the control and status registers have csrs and csrc instructions that set or clear bits atomically; that is how firmware enables interrupts in mstatus safely. For memory-mapped registers the "A" extension's atomic memory operations exist, but whether a peripheral supports them depends on the bus, so check the manual.
  • Make it a short critical section. Disable interrupts, do the read-modify-write, restore the previous interrupt state.

Hazard two: bits that react to being written

Not every bit is plain storage. Status registers often have write-1-to-clear (W1C) flags: the hardware sets a flag, and firmware clears it by writing a 1 to that bit position. Now look at what STATUS |= RX_DONE does when both RX_DONE and TX_DONE are set: it reads both 1s and writes both back, clearing both flags. The transmit event is lost.

For a W1C register, never read-modify-write. Write only the bit you mean:

STATUS = RX_DONE;    /* clears RX_DONE; writing 0 elsewhere has no effect */

Other bit types to look for in the register description:

  • Read-to-clear: reading the register clears flags, so even a debugger window that polls it changes behaviour.
  • Write-only or reserved bits: they may read as 0 whatever you wrote, so a read-modify-write can reset a field you set earlier. Reserved bits should usually be written with their reset value.
  • Self-clearing bits: a "start" bit that hardware clears when done. Reading back 0 is normal.

Pitfalls checklist

  • Signed shifts: always 1u << n or UINT32_C(1) << n.
  • Integer promotion: ~(uint8_t)0x01 is an int with value -2, not 0xFE. Cast or mask the result when working with narrow types.
  • Precedence: reg & mask == 0 parses as reg & (mask == 0). Use parentheses.
  • Testing a bit you just wrote in a write-only field. Keep a shadow copy in RAM if you need to know what you wrote.

Try it yourself

  1. Copy field_set and field_get into a host C file and write assert tests with gcc: out-of-range values, the top field in the register, and a check that every bit outside the mask is unchanged.
  2. Compile GPIO_OUT |= 1u; for RISC-V with riscv64-unknown-elf-gcc -O2 -S and find the load, OR and store. Mark the instruction gap where an interrupt would cause a lost update.
  3. Open the register description of any peripheral in a reference manual and classify each status bit as read/write, W1C, read-to-clear or read-only. Compare your list with a colleague's.
