Collecting your own sensor dataset: labels, balance and the boring parts that matter

Edge AI Beginner 27 Nov 2026 6 min read By Ketuna

A small edge model is only as good as the data recorded with the real sensor. How to plan recordings, write a labelling guide, cover conditions, balance classes and document the dataset so it stays usable.

In this article

Public datasets are great for learning, but a product model has to work with your sensor, mounted your way, in your users' conditions. That almost always means recording your own data. It is the least glamorous part of an edge AI project and the one with the most influence on the result: a tidy, well-labelled dataset with a simple model regularly beats a clever model trained on messy data. The good news is that the skills involved are mostly planning and discipline, not mathematics.

Start with the question and the classes

Write down, in one sentence, what the model must decide, and list the classes with a definition for each. For a pump monitor: normal running, dry running, blocked inlet, off. For a gesture band: flick, twist, shake, none.

Two rules save a lot of trouble later:

  • Include the "nothing" class. Most of the time a sensor sees nothing of interest. Record plenty of ordinary background, or the model will force every input into one of the interesting classes.
  • Make classes decidable from the data. If a person watching the signal (or the video recorded alongside it) cannot tell two classes apart, the model will not either. Merge them or record more context.

Plan the conditions, not just the count

How much data is "enough" depends on the task, so a raw target number is less useful than a conditions matrix: the list of things that change in the field and that the model must survive. For a wearable, that might be people, wrist (left or right), strap tightness, activity before the gesture and time of day. For a machine sensor: load, speed, temperature, mounting position and different units of the same machine model.

Record every class across as many of those conditions as you can, and spread recordings over several sessions on different days. A dataset recorded in one afternoon captures that afternoon: the same temperature, the same mood, the same sensor placement. Models trained on it learn the afternoon.

Write a short recording protocol for each session: equipment and firmware version, sensor settings (sample rate, range, filters), where and how the sensor is mounted, what the subject or operator does, in what order, and for how long. Following the same protocol every time is what makes sessions comparable.

Labelling consistently

Labels are where datasets quietly go wrong. Two people, or one person on two days, label the same borderline example differently, and the model learns the inconsistency.

  • Write a labelling guide with the class definitions, the exact rule for where an event starts and ends, and examples of tricky cases. When a new edge case comes up, add it to the guide.
  • Capture labels at recording time where you can: a button press, a prompt telling the subject what to do and when, or a synchronised video. Labelling hours of signal afterwards from memory is slow and error-prone.
  • Check agreement. Have two people label the same small sample independently and compare. Where they disagree, the guide is unclear; fix the guide, not just the label.
  • Keep an "unsure" option and leave those examples out of training and testing rather than guessing.

Balance, without fooling yourself

Real data is usually unbalanced: a machine runs normally almost all the time, and faults are rare. A model trained on that data can score well by always predicting the common class.

For training, you can rebalance: record extra examples of rare classes where it is safe to do so, oversample them, or weight their loss more heavily. For testing, keep the proportions you expect in the field, so the reported numbers mean something, and always report per-class results rather than overall accuracy alone.

Also decide early how you will split the data, and record what you need to do it: the person, device and session for every file. Splitting by person or session, so the test set contains people and sessions the model never saw, is the honest way to estimate field performance.

Files, metadata and documentation

Store raw data, not just features: you will change your windowing and features many times. Use one file per recording and a single metadata table that describes every file:

file,session,date,subject,device,position,fw,hz,labels
s01_r001.csv,s01,2026-10-02,p03,dev2,wrist_l,1.4.0,100,s01_r001_lab.csv
s01_r002.csv,s01,2026-10-02,p03,dev2,wrist_l,1.4.0,100,s01_r002_lab.csv
s02_r001.csv,s02,2026-10-05,p07,dev1,wrist_r,1.4.0,100,s02_r001_lab.csv

A short script then tells you whether the dataset covers what you planned:

import pandas as pd

meta = pd.read_csv("metadata.csv")
events = pd.concat(
    pd.read_csv(f).assign(labels=f) for f in meta["labels"])
merged = events.merge(meta, on="labels")
print(merged.pivot_table(index="label", columns="subject",
                         values="start", aggfunc="count", fill_value=0))

Here each label file is assumed to have one row per labelled event with label, start and end columns. The table of counts per class per subject shows at a glance which class is thin and which person is missing a class.

Finally, write a dataset README: why it was collected, the protocol, the class definitions and labelling guide, the conditions covered and, just as important, those not covered, known problems, and a version number. Freeze each version once a model has been trained on it, so results can be traced back to exact data.

People and permission

If the data comes from people, such as motion, voice, images or body signals, it is personal data. Explain to participants what is recorded and why, get their consent, collect only what the task needs, store it securely, and replace names with codes like p03. Health-related data deserves extra care, and studies involving people may need ethics review; check the rules that apply to your organisation and country.

Common mistakes:

  • recording everything in one session with one person and one device
  • no "nothing" class
  • labels made from memory hours later, without a written guide
  • keeping only features and discarding raw data
  • no record of which person or session a file came from, making an honest split impossible

Try it yourself

  1. Write a conditions matrix for a sensing idea of your own, and mark which combinations you can realistically record.
  2. Draft a one-page labelling guide and ask a friend to label ten examples with it; compare with your own labels.
  3. Record a small dataset over at least three sessions with a phone's motion sensors or a development board, with a metadata table like the one above.
  4. Run the coverage script on your metadata and plan the next session to fill the thinnest cells.
