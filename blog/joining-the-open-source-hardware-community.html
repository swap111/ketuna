Finding and joining the open-source hardware community from India

India's electronics ecosystem Beginner 27 Nov 2026 5 min read By Ketuna

Where open-source hardware communities gather, from forums and repositories to meet-ups and shared tape-out groups, and how to make your first contributions genuinely useful to the people who maintain the projects.

Open-source hardware and EDA projects are built by people spread across the world, many of them volunteers, and anyone with an internet connection can join. For a student in India this is one of the best ways to learn from experienced engineers, build a visible track record and work on real tools and designs. But open-source communities can feel opaque from outside: where do people actually talk, and how do you contribute without wasting a maintainer's time? This article answers both.

What the community looks like

"Open-source hardware" covers several overlapping groups, each with its own projects and habits:

  • Open EDA tools: simulators, synthesis, place-and-route, layout and verification tools such as Yosys, Verilator, Icarus Verilog, OpenROAD, LibreLane, Magic, KLayout, Netgen and cocotb
  • Open PDKs: process kits such as sky130, gf180 and IHP SG13G2, and the communities designing on them
  • Open processor cores and IP: RISC-V cores, peripherals and SoC frameworks
  • Shared tape-out communities: projects that combine many small designs onto one chip, such as Tiny Tapeout
  • Open boards and firmware: board designs in KiCad, and firmware projects such as Zephyr
  • Foundations and standards groups: organisations that support open-source silicon and open instruction sets, such as the FOSSi Foundation and RISC-V International

You do not have to pick one forever, but picking one to start keeps your learning focused.

Where people gather

Each project usually has a few places where real work happens:

Place What happens there How to start
Code repository Issues, pull requests, design discussions Read open issues and the contributing guide
Chat server or channel Quick questions, help, coordination Read the channel history before asking
Mailing list or forum Longer discussions, announcements Subscribe and read for a while
Meet-ups, workshops, conferences Talks, tutorials, meeting people in person Attend local events, online sessions or recordings

Many projects link to their chat, forum and contributing guide from the README. Start there rather than searching widely. Local and college groups, open-source clubs and online study circles can also be a good way in, especially if you find people working on the same project.

Ask good questions

A large part of joining is asking questions in a way people want to answer:

  • Search first: the documentation, the issue tracker and the chat history often already have the answer
  • Give context: what you are trying to do, what you ran, the exact error, tool and PDK versions and your operating system
  • Make it reproducible: a minimal example that shows the problem is worth more than a long description
  • Be patient and polite: maintainers are often volunteers in different time zones
  • Close the loop: when you solve it, say how, so the next person can find it

Asking a clear question in public, rather than messaging a maintainer privately, also helps everyone who has the same problem later.

Contribute usefully

Your first contribution does not need to be a new feature. In fact it usually should not be. Useful first contributions include:

  1. Reproducing bug reports: confirm an issue on your setup, or show it no longer happens on the latest version
  2. Improving documentation: fix an unclear installation step you just struggled with; you are the best person to spot it
  3. Adding tests or examples: a small example design or a test that covers an untested case
  4. Fixing a small bug: many projects label beginner-friendly issues
  5. Reviewing: testing someone else's pull request and reporting what you found

Before writing code, read the contributing guide, check the licence, follow the project's coding style, and say on the issue that you are working on it so effort is not duplicated. Keep pull requests small and focused; a single clear change gets reviewed quickly, while a large one may sit for weeks.

If you use AI tools to help write a contribution, understand and test every line before submitting it, and follow the project's policy on such tools if it has one. Maintainers spend real time reviewing; sending them code you cannot explain costs them more than it helps.

Turning participation into learning

Contributing teaches skills that classes rarely do: reading a large unfamiliar codebase, writing code others will maintain, accepting review, and explaining technical choices in writing. It also leaves a public record. Your merged pull requests, issue reports and discussions show an employer how you work, not just what you know.

Over time, take on more: own a small area of documentation, help newcomers in the chat, give a short talk at a local meet-up about what you learned, or submit a design to a shared tape-out and document it openly. Communities grow because people who were helped go on to help others.

Common mistakes

  • Asking "can anyone help?" without saying what the problem is
  • Opening a large pull request before discussing it on an issue
  • Messaging maintainers privately for help with public questions
  • Submitting changes without running the project's tests
  • Giving up after the first review comment instead of addressing it

Try it yourself

  1. Pick one project, such as Yosys, cocotb or KLayout, read its contributing guide and browse its open issues for a week.
  2. Install it from source, following the documentation exactly, and note every step that confused you; turn one into a documentation fix.
  3. Reproduce one open bug report and add your findings to the issue, with versions and a minimal example.
