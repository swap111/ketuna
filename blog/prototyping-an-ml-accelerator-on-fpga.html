Prototyping a small ML accelerator on an FPGA

Edge AI Advanced 27 Nov 2026 6 min read By Ketuna

Build a MAC-lane array with on-chip buffers, attach it to a soft RISC-V core as a memory-mapped peripheral, and measure real end-to-end throughput with cycle counters, which is where the data-movement surprises appear.

In this article
  1. The system to build
  2. Verify before you measure
  3. Measuring real throughput

Simulation tells you an accelerator computes the right numbers. It rarely tells you how fast the whole system runs, because the interesting delays live outside the MAC array: the processor configuring registers, data crossing a bus, a driver waiting on a status bit. An FPGA prototype puts the accelerator next to a real processor running real firmware, at real (if not final) clock speeds, for millions of inferences instead of a few simulated ones. For a small edge accelerator this is the cheapest way to find out whether the design you plan to tape out actually delivers its speed-up end to end.

The system to build

Keep the first prototype small and complete rather than large and partial:

  • A soft RISC-V core running bare-metal firmware from block RAM. Open-source cores and SoC generators make this a configuration task rather than a design task; pick one whose bus your accelerator can attach to simply.
  • The accelerator as a memory-mapped peripheral: a register block for control and status, plus three on-chip buffers for inputs, weights and outputs, built from the FPGA's block RAM.
  • A MAC-lane array, for example 8 lanes computing 8 output neurons in parallel from a broadcast input, each lane an 8 × 8-bit multiplier feeding a 24- or 32-bit accumulator, mapped onto the FPGA's hard multiplier blocks.
  • A requantization stage at the array output (multiply by M0, rounding shift, add zero point, clamp) so results go back to the output buffer already in int8.
  • Counters: a free-running cycle counter in the core, and a busy-cycle counter in the accelerator.

A minimal register map might look like this:

Offset Register Purpose
0x00 CTRL bit 0 START, bit 1 RELU
0x04 STATUS bit 0 DONE, bit 1 OVERFLOW (sticky)
0x08 DIMS inputs in [15:0], outputs in [31:16]
0x0C QPARAM M0 multiplier
0x10 SHIFT_ZP shift in [5:0], output zero point in [15:8]
0x14 BUSY_CYCLES cycles the array was busy in the last job

Write the firmware driver against this map before the RTL is final. Awkward sequences or race conditions in the interface show up as awkward driver code, and they are cheap to fix at this stage.

#include <stdint.h>

#define ACC_BASE   0x40000000u
#define REG(off)   (*(volatile uint32_t *)(ACC_BASE + (off)))

uint32_t run_dense(uint16_t n_in, uint16_t n_out, uint32_t m0,
                   uint8_t shift, int8_t zp, int relu)
{
    REG(0x08) = ((uint32_t)n_out << 16) | n_in;
    REG(0x0C) = m0;
    REG(0x10) = ((uint32_t)(uint8_t)zp << 8) | (shift & 0x3Fu);
    REG(0x00) = 1u | (relu ? 2u : 0u);        /* start */
    while ((REG(0x04) & 1u) == 0)             /* wait for DONE */
        ;
    return REG(0x14);                         /* busy cycles */
}

Polling is fine for the first measurements; an interrupt with the core sleeping comes later, once the numbers are understood.

Verify before you measure

Bring the same golden model to the FPGA that you used in simulation. The firmware loads test vectors generated by the Python integer reference, runs the accelerator, and compares every output byte, reporting mismatches over a UART. Run this for many random layers and the corner cases, on the board, before trusting any throughput number. A fast wrong answer is not a result.

The FPGA also catches things simulation misses: a buffer address that wraps on the largest layer, a status bit read one cycle too early, a timing path that fails at the FPGA clock so the array occasionally computes garbage. If results are wrong only on hardware, check the timing report of the FPGA build before debugging the logic.

Measuring real throughput

Take a dense layer of 256 inputs and 64 outputs: 16,384 MACs. With 8 lanes, the ideal is 16,384 / 8 = 2,048 busy cycles. Suppose the accelerator's own counter reports 2,304, because each of the 64 / 8 = 8 passes spends about 32 cycles on pipeline fill, bias load and requantization. Array utilisation is 16,384 / (8 × 2,304) ≈ 89 %. So far, so good.

Now read the core's cycle counter around the whole operation, including the firmware copying 16,384 weight bytes into the weight buffer. The numbers in this example are illustrative, of the kind your own counters will produce. If the copy runs as 4,096 word stores at about 3 cycles each, that is 12,288 cycles, plus around 200 cycles of configuration and polling. End to end: 12,288 + 2,304 + 200 = 14,792 cycles, about 1.1 MACs per cycle against a peak of 8.

Compare with software on the same core at, say, 4 cycles per MAC (loads, multiply-accumulate, loop overhead): 65,536 cycles. The kernel alone is about 28 times faster than software, but end to end the speed-up is only about 4.4 times. The weight copy, not the MAC array, dominates. This is the most common lesson of a first accelerator prototype, and it is invisible in a testbench that preloads the buffers.

The fixes are architectural, which is exactly why you want to find this before tape-out:

  • Keep weights resident. If the buffers can hold the model's weights, load them once at start-up; per inference only the input moves. In this example that removes 12,288 cycles per call, and the end-to-end speed-up approaches the kernel's.
  • Let the accelerator fetch its own data through a bus master port or a DMA engine, so the core is not the copy engine.
  • Batch work per start: run several layers from one configuration, so the fixed cost of configuring and polling is paid once.

What carries over to silicon, and what does not

Cycle counts, utilisation, the balance between compute and data movement, and the correctness of the driver all transfer from the FPGA to an ASIC implementation of the same RTL. Absolute clock frequency, power and area do not: an FPGA implements logic in lookup tables and routing that behave very differently from standard cells. Report FPGA results in cycles and ratios, and use ASIC synthesis and static timing analysis for frequency and power estimates.

Common mistakes:

  • measuring only the accelerator's busy cycles and calling it the speed-up
  • trusting throughput before the on-board bit-exact check passes
  • ignoring FPGA timing failures that cause intermittent wrong results
  • quoting FPGA clock frequency or power as a prediction for the chip
  • designing the register map without writing the driver

Try it yourself

  1. Build a small RISC-V SoC with an open-source SoC generator, synthesise it with Yosys and place and route it with nextpnr for an FPGA board that the open-source flow supports, and run a "hello" program over UART.
  2. Add a memory-mapped register block with a cycle counter and read it from firmware.
  3. Add a 4- or 8-lane MAC array with block-RAM buffers, verify it against the Python reference first in Verilator and then on the board.
  4. Measure kernel-only and end-to-end cycles for a dense layer, then move the weights to load once at start-up and measure again.
