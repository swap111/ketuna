Reading a spec like a bug hunter: looking for what it does not say

Verification Beginner 27 Nov 2026 6 min read By Ketuna

Many hardware bugs start as gaps in the specification. Learn a repeatable way to read a spec for ambiguities, unstated corner cases and missing error behaviour, using a short watchdog timer description as the example.

In this article
  1. A short spec to practise on
  2. Five hunts through the same paragraph
  3. Turning the hunt into questions
  4. Habits that make the hunt routine
  5. Try it yourself

When a verification engineer and a designer read the same specification, they often come away with two slightly different designs in their heads. Neither is wrong; the spec simply did not say. Those differences become bugs, or worse, become arguments after silicon about whose reading was correct. The cheapest time to find them is before any RTL or testbench exists, by reading the spec with one question in mind: what happens in the cases it does not mention?

A short spec to practise on

Here is a description of a watchdog timer, written the way many first-draft specs are written.

The watchdog has a 16-bit down-counter clocked by the system clock. Software enables it by setting WDT_CTRL.EN. Writing the value 0xA5 to WDT_KICK reloads the counter from WDT_LOAD. If the counter reaches zero, the watchdog asserts wdt_reset to reset the chip. WDT_LOAD resets to 0xFFFF.

It reads clearly. Now read it again, hunting.

Five hunts through the same paragraph

Hunt 1: boundaries and special values

Every number in a spec has edges, and edges are where designs break.

  • What does WDT_LOAD = 0 do? Reset immediately on the next kick? Never? Is it even allowed?
  • What does WDT_LOAD = 1 do? Is there time for software to react at all?
  • "Reaches zero": is wdt_reset asserted on the cycle the counter becomes 0, or when it would go below 0? That is a one-cycle difference, and the designer and verifier will each pick one.

Hunt 2: simultaneous events

Specs describe events one at a time. Hardware experiences them all at once.

  • What if a kick arrives on the same cycle the counter reaches zero? Does the kick save the chip, or is it too late?
  • What if software writes WDT_LOAD and kicks in back-to-back cycles? Does the kick use the old or new value?
  • What if EN is cleared on the same cycle the counter reaches zero?

These are exactly the questions a random testbench will eventually stumble into. Better to have the answer written down before it does.

Hunt 3: wrong or unexpected inputs

Specs usually describe correct use. Bugs live in incorrect use.

  • What does writing any value other than 0xA5 to WDT_KICK do? Nothing? Count as a fault and reset at once? Many watchdog designs treat a wrong key as a sign of runaway software, so this is a real design decision, not a detail.
  • What does reading WDT_KICK return?
  • Can WDT_LOAD be changed while the watchdog is enabled? If so, does the change take effect immediately or at the next kick?
  • Can software disable the watchdog once enabled? If it can, runaway software can disable it too, which defeats its purpose.

Hunt 4: reset, power-up and what happens after

  • What is the reset value of WDT_CTRL.EN? The spec gives WDT_LOAD's reset value but not the enable's.
  • Is the counter's value defined before the first kick? Does enabling load the counter from WDT_LOAD, or does it start from whatever value it holds?
  • wdt_reset resets the chip. Does it reset the watchdog itself? If not, the watchdog may fire again immediately after reset. If so, software cannot tell afterwards that a watchdog reset occurred, unless there is a status flag that survives. The spec does not mention one.
  • How long is wdt_reset asserted? One cycle may be too short for the reset controller.

Hunt 5: things the spec assumes you know

  • "Clocked by the system clock": does the counter keep running when the processor is halted by a debugger? Many watchdogs pause in debug mode, because otherwise a breakpoint resets the chip.
  • What about low-power modes where the system clock stops?
  • Is any register write-protected, and if so, how is protection unlocked?

Turning the hunt into questions

You now have around twenty questions from five sentences. That is normal. Write them as a numbered list addressed to the spec owner, each phrased so that it has a definite answer:

# Question Why it matters
Q1 Is wdt_reset asserted when the counter becomes 0, or one cycle later? Defines the exact check
Q2 Does a kick on the cycle the counter reaches 0 prevent the reset? Simultaneous-event behaviour
Q3 What does a write of a value other than 0xA5 to WDT_KICK do? Error behaviour
Q4 What is the reset value of WDT_CTRL.EN? Missing reset value
Q5 Does the counter run while the core is halted in debug? Unstated mode behaviour
Q6 Is there a status flag that records a watchdog reset? Observability after reset

Bring the list to a short review with the designer and the spec author. Some questions will be answered in a sentence; some will reveal that nobody had decided; a few may turn into design changes. Every answer goes back into the spec, so the next reader gets it for free, and each answer becomes a numbered item in the verification plan with a check and a coverage goal.

Habits that make the hunt routine

  • Read once for understanding, once for gaps. Hunting on the first read is hard because you are still learning what the block does.
  • For every "when X, do Y", ask about "when not X" and "when X and Z together".
  • For every number, ask about zero, one, the maximum and one past it.
  • For every register, ask about reset value, access type, and what happens on writes and reads of unexpected values.
  • For every output, ask how long it lasts and what resets it.

You can ask an AI assistant to suggest further questions once you have done your own pass. Treat its suggestions as a checklist to consider against the spec, not as answers, since it has no more knowledge of the designer's intent than the spec gives it.

Try it yourself

  1. Take the watchdog paragraph above and write your own list of questions before rereading the hunts; compare how many you found.
  2. Pick a peripheral from an open-source microcontroller or SoC project and read its documentation with the five hunts, writing down every question.
  3. Answer what you can from that project's RTL, and note where the RTL had to make a choice the documentation did not state.
  4. Write a cocotb test with Icarus Verilog that pins down one of those choices, so that a future change to the behaviour is noticed.
