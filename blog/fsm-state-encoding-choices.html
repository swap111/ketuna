Binary, one-hot or Gray: how state encoding changes area, speed and safety

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

State encoding decides how many flops an FSM uses, how deep its next-state logic is and what happens after an upset. Compare binary, one-hot and Gray, and learn to recover from illegal states.

In this article
  1. The three common encodings
  2. What each encoding does to the logic
  3. What synthesis does with your choice
  4. Illegal states and how to recover
  5. Choosing an encoding
  6. Try it yourself

When you write typedef enum {IDLE, LOAD, RUN, DONE}, you have described the behaviour of a state machine but not its hardware. Someone still has to decide which bit pattern stands for each state. That choice, the state encoding, changes the flip-flop count, the depth of the next-state logic, the glitchiness of decoded outputs and, less obviously, what the machine does when a bit flips that should not have.

The three common encodings

For a machine with N states:

Encoding Flops Patterns for 8 states
Binary ⌈log2 N⌉ 000, 001, 010 … 111
Gray ⌈log2 N⌉ 000, 001, 011, 010, 110 …
One-hot N 00000001, 00000010 …

Binary uses the fewest flops. The cost is in logic: to decide "am I in state 5?" you must decode all three bits, and the next-state equation for each bit can depend on every state bit and every input.

One-hot uses one flop per state, exactly one of which is 1. "Am I in state 5?" is a single wire. The next-state logic for each flop only has to OR together the conditions that lead into that state, which is usually shallow. So one-hot trades flops for speed, and on architectures rich in flip-flops, such as FPGAs, it is often the default.

Gray also uses the minimum number of flops, but assigns codes so that the transitions you take most often change only one bit. For a machine that mostly walks through states in sequence, like a counter or a pointer, that means one bit changes per step.

What each encoding does to the logic

Consider a four-state controller IDLE → LOAD → RUN → DONE → IDLE, with an output busy that is high in LOAD and RUN.

  • Binary (00, 01, 10, 11): busy = s[1] ^ s[0]. Going from LOAD (01) to RUN (10) changes both bits. If one flop switches slightly before the other, the state momentarily looks like 00 or 11, and the XOR can glitch low for a moment.
  • Gray (00, 01, 11, 10): busy = s[0]. Every step in the sequence changes one bit, so the decoded output changes cleanly.
  • One-hot (0001, 0010, 0100, 1000): busy = s[1] | s[2]. Going from LOAD to RUN clears one bit and sets another, so a short glitch is possible on the OR only if the timing is very unbalanced; in practice the output logic is small and fast.

Gray's advantage is real but narrow. It matters most when a state value is used asynchronously, sampled in another clock domain, or decoded into an output that must not glitch. For most internal FSMs whose outputs are sampled by flops in the same domain, glitches do not matter and the comparison is mostly about area and speed.

What synthesis does with your choice

Most synthesis tools have an FSM extraction step. They recognise a state register with a known set of values, and may re-encode it, often to one-hot or to a heuristic choice, unless you tell them otherwise. Two consequences:

  • The encoding in your RTL may not be the encoding in the netlist. Read the synthesis log; tools typically report the FSMs they found and the encoding they chose.
  • If you rely on a specific encoding, for example because a state bit is used as an output or crosses clock domains, you must stop the tool re-encoding it, using the attribute or option your tool provides, and check the netlist.

In open-source flows, Yosys has an fsm pass that extracts and can re-encode state machines; running synth includes it, and the log shows what it did.

Illegal states and how to recover

A 4-state binary machine has no unused patterns. A 5-state binary machine has three. A 4-state one-hot machine has twelve: every pattern with zero bits set or more than one bit set is illegal. You reach an illegal state through a radiation-induced upset, a supply glitch, a reset that releases unevenly, or a timing violation.

What happens next depends on the logic:

  • In binary, the illegal codes go wherever the minimised next-state logic happens to send them. The machine may recover or may lock up in a loop of unused states.
  • In one-hot, an all-zero state is a dead end: every next-state term needs some current-state bit to be 1, so nothing ever becomes 1 again. Two bits set at once can make two "branches" run in parallel.

The intended fix is a default branch that returns to a safe state:

always_comb begin
  nx = IDLE;                 // safe default
  case (st)
    IDLE: if (start) nx = LOAD;
    LOAD:            nx = RUN;
    RUN:  if (last)  nx = DONE; else nx = RUN;
    DONE:            nx = IDLE;
    default:         nx = IDLE;
  endcase
end

There is a catch. Synthesis knows the enum has only four legal values, so it may treat default as unreachable and remove the recovery logic entirely, especially after re-encoding. If recovery from illegal states is a requirement, ask for it explicitly with your tool's "safe FSM" option or attribute, or code the state register as a plain vector so the tool cannot assume which values occur. Then verify it: force an illegal value in simulation, or prove recovery with a formal tool.

For one-hot designs, a common hardware check is that exactly one bit is set ($onehot(st) in a SystemVerilog assertion), with an error flag or a reset of the machine if it fails.

Choosing an encoding

  • Small FSM, sampled outputs, ASIC: binary or let the tool choose
  • Speed-critical FSM, many states: one-hot
  • State value used across clock domains, or outputs that must not glitch: Gray, or registered outputs
  • Must recover from upsets: any encoding, plus explicit safe recovery that you have verified survives synthesis

Try it yourself

  1. Write the four-state controller as an enum and synthesise it with Yosys (yosys -p "read_verilog -sv fsm.sv; synth -top ctrl; stat"). Find the FSM messages in the log and see which encoding was chosen.
  2. Repeat with synth -top ctrl -nofsm and compare cell counts.
  3. In an Icarus Verilog testbench, force the state register to an illegal value with force and release, and check whether the machine returns to IDLE.
