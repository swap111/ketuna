Accumulator width in quantized inference: avoiding overflow

Edge AI Advanced 27 Nov 2026 6 min read By Ketuna

How many int8 products a 32-bit accumulator can safely sum, how to bound the real requirement per layer from its weights, why wrapping beats saturating mid-sum, and what hardware does when the bits run out.

In this article
  1. The worst case for raw int8 products
  2. Zero points change the operand range
  3. Bounding the real requirement per layer
  4. Wrapping is harmless; saturating mid-sum is not
  5. What hardware does when the bits run out
  6. Try it yourself

An int8 multiply produces a 16-bit result, and a dot product adds hundreds or thousands of them. The accumulator that holds the running sum therefore needs many more bits than the operands, and every extra bit costs area and energy in each of the hundreds of MAC units an accelerator might have. Too few bits and the sum wraps or clips on some inputs, usually rare ones that the test set never exercised. Too many and you waste silicon in every lane. Sizing the accumulator is a short calculation, but it has subtleties that are easy to get wrong.

The worst case for raw int8 products

For signed int8 operands in [−128, 127], the extreme products are (−128) × (−128) = 16,384 = 214 and (−128) × 127 = −16,256. So every product fits in [−16,256, 16,384], and a sum of N products lies in [−16,256 N, 16,384 N].

The signed bits needed for the sum are the bits for the largest magnitude plus a sign bit. For N = 64, the largest possible sum is 64 × 214 = 220 = 1,048,576. A 21-bit signed number tops out at 220 − 1, one short, so the accumulator needs 22 bits. In general, about 16 + log2(N) bits, rounded up, with care at exact powers of two.

For a 32-bit accumulator, the number of worst-case products that always fit is ⌊(231 − 1) / 16,384⌋ = 131,071.

Zero points change the operand range

The usual int8 scheme does not multiply raw inputs. It multiplies (x − zx) by the weight, where zx is the input zero point. With zx anywhere in [−128, 127], the difference ranges over [−255, 255]: a 9-bit quantity. Weights are usually symmetric, often restricted to [−127, 127].

Now the largest product magnitude is 255 × 127 = 32,385, or 255 × 128 = 32,640 if −128 weights are allowed, roughly twice the raw case. The safe count for int32 halves to ⌊(231 − 1) / 32,640⌋ = 65,793 products, before leaving room for the bias.

That is still large. A 3 × 3 convolution over 256 input channels sums 2,304 products, and even at the absolute worst case, 2,304 × 255 × 127 = 74,615,040, which needs 28 signed bits. So for int8 networks of ordinary size, int32 accumulation does not overflow, which is why software kernels simply use int32_t. The question becomes real in two situations: hardware that wants a narrower accumulator to save area, and wider operands. With 16-bit activations and 8-bit weights, each product can reach 222 in magnitude, and int32 is guaranteed safe for only ⌊(231 − 1) / (32,768 × 128)⌋ = 511 products. That is why 16-bit activation schemes commonly use wider accumulators.

Bounding the real requirement per layer

The worst case above assumes every weight is at its extreme with the same sign, which never happens in a trained model. Since the weights are known constants after training, you can compute the exact worst case for each output channel: for each weight, pick the input extreme that maximises (or minimises) its product, and sum.

import numpy as np

def acc_bits_needed(w, b, zx):
    """Worst-case signed accumulator bits for each output row of int8 w."""
    w = w.astype(np.int64)
    hi_in, lo_in = 127 - zx, -128 - zx          # range of x - zx
    hi = np.maximum(w * hi_in, w * lo_in).sum(axis=1) + b
    lo = np.minimum(w * hi_in, w * lo_in).sum(axis=1) + b
    bits = lambda v: int(v).bit_length() + 1    # including sign
    return [max(bits(h), bits(-l - 1) if l < 0 else 1)
            for h, l in zip(hi, lo)]

rng = np.random.default_rng(0)
w = rng.integers(-127, 128, (4, 2304), dtype=np.int8)  # 3x3x256 conv
print(acc_bits_needed(w, np.zeros(4, np.int64), zx=-128))
# [26, 26, 26, 26]

With uniformly random weights, roughly half positive and half negative, the bound for this layer is 26 bits instead of 28. Trained weights, which cluster near zero, usually give tighter bounds still. This bound is a guarantee, not a statistical estimate: no input can exceed it. Run it over every layer of the model you plan to deploy, and you know whether a 24-bit accumulator is safe for that model. The catch is that the answer belongs to that model; a retrained or different model must be checked again, so a design that relies on it needs the check built into the deployment flow and a defined behaviour when it fails.

Wrapping is harmless; saturating mid-sum is not

Here is the subtle part. Two's-complement addition is arithmetic modulo 2n. If the final sum fits in n bits, it comes out correct even if intermediate partial sums overflowed and wrapped along the way, because modular addition does not care about order. For example, in 32 bits, 230 + 230 wraps to −231, but adding −230 and then −230 + 5 brings it back to exactly 5.

A saturating accumulator breaks this. Once it clips at its maximum, the information is lost, and later negative products pull it down from the wrong place. So:

  • if the final-sum bound fits, a plain wrapping accumulator gives exact results regardless of the order of products
  • saturation belongs at the end, in the requantization and clamp to int8, not inside the MAC loop
  • the bound to check is on the final sum (plus bias), not on every partial sum

In C, signed integer overflow is undefined behaviour, so do not rely on wrapping with int32_t; either prove no overflow, as above, or accumulate in uint32_t and convert at the end. In RTL, a plain adder of the chosen width wraps naturally.

What hardware does when the bits run out

When the bound says a layer needs more bits than the lanes have, there are a few standard options:

  • Size for the worst case of the layers you must support. Simple and safe; costs area in every lane.
  • Split the reduction. Accumulate chunks of K in the narrow lane accumulator, each chunk short enough to be safe, and add the chunk results in a wider accumulator shared at the array edge or in a wider memory. This is natural for tiled accelerators anyway.
  • Detect and flag. Keep a sticky overflow bit per lane that firmware checks after each layer. It does not fix the result, but it turns a silent error into a visible one during bring-up and testing.
  • Constrain training. Some flows limit weight ranges so that a narrower accumulator is provably safe for every model the training produces. The bound computation above is still how you prove it.

Common mistakes:

  • sizing the accumulator for 8-bit operands and forgetting that (x − zx) is 9 bits
  • testing overflow with random data, which almost never approaches the bound
  • saturating inside the accumulation loop
  • relying on signed overflow wrapping in C
  • checking one model's bound and assuming it holds for the next version

Try it yourself

  1. Run acc_bits_needed on the weights of every layer of a small trained int8 model and find the layer that needs the most bits.
  2. Construct the input that achieves the bound for one output channel (each input at whichever extreme matches its weight's sign) and confirm the sum equals the computed maximum.
  3. Simulate a 20-bit wrapping accumulator and a 20-bit saturating one in numpy on a sum whose partial values exceed the range but whose final value fits, and compare.
  4. Write a Verilog MAC lane with a parameterized accumulator width and a sticky overflow flag, and test it with the worst-case input from step 2.
