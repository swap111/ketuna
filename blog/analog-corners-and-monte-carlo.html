Simulating an analog block across corners and with Monte Carlo

Analog & mixed-signal Intermediate 27 Nov 2026 6 min read By Ketuna

One typical simulation proves little. Learn what process corners and Monte Carlo each model, script a PVT sweep around ngspice, and read a Monte Carlo spread as margin and confidence rather than one number.

The first simulation of a new analog block uses typical models at room temperature and nominal supply, and it usually looks good. Then the chip is made, and every die is a little different: transistors a bit faster or slower, the supply a little low, the die hot. An analog design is only finished when it works across all of that. Two tools cover it: corner simulation for the systematic shifts that move every transistor on a die together, and Monte Carlo for the random differences between neighbouring transistors. They answer different questions, and confusing them is a common way to sign off a design that fails.

Corners: the whole die shifts together

Process variation between wafers and between dies moves parameters such as threshold voltage, oxide thickness and mobility. On any one die, all NMOS transistors shift roughly together, and all PMOS transistors shift roughly together, though not necessarily in the same direction as the NMOS. PDKs capture this as named process corners, each a set of model parameters representing a plausible extreme:

  • TT: typical NMOS, typical PMOS
  • FF and SS: both fast, or both slow
  • FS and SF: fast NMOS with slow PMOS, and the reverse

Add voltage, typically nominal ±10 %, and temperature, for example −40 °C to 125 °C for an industrial part, and you have a PVT grid. Five process corners, three voltages and three temperatures already make 45 simulations.

Which corner is worst depends on the circuit and the specification. Gain and output swing usually suffer at slow corners and low supply, where overdrive and headroom are smallest. Bandwidth and power consumption are worst at opposite corners. Anything that depends on the balance between NMOS and PMOS, such as an inverter's switching point or a ring oscillator's duty cycle, is worst at the skewed corners FS and SF. So run them all; do not guess.

Scripting a PVT sweep

ngspice selects the corner through the section name on the .lib line. A short Python driver that writes a netlist per point, runs ngspice in batch mode and parses a .meas result makes the sweep painless. This one measures an inverter's switching point as a fraction of the supply:

import re
import subprocess

LIB = "sky130A/libs.tech/ngspice/sky130.lib.spice"   # adjust to your install

NETLIST = """* inverter switching point at one PVT point
.lib "{lib}" {corner}
.temp {temp}
VDD vdd 0 {vdd}
VIN in 0 0
XMP out in vdd vdd sky130_fd_pr__pfet_01v8 W=2 L=0.15
XMN out in 0 0 sky130_fd_pr__nfet_01v8 W=1 L=0.15
.dc VIN 0 {vdd} 0.002
.meas dc vm when v(out)=v(in)
.end
"""

def switching_point(corner, temp, vdd):
    with open("pvt.spice", "w") as f:
        f.write(NETLIST.format(lib=LIB, corner=corner, temp=temp, vdd=vdd))
    out = subprocess.run(["ngspice", "-b", "pvt.spice"],
                         capture_output=True, text=True).stdout
    m = re.search(r"^vm\s*=\s*([-+0-9.eE]+)", out, flags=re.M)
    return float(m.group(1)) if m else None

for corner in ("tt", "ss", "ff", "sf", "fs"):
    for temp in (-40, 27, 125):
        for vdd in (1.62, 1.80, 1.98):
            vm = switching_point(corner, temp, vdd)
            if vm is None:
                print(f"{corner} {temp} {vdd}: no result, check the log")
                continue
            print(f"{corner} {temp:>4} C {vdd:.2f} V  VM/VDD = {vm/vdd:.3f}")

Collect the results in a table and look at the extremes and at which corner produced them. If the worst case surprises you, that is useful: it usually points to a device you thought was saturated and is not.

Monte Carlo: neighbours that differ

Corners assume that two identical transistors on the same die are identical. They are not. Random dopant fluctuation and edge roughness give every transistor its own small threshold and current-factor offset, and these do not cancel in circuits that rely on matching: differential pairs, current mirrors, comparators, bandgaps. A comparator's input offset, for example, is zero at every corner, because a corner shifts both input transistors equally. Only a mismatch simulation shows it.

Monte Carlo simulation runs the circuit many times, each time drawing random parameters for every device from the distributions in the PDK's statistical models. PDKs that support it provide a statistical section of the model library, often with separate options for global (die-to-die) variation, local mismatch, or both; check your PDK's documentation for the names. ngspice can repeat a run in a .control loop, or you can drive it from Python as above, collecting one measurement per run.

Reading the spread

A Monte Carlo run gives a cloud of results, not one number. Reduce it to a few honest statements.

  • Mean and standard deviation. The mean shows any systematic offset, for example from asymmetric layout. The standard deviation σ is the random spread.
  • Margin in sigma. Divide the distance from the mean to the nearer specification limit by σ. Three sigma, if the distribution is Gaussian, corresponds to roughly one failure in several hundred; many teams target more.
  • Failures and confidence. Zero failures in n runs does not mean zero failures in production. A standard rule of thumb says that with zero failures in n independent trials, you can claim the failure rate is below about 3/n with 95 % confidence. With 200 runs that is 1.5 %: far too weak to prove a high yield by counting alone, which is why the sigma margin is used.
  • The estimate itself is uncertain. The standard deviation from n samples has a relative uncertainty of roughly 1/√(2(n − 1)), about 7 % for 100 runs. A margin of 3.1σ from 100 runs is not clearly better than 3.0σ.

A helper makes these statements routine. The samples here are random stand-ins drawn with a mean of 0.2 mV and σ of 1.5 mV, made up for illustration:

import numpy as np

def summarise(samples, lo, hi):
    """Report spread and margin of Monte Carlo results against a spec."""
    x = np.asarray(samples)
    mu, sd = x.mean(), x.std(ddof=1)
    fails = np.count_nonzero((x < lo) | (x > hi))
    k = min(hi - mu, mu - lo) / sd           # distance to nearer limit
    print(f"n={len(x)}  mean={mu:+.2f}  sigma={sd:.2f}  "
          f"margin={k:.1f} sigma  fails={fails}")
    if fails == 0:
        print(f"fail rate below {3/len(x):.1%} (95 % confidence)")

# Stand-in for 200 simulated comparator offsets in mV (made up).
rng = np.random.default_rng(1)
summarise(rng.normal(0.2, 1.5, 200), lo=-5.0, hi=5.0)

Note that the sample estimates (mean 0.09 mV, σ 1.39 mV) differ from the values used to generate them. That gap is exactly the sampling uncertainty described above.

Pitfalls

  • Running Monte Carlo only at TT. Mismatch and corners combine. Run Monte Carlo at the worst corners too, or at least check that the σ does not grow there.
  • Including global variation twice. If you run corners and a Monte Carlo that also varies global parameters, you may double-count. Know what each model section varies.
  • Plotting a histogram and stopping. Look for outliers and bimodal shapes; a second cluster often means a start-up or bias problem, not mismatch.
  • Forgetting layout. Schematic Monte Carlo ignores gradients and parasitics; repeat key checks on the extracted netlist.

Try it yourself

  1. Install ngspice and the sky130 PDK, fix the LIB path, and run the PVT sweep. Identify the corner with the lowest and highest switching point and explain why.
  2. Find the statistical or mismatch sections in your PDK's ngspice model library, and run 100 Monte Carlo iterations of a five-transistor differential amplifier, measuring input offset.
  3. Feed the offsets to summarise, then rerun with the input pair four times larger in area and check that σ roughly halves.
