Clock tree synthesis: skew, latency and why zero skew is not the goal

Physical design & tape-out Advanced 27 Nov 2026 5 min read By Ketuna

Clock tree synthesis balances arrival times across thousands of flops, but chasing zero skew wastes power and can hurt timing. Learn how latency and skew trade off and how useful skew fixes a critical path.

In this article
  1. Latency, skew and what each costs
  2. Why zero global skew is the wrong target
  3. Useful skew: borrowing time between stages
  4. The limits of useful skew
  5. Try it yourself

Textbooks often present clock tree synthesis (CTS) as a balancing exercise: deliver the clock edge to every flip-flop at the same instant. That is a good starting point and a poor final goal. Skew is a tool as well as a defect, and the effort spent driving it to zero costs buffers, power and insertion delay that may buy nothing. This article treats CTS as a set of trade-offs between latency, skew, power and on-chip variation, and then shows how deliberate skew rescues a critical path.

Latency, skew and what each costs

Two quantities describe a built clock tree:

  • Insertion delay (latency): the time from the clock root to a flop's clock pin. A tree serving tens of thousands of sinks needs several levels of buffering, so latency is typically many buffer delays.
  • Skew: the difference in latency between two flops. Global skew is the spread across all sinks; local skew is the difference between flops that actually share a timing path. Only local skew enters timing checks.

Large latency is not directly harmful for paths inside one clock tree, because launch and capture both carry it. It matters in three indirect ways. First, on-chip variation: every buffer's delay varies a little with local process, voltage and temperature, and sign-off tools derate the launch and capture paths differently. The longer the non-shared part of the two clock paths, the more pessimism they add. Second, I/O timing: an input port's data arrives relative to the clock at the pin, but the capturing flop sees the clock a full insertion delay later, which shifts the input budget. Third, power: the clock net switches every cycle, so every buffer in the tree burns dynamic power continuously.

This is why good CTS keeps flops that talk to each other on shared branches for as long as possible. Common path pessimism removal (CPPR) gives back the derating on the shared part, but only the shared part.

Why zero global skew is the wrong target

Forcing every sink in a block to the same latency means padding the short branches with buffers until they match the longest. That increases power, area and routing, and it lengthens the non-shared portion of many clock paths, which increases variation. Meanwhile, most pairs of flops in a large design never exchange data, so their skew is irrelevant.

A better specification is: keep local skew small for flops that share paths, keep total latency modest, meet transition limits on every clock net, and stop. Many CTS engines, including TritonCTS inside OpenROAD, build a tree by clustering sinks by location and then balancing, which keeps nearby flops on common branches naturally.

Useful skew: borrowing time between stages

Once the tree exists, skew can be adjusted on purpose. Consider three flops in a pipeline, A → B → C, with these illustrative setup slacks:

Path Setup slack Hold slack
A → B −0.15 ns 0.30 ns
B → C +0.40 ns 0.35 ns

Path A → B fails, and B → C has spare time. Delay the clock at flop B by 0.20 ns, for example by inserting a buffer on B's branch only.

  • A → B setup gains 0.20 ns, because B captures later: −0.15 + 0.20 = +0.05 ns.
  • B → C setup loses 0.20 ns, because B launches later: 0.40 − 0.20 = +0.20 ns.
  • A → B hold loses 0.20 ns, because the capture edge at B is now later relative to new data: 0.30 − 0.20 = +0.10 ns.
  • B → C hold gains 0.20 ns: 0.35 + 0.20 = 0.55 ns.

All four checks now pass. Nothing in the logic changed; the clock tree moved slack from a stage that had spare to one that did not. The same idea is used by optimisation engines that compute a target latency per flop and let CTS build to those targets.

The limits of useful skew

  • It must be checked at every corner. A skew that helps setup at the slow corner reduces hold margin at the fast corner. Hold is where useful skew usually breaks.
  • It cannot create time. It moves slack around a loop of paths. If a cycle of flops (A → B → A) has negative total slack, no skew assignment fixes it.
  • It interacts with variation. A deliberate buffer on one branch adds non-shared clock path, which adds derating pessimism.
  • It complicates later changes. An engineering change that touches flop B now has to respect a clock offset someone chose for a reason. Record the reason.

Try it yourself

  1. Harden a small pipelined design with LibreLane on sky130 and read the CTS report for latency and skew per clock.
  2. In OpenSTA, load the routed netlist and parasitics, then use report_clock_skew and report_checks on the worst path. Note launch and capture latencies.
  3. Model the useful-skew example with set_clock_latency on one flop's clock pin, rerun setup and hold, and confirm the slack changes match the table above.
  4. Work the numbers by hand first, then compare with the tool.
