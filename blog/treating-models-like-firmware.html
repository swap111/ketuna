Treating models like firmware: versioning, tests and CI for edge AI

Edge AI Intermediate 27 Nov 2026 5 min read By Ketuna

A deployed model is part of the firmware image and deserves the same discipline - pinned and hashed model files, regression tests on frozen held-out data, bit-exact checks of the device code, and budgets enforced in CI.

In this article
  1. Pin the model and everything that made it
  2. Three kinds of test
  3. A CI job that runs them
  4. Releasing and rolling back
  5. Try it yourself

On an edge device, the model is not a separate service that someone can quietly redeploy. It is an array of bytes compiled into the firmware, run by C code, shipped in every unit. Yet in many projects the model file arrives by chat message, gets renamed model_final2.tflite, and is dropped into the source tree without anyone being able to say which training run, which data or which quantization settings produced it. Firmware engineers already have tools for exactly this problem: version control, reproducible builds, regression tests and continuous integration (CI). Applying them to the model is mostly a matter of deciding to.

Pin the model and everything that made it

A model file is a build artefact, like a compiled library. Treat it that way:

  • Record its provenance. For every model that could ship, keep the training code commit, the dataset version, the training configuration, the quantization settings and the random seeds.
  • Identify it by content. A file name can lie; a cryptographic hash cannot. Store the SHA-256 of the exact .tflite (or equivalent) file in a small manifest committed beside the firmware.
  • Generate, never hand-edit, the C array. The header that embeds the model is produced by a script from the pinned file. If the header and the manifest disagree, the build fails.
  • Expose the version at run time. Compile the model's version string and hash into the firmware and report them over the debug console or in device telemetry, so a field report can be traced to an exact model.

A manifest can be as simple as:

model: kws_int8
version: 1.3.0
file: models/kws_int8_v1.3.0.tflite
sha256: <64 hex characters from sha256sum>
train_commit: <git commit of the training repository>
dataset: kws-data v4
input: int8 49x10, scale 0.1015, zero_point -12

The numbers in the input line are only an example of what to record: the input scale and zero point are part of the model's interface, and firmware that computes features must use exactly those values.

Three kinds of test

Model changes can break a product in different ways, and each needs its own test.

1. Accuracy regression on frozen data. Keep a held-out test set that is versioned and never used for training or tuning. For every candidate model, run the quantized model on it and check per-class results against minimum values agreed with the product team, not just overall accuracy. A new model that improves the average while losing recall on a rare but important class should fail CI.

2. Bit-exact check of the deployed code. The C code on the device must compute exactly what the integer reference computes in Python. Keep a set of input vectors with their expected int8 outputs, generated by the reference, and check that the firmware's inference code reproduces them exactly, both compiled for the host and cross-compiled for the target and run in an emulator. This catches a broken kernel, a wrong compiler flag, a mismatched feature scale or an operator missing from the resolver.

3. Resource budgets. Flash, RAM and cycles per inference are requirements. Read flash and static RAM from the build with the size tool, the arena usage from the runtime after allocation, and cycles from a cycle-accurate simulator or the target. Fail the build if any exceeds its budget. Otherwise the model grows a layer at a time until one day it no longer fits.

A CI job that runs them

Each step below is an ordinary command, so any CI system can run it. A bash script makes the order explicit:

#!/usr/bin/env bash
set -euo pipefail

# 1. The model file is the one the manifest names
expected=$(awk '/^sha256:/ {print $2}' models/manifest.yaml)
actual=$(sha256sum models/kws_int8_v1.3.0.tflite | cut -d' ' -f1)
[ "$expected" = "$actual" ] || { echo "model hash mismatch"; exit 1; }

# 2. Regenerate the C array and the reference vectors from it
python tools/gen_model_header.py models/kws_int8_v1.3.0.tflite
python tools/gen_vectors.py --out build/vectors.h

# 3. Accuracy on the frozen test set, per class
python -m pytest tests/test_accuracy.py

# 4. Bit-exact on host, then on the target CPU in an emulator
make -C firmware host-test
make -C firmware qemu-test

# 5. Budgets from the target build
python tools/check_budgets.py firmware/build/app.elf

The script names in it are your project's own; the point is the sequence. The accuracy test is ordinary pytest:

import numpy as np
from evaluate import run_int8_model   # your project's evaluation code

MIN_RECALL = {"keyword": 0.90, "unknown": 0.85, "silence": 0.95}

def test_per_class_recall():
    y_true, y_pred, names = run_int8_model("data/test_v4")
    for k, name in enumerate(names):
        mask = y_true == k
        recall = float(np.mean(y_pred[mask] == k))
        assert recall >= MIN_RECALL[name], f"{name}: {recall:.3f}"

The thresholds above are placeholders for illustration; yours come from the product's requirements and from the current model's measured performance.

Releasing and rolling back

When a model passes, it is released like firmware: a version number, a changelog entry saying what changed and why (new data, new architecture, retuned threshold), and the measured results on the frozen test set. Keep the previous model and its manifest in the repository so a rollback is a one-line change and a rebuild, not a search through someone's laptop.

Be careful with what you change at once. A firmware release that updates the feature code, the model and the decision threshold together makes it impossible to tell which one caused a field problem. Changing one thing per release, where you can, keeps cause and effect visible.

Common mistakes:

  • model files identified only by name, with no hash or provenance
  • testing the float model in CI while shipping the int8 one
  • a "test set" that has quietly been used for tuning
  • no budget checks, so flash and RAM creep up release by release
  • hand-editing the generated model header

Try it yourself

  1. Write a manifest for the model in your current project, including its SHA-256 from sha256sum, and add a build step that fails if they disagree.
  2. Generate twenty reference input and output vectors from your Python integer model and add a host test that compares your C inference code with them.
  3. Cross-compile the same test for a RISC-V target and run it under qemu-riscv32 in CI.
  4. Add a budget check that reads size output for your firmware image and fails above a limit you set.
