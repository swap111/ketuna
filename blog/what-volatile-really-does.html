What volatile really does in embedded C, and what it does not

Embedded systems Beginner 27 Nov 2026 6 min read By Ketuna

volatile tells the compiler that every read and write of a variable matters, so hardware registers and ISR flags work. It does not make an access atomic or ordered, and it is not a lock.

In this article

  2. Watching the optimiser remove your loop
  3. The rule volatile gives you

  5. Common mistakes
  6. Try it yourself

A classic first firmware bug: the code that waits for a UART byte works perfectly at -O0, then hangs forever when you switch on optimisation. Nothing is wrong with the UART. The compiler simply did what the C language allows, and the one keyword that would have stopped it, volatile, was missing. This article shows what volatile changes in the generated code, and just as importantly, the jobs people wrongly expect it to do.

The compiler assumes nobody else touches memory

An optimising compiler works on a simple model: memory changes only when this code writes to it. Under that model, reading the same address twice without a write in between must give the same value, so the second read can be skipped. Writing an address twice in a row means the first write is dead, so it can be removed. These are perfectly sensible optimisations for ordinary variables and they make programs smaller and faster.

On a microcontroller that model is wrong in two places:

  • Memory-mapped registers. A status register changes because hardware changed it. A data register may deliver a new byte on every read, and a write may start a transmission.
  • Variables shared with an interrupt. An interrupt service routine (ISR) can run between any two instructions of the main loop. From the main loop's point of view, the variable changed by itself.

Watching the optimiser remove your loop

Here is a polling loop for the receive-ready bit of a 16550-style UART on QEMU's RISC-V virt machine, written without volatile:

#include <stdint.h>
#define UART_LSR (*(uint8_t *)0x10000005u)   /* bug: no volatile */

void wait_for_byte(void)
{
    while ((UART_LSR & 1u) == 0) { }         /* wait for data ready */
}

Compiled with riscv64-unknown-elf-gcc -O2, the function loads the register once. If the bit is clear, it jumps to a label that contains nothing but a jump to itself: an infinite loop that never reads the register again. The compiler reasoned that nothing in the loop body writes UART_LSR, so its value cannot change, so checking it once is enough.

Change one word and the code is correct:

#define UART_LSR (*(volatile uint8_t *)0x10000005u)

Now the generated loop contains the load instruction inside it, and the hardware is read on every iteration.

The same thing happens to writes. Without volatile, sending two characters with UART_THR = 'O'; UART_THR = 'K'; compiles to a single store of 'K'. The compiler saw two writes to the same address and kept only the last one. With volatile, both stores are emitted, in that order.

The rule volatile gives you

Every access to a volatile object in the source becomes exactly one access in the generated code, and volatile accesses keep their order relative to each other.

That is all. The compiler must not cache the value in a register, merge accesses, invent extra ones or drop any. This is exactly what hardware registers need, and it is why every register definition in a vendor header or a driver is volatile.

For an ISR flag the pattern looks like this:

#include <stdbool.h>

static volatile bool tick;        /* written by ISR, read by main */

void timer_isr(void)
{
    /* clear the timer's interrupt source here */
    tick = true;
}

int main(void)
{
    for (;;) {
        if (tick) {
            tick = false;
            do_periodic_work();
        }
    }
}

Without volatile, the compiler may read tick once before the loop and never again.

Where you put the keyword matters with pointers. volatile uint32_t *p is a pointer to volatile data: accesses through p are kept. uint32_t *volatile p is a volatile pointer to ordinary data: the pointer variable itself is re-read, but what it points to is not. For registers you want the first form.

What volatile does not do

This is where most of the bugs live.

It does not make an operation atomic. count++ on a volatile variable still compiles to load, add, store. If an ISR also increments count between the load and the store, one increment is lost. Similarly, reading a 64-bit volatile counter on a 32-bit core takes two loads, and an interrupt between them can give you the low half of one value and the high half of another. Volatile guarantees that the two loads happen; it does not guarantee nothing happens between them. For that you need a critical section or an atomic operation.

It does not order ordinary accesses. The compiler may still move a normal (non-volatile) store past a volatile one. If an ISR fills a normal buffer and then sets a volatile ready flag, the compiler is allowed to emit the flag store first. You need a compiler barrier or C11 atomics with release and acquire ordering to keep them in order.

It does not control the hardware. On larger chips with caches, write buffers or several cores, the CPU itself can reorder or delay accesses. volatile only constrains the compiler. Hardware fences (fence on RISC-V) and cache maintenance are separate tools.

It is not a lock. Volatile says nothing about who may access a variable or when. Two tasks writing the same volatile structure still race.

Common mistakes

  • Making every global volatile "to be safe". It disables useful optimisations everywhere and still does not fix atomicity, so it hides bugs rather than removing them.
  • Testing only at -O0. At that level the compiler keeps every access anyway, so missing volatile is invisible. Test at the optimisation level you ship.
  • Casting away volatile, for example passing a volatile buffer to memcpy. The library function is free to optimise its accesses.
  • Using volatile for a variable shared between threads on a big operating system. There, use the language's atomics or the OS's synchronisation primitives.

Try it yourself

  1. Save the polling example to poll.c and run riscv64-unknown-elf-gcc -march=rv32im_zicsr -mabi=ilp32 -O2 -S poll.c. Read poll.s and find the self-jump. Add volatile and compare.
  2. Do the same with the two-character write and count the store (sb) instructions with and without volatile.
  3. Write a function that returns a volatile uint64_t global and compile it for the same 32-bit target. Find the two lw instructions and mark the point between them where an interrupt could tear the value.
  4. Predict the assembly for each case before you compile, then check. Ask an AI assistant the same questions and compare its answers with what the compiler actually produced.
