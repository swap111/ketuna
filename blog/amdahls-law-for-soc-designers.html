Amdahl's law for SoC designers: when an accelerator is worth it

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

Speeding up one part of a workload helps only as much as the rest allows. Use Amdahl's law with data-movement overhead to decide, from a profile, whether a hardware accelerator earns its silicon.

A common pitch in SoC projects goes like this: "the filter is slow, so let us build a hardware block that runs it ten times faster." The block gets built, and the product ends up barely twice as fast. Nothing went wrong with the block. The disappointment was predictable from a one-line formula, known as Amdahl's law, and from a profile of where the time actually goes. Learning to apply both before writing RTL saves months of work.

The formula

Suppose a fraction f of a program's run time is spent in the part you can accelerate, and the accelerator makes that part s times faster. The rest, a fraction 1 − f, runs exactly as before. The new run time, relative to the old, is (1 − f) + f / s, so the overall speed-up is:

Speed-up = 1 / ((1 − f) + f / s)

The important consequence comes from letting s grow without limit. The f / s term vanishes and the speed-up approaches 1 / (1 − f). If the accelerated part is 60% of the time, no accelerator, however fast, can make the program more than 1 / 0.4 = 2.5 times faster. The part you did not touch sets the ceiling.

A worked example with a profile

Imagine a sensor product whose processing loop takes 100 ms per frame on the SoC's processor core. A profile (numbers made up for illustration) shows:

  • 60 ms in a frequency-domain transform
  • 25 ms in filtering and feature extraction
  • 15 ms in packet formatting and communication

The transform is the obvious target: f = 0.6. Propose an accelerator that runs it 10 times faster.

Speed-up = 1 / (0.4 + 0.6 / 10) = 1 / 0.46 ≈ 2.17.

The frame now takes 46 ms instead of 100. A 10× block delivered about 2.2× overall.

Data movement is part of the bill

Accelerators rarely work in place. The processor or a DMA engine has to move input data to the block, start it, wait for it, and move results back. That time belongs in the formula as an extra term o, expressed as a fraction of the original run time:

Speed-up = 1 / ((1 − f) + f / s + o)

If moving data and synchronising cost 5 ms per frame, o = 0.05 and the speed-up drops to 1 / (0.4 + 0.06 + 0.05) = 1 / 0.51 ≈ 1.96. Doubling the accelerator to 20× barely helps: 1 / (0.4 + 0.03 + 0.05) ≈ 2.08. Past a certain point, the block's raw speed stops mattering and the interface does.

That is why good accelerator designs attack data movement as hard as computation: they share buffers with the processor, use DMA so the core can do other work, process data in streams rather than whole frames, or keep intermediate results inside the block between stages.

Compare the alternatives honestly

Amdahl's law also tells you what else could reach the same goal. Suppose the requirement is a 2× speed-up. Options include:

  • The transform accelerator. About 2× with overhead, at the cost of new RTL, verification, area and a driver.
  • A faster software transform. A better algorithm or an optimised library might make the transform 4× faster in software: 1 / (0.4 + 0.15) ≈ 1.82. Close, with no silicon change.
  • A small instruction set extension. A multiply-accumulate or bit-manipulation instruction might speed up both the transform and the filtering, attacking more than 60% of the time.
  • Accelerating something smaller. A 100× block for the 15 ms communication stage gives only 1 / (0.85 + 0.0015) ≈ 1.17. Small fractions are rarely worth hardware.

Hardware is the most expensive option to build and the hardest to change after tape-out, so it should win only when the numbers say so, including the energy, area and verification cost.

Profile before you build

All of this depends on knowing f, and intuition about where time goes is often wrong. Measure it.

  • On a RISC-V core, the mcycle and minstret counters give cycles and retired instructions; read them before and after each stage.
  • On a host or a simulator, use a profiler on a representative input, not a toy one.
  • Profile the whole product loop, including communication and waiting, not just the computation you find interesting.
  • Repeat after each change. Once the big stage is accelerated, a different stage becomes the largest, and the next decision depends on the new profile.

Common mistakes

  • Quoting the accelerator's speed-up as the product's speed-up. Only the formula tells you the overall gain.
  • Ignoring data movement and synchronisation. The o term can dominate a fast block.
  • Profiling a different workload. A benchmark with a small input may spend its time somewhere else entirely.
  • Accelerating early. Build hardware after software has been optimised, or you may accelerate code that a better algorithm would have removed.

Try it yourself

  1. Write a Python function for the speed-up with overhead and plot speed-up against s for f = 0.6 and o = 0.05 using numpy and matplotlib. Note where the curve flattens.
  2. Run a small signal-processing program on QEMU or Spike, or on a RISC-V core in Verilator, and read mcycle around each stage to build your own profile.
  3. Feed your measured fractions into the formula and decide, with numbers, which stage, if any, deserves hardware.
