Priority inversion, and how priority inheritance fixes it

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

A high-priority task waiting on a mutex held by a low-priority task can be delayed without bound by medium-priority work. A millisecond-by-millisecond timeline shows how it happens and how priority inheritance bounds it.

In this article

  2. The timeline without inheritance
  3. How priority inheritance fixes it
  4. Using it in practice
  5. Rules that keep blocking short
  6. Try it yourself

Priorities in an RTOS promise one thing: the most important ready task runs. Add a shared resource protected by a mutex and that promise quietly breaks. A high-priority task can end up waiting not just for the low-priority task that holds the lock, but for every unrelated medium-priority task that happens to be ready. The effect is called priority inversion. It is easy to create, hard to spot in testing, and fixed by a mutex feature that you should know how to switch on and check.

Three tasks and one lock

Take three tasks with fixed priorities, made up for illustration:

  • H, high priority: reads a sensor bus that is shared, through a mutex, with L
  • M, medium priority: a 6 ms computation that never touches the bus
  • L, low priority: logs data and uses the shared bus inside a 3 ms critical section

Blocking on a lock held by a lower-priority task is unavoidable and acceptable if it is short: H waits for L to finish its critical section, at most 3 ms here. That bounded wait is not the problem. The problem is what happens when M becomes ready while H is waiting.

The timeline without inheritance

Follow it millisecond by millisecond (upper half of the figure):

  1. t = 0: only L is ready; it runs. At t = 1 it locks the mutex and enters its 3 ms critical section.
  2. t = 2: H is released. It has higher priority, so it preempts L immediately. L has done 1 ms of its critical section.
  3. t = 3: H tries to lock the mutex, finds it held, and blocks. L is the only ready task and resumes its critical section.
  4. t = 4: M is released. M has higher priority than L, so it preempts L. Nothing stops it: M does not need the mutex, and the scheduler does not know that H is waiting for L.
  5. t = 10: M finishes. L resumes and completes its critical section at t = 11, releasing the mutex.
  6. t = 11: H finally gets the lock and runs.

H was blocked from t = 3 to t = 11, for 8 ms. Only 2 ms of that was L's remaining critical section. The other 6 ms was M, a task of lower priority than H, running while H waited. That is the inversion. Worse, it is unbounded: if two or three medium-priority tasks become ready in turn, they all run before L can release the lock, and H's wait grows with each one.

How priority inheritance fixes it

With priority inheritance, when a task blocks on a mutex, the mutex's current owner temporarily runs at the blocked task's priority. When the owner releases the mutex, its priority drops back.

Replay the timeline (lower half of the figure). At t = 3, H blocks on the mutex and L is raised to H's priority. At t = 4, M is released but cannot preempt L, which now outranks it. L finishes its critical section at t = 5 and drops back to low priority. H takes the lock and runs from 5 to 7, then M runs. H was blocked for 2 ms, exactly the remaining critical section, and no amount of medium-priority work can extend that.

The blocking is now bounded: H waits at most for the longest critical section of any lower-priority task that shares a lock with it. That bound is a number you can put into a response-time analysis.

This is why a mutex and a binary semaphore are not interchangeable even though both can protect a resource. A mutex has an owner, so the kernel knows whose priority to raise. A semaphore has no owner, so the kernel cannot help.

Using it in practice

Most RTOS mutexes support inheritance, but check rather than assume. In Zephyr, k_mutex objects apply priority inheritance:

#include <zephyr/kernel.h>

K_MUTEX_DEFINE(bus_lock);

int bus_read(uint8_t reg, uint8_t *val)
{
    if (k_mutex_lock(&bus_lock, K_MSEC(10)) != 0)
        return -EBUSY;              /* never wait forever */
    int ret = do_bus_transfer(reg, val);
    k_mutex_unlock(&bus_lock);
    return ret;
}

On a POSIX system, the same protection is requested explicitly with pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT) before creating the mutex. In other kernels, look for the word "inheritance" in the mutex documentation and for any configuration option that enables it.

An alternative is the priority ceiling protocol: each mutex is given the priority of the highest task that ever uses it, and any task that locks it runs at that priority immediately. It prevents some chained-blocking and deadlock cases that inheritance does not, at the cost of raising priority even when there is no contention.

Rules that keep blocking short

  • Keep critical sections short. Inheritance bounds the wait by the longest critical section, so a 3 ms section means up to 3 ms of blocking. Copy data out under the lock and process it afterwards.
  • Never block inside a critical section. Waiting for a bus transfer or a queue while holding a mutex multiplies the bound.
  • Use timeouts on locks. A timeout turns a deadlock into a reported error instead of a silent hang.
  • Do not lock mutexes in interrupts. An ISR cannot block, and inheritance does not apply to it. Hand data to a task instead.
  • Avoid nested locks, or always take them in the same global order.

Try it yourself

  1. Draw the timeline above on paper, then add a second medium-priority task released at t = 6 that runs for 4 ms, and work out H's blocking time with and without inheritance.
  2. Build a Zephyr application for the qemu_x86 or qemu_riscv32 board with three threads at different priorities that reproduce this scenario, using k_busy_wait() for the computations. Log timestamps with k_uptime_get() and compare H's waiting time with the expected 2 ms. Then replace the mutex with a k_sem and see the inversion return.
  3. Explain the difference between the two runs to someone else, using your hand-drawn timeline.
