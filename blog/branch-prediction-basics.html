Branch prediction from static rules to two-bit counters

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

Every wrong branch guess throws away pipeline work. Work out the cost of a misprediction, compare static rules with one-bit and two-bit predictors by hand, and see where each one fails.

A pipelined core fetches a new instruction every cycle, but it learns whether a branch is taken only several stages later. In the meantime it has to fetch something. If it guesses wrong, the instructions fetched on the wrong path are thrown away and the cycles they occupied are lost. Branch prediction is the art of guessing well and cheaply. This article starts with the cost of a wrong guess, then works through static rules and the two simplest dynamic predictors by hand.

The cost of a wrong guess

In a classic five-stage pipeline that resolves branches in EX, two younger instructions are already in IF and ID when the outcome is known. If the guess was wrong, both are flushed: a misprediction penalty of two cycles. Deeper pipelines resolve branches later and pay more.

The effect on average cycles per instruction (CPI) is a single formula:

CPI = CPIbase + (branch fraction) × (misprediction rate) × (penalty)

Take numbers made up for illustration: a base CPI of 1, 15% of instructions are branches, and the penalty is 3 cycles.

  • If half of all branches are mispredicted: CPI = 1 + 0.15 × 0.5 × 3 = 1.225.
  • If only 10% are mispredicted: CPI = 1 + 0.15 × 0.1 × 3 = 1.045.

The better predictor makes the whole program about 17% faster (1.225 / 1.045), and the only thing that changed was the guess. The penalty term grows with pipeline depth, which is why deep pipelines spend so much hardware on prediction.

Static rules: no state at all

The simplest predictors use no memory of the past.

  • Always not-taken. Keep fetching PC + 4. It costs nothing and is right whenever the branch falls through. It is wrong on every iteration of a loop's backward branch.
  • Backward taken, forward not taken (BTFN). A branch with a negative offset usually closes a loop, so predict it taken; a forward branch usually skips an if body, so predict it not taken. The sign of the offset is bit 31 of the instruction, available at fetch.

Static rules are a sensible choice for small embedded cores, where area matters more than the last few percent of speed. They fail on branches whose behaviour depends on data.

One bit of history

A one-bit predictor keeps one bit per branch: the last outcome. Predict whatever happened last time. The bits live in a small table, the branch history table, indexed by low bits of the branch's PC.

Trace a loop that runs 8 iterations and is entered many times. Its backward branch produces the pattern T, T, T, T, T, T, T, N, then repeats. In steady state:

  • At the final N, the bit says T (it was taken last time): miss.
  • On re-entry, the first T: the bit now says N: miss.
  • The other six are correct.

Two misses in eight, 75% accuracy. The second miss is annoying: one unusual exit has spoiled the prediction for the next entry.

Two-bit saturating counters

A two-bit counter fixes that by requiring two wrong outcomes in a row before changing its mind. Each branch gets a counter from 0 to 3. Taken increments it, not taken decrements it, and it saturates at both ends. Predict taken when the counter is 2 or 3.

Trace the same 8-iteration loop. During the loop the counter sits at 3. At the final N it predicts T, a miss, and drops to 2. On re-entry it still predicts T, which is right, and climbs back to 3. One miss in eight: 87.5% accuracy, against 75% for the one-bit scheme and 12.5% for always not-taken. BTFN also gets 87.5% on this loop for free, which is why static rules remain respectable for loop-heavy code.

Now a branch that alternates, T, N, T, N, such as if (i & 1) inside a loop. Start the counter at 1 (weakly not taken):

Outcome Counter before Prediction Result
T 1 N miss
N 2 T miss
T 1 N miss
N 2 T miss

Every guess is wrong. The counter bounces between 1 and 2, always one step behind. Always not-taken would get half of them right. Simple counters capture "this branch is usually one way"; they cannot capture patterns. That requires history-based predictors, which combine the PC with a record of recent outcomes to pick a counter.

Direction is only half the problem

A taken prediction is useless unless fetch also knows the target address in the same cycle, before the instruction has even been decoded. Cores therefore pair the counter table with a branch target buffer (a small cache from branch PC to target), and often a return address stack for function returns. A small embedded core may skip these and redirect after decode instead, accepting a one-cycle bubble on every taken branch.

Common mistakes

  • Updating the counters with wrong-path branches. Train the table when the branch resolves, not when it is fetched speculatively.
  • Indexing with PC bits 1:0. With 4-byte instructions they are always zero; skip the alignment bits.
  • Judging a predictor on one loop. Accuracy depends entirely on the workload; replay real traces.
  • Forgetting aliasing. Two branches with the same low PC bits share a counter and can spoil each other.

Try it yourself

  1. Write a 30-line Python model that replays a list of (PC, taken) pairs through always not-taken, BTFN, one-bit and two-bit predictors and prints the accuracy of each.
  2. Generate a branch trace by running a small program in Spike with its instruction log enabled, or in QEMU, and filter out the branches.
  3. Implement a 64-entry table of two-bit counters in Verilog, simulate it in Icarus Verilog against your Python model, and synthesise it with Yosys to see how little logic it needs.
