Timing closure when the last few paths will not close

Physical design & tape-out Advanced 27 Nov 2026 5 min read By Ketuna

When a handful of paths stay negative after every optimisation run, more tool effort rarely helps. A decision order for checking constraints, path structure, floorplan and RTL before touching tool knobs.

Late in a project, timing often looks almost done: thousands of paths pass, and a few dozen remain stubbornly negative. The natural response is to rerun with higher effort, a different seed or a more aggressive repair setting, and sometimes that works. When it does not, each extra run costs hours and the slack moves by a few picoseconds in either direction. At that point the problem is no longer the tool's optimisation. It is in the constraints, the floorplan or the logic, and the fastest way to closure is to work out which, in a fixed order.

Step 1: is the path real and correctly constrained?

Before changing any hardware, confirm that the failing path is one the chip actually needs to meet in a single cycle.

  • Clock relationship. Is the path between two clocks that are genuinely related? A path between asynchronous domains needs a synchronizer and a clock group or false path, not a timing fix.
  • Multicycle intent. Does the control logic only sample this result every second cycle? If so, a multicycle constraint with its matching hold adjustment is the correct description.
  • Static configuration. Paths from registers written once at start-up and then held constant do not need single-cycle timing, if the design guarantees they are stable before use.
  • I/O budgets. For port paths, check that the input and output delays were agreed with the neighbouring block and were not placeholder guesses.
  • Uncertainty and derates. Check that clock uncertainty after clock tree synthesis reflects jitter and margin only, not an estimate of skew that is now computed for real.

Every exception added at this step must be justified in writing and reviewed by someone who understands the design's intent. Turning a real path into a false path to meet a deadline is the most expensive mistake in this article, because it passes every report and fails on silicon.

Step 2: what kind of path is it?

Read the worst path line by line and classify it. Three patterns cover most cases:

Pattern in the report Diagnosis Leads to
Many cell delays of similar size, few long wires Deep logic RTL change
One or two very large wire or buffer delays Distance Floorplan change
Large difference between launch and capture clock latency Skew Clock tree change

As an illustrative example, suppose a path fails by 0.40 ns at a 4.0 ns clock. If 2.6 ns of its 4.2 ns arrival is in buffers and wires between a memory macro on one side of the block and a register bank on the other, no amount of cell sizing will recover 0.40 ns. The cells are not the problem; the distance is.

If instead the path has eighteen levels of logic each contributing around 0.2 ns, the wires are fine and the logic is simply too deep for the period.

Also look at the whole group of failing paths, not just the worst. If they all share a start or end point, one structural fix may close them all.

Step 3: fix distance in the floorplan

Distance problems are fixed by moving things, and moving things is cheapest at the floorplan.

  • Move the macro or the pins so that the endpoints of the critical paths are close together.
  • Constrain related logic to a region so that the placer keeps it near the macro it talks to.
  • Rotate a macro so its pins face the logic that uses them.
  • Change the block's shape if the critical paths run along its long dimension.

After a floorplan change, the whole flow reruns, so this costs a day rather than an hour. It is still far cheaper than repeated optimisation runs that cannot succeed.

Step 4: fix depth in the RTL

Deep logic needs fewer levels between registers. The main options:

  • Pipelining: add a register stage in the middle of the path, and adjust the surrounding control logic for one extra cycle of latency.
  • Restructuring: compute in parallel what was computed in series. A priority chain of comparisons can often become a balanced tree; a ripple structure can become a carry-lookahead or prefix structure.
  • Precomputation: compute part of the result a cycle early, from values already known, and register it.
  • Retiming by hand: move existing registers across logic so that each stage has a similar delay.
// Before: compare and select in one cycle
always @(posedge clk)
  y <= (a > b) ? a : b;   // 32-bit compare + 32-bit mux

// After: register the compare, select one cycle later
always @(posedge clk) begin
  gt  <= (a > b);
  a_q <= a;
  b_q <= b;
  y   <= gt ? a_q : b_q;
end

The second version has one more cycle of latency, which the rest of the design must account for. That is why RTL changes need verification to be rerun; a closure fix that introduces a functional bug is not a fix.

Step 5: only then, tool settings

With constraints confirmed, distance addressed and depth reasonable, the remaining small violations are what tools are good at. Useful levers include allowing larger drive strengths or a faster cell variant on critical paths, enabling useful skew, prioritising critical nets in routing (upper layers, wider spacing) and running more repair iterations after routing. These recover tens of picoseconds, not nanoseconds. If you find yourself needing nanoseconds from them, go back up the list.

Habits that help

  • Track worst and total negative slack per run in a table, with the change you made. Trends tell you whether you are converging.
  • Change one thing per run. Otherwise you cannot tell which change helped.
  • Talk to the RTL author early. A one-line change in RTL often beats a week of physical design effort.

Try it yourself

  1. Harden a small design with LibreLane on sky130 and tighten CLOCK_PERIOD until a few paths fail.
  2. In OpenSTA, load the final netlist and SPEF, then use report_wns, report_tns and report_checks -path_delay max -fields {fanout cap slew} to classify each failing path by the table above.
  3. Apply the matching fix: pipeline the RTL for a deep path, or change pin placement or aspect ratio for a distance path. Rerun and record slack before and after.
  4. Write down your prediction of the slack change before each run, and compare.
