Blocking vs non-blocking assignments: the one rule and why it exists

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

Use <= in clocked blocks and = in combinational blocks. A shift register that collapses when written with = shows how the simulator's scheduler makes this rule necessary.

Verilog gives you two ways to assign a value inside an always block: = (blocking) and <= (non-blocking). Beginners are told a rule, "non-blocking for flip-flops, blocking for combinational logic", and usually follow it without knowing why. The reason is worth learning, because when the rule is broken the code often still compiles, still synthesises, and simulates differently from the hardware you meant.

The one rule

  • In a clocked block (always @(posedge clk)), assign every register with <=.
  • In a combinational block (always @*), assign with =.
  • Never assign the same variable from more than one always block, and never mix = and <= for the same variable.

That is the whole rule. The rest of this article explains the mechanism behind it.

What the two operators do in the simulator

A blocking assignment a = b; evaluates b and updates a immediately. The next statement in the block already sees the new value of a. It behaves like a line of C.

A non-blocking assignment a <= b; evaluates b now but schedules the update of a for later in the same simulation time step, after every block triggered by this clock edge has finished reading its inputs. Every statement in every block therefore sees the values from before the edge.

You can picture each time step as two phases. In the first, the simulator runs every block that the clock edge woke up and evaluates all the right-hand sides of the non-blocking assignments, writing the results into a waiting list. In the second, it applies everything on the waiting list at once.

That second behaviour is exactly what a flip-flop does. On a clock edge, all flip-flops sample their D inputs at the same instant, using the old values, and only then do the outputs change. Non-blocking assignment is how a sequential, one-statement-at-a-time simulator imitates thousands of flops all switching at once.

A shift register that silently breaks

Here is a three-stage shift register written the right way:

module shift3_ok (
  input  wire clk,
  input  wire din,
  output reg  q3
);
  reg q1, q2;
  always @(posedge clk) begin
    q1 <= din;
    q2 <= q1;
    q3 <= q2;
  end
endmodule

At each edge, q1 takes din, q2 takes the old q1 and q3 takes the old q2. A bit entering on din reaches q3 three clocks later, as intended.

Now change only the operators:

  always @(posedge clk) begin
    q1 = din;
    q2 = q1;   // q1 already holds din
    q3 = q2;   // q2 already holds din
  end

Each line now sees the value written by the line above. After one edge, q1, q2 and q3 all equal din. The three-stage delay has become a one-stage delay. In simulation you see q3 follow din after a single clock. Synthesis tools usually build what the simulation shows here: one flop driving q3, with q1 and q2 optimised away because nothing needs them.

Reverse the order of the three lines (q3 = q2; q2 = q1; q1 = din;) and the blocking version happens to work again, because each register is read before it is overwritten. That is the trap: correctness now depends on statement order, and a later edit that reorders lines or splits the block breaks it without any warning.

The race between blocks

The problem gets worse when registers live in different always blocks:

  always @(posedge clk) q1 = din;
  always @(posedge clk) q2 = q1;

The standard does not say which of these two blocks the simulator runs first on a clock edge. If it runs the first, q2 gets the new q1; if the second, q2 gets the old one. Two simulators, or the same simulator after an unrelated change, can disagree. This is a classic race condition. With <= in both blocks the race disappears, because all right-hand sides are read before any left-hand side is updated, whatever the order.

Why combinational blocks use =

Inside a combinational block you often compute intermediate values and use them a line later:

  always @* begin
    sum   = a + b;
    carry = sum[8];
    y     = carry ? 8'hFF : sum[7:0];
  end

You want each line to see the result of the line above, because that is how the wires connect in the gates. With <=, carry would be computed from the previous value of sum, the block would need extra passes to settle, and in some simulators the output could lag or show transient wrong values. Blocking assignment makes the block evaluate top to bottom in one pass, like the logic it describes.

Common mistakes

  • Using = in a clocked block "because it worked". It worked because of statement order. It will stop working when someone reorders the code.
  • Mixing both operators on one variable. Linters flag this; some synthesis tools reject it. Pick one per variable, following the rule.
  • Reading a variable assigned with <= and expecting the new value on the same edge. You get the old value. That is not a bug; it is the flip-flop behaviour you asked for.
  • Trusting synthesis to catch it. Synthesis only builds the logic the code describes. A wrong operator usually produces a working but different circuit, not an error.

Try it yourself

  1. Put both versions of the shift register in one file with a small testbench and simulate with Icarus Verilog (iverilog -o sim shift.v tb.v && vvp sim). Dump a VCD with $dumpfile and $dumpvars and compare q3 in GTKWave.
  2. Synthesise each version with Yosys (yosys -p "synth -top shift3_ok; stat") and compare the flip-flop counts in the stat report.
  3. Run Verilator in lint mode (verilator --lint-only -Wall shift.v) on a version that mixes = and <= and read the warning it gives. Predict the warning before you run it.
