Will every task meet its deadline? Response-time analysis worked by hand

Embedded systems Advanced 27 Nov 2026 6 min read By Ketuna

The utilisation bound only says yes or don't know. Response-time analysis gives each task's exact worst case under fixed-priority preemption: the equation, a worked example and what real systems add.

Testing a real-time system tells you that no deadline was missed in the runs you made. It cannot tell you that the worst alignment of task releases, interrupts and lock contention never happens, because that alignment may be rare. For fixed-priority preemptive scheduling, the model behind most RTOS configurations, there is a calculation that answers the question for every possible alignment, and it fits on half a page. Every firmware engineer who sets task priorities should be able to do it by hand.

The model and its assumptions

Each task i is periodic with period Ti, a worst-case execution time Ci and a deadline Di; here Di = Ti. Each task has a fixed, unique priority, and the scheduler always runs the highest-priority ready task, preempting lower ones immediately. For now, assume tasks do not share locks, do not suspend themselves mid-job, and that switching costs nothing. We will add those back later, and they matter.

Under these assumptions the worst case for task i happens at the critical instant: when it is released at the same moment as every higher-priority task. Anything else gives higher-priority tasks fewer chances to interfere.

Why the utilisation test is not enough

The well-known Liu and Layland result says that with rate-monotonic priorities (shorter period, higher priority), n tasks are schedulable if total utilisation U = Σ Ci/Ti is at most n(21/n − 1). For three tasks that is about 0.780. The test is sufficient but not necessary: a task set above the bound may still be fine. It answers "yes" or "don't know", never "no" (except when U exceeds 1). Response-time analysis gives the exact answer for this model.

The response-time equation

Task i's worst-case response time Ri is its own execution time plus the time stolen by higher-priority tasks while it is waiting or running. A higher-priority task j is released ⌈Ri/Tj⌉ times within a window of length Ri starting at the critical instant, and each release costs Cj:

Ri = Ci + Σj ∈ hp(i) ⌈Ri / Tj⌉ · Cj

Ri appears on both sides, so solve it by iteration: start with R = Ci, evaluate the right-hand side, and repeat until the value stops changing (the task is schedulable if that fixed point is at most Di) or exceeds Di (it is not). The iteration always increases or stays the same, so it terminates.

A three-task example by hand

All times in milliseconds; the task set is made up for illustration.

Task C T = D Priority
τ1 1 4 high
τ2 2 6 medium
τ3 3 12 low

U = 1/4 + 2/6 + 3/12 ≈ 0.833, above the three-task bound of 0.780. The simple test is inconclusive, so we compute.

τ1 has no higher-priority tasks: R1 = 1 ≤ 4.

τ2 suffers interference from τ1:

  • R = 2 → 2 + ⌈2/4⌉·1 = 3
  • R = 3 → 2 + ⌈3/4⌉·1 = 3, fixed point. R2 = 3 ≤ 6.

τ3 suffers interference from both:

  • R = 3 → 3 + ⌈3/4⌉·1 + ⌈3/6⌉·2 = 3 + 1 + 2 = 6
  • R = 6 → 3 + ⌈6/4⌉·1 + ⌈6/6⌉·2 = 3 + 2 + 2 = 7
  • R = 7 → 3 + ⌈7/4⌉·1 + ⌈7/6⌉·2 = 3 + 2 + 4 = 9
  • R = 9 → 3 + ⌈9/4⌉·1 + ⌈9/6⌉·2 = 3 + 3 + 4 = 10
  • R = 10 → 3 + ⌈10/4⌉·1 + ⌈10/6⌉·2 = 3 + 3 + 4 = 10, fixed point.

R3 = 10 ≤ 12. Every task meets its deadline in the worst case, despite failing the utilisation test. Each step of the iteration has a physical meaning: "if τ3 has not finished by time R, how many times have the others been released by then?"

Now change the set slightly: τ2's period becomes 5 and τ3 needs 4. U ≈ 0.983. For τ3 the iteration runs 4, 7, 10, 11, 13: at R = 11, ⌈11/5⌉ = 3 releases of τ2 push the window to 13, past τ3's deadline of 12. The set is unschedulable, although utilisation is below 1. The difference between "the CPU has enough capacity on average" and "every deadline holds" is exactly what this analysis captures.

Checking it with a few lines of Python

def response_times(tasks):
    """tasks: (C, T) pairs, highest priority first, D = T, integers.
    Returns R for each task, or None if it can miss its deadline."""
    out = []
    for i, (c, t) in enumerate(tasks):
        r = c
        while True:
            nxt = c + sum(-(-r // tj) * cj for cj, tj in tasks[:i])
            if nxt > t:
                out.append(None)
                break
            if nxt == r:
                out.append(r)
                break
            r = nxt
    return out

print(response_times([(1, 4), (2, 6), (3, 12)]))   # [1, 3, 10]
print(response_times([(1, 4), (2, 5), (4, 12)]))   # [1, 3, None]

-(-r // tj) is an integer ceiling. Keep the times in integer units, such as microseconds; a floating-point ceil of 2.0000000001 gives 3 and can make a schedulable set look unschedulable.

What real systems add to the equation

The clean model leaves out several costs. A defensible analysis adds each one explicitly:

  • Blocking, Bi. If a lower-priority task holds a mutex that τi needs, τi waits. With a priority inheritance or priority ceiling protocol, the wait is bounded, and you add the longest such critical section to the equation as Bi. Without such a protocol the wait is unbounded and no analysis helps.
  • Interrupts. Every ISR behaves like a very high-priority task. Add each one as a term with its minimum inter-arrival time and worst-case duration.
  • Kernel overhead. Each preemption costs a context switch in and out. A common approximation adds two switch times to every Cj.
  • Release jitter. If a task is released by a tick, it may become ready up to one tick late. Jitter Jj on a higher-priority task increases its interference to ⌈(Ri + Jj)/Tj⌉·Cj, and the task's own jitter adds to its response time.
  • Execution-time estimates. The analysis is only as good as C. Measured maxima from tests are optimistic; leave margin, and record how each C was obtained.

Treat results that land exactly on a deadline or on another task's release time with suspicion: a tick of jitter or one extra cache miss turns "exactly meets" into "misses".

Try it yourself

  1. Redo the τ3 iteration on paper without looking, then run the Python function and compare.
  2. Add a blocking term Bi to the function and find the largest critical section in τ3 that still lets τ2 meet its deadline.
  3. In the Ketuna track D lab D5, a small preemptive kernel runs three tasks on QEMU and compares measured response times with your RTA. Make one task's work land exactly on a release boundary and explain the difference you see between prediction and measurement.
