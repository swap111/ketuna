APB, AHB and AXI compared: picking a bus for each peripheral

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

APB for simple registers, AHB for pipelined memory traffic, AXI for independent read and write streams. Work out each bus's bandwidth, match it to real peripherals, and write a small APB register block.

In this article

  2. AHB: overlap the address and data phases
  3. AXI: five independent channels
  4. Matching bandwidth to the peripheral
  5. Pitfalls when choosing
  6. Try it yourself

An SoC connects a processor to memories and peripherals through on-chip buses, and most designs use more than one kind. APB, AHB and AXI are three members of one widely used family of on-chip bus specifications, and each makes a different trade between simplicity and throughput. Choosing well means matching each block's bandwidth and latency needs to the cheapest bus that meets them, rather than putting everything on the most capable one. This article compares the three with numbers.

APB: one register access at a time

APB is the simplest of the three. Every transfer has two phases. In the setup phase the manager drives the address, direction and write data and asserts psel. In the access phase it asserts penable, and the transfer completes on the first clock edge where the subordinate's pready is high. A subordinate that needs more time holds pready low to insert wait states, and can flag a failure with pslverr.

There is no pipelining and no burst: one transfer takes at least two cycles, and the next cannot start until the current one ends. That sounds slow, and it is, but it is exactly right for control registers. A UART, a timer or a GPIO block is written a few times to configure it and then read occasionally. What matters is a small, easy-to-verify interface, and APB delivers that.

A minimal APB register block, with two registers and no wait states, fits on a screen:

module apb_regs (
  input  wire        pclk, presetn,
  input  wire        psel, penable, pwrite,
  input  wire [3:0]  paddr,
  input  wire [31:0] pwdata,
  output reg  [31:0] prdata,
  output wire        pready, pslverr
);
  reg [31:0] ctrl, baud;
  assign pready  = 1'b1;          // always ready: no wait states
  assign pslverr = 1'b0;
  wire wr = psel & penable & pwrite;

  always @(posedge pclk or negedge presetn)
    if (!presetn) begin
      ctrl <= 32'd0;
      baud <= 32'd0;
    end else if (wr) begin
      case (paddr)
        4'h0: ctrl <= pwdata;
        4'h4: baud <= pwdata;
        default: ;
      endcase
    end

  always @(*)
    case (paddr)
      4'h0:    prdata = ctrl;
      4'h4:    prdata = baud;
      default: prdata = 32'd0;     // reserved reads as zero
    endcase
endmodule

AHB: overlap the address and data phases

AHB keeps a single shared channel but pipelines it. While the data of transfer n moves, the address of transfer n + 1 is already on the bus. In the best case a new transfer completes every cycle. It also supports bursts, where the manager signals that the next addresses follow on in sequence, which lets a memory controller prepare ahead. A subordinate stretches a transfer by holding hready low, which stalls the pipeline for everyone.

That makes AHB a good fit for on-chip SRAM, flash with a prefetch buffer, and a simple DMA engine: blocks that move data steadily and benefit from one transfer per cycle, but do not need concurrent reads and writes.

AXI: five independent channels

AXI splits a transaction into separate channels: read address, read data, write address, write data and write response. Each has its own valid/ready handshake, so a read and a write can proceed at the same time. A manager can issue several requests before the first completes (outstanding transactions), tag them with IDs, and in some cases receive responses out of order. Bursts move many beats of data for a single address.

The result is the highest throughput and the best tolerance of long latency, for example DRAM, at the price of the most logic and the hardest verification. The reasons for that split are the subject of AXI's five channels.

Matching bandwidth to the peripheral

Put rough numbers on the three buses at an illustrative 50 MHz with a 32-bit data path, ignoring wait states:

Bus Best-case transfers Peak bandwidth at 50 MHz, 32 bits
APB 1 per 2 cycles 25 M × 4 B = 100 MB/s
AHB 1 per cycle 50 M × 4 B = 200 MB/s
AXI 1 read and 1 write per cycle up to 200 MB/s each way

Now look at what typical blocks need (all derived from the interface settings, not measured):

  • UART at 115200 baud: 10 bits per byte on the wire (start, 8 data, stop), so 11,520 bytes per second. A tiny fraction of APB.
  • Stereo audio, 48 kHz, 32-bit slots: 48,000 × 2 × 4 = 384,000 bytes per second. Still easy on APB, though you would usually move it with DMA rather than an interrupt per sample.
  • A 640 × 480 camera at 30 frames per second, 2 bytes per pixel: 640 × 480 × 2 × 30 = 18.4 MB/s. That is about 18% of APB's theoretical peak, but real APB transfers often have wait states and the bus is shared with every other peripheral. Put the camera's data path on AHB or AXI and keep only its control registers on APB.
  • External DRAM: latency of many cycles and bursts of data. Without outstanding transactions, the bus would sit idle while each access waits, so this is AXI's natural place.

The usual structure follows directly: the processor and DMA sit on an AXI or AHB interconnect with memories and high-bandwidth blocks, and a bridge leads to an APB segment that hosts the slow control registers. The bridge turns one fast transaction into a two-phase APB access, which is cheap because APB traffic is light.

Pitfalls when choosing

  • Putting everything on AXI "for performance". Each AXI subordinate needs channel logic and protocol checks; for a register block that is pure cost.
  • Putting a streaming data path on APB. Bandwidth looks fine on paper until wait states and sharing are counted.
  • Ignoring latency. A peripheral that stalls with hready low stalls every AHB manager behind it.
  • Forgetting the bridge's ordering rules. Writes posted through a bridge may complete later than the processor thinks; read back or fence before depending on them.

Try it yourself

  1. Simulate the apb_regs module in Icarus Verilog with a testbench task that performs a setup and access phase, and check reads and writes in GTKWave.
  2. Write the same testbench in cocotb with Python coroutines for APB read and write, and add a check that a reserved address reads zero.
  3. Add a pready wait state to one register and confirm your testbench waits for it rather than assuming two cycles.
