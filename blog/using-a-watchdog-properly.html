Using a watchdog properly: what to kick, where, and when not to

Embedded systems Intermediate 27 Nov 2026 6 min read By Ketuna

A watchdog only helps if it is refreshed when the whole system is healthy. How to collect check-ins from every task, size the timeout, use a windowed watchdog, and record why the last reset happened.

Every microcontroller has a watchdog timer, and most firmware turns it on. Far fewer projects use it well. A watchdog that is refreshed from a timer interrupt will happily keep a device alive while its main loop is stuck forever, and a device that resets without recording why gives you nothing to fix. The value of a watchdog lies entirely in two decisions: what has to be true before you refresh it, and what you do after it fires.

What the hardware actually does

A watchdog is a down-counter, usually clocked from its own low-speed oscillator so it keeps running even if the main clock fails. Firmware must refresh (or "kick", or "feed") it before it reaches zero, typically by writing a special key value to a register. If the count reaches zero, the watchdog resets the chip. Once started, many watchdogs cannot be stopped by software at all, so a bug cannot switch them off.

The watchdog cannot know whether your firmware is healthy. It only knows that someone wrote the key in time. Every bit of intelligence must come from where and when you write it.

The classic mistake: kicking from an interrupt

void systick_isr(void)          /* do not do this */
{
    wdt_refresh();
}

The timer interrupt keeps firing even when the main loop is stuck in an endless loop waiting for a flag that never comes, or when a task has deadlocked on a mutex. The watchdog is refreshed every millisecond and never fires. You have paid the cost of a watchdog and turned off its only function.

The rule: refresh the watchdog only from a place that runs when the useful work is running, and only after checking that it really is.

Check in from every task, refresh from one place

In a system with several tasks or several jobs in a superloop, give each one a bit. Each job sets its bit when it completes a normal cycle. A single supervisor refreshes the watchdog only when every expected bit is set, then clears them all.

#include <stdatomic.h>
#include <stdint.h>

enum {
    ALIVE_SENSOR = 1u << 0,
    ALIVE_COMMS  = 1u << 1,
    ALIVE_CTRL   = 1u << 2,
    ALIVE_ALL    = ALIVE_SENSOR | ALIVE_COMMS | ALIVE_CTRL,
};

static atomic_uint alive;

void task_checkin(unsigned bit)          /* called by each task */
{
    atomic_fetch_or(&alive, bit);
}

void supervisor_poll(void)               /* runs periodically */
{
    unsigned seen = atomic_load(&alive);
    if ((seen & ALIVE_ALL) == ALIVE_ALL) {
        atomic_fetch_and(&alive, ~(unsigned)ALIVE_ALL);
        wdt_refresh();
    }
    /* if a bit is missing, do nothing: the watchdog will fire */
}

The atomic OR matters: each task may run at a different priority, and a plain alive |= bit is a read-modify-write that can lose another task's bit. On a single-core part without atomic instructions, a two-instruction critical section does the same job.

Choose where each task checks in carefully. A comms task that checks in at the top of its loop proves only that the loop started; checking in after it has processed a message, or after its blocking wait returns with a timeout, proves it is still making progress. A task that legitimately waits a long time for an event should wait with a timeout shorter than the watchdog period and check in on each timeout.

Sizing the timeout

The timeout must be longer than the longest legitimate gap between refreshes and short enough that the system recovers before harm is done.

  • Find the longest legitimate gap. Erasing a flash sector, writing a log page, a radio join, a long calculation: measure each in the worst case. If erasing a sector blocks the CPU for longer than the watchdog period, every firmware update will reset the device.
  • Add margin for the watchdog's own clock. Low-speed RC oscillators vary noticeably with temperature and between chips; the datasheet gives the range. Size the timeout using the fastest the oscillator can run, because that gives the shortest real timeout.
  • Ask what failure costs. A motor controller that must stop within a short time after a hang needs a short timeout; a data logger can tolerate seconds.

Windowed watchdogs catch the other failure

A plain watchdog catches code that stops. It does not catch code that runs too fast: a loop that skips its real work because of a corrupted state variable may hit the refresh more often, not less. A windowed watchdog also resets the chip if it is refreshed too early, before a window opens. Configure the window around the expected period of your supervisor, for example "not before 60 % of the timeout", and an out-of-control fast loop is caught as surely as a stuck one. Your supervisor then has to refresh on a steady schedule, which is good discipline anyway.

After the reset: record the cause

A watchdog reset without a record is a lost bug report. Two pieces of information make it useful.

  1. The reset cause. Most microcontrollers have a reset-cause register with flags for power-on, external pin, brown-out, software and watchdog resets. Read it first thing in startup, save it, then clear the flags so the next reset is reported correctly.
  2. What was happening. Keep a small structure in a RAM section that startup code does not zero (a .noinit section in the linker script). Tasks write their current state or the missing check-in bits there. After a watchdog reset, the structure survives and tells you which task stopped. Protect it with a magic number and a checksum, since after a power-on it holds random data.

Count consecutive watchdog resets in the same section. If the device resets several times in a row within a short time, boot into a safe mode with fewer features instead of looping forever, and report the fault the next time communication works.

Pitfalls

  • Leaving the watchdog running while halted in a debugger. Most parts can freeze the watchdog in debug mode; set that bit, or every breakpoint resets the board.
  • Refreshing inside a long loop "to keep it quiet". That hides exactly the hang you want to catch.
  • Starting the watchdog after a long initialisation. Initialisation can hang too; start it early with a generous timeout, then tighten it.
  • Treating watchdog resets as normal. Each one is a bug to understand, not background noise.

Try it yourself

  1. In a QEMU-based project such as the Ketuna track D labs, simulate a watchdog in software with the timer interrupt: count down, and at zero jump back to the reset entry _start (a stand-in for a real reset). Implement the check-in supervisor and confirm that blocking one task triggers the reset.
  2. Add a .noinit section to the linker script, store the missing check-in bits there before the simulated reset, and print them after restart.
  3. On a real board, measure the worst-case flash sector erase time with a GPIO and a logic analyser, and write down the minimum watchdog timeout that survives it.
