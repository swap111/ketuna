Making a physical design flow reproducible: pinned tools, configs and seeds

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

A layout result is only useful if someone else can produce it again. Learn how to pin the flow and PDK versions, keep configuration in version control, record seeds and write a run record anyone can follow.

You get a clean run: timing met, DRC clean, LVS matched. A week later a teammate runs "the same thing" on their machine and gets negative slack and a hundred DRC errors. Neither of you did anything wrong, but you were not running the same thing. A physical design result depends on the RTL, the configuration, the flow version, every tool inside it, the PDK version and sometimes a random seed. Unless all of those are pinned and recorded, a result cannot be repeated, reviewed or trusted.

What a run actually depends on

List the inputs honestly and the reasons for each become obvious:

Input Why it changes results
RTL and constraints Obviously; even a comment change can alter synthesis names and ordering
Flow configuration Utilisation, density, clock period, every override
Flow version Default values, step order and scripts change between releases
Tool versions inside the flow Yosys, OpenROAD, Magic, KLayout and Netgen each evolve
PDK version Cell libraries, rule decks and models are updated over time
Seeds and threading Some algorithms use randomness or parallel ordering
Host environment Rarely matters inside a container, but can outside one

A practical example of why the PDK matters: a flow release expects the standard-cell libraries of a specific PDK build. Pair it with a newer PDK build whose libraries were revised, and the run can stop in the first few steps with an error that looks unrelated. Pinning both together, as a pair, avoids that.

Pin the tools with a container

The simplest way to pin every tool at once is to run the flow from a container image with an exact tag, rather than tools installed by hand on each machine. The image carries the flow and the specific versions of the tools it was tested with.

  • Use an exact tag, never latest. A tag such as latest changes under you.
  • For stronger pinning, record the image digest, a content hash that identifies exactly one image even if someone moves a tag.
  • Change the image tag only deliberately, in a commit that says why, and rerun your reference designs to see what moved.

Pin the PDK

PDKs are installed as versioned builds. Tools such as ciel install a PDK build identified by a commit hash into a directory you choose, so several versions can live side by side.

  • Record the exact PDK hash in your repository, next to the flow configuration.
  • Use the hash that your flow release documents as compatible. Many flow releases ship a list of the PDK versions they expect.
  • Point the flow at that directory explicitly (for example through PDK_ROOT) instead of relying on whatever is installed in a default location.

Put the configuration under version control

Everything that is not a tool belongs in Git:

  • RTL, constraints, the flow configuration file and any custom scripts,
  • a small script or Makefile that runs the flow the same way every time,
  • a file recording the image tag and PDK hash.

Do not keep "the real settings" in your shell history. If a run used a command-line override, it belongs in a configuration file or in the run script. Run outputs, which are large, usually stay out of Git; the metrics summary of a reference run is small and worth committing, so later runs can be compared with it.

Record seeds and settle nondeterminism

Some steps can produce slightly different results from run to run. Placement and routing algorithms may use random initial conditions, and multithreaded steps can process work in different orders. If a step exposes a seed, set it explicitly and record it. If results still vary between identical runs, note how much, and do not treat differences smaller than that variation as meaningful. Comparing two settings on a single run each can mislead you if run-to-run variation is of the same size as the effect.

Write a run record

Every run you want to cite should leave a record. A short script can capture the essentials automatically:

#!/usr/bin/env bash
# Write a run record next to the run directory.
set -euo pipefail
image=ghcr.io/librelane/librelane:3.0.16
pdk_hash=$(cat pdk_hash.txt)
tag=$1
{
  echo "run:       $tag"
  echo "date:      $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo "commit:    $(git rev-parse HEAD)"
  echo "dirty:     $(git status --porcelain | wc -l) changed files"
  echo "image:     $image"
  echo "digest:    $(docker image inspect --format \
                   '{{index .RepoDigests 0}}' "$image")"
  echo "pdk:       sky130A $pdk_hash"
  echo "config:    $(sha256sum config.json | cut -d' ' -f1)"
} > "runs/$tag.record.txt"
cat "runs/$tag.record.txt"

The "dirty" line matters: a run made from a working copy with uncommitted changes cannot be reproduced from the commit alone. Make it a rule that sign-off runs come from a clean checkout.

Test reproducibility on purpose

Reproducibility is a claim, so check it:

  1. Clone the repository into a fresh directory, or ask a teammate to do it on their machine.
  2. Install the pinned PDK, pull the pinned image, and run the script.
  3. Compare the new metrics summary with the committed one. Cell counts, die area, wire length and slack should match, or differ only within the run-to-run variation you measured.

If they do not match, the difference is information: some input was not pinned. Find it and add it to the record.

Common mistakes

  • Using latest images or "whatever PDK is installed". Results drift silently.
  • Upgrading the flow without the matching PDK, or the reverse.
  • Keeping settings in command-line overrides only. Nobody can rerun them later.
  • Comparing single runs when results vary from run to run.

Try it yourself

  1. Harden a small design with LibreLane in its container, using an exact image tag and a PDK installed by hash with ciel.
  2. Write the run record script above into your repository and run it after each flow run.
  3. Clone the repository into a new directory, rerun, and diff the two metrics.json files with a short Python script.
  4. Run the identical configuration three times and note any variation in slack or wire length.
