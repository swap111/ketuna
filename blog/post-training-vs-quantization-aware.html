Post-training quantization vs quantization-aware training

Edge AI Advanced 27 Nov 2026 6 min read By Ketuna

Post-training quantization calibrates a finished model; quantization-aware training simulates int8 while the model learns. How each works, how to diagnose the gap, and when the cheaper one is enough.

In this article
  1. What post-training quantization does
  2. What quantization-aware training does
  3. Diagnosing the gap before choosing
  4. When each one is enough
  5. Try it yourself

You have a float model that meets its accuracy target and a device that only runs int8. There are two ways across. Post-training quantization (PTQ) leaves the trained weights alone and chooses scales and zero points by watching the model run on sample data. Quantization-aware training (QAT) puts the rounding inside the training loop so the weights learn to tolerate it. PTQ costs minutes; QAT costs a training run and a pipeline you have to maintain. Knowing what each one actually fixes tells you when to stop at PTQ.

What post-training quantization does

PTQ has two jobs. Weights are easy: they are known constants, so their ranges come straight from the tensors, usually per output channel and symmetric. Activations are the hard part, because their ranges depend on the input. PTQ runs a calibration set, a few hundred representative inputs, through the float model, records statistics at every tensor that will be quantized, and turns those statistics into a range.

How it turns statistics into a range is where calibration methods differ:

  • Min-max takes the extreme values seen. It never clips calibration data, but a single outlier inflates the step size for everything else.
  • Percentile takes, say, the 99.99th percentile of |x|, deliberately clipping the rare tail.
  • Error-minimising searches for the clipping threshold that minimises mean squared error (or a divergence between float and quantized histograms) for that tensor.

A minimal percentile observer looks like this:

import numpy as np

class PercentileObserver:
    def __init__(self, pct=99.99):
        self.pct, self.samples = pct, []

    def observe(self, x):
        self.samples.append(np.asarray(x).ravel())

    def qparams(self):
        v = np.concatenate(self.samples)
        lo = min(0.0, np.percentile(v, 100 - self.pct))
        hi = max(0.0, np.percentile(v, self.pct))
        s = (hi - lo) / 255
        z = int(round(-lo / s)) - 128
        return s, z

Good PTQ flows also do some housekeeping that is easy to forget. Batch-normalisation layers are folded into the preceding convolution's weights and bias before weight ranges are measured, because the device never runs batch norm separately. ReLU is fused into the layer's output clamp. Some flows apply bias correction, which measures the average shift in each channel's output caused by weight rounding and subtracts it from the bias.

What quantization-aware training does

QAT inserts fake quantization nodes into the float graph: each one quantizes and immediately dequantizes, so the forward pass sees exactly the rounding and clipping the device will apply, while everything stays in floating point for the optimiser.

The difficulty is the backward pass. Rounding has zero gradient almost everywhere, which would stop learning. The standard fix is the straight-through estimator (STE): treat the quantizer as the identity when computing gradients, except that values clipped outside the range get zero gradient. In PyTorch the core trick is one line:

import torch

def fake_quant(x, s, z, qmin=-128, qmax=127):
    q = torch.clamp(torch.round(x / s) + z, qmin, qmax)
    xq = (q - z) * s
    return x + (xq - x).detach()   # forward: xq, backward: identity

The detach() hides the rounding from autograd, so the forward value is the quantized one and the gradient flows as if nothing happened. Real QAT frameworks add a clipped gradient and often make the scale itself learnable, but the idea is the same. You start QAT from the trained float weights, not from scratch, and fine-tune for a fraction of the original training with a small learning rate. The weights drift towards values that sit well on the integer grid, and layers learn to keep activations within ranges that quantize cleanly.

Diagnosing the gap before choosing

Do not jump to QAT because the int8 accuracy dropped. First find out where it dropped. Two cheap experiments locate most problems:

  1. One layer at a time. Quantize a single layer, keep the rest in float, and measure accuracy. Repeat for every layer. Usually one or two layers account for most of the loss: often the first layer (raw inputs with an awkward range), the last layer (small logit differences decide the class) or depthwise convolutions (few weights per channel, wide variation between channels).
  2. Weights only, then activations only. If quantizing weights alone loses little, the problem is activation ranges, which better calibration may fix. If weights alone hurt, check that you are using per-channel scales before anything else.

Fixes then come in order of cost: a better calibration set, per-channel weights, a different clipping method, keeping one sensitive layer at higher precision if the runtime supports it, and only then QAT.

When each one is enough

PTQ tends to be enough when:

  • the target is 8 bits for both weights and activations
  • weights use per-channel scales
  • the model has some redundancy, for example a convolutional network that is not already squeezed to the minimum size
  • the calibration data really looks like field data, captured with the same sensor and front end

QAT tends to be worth the effort when:

  • you go below 8 bits, where each step is so coarse that the weights must adapt
  • the model is very small or uses many depthwise layers, so there is little slack to absorb error
  • the per-layer experiments show a loss that calibration choices cannot remove
  • the model will be retrained regularly anyway, so a QAT pipeline is a one-time cost

There is also an engineering cost to QAT that does not show up in accuracy tables. The fake-quant graph must match the device arithmetic exactly: the same rounding mode, the same fused operations, the same clamp on ReLU. If training simulates round-half-to-even and the kernel rounds half up, the model is learning to fit a device that does not exist. Whatever route you take, the final check is the same: run the converted integer model, not the fake-quant float graph, on the held-out test set, and compare it bit for bit with the code that runs on the device.

Common mistakes:

  • calibrating on training data augmented in ways the field never produces
  • measuring weight ranges before folding batch norm
  • reporting QAT accuracy from the fake-quant graph instead of the exported integer model
  • training QAT from random initialisation instead of fine-tuning the float model

Try it yourself

  1. Train a small convolutional network on a public digit dataset in PyTorch, then quantize it with post-training static quantization using min-max and percentile observers. Record int8 accuracy for both.
  2. Write the one-layer-at-a-time sensitivity loop and plot accuracy against layer index.
  3. Add the fake_quant function above to the most sensitive layer's weights and output, fine-tune for one or two epochs with a small learning rate, and compare with PTQ.
  4. Export both versions and confirm the deployed integer model, not the training graph, gives the accuracy you report.
