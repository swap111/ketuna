Low-power verification basics: what UPF adds to simulation

Verification Advanced 27 Nov 2026 5 min read By Ketuna

Power intent adds domains that switch off, isolation at their boundaries and retention of state. Learn how power-aware simulation corrupts powered-down logic, and the sequencing bugs that only this reveals.

Plain RTL simulation assumes every flip-flop is powered all the time. Chips designed for battery life break that assumption on purpose: whole blocks are switched off when idle and brought back when needed. The RTL itself usually says nothing about this. The power architecture lives in a separate file written in the Unified Power Format (UPF, IEEE 1801), and unless the simulator reads that file, the testbench verifies a chip that never powers anything down. Some of the most expensive bugs live exactly in the gap.

What the power intent describes

A UPF file overlays the RTL with a few concepts:

  • Power domains: groups of instances sharing a supply. An always-on domain holds the power controller; switchable domains can be turned off.
  • Power switches: the controlled connection between a supply and a switchable domain.
  • Isolation: cells at the outputs of a switchable domain that clamp signals to a safe value while the domain is off, powered from the always-on supply.
  • Retention: flip-flops with a shadow storage element on the always-on supply, so selected state survives power-down.
  • Level shifters: translation between domains at different voltages.
  • Power states: the legal combinations of supply states.

What power-aware simulation does differently

A simulator that reads the UPF changes the behaviour of the RTL in three ways.

Powered-down logic is corrupted. When a domain's supply turns off, every flop and output inside it goes to X. When the supply returns, ordinary flops stay X until reset or written. This is how the simulation models the physical truth that an unpowered flop holds nothing.

Isolation clamps the boundary. While isolation is enabled, outputs of the off domain are forced to their clamp value, typically 0 or 1, so the always-on logic sees a defined signal instead of X.

Retention saves and restores. On a save signal, retention flops copy their value to the shadow element. On restore, they copy it back. Between the two, the main flop may be X while the shadow holds the value.

None of this appears in a plain RTL simulation. There, a block "switched off" by the controller simply keeps its state and keeps driving its outputs, so every power-down test passes regardless of how the sequence is written.

The bugs it reveals

Power-aware simulation exists to find a specific family of errors, almost all about order and completeness.

  • Isolation enabled too late. If the switch opens before isolation is enabled, X escapes into the always-on domain for a few cycles. That might corrupt an interrupt controller or a bus.
  • Isolation released too early. On wake-up, releasing isolation before the domain has been restored or reset lets X or stale values out.
  • Save after power-off. If the save pulse arrives after the supply drops, the shadow captures X. The design wakes up with garbage in its "retained" state.
  • Reset clobbers restored state. A wake-up sequence that restores and then asserts reset wipes the retained values. The sequence has to be restore-then-release, with reset handled carefully.
  • Missing isolation. An output that crosses into the always-on domain with no isolation rule. Static checks on the RTL plus UPF find these structurally; simulation shows their effect.
  • Software touching an off domain. A bus access to a register in a powered-down block. The power-aware simulation returns X or hangs, exposing a missing check in the bus fabric or firmware.
  • Unretained state that matters. A configuration register that was not marked for retention comes back as X after wake-up, and the block misbehaves until software reconfigures it.

Checking the sequence with assertions

The controller's sequence is a protocol, and assertions describe it well. These checks work in any SVA-capable simulator, power-aware or not, because they look only at the controller's outputs.

module pwr_seq_props (input logic clk, rst_n,
                      pwr_on, iso_en, ret_save, ret_restore);
  default clocking cb @(posedge clk); endclocking
  default disable iff (!rst_n);

  a_iso_before_off:  assert property ($fell(pwr_on) |-> iso_en);
  a_save_powered:    assert property (ret_save |-> pwr_on);
  a_restore_powered: assert property (ret_restore |-> pwr_on);

  // Isolation may be released only after a restore since power-up
  logic restored, pwr_q;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      restored <= 1'b1;
      pwr_q    <= 1'b1;            // domain starts powered after reset
    end else begin
      pwr_q <= pwr_on;
      if (pwr_on && !pwr_q)  restored <= 1'b0;   // power just returned
      else if (ret_restore)  restored <= 1'b1;
    end

  a_iso_release: assert property ($fell(iso_en) |-> restored);
endmodule

The tracking flop restored is cleared each time power comes back and set by a restore pulse. Releasing isolation while it is clear means the domain is about to drive unrestored values out.

Learning it with open tools

UPF-aware simulation and static power checking are features of commercial tools. You can still learn the concepts with open-source simulators by modelling the effects behaviourally: wrap the switchable block so that its outputs pass through a clamp controlled by iso_en, and add a simulation-only process that forces its registers to X (or random values in a two-state simulator) whenever pwr_on is low. It is not a substitute for the real flow, but it exposes the same sequencing errors, and the assertions above carry over unchanged.

Try it yourself

  1. Write a small power controller FSM with pwr_on, iso_en, ret_save and ret_restore, and a switchable counter block with one retained register.
  2. Model power-down behaviourally in Icarus Verilog: force the block's ordinary registers to X while pwr_on is low, and clamp its outputs while iso_en is high.
  3. Bind the property module above and run a sleep and wake cycle; then swap the order of isolation and power-off and confirm a_iso_before_off fires.
  4. Move reset after restore in the wake-up sequence and observe the retained register being clobbered.
