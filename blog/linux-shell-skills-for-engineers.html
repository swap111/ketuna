The Linux shell skills every chip and firmware engineer uses

Careers & skills Beginner 27 Nov 2026 5 min read By Ketuna

Chip and firmware tools run from the Linux shell. Learn the daily skills that matter, navigating, searching logs, pipes, small scripts and environment variables, with examples from real tool flows.

In this article

Almost every tool in a chip or firmware flow, simulators, synthesis, place and route, cross-compilers, debuggers, runs from a Linux command line. A regression produces hundreds of log files; a build depends on environment variables pointing at the right tool versions. Engineers who are comfortable in the shell find the failing test in seconds and automate the boring parts. You do not need to know everything; a small set of skills covers most days.

Moving around and finding files

Start with navigation until it is automatic: pwd shows where you are, ls -l lists files with sizes and dates, cd moves, and cd - returns to the previous directory. Tab completion saves typing and catches spelling mistakes, because if Tab does not complete, the file is not there.

Tool flows create deep directory trees, so finding files is a daily task:

find . -name "*.vcd"                 # every waveform under here
find . -name "*.log" -mtime -1       # logs changed in the last day
ls -lt runs/ | head                  # newest run directories first
du -sh runs/*                        # how much space each run uses

The last command matters more than it looks. Waveform dumps and place-and-route outputs grow large quickly, and a full disk causes strange tool failures that look like design bugs.

Searching logs with grep

A simulation or synthesis log can be thousands of lines long. Reading it top to bottom is slow; searching it is fast. grep prints lines matching a pattern:

grep -n "ERROR" sim.log              # matching lines with line numbers
grep -i "warning" synth.log | wc -l  # count warnings, any case
grep -rl "FAIL" regress/             # which files under regress/ failed
grep -B2 -A5 "Assertion" sim.log     # context around each assertion
grep -v "INFO" sim.log               # everything except INFO lines

The -B and -A options show lines before and after a match. The cause of an error is often a few lines above the message itself. For very large files, less lets you scroll and search interactively (type /ERROR and press n for the next match), and tail -f run.log follows a log while a long job is still writing it.

Comparing outputs between runs

Much debugging comes down to one question: what changed between the run that worked and the run that failed? The shell answers it directly. diff old.log new.log prints the lines that differ, and diff -u shows them with a little surrounding context, in the same format code reviews use. For whole directories, diff -rq good_run/ bad_run/ lists which files differ without printing their contents.

Logs often contain timestamps or run directories that differ every time and hide the real change. Filter them out before comparing:

grep -v "Time:" good.log > a.txt
grep -v "Time:" bad.log  > b.txt
diff -u a.txt b.txt | head -40

The same idea works for netlists, cell counts and register dumps. Keep a copy of the output from a known good run, and comparing against it becomes a quick first step whenever something breaks.

Pipes: small tools joined together

The shell's real power is the pipe, |, which sends one command's output into the next. Each tool does one small thing, and you chain them to answer a question.

Suppose a regression writes one line per test like test_fifo_overflow seed=42 PASS. To list the failing tests and count how often each failed:

grep FAIL regress.txt | awk '{print $1}' | sort | uniq -c | sort -rn

Read it left to right: keep failing lines, take the first field (the test name), sort so identical names are adjacent, count each group, then sort by count, highest first. The result tells you immediately whether one test fails on many seeds or many tests fail once, which point to very different problems.

Redirection is the other half: > writes output to a file (overwriting it), >> appends, and 2>&1 sends error messages to the same place as normal output. Many tools print errors on the error stream, so make sim > sim.log 2>&1 captures everything.

Small scripts for repeated work

When you type the same sequence of commands a third time, put it in a script. A short Bash script that runs every test and reports a summary:

#!/usr/bin/env bash
set -u
pass=0; fail=0
mkdir -p build
for t in tests/*.v; do
    name=$(basename "$t" .v)
    if iverilog -o "build/$name" rtl/*.v "$t" &&
       vvp "build/$name" | grep -q "PASS"; then
        pass=$((pass + 1))
    else
        fail=$((fail + 1)); echo "FAIL: $name"
    fi
done
echo "passed=$pass failed=$fail"
[ "$fail" -eq 0 ]

Save it as run_tests.sh, make it executable with chmod +x run_tests.sh, and run ./run_tests.sh. The last line makes the script's exit status non-zero if anything failed, so a CI job or make target can use it directly. Quote variables ("$t") so file names with spaces do not break the loop.

Environment variables and tool versions

Tools find each other and their data through environment variables. PATH lists the directories searched for commands; others point to libraries or process design kits. When a tool is "not found" or the wrong version runs, check these first:

echo "$PATH"
which iverilog        # which copy will actually run
iverilog -V | head -1 # its version
export PDK_ROOT="$HOME/pdks"   # set for this shell and its children

A variable set with export lasts only for the current shell session. To make it permanent, add the line to your shell start-up file, usually ~/.bashrc. Many teams keep a small env.sh per project and source env.sh before working, so everyone uses the same tool versions.

Common mistakes

  • Running rm -rf with a variable that might be empty. rm -rf "$DIR/" with an unset DIR targets /. Use set -u in scripts and check paths before deleting.
  • Forgetting 2>&1. The error you need was printed on the error stream and never reached the log.
  • Spaces in file names without quotes. The loop splits one name into two arguments.
  • Editing PATH permanently with a mistake. Every new shell then breaks; test with export first.

Try it yourself

  1. Install Icarus Verilog on Linux or WSL2, write two tiny testbenches that print PASS or FAIL, and run the script above on them.
  2. Create a fake regression file with a few dozen name seed=N PASS/FAIL lines and use the grep | awk | sort | uniq -c pipeline to rank failures.
  3. Run a Yosys synthesis with output captured using > synth.log 2>&1, then use grep -i warning and grep -B2 -A5 to read the warnings in context.
  4. Write an env.sh that sets PATH and one tool variable for a project, source it, and confirm with which that the right tools run.
