Building a single-cycle RISC-V datapath on paper first

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

Before writing CPU RTL, trace each instruction class through fetch, decode, execute, memory and write-back on paper. You get the control table, the muxes and the critical path almost for free.

Many students who start a RISC-V core open an editor and begin typing Verilog. A few hundred lines later the core runs addi but not sw, and nobody can say which multiplexer is wrong. The fix is old-fashioned: draw the datapath on paper, and trace every instruction class through it by hand before writing a line of RTL. An hour of tracing gives you the list of blocks, every multiplexer, the full control table and a first estimate of the clock period.

The five steps every instruction takes

A single-cycle core does all the work for one instruction between two clock edges. Conceptually there are five steps:

  1. Fetch: the program counter (PC) addresses instruction memory and the 32-bit instruction comes out.
  2. Decode: the fields are sliced, the register file reads rs1 and rs2, and the immediate is rebuilt.
  3. Execute: the ALU computes a result, an address, or a branch comparison.
  4. Memory: loads read data memory; stores write it.
  5. Write-back: a result goes into rd, and the PC is updated to PC + 4, a branch target or a jump target.

Not every instruction uses every step. A store has no write-back; an add never touches data memory. Tracing shows you exactly which parts each class uses, and that is where the multiplexers come from.

Trace one instruction of each class

Take five instructions and push each through the drawing with a pencil. Mark the wires that carry useful data and note what every multiplexer must select.

  • add x3, x1, x2 (R-type): register file reads x1 and x2; the ALU operand mux selects rs2; the ALU adds; data memory is idle; the write-back mux selects the ALU result; the register file writes x3; next PC is PC + 4.
  • addi x3, x1, 5 (I-type): same as add, except the ALU operand mux selects the immediate.
  • lw x6, 8(x5) (load): the ALU adds x5 and 8 to form an address; data memory reads; the write-back mux selects the loaded data. This instruction uses every block in series.
  • sw x6, 8(x5) (store): the ALU forms the address as for a load; rs2 (x6) goes to the data memory's write port; the register file does not write.
  • beq x1, x2, label (branch): the ALU compares x1 and x2; a separate adder computes PC + offset; if they are equal, the next-PC mux selects the target. No memory access, no register write.

jal, jalr, lui and auipc add a few more inputs: the write-back mux gains a PC + 4 input for the return address, and the ALU's first operand may need to be the PC for auipc. Draw them in too.

The control table falls out of the trace

Each multiplexer select and each write enable becomes a column. Each instruction class becomes a row. Filling it from your traces gives the control unit directly:

Class ALU operand B Memory Reg write Write-back source
R-type rs2 none yes ALU
I-type ALU imm none yes ALU
Load imm read yes memory
Store imm write no (none)
Branch rs2 none no (none)
jal (unused) none yes PC + 4

Add a next-PC column (PC + 4, branch target if taken, jump target) and an ALU-operation column driven by funct3 and funct7, and you have the whole decoder on one page. In RTL it becomes a case on the opcode with a handful of assignments per row. When a test fails later, you can check the waveform against the table row by row.

The critical path, also on paper

Because everything happens in one cycle, the clock period must cover the slowest instruction. Write a delay next to each block and add them along each class's path. With delays made up for illustration (instruction memory 250 ps, register read 150 ps, ALU 200 ps, data memory 250 ps, write-back mux plus register setup 50 ps):

Class Blocks on the path Total
R-type imem, regfile, ALU, mux 250 + 150 + 200 + 50 = 650 ps
Store imem, regfile, ALU, dmem 250 + 150 + 200 + 250 = 850 ps
Load imem, regfile, ALU, dmem, mux 250 + 150 + 200 + 250 + 50 = 900 ps

The load sets the period at 900 ps, so the core runs at about 1.11 GHz in this made-up technology, and every add wastes 250 ps waiting. That waste is exactly what pipelining recovers, and you can see it before writing any code.

Common mistakes

  • Drawing one memory. A single-cycle core fetches and loads in the same cycle, so it needs separate instruction and data ports.
  • Letting x0 be written. The register file must ignore writes to x0; mark it on the drawing.
  • Forgetting byte enables. sb and sh write only some bytes of a word, so the data memory needs per-byte write enables.
  • Leaving control signals undefined for some rows. Unused selects should still have a safe default, especially register write and memory write, which must be off.

Try it yourself

  1. Print the datapath above, then trace jalr x1, 0(x5) and auipc x7, 0x10. Add whatever wires and mux inputs they need.
  2. Turn your control table into a Verilog case statement and simulate a small core in Icarus Verilog with a self-checking program of one test per class.
  3. Compare your trace with a waveform in GTKWave: for each instruction, check every select signal against the table before trusting the result.
