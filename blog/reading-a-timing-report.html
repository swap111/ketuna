How to read a static timing report line by line

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

A timing report is two sums, one for when data arrives and one for when it is needed. Walk through a setup path line by line and learn what launch, capture, arrival, required time and slack mean.

In this article
  1. The header names the race
  2. The arrival section: when the data gets there
  3. The required section: when the data is needed
  4. Slack is the gap between the two
  5. Questions to ask of every failing path
  6. Try it yourself

A static timing report looks like a column of small numbers with cryptic pin names beside them. Most beginners jump straight to the last line, see "slack (MET)" or "slack (VIOLATED)", and stop. That last line is the answer, but the lines above it are the working, and when a path fails you need the working to know what to change. This article walks through one report from top to bottom.

The header names the race

Every path report starts by saying which race it describes:

Startpoint: a_q[0] (rising edge-triggered flip-flop clocked by clk)
Endpoint: sum_q[8] (rising edge-triggered flip-flop clocked by clk)
Path Group: clk
Path Type: max
  • Startpoint is where the data is launched, usually a flip-flop's clock pin or an input port.
  • Endpoint is where it is captured, usually a flip-flop's data pin or an output port.
  • Path Type: max means a setup check: the tool used the longest delays because it wants to know whether data can be too late. A min path is a hold check, built from the shortest delays, asking whether data can be too early.

Both flops here are clocked by clk on the rising edge, so the capture edge is one full period after the launch edge.

The arrival section: when the data gets there

Here is an illustrative report in the format OpenSTA prints, for a 4.0 ns clock. The numbers are made up for illustration.

  Delay    Time   Description
-------------------------------------------------------
   0.00    0.00   clock clk (rise edge)
   0.45    0.45   clock network delay (propagated)
   0.00    0.45 ^ a_q_reg_0_/CLK (dfrtp_1)
   0.38    0.83 ^ a_q_reg_0_/Q (dfrtp_1)
   0.21    1.04 v _201_/Y (nand2_1)
   0.35    1.39 ^ _214_/Y (a21oi_1)
   0.52    1.91 ^ _230_/X (maj3_1)
   0.44    2.35 ^ _236_/X (maj3_1)
   0.30    2.65 v _241_/Y (xnor2_1)
   0.18    2.83 v _250_/X (buf_2)
   0.27    3.10 v sum_q_reg_8_/D (dfrtp_1)
           3.10   data arrival time

Read it as a stopwatch. The Delay column is the time added by each line; the Time column is the running total.

  1. At time 0 the ideal clock edge happens at the clock source.
  2. It takes 0.45 ns to travel through the clock tree to the launch flop. This is the launch clock latency.
  3. The flop's clock-to-Q delay adds 0.38 ns. The new value appears on Q at 0.83 ns.
  4. Each gate adds its delay. The ^ and v marks show whether that pin is rising or falling; the tool tracks both because a cell's rise and fall delays differ.
  5. The data reaches the capture flop's D pin at 3.10 ns. That is the data arrival time.

The delay on each line includes both the cell and the wire driving the next pin. In a report from after routing, wire delay can be a large part; before placement, it is only an estimate.

The required section: when the data is needed

   4.00    4.00   clock clk (rise edge)
   0.48    4.48   clock network delay (propagated)
  -0.25    4.23   clock uncertainty
   0.00    4.23   clock reconvergence pessimism
           4.23 ^ sum_q_reg_8_/CLK (dfrtp_1)
  -0.12    4.11   library setup time
           4.11   data required time

This is the other runner. The next rising edge happens at 4.00 ns, one period later. It reaches the capture flop 0.48 ns later through its own branch of the clock tree (capture clock latency). Then two deductions:

  • Clock uncertainty, set in your constraints, is a margin for jitter and anything not modelled. Here 0.25 ns is taken away.
  • Library setup time of the capture flop, 0.12 ns, comes from the cell library. The data must be there this long before the edge.

The result, 4.11 ns, is the data required time: the latest moment the data may arrive.

Slack is the gap between the two

           4.11   data required time
          -3.10   data arrival time
-------------------------------------------------------
           1.01   slack (MET)

For a setup check, slack = required − arrival. Positive slack means the data arrived with time to spare; negative slack means it was late. Here we have 1.01 ns of margin.

Slack tells you more than pass or fail:

  • How much margin you have. A path with 1.01 ns of slack at 4.0 ns could tolerate the period shrinking by about that much, all else equal. Remove the 1.01 ns and the period would be 2.99 ns.
  • Where to look when it is negative. A path with −0.05 ns slack is a small fix: resize a cell, shorten a wire. A path with −1.5 ns needs a change in architecture or RTL.
  • That the clock tree helps or hurts. The capture latency (0.48) is larger than the launch latency (0.45), so the 0.03 ns of skew gave this setup path a little extra time. The same skew would make a hold check on these flops harder.

For a hold report the subtraction flips: slack = arrival − required, because data must arrive after the hold requirement, and the capture edge is the same edge as the launch.

Questions to ask of every failing path

  • Is most of the delay in cells or in wires? Many small cell delays mean deep logic; one big jump on a single line usually means a long wire or a weak driver with a heavy load.
  • Is the clock latency very different between launch and capture? Large skew may be a clock tree problem rather than a logic problem.
  • Is this even a real path? A path between two unrelated clocks, or through a configuration register that never changes during operation, may need a constraint rather than a fix.

Try it yourself

  1. Synthesise a small registered adder with Yosys against a sky130 standard-cell library.
  2. In OpenSTA, run read_liberty, read_verilog, link_design, then create_clock -period 4 [get_ports clk].
  3. Run report_checks -path_delay max -fields {slew cap} and match every line to the sections above. Then run report_checks -path_delay min for the hold view.
  4. Before running, add up the cell delays you expect by hand. Compare, and explain any difference.
