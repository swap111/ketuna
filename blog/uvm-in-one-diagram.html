UVM in one diagram: sequences, drivers, monitors and the agent

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

One picture of a UVM testbench, from test to pins, with what each component owns, how transactions flow between them, and why splitting the work this way lets the same pieces be reused.

The Universal Verification Methodology (UVM, standardised as IEEE 1800.2) looks intimidating mainly because of its vocabulary. There are dozens of base classes, and tutorials often start with phases and factories before showing why any of it exists. Underneath, a UVM testbench is a small number of components, each doing one job, connected in a fixed pattern. If you can draw that pattern from memory, the rest is detail you can look up.

The picture

There are two paths in this picture, and they never mix. The stimulus path goes from a sequence, through the sequencer and driver, to the pins. The observation path goes from the pins, through the monitor, to the scoreboard and coverage. Nothing on the observation path asks the stimulus path what it meant to do; it looks only at what actually happened on the wires.

What each piece is responsible for

  • Sequence item. One transaction as data: an address, write data, a direction. No timing, no pins. It knows how to copy, compare and print itself.
  • Sequence. Decides what to send. Its body() creates items, randomises them under constraints and hands them over one at a time. A test can run several sequences, and a sequence can start other sequences.
  • Sequencer. Arbitrates when several sequences want the same interface, and passes one item at a time to the driver. You rarely write any code in it.
  • Driver. Decides how to send. It pulls an item with get_next_item, wiggles the pins through a virtual interface according to the protocol, and calls item_done. It is the only component that knows the protocol's timing for driving.
  • Monitor. Passive. It samples the pins, reassembles complete transactions, and broadcasts each one on an analysis port. It never drives anything.
  • Agent. A container for one interface's sequencer, driver and monitor. An active agent has all three; a passive agent has only the monitor.
  • Scoreboard and coverage. Subscribers to the monitor's broadcasts. The scoreboard checks against a reference model; the coverage collector counts which plan items occurred.
  • Env. Holds the agents and checkers for one block or subsystem.
  • Test. Builds and configures the env, picks the sequences, and decides when the run ends by raising and dropping an objection.

Why the separation pays off

Splitting "what", "how" and "check" into separate classes looks like ceremony on a small block. It earns its keep the moment anything changes.

New tests cost only a sequence. A test that hammers back-to-back writes, one that does reads after reset, and one that randomises everything all reuse the same driver, monitor and scoreboard. You write a new body(), not a new testbench.

Passive agents move up to chip level. When your block is placed in a larger system, its interface is driven by real RTL, not by your driver. Switch the agent to passive, and its monitor, scoreboard and coverage keep checking the block inside the bigger design with no edits. This is the main reason the monitor must not depend on the driver: at chip level there is no driver.

Checks see the truth. Because the scoreboard is fed from the monitor, it checks what the pins actually did. If the driver has a bug and sends the wrong thing, the model predicts from what was really sent, and the mismatch points at the design only when the design is wrong.

Analysis ports decouple observers. A monitor's write() broadcasts to any number of subscribers and never blocks. Adding a protocol checker or a transaction logger means connecting one more subscriber, not editing the monitor.

Three supporting mechanisms

Three UVM facilities hold the structure together. You can learn them after the picture makes sense.

  • Phases run in the same order for every component: build, connect, then the time-consuming run phase in parallel, then check and report. They guarantee that everything exists and is connected before simulation time starts.
  • The configuration database passes settings, such as the virtual interface handle or active/passive mode, down the hierarchy by path, so components do not need hard-wired references to each other.
  • The factory lets a test replace one component type with another, for example a driver that injects errors, without editing the env.

Common mistakes

  • Checking inside the driver. It feels convenient, but it disappears when the agent becomes passive. Checks belong on the observation path.
  • Monitors that peek at the sequence. If the monitor learns the expected value from the stimulus side, a dropped transaction becomes invisible.
  • Protocol timing in the sequence. Sequences should not count clock cycles on pins; that couples them to one interface and breaks reuse.

Try it yourself

  1. Draw the diagram above from memory for a simple valid/ready interface, and label which class owns the handshake timing.
  2. Install pyuvm and cocotb in a Python virtual environment and build the smallest version: one item, one sequence, a driver, a monitor and a scoreboard around a register or FIFO, simulated on Icarus Verilog.
  3. Write a second sequence and a second test that reuse every other component unchanged.
  4. Disable the driver and drive the pins from a plain cocotb coroutine instead; confirm the monitor and scoreboard still work, which is the passive-agent idea in miniature.
