What simulation cannot tell you about clock domain crossings

Verification Advanced 27 Nov 2026 5 min read By Ketuna

RTL simulation never goes metastable and resolves every synchronizer in a fixed number of cycles, so it hides real CDC bugs. Structural checks, randomised synchronizer delay and targeted assertions fill the gap.

In this article
  1. What RTL simulation assumes
  2. Bugs that hide behind those assumptions
  3. Structural checks come first
  4. Making simulation less optimistic
  5. Assertions on the crossing rules
  6. Try it yourself

Clock domain crossing bugs have an unpleasant profile: they pass every simulation, pass static timing because the crossing paths are excluded, and then appear on silicon as rare, temperature-dependent failures that nobody can reproduce on demand. The reason is not that teams test too little. It is that RTL simulation is structurally unable to show the failure mechanisms of asynchronous crossings. Knowing exactly what it hides tells you which other checks you need.

What RTL simulation assumes

An RTL simulator evaluates a flip-flop as an ideal sampler. On the clock edge it takes whatever value its input holds and presents it at the output after zero or one delta cycle. There is no setup window, no hold window and no metastability. Two consequences follow.

First, a two-flop synchronizer in simulation always has exactly the same latency, determined only by when the source changes relative to the destination clock edges in the simulated waveform. On silicon, when the input changes close to an edge, the first flop may resolve either way, so the signal arrives one destination cycle earlier or later. Its latency is non-deterministic by one cycle.

Second, clocks in a testbench usually have fixed, rational periods, such as 10 ns and 15 ns. Their relative phase repeats every few cycles, so the simulation explores only a handful of alignments. Real asynchronous clocks drift through every phase.

Bugs that hide behind those assumptions

Multi-bit values synchronized bit by bit. If a 4-bit value changes from 0111 to 1000 and each bit has its own synchronizer, silicon can deliver any mixture for a cycle, such as 1111 or 0000. In simulation every bit arrives on the same edge, and the intermediate value never appears.

Reconvergence. Two control signals synchronized separately and then combined, as in the diagram, can arrive one cycle apart even if they changed together. Logic that expects them to agree sees a mismatch that simulation never produces.

Pulses lost between slow edges. A one-cycle pulse from a fast domain may fall entirely between two edges of the slower clock. Whether simulation catches this depends on the chosen periods and phases; a lucky ratio can make the pulse land on an edge every time.

Data sampled before it is stable. A handshake that sends a request and changes the data in the same source cycle relies on the data path being faster than the request synchronizer. Simulation with zero-delay wires always agrees; silicon may not.

Structural checks come first

The most effective defence is static. Structural CDC analysis reads the design, identifies which clock drives each flop, and examines every path where data moves between flops in different domains. It reports crossings with no synchronizer, combinational logic in front of the first synchronizer flop (which can glitch), multi-bit buses whose bits are synchronized separately, and signals that reconverge after separate synchronization.

Dedicated CDC tools do this thoroughly. In a fully open-source flow the support is thinner, so design discipline matters more: put every crossing in a small set of reviewed synchronizer modules (two-flop, toggle pulse, handshake, asynchronous FIFO), forbid crossings anywhere else, and have each crossing reviewed by a second engineer. A netlist script that lists every flop-to-flop path between clock domains and flags any that does not end in an approved synchronizer is a worthwhile project in itself.

Making simulation less optimistic

You cannot make an RTL simulator go metastable, but you can make it model the consequence: uncertain latency. Give the synchronizer a simulation-only mode that randomly adds a cycle.

module sync2 (input wire clk, input wire d, output wire q);
  reg s1, s2;
  always @(posedge clk) begin s1 <= d; s2 <= s1; end
`ifdef CDC_RANDOM_DELAY
  reg s3, pick;
  always @(posedge clk) begin
    s3 <= s2;
    if (s1 != s2) pick <= $urandom % 2;   // choose on each change
  end
  assign q = pick ? s3 : s2;
`else
  assign q = s2;
`endif
endmodule

With the define set, each change takes either two or three cycles to appear, chosen randomly per change and reproducible through the simulator's seed. Separately synchronized bits now arrive out of step, and reconvergence bugs that were invisible start failing. Run the regression with and without the define, and with several seeds.

Two more habits help. Use clock periods with an awkward ratio, such as 10 ns and 13.7 ns, so the relative phase walks through many alignments. And vary the phase offset of the second clock between seeds.

Assertions on the crossing rules

Each synchronization scheme has rules that make it safe. Write them down as assertions in the source domain, where they can be checked in every simulation.

// Gray-coded pointer: at most one bit changes per source clock
a_gray_one_bit: assert property (@(posedge clk_a) disable iff (!rst_a_n)
                  $countones(wptr_gray ^ $past(wptr_gray)) <= 1);

// Handshake: data stays stable while the request is outstanding
a_data_held: assert property (@(posedge clk_a) disable iff (!rst_a_n)
               req && !ack_sync |=> $stable(data));

// Level signal into a slower domain lasts long enough to be seen
a_min_width: assert property (@(posedge clk_a) disable iff (!rst_a_n)
               $rose(flag) |=> flag[*3]);

The last one needs its repeat count derived from the actual clock ratio, with margin; three cycles here is only a placeholder. These assertions check the protocol that makes the crossing safe. They do not prove the absence of metastability, but they catch the design mistakes that turn metastability into a functional failure.

Try it yourself

  1. Build an asynchronous FIFO, or take one from your coursework, and simulate it with Icarus Verilog using clocks of 10 ns and 13.7 ns.
  2. Replace the Gray-code pointer synchronizer with one that synchronizes the binary pointer bit by bit, and confirm that plain simulation still passes.
  3. Add the random-delay sync2 with -DCDC_RANDOM_DELAY and run several seeds; see whether the scoreboard now catches corrupted data.
  4. Add the Gray-code assertion and check it fires immediately on the binary version.
