The valid/ready handshake: the rules that keep pipelines from losing data

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

A transfer happens on a clock edge where valid and ready are both high. Learn the rules that follow from that, why valid must never wait for ready, and how backpressure ripples back through pipeline stages.

Almost every streaming interface inside a chip, from a sensor front end to a DMA engine, uses the same two-wire handshake: the sender drives valid, the receiver drives ready. It looks trivial. Yet many integration bugs in streaming designs are handshake bugs: data dropped during a stall, a word sent twice, or two blocks waiting for each other forever. They all come from breaking one of a handful of rules.

When a transfer happens

The core definition is one sentence:

A transfer happens on a rising clock edge where valid and ready are both 1.

Nothing else counts. valid high with ready low means "I have data, you are not taking it": the sender must wait. ready high with valid low means "I could take data, you have none": nothing happens. Only the coincidence of both on an edge moves a word.

The sender's rules

Once valid is high, it stays high until the transfer. The sender may not change its mind and withdraw a word because ready was low for a while. A receiver that is about to accept, say because it needed a cycle to free space, would otherwise miss data it was promised.

While valid is high, the data must not change. The receiver may sample the data on any edge where it raises ready. If the sender swapped D0 for D1 during a stall, D0 would be lost.

Valid must not depend on ready. The sender decides whether it has data based on its own state, never by waiting to see ready first. This is the rule that prevents deadlock. If the sender waits for ready before raising valid, and the receiver waits for valid before raising ready, which many receivers legitimately do, neither will ever move. It also forbids a combinational path from ready to valid in the sender, which could form a loop with a receiver whose ready depends on valid.

The receiver's rules

Ready may depend on valid. A receiver is allowed to look at valid before deciding to accept. It may also raise ready in advance, with no data present, which is often the simplest design.

Ready may be withdrawn at any time before the transfer. Unlike valid, ready carries no promise. A receiver can raise it, lower it again, and raise it later. Only an edge with both high counts.

Sample on the transfer edge, not before. A receiver that captures data on edges where valid is high but ready is low will capture the same word several times. Use the condition valid && ready everywhere a transfer is counted: write enables, counters, last-beat detection.

A pipeline stage with backpressure

A pipeline built from handshaking stages must pass backpressure, the "I am full" condition, backwards. Here is the simplest correct register stage:

module hs_stage #(parameter int W = 16) (
  input  logic         clk, rst_n,
  input  logic         in_valid,
  output logic         in_ready,
  input  logic [W-1:0] in_data,
  output logic         out_valid,
  input  logic         out_ready,
  output logic [W-1:0] out_data
);
  // can accept if empty, or if the held word leaves this cycle
  assign in_ready = !out_valid || out_ready;

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n)        out_valid <= 1'b0;
    else if (in_ready) out_valid <= in_valid;

  always_ff @(posedge clk)
    if (in_ready && in_valid) out_data <= in_data;
endmodule

Trace a stall. The downstream block drops out_ready. If the stage holds a word, in_ready falls in the same cycle, so the upstream stage holds its word too. When out_ready returns, the held word leaves and a new word enters on the same edge, so throughput stays at one word per cycle.

How backpressure ripples, and its cost

Look at in_ready: it is a combinational function of out_ready. Chain eight of these stages and the ready from the far end passes through eight gates back to the start in one cycle. The forward path, valid and data, is registered at every stage and short; the backward ready path grows with pipeline depth. In a long pipeline, or one spread across a large die, that path becomes the critical timing path.

You cannot simply add a flop to ready, because the sender would see a stale ready and push a word the receiver cannot take, losing data. The standard fix is a stage that registers ready and adds a second storage slot to catch the word that arrives during the one-cycle delay: a skid buffer. That design deserves its own article.

Common mistakes

  • Dropping valid, or changing data, during a stall
  • Generating valid from ready, creating deadlock or a combinational loop
  • Counting a beat whenever valid is high instead of on valid && ready
  • Registering ready with a plain flop and losing the word that arrives in the gap
  • Not resetting valid, so the pipeline starts with garbage words in flight

Try it yourself

  1. Draw the waveform above on paper for three words with two stalls, marking every transfer edge, before you simulate anything.
  2. Chain three hs_stage instances in Icarus Verilog or Verilator, drive out_ready with a random pattern from a cocotb test, and check with a scoreboard that every word arrives once, in order.
  3. Write SystemVerilog assertions for the sender rules, for example that valid high with ready low implies valid stays high and data is unchanged on the next cycle, and check them with SymbiYosys.
