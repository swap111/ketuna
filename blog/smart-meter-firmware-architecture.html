Firmware architecture for a smart energy meter: metering, events and logs

Embedded systems Advanced 27 Nov 2026 5 min read By Ketuna

How to structure smart meter firmware so metering is never disturbed by communication, tamper events are recorded reliably, and energy totals survive sudden power loss, with the hold-up and flash-wear arithmetic.

In this article
  1. Three layers with different rules
  2. Passing data upward without locks
  3. Surviving power loss
  4. The event log
  5. Try it yourself

An energy meter looks like a simple device: measure voltage and current, multiply, add up, show a number. The firmware is harder than that, because three demands pull against each other. Metering must run continuously and accurately whatever else happens. Communication stacks are large, change often and occasionally misbehave. And the energy total and every tamper event must survive a power cut that arrives without warning, in a device that is powered by the very supply it measures. This article describes an architecture that keeps those demands apart, with the arithmetic behind the design choices.

Three layers with different rules

Split the firmware by how much each part is allowed to be delayed:

The metering engine samples voltage and current at a fixed rate, typically through a timer-triggered ADC and DMA, computes power over each mains cycle and adds energy into accumulators. It runs at the highest interrupt priority or on a dedicated measurement front end. It never waits for anything and never calls into the layers below.

Events and storage detects tamper conditions and power events, timestamps them, and manages non-volatile memory: the event log and the saved energy registers.

Application and communication formats the display, applies tariffs, and runs the network or optical-port protocol stack. It is the largest and least predictable code, so it runs at the lowest priority and can be delayed or even restarted without affecting the layers above.

Where a meter must be certified, keeping the metrology code in a separate module with a narrow interface also lets the communication firmware change without disturbing it. The rules on what must be re-evaluated after a change vary; check the current requirements that apply to your product.

Passing data upward without locks

The communication layer needs the latest readings, but it must never stop the metering engine with a lock. A common pattern is a sequence-counted snapshot: the writer increments a counter, copies the values, and increments the counter again; the reader copies the values and retries if the counter was odd or changed during its copy. The writer never waits, and the reader always gets a consistent set. On a single core this needs only that the counter updates are not reordered around the copy, which C11 atomics or compiler barriers provide.

Surviving power loss

Energy totals live in RAM while the meter runs, because writing non-volatile memory constantly would wear it out. Consider the numbers: if the flash datasheet specified, say, 100,000 erase cycles per sector, and you saved the totals to the same sector once a minute, the sector would reach its limit in about 69 days. Wear-levelling across many sectors helps, but the better design writes rarely and saves precisely when it matters.

So the meter saves when power is failing. A comparator watches an early point in the supply, before the regulator, and interrupts the processor as soon as it starts to drop. From then on, the remaining energy in the supply's hold-up capacitor is all you have:

thold = C × (V12 − V22) / (2 × P)

With illustrative values of 470 µF, a rail falling from 12 V to the 8 V at which the regulator drops out, and a 0.2 W load, thold = 470 µF × (144 − 64) V2 / 0.4 W ≈ 94 ms. The save must fit comfortably inside that, measured on real hardware at the worst load.

#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint32_t magic, seq;
    uint64_t import_wh_x1000, export_wh_x1000;  /* integer milli-Wh */
    uint32_t rtc_seconds;
    uint32_t crc;
} energy_rec_t;

void power_fail_isr(void)                       /* highest priority */
{
    loads_off();                 /* display backlight, radio, LEDs */
    energy_rec_t r = {
        .magic = 0x454E5247u, .seq = next_seq++,
        .import_wh_x1000 = acc_import, .export_wh_x1000 = acc_export,
        .rtc_seconds = rtc_now(),
    };
    r.crc = crc32(&r, offsetof(energy_rec_t, crc));
    nvm_write_preerased(next_slot, &r, sizeof r); /* no erase here */
    for (;;) { }                 /* wait for the supply to collapse */
}

Three details make this work. The first action switches off every load that is not needed, which stretches the hold-up time. The record goes into a slot that was erased in advance during normal operation, because a flash erase takes far longer than a write and might not finish. And each record carries a sequence number and a CRC, so at start-up the firmware picks the newest valid record and ignores one that was cut short. The CRC routine must be fast too; measure the whole handler with a GPIO toggle and compare it with the hold-up budget.

The event log

Tamper events, such as a cover opened, a strong magnetic field near the meter, reversed current flow or a missing neutral, must be recorded when they happen, not at the next convenient moment. Each is written as a fixed-size record to an append-only log in non-volatile memory: sequence number, timestamp, event type, a few bytes of data, and a CRC. The log occupies a ring of sectors; the sector after the current one is always kept erased, so appending never waits for an erase, and when the ring wraps the oldest sector is erased in the background.

Design points worth reviewing:

  • Record before reacting. Write the event first, then update the display or notify the network, so a power cut mid-way still leaves the evidence.
  • Debounce in time, not by dropping events. A cover switch that bounces should produce one event with a start and end time, not fifty.
  • Detection while unpowered. Some tamper events happen with mains removed; a battery-backed real-time clock and a wake-capable input can timestamp them.
  • Integrity. CRCs catch corruption. If records must also be trusted as evidence, add a cryptographic authentication code per record or per block.

Try it yourself

  1. Write the energy record save and the start-up "newest valid record" search in C, and test them on your laptop with simulated flash that can lose power after any byte.
  2. Implement the sequence-counted snapshot and test it with a host program that calls the writer from a POSIX signal handler while the reader loops.
  3. Calculate the hold-up time for your own supply design, then measure it with an oscilloscope by switching off the input and timing the rail from the comparator threshold to the regulator's drop-out.
