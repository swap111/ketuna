Floorplanning a low-power drone controller chip: motor PWM, sensors and always-on logic

Physical design & tape-out Advanced 27 Nov 2026 6 min read By Ketuna

A flight controller chip mixes noisy motor outputs, sensitive sensor interfaces, a processor and always-on logic. Work through partitioning it into regions, power domains and pin groups, and why each choice is made.

In this article

  2. Power domains follow behaviour
  3. Regions on the die

  5. Clocking the PWM
  6. What to verify
  7. Try it yourself

Most floorplanning examples are a single block of logic with a memory or two. A small control chip for a drone's flight controller is a better exercise, because its parts have conflicting needs. Motor outputs switch hard and are electrically noisy; sensor interfaces want quiet; the processor wants to sleep between control loops; and something must stay awake to wake it and to keep the motors in a safe state. This article partitions a hypothetical chip of this kind, a design concept for learning rather than a product, and explains each floorplan decision.

A note on scope: a flight controller is safety-relevant. Real flight systems need independent failsafes, extensive testing and compliance with the applicable rules. Nothing in a floorplan replaces that.

The functions to place

Assume the chip contains:

  • A small processor core with instruction and data SRAM, running the attitude control loop.
  • A sensor interface block: SPI and I2C controllers for an inertial measurement unit (IMU), a barometer and a magnetometer, with timestamping.
  • A motor PWM block: four or more PWM channels driving external motor controllers, with dead-time logic and a hardware disarm input.
  • Always-on logic: a real-time counter, a wake-up controller, the power-management state machine, and a watchdog.
  • Debug and test: JTAG, scan control and a UART for telemetry.

Power domains follow behaviour

Partition by what must stay on, not by function names.

Domain Contents Why
Always-on (AON) Wake controller, real-time counter, watchdog, power state machine, PWM safe-state logic Must work when everything else sleeps; must force motors to a known state
Core (switchable) Processor, SRAM, sensor controllers, UART Largest leakage; can sleep between loops or when disarmed
I/O Pad ring, possibly at a higher voltage Interfaces with external parts

The PWM block deserves care. Its counters and comparators can live in the switchable core, but the logic that defines the output state when the core is off, or when the watchdog fires, must be always-on. In practice that means isolation cells on the PWM outputs that clamp them to the "motor off" level, controlled from AON, and a hardware disarm path from an input pin to those clamps that does not pass through any software.

Regions on the die

Motor PWM on one edge, near its pads. PWM outputs drive off-chip loads through strong I/O drivers, and their edges inject noise into the supply and substrate. Grouping them on one side, with their own I/O supply and ground pads, keeps that noise local. Placing the PWM block right behind those pads keeps output paths short and the clamping isolation cells close to the boundary.

Sensors on the opposite edge. The IMU interface is the input to the control loop; corrupted samples become wrong motor commands. Putting the sensor pads and controllers far from the motor pads, with separate supply pads, reduces coupling. If the chip contains any analog sensing, such as an ADC for battery voltage, it belongs on this quiet side too, with its own supply and guard structures.

Processor and SRAM in the middle. The core talks to both the sensors and the PWM block, so it sits between them. The SRAM goes at the top edge of the core region, with its pins facing the processor, leaving one connected area for standard cells.

A compact always-on region near its pins. The AON domain is small. Placing it at a corner next to the crystal and wake-up pads keeps its supply and its signals short, and gives it a simple rectangular boundary with the core domain. Its control signals to the PWM clamps run along the bottom to the PWM region; they must be routed with always-on buffers if they cross the switchable core.

Pin groups

Plan pins in groups before drawing any region:

  • Motor group: PWM outputs, disarm input, with dedicated I/O power and ground pairs.
  • Sensor group: SPI and I2C pins and interrupt inputs from the sensors, with their own supply pair.
  • Clock and wake group: crystal or clock input, wake-up input, reset.
  • Debug group: JTAG, scan enable, UART.

Each group maps to one edge segment, and the package pinout should keep the same grouping so the board can keep noisy and quiet traces apart as well.

Clocking the PWM

PWM resolution follows directly from the timer clock. With illustrative numbers, a 50 MHz timer clock and a 20 kHz PWM frequency give 50,000,000 / 20,000 = 2,500 counts per period, a little over 11 bits of resolution. That timer clock must reach the PWM block cleanly, so the clock tree for that region should be short and balanced. If the processor clock is scaled down to save power, the PWM timer may need its own clock source so that motor timing does not change with the processor's frequency.

What to verify

  • Power-down behaviour: with the core off, every PWM output is clamped to the off level, in simulation with power-aware models and later on silicon.
  • Watchdog path: a watchdog timeout forces the clamps without software involvement.
  • Noise separation: supply pad counts and placement keep motor switching current off the sensor and core supplies.
  • Timing across domains, including isolation and any level shifters.

Try it yourself

  1. Write the pin table for this chip by hand, grouped as above, and choose a package pin count that fits it with enough power pairs.
  2. Implement a four-channel PWM block in Verilog with an always-on clamp input, and simulate in Icarus Verilog that a disarm forces all outputs off within one clock.
  3. Harden the PWM block alone with LibreLane on sky130, placing its outputs on one edge using the pin order configuration, and inspect the layout in KLayout.
  4. Sketch the floorplan on paper first, then ask a colleague to review it against the noise and power-domain rules above.
