Writing a little RISC-V assembly to understand what your C compiles to

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

Read compiler output for a loop and a function call with the RISC-V calling convention in hand. Learn which register holds what, why the stack frame looks the way it does, and how to check your reading.

You do not need to write programs in assembly to benefit from reading it. When a firmware bug only appears at -O2, when an interrupt handler is slower than expected, or when you want to know whether a loop really uses the instruction you designed into your core, the answer is in the compiler's output. Reading that output is a skill you can learn in an afternoon, provided you have two things in hand: the RV32I instructions and the calling convention. This article walks through two small functions.

The calling convention on one card

The ISA gives you 32 registers, x0 to x31. The calling convention, part of the ABI (application binary interface), says how compiled code uses them, so that functions compiled separately can call each other. The assembler accepts the ABI names, and compiler output uses them:

ABI name Register Role Preserved across a call?
zero x0 Always 0 (constant)
ra x1 Return address No
sp x2 Stack pointer Yes
a0 to a7 x10 to x17 Arguments; a0 and a1 also return values No
t0 to t6 x5 to x7, x28 to x31 Temporaries No
s0 to s11 x8, x9, x18 to x27 Saved registers; s0 can be the frame pointer Yes

Two rules carry most of the meaning. Arguments arrive in a0, a1, …, and the result leaves in a0. And s registers must be preserved by any function that uses them, while a and t registers may be destroyed by any call. The stack grows downwards and sp is kept 16-byte aligned.

A loop: where did my index go?

int sum(const int *a, int n)
{
    int s = 0;
    for (int i = 0; i < n; i++)
        s += a[i];
    return s;
}

Compiled for RV32I at -O2, the output looks like this. Exact register choices and labels vary with compiler version, so treat it as representative rather than exact:

sum:
    ble   a1, zero, .L4    # if n <= 0, return 0
    slli  a1, a1, 2        # n * 4: size in bytes
    add   a3, a0, a1       # a3 = &a[n], one past the end
    li    a5, 0            # s = 0
.L3:
    lw    a4, 0(a0)        # load *a
    addi  a0, a0, 4        # a++ (4 bytes per int)
    add   a5, a5, a4       # s += value
    bne   a0, a3, .L3      # loop until a reaches the end
    mv    a0, a5           # return s in a0
    ret
.L4:
    li    a0, 0
    ret

Read it with the convention in mind. a arrives in a0 and n in a1. The variable i has disappeared: the compiler turned a[i] into a pointer that advances by 4 bytes each iteration and compares it with an end pointer computed once before the loop. That removes a multiply (or shift) and an add from every iteration. The loop body is four instructions. The result is moved into a0 just before ret, which is a pseudo-instruction for jalr x0, 0(ra): jump to the return address and discard the link.

Two habits help here. Map each C variable to a register before reading the loop, and look for the loop's back branch (here bne ... .L3) to find the body quickly.

A function call: why the stack frame looks like that

int scale(int x);              /* defined elsewhere */

int twice_scaled(int x)
{
    return scale(x) + scale(x + 1);
}

Again at -O2, representative output:

twice_scaled:
    addi  sp, sp, -16      # make a 16-byte frame
    sw    ra, 12(sp)       # save return address
    sw    s0, 8(sp)        # save caller's s0
    sw    s1, 4(sp)        # save caller's s1
    mv    s0, a0           # keep x safe across the call
    call  scale            # a0 = scale(x)
    mv    s1, a0           # keep the first result safe
    addi  a0, s0, 1        # argument: x + 1
    call  scale            # a0 = scale(x + 1)
    add   a0, s1, a0       # sum, in the return register
    lw    ra, 12(sp)
    lw    s0, 8(sp)
    lw    s1, 4(sp)
    addi  sp, sp, 16
    ret

Every line follows from the convention:

  • call overwrites ra with its own return address, so ra must be saved first, or twice_scaled could never return to its caller.
  • x is needed after the first call, but a0 is not preserved across calls. The compiler copies it into s0, which scale must preserve. Because twice_scaled now uses s0, it must save the caller's s0 and restore it at the end. The same reasoning applies to s1, which holds the first result.
  • The frame is 16 bytes even though only 12 are used, to keep sp 16-byte aligned.

Compile the same function at -O0 and the picture changes: every variable lives in the stack frame, s0 is set up as a frame pointer, and each use reloads from memory. It is easier to map to the source line by line, and much slower. When a bug appears only at -O2, comparing the two outputs often shows which assumption the optimiser was entitled to make, such as a missing volatile.

Writing a few lines yourself

Reading leads naturally to writing small pieces. Here is sum written by hand, which you can assemble, link with a C main, and call:

    .text
    .globl sum_asm
sum_asm:                   # int sum_asm(const int *a, int n)
    li    t0, 0            # running sum in a temporary
1:  beqz  a1, 2f           # n == 0: done
    lw    t1, 0(a0)
    add   t0, t0, t1
    addi  a0, a0, 4
    addi  a1, a1, -1
    j     1b
2:  mv    a0, t0           # result in a0
    ret

It uses only a and t registers and calls nothing, so it needs no stack frame at all. Compare it with the compiler's version and you will see why the compiler moved the test out of the loop: yours runs two branches per iteration, the compiler's only one.

Common mistakes

  • Reading -O0 output as "what the program does". Optimised code can look completely different and still be correct.
  • Forgetting that a call destroys a and t registers. Any value needed afterwards must live in an s register or on the stack.
  • Not saving ra in a function that calls another. It returns to itself forever.
  • Misaligning the stack. Keep sp a multiple of 16 at call boundaries.

Try it yourself

  1. Compile both C functions with riscv64-unknown-elf-gcc -O2 -march=rv32i -mabi=ilp32 -S and compare with the listings above; then repeat with -O0.
  2. Assemble sum_asm, link it with a C test program, and run it under qemu-riscv32 or Spike, checking that it matches sum.
  3. Disassemble the linked program with riscv64-unknown-elf-objdump -d and find how call was encoded (as jal, or as an auipc and jalr pair).
