Inside an asynchronous FIFO: why the pointers cross in Gray code

Digital & VLSI design Advanced 27 Nov 2026 6 min read By Ketuna

An async FIFO works because each pointer crosses the clock boundary in Gray code, where only one bit changes per step. Learn the synchronization, the full and empty compares, and why the flags are safely pessimistic.

An asynchronous FIFO is the standard way to move a stream of data between two unrelated clocks. The memory itself is easy: a dual-port RAM written on one clock and read on the other. The hard part is that each side must know how full the FIFO is, and that requires sending a multi-bit pointer across the clock boundary, which is exactly what you are told never to do. The design works because of one property of Gray code, and every detail of the classic structure follows from protecting that property.

The structure

Each side keeps its own pointer, in its own clock domain. The write side increments wptr on every write; the read side increments rptr on every read. The pointers are one bit wider than needed to address the memory, so that full and empty can be told apart: for a 16-entry FIFO they are 5 bits.

To compute empty, the read side needs the write pointer. To compute full, the write side needs the read pointer. So each pointer is converted to Gray code in its home domain, registered, and passed through a two-flop synchronizer into the other domain.

Why binary pointers would fail

Suppose the write pointer crossed in binary. Going from 7 (0111) to 8 (1000) changes four bits at once. The synchronizer flops in the read domain may sample this change on the edge where it happens, and each bit can resolve to old or new independently. The read side might see 1111 (15) or 0000 (0), or any mix. Seeing 15 would make it believe eight extra entries are present, and it would read garbage. Seeing 0 might make it think the FIFO is empty when it is not, which is harmless, but the first case corrupts data.

Why Gray code fixes it

In Gray code consecutive values differ in exactly one bit. If the pointer changes from Gray(7) to Gray(8), only one bit is in flight. Whichever way that bit resolves in the synchronizer, the receiver sees either the old pointer or the new one, both of which were real values. The worst case is that it sees the old value for one extra cycle.

This only holds if three conditions are true:

  • The pointer changes by at most one step per source clock. A write pointer that jumps by two would change more than one Gray bit.
  • The Gray value comes straight from a register. If it came from combinational logic, glitches on the conversion could put multi-bit hazards on the wire. Register the Gray code in the source domain before it crosses.
  • The depth is a power of two. Gray code is cyclic, with one bit changing on the wrap, only over a power-of-two range. A depth of 12 would make the wrap from 11 to 0 change several bits.

Conversion is cheap in both directions:

// binary to Gray: one XOR per bit
function automatic logic [4:0] bin2gray(logic [4:0] b);
  return b ^ (b >> 1);
endfunction

// Gray to binary: a prefix XOR from the top bit down
function automatic logic [4:0] gray2bin(logic [4:0] g);
  logic [4:0] b;
  b[4] = g[4];
  for (int i = 3; i >= 0; i--) b[i] = b[i+1] ^ g[i];
  return b;
endfunction

The full and empty compares

With N+1-bit pointers in binary, the FIFO is empty when the pointers are equal and full when the low N bits are equal and the top bits differ. In Gray code the empty test is still plain equality, compared in the read domain:

assign empty = (rgray_next == wgray_sync);

The full test is less obvious. Because of the reflected structure of Gray code, the pattern that corresponds to "same position, one lap ahead" is the other pointer with its top two bits inverted and the rest equal:

assign full = (wgray_next == {~rgray_sync[4:3], rgray_sync[2:0]});

You can check this by hand: for a 16-entry FIFO, binary 3 and binary 19 (3 + 16) are one lap apart. Gray(3) is 00010 and Gray(19) is 11010. They differ in exactly the top two bits. Using _next values lets the flags be registered on the same edge as the pointer update, so they are ready without an extra cycle of delay.

Why the flags are pessimistic, and why that is safe

The synchronized pointer is two or three cycles old by the time it is compared. Consider each flag:

  • Empty uses a stale write pointer. The writer may have added entries the reader cannot see yet. So empty can stay asserted a little too long, but it can never deassert when the FIFO is truly empty, because the reader's own pointer is always current.
  • Full uses a stale read pointer. The reader may have freed entries the writer cannot see yet. So full can stay asserted a little too long, but never deasserts too early.

Both errors are in the safe direction: a side may wait a few cycles unnecessarily, but it never overwrites unread data or reads empty slots. The cost is that the usable throughput near full or empty is slightly lower, which is one reason to size the FIFO with margin.

Pitfalls seen in reviews

  • Synchronizing the binary pointer and converting to Gray afterwards
  • Computing Gray in combinational logic and sending it across unregistered
  • A non-power-of-two depth with the simple Gray scheme
  • Timing exceptions that declare the whole crossing a false path, which also hides excessive skew between the Gray bits; a max-delay constraint on the crossing keeps the bits arriving within about one destination clock period of each other
  • Using the almost-full count computed from a stale pointer as if it were exact

Try it yourself

  1. Write the two conversion functions in Python, print Gray codes for 0 to 31, and confirm that each step, including the wrap from 31 to 0, changes one bit. Check the "top two bits inverted" rule for every pair one lap apart.
  2. Study the asynchronous FIFO lab in Track A of the program's lab set, or build your own, and simulate it in Icarus Verilog with clock periods that are not multiples of each other, such as 7 ns and 11 ns.
  3. Add an assertion in the write domain that $countones(wgray ^ $past(wgray)) is at most 1 on every clock, and run it in simulation or with SymbiYosys.
