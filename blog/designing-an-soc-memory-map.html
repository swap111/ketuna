Designing an SoC memory map: regions, alignment and room to grow

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

Lay out a small RISC-V SoC's memory map by hand, choose sizes and alignments that make address decoding cheap, make the holes fault instead of alias, and leave space for the next chip.

The memory map is one of the first decisions in an SoC and one of the hardest to change later. The RTL decoder, the linker script, the C headers, the boot ROM, the debugger configuration and every driver depend on it. A careless map works for the first chip and then forces a painful software break on the second, or hides bugs by letting a wrong address silently hit a real peripheral. This article lays out a map for a small RISC-V microcontroller and explains each choice.

What has to fit

A typical small SoC has these address consumers:

  • Boot ROM: a few kilobytes of code that runs out of reset.
  • On-chip SRAM: data, stack, and often code copied from flash.
  • Flash or an external memory window: for execute-in-place code or a memory-mapped serial flash.
  • Core-local timer and software interrupt registers: in RISC-V systems, the machine timer (mtime, mtimecmp) is memory-mapped.
  • A platform interrupt controller: priorities, enables, and claim/complete registers.
  • Peripherals: UART, SPI, I2C, GPIO, timers, ADC, each with a small block of registers.
  • Debug: a debug module that an external debugger reaches.

A 32-bit address space is 4 GiB, vastly more than these need. That is a gift: you can be generous with alignment and spacing, which makes hardware cheaper and software simpler.

Alignment makes decoding cheap

Make every region a power of two in size and aligned to its size. Then the decoder only compares the upper address bits:

// Region selects; addr is the 32-bit bus address.
wire sel_rom  = (addr[31:14] == 18'h0);      // 0x0000_0000, 16 KiB
wire sel_sram = (addr[31:16] == 16'h2000);   // 0x2000_0000, 64 KiB
wire sel_uart = (addr[31:12] == 20'h40000);  // 0x4000_0000, 4 KiB
wire sel_gpio = (addr[31:12] == 20'h40001);  // 0x4000_1000, 4 KiB
wire sel_tmr  = (addr[31:12] == 20'h40002);  // 0x4000_2000, 4 KiB
wire sel_none = ~(sel_rom | sel_sram | sel_uart | sel_gpio | sel_tmr);

Each select is a single equality compare: no adders, no less-than comparators. A region of 48 KiB at an odd base would need a range check, which is bigger, slower and easier to get wrong.

Alignment also helps software. Physical memory protection in RISC-V can describe a naturally aligned power-of-two region with a single entry, and a Linux-class system maps memory in 4 KiB pages. Giving each peripheral its own 4 KiB slot, even if it has only four registers, lets either mechanism protect or map each peripheral separately. A UART that shares a page with the key-storage block cannot be handed to an untrusted task without handing over the keys as well.

Make the holes fault, not alias

Look at sel_none. Any address that selects nothing must return a bus error, which the core turns into an access-fault exception. The tempting shortcut is partial decoding: compare fewer bits, so the 4 KiB UART also answers at 0x4000_8000, 0x4001_0000 and thousands of other addresses. It saves a few gates and costs days of debugging, because a wrong pointer that should have faulted instead writes a real register. The same applies inside a peripheral: undefined register offsets should read as zero and ignore writes, and should be documented as reserved.

Leave room for the next chip

The map above uses 64 KiB of SRAM but reserves the region up to 512 MiB, keeps the peripheral area sparse, and leaves everything above 0x5000_0000 untouched. On the next chip the SRAM can grow, new peripherals can take the next free slots, and existing binaries and drivers keep working, because nothing that existed has moved. A good rule is that a peripheral, once placed, never moves and its existing registers never change meaning; new features get new registers.

One source of truth

The map lives in many places: RTL decoder, linker script, C header, device tree, debugger configuration, documentation, test register model. Keep one machine-readable description and generate the rest from it. SystemRDL is an open standard for describing registers and address maps, and open-source tools exist that generate RTL, C headers and documentation from it. Hand-maintained copies drift apart, and the drift is usually discovered on silicon.

Common mistakes

  • Packing peripherals tightly to "save space". Address space is free; protection granularity is not.
  • Partial decoding. Aliases turn wild pointers into silent register writes.
  • No bus error response. A read from a hole that returns stale bus data hides bugs.
  • Moving a peripheral between chip versions. Every driver and binary must change with it.

Try it yourself

  1. Write the map above as a small table in Python and generate both the Verilog select lines and a C header of #define base addresses from it.
  2. Simulate the decoder in Icarus Verilog with a testbench that sweeps addresses at region boundaries and in holes, checking that exactly one select, or sel_none, is active.
  3. Write a linker script for the map with ROM and SRAM regions, build a small program with a RISC-V GCC cross-compiler, and check the section addresses with riscv64-unknown-elf-objdump -h.
