Writing an interrupt-safe ring buffer for UART receive

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

A UART interrupt fills a buffer and the main loop empties it. With one writer per index, free-running counters and the right memory ordering, you need no lock and lose no bytes.

Almost every firmware project has the same small problem. Bytes arrive on a UART at a rate you do not control, and the code that parses them runs whenever the main loop gets round to it. The standard answer is a ring buffer: the receive interrupt writes into it and the main loop reads from it. The idea fits in a sentence, yet it is a common source of rare, hard-to-reproduce bugs. This article builds one that is correct, and explains why each line is there.

One writer per variable

The design rests on a single rule: every shared variable has exactly one writer.

  • The interrupt service routine (ISR) is the producer. It writes the data slots and the head index.
  • The main loop is the consumer. It writes only the tail index.

Each side may read the other's index, but never writes it. Because no variable is written from two places, there is no read-modify-write race and no lock is needed. This is the classic single-producer, single-consumer (SPSC) queue.

Compare a design with a shared count variable that the ISR increments and the main loop decrements. count-- compiles to load, subtract, store. If the interrupt fires between the load and the store, the main loop writes back a stale value and one byte is silently lost or duplicated. That bug might appear once a week under load, which is the worst kind.

Free-running indices

Instead of wrapping head and tail at the buffer size, let them count up forever and wrap only when you index the array:

  • the number of bytes waiting is head - tail;
  • the buffer is empty when head == tail;
  • the buffer is full when head - tail == SIZE;
  • the slot for an index is index & (SIZE - 1).

Unsigned subtraction in C is defined modulo 232 for a 32-bit type, so head - tail stays correct even after head wraps past the largest value, as long as SIZE divides 232. That is one reason the size must be a power of two; the other is that the mask is cheaper than a modulo. A bonus of this scheme is that all SIZE slots are usable, unlike the "leave one slot empty" approach needed when indices wrap early.

The code

This version uses C11 atomics, which GCC supports on RISC-V and other common targets. On a 32-bit core, aligned 32-bit loads and stores are single instructions, so these atomics cost little more than ordinary accesses plus ordering.

#include <stdatomic.h>
#include <stdbool.h>
#include <stdint.h>

#define RB_SIZE 256u                    /* must be a power of two */
#define RB_MASK (RB_SIZE - 1u)

typedef struct {
    uint8_t     buf[RB_SIZE];
    atomic_uint head;                   /* written only by the ISR       */
    atomic_uint tail;                   /* written only by the main loop */
    uint32_t    overflows;              /* written only by the ISR       */
} ringbuf_t;

static ringbuf_t rx;

/* Producer: called from the UART receive interrupt. */
void uart_rx_isr(void)
{
    uint8_t byte = uart_read_data();    /* reading the data register usually clears the RX flag */
    unsigned head = atomic_load_explicit(&rx.head, memory_order_relaxed);
    unsigned tail = atomic_load_explicit(&rx.tail, memory_order_acquire);

    if (head - tail == RB_SIZE) {       /* full: drop the new byte and count it */
        rx.overflows++;
        return;
    }
    rx.buf[head & RB_MASK] = byte;
    atomic_store_explicit(&rx.head, head + 1u, memory_order_release);
}

/* Consumer: called from the main loop. Returns false when empty. */
bool rb_get(uint8_t *out)
{
    unsigned tail = atomic_load_explicit(&rx.tail, memory_order_relaxed);
    unsigned head = atomic_load_explicit(&rx.head, memory_order_acquire);

    if (head == tail)
        return false;
    *out = rx.buf[tail & RB_MASK];
    atomic_store_explicit(&rx.tail, tail + 1u, memory_order_release);
    return true;
}

Here uart_read_data() stands in for your driver's register read.

Why the memory ordering matters

The data slot buf[...] is an ordinary array. Without guidance, the compiler is free to move the store to buf after the store to head, because to a single thread the order looks irrelevant. If that happens, the main loop can see the new head, read the slot and get stale data.

The release store on head forbids that: every write before it, including the data byte, must be visible before the new head is. The acquire load of head in rb_get is the matching half, so reads of the slot cannot be hoisted above it. The same pairing on tail protects the producer from overwriting a slot the consumer is still reading.

You will often see this written with volatile indices instead. volatile stops the compiler from caching the index in a register, which is necessary, but it does not order the non-volatile array accesses around it. If you use volatile, add a compiler barrier such as __asm__ volatile ("" ::: "memory") before publishing head. On a simple single-core microcontroller that is enough; on parts with caches, DMA or several cores, prefer the atomics, which also emit any hardware fences the target needs.

Pitfalls worth checking

  • Index width on small cores. On an 8-bit microcontroller a 32-bit index is not read in one instruction, so the main loop can read half of an old value and half of a new one. Use 8-bit indices with a size of at most 128, or briefly mask interrupts around the read.
  • Overflow policy. "Overwrite the oldest byte" sounds friendly, but it means the ISR must move tail, which breaks the one-writer rule. Drop the new byte and count overflows instead, then size the buffer so the counter stays at zero.
  • Error flags. Framing, parity and overrun errors are usually reported in a status register. Read and clear them in the ISR, or the interrupt may keep firing.

Sizing the buffer

With the common 8N1 format, each byte takes 10 bit times on the wire: start bit, 8 data bits, stop bit. At 115200 baud that is at most 11,520 bytes per second. If the main loop can be away for 10 ms in the worst case, up to about 116 bytes can arrive in that gap. A 256-byte buffer covers it with roughly two times margin. Measure the real worst-case loop time rather than guessing; the overflows counter tells you if you got it wrong.

Try it yourself

  1. Compile the buffer for your laptop with gcc and write host unit tests: fill it to exactly full, check that the next byte is dropped, drain it, and repeat. Start head and tail near UINT32_MAX so the wrap is exercised in the first few operations.
  2. Simulate an interrupt arriving at the worst moment by calling uart_rx_isr() between the steps of rb_get() in a test, using a fake uart_read_data().
  3. Run it on an emulated board. QEMU's RISC-V virt machine has a 16550-style UART, and Renode can script long streams of input. Send bursts larger than the buffer and confirm that the overflow count matches what you expect.

Write the buffer by hand first. Then ask an AI assistant to write one and review its output against the one-writer rule and the ordering rules above; it is a good test of both the tool and your understanding.
