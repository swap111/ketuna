Moving ADC samples with DMA and double buffering

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

Let DMA fill a circular buffer from the ADC while the CPU processes the half that is already full. How half-transfer and transfer-complete interrupts divide the work, how to budget time, and how to detect an overrun.

Sampling a microphone or a vibration sensor at tens of kilohertz with one interrupt per sample works on paper and fails in practice: the CPU spends most of its time entering and leaving the handler, and any other interrupt causes a missed sample. The standard answer is to let the DMA controller move samples from the ADC into memory by itself, and to let the CPU work on blocks. Double buffering is what lets the two run at the same time without stepping on each other.

DMA in one paragraph

A DMA (direct memory access) controller is a small bus master that copies data without the CPU. You configure a channel with a source address (the ADC data register), a destination (an array in RAM), an element size (16 bits for a 12-bit ADC result), a count, and whether each address increments. Here the source stays fixed and the destination increments. Each time the ADC finishes a conversion it raises a DMA request, and the DMA moves one sample. The CPU is not involved at all until the DMA tells it, through an interrupt, that it has reached some point in the buffer.

One buffer, two halves

The usual arrangement is a single array of 2N samples with the DMA in circular mode: when it writes the last element, it wraps to the first and carries on. Two interrupts mark the halfway points:

  • Half transfer (HT) fires when the first N samples are written. The DMA is now filling the second half, so the first half is safe to read.
  • Transfer complete (TC) fires when the second half is written. The DMA has wrapped and is filling the first half again, so the second half is safe.

Some DMA controllers support two separate buffers with a "current target" bit instead (often called double-buffer mode). The principle is identical; only the bookkeeping differs.

The code

The interrupt handlers do almost nothing: clear the flag, note which half is ready, and detect whether the previous block was ever processed. The processing runs in the main loop or a task. The dma_* names stand for your part's driver calls.

#include <stdbool.h>
#include <stdint.h>

#define HALF  256u
static uint16_t adc_buf[2 * HALF];     /* static: DMA needs it forever */

static volatile int16_t  ready_half = -1;   /* -1 none, 0 first, 1 second */
static volatile uint32_t overruns;

void dma_isr(void)
{
    int16_t half;
    if (dma_half_transfer_flag()) {
        dma_clear_half_transfer_flag();
        half = 0;
    } else if (dma_transfer_complete_flag()) {
        dma_clear_transfer_complete_flag();
        half = 1;
    } else {
        return;
    }
    if (ready_half != -1)              /* last block not taken yet */
        overruns++;
    ready_half = half;
}

int main(void)
{
    adc_dma_start(adc_buf, 2 * HALF);  /* circular, HT + TC enabled */
    for (;;) {
        int16_t h = ready_half;
        if (h < 0)
            continue;                  /* or sleep until an interrupt */
        ready_half = -1;               /* take the block */
        process_block(&adc_buf[h * HALF], HALF);
    }
}

There is a short window between reading ready_half and clearing it in which the ISR could post the other half; the overrun counter catches that too, because if it ever happens your processing is far too slow anyway. Clearing a slot before the work starts, rather than after, also makes the overrun check stricter: the counter measures whether you started every block in time. To check that you also finish in time, compare a timestamp at the end of process_block with the next interrupt, or record the DMA's remaining count when processing ends and confirm it never passed into the half you were reading.

The time budget

Suppose the ADC runs at 16,000 samples per second and each half holds 256 samples. A half fills in 256 / 16,000 s = 16 ms. That is the deadline: processing of one half must finish within 16 ms of its interrupt, or the DMA starts overwriting samples you are still reading.

If process_block takes 5 ms in the worst case, the CPU is busy about 31 % of the time and has 11 ms of slack per block for everything else: other interrupts, communication, logging. Measure the real worst case with a GPIO toggle around process_block rather than estimating it.

The block size is a trade-off. Bigger halves mean fewer interrupts and more efficient processing (filters and FFTs like long blocks), but more RAM and more delay between a sound happening and your code seeing it. With 256-sample halves at 16 kHz, a sample can wait up to 16 ms before its block is even ready. For a vibration logger that is fine; for a control loop it may not be.

Pitfalls that cost days

  • Buffer on the stack. If adc_buf is a local variable in a function that returns, the DMA keeps writing into memory that now belongs to something else. DMA buffers are static or global.
  • Data caches. On parts with a data cache, the DMA writes RAM but the CPU may read stale cached copies. Invalidate the cache lines of a half before processing it, align and size the buffer to whole cache lines, or place it in a non-cacheable region.
  • Unreachable memory. Some RAM blocks on some chips are not connected to the DMA. Check the bus matrix table and place the buffer with a linker section if needed.
  • Element size mismatch. A 16-bit peripheral read into an 8-bit destination drops or packs bytes. Match both sides to the data.
  • Processing in the ISR. It turns the DMA interrupt into exactly the long handler you were trying to avoid.

Try it yourself

  1. Before using hardware, model the scheme in Python with numpy: generate a test signal, split it into 256-sample halves, and write process_block there first, so you know the expected output of each block.
  2. Port process_block to C and test it on your laptop with gcc against the numpy results, block by block.
  3. On a board, wrap process_block in a GPIO toggle, view it next to the HT/TC interrupts on a logic analyser with sigrok PulseView, and confirm the busy fraction matches your budget. Then make the processing deliberately slow and watch the overrun counter rise.
