Audio features for edge AI: from samples to a spectrogram

Edge AI Beginner 27 Nov 2026 6 min read By Ketuna

Why small audio models are fed spectrograms rather than raw samples, and how to compute one step by step - framing, windowing, the FFT, mel scaling and the logarithm - with numpy code you can run.

A microphone sampled at 16 kHz produces 16,000 numbers every second. You could hand those straight to a neural network, and large models sometimes do. Small models on microcontrollers almost never do: they are fed a compact picture of how the sound's energy is spread across frequency over time, called a spectrogram. Building that picture is a short chain of classic signal processing, and every step has a reason you can understand without heavy maths.

Why not raw samples

Consider the same spoken word recorded twice. The two waveforms look very different sample by sample: the word starts a few milliseconds later, the voice is a little louder, the phase of every frequency component is different. Yet a listener hears the same word, because the ear responds mainly to which frequencies are present and how strong they are, changing over time.

A spectrogram captures exactly that and throws away what does not matter, such as phase. This has three benefits for a small device:

  • Smaller input. One second becomes about 49 frames of 40 numbers, 1,960 values instead of 16,000.
  • Easier learning. Patterns such as a vowel's resonances become visible as bands, so a small network with few weights can find them.
  • Robustness. Small shifts in timing and level change the spectrogram only a little.

Step 1: frames and windows

Sound changes over time, but over a few tens of milliseconds speech is roughly steady. So you cut the signal into short frames, for example 30 ms (480 samples at 16 kHz), starting a new frame every 20 ms (320 samples). The overlap means no sound falls between two frames.

Cutting a frame out with sharp edges creates a problem. The FFT, used in the next step, assumes the frame repeats forever, so the jump between the frame's last and first sample looks like a click and smears energy across all frequencies. The fix is to multiply each frame by a window that tapers smoothly to zero at both ends. The Hann window, a raised cosine, is a common choice.

Step 2: the FFT and the power spectrum

The fast Fourier transform (FFT) turns a frame of N samples into N frequency components. For a real signal only the first N/2 + 1 are unique. FFTs are fastest for powers of two, so the 480-sample frame is padded with zeros to N = 512. That gives 257 frequency bins, spaced 16,000 / 512 = 31.25 Hz apart, from 0 Hz up to 8 kHz, which is half the sample rate and the highest frequency the samples can represent.

Each bin is a complex number. Its squared magnitude is the power at that frequency, and the phase is discarded.

Step 3: mel scaling

Human hearing resolves low frequencies finely and high frequencies coarsely: the step from 200 Hz to 300 Hz sounds large, the step from 7,000 Hz to 7,100 Hz hardly noticeable. Speech is organised the same way, with most of its distinguishing detail at lower frequencies. The mel scale models this. A common formula is:

mel = 2595 × log10(1 + f / 700)

It is roughly linear below 1 kHz and logarithmic above: 1,000 Hz maps to about 1,000 mel, but 8,000 Hz maps to only about 2,840 mel.

To apply it, you build a filterbank: for example 40 triangular filters whose centres are evenly spaced in mel, so they are narrow at low frequencies and wide at high ones. Each filter takes a weighted sum of the power in the bins under it. The 257 power values become 40 band energies.

Step 4: the logarithm

Loudness spans a huge range: a whisper and a shout differ in power by several orders of magnitude. Taking the log of each band energy compresses that range, so the model sees comparable numbers for quiet and loud speech, and a change in overall volume becomes a constant offset rather than a scaling. A small constant is added first so that silent bands do not produce log(0).

The result, frame after frame, is a log-mel spectrogram. Some pipelines go one step further and apply a discrete cosine transform to each frame to get MFCCs (mel-frequency cepstral coefficients), keeping perhaps 10 to 13 of them. That decorrelates and compresses the features further, which suits very small models.

The whole chain in numpy

import numpy as np

FS, WIN, HOP, NFFT, NMEL = 16000, 480, 320, 512, 40

def hz_to_mel(f):
    return 2595 * np.log10(1 + f / 700)

def mel_to_hz(m):
    return 700 * (10 ** (m / 2595) - 1)

def mel_filterbank():
    edges = mel_to_hz(np.linspace(0, hz_to_mel(FS / 2), NMEL + 2))
    bins = np.floor((NFFT + 1) * edges / FS).astype(int)
    fb = np.zeros((NMEL, NFFT // 2 + 1))
    for m in range(1, NMEL + 1):
        lo, mid, hi = bins[m - 1], bins[m], bins[m + 1]
        fb[m - 1, lo:mid] = (np.arange(lo, mid) - lo) / max(mid - lo, 1)
        fb[m - 1, mid:hi] = (hi - np.arange(mid, hi)) / max(hi - mid, 1)
    return fb

def log_mel(x):
    n_frames = 1 + (len(x) - WIN) // HOP
    window = np.hanning(WIN)
    fb = mel_filterbank()
    out = np.empty((n_frames, NMEL))
    for t in range(n_frames):
        frame = x[t * HOP : t * HOP + WIN] * window
        power = np.abs(np.fft.rfft(frame, NFFT)) ** 2
        out[t] = np.log(fb @ power + 1e-6)
    return out

t = np.arange(FS) / FS
x = 0.5 * np.sin(2 * np.pi * 1000 * t)      # one second of a 1 kHz tone
S = log_mel(x)
print(S.shape, S.mean(axis=0).argmax())     # (49, 40) 14

For the 1 kHz test tone, the strongest band is filter 14, whose triangle spans roughly 955 Hz to 1,170 Hz. A test like this, where you know the answer in advance, is worth writing before you trust any feature code.

Getting it onto a device

On a microcontroller the same chain runs once per hop, in fixed point: a precomputed window table, an integer FFT, a sparse filterbank stored as start bin and weights per filter, and a log implemented with a table or a few shifts. The filterbank and window are constants in flash, and only one frame's buffers need RAM.

The one rule that matters most: the device must compute the same features as the training pipeline. A different window, a different FFT scaling or a natural log versus log base 10 produces features the model has never seen, and accuracy collapses without any error message. Port one implementation and compare its output against the training code on the same audio clip, frame by frame.

Common mistakes:

  • skipping the window and getting smeared spectra
  • training with one library's defaults and writing different defaults into the firmware
  • forgetting the small constant before the log, which produces minus infinity on silence
  • assuming more mel bands is always better, when it costs input size and model weights

Try it yourself

  1. Run the script above, then plot S.T with matplotlib's imshow for a recording of your own voice.
  2. Remove the window (multiply by ones) and compare the spectrogram of the pure tone.
  3. Change NMEL to 20 and to 64 and note how the image changes.
  4. Write a fixed-point version of one step, for example the filterbank with int16 weights, and compare it with the float output.
