Why 100% code coverage does not mean the design is verified

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Line, branch, toggle and FSM coverage show which parts of the RTL were exercised. They cannot show wrong conditions that were never tested at the boundary, unchecked outputs, or features nobody wrote.

In this article
  1. What each metric counts
  2. Executed is not the same as checked
  3. Covered at the wrong values
  4. Code that should exist but does not

Code coverage is the first metric most students meet, and the easiest to misread. The simulator reports that 100% of lines and branches executed, the bar turns green, and it feels like the job is finished. It is not. Code coverage measures what the simulator did with the code that exists. It says nothing about whether the results were checked, whether the code does what the spec asks, or whether something the spec requires was never written at all.

What each metric counts

Simulators can collect several kinds of code coverage automatically, with no extra testbench code.

Metric What it counts What a hole tells you
Line (statement) Each statement executed at least once Some code never ran
Branch Each side of every if and each case item taken A decision only ever went one way
Condition / expression Each sub-term of a boolean expression affecting the outcome Part of a condition was never tested on its own
Toggle Each bit of each signal went 0→1 and 1→0 A bit was stuck, or a field was never used
FSM Each state visited, each transition taken A state or transition was never reached

These are useful. A line that never ran is a line nobody has tested, and a hole in FSM transition coverage often points straight at an error path the tests forgot. Code coverage is a good minimum. The trouble starts when it is treated as a maximum.

Executed is not the same as checked

Coverage tools record that a line ran. They do not know whether any checker looked at the result. Imagine a testbench whose scoreboard is accidentally disconnected: every line of RTL still executes, coverage still reports 100%, and no wrong output would ever be caught.

This is not far-fetched. A monitor that samples on the wrong edge, a comparison that is skipped when a queue is empty, or an assertion compiled out by a missing define all produce full coverage and zero checking. The defence is to prove the checkers can fail: inject a bug on purpose and confirm a test reports it.

Covered at the wrong values

Here is a level comparator for an over-temperature flag. Suppose the spec says the flag must assert when the reading is at or above the limit.

module overtemp (
  input  wire       clk,
  input  wire [7:0] temp,
  input  wire [7:0] limit,
  output reg        hot
);
  always @(posedge clk) begin
    if (temp > limit)   // bug: spec says temp >= limit
      hot <= 1'b1;
    else
      hot <= 1'b0;
  end
endmodule

A test that drives temp = 20, limit = 100 and then temp = 200, limit = 100 takes both branches. Line coverage is 100%, branch coverage is 100%, and the outputs are correct for those inputs. The bug shows only when temp == limit, a value the test never used. No code-coverage metric can see this, because the faulty line was executed. What was missing is a test at the boundary, and only a person reading the spec knows the boundary matters.

Functional coverage catches it if the plan has a bin for temp == limit. That bin exists only because someone wrote down that equality is a special case.

Code that should exist but does not

The deepest limit is the simplest. Coverage measures code that exists. If the spec says the receiver must flag a parity error and the designer never implemented parity checking, there is no line, branch or state to be uncovered. The coverage report is complete and clean, and the feature is missing.

The same applies to:

  • an error response that the spec requires and the RTL never generates
  • a register field that should be read-only but is writable, because the decode simply treats it like the others
  • a timeout that should abort a stuck transfer, absent from the FSM entirely

Only a verification plan derived from the spec, with a check and a functional coverage goal for each feature, exposes these. That is why the plan comes first and code coverage comes last, as a cross-check.

How to use code coverage well

Code coverage earns its place when you read the holes rather than the percentage.

  1. Close functional coverage first. Then look at code coverage to find RTL your plan did not anticipate.
  2. Explain every hole. An unreached line is either missing stimulus, dead code that should be removed, or a defensive branch that cannot be reached by design. Each needs a decision, and a waiver needs a written reason.
  3. Treat toggle holes on control bits seriously. A mode bit that never toggled means one mode was never tested. Toggle holes on the top bits of a wide data bus are usually less alarming.
  4. Look at FSM transitions, not just states. Visiting every state by the common path can leave the error transitions untested.
  5. Exclude carefully. Excluding code to reach a target hides exactly the places where bugs like to sit. Every exclusion should be reviewed.

Try it yourself

  1. Save the comparator above as overtemp.v and write a cocotb or SystemVerilog test that drives only the two values described, checking hot each cycle.
  2. Build it with Verilator using --coverage, run it, and annotate the source with verilator_coverage --annotate; confirm the if shows both branches taken.
  3. Add a test at temp == limit and watch it fail against the spec while the coverage numbers stay exactly the same.
  4. Write a one-line functional coverage bin for the equality case, fix the RTL, and rerun to see it pass.
