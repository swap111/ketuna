Git for hardware engineers: branches, reviews and generated files

Careers & skills Intermediate 27 Nov 2026 5 min read By Ketuna

How to branch for RTL and firmware work, what belongs in the repository and what does not, how to handle large tool outputs, and how to review a hardware change so it lands safely on main.

In this article
  1. What belongs in the repository
  2. The exceptions: outputs worth keeping
  3. Branching for RTL and firmware
  4. Reviewing a hardware change
  5. Bisect works only if history is clean
  6. Try it yourself

Git was built for software, and hardware projects stretch it in particular ways. A synthesis run produces hundreds of megabytes of reports. A layout flow writes a fresh directory every time. A waveform dump can be bigger than the whole source tree. A one-line constraint change can move timing on the whole chip. This article covers the habits that keep a hardware repository small, reviewable and safe to bisect.

What belongs in the repository

The rule is simple: commit the inputs that a person writes, not the outputs that a tool regenerates. If you can rebuild a file by running a command from a clean checkout, it does not belong in Git.

Commit Do not commit
RTL, testbenches, cocotb tests Simulation build folders, compiled models
Constraints (SDC), flow configuration Flow run directories, intermediate databases
Makefiles, scripts, CI config Waveform dumps (.vcd, .fst)
Specs, test plans, README Logs and reports from routine runs
Small reference data the tests need Tool licences, keys, credentials

A .gitignore written on day one saves you from the most common mess. A reasonable start for an RTL and firmware project:

# simulation and lint outputs
sim_build/
obj_dir/
*.vcd
*.fst
results.xml
__pycache__/

# physical design runs
runs/
*.log

# firmware builds
build/
*.o
*.elf
*.bin

Adjust it to your flow, and check git status after a full run. Anything new that shows up is either a source file you forgot to add or an output you forgot to ignore.

The exceptions: outputs worth keeping

Some generated files are worth keeping, but deliberately and not in every commit:

  • Signoff evidence. The final timing summary, the DRC and LVS result for a tape-out, the netlist you actually submitted. These record what you shipped. Keep them in a release or a tagged folder, not regenerated on every change.
  • Golden reference data. Expected outputs that tests compare against. Keep them small and explain in a README how they were produced.
  • Large binary files you must keep, such as a final GDS. Ordinary Git stores every version of a binary in full and cannot diff it, so the repository grows quickly. Git LFS, an open-source extension, keeps large files outside the normal history and stores a small pointer in their place. Use it, or attach the file to a tagged release, rather than committing binaries directly.

Whatever you decide, write it down in the README so the next person knows which outputs are deliberate.

Branching for RTL and firmware

Keep main always passing: lint clean, tests green. Do every change on a short-lived branch named for what it does, such as fix/fifo-full-flag or feat/uart-parity, and merge it through a pull request once CI passes and someone has reviewed it.

Hardware work has a few extra rules:

  • Keep branches short. A branch that lives for three weeks drifts away from main, and merging RTL with conflicting port changes is painful. Merge small pieces often, behind a parameter if the feature is not finished.
  • Change one thing per commit. RTL, its test and its spec update belong in one commit if they describe one behaviour change. A rename of every signal does not belong in the same commit as a logic fix, because the reviewer cannot see the fix in the noise.
  • Tag what you hand off. Tag the exact commit you sent to synthesis, to a shuttle or to a board build (git tag -a v0.3-tapeout -m "..."). Months later, that tag is how you reproduce what is on the silicon.
  • Never rewrite shared history. Rebasing your own unpushed branch is fine. Force-pushing a branch others use rewrites their history.

Reviewing a hardware change

Reviewing RTL is not like reviewing application code, because a small text change can have large physical effects. Before approving, a reviewer should check:

  1. Does the diff match the description? The commit message says why; the diff should contain nothing else.
  2. Width, reset and clocking. Width mismatches, a new register without a reset, a signal that crosses into another clock domain without a synchronizer.
  3. Inferred hardware. An incomplete case in combinational logic that infers a latch; a loop that unrolls into far more logic than intended.
  4. Tests. Is there a test that would have failed before this change? If not, the change is unverified.
  5. Flow impact. For constraint or interface changes, did the author rerun synthesis or timing, and is the result in the pull request?

Ask the author to paste the evidence (lint output, test summary, slack before and after) into the pull request description. That makes the review fast and leaves a record.

Bisect works only if history is clean

When a regression starts failing, git bisect finds the first bad commit by binary search. With 128 commits between a known good and a known bad version, it needs at most 7 test runs, because 27 = 128. This only works if every commit builds and the test runs from a clean checkout. Giant commits, committed outputs that hide source changes and broken intermediate commits all defeat bisect. Clean history is not tidiness for its own sake; it is a debugging tool you build in advance.

Try it yourself

  1. Add the .gitignore above to a lab repository, run your full simulation and synthesis, and check git status shows nothing new.
  2. Make a fix on a branch, push it and open a pull request whose description includes the lint and test output. Ask a classmate to review it against the five checks above.
  3. Tag a known good commit, plant a bug a few commits later, and run git bisect start, git bisect bad, git bisect good <tag> and git bisect run make test (or your own test command). Confirm it finds your planted commit, then git bisect reset.
