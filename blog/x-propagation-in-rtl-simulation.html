X in RTL simulation: how unknowns hide bugs and how to flush them out

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Why if and case statements swallow X values in RTL simulation, how that hides missing resets, and how assertions, coding style and randomised initial values make uninitialised state visible.

In this article

  2. How if and case swallow X
  3. The conditional operator is more honest
  4. Making uninitialised state visible
  5. Which X to fix
  6. Try it yourself

In a four-state simulator, X means "this bit could be 0 or 1 and the simulator does not know which". It is the simulator's honest way of reporting an uninitialised flop, an undriven wire or a conflict between two drivers. The trouble is that Verilog's procedural semantics often throw that honesty away. An X walks into an if statement and comes out as a definite decision, and the simulation carries on looking perfectly healthy. Real hardware makes a definite decision too, but you do not get to choose which one.

Where X comes from

Before chasing X behaviour, know the usual sources:

  • flip-flops without reset, before their first load
  • memories read before being written
  • signals declared but never driven, often after a refactor renames a port
  • multiple drivers fighting on one net
  • explicit X assignments used as don't-cares, such as default: y = 'x;
  • out-of-range array indices or part-selects

Each of these is a potential silicon bug, because silicon replaces X with an unpredictable real value.

How if and case swallow X

Here is a small control block with a missing reset on its mode register.

reg [1:0] mode;               // no reset
reg [7:0] out;

always @(posedge clk)
  if (load_mode) mode <= mode_in;

always @(*) begin
  if (mode == 2'd1) out = a;
  else              out = b;
end

Before load_mode arrives, mode is X, so mode == 2'd1 evaluates to X. The Verilog if treats any condition that is not 1 as false and takes the else branch. out gets b, a clean value. The simulation shows no X anywhere downstream, and if the test happens to expect b at that time, it passes. On silicon, mode powers up as any of four values and out might be a.

case behaves similarly. With an X selector, no item matches exactly, so the default branch runs:

always @(*)
  case (mode)
    2'd0: out = a;
    2'd1: out = b;
    2'd2: out = c;
    default: out = d;       // X selector lands here
  endcase

Again, a definite value hides an indefinite cause. This behaviour is called X-optimism: the simulator is more confident about the result than the hardware would be.

The conditional operator is more honest

The ?: operator handles an X condition differently. If the condition is X, the result is formed bit by bit: bits where both operands agree keep their value, and bits where they differ become X.

assign out = (mode == 2'd1) ? a : b;   // X condition -> X where a != b

With a = 8'h0F and b = 8'h0C, the result is 8'b0000_11xx: the top six bits agree and survive, and the bottom two differ and become X. Now the uncertainty is visible downstream. This is one reason some teams prefer continuous assignments with ?: for muxes in control paths. It is not a complete solution, because case and if remain natural for many structures, but it shows the principle: X should spread in simulation the way uncertainty would spread in hardware.

Making uninitialised state visible

Several techniques, used together, flush hidden X out of an RTL simulation.

Assert that important signals are known. An assertion with $isunknown fails as soon as an X reaches a control signal, even if later logic would have hidden it:

a_mode_known: assert property (@(posedge clk) disable iff (!rst_n)
                               !$isunknown(mode));

Put such checks on every control register, every FSM state, every valid and ready, and on data buses qualified by their valid.

Check the testbench's view too. In cocotb, int(dut.mode.value) raises an exception if any bit is X or Z. Converting control outputs to integers in a monitor turns hidden X into an immediate failure.

Randomise initial values in two-state simulators. Verilator is a two-state simulator: it has no X at all, and by default it initialises unknown state to a fixed value, which can hide the same bugs in a different way. It can instead initialise to random values. Build with --x-assign unique and --x-initial unique, then pass +verilator+rand+reset+2 at run time, with +verilator+seed+ and a number to vary the values. A design that only works when unreset state happens to be zero fails on some seeds. Run several seeds in regression and record them so a failure can be reproduced.

Do not mask X in the RTL. Avoid writing if (mode === 2'd1) or case statements with defaults whose only purpose is to make X go away in simulation. They make the waveform clean and the silicon unpredictable.

Use explicit X assignments carefully. default: y = 'x; is a legitimate synthesis hint that a value does not matter. Make sure it truly does not matter: add an assertion that the default branch is never reached in normal operation, so the hint never becomes a silent bug.

Which X to fix

Not every X needs a reset. Datapath registers that are always written before they are read, such as a pipeline data register qualified by a valid bit, can start unknown without harm, and adding resets to them costs area and routing. The rule is about control: any state that influences a decision, a handshake or an output enable must start known. Qualified data is allowed to be X while its valid is low.

A short review question settles most cases: if this flop powered up as the wrong value, could the design do something visible before the flop is first written? If yes, reset it.

Try it yourself

  1. Write the mode block above, simulate it with Icarus Verilog, and dump mode and out to a VCD; confirm mode is X while out is clean.
  2. Rewrite the mux with ?: and choose a and b that differ in only a few bits; check which bits of out become X.
  3. Build the same design with Verilator using --x-assign unique --x-initial unique, run it with +verilator+rand+reset+2 and several seeds, and see the output change between runs.
  4. Add the $isunknown assertion and a reset on mode, and confirm both simulators now behave identically from time zero.
