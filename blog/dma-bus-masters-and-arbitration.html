DMA from the architecture side: bus masters, arbitration and coherence

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

A DMA engine is a second bus master competing with the CPU. Work out arbitration latency and burst efficiency, and see why caches make DMA buffers tricky and what clean, invalidate and alignment fix.

From a firmware point of view, DMA is a convenience: configure a channel, start it, get an interrupt when the data has moved. From the architecture side, a DMA engine is a second processor of sorts. It issues its own reads and writes, competes with the CPU for the same buses and memories, and bypasses the CPU's caches. Those three facts decide how much bandwidth DMA really gets, how much it slows the CPU down, and why a correct-looking driver can return stale data. This article looks at each.

A DMA engine is a bus master

On an on-chip bus, masters (managers) start transactions and slaves (subordinates) respond. The CPU's instruction and data ports are masters. So is every DMA engine, and so are other blocks that move data themselves, such as an Ethernet or USB controller with built-in DMA. When two masters want the same subordinate in the same cycle, typically the main SRAM, an arbiter decides who goes first.

A bus matrix (or crossbar) reduces conflicts by giving each master its own path to each subordinate, so the CPU can fetch from flash while DMA writes to SRAM. Conflicts remain whenever two masters target the same subordinate. Splitting SRAM into several banks on separate matrix ports, and placing DMA buffers in a bank the CPU's stack and hot data do not use, is one of the cheapest performance improvements in an SoC.

Arbitration policies

  • Fixed priority. The highest-priority requester always wins. Simple and predictable for the winner, but a busy high-priority master can starve the others completely.
  • Round-robin. Grants rotate among requesters. Nobody starves, and the worst-case wait is bounded by the number of masters.
  • Weighted or programmable. Each master gets a share of slots, or priority changes with how long it has waited. Used when one master needs bandwidth guarantees, such as a display controller that must never underrun.

The policy interacts with burst length. Once a master wins, it usually keeps the bus for a whole burst. Long bursts are efficient, because the address and arbitration overhead is paid once per burst; short bursts give other masters a turn sooner.

Working the trade-off

Suppose, with numbers made up for illustration, that each burst costs 2 cycles of arbitration and address overhead plus one cycle per data beat, and that three masters (the CPU and two DMA channels) share one SRAM port with round-robin arbitration.

Efficiency. A 16-beat burst uses 16 of 18 cycles for data: 89% efficiency. A 4-beat burst uses 4 of 6: 67%. Longer bursts move more data per cycle of bus time.

CPU latency. In the worst case, the CPU's request arrives just after both DMA channels have been granted. With 16-beat bursts it waits for two full bursts: 2 × (16 + 2) = 36 cycles before its own access starts. With 4-beat bursts it waits 2 × (4 + 2) = 12 cycles.

DMA burst length Bus efficiency Worst-case CPU wait
4 beats 67% 12 cycles
16 beats 89% 36 cycles

Neither is "right". A design that streams audio while running a hard real-time control loop may cap DMA bursts to bound interrupt and load latency. A design that moves camera frames to memory may favour long bursts. What matters is that the choice is made on purpose, with numbers, and that worst-case latency is checked against the CPU's real-time requirements, not just the average.

Coherence: why caches complicate DMA

A CPU with a data cache keeps copies of memory lines and, with a write-back cache, may hold newer data than memory for a long time. A typical DMA engine reads and writes memory directly and does not look in the cache. Two failure modes follow:

  1. CPU writes, DMA reads (memory to peripheral). The CPU fills a transmit buffer; the new bytes sit in dirty cache lines. DMA reads memory and transmits the old contents. Fix: clean (write back) the buffer's lines before starting the transfer.
  2. DMA writes, CPU reads (peripheral to memory). DMA fills a receive buffer in memory, but the CPU still has old copies of those lines in its cache and reads them. Fix: invalidate the buffer's lines before the CPU reads, and make sure no speculative access refills them during the transfer, which on some cores means invalidating both before and after.

There is a subtle third trap: alignment. Cache maintenance works on whole lines. If a receive buffer shares a cache line with an unrelated variable, invalidating the buffer also throws away any pending write to that variable, and the variable silently reverts to an old value. DMA buffers should therefore start on a cache-line boundary and occupy whole lines:

#include <stdint.h>

#define CACHE_LINE 64u   /* check your core's line size */

static uint8_t rx_buf[512] __attribute__((aligned(CACHE_LINE)));

void start_rx(void)
{
    cache_invalidate_range(rx_buf, sizeof rx_buf);  /* drop stale lines */
    dma_start_rx(rx_buf, sizeof rx_buf);
}

void on_rx_complete(void)
{
    cache_invalidate_range(rx_buf, sizeof rx_buf);  /* in case of refills */
    process(rx_buf, sizeof rx_buf);
}

The cache_invalidate_range helper is platform-specific. On RISC-V cores it is built on the cache-block management instructions of the Zicbom extension (cbo.clean, cbo.inval, cbo.flush), or on vendor-specific operations on older cores. Combine it with the right fences so that the maintenance completes before the DMA engine is told to start.

Architectural alternatives

Software maintenance works but costs CPU time and is easy to get wrong. Architects have three other options:

  • Non-cacheable buffer regions. Map DMA buffers into memory the cache never holds. Simple and safe, but every CPU access to the buffer goes to memory.
  • Uncached SRAM banks or tightly coupled memory. A separate on-chip memory that both CPU and DMA access directly, with fixed timing.
  • Hardware I/O coherence. Route DMA traffic through a coherent port, so the interconnect snoops the CPU's caches on DMA accesses. This removes the software burden at the cost of interconnect complexity and snoop traffic. It is common in larger application processors, less so in small microcontrollers.

Common mistakes

  • Testing DMA with the cache disabled. Everything works until the cache is turned on.
  • Unaligned DMA buffers. Invalidation corrupts neighbouring variables.
  • Letting DMA starve the CPU. Fixed-priority DMA with long bursts can break real-time deadlines.
  • Starting DMA before cache maintenance has completed. Order it with a fence.

Try it yourself

  1. Write a Python model of a round-robin arbiter with three masters and configurable burst length, and measure the worst-case and average CPU wait over random request patterns.
  2. Implement the arbiter in Verilog, simulate it in Verilator against the Python model, and prove "no master waits more than N cycles" with SymbiYosys.
  3. In a QEMU or Renode bare-metal project, place an unrelated variable next to an unaligned DMA buffer and reason through what an invalidate would do to it.
