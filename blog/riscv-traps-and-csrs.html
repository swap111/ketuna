RISC-V traps and CSRs: what happens between an interrupt and your handler

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

Follow a machine-mode trap step by step through mtvec, mepc, mcause and mstatus, write a minimal trap entry in assembly and C, and see exactly how mret puts everything back.

On a RISC-V microcontroller, a timer fires, and a few cycles later your C function timer_tick() is running. In between, the hardware does a short, precisely defined sequence of steps through a handful of control and status registers (CSRs), and your trap entry code does the rest. If you know that sequence you can write the entry code yourself, debug a handler that returns to the wrong place, and read a core's RTL with confidence. This article walks through machine mode, the one privilege level every RISC-V core has.

Exceptions and interrupts share one mechanism

RISC-V calls both kinds of event a trap.

  • An exception is caused by the instruction itself: an illegal instruction, a misaligned or faulting access, an ecall or an ebreak. It is synchronous; it happens at that instruction every time.
  • An interrupt comes from outside the instruction stream: the machine timer, a software interrupt from another hart, or an external interrupt from a platform interrupt controller. It is asynchronous and is taken between instructions.

Both go through the same entry sequence. The mcause register tells your handler which one it was: its most significant bit is 1 for interrupts and 0 for exceptions, and the remaining bits give the cause code.

What the hardware does, in order

When a trap is taken in machine mode, the core performs these updates as a single step:

  1. mepc gets the address to come back to. For an exception, that is the faulting instruction itself. For an interrupt, it is the instruction that would have executed next.
  2. mcause gets the cause: for example 0x8000_0007 for the machine timer interrupt, 0x0000_0002 for an illegal instruction, 0x0000_000B for ecall from machine mode.
  3. mtval gets extra information where it helps: the faulting address for an access fault or misaligned access, the bad instruction bits for an illegal instruction (if the core supports that), otherwise zero.
  4. mstatus saves and disables interrupts: the previous interrupt enable MIE is copied into MPIE, MIE is cleared, and the previous privilege level is saved in MPP.
  5. The PC jumps to the address in mtvec. In direct mode every trap goes to the same address. In vectored mode, interrupts go to mtvec base + 4 × cause, so each interrupt source can have its own entry point, while exceptions still go to the base.

Notice what the hardware does not do: it saves no general-purpose registers and switches no stack. That is deliberate. A minimal trap entry keeps hardware small and leaves the policy to software, which knows how many registers it needs.

Interrupts are taken only when they are enabled at two levels: the global mstatus.MIE bit, and the per-source bit in mie (bit 7, MTIE, for the timer). The mip register shows which sources are pending. An interrupt is taken when MIE is set and a source is both pending and enabled.

A minimal trap entry

Because a C function may freely overwrite the caller-saved registers (ra, t0 to t6, a0 to a7, sixteen in all), the entry code must save those before calling C. The callee-saved registers are preserved by the C function itself.

    .text
    .align 2                  # mtvec needs 4-byte alignment
    .globl trap_entry
trap_entry:
    addi  sp, sp, -64         # 16 registers x 4 bytes
    sw    ra,  0(sp)
    sw    t0,  4(sp)
    sw    t1,  8(sp)
    sw    t2, 12(sp)
    sw    a0, 16(sp)
    sw    a1, 20(sp)
    # ... a2-a7 and t3-t6 at 24(sp) to 60(sp)
    csrr  a0, mcause          # argument 1
    csrr  a1, mepc            # argument 2
    call  trap_handler        # returns the resume address
    csrw  mepc, a0
    lw    ra,  0(sp)
    # ... restore the other 15 registers
    addi  sp, sp, 64
    mret

The C side decides what to do and where to resume:

#include <stdint.h>

#define MCAUSE_IRQ (1u << 31)

void timer_tick(void);   /* writes a new mtimecmp */

uint32_t trap_handler(uint32_t mcause, uint32_t mepc)
{
    if (mcause & MCAUSE_IRQ) {
        if ((mcause & 0x7FFFFFFFu) == 7u)
            timer_tick();
        return mepc;          /* resume where we were */
    }
    if (mcause == 11u)        /* ecall from M-mode */
        return mepc + 4u;     /* ecall is always 4 bytes */
    for (;;) { }              /* unexpected: stop for the debugger */
}

The ecall case shows the most common trap bug. For an exception, mepc points at the trapping instruction. If the handler returns to it unchanged, the core executes ecall again, traps again, and loops forever. For an interrupt, mepc already points to the next instruction, so it must not be adjusted.

The timer case shows the second most common bug. The machine timer interrupt stays pending while mtime ≥ mtimecmp. If timer_tick() does not write a later value into mtimecmp, the interrupt fires again the moment mret re-enables interrupts.

To set it all up: write the address of trap_entry into mtvec (low two bits 0 for direct mode), set MTIE in mie, and finally set MIE in mstatus, for example with csrsi mstatus, 8, since MIE is bit 3.

What mret undoes

mret reverses step 4 and step 5: the PC is loaded from mepc, MIE is restored from MPIE, MPIE is set to 1, and the privilege level returns to the one saved in MPP. Because MIE was cleared on entry and is restored only by mret, a handler is not interrupted by another machine-mode interrupt unless it deliberately sets MIE again. Nested interrupts are possible, but then the handler must first save mepc and mstatus, since a second trap would overwrite them.

Common mistakes

  • Returning to mepc after an exception. The instruction traps again; advance past it if the cause is handled.
  • Not clearing the interrupt source. Level-sensitive sources re-trigger immediately after mret.
  • Misaligned mtvec. The low bits are the mode field, so an odd handler address silently changes the mode.
  • Enabling MIE before mtvec is set. The first interrupt jumps to whatever reset left in mtvec.

Try it yourself

  1. Build the entry code and handler with a RISC-V GCC cross-compiler for rv32imac with -mabi=ilp32 and run it on the QEMU virt machine, which has a machine timer.
  2. Start QEMU with -s -S and connect GDB; put a breakpoint on trap_handler and print mcause, mepc and mstatus at each trap.
  3. Add a deliberate illegal instruction (.word 0) and check that mcause is 2 and mepc points at it.
