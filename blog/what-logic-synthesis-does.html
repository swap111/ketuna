What logic synthesis actually does to your RTL

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

Synthesis elaborates your RTL, optimises it as generic logic, then maps it onto real library cells. Here is what happens at each stage and how to read the cell-count report it leaves behind.

In this article

  2. Stage 2: generic optimisation simplifies the logic
  3. Stage 3: technology mapping picks real cells
  4. Reading the cell-count report

You write assign y = a + b; and a few seconds later a tool hands you a file full of cells with names like sky130_fd_sc_hd__xor2_1. Between those two moments, synthesis has done three distinct jobs. Knowing them helps you predict what hardware your code becomes, and lets you read the report at the end as evidence rather than as noise.

Stage 1: elaboration turns text into a circuit

Elaboration reads your Verilog, resolves parameters and generate blocks, connects module instances into a hierarchy, and converts every always block and assign into a graph of abstract operators: adders, multiplexers, comparators, and storage elements.

The most important decision here is what becomes a flip-flop. A signal assigned inside always @(posedge clk) becomes a register. A signal assigned in a combinational block that is not given a value on every path becomes a latch, because the hardware must remember the old value when no branch assigns it. Elaboration is where an incomplete case statement turns into a latch you did not want, and the log says so.

// Missing default: synthesis infers a latch on y
always @(*) begin
  case (sel)
    2'b00: y = a;
    2'b01: y = b;
    2'b10: y = c;
  endcase
end

Adding default: y = 1'b0; (or assigning y before the case) gives every path a value and removes the latch.

Stage 2: generic optimisation simplifies the logic

Next, the tool works on technology-independent logic. It does not yet know which cells exist; it just wants fewer and simpler operations. Typical transformations:

  • Constant propagation: an input tied to 0 removes the gates it feeds.
  • Dead logic removal: anything that does not reach an output or a register is deleted. If you forget to connect an output, a whole block can vanish.
  • Sharing: two identical expressions are computed once.
  • Finite state machine extraction and re-encoding in some tools.
  • Boolean minimisation: the logic is rewritten into a smaller network of AND, OR and inverter nodes.

This stage is why synthesis results sometimes surprise you. A register that never changes is replaced by a constant. A counter whose upper bits are never read loses those bits. The tool is right: it only keeps hardware that affects an observable output.

Stage 3: technology mapping picks real cells

Finally, the optimised logic is covered with cells from the standard-cell library. The library's Liberty file describes each cell's function, area, input capacitance and delay tables. The mapper (ABC inside Yosys) chooses a combination of cells that implements the logic while meeting a target, usually minimum area or a delay goal.

Flip-flops are mapped separately onto the library's flip-flop cells, including versions with reset or enable if the library has them. Then the tool may resize cells, picking a stronger drive version (for example _2 or _4 rather than _1) for nets with many loads or tight timing.

The output is a gate-level netlist: still Verilog, but every instance is a library cell. You can simulate it, and you should, because it is the first point where a mistake in your RTL style becomes real hardware.

Reading the cell-count report

At the end, Yosys's stat command (or the equivalent in any tool) prints the number of cells of each type and, given a Liberty file, the total area. Here is an illustrative report for a small registered 8-bit ALU; the numbers are made up for illustration but the shape is typical.

Number of cells:                142
  sky130_fd_sc_hd__dfrtp_1       17
  sky130_fd_sc_hd__a21oi_1       21
  sky130_fd_sc_hd__xor2_1        14
  sky130_fd_sc_hd__nand2_1       25
  sky130_fd_sc_hd__mux2_1        16
  ...
Chip area for module '\alu8_reg': 1534.2

Questions to ask of a report like this:

  • Does the flip-flop count match what you expected? Two 8-bit input registers and one output register with a carry give 8 + 8 + 9 = 25 flops. Seeing 17 here means some register was optimised away, perhaps because its value was constant or unused. Find out which one before moving on.
  • Are there any latches? Any latch cell in a design that was meant to be fully synchronous is a bug until proven otherwise.
  • Which cells dominate? Many xor2 and maj3 or a21oi cells point to arithmetic; many mux2 cells point to wide multiplexers or shift logic. If the mix does not match your mental picture of the design, your picture or your RTL is wrong.
  • What is the area per function? Area is in square micrometres for an open PDK library. Comparing it before and after an RTL change tells you what the change cost.

Also read the warnings. Messages about undriven nets, multiple drivers, or signals "removed" are often the only clue to a real bug.

Common mistakes

  • Treating synthesis as a black box. If you cannot sketch roughly what hardware a block of RTL becomes, you cannot judge the report.
  • Ignoring disappeared logic. A suspiciously small netlist usually means an output was not connected.
  • Trusting RTL simulation alone. Synthesis and simulation can interpret some constructs differently, such as incomplete sensitivity lists. Simulate the gate netlist too.

Try it yourself

  1. Write a small registered ALU in Verilog. In Yosys, run read_verilog alu.v, then synth -top alu, then stat. Note the generic cell counts.
  2. Map to a real library from the open sky130 PDK: dfflibmap -liberty <lib>, abc -liberty <lib>, then stat -liberty <lib> to see area.
  3. Remove one output port's connection, resynthesise and watch the cell count drop. Then add the latch example above and find the latch in the log.
  4. Simulate the written netlist with Icarus Verilog against your RTL testbench and confirm the results match.
