Writing your first SDC: clocks, I/O delays and false paths

Physical design & tape-out Intermediate 27 Nov 2026 5 min read By Ketuna

Timing tools only check what your constraints describe. Build a minimum SDC for a block, line by line, and learn the over-constraints and missing constraints that hide real failing paths.

In this article
  1. Start with the clock
  2. Describe the outside world with I/O delays
  3. Exceptions: false paths and multicycle paths
  4. Over-constraints and under-constraints
  5. Check the constraints, not just the timing
  6. Try it yourself

Static timing analysis proves that every path meets timing, but only the paths it knows about, against the requirements you gave it. Those requirements live in an SDC file, written in a Tcl-based constraint format that commercial and open tools alike read, including OpenSTA and OpenROAD. A missing line does not cause an error; it silently removes paths from the check. That makes the SDC one of the few files where a mistake can pass every report and still fail on silicon.

Start with the clock

Nothing is timed until a clock exists. For a block with one clock input:

create_clock -name clk -period 10.0 [get_ports clk]
set_clock_uncertainty 0.25 [get_clocks clk]
set_clock_transition  0.15 [get_clocks clk]
  • create_clock defines the period (here 10 ns, 100 MHz) and the waveform, which defaults to a rising edge at 0 and a falling edge at half the period.
  • set_clock_uncertainty takes margin away from every setup and hold check. Before clock tree synthesis it stands in for the skew you have not built yet plus jitter; after CTS, real skew is computed, so many flows reduce it.
  • set_clock_transition gives the ideal clock a realistic edge rate before the tree exists.

If the block has a derived clock, for example a divide-by-two made from a flip-flop, describe it with create_generated_clock so the tool knows the relationship. Otherwise the divided clock is either untimed or timed as if it were unrelated.

Describe the outside world with I/O delays

A flip-flop inside your block that drives an output port is only half of a path. The other half is in the next block or chip, which you cannot see. set_input_delay and set_output_delay describe those hidden halves.

set in_ports [remove_from_collection [all_inputs] [get_ports clk]]
set_input_delay  4.0 -clock clk $in_ports
set_output_delay 3.0 -clock clk [all_outputs]
set_driving_cell -lib_cell sky130_fd_sc_hd__buf_2 $in_ports
set_load 0.02 [all_outputs]

An input delay of 4.0 ns says: data on this pin arrives 4.0 ns after the clock edge, because logic outside took that long. With a 10 ns period, your internal logic from that pin to the first flop now has 10 − 4.0 = 6.0 ns, minus setup time and uncertainty. An output delay of 3.0 ns says the receiver needs the data 3.0 ns before its next edge, so your logic from the last flop to the pin gets 7.0 ns minus clock-to-Q.

These numbers come from a budget agreed with whoever designs the neighbouring logic. A common starting point when nobody knows yet is to give each side a share of the period, then refine. The driving cell and load make the tool compute realistic transition times at the ports instead of assuming perfect edges. The load value is in the library's capacitance unit, often picofarads; check the Liberty header.

Exceptions: false paths and multicycle paths

Some paths exist in the netlist but do not need to meet single-cycle timing.

# Configuration register written once at start-up, then static
set_false_path -from [get_cells cfg_mode_reg*]

# Asynchronous reset input, synchronised inside the block
set_false_path -from [get_ports rst_n]

# A multiply that the control logic only samples every 2nd cycle
set_multicycle_path 2 -setup -from [get_cells mul_a_reg*] \
    -to [get_cells mul_q_reg*]
set_multicycle_path 1 -hold  -from [get_cells mul_a_reg*] \
    -to [get_cells mul_q_reg*]

The multicycle pair is the classic trap. Moving the setup check to the second edge also moves the default hold check one edge later, which would demand an impossibly long minimum delay. The -hold 1 line moves the hold check back to where it belongs. Write the two together, every time.

For two genuinely asynchronous clocks, set_clock_groups -asynchronous -group clk_a -group clk_b removes timing between them. That is correct only if every crossing has a proper synchronizer; the SDC cannot check that for you.

Over-constraints and under-constraints

Two kinds of mistakes, with opposite symptoms:

Mistake What you see What really happens
Missing create_clock on a clock pin Few or no paths reported Every flop on that clock is untimed
No I/O delays Ports look fine Port paths checked against no external budget, or not at all
Wildcard false path such as -from [all_registers] Timing is clean Real paths are switched off
Multicycle without the hold fix Huge hold violations Tool inserts many unnecessary buffers
Uncertainty far too large Endless violations Tool upsizes cells and burns area and power
Period tighter than the spec "for margin" Harder closure Margin you may not need, paid in power and area

Under-constraint is the dangerous one, because clean reports feel like success. Over-constraint costs effort and silicon but is visible.

Check the constraints, not just the timing

Open tools give you ways to test the SDC itself:

  • report_checks -unconstrained in OpenSTA lists paths that have no requirement. In a finished block, this list should be empty or fully explained.
  • report_clock_properties (or report_clocks in other tools) confirms each clock's period and waveform.
  • Count the endpoints timed against each clock and compare with the number of flip-flops you expect.
  • Review every set_false_path and set_multicycle_path with a colleague, and write a comment saying why the path is safe. An exception without a reason will not survive the next design change.

Try it yourself

  1. Take a small design with a configuration register, a two-cycle multiplier and an asynchronous reset. Synthesise it with Yosys against a sky130 library.
  2. Load it into OpenSTA with only create_clock. Run report_checks -unconstrained and note what is untimed.
  3. Add the I/O delays, then the exceptions one at a time. After each, rerun report_checks and see which paths appear or disappear.
  4. Leave out the -hold 1 line on the multicycle path and look at the hold report. Then add it back and confirm the hold check returns to the launch edge.
