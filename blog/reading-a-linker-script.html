Reading a linker script: sections, memory regions and the map file

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

How a GNU linker script places code and data in flash and RAM, why .data has two addresses, and how to use the map file, size and nm to find out what is eating your memory.

In this article

  2. Load address and run address
  3. Three numbers from size
  4. Reading the map file
  5. Common memory hogs
  6. Try it yourself

Sooner or later a firmware build fails with "region RAM overflowed", or the image suddenly grows by 20 kB after a one-line change. Both questions are answered by two files most people never open: the linker script, which says where everything goes, and the map file, which says where everything went. Reading them takes about fifteen minutes to learn and saves days.

Two blocks: MEMORY and SECTIONS

A GNU ld linker script for a microcontroller has two main parts. MEMORY lists the physical memories. SECTIONS says which pieces of your program go into which memory, in what order.

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x80000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x80040000, LENGTH = 256K
}

SECTIONS
{
  .text : {
    KEEP(*(.text.start))
    *(.text .text.*)
  } > FLASH

  .rodata : { *(.rodata .rodata.*) } > FLASH

  .data : ALIGN(4) {
    _sdata = .;
    *(.data .data.*)
    . = ALIGN(4);
    _edata = .;
  } > RAM AT > FLASH
  _sidata = LOADADDR(.data);

  .bss (NOLOAD) : ALIGN(4) {
    _sbss = .;
    *(.bss .bss.* COMMON)
    . = ALIGN(4);
    _ebss = .;
  } > RAM
}

This is the layout used in the Ketuna track D labs on QEMU's virt machine, which pretends the first 256 kB of its RAM is flash. Read the SECTIONS block line by line:

  • .text : { ... } > FLASH creates an output section called .text and fills it with input sections from every object file. *(.text .text.*) means "from all files, every section whose name is .text or starts with .text.". The > FLASH puts the result in the flash region.
  • KEEP(...) protects a section from --gc-sections, which removes anything no code refers to. The reset entry is referenced only by the hardware, so it must be kept.
  • . is the location counter: the current address. _sdata = .; defines a symbol whose value is that address. It occupies no memory; it is a label that startup code can use.
  • ALIGN(4) rounds the counter up to a multiple of 4, so word-wide copy loops work.

Load address and run address

The line that confuses most readers is > RAM AT > FLASH. An initialised global such as int mode = 3; must be in RAM when the program runs, because the program may change it. But RAM is empty at power-up, so the value 3 has to be stored in flash. The section therefore has two addresses:

  • the VMA (virtual memory address, really just the run address): where the code expects the variable, in RAM;
  • the LMA (load memory address): where its bytes sit in the image, in flash.

> RAM AT > FLASH sets the VMA in RAM and the LMA in flash. LOADADDR(.data) gives the LMA, which startup code reads as _sidata and copies to _sdata. Code and constants run in place, so for .text and .rodata the two addresses are the same. .bss has no initial contents, so it is marked NOLOAD and gets only a run address.

Three numbers from size

After every link, run the size tool. Here is output from a made-up build, for illustration:

$ riscv64-unknown-elf-size app.elf
   text    data     bss     dec     hex filename
   6716     136   12544   19396    4bc4 app.elf

The columns are totals, not sections. text includes code and constants. Flash use is text + data = 6852 bytes, because the initial values of .data live in flash. Static RAM use is data + bss = 12,680 bytes. If the script reserves the stack as a NOLOAD section, as the lab script does with 8 kB, that reservation is counted inside bss.

For a percentage view, add -Wl,--print-memory-usage to the link command. With the same numbers, FLASH shows 6852 B of 256 kB, about 2.61 %, and RAM 12,680 B, about 4.84 %.

Reading the map file

Totals tell you that memory is used, not by what. For that, ask the linker for a map: add -Wl,-Map=app.map. The file is long, but the part you need is the "Linker script and memory map" section, which lists each output section with its address and size, followed by every input section that went into it:

.data           0x80040000       0x88 load address 0x80001a3c
                0x80040000                _sdata = .
 *(.data .data.*)
 .data.lut      0x80040000       0x80 build/filter.o
 .data.mode     0x80040080        0x4 build/main.o

Each input line gives the section name, its run address, its size in hex and the object file it came from. The header line shows both addresses at once: run address 0x80040000, load address after the code. Search for the largest sizes and you know which file to look at.

A quicker route to the biggest symbols is nm:

riscv64-unknown-elf-nm --print-size --size-sort --reverse-sort app.elf | head

The symbol type letter tells you where each item lives: T for code, R for read-only data, D for initialised data, B for .bss.

Common memory hogs

  • A missing const. static uint16_t lut[64] = {...}; goes into .data and costs 128 bytes of flash and 128 bytes of RAM. Add const and it moves to .rodata, flash only. In the map, a table under .data that the code never writes is the clue.
  • Formatted printing. A full printf with floating-point support can be the largest thing in a small image. The map shows library objects by name, so you can see exactly what one printf("%f") pulled in.
  • Large zeroed buffers. They cost nothing in flash but all of their size in RAM, under .bss. Check whether two buffers that are never used at the same time could share memory.
  • Dead code kept alive. Build with -ffunction-sections -fdata-sections and link with --gc-sections so unused functions are dropped. Without the first two flags, each object file is one big section and the linker can only keep or drop it whole.

Try it yourself

  1. Link any small RISC-V program with the script above and -Wl,-Map=app.map,--print-memory-usage. Open the map and find _sdata, _sidata and the file each .data input section came from.
  2. Run riscv64-unknown-elf-objdump -h app.elf. Check that .data shows different VMA and LMA columns and .text does not.
  3. Add a 64-entry initialised table without const, rebuild, and note the change in the data column of size. Add const and watch the bytes move to text.
  4. Make the RAM region 8 kB long and read the linker's overflow message. Then explain to a colleague, using the map, which section pushed it over.
