SystemVerilog Assertions for beginners: immediate vs concurrent, and your first property

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Learn the difference between immediate and concurrent assertions, exactly which values a concurrent assertion samples on a clock edge, and how to write and read a property for a request/acknowledge handshake.

In this article
  1. Immediate assertions: a check at one instant
  2. Concurrent assertions: rules over clock cycles

A scoreboard checks results at the end of a transaction. An assertion checks a rule at the moment it is broken, next to the signal that broke it. When an assertion fires, the failure message points at a time and a line of RTL, often many cycles before any wrong output appears. SystemVerilog Assertions (SVA) give you two kinds of assertion, and the difference between them, along with when values are sampled, is what every beginner needs first.

Immediate assertions: a check at one instant

An immediate assertion lives in procedural code and checks a condition right now, like assert in C or Python.

always_comb begin
  assert (!(push && pop && empty))
    else $error("pop from empty FIFO while pushing");
end

It is easy to read and good for simple conditions that must hold whenever the code runs. Its weakness is that it has no idea of time. It cannot say "within three cycles", and in combinational code it may evaluate several times in one time step while signals are still settling, which can produce false failures on glitches. Deferred forms (assert #0 and assert final) reduce that problem, but they still check a single instant.

Concurrent assertions: rules over clock cycles

A concurrent assertion is tied to a clock and can describe behaviour across many cycles.

a_ack_in_time: assert property (
  @(posedge clk) disable iff (!rst_n)
  req |-> ##[1:3] ack
);

Read it as: "On every rising edge of clk, unless reset is active, if req is 1, then ack must be 1 on some edge between one and three cycles later." The pieces:

  • @(posedge clk) is the sampling clock.
  • disable iff (!rst_n) switches the check off during reset, when signals are not meaningful.
  • req is the antecedent, the condition that starts a check.
  • |-> is overlapping implication: the consequent starts on the same edge the antecedent matched. |=> would start one edge later.
  • ##[1:3] ack is the consequent: ack true one to three cycles later.

If req is 0 on an edge, the implication passes trivially for that edge. This is called a vacuous pass, and it is why you will later pair assertions with cover statements.

What a concurrent assertion actually sees

This is the part that confuses people. A concurrent assertion samples signal values just before the clock edge, in what the standard calls the preponed region. It sees the same values a flip-flop would capture on that edge. A signal that changes slightly after an edge is seen at the next edge.

Walk through it edge by edge. At edge 1, req is still 0, so nothing starts. req rises just after edge 1, so edge 2 is the first edge that samples it as 1; the check starts there. At edge 3, ack is 0, so the property keeps waiting. ack rises just after edge 3, so edge 4 sees it as 1. That is two cycles after the start, inside the window, so this attempt passes.

Notice also that req is still 1 at edges 3 and 4. Each of those edges starts a new attempt. The attempt from edge 3 needs ack at edge 4, 5 or 6, and is satisfied at edge 4. The attempt from edge 4 needs ack at edges 5 to 7, but ack falls before edge 5. If it never comes back, that attempt fails at edge 7. This is a common surprise: an assertion that seems to describe "one handshake" actually starts a fresh check on every edge where the antecedent is true. Writing $rose(req) |-> ##[1:3] ack starts one check per request instead, which is usually what the spec means.

A small set of handshake properties

A spec for this handshake might say: a request is acknowledged within one to three cycles; ack never appears without an outstanding request; ack is a single-cycle pulse. Those turn into three properties and a cover.

module handshake_props (input logic clk, rst_n, req, ack);
  default clocking cb @(posedge clk); endclocking
  default disable iff (!rst_n);

  a_ack_in_time:  assert property ($rose(req) |-> ##[1:3] ack);
  a_no_stray_ack: assert property (ack |-> req);
  a_ack_pulse:    assert property (ack |=> !ack);

  c_slowest_ack:  cover property ($rose(req) ##3 ack);
endmodule

The cover proves the slowest legal case actually happened in your simulation. Without it, every test might acknowledge in one cycle and the three-cycle edge would never be exercised.

Common beginner mistakes

  • Forgetting disable iff. Signals are often X or arbitrary during reset, and the assertion fails before the test even starts.
  • Expecting to see a value on the edge it changed. Concurrent assertions see the value from just before the edge, like a flip-flop.
  • Using |-> where |=> was meant. a |-> b checks b on the same edge as a; a |=> b checks it on the next edge.
  • Trusting a pass without a cover. If the antecedent never matched, the property passed vacuously and checked nothing.

Try it yourself

  1. Write a tiny Verilog requester and responder where ack follows req after a parameterised delay, and attach the property module above with a bind statement.
  2. Simulate it with Verilator and --assert, and confirm the assertions pass for delays of 1 to 3. Open-source SVA support is a subset that grows with each release, so use a recent version and read any "unsupported" message as a hint to rewrite that property in simpler terms.
  3. Set the delay to 4 and read the failure message: which edge does it report, and why that one?
  4. Remove $rose from the first property, hold req high for several cycles, and explain from the diagram why it now fails.
