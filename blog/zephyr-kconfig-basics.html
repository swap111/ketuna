Kconfig in Zephyr: turning features on without editing source

Embedded systems Beginner 27 Nov 2026 5 min read By Ketuna

How Zephyr's Kconfig decides what gets compiled, how prj.conf and menuconfig set options, why an option you set can silently stay off, and how to check what actually ended up in your build.

Zephyr contains drivers, network stacks, file systems, shells and logging, far more than any one product needs. You choose which parts go into your firmware without editing a line of Zephyr's source, using a configuration system called Kconfig. It is simple to use and easy to misread: the most common beginner problem is setting an option that then quietly does not take effect. This article explains how the system works and how to check what your build really contains.

Options, values and where they live

Kconfig is a language for declaring configuration symbols. Each symbol has a type, usually a boolean (y or n), an integer or a string, along with a default value, a help text and rules about other symbols it depends on. Zephyr and its modules declare thousands of them in files named Kconfig.

At build time every symbol gets a final value, and those values become C macros. A boolean set to y appears as CONFIG_NAME defined to 1; one set to n is simply not defined. CMake reads the same values to decide which source files to compile, so turning off a driver removes its code entirely rather than skipping it at run time.

Values come from several places, merged in order:

  1. the defaults written in the Kconfig files;
  2. the board's default configuration file, supplied with the board;
  3. your application's prj.conf;
  4. an optional boards/<board>.conf in your application, for one board only;
  5. extra fragments passed on the command line, for example west build -- -DEXTRA_CONF_FILE=debug.conf (older releases called this OVERLAY_CONFIG).

Later sources override earlier ones, as long as the dependency rules allow it.

A first prj.conf

prj.conf is a plain list of assignments:

CONFIG_GPIO=y
CONFIG_I2C=y
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3
CONFIG_MAIN_STACK_SIZE=2048
CONFIG_ASSERT=y

Each line has a reason worth writing down next to it, using # comments. CONFIG_I2C builds the I2C subsystem and the drivers for enabled I2C controllers. CONFIG_MAIN_STACK_SIZE sets the stack of the thread that runs main() in bytes. CONFIG_ASSERT enables run-time assertions, useful during development and a deliberate decision for release builds.

A rule of thumb: put only what your application needs in prj.conf, and nothing that is already the default. A short file is easy to review, and it does not pin values that should follow the board.

Dependencies, and why your option can stay off

Symbols declare relationships with depends on and select. A symbol that depends on I2C cannot be y unless I2C is y. A symbol that selects another forces it on.

Here is the trap. If you write CONFIG_SOME_DRIVER=y in prj.conf but its dependency is not met, Kconfig cannot honour the assignment. The symbol stays n, its code is not compiled, and your application fails later with an undefined function or a device that never appears. The build reports the conflict, naming the symbol, the value you asked for, the value it got and the dependency that was not satisfied. Read the configuration output when a build starts behaving unexpectedly, rather than scrolling past it.

Drivers add a second condition. In Zephyr, many driver options default to y only when the devicetree contains an enabled node for that hardware. A driver is built when both its Kconfig symbol is on and a matching devicetree node has status = "okay". If either half is missing, the device is not there.

Exploring and checking the configuration

Browsing with menuconfig

To browse all options with their help text and dependencies, open the interactive menu on a configured build:

west build -b qemu_riscv32 samples/hello_world
west build -t menuconfig        # text interface
west build -t guiconfig         # graphical interface, if available

Press / in menuconfig to search for a symbol by name. Selecting a symbol and pressing ? shows its help, where it is defined, what it depends on and what selects it. That screen answers most "why can't I enable this?" questions.

Changes made in menuconfig are saved to the build folder only. A pristine rebuild (west build -p) discards them. Once you have found the settings you want, copy the lines into prj.conf so that they are versioned and reviewed like code.

Checking what you actually got

Do not trust what you asked for; read what you got. After every configuration, Zephyr writes the full resolved configuration to:

build/zephyr/.config

Search it for the options you care about:

grep -E "CONFIG_(I2C|LOG|ASSERT)=" build/zephyr/.config
grep "CONFIG_SOME_DRIVER" build/zephyr/.config

A disabled boolean appears as a comment such as # CONFIG_SOME_DRIVER is not set. Comparing two .config files with diff is the fastest way to see why one build behaves differently from another.

Your own options

Applications can declare their own symbols in a Kconfig file next to prj.conf. It must end by including Zephyr's own Kconfig tree:

mainmenu "Sensor demo"

config DEMO_SAMPLE_PERIOD_MS
    int "Sample period in milliseconds"
    default 250
    range 10 10000

config DEMO_VERBOSE
    bool "Log every sample"
    depends on LOG

source "Kconfig.zephyr"

In C, use the value directly and test booleans with IS_ENABLED, which works in ordinary if statements so that both branches are still compiled and type-checked:

k_msleep(CONFIG_DEMO_SAMPLE_PERIOD_MS);
if (IS_ENABLED(CONFIG_DEMO_VERBOSE)) {
    LOG_INF("sample %d", value);
}

The range line means a typo such as CONFIG_DEMO_SAMPLE_PERIOD_MS=5 is rejected at configuration time, not discovered on the bench.

Common mistakes

  • Setting an option whose dependency is off and assuming it worked
  • Editing options in menuconfig and losing them on the next pristine build
  • Copying a whole .config into prj.conf, which pins hundreds of defaults and hides the few choices that matter
  • Using #ifdef everywhere instead of IS_ENABLED, so code in disabled branches stops being compiled and rots
  • Forgetting that a board-specific .conf file also applies, and wondering where a value came from

Try it yourself

  1. Build samples/hello_world for qemu_riscv32, run west build -t run, and then search build/zephyr/.config for CONFIG_SERIAL and CONFIG_CONSOLE.
  2. Add CONFIG_LOG=y to the sample's prj.conf, rebuild, and use diff between the old and new .config to see every symbol it pulled in.
  3. Add an application Kconfig with an integer option, set an out-of-range value in prj.conf, and read the message. Then find your option in menuconfig with /.
