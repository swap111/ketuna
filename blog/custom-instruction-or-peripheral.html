Adding a custom instruction to a RISC-V core: when it beats a peripheral

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

RISC-V reserves opcode space for your own instructions. Compare a custom instruction with a memory-mapped accelerator on overhead, datapath changes, toolchain and verification, and pick by the size of the work.

In this article

Once profiling shows that a small kernel dominates a workload, there are two common ways to put it in hardware on a RISC-V SoC. You can add a custom instruction to the core, so the kernel becomes one more operation in the pipeline. Or you can build a memory-mapped peripheral that the core drives through registers, possibly with DMA. Both work. They differ in where the overhead lands, how much of the system you have to change, and how the decision ages when the software changes. The deciding factor is usually the granularity of the work.

Where custom instructions live

The RISC-V base specification sets aside major opcodes for non-standard extensions. The two that are safest for 32-bit cores are custom-0 (opcode 0001011) and custom-1 (opcode 0101011); the standard extensions promise never to use them. Inside a custom opcode you can reuse the standard R, I or S formats, keeping funct3 and funct7 to select among several operations. Staying with standard formats keeps the register fields where the decoder already looks, so the register file is read exactly as for any other instruction.

Take a concrete example: a four-lane signed 8-bit dot product. Each source register holds four packed int8 values, and the result is their 32-bit dot product. It is the inner step of many quantized neural network and filter kernels.

// Functional unit for dot4 (custom-0, funct3 = 0, funct7 = 0).
module dot4_unit (
  input  wire [31:0] rs1, rs2,
  output wire [31:0] result
);
  wire signed [15:0] p0 = $signed(rs1[ 7: 0]) * $signed(rs2[ 7: 0]);
  wire signed [15:0] p1 = $signed(rs1[15: 8]) * $signed(rs2[15: 8]);
  wire signed [15:0] p2 = $signed(rs1[23:16]) * $signed(rs2[23:16]);
  wire signed [15:0] p3 = $signed(rs1[31:24]) * $signed(rs2[31:24]);
  assign result = {{16{p0[15]}}, p0} + {{16{p1[15]}}, p1}
                + {{16{p2[15]}}, p2} + {{16{p3[15]}}, p3};
endmodule

What changes in the core

Adding the instruction touches more than the functional unit:

  • Decode. Recognise the custom opcode and funct fields, mark the instruction as writing rd, and route operands to the new unit. Everything else should still raise an illegal-instruction trap.
  • Execute. Add the unit beside the ALU and a new input to the result multiplexer. Four 8 × 8 multipliers and an adder tree may not fit in one cycle at your target clock; if not, the instruction becomes multi-cycle and needs a stall, or the unit is pipelined and needs forwarding from its later stage.
  • Hazards. A multi-cycle unit makes the hazard logic aware of a new producer with a longer latency.
  • Register file ports. The base RISC-V register file has two read ports and one write port. An instruction that wants three sources, such as dot-product-and-accumulate, needs a third read port or a different encoding (for example, rd doubling as an accumulator source). Extra ports are expensive and affect timing everywhere.
  • State. Any architectural state the instruction keeps, such as an internal accumulator, must be saved on context switches. Keeping custom instructions stateless avoids touching the operating system.

Toolchain and software

You do not need to modify the compiler to use a custom instruction. The GNU assembler's .insn directive emits arbitrary encodings in a standard format, and an inline-assembly wrapper makes it callable from C:

#include <stdint.h>

static inline int32_t dot4(uint32_t a, uint32_t b)
{
    int32_t r;
    __asm__ (".insn r 0x0B, 0, 0, %0, %1, %2"
             : "=r"(r) : "r"(a), "r"(b));
    return r;
}

The compiler treats the call as an opaque instruction: it allocates registers correctly but will not vectorise or schedule around it cleverly. That is usually acceptable for a hot inner loop. You also need a reference model of the instruction for the instruction set simulator that verification compares against, plus a pure-C fallback for cores without the extension.

The peripheral alternative

A memory-mapped accelerator needs no change to the core, the decoder or the toolchain. The core writes operands to registers or points a DMA engine at a buffer, starts the block, and collects results. It can run concurrently with the core, it works with any processor on the bus, and it can process large blocks with its own internal buffers.

Its cost is per-invocation overhead. Every register access crosses the bus. Suppose, as an illustration, each uncached peripheral access takes 5 cycles. One dot product through registers needs two operand writes, a start write, a status poll and a result read: at least 5 accesses, or about 25 cycles, for work the custom instruction does in 1 or 2. Over a million dot products, that is roughly 25 million cycles of overhead against 1 to 2 million.

Turn the granularity around and the answer flips. If the job is "compute the dot products of a 4 KiB weight buffer against a 4 KiB input buffer", the peripheral receives two addresses and a length, streams the data with DMA, and interrupts when done. The setup cost is paid once per buffer, the core is free meanwhile, and the accelerator can use far wider datapaths than the register file would ever allow.

Choosing between them

Factor Custom instruction Memory-mapped accelerator
Work per call A few cycles, register-sized operands Large blocks, long-running jobs
Overhead per call Near zero Bus accesses, interrupts or polling
Core changes Decoder, datapath, hazards None
Toolchain .insn or intrinsics, ISS model A driver
Concurrency with core None: it is the core Runs in parallel
Portability Only cores with the extension Any bus master

A useful rule: if operands fit in two registers and the result in one, and the operation is called in a tight loop, a custom instruction is likely to win. If the operation consumes buffers, keeps internal state or takes many cycles, a peripheral is likely to win. Many designs end up with both: a few custom instructions for fine-grained operations and a DMA-fed block for bulk work.

Common mistakes

  • Using opcode space that standard extensions may claim. Stay in custom-0 and custom-1 for 32-bit encodings.
  • Adding architectural state casually. Hidden accumulators complicate interrupts and context switches.
  • Forgetting the ISS. Lock-step verification fails on the first custom instruction unless the reference model knows it.
  • Ignoring the multi-cycle timing. A unit that misses timing pulls down the whole core's clock.

Try it yourself

  1. Write a Python reference for dot4 and test the Verilog unit against random operands in Icarus Verilog or with cocotb.
  2. Add the instruction to a small open-source RV32I core, assemble a test with .insn using a RISC-V GCC toolchain, and check the result in simulation.
  3. Synthesise the core with Yosys before and after the change and compare cell counts and the longest path with OpenSTA.
