What happens before main(): startup code on a microcontroller

Embedded systems Beginner 27 Nov 2026 5 min read By Ketuna

Between reset and the first line of main() a few dozen instructions set the stack pointer, copy initialised globals into RAM and zero the rest. Here is each step on a RISC-V microcontroller, and why C needs it.

In this article
  1. The C language makes promises the hardware does not keep
  2. The sequence from reset to main
  3. The startup code itself
  4. Bugs that live before main
  5. Try it yourself

On a laptop, main() feels like the beginning of the program. On a microcontroller it is not. When the chip comes out of reset, RAM holds random bits, there is no stack, and nothing has set your global variables to the values you wrote in the source. A short piece of startup code fixes all of that before main() is called, and when it is wrong the symptoms are baffling: globals with strange values, a crash on the first function call, or a bug that appears only after a power cycle.

The C language makes promises the hardware does not keep

Look at three lines of ordinary C:

int boot_count = 5;        /* initialised global  */
int errors;                /* uninitialised global */
int main(void) { return boot_count + errors; }

The C standard says boot_count starts at 5 and errors starts at 0. It also assumes that calling a function works, which needs a stack. None of this is true at reset. RAM is volatile memory: after power-up each bit is whatever the cells settled to. The only thing that survives power-off is flash, so the value 5 must be stored in flash and copied into RAM at run time.

The compiler and linker sort your variables into sections so the startup code can deal with each kind in bulk:

Section Holds Lives in Startup must
.text, .rodata Code and constants Flash Nothing; used in place
.data Initialised globals RAM, initial values in flash Copy flash to RAM
.bss Zero or uninitialised globals RAM only Fill with zeros
stack Locals and return addresses RAM Set the stack pointer

.bss takes no space in flash at all: there is nothing to store except "this many bytes of zeros", which is why a large zeroed array makes RAM use grow but not the firmware image.

The sequence from reset to main

What the hardware does at reset depends on the architecture. Some cores read an initial stack pointer and a reset address from a table at a fixed location. A RISC-V core simply starts fetching instructions at an implementation-defined reset address, with almost every register undefined. On RISC-V, the first instructions therefore must be assembly, because a C function cannot run before the stack pointer is valid.

Each step has a reason:

  1. Set the stack pointer. Every function call stores its return address and locals on the stack. The stack usually starts at the top of RAM and grows down.
  2. Set the global pointer (gp). The RISC-V toolchain can reach small globals with one instruction relative to gp. If gp is wrong, those accesses hit the wrong addresses.
  3. Set the trap vector (mtvec). If anything faults before this, the core jumps to an undefined address and you learn nothing. With a handler in place, an early bug at least lands somewhere you can inspect.
  4. Copy .data, zero .bss. After this, every global holds the value the C code expects.
  5. Optional early hardware setup. Switching to a faster clock, enabling an FPU, running C++ static constructors.
  6. Call main(). On bare metal there is nothing to return to, so the startup code loops (or resets) if main() ever returns.

The startup code itself

This is a minimal RISC-V version, close to what the Ketuna track D labs use on QEMU's virt machine. The symbols with leading underscores are not variables; the linker script defines them as addresses.

    .section .text.start, "ax"
    .globl _start
_start:
    la    sp, _stack_top        # 1. stack
    .option push
    .option norelax
    la    gp, __global_pointer$ # 2. global pointer
    .option pop
    la    t0, trap_vector       # 3. trap vector
    csrw  mtvec, t0

    la    t0, _sidata           # 4a. .data source (flash)
    la    t1, _sdata            #     .data destination (RAM)
    la    t2, _edata
1:  bgeu  t1, t2, 2f
    lw    t3, 0(t0)
    sw    t3, 0(t1)
    addi  t0, t0, 4
    addi  t1, t1, 4
    j     1b
2:  la    t1, _sbss             # 4b. zero .bss
    la    t2, _ebss
3:  bgeu  t1, t2, 4f
    sw    zero, 0(t1)
    addi  t1, t1, 4
    j     3b
4:  call  main                  # 6.
5:  wfi
    j     5b

The .option norelax around the gp load matters. The linker normally "relaxes" address calculations into shorter gp-relative forms, and it would happily do that to the instruction that is supposed to set gp, producing an instruction that computes gp from itself.

Notice that the copy loop moves whole 32-bit words. That only works if the linker script aligns _sdata, _edata, _sbss and _ebss to 4 bytes. If they are not aligned, the last variable in the section may be skipped or a neighbour overwritten.

Bugs that live before main

  • Startup code that reads a global before the copy. If clock setup runs before step 4 and reads a configuration global, it reads random RAM. Use only constants and locals there.
  • A debugger that skips startup. Some debug flows load the image and jump straight to main. A global like boot_count then holds whatever was in RAM, and the bug vanishes on a real power-up.
  • Wrong stack top. If _stack_top points past the end of physical RAM, the first function call writes to nothing and the core faults, often before any output.
  • Forgetting KEEP on the startup section. With --gc-sections, the linker removes sections nothing refers to. The reset code is referenced only by the hardware, so it must be kept explicitly.
  • Several cores. On a multi-core part, every core may start at the same address. The startup code reads the core ID (mhartid on RISC-V) and parks all but one, or each needs its own stack.

Try it yourself

  1. Install the RISC-V cross-compiler and QEMU (gcc-riscv64-unknown-elf and qemu-system-misc on Ubuntu). Build a tiny program with the startup code above and run it with qemu-system-riscv32 -M virt -bios none -nographic -kernel app.elf.
  2. Start QEMU with -s -S added, attach gdb-multiarch app.elf, type target remote :1234, then stepi through _start. Use x/4wx &boot_count before and after the copy loop and watch the value 5 appear.
  3. Run riscv64-unknown-elf-objdump -h app.elf and find the .data section. Its VMA (where it runs) and LMA (where it is stored) differ; .text has the same value in both columns.
  4. Delete the .bss zero loop, add errors++ to main, and see what value you get. Then explain it to someone else before you put the loop back.
