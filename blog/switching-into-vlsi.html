Switching into VLSI from software or another branch: what transfers and what to learn

Careers & skills Intermediate 27 Nov 2026 6 min read By Ketuna

Moving into chip design from software, mechanical, civil or another branch. Which of your skills carry over, which fundamentals you must rebuild, and one project that shows a reviewer the switch is real.

In this article
  1. What carries over from software
  2. What does not carry over
  3. What carries over from other engineering branches
  4. The fundamentals to rebuild, whichever way you come
  5. One project that proves the switch
  6. Try it yourself

People arrive at chip design from many directions: software developers drawn to hardware, electrical engineers who spent years in power or controls, mechanical or civil graduates who found digital logic more interesting than their own branch. The switch is possible, but it is easy to spend months on the wrong things. The useful question is not "where do I start?" but "what do I already have, what is genuinely missing, and how will I prove the gap is closed?"

What carries over from software

Software engineers usually underestimate how much transfers, and then overestimate how much of their programming instinct applies to RTL.

Software skill Where it helps in VLSI
Version control, code review, CI Directly. RTL, testbenches and flow scripts live in Git with the same workflows
Python and scripting Testbenches with cocotb, report parsing, flow automation, reference models
Testing mindset Verification is mostly testing: stimulus, checkers, coverage, regressions
Object-oriented design SystemVerilog testbench classes and UVM-style frameworks reuse these ideas
Debugging discipline Reproduce, localise, change one thing at a time; it is the same craft
Linux and the shell Every EDA flow runs there

This is why many people from software enter through verification: the language of testbenches, randomisation and coverage is close to what they know.

What does not carry over

The biggest trap is reading Verilog as a programming language. It looks like C, but RTL describes hardware that all exists at once. Every always block runs in parallel, every signal is a wire or a register, and a for loop in synthesizable code builds copies of logic rather than repeating work in time.

// Software reading: "add the four values one by one".
// Hardware reality: a chain of adders, all present at
// once, producing the result in the same clock cycle.
module sum4 (
  input  wire [31:0] data,   // four 8-bit values
  output reg  [9:0]  sum
);
  integer i;
  always @(*) begin
    sum = 0;
    for (i = 0; i < 4; i = i + 1)
      sum = sum + data[8*i +: 8];
  end
endmodule

Other instincts that need rebuilding:

  • Time is physical. A path that is too long fails timing; there is no "it just runs slower".
  • Resources are fixed after tape-out. You cannot patch a missing gate with an update, so verification before tape-out matters far more than testing after release does in software.
  • Clocks and resets are design decisions, and crossing between clock domains is a whole category of bugs with no software equivalent.

What carries over from other engineering branches

Engineers from electrical, mechanical, civil or instrumentation backgrounds bring different strengths. Circuit theory, signals and control carry over strongly to analog and mixed-signal work. A habit of tolerances, safety margins and design reviews carries over to every part of chip design: timing margin and corner analysis are the same idea as a structural safety factor. Experience with requirements, documentation and sign-off processes is valued everywhere, because chips are built by large teams with hard gates.

What these engineers usually need to rebuild is digital fundamentals and programming. If you have not written code daily, budget real time for C or Python and the Linux shell, because every flow assumes them.

The fundamentals to rebuild, whichever way you come

Whatever your starting point, a short list of topics comes up in every digital design and verification role, and you need to be able to work them by hand, not just recognise them:

  1. Combinational and sequential logic, and how synthesis turns RTL into gates
  2. Finite state machines: drawing, coding and testing them
  3. Setup and hold time, and finding the maximum clock frequency of a path
  4. Clock domain crossing: synchronizers, handshakes and asynchronous FIFOs
  5. A bus protocol, such as a simple APB-style register interface
  6. Self-checking testbenches with a reference model, and what coverage tells you

For the physical design path, add floorplanning, placement, clock tree synthesis, routing, static timing analysis and DRC/LVS. For analog, add transistor-level circuit analysis and SPICE simulation. Pick one direction first. Trying to cover all of them at once is the most common reason a switch stalls.

One project that proves the switch

A reviewer looking at someone switching fields has one question: can this person actually do the work, or have they only watched lectures? Certificates and course lists answer that weakly. A finished project in public answers it strongly.

A good switching project is small enough to finish and complete enough to show the whole loop. One option for front-end design or verification:

  • Design: a UART receiver with a small FIFO and an APB-style register interface, written in synthesizable Verilog
  • Verify: a cocotb testbench with a Python reference model, random stimulus, and at least one deliberately planted bug that the bench catches
  • Check: clean Verilator lint and a Yosys synthesis run with the cell count recorded
  • Optionally harden it: take it through an open flow such as LibreLane on the sky130 PDK and report timing at one corner
  • Document: a README that states what works, what does not, and what you would do next

Make the reasoning visible. Explain in the README why you chose a particular synchronizer, how you decided the FIFO depth, and what the planted bug taught you. If you used an AI assistant for parts of it, say which parts and how you checked them. A reviewer can then judge your thinking, which is what they are really hiring.

Lean on your background in the write-up, too. A former software developer can show a clean CI pipeline; an electrical engineer can show a careful timing analysis. The switch is more convincing when the old skills visibly strengthen the new work.

Try it yourself

  1. Write down your existing skills in two columns: "transfers directly" and "needs rebuilding", using the tables above as a starting point. Be honest about the second column.
  2. Take the four-input adder loop above, synthesise it with Yosys (yosys -p "read_verilog sum4.v; synth; stat") and look at the cell count. Confirm for yourself that the loop became parallel hardware.
  3. Work one setup-time calculation and one FSM by hand on paper, then check them in Icarus Verilog or OpenSTA.
  4. Scope the switching project above into three milestones, and finish the first one, a passing self-checking test, before adding anything else.
