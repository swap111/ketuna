Debugging bare-metal firmware with GDB and OpenOCD

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

How GDB, OpenOCD and a JTAG probe fit together, and how to use breakpoints, watchpoints and memory examination to inspect a running microcontroller and its peripherals without adding a single printf.

In this article

When firmware misbehaves, the first instinct is to add printf calls. On a microcontroller that has real costs: it needs a working UART, it changes timing, it grows the image, and it cannot show you a variable at the moment a fault happens. A debugger can. With GDB, OpenOCD and an inexpensive probe you can stop the core at any line, read any variable or peripheral register, and catch the instruction that corrupts memory. This article walks through the set-up and the handful of commands that do most of the work.

Three programs and a cable

The chain has four links:

  • GDB, the GNU debugger, built for your target (riscv64-unknown-elf-gdb or a multi-architecture build such as gdb-multiarch). It reads your ELF file, so it knows the source lines, symbols and types.
  • OpenOCD, an open-source debug server. It speaks the GDB remote protocol on a TCP port (3333 by default) and translates requests into low-level debug operations.
  • A debug probe, a small USB device that drives the target's JTAG pins.
  • The on-chip debug logic. On RISC-V this is the debug module described by the RISC-V Debug Specification. It can halt the core, read and write registers and memory, and provides a limited number of hardware triggers for breakpoints and watchpoints.

GDB never touches the hardware directly. It asks OpenOCD to "halt", "read 4 bytes at this address" or "set a breakpoint here", and OpenOCD does it through the probe. QEMU provides the same GDB protocol with no hardware at all, which makes it a good place to practise.

Connecting

OpenOCD is configured with two script files: one for the probe (the interface) and one for the chip (the target). Many boards also have a single board file.

openocd -f interface/<your-probe>.cfg -f target/<your-chip>.cfg

The exact file names come from your OpenOCD installation's scripts folder or your board's documentation. Once OpenOCD reports that it found the target, start GDB in another terminal:

$ riscv64-unknown-elf-gdb build/app.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) break main
(gdb) continue

monitor passes a command straight to OpenOCD; here it resets the chip and halts it at the first instruction. load writes the ELF file's loadable sections to the target, including flash if OpenOCD knows the flash layout. After continue, the core runs until it reaches main.

To practise without a board, run a RISC-V program on QEMU with -s -S added to the command line. -s opens a GDB server on port 1234 and -S holds the CPU at reset until GDB says go. Then use target remote :1234 instead of port 3333.

Breakpoints: software and hardware

A software breakpoint replaces an instruction with a break instruction (ebreak on RISC-V). That needs writable memory, so it works for code in RAM. Code in flash cannot be patched this way on most parts, so GDB needs a hardware breakpoint, which uses one of the core's trigger registers to compare the program counter.

(gdb) hbreak uart_isr          # hardware breakpoint on a function
(gdb) break ringbuf.c:42 if head == tail
(gdb) info breakpoints
(gdb) delete 2

The number of hardware triggers is small and differs between implementations; when you run out, GDB or OpenOCD reports an error when it tries to insert them. The conditional breakpoint above is evaluated by GDB each time the core stops there, so it is slow if the line runs often, but it saves restarting until the interesting case appears.

Watchpoints: who changed my variable

The most valuable debugger feature in firmware is the watchpoint: stop the core when an address is written. It answers the question "which code is corrupting this variable?", which is nearly impossible with print statements.

(gdb) watch rx.overflows        # stop on write
(gdb) rwatch config_ptr         # stop on read
(gdb) continue
Hardware watchpoint 3: rx.overflows
Old value = 0
New value = 1
uart_rx_isr () at ringbuf.c:31

GDB shows the old and new values and the line that wrote it. Watchpoints use the same limited hardware triggers, so watch a single variable rather than a large array.

Looking at memory and peripherals

Peripheral registers are just addresses, so GDB can read them:

(gdb) x/1bx 0x10000005          # UART line status register (QEMU virt)
0x10000005:     0x60
(gdb) x/8wx &rx.buf             # 8 words of a buffer, in hex
(gdb) p/x rx.head
(gdb) p/x $mcause               # RISC-V CSR, if the target exposes it
(gdb) info registers pc sp ra

x/NFU addr means examine N units of size U (b byte, h half-word, w word) in format F (x hex, d decimal, i instructions). On the QEMU virt machine's 16550-style UART, the line status value 0x60 has both "transmitter empty" bits set and the "data ready" bit clear.

Be careful: reading a register can change the hardware. Reading the UART's receive register removes a byte from its FIFO; reading some status registers clears their flags. A debugger window that refreshes a peripheral view every time the core stops can silently eat data. Read side-effect registers deliberately, once, or not at all.

Making the debugger tell the truth

  • Build with -g so GDB has source and type information. It does not change the generated code.
  • Debug at -Og while stepping. At -O2 variables live only in registers, lines are reordered and GDB reports "optimized out". Retest at release settings afterwards, because some bugs only appear there.
  • Remember that halting changes behaviour. While the core is stopped, peripherals keep running: UART bytes overflow, timers wrap, and a watchdog may reset the chip unless it is frozen in debug mode. For timing problems, use a GPIO toggle and a logic analyser instead.
  • Script repetitive set-up. Put the connection, monitor reset halt, load and your usual breakpoints in a file and start with gdb -x debug.gdb build/app.elf.

Try it yourself

  1. Build any program from the Ketuna track D labs, start it on QEMU with -s -S, connect with target remote :1234, and step from _start to main with stepi while printing $sp.
  2. Set a watchpoint on a ring-buffer index, type into the QEMU console, and confirm that GDB stops inside the receive interrupt handler.
  3. With a real board and OpenOCD, read the UART status register with x/1bx before and after sending a character from your laptop, and explain each bit that changed.
