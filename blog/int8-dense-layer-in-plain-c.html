Writing int8 inference for one dense layer in plain C

Edge AI Intermediate 27 Nov 2026 5 min read By Ketuna

A complete int8 dense layer in portable C - integer multiply-accumulate, 32-bit accumulators, requantization with a fixed-point multiplier and shift - and a numpy-generated test that proves it bit-exact.

In this article

  2. Turning M into a multiplier and a shift
  3. The C code
  4. Proving it bit-exact
  5. Try it yourself

Inference libraries hide the integer arithmetic of a quantized layer behind one function call. That is convenient until the device output differs from the Python model by one count on some inputs, or you need the same layer on a core the library does not support, or you are designing an accelerator and need to know exactly what it must compute. Writing one dense layer yourself, about thirty lines of C, removes the mystery. The other half of the job, and the more important half, is proving those thirty lines match a reference bit for bit.

The arithmetic you have to reproduce

The usual int8 scheme stores weights symmetrically (zero point 0), activations asymmetrically (zero point zx for the input, zy for the output) and biases as int32 in the scale sx × sw. For each output neuron o, the layer computes:

  1. Accumulate: acc = b[o] + Σi (x[i] − zx) × w[o][i], in int32.
  2. Requantize: y = round(M × acc) + zy, where M = sx sw / sy is a real number, usually much less than 1.
  3. Clamp y to the int8 range, or to [zy, 127] if a ReLU is fused into the layer.

Step 2 contains a real number, and the whole point is to avoid floating point on the device. The trick is to write M as a 31-bit integer and a shift.

Turning M into a multiplier and a shift

Any positive M can be written as m × 2−n with m in [0.5, 1). Store m as a fixed-point integer M0 = round(m × 231), which fits in an int32. Then

round(M × acc) = (acc × M0 + 2shift−1) >> shift, with shift = 31 + n

The product of a 32-bit accumulator and a 31-bit multiplier needs 64 bits, so it is computed in int64_t. Adding 2shift−1 before shifting rounds to nearest, with halves going up.

For example, take M = 0.0015. Python's math.frexp gives 0.0015 = 0.768 × 2−9, so M0 = round(0.768 × 231) = 1,649,267,442 and shift = 31 + 9 = 40. These two integers are computed once, offline, and stored with the layer's weights.

import math

def quant_mult(M):
    m, e = math.frexp(M)          # M = m * 2**e, 0.5 <= m < 1
    m0 = round(m * (1 << 31))
    if m0 == (1 << 31):           # rounding pushed m up to 1.0
        m0 //= 2
        e += 1
    return m0, 31 - e             # (multiplier, total right shift)

print(quant_mult(0.0015))         # (1649267442, 40)

The C code

#include <stdint.h>

static int8_t requant(int32_t acc, int32_t m0, int shift,
                      int32_t zy, int32_t lo, int32_t hi)
{
    int64_t p = (int64_t)acc * m0;
    p += (int64_t)1 << (shift - 1);          /* round half up */
    int32_t v = (int32_t)(p >> shift) + zy;  /* arithmetic shift */
    if (v < lo) v = lo;
    if (v > hi) v = hi;
    return (int8_t)v;
}

void dense_int8(const int8_t *x, int32_t zx,
                const int8_t *w, const int32_t *b,
                int n_in, int n_out,
                int32_t m0, int shift, int32_t zy,
                int32_t lo, int32_t hi, int8_t *y)
{
    for (int o = 0; o < n_out; o++) {
        const int8_t *row = &w[o * n_in];
        int32_t acc = b[o];
        for (int i = 0; i < n_in; i++)
            acc += ((int32_t)x[i] - zx) * (int32_t)row[i];
        y[o] = requant(acc, m0, shift, zy, lo, hi);
    }
}

A few decisions in this code are worth spelling out.

  • Widen before multiplying. Each operand is cast to int32_t before the multiply. In C the int8 values would be promoted to int anyway, but the explicit casts make the intent clear and keep the code correct on a target where int is 16 bits.
  • The accumulator is 32 bits. One product of (x − zx), which can reach ±255, and a weight of magnitude up to 128 is at most 32,640 in size. Even a few thousand inputs stay far inside the int32 range, while a 16-bit accumulator would overflow after a couple of products.
  • Right-shifting a negative number. Before C23, right-shifting a negative signed integer is implementation-defined. Common compilers for common cores perform an arithmetic shift, which is what the rounding formula assumes, but check your compiler's documentation, and let the test below catch it if not.
  • The zero point can be folded away. Σ (x − zx) w = Σ x w − zx Σ w. The second term depends only on constants, so you can precompute b'[o] = b[o] − zx Σi w[o][i] offline and drop the subtraction from the inner loop. That saves one operation per MAC and is what optimised kernels do. Write the plain version first, then fold, and keep the test.

Proving it bit-exact

"Close to the float model" is the wrong test for integer code. The right test is that the C output equals an integer reference exactly for every element. Off-by-one differences are not noise: they mean the rounding, the shift or a zero point differs, and those differences accumulate through a network.

Write the reference in numpy with the same integer steps, generate random inputs, and emit a header the C test includes:

import numpy as np

def requant_ref(acc, m0, shift, zy, lo, hi):
    v = (acc.astype(np.int64) * m0 + (1 << (shift - 1))) >> shift
    return np.clip(v + zy, lo, hi).astype(np.int8)

rng = np.random.default_rng(1)
x = rng.integers(-128, 128, 32, dtype=np.int8)
w = rng.integers(-127, 128, (8, 32), dtype=np.int8)
b = rng.integers(-2000, 2000, 8, dtype=np.int32)
zx, zy = -5, 3
m0, shift = quant_mult(0.0015)
acc = b + ((x.astype(np.int32) - zx) * w.astype(np.int32)).sum(axis=1)
y = requant_ref(acc, m0, shift, zy, -128, 127)
# write x, w, b, y and the constants to vectors.h as C arrays

numpy's >> on int64 is an arithmetic shift, matching the C. The C test then calls dense_int8 on the arrays from vectors.h and compares every output with the expected array, printing any mismatch and returning a non-zero exit code. With the random seed above, all eight outputs match; changing the rounding term to zero, for example, makes several fail. Random data is a start, not an end: add vectors at the corners too, such as all inputs at −128 with all weights at −127, and values of acc that land exactly on a rounding half.

Common mistakes:

  • rounding with (acc * M0) >> shift alone, which truncates towards minus infinity and biases outputs down
  • computing the product in 32 bits, which overflows silently
  • clamping to [−128, 127] when the model expects a fused ReLU clamp at zy
  • testing against the float model and accepting "close", which hides rounding mismatches

Try it yourself

  1. Put the C functions and a small main that compares against vectors.h in one file, generate the header with the Python above, and build it with gcc -std=c99 -Wall -O2.
  2. Cross-compile the same file with a RISC-V GCC toolchain and run it under QEMU user mode (qemu-riscv32) to confirm the result does not depend on the host.
  3. Fold the zero point into the bias, regenerate the expected values, and confirm the test still passes.
  4. Count cycles for the inner loop on the target and compare with the number of MACs.
