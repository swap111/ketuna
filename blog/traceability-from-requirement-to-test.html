Traceability from requirement to test: why it saves projects

Systems & product engineering Intermediate 27 Nov 2026 5 min read By Ketuna

Linking every requirement up to a need and down to design items and tests makes gaps and the impact of changes visible. A small Python script shows how to find both.

Late in a project someone asks two questions that sound simple. "Have we tested everything we promised?" and "If we change this requirement, what else has to change?" Without traceability, answering either one means a week of reading documents and asking colleagues what they remember. With it, each answer is a query that takes a minute. Traceability is not paperwork for auditors; it is the index that lets a team see its own project.

What a trace link is

A trace link is a recorded relationship between two items, each with a unique ID. The common chain in a hardware or chip project runs like this:

  • a stakeholder need (what a user or customer wants)
  • is refined into one or more system requirements (testable statements)
  • which are allocated to subsystem requirements (hardware, firmware, RTL)
  • which are realised by design elements (a schematic block, an RTL module, a firmware function)
  • and verified by tests (a bench procedure, a testbench, an analysis report).

Links run in both directions. Looking down from a requirement tells you how it is met and proven. Looking up from a test tells you why it exists.

The two gaps traceability exposes

Once the links exist, two kinds of gap become visible without anyone having to remember them.

Untested requirements. A requirement with no test below it is a promise nobody is checking. On a board this might be a sleep-current limit that everyone assumed someone else would measure. In RTL it might be an error-handling feature with no testbench scenario. Finding it at review time costs an afternoon; finding it in the field costs a recall or a respin.

Orphans. A test or design element with nothing above it is either justified by a missing requirement (write it down) or is unnecessary work (delete it). Orphan features are a quiet source of schedule slip and of bugs, because nobody specified how they should behave.

Impact analysis when things change

Requirements change. A customer raises the operating temperature range, or a regulator adds a limit. The useful question is not "what changed" but "what does this touch". Follow the links down from the changed requirement and you get the list: which subsystem requirements must be revisited, which schematic blocks and RTL modules implement them, and which tests must be rerun or rewritten. Without links, teams update the specification and forget the test, and the old test keeps passing against the old limit. That is how a product passes verification and still fails the new requirement.

A trace matrix in plain text

You do not need a special tool to start. A CSV file with one row per link, kept under version control next to the design, is enough for a small team. Here is a checker that reads requirements, tests and links and reports both gaps.

import csv, io

reqs = {"SR-12", "SR-14", "SR-15", "HW-7", "FW-4", "FW-9"}
tests = {"T-21", "T-22", "T-25", "T-30", "T-41"}
parent = {"HW-7": "SR-12", "FW-4": "SR-12", "FW-9": "SR-15"}

links = io.StringIO("""req,test
HW-7,T-21
FW-4,T-22
SR-12,T-30
SR-14,T-25
""")
verified_by = {}
for row in csv.DictReader(links):
    verified_by.setdefault(row["req"], set()).add(row["test"])

untested = sorted(r for r in reqs if r not in verified_by)
used = set().union(*verified_by.values())
orphans = sorted(tests - used)
print("untested:", untested)
print("orphan tests:", orphans)

# impact of a change to SR-12: children, then every linked test
changed = "SR-12"
children = [c for c, p in parent.items() if p == changed]
affected = set(verified_by.get(changed, set()))
for c in children:
    affected |= verified_by.get(c, set())
print("change", changed, "-> reqs", children, "tests", sorted(affected))

It prints untested: ['FW-9', 'SR-15'], orphan tests: ['T-41'], and for the change it lists HW-7, FW-4 and tests T-21, T-22, T-30. Note that SR-15 counts as untested even though its child FW-9 exists; a parent is only covered when its own test, or every child's test, is present. Decide that rule as a team and write it into the checker.

Keeping it alive

Traceability decays if it is a separate chore. A few habits keep it honest:

  • Create the link when you create the item. A new test file starts with the requirement IDs it covers, as a comment or a tag, so a script can harvest them.
  • Run the checker in continuous integration. A pull request that adds an orphan test or leaves a new requirement untested gets flagged automatically.
  • Report status by requirement, not by test count. "212 tests pass" says little. "41 of 44 requirements verified, 3 pending with owners" says what the project needs to know.
  • Change requirements through a log. Each change records the reason, the impact list from the trace data and who approved it.

Common mistakes

  • Linking at the wrong level. Tying every test to one top-level requirement makes everything look covered. Link to the lowest requirement the test actually proves.
  • Counting a link as a pass. A link says a test exists. Status comes from the latest result of that test on the current design.
  • One giant spreadsheet that only one person edits. It becomes a bottleneck and goes stale. Keep links close to the items, in plain text, and generate the matrix.

Try it yourself

  1. Take five requirements from a past lab or project, give each an ID, and write a CSV linking them to the tests you actually ran.
  2. Run the script above on your data with Python 3 and fix every untested requirement or orphan it reports, either by writing the missing item or by deleting the unnecessary one.
  3. Add a tag such as # covers: SR-12 to the top of your cocotb or C test files and extend the script to collect links by searching those files, so the matrix builds itself.
