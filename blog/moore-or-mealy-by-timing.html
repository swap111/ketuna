Moore or Mealy? Choosing an FSM style by timing, not by textbook

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

A 101 sequence detector written as Moore and as Mealy shows the real difference: when the output appears, whether it can glitch, and how a registered output gives you the best of both.

Textbooks define Moore and Mealy machines by where the output comes from: Moore outputs depend only on the state, Mealy outputs depend on the state and the current inputs. That definition is correct, but it does not tell you which one to choose. In practice the choice is a timing decision: how soon the output must react, and whether it may be driven by combinational logic from an input you do not control.

One problem, two machines

Take a detector that watches a serial bit din, one bit per clock, and raises hit when the last three bits were 1 0 1, allowing overlaps (so 10101 gives two hits).

The Moore version needs a state that means "I have just seen 101", because the output can only depend on the state. It has four states: S0 (nothing useful), S1 (seen 1), S10 (seen 10) and S101 (seen 101, output high).

The Mealy version needs only three states, S0, S1 and S10. When it is in S10 and din is 1, it raises hit immediately, during the same clock cycle, and moves to S1.

module det101_moore (
  input  logic clk, rst_n, din,
  output logic hit
);
  typedef enum logic [1:0] {S0, S1, S10, S101} st_t;
  st_t st, nx;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) st <= S0; else st <= nx;
  always_comb begin
    case (st)
      S0:   nx = din ? S1   : S0;
      S1:   nx = din ? S1   : S10;
      S10:  nx = din ? S101 : S0;
      S101: nx = din ? S1   : S10;
      default: nx = S0;
    endcase
  end
  assign hit = (st == S101);      // state only
endmodule

module det101_mealy (
  input  logic clk, rst_n, din,
  output logic hit
);
  typedef enum logic [1:0] {S0, S1, S10} st_t;
  st_t st, nx;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) st <= S0; else st <= nx;
  always_comb begin
    case (st)
      S0:  nx = din ? S1 : S0;
      S1:  nx = din ? S1 : S10;
      S10: nx = din ? S1 : S0;
      default: nx = S0;
    endcase
  end
  assign hit = (st == S10) && din; // state and input
endmodule

When the output appears

Feed both machines the bits 1, 0, 1, with din changing just after each rising edge. The third bit, the final 1, is present on din during clock cycle 3.

  • The Mealy output goes high during cycle 3, as soon as din becomes 1 while the state is S10. It is valid at the edge that ends cycle 3.
  • The Moore output goes high only after that edge, when the state register becomes S101. It is high during cycle 4.

That one-cycle difference is the whole speed argument for Mealy. If the next block must act on the very cycle the pattern completes, Mealy delivers it. If one cycle of latency is acceptable, the argument disappears.

Glitches and where the path goes

The Mealy output is a combinational function of din. That has two consequences:

  • Glitches. If din comes through logic, or changes near the state transition, hit can pulse briefly at the wrong time. A downstream flip-flop sampling hit on the clock edge will usually not care. A downstream block that uses hit as an asynchronous signal, a clock enable for a gated clock, or an output pin that drives another chip will care a lot.
  • Long combinational paths. The path now runs from wherever din was launched, through the Mealy output logic, into whatever consumes hit. In a bigger design, chaining several Mealy machines can create a long path across module boundaries, or even a combinational loop if two machines feed each other.

A Moore output, by contrast, comes from state flops through a small decoder. Its timing is local and easy to reason about. It can still glitch while the decoder settles, if several state bits change at once, but it does not depend on an input changing mid-cycle.

The registered-output option

The most robust choice for an output that leaves your module is often neither textbook style: compute the Mealy condition and register it.

always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) hit_q <= 1'b0;
  else        hit_q <= (st == S10) && din;

hit_q rises at exactly the same moment as the Moore output, comes straight from a flip-flop so it cannot glitch, and the machine keeps the smaller Mealy state count. For a signal that crosses a module boundary or goes off chip, this is the usual default.

How to choose

Need Choose
Output used in the same cycle by local logic Mealy
Output leaves the module or chip Registered output
Output must never glitch, latency is fine Moore or registered
Fewest states, inputs are clean and registered Mealy

Common mistakes

  • Comparing waveforms without lining up the edges. A Moore output that is "one cycle late" is not a bug; check which edge the consumer samples on before you call it one.
  • Feeding a Mealy output straight into another Mealy machine. The two output functions chain into one long combinational path, and if the second machine's output feeds back to the first you have built a loop.
  • Assuming fewer states means less hardware. The Mealy detector saves a state, but with a 2-bit state register both versions here use two flops. The savings show up in larger machines, and only sometimes.
  • Drawing the state diagram after the code. Draw it first, with the output written on the states (Moore) or on the arrows (Mealy). The drawing makes the timing visible before any simulation does.

Try it yourself

  1. Simulate both modules side by side with Icarus Verilog (iverilog -g2012) on the input 0101011010 and mark every hit on paper before you run it. Count the cycles between each Mealy and Moore pulse.
  2. Synthesise both with Yosys (synth -top det101_mealy, then stat) and compare flip-flop and logic counts.
  3. Add the registered-output version and confirm in GTKWave that hit_q matches the Moore output cycle for cycle.
