Cache coherence in two cores: the problem MESI solves

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

Two cores with private caches can hold different values for one address. Trace a shared counter through the four MESI states on a snooping bus, and see why coherence alone does not make the increment atomic.

Put two cores on one chip, give each a private write-back data cache, and a new problem appears. Core 0 writes a variable; the new value sits in core 0's cache, marked dirty. Core 1 reads the same variable and gets the old value from memory or from its own stale copy. Neither cache is broken, yet the system as a whole is wrong. Coherence protocols keep private caches consistent in hardware, and MESI is the classic one. Tracing it through a shared counter shows both how it works and why multicore performance often hinges on it.

What coherence must guarantee

A system is coherent if, for each memory location, all cores agree on a single order of writes, and every read returns the value of the most recent write in that order. In practice a protocol enforces one rule per cache line: at any moment, either one cache may write the line, or any number of caches may read it, but not both. This is often called single-writer, multiple-reader.

Coherence is about one location at a time. Ordering between different locations is the memory model's job, which is why multicore code still needs fences or ordered atomics.

The four MESI states

Each line in each cache carries one of four states:

  • Modified (M): this cache has the only copy, and it is dirty; memory is stale. This cache may read and write freely.
  • Exclusive (E): this cache has the only copy, and it is clean (matches memory). It may read, and may write by silently switching to M.
  • Shared (S): this cache has a clean copy, and others may too. Reads are free; a write needs permission first.
  • Invalid (I): no valid copy.

In a snooping protocol, all caches share a bus (or a broadcast interconnect) and watch every request. The main request types are a read (BusRd), a read with intent to modify (BusRdX), and an upgrade that only invalidates other copies (BusUpgr), plus write-backs of dirty lines. When a cache sees a request for a line it holds in M, it supplies or writes back the data and downgrades its own copy.

The E state is the refinement over the simpler MSI protocol. Private data is very often loaded and then written. With E, the load brings the line in exclusive (no other cache has it), and the store upgrades to M without any bus traffic.

Tracing a shared counter

Two cores take turns incrementing a counter that starts at 0 in memory, with both caches empty. Each increment is a load followed by a store.

Step Action Bus transaction Core 0 Core 1 Value
1 Core 0 loads BusRd (no other copy) E I 0
2 Core 0 stores none M I 1
3 Core 1 loads BusRd; core 0 supplies data S S 1
4 Core 1 stores BusUpgr; core 0 invalidates I M 2
5 Core 0 loads BusRd; core 1 supplies data S S 2
6 Core 0 stores BusUpgr; core 1 invalidates M I 3

Two observations matter for real designs.

First, after step 2 every increment costs two bus transactions: one to get a readable copy, one to invalidate the other cache before writing. The line "ping-pongs" between the caches. On a large chip each transaction may take many cycles. A counter that every core updates often can become a serious bottleneck, not because the arithmetic is slow but because ownership of one cache line has to keep moving.

Second, the protocol worked. At every step only one cache could write, and every load saw the latest value. That is all coherence promises.

Coherence is not atomicity

Now let both cores increment at the same time, each with a separate load and store:

  1. Core 0 loads the counter (value 5); the line becomes S in both caches after core 1 also loads it (value 5).
  2. Core 0 upgrades and stores 6; core 1's copy is invalidated.
  3. Core 1, which already loaded 5 into a register, upgrades its line (re-fetching it) and stores 6.

Two increments, one lost. Every step was coherent; the problem is that the read-modify-write was not a single indivisible operation. Fixing it needs atomic instructions. In RISC-V, the A extension provides amoadd.w, which performs the load, add and store as one operation while the cache holds the line in M, so no other core can intervene, and the load-reserved / store-conditional pair (lr.w / sc.w), where the store fails and software retries if the line was lost in between:

#include <stdatomic.h>

atomic_int counter;

void increment(void)
{
    /* compiles to amoadd.w on a core with the A extension */
    atomic_fetch_add_explicit(&counter, 1, memory_order_relaxed);
}

Atomics rely on coherence: they work by acquiring the line in an exclusive state and keeping it for the duration of the operation.

False sharing

The ping-pong in the trace happened because both cores wrote the same variable. It also happens when they write different variables that share one cache line:

struct stats {
    int core0_events;   /* written only by core 0 */
    int core1_events;   /* written only by core 1 */
};                      /* 8 bytes: both in one line */

Coherence tracks whole lines, so each core's write invalidates the other's copy, exactly as if they shared one counter, though the program has no logical sharing at all. This is false sharing. The fix is layout: align each per-core field to its own cache line, for example with _Alignas(64) on a 64-byte-line system, at the cost of some memory. Profiling tools that report coherence misses are the usual way to find it.

Snooping versus directories

Snooping is simple and fast for a few cores, because every cache sees every request directly. It does not scale well, since every request is broadcast and every cache must check its tags. Larger systems use a directory: a structure, usually beside the shared cache or memory, that records which caches hold each line, so requests go only to the caches that matter. The states are similar; what changes is how messages find their destination.

Common mistakes

  • Assuming coherence makes read-modify-write safe. Use atomic instructions or locks.
  • Ignoring line granularity. Independent variables in one line still ping-pong.
  • Expecting a shared counter to scale. Use per-core counters, padded to separate lines, and combine them when read.
  • Confusing coherence with ordering. Fences and acquire/release semantics are still needed between different addresses.

Try it yourself

  1. Write a Python simulator of two MESI caches on a snooping bus that prints states and bus transactions for a sequence of (core, load or store, address) operations, and reproduce the table above.
  2. Add false sharing to the simulator by mapping two addresses to the same line, and count the bus transactions with and without padding.
  3. Run a two-thread C program on QEMU with -smp 2 that increments a counter with plain ++ and with atomic_fetch_add, and compare the final counts.
