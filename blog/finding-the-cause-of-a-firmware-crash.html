Finding the cause of a firmware crash from the trap state

Embedded systems Advanced 27 Nov 2026 5 min read By Ketuna

When a RISC-V core traps, three registers say what went wrong and where. Capture them with the stack pointer and return address, then walk the stack back by reading function prologues, as in this real QEMU example.

A crash on a desktop gives you a core dump and a stack trace. A crash on a microcontroller usually gives you a board that stops responding. The information you need is still there for an instant, in a few control registers and on the stack, and a trap handler written with care can capture it. This article shows what to save, how to decode it, and how to walk back up the call chain by hand, using a crash reproduced on QEMU's RISC-V virt machine so every number below is real output.

The three registers that describe a trap

When a RISC-V core takes a trap in machine mode, it records:

  • mcause: why. If the top bit is set, it was an interrupt; otherwise the low bits are an exception code.
  • mepc: where. The address of the instruction that faulted (for interrupts, the instruction that would have run next).
  • mtval: extra detail. For access faults and misaligned accesses it holds the faulting address; for an illegal instruction it may hold the instruction bits or zero, depending on the implementation.

The exception codes you will meet most in firmware:

mcause Meaning Typical firmware cause
1 Instruction access fault Jump through a bad function pointer
2 Illegal instruction Corrupted return address, missing extension
4 / 6 Load / store misaligned Casting a byte buffer to a wider type
5 / 7 Load / store access fault NULL or wild pointer, stack overflow into a guard

If mcause has the interrupt bit set, it is not a crash at all: an interrupt was enabled with no handler for it.

Capture before you do anything else

Two more values matter: the stack pointer sp and the return address ra at the moment of the trap. The first instructions of the handler must save them, before any C code runs and changes them. A handler for fatal traps can afford to clobber two temporary registers:

    .globl trap_vector
    .balign 4
trap_vector:
    la    t6, crash_rec          # t5, t6 are lost: acceptable here
    sw    sp,  0(t6)
    sw    ra,  4(t6)
    csrr  t5, mcause
    sw    t5,  8(t6)
    csrr  t5, mepc
    sw    t5, 12(t6)
    csrr  t5, mtval
    sw    t5, 16(t6)
    la    sp, crash_stack_top    # separate stack: keep the evidence
    call  crash_report
1:  j     1b

The last two lines carry a lesson that is easy to learn the hard way. A first version of this handler reset sp to the top of the normal stack before calling the C reporter. The crashed code was only a few words below that point, so crash_report's own stack frame overwrote the saved return address it was trying to print. A fatal-trap handler needs its own small stack, so the crashed stack stays untouched. In production, crash_report would also copy a few dozen words from the old sp into a RAM section that startup code does not zero, then reset, so the record can be sent home after reboot.

The crash

This deliberately broken program reads a field through a pointer that was never set:

struct sensor { uint32_t id; uint32_t value; };
static struct sensor *active;          /* never set: NULL */

__attribute__((noinline))
uint32_t sensor_value(const struct sensor *s)
{
    return s->value;                   /* load from s + 4 */
}

__attribute__((noinline))
uint32_t poll_sensors(void) { return sensor_value(active) + 1u; }

int main(void) { uart_init(); uart_puts("start\n");
                 return (int)poll_sensors(); }

Built with GCC at -O2 for RV32 with compressed instructions, run on QEMU, the reporter printed:

mcause=0x00000005 mepc=0x8000014a mtval=0x00000004
ra=0x80000156 sp=0x80042210
stack: 0x00000000 0x00000000 0x00000000 0x80000068 ...

Decoding it

What: mcause = 5 is a load access fault. Which address: mtval = 4. An address that small is almost always a NULL pointer plus a field offset; value is at offset 4 in the structure.

Where: turn mepc into a source line with the ELF file that was flashed:

$ riscv64-unknown-elf-addr2line -f -e app.elf 0x8000014a 0x80000156
sensor_value
main.c:8
poll_sensors
main.c:12

The fault is the return s->value; line. ra points into poll_sensors, just after its call to sensor_value, so that is the caller. sensor_value is a leaf function that never saved ra, which is why the register still holds its return address.

Walking further up the stack

To go beyond one level, you need to know where each function saved its caller's return address. GCC does not use frame pointers at -O2 by default, but every function that calls another saves ra in its prologue, and the disassembly shows exactly where:

8000014e <poll_sensors>:
8000014e:  1141   addi  sp,sp,-16
80000150:  4501   li    a0,0
80000152:  c606   sw    ra,12(sp)
80000154:  3fdd   jal   8000014a <sensor_value>
80000156:  40b2   lw    ra,12(sp)

poll_sensors reserved 16 bytes and stored ra at offset 12. The trap happened inside sensor_value, which allocated no stack, so the trapped sp (0x80042210) is poll_sensors's frame. The word at sp + 12 is the fourth word of the stack dump: 0x80000068. addr2line says that is in _start, just after call main.

Notice what is missing: main. The compiler turned return poll_sensors() into a tail call, a plain jump, so main left no frame. Optimised stack walks skip such functions, and you must allow for that when reading them. To continue past poll_sensors, add its frame size (16) to sp and repeat with the caller's prologue.

Doing this by hand for a few levels is practical. For routine use, build with -fno-omit-frame-pointer, which keeps a chain of saved frame pointers that a few lines of code can follow, or keep the ELF file and let GDB unwind a saved memory dump using the debug information.

Pitfalls

  • Decoding with the wrong ELF. Addresses only mean something against the exact build that crashed. Archive every released ELF file next to its binary.
  • Trusting a stack after an overflow. If sp is outside the stack region, the stack itself is the victim; check sp against the linker symbols first.
  • Taking mtval as always meaningful. It is defined per exception type, and some implementations write zero.
  • A handler that itself faults. Keep it to plain stores and a polled UART, on its own stack.

Try it yourself

  1. Reproduce this crash with the Ketuna track D platform files on QEMU, then change the field offset and confirm that mtval follows it.
  2. Call through a function pointer that was never set. On QEMU this gives mcause = 1 with mepc and mtval both 0, so the faulting address tells you nothing; explain why ra is now the only clue to the caller.
  3. Rebuild with -fno-omit-frame-pointer, read the new prologues, and write a loop in crash_report that follows the frame chain.
