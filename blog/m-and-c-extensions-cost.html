The M and C extensions: what multiply and compressed instructions cost in hardware

Computer architecture & RISC-V Intermediate 27 Nov 2026 6 min read By Ketuna

Adding M means choosing a multiplier and divider; adding C means a decompressor and a fetch unit that handles 16-bit alignment. What each costs, what it buys, and how to measure the trade for your product.

In this article

  2. What C adds
  3. What C buys

A RISC-V core can implement just the base integer set, RV32I, and run any program. So why do most microcontroller cores add M (multiply and divide) and C (compressed 16-bit instructions)? Because each one moves work from software into hardware, or bytes out of flash, at a cost in gates. The right answer for a product depends on the workload and the memory budget. This article looks at what each extension asks of the hardware and how to decide with measurements rather than habit.

What M adds

The M extension adds eight instructions: mul (low 32 bits of the product), mulh, mulhu and mulhsu (high 32 bits for signed, unsigned and mixed operands), and div, divu, rem, remu. Without them, the compiler calls library routines that multiply by shifting and adding, and divide by shifting and subtracting, one bit at a time.

The ISA specifies the results, not the speed. That leaves a wide range of implementations:

Multiplier option Latency Relative area Typical use
Iterative, 1 bit per cycle about 32 cycles smallest: an adder and shift registers Area-critical control cores
Iterative, 2 to 4 bits per cycle about 8 to 16 cycles moderate Balanced microcontrollers
Single-cycle or pipelined array 1 to 3 cycles large: tens of adders in a tree Signal processing, ML kernels

The division side is almost always iterative, because a fast divider is expensive and division is rare in most code. A simple restoring or non-restoring divider produces one quotient bit per cycle, so roughly 32 cycles plus setup.

To see what the hardware buys, compare with software. A shift-and-add multiply loop in RV32I runs 32 iterations of roughly four or five instructions (test a bit, conditionally add, shift two registers, decrement and branch), so on the order of 130 to 160 instructions before overheads. Even the smallest 32-cycle iterative multiplier is several times faster, and a single-cycle one is two orders of magnitude faster. Whether that matters depends on how often your code multiplies. A protocol state machine barely does; a filter or a fixed-point control loop does constantly.

Two specification details reduce the hardware further. Division by zero does not trap: div returns all ones and rem returns the dividend, so the divider needs no exception path. And the Zmmul extension provides only the multiply instructions, for designs that want fast multiplication without paying for a divider.

What C adds

The C extension defines 16-bit encodings for the most common instructions, for example c.addi, c.lw, c.sw, c.mv, c.j and c.beqz. Every compressed instruction is an exact equivalent of one 32-bit instruction; it adds no new operations. Its restrictions are what make it fit in 16 bits: many forms reach only the eight "popular" registers x8 to x15 through a 3-bit field, immediates are short, and some forms require the destination to equal a source.

The decoding cost is modest: a decompressor in front of the normal decoder that expands each 16-bit instruction into its 32-bit equivalent. Take c.addi x10, -1. Its encoding is 0x157D: the low two bits 01 select quadrant 1, bits 15 to 13 (000) select c.addi, bits 11 to 7 hold rd = 10, and the 6-bit immediate −1 is split into bit 12 and bits 6 to 2. The decompressor rewrites it as addi x10, x10, -1, which is 0xFFF50513, and the rest of the pipeline never knows the difference.

The larger cost is in fetch. With C, instructions are aligned to 2 bytes, not 4. A 32-bit instruction can start in the upper half of one fetched word and finish in the lower half of the next, so the fetch unit needs a small buffer to stitch halves together, and a branch target can land mid-word. Branch predictors and target buffers must index with bit 1 of the PC as well. In a pipelined core, that fetch logic is often where the real complexity of C lives.

What C buys

The benefit is code size, and therefore flash or instruction memory, which on a small SoC can occupy more area than the core itself. Code that fits in less memory may also need fewer instruction cache lines and fetch cycles. How much smaller depends heavily on the program and the compiler, so do not take a number from anyone else's slide: build your own firmware with and without C and compare.

riscv64-unknown-elf-gcc -Os -march=rv32im  -mabi=ilp32 \
    -o fw_im.elf  main.c drivers.c
riscv64-unknown-elf-gcc -Os -march=rv32imc -mabi=ilp32 \
    -o fw_imc.elf main.c drivers.c
riscv64-unknown-elf-size fw_im.elf fw_imc.elf

The text column gives the code size of each build. Multiply the difference by the cost of the memory it saves and compare that with the area of the decompressor and fetch changes. For a core paired with a large external flash, the saving may not matter; for a core with a few kilobytes of on-chip ROM, it can decide whether the firmware fits.

Deciding for a product

  • Profile first. Count multiplies and divides in the instruction trace of real workloads before choosing a multiplier.
  • Consider Zmmul. If divides are rare, keep them in software and add only a multiplier.
  • Size the multiplier to the loop. A fixed-point control loop at a few kilohertz may be fine with an iterative multiplier; a sensor-fusion filter may not be.
  • Measure C with your own code. Build with and without it, and count the memory you actually save.
  • Budget verification. Each extension adds instructions to test, and C adds fetch corner cases that only appear with particular alignments.

Common mistakes

  • Mismatched -march. Code built with M or C traps as illegal on a core without them.
  • Forgetting multiply latency in timing estimates. A 32-cycle multiplier inside an interrupt handler changes worst-case latency.
  • Testing C only with aligned code. Bugs hide in 32-bit instructions that straddle a fetch word.
  • Expecting division by zero to trap. It returns a defined value; software must check if it cares.

Try it yourself

  1. Compile a small fixed-point filter with -march=rv32i and with -march=rv32im, add -S, and find the library call that replaces mul in the first version.
  2. Run the size comparison above on any firmware you have and record the text difference.
  3. Write a 1-bit-per-cycle iterative multiplier in Verilog, check it against Python products in Icarus Verilog, and compare its Yosys stat cell count with a single-cycle a * b.
