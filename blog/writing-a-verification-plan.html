Writing a verification plan that someone can actually check against

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Turn a specification into numbered plan items, each with a stimulus, a check and a coverage goal, so that anyone can trace a requirement to the test that proves it.

Most first verification plans are a list of test names: test_basic, test_reset, test_random. Nobody can review such a list, because nothing in it says what the design is supposed to do or how you will know it did. A useful plan reads the other way round. It starts from the specification, breaks it into features small enough to check, and says for each one how it will be stimulated, how it will be checked and how you will know it was exercised.

What a plan item contains

A plan item is one checkable statement about the design. Each item should carry five things:

  • An ID, such as F-07, so tests, coverage and bug reports can refer to it
  • A spec reference, the section or line it comes from
  • The behaviour, written as a sentence a reviewer can agree or disagree with
  • The check: an assertion, a scoreboard comparison, or a directed expected value
  • The coverage goal: the condition that must be seen before the item counts as exercised

The last two are separate on purpose. A check tells you the design behaved correctly when the situation arose. Coverage tells you the situation did arise. A scoreboard that never saw a write-while-full cycle has passed nothing about write-while-full, even though it reported zero mismatches.

A worked example: a small synchronous FIFO

Take a spec paragraph for an 8-entry FIFO with wr_en, rd_en, full and empty. Suppose it says: data comes out in the order it went in; a write when full is ignored; a read when empty returns no data and does not change state; full and empty are registered outputs; reset empties the FIFO.

Here is that paragraph turned into plan items.

ID Behaviour Check Coverage goal
F-01 Data leaves in write order Scoreboard queue compare 1000 words passed
F-02 Write when full is dropped Scoreboard: item not queued; count unchanged wr_en && full seen
F-03 Read when empty has no effect Assertion on count and pointers rd_en && empty seen
F-04 Simultaneous read and write keep count Assertion on count wr_en && rd_en at count 0, mid and 8
F-05 full asserts at 8 entries exactly Assertion: full == (count == 8) full rises and falls
F-06 Reset empties the FIFO Directed test after a non-empty state Reset applied with count > 0

Notice what writing the table forced. F-04 needed three bins, because a read and write together at count 0 and at count 8 are the interesting cases: at empty, the read has nothing to return; at full, the write may or may not be accepted depending on whether the design lets the read free a slot in the same cycle. The spec paragraph did not say which. That is a question for the designer, found before a single line of testbench existed.

Keeping it traceable

Traceability means you can walk from a requirement to its evidence and back. In practice that comes down to a few habits:

  1. Put the plan item ID in the test or assertion name: a_F05_full_matches_count, test_F06_reset_mid_fill.
  2. Name coverage bins after items too, so the coverage report can be mapped back without guesswork.
  3. Keep the plan in a plain text format, such as a CSV or a Markdown table, in the same repository as the RTL and testbench. Then a change to the spec, the RTL and the plan can be reviewed in one pull request.
  4. Record status per item, not per test: not started, check written, covered, waived (with reason).

With those habits a short script can produce a sign-off table. The one below reads a plan CSV and a list of hit coverage bins and reports items that are checked but not yet covered.

import csv

def plan_status(plan_csv, hit_bins):
    """Return plan items whose coverage goal has not been hit."""
    open_items = []
    with open(plan_csv, newline="") as f:
        for row in csv.DictReader(f):
            if row["bin"] not in hit_bins:
                open_items.append((row["id"], row["behaviour"]))
    return open_items

hits = {"F01_words", "F02_wr_full", "F05_full_edge"}
for item_id, text in plan_status("fifo_plan.csv", hits):
    print(f"{item_id}: not yet covered - {text}")

What makes an item checkable

A reviewer should be able to read an item and say "yes, that test would catch a bug here". Items fail this test in predictable ways.

  • Too vague. "FIFO works correctly" cannot be checked. Split it until each piece names one condition and one observable outcome.
  • Too implementation-bound. "Pointer wr_ptr increments" ties the plan to one RTL structure. Prefer observable behaviour at the interface, and keep internal checks for assertions owned by the designer.
  • No coverage goal. Without one, a passing random regression proves nothing about rare cases, because you cannot tell whether they happened.
  • No negative cases. Specs describe what should happen; many bugs live in what should not happen. Every "when X, do Y" invites an item for "when X is illegal, do nothing harmful".

Reviewing the plan

A plan is worth most when someone other than its author reads it. Book half an hour with the designer and walk the table row by row. The designer will catch items that misread the spec; you will catch places where the spec and the RTL disagree. Write the answers into the spec, not just the plan, so the next reader benefits.

Draft the first version by hand from the spec. If you then ask an AI assistant to suggest missing items, treat each suggestion as a question to check against the spec, not as a fact about the design. The value of the plan comes from someone understanding the spec well enough to argue about it.

Try it yourself

  1. Pick a block from an open-source project you can read, such as a UART or a timer, and write six to ten plan items in a CSV with columns id, spec_ref, behaviour, check, bin.
  2. Write a cocotb test for two of the items with the item ID in the test name, and run it on Icarus Verilog.
  3. Add a counter in the test for each coverage goal and print which ones were hit; feed that set into the script above.
  4. Ask a classmate to review the CSV without reading your code, and record each question they raise as either a new item or a spec clarification.
