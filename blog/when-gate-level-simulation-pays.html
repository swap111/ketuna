When gate-level simulation is still worth running

Verification Advanced 27 Nov 2026 5 min read By Ketuna

Equivalence checking and static timing cover most of what gate-level simulation once did. What remains: reset and initialisation bugs, X behaviour, constraint mistakes and test or power modes.

In this article

  2. Reset and initialisation
  3. X-optimism and X-pessimism

Gate-level simulation (GLS) is slow, noisy and painful to debug, and the two static methods that replaced most of it are better at what they do. Equivalence checking proves the netlist computes the same functions as the RTL; static timing analysis (STA) proves every path meets setup and hold under the stated constraints. Teams that drop GLS entirely, though, eventually ship a bug that only GLS would have shown. The useful question is not whether to run it, but which narrow set of problems justifies its cost.

What the static methods already cover

It helps to be precise about what you are not trying to find with GLS.

Concern Covered by Why GLS adds little
Netlist logic equals RTL logic Equivalence checking Proven for all inputs, not just simulated ones
Setup and hold on constrained paths STA Exhaustive over paths and corners
Functional correctness of the RTL RTL simulation, formal Far faster at RTL level

If GLS is used to re-run the full functional regression on the netlist, it spends a great deal of compute to re-prove what these methods already established. The value lies where their assumptions break.

Reset and initialisation

Both equivalence checking and STA reason about a design in a known state. Neither tells you whether the design actually reaches a known state from power-up.

RTL simulation is often too kind here. Consider a flop without reset feeding a control decision:

reg       armed;            // no reset: designer assumed "it starts at 0"
reg [7:0] cnt;
always @(posedge clk) begin
  if (!rst_n) cnt <= 8'd0;
  else if (armed) cnt <= cnt + 8'd1;
  if (start) armed <= 1'b1;
end

In RTL, armed starts as X. The if (armed) treats X as false and takes the else path, so cnt stays at 0 and the simulation looks clean. In the netlist, the X on armed drives the enable logic of the counter flops, and the cell models propagate X into cnt itself. GLS shows cnt going X right after reset, and points at a real hazard: on silicon, armed powers up as 0 or 1 unpredictably, and the counter may start running before anyone pressed start.

The same class includes memories read before being written, registers that depend on a reset synchronizer whose release ordering differs from the RTL model, and clock-gating cells whose enable latch has no defined initial value.

X-optimism and X-pessimism

RTL simulation is X-optimistic: if and case collapse an unknown into one definite branch, hiding uncertainty. Gate-level models are closer to the hardware but are often X-pessimistic: a simple mux model with an X select produces X even when both data inputs are equal and real silicon would settle to that value.

That means every X in a GLS run needs classification. Some are real (an unreset flop that influences behaviour); some are artefacts of the cell model. The disciplined approach is to start GLS from reset with all non-reset state at X, trace each X that reaches an important signal back to its source, and record the verdict. Forcing state to zero to make the Xs disappear defeats the purpose.

Timing-annotated runs: checking the constraints

STA proves timing under the constraints you wrote. If a constraint is wrong, STA proves the wrong thing. Typical examples:

  • a path declared false that is actually exercised in some mode
  • a multicycle exception applied to a path whose data does change every cycle
  • an asynchronous reset release treated as untimed, when the release can land near a clock edge
  • a generated clock defined with the wrong relationship to its source

An SDF-annotated simulation applies real cell and wire delays to the netlist. Timing checks in the cell models fire when a flop's setup or hold is violated during the run. If a path you declared false shows violations under a real test, the exception is wrong. Running at the slow and fast corners used for STA gives you the setup and hold extremes respectively.

Timing GLS needs care to be useful. Read the SDF annotation report: an instance that failed to annotate silently runs with zero delay. Expect and suppress violations on the first flop of each synchronizer, which are supposed to see asynchronous data; anything else that violates deserves an explanation.

Modes the RTL never exercised

Some behaviour exists only in the netlist:

  • Test modes. Scan chains, test-mode muxes and on-chip test controllers are inserted after synthesis. Equivalence checking usually ties them off; a short GLS run in each test mode confirms they work and that leaving test mode returns the design to function.
  • Power and clock sequencing. Clock-gating cells, glitch-free clock muxes and level shifters are often instantiated from the library, with behaviour that an RTL model only approximated.
  • Simulation–synthesis mismatches. initial blocks are ignored by synthesis for most ASIC flows; incomplete sensitivity lists in old-style combinational blocks simulate differently from the hardware; casez patterns with unexpected X or Z behave differently. Equivalence checking catches many of these as logic differences, but a short GLS run confirms what the hardware does from reset.

A targeted plan

Keep GLS small and pointed at those risks:

  1. A zero-delay run from power-up with all non-reset state X, through reset and the first few transactions on each interface
  2. One test per test mode, entering and leaving it
  3. SDF runs at the fast and slow corners for a handful of tests that exercise every clock domain and every timing exception
  4. A written classification of every X and every timing-check violation

That is usually a small fraction of the full regression, and it targets exactly the gaps the static methods leave.

Try it yourself

  1. Synthesise the counter above with Yosys against the sky130 standard-cell library and write the netlist with write_verilog.
  2. Simulate the RTL and the netlist with Icarus Verilog using the library's Verilog cell models, with the same testbench and no initialisation of armed; compare when cnt goes X.
  3. Add a reset to armed, rerun both, and confirm the X disappears in the netlist.
  4. Write an SDF file from OpenSTA with write_sdf, check your simulator's SDF support, and run one annotated test at a slow corner.
