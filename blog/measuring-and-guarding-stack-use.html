How big should the stack be? Measuring and guarding stack use

Embedded systems Advanced 27 Nov 2026 6 min read By Ketuna

Stack overflow on a microcontroller corrupts data silently. Combine stack painting, the compiler's per-function stack reports and a guard region that faults on overflow to size stacks with evidence instead of hope.

In this article

  4. Technique 3: make overflow fail loudly

On a microcontroller without memory protection, nothing stops the stack. When it grows past its allotted space it simply writes over whatever is next: .bss variables, the heap, another task's stack. The result is a bug that appears far from its cause, often only under a rare combination of deep calls and a well-timed interrupt. "Make the stack bigger" is the usual cure, and it is a guess. This article shows three complementary techniques that replace the guess with numbers: measure what is used, compute what could be used, and make overflow fail loudly.

Why stack depth is hard to know

The stack use at any moment is the sum of the frames of every function on the current call path, plus whatever interrupt frames are stacked on top. The worst case is therefore:

worst main-stack use ≈ deepest call path + deepest interrupt path × nesting levels

Each term is hard to see. The deepest path may run only in an error handler. Inlining moves locals from one frame to another. A library function you never read may allocate a large buffer. Interrupts nest only when priorities allow, and only occasionally. With an RTOS, every task has its own stack, and depending on the port, interrupts may run on the interrupted task's stack, so each task must reserve room for them.

Technique 1: paint the stack and read the high-water mark

Fill the whole stack with a known pattern at start-up, run the system through its heaviest scenarios, then scan from the far end for the first word that no longer holds the pattern. Everything above that point has been used at least once.

#include <stddef.h>
#include <stdint.h>

extern uint32_t _stack_bottom[], _stack_top[];  /* linker symbols */
#define STACK_PAINT 0xA5A5A5A5u

/* Call early in main(), while little of the stack is in use. */
void stack_paint(void)
{
    uint32_t *sp;
    __asm__ volatile ("mv %0, sp" : "=r"(sp));
    for (uint32_t *p = _stack_bottom; p < sp - 16; p++)
        *p = STACK_PAINT;            /* stop short of the live frames */
}

/* Bytes of stack that have ever been used since painting. */
size_t stack_high_water(void)
{
    const uint32_t *p = _stack_bottom;
    while (p < _stack_top && *p == STACK_PAINT)
        p++;
    return (size_t)((const char *)_stack_top - (const char *)p);
}

The stack grows downward from _stack_top, so unused space is at the bottom. The linker script needs a _stack_bottom = .; line before it reserves the stack. Painting in the startup assembly, before main(), is even cleaner, since then nothing is live yet.

Report the high-water mark over a debug UART or store it where a test can read it. As an illustration: if an 8 KB stack shows a high-water mark of 2,912 bytes after a full test run, about 36 % has been used in the paths you exercised. That last phrase is the weakness. Painting measures; it does not prove. A path your tests never reached, such as a rarely used error branch or an interrupt landing at the deepest point, is not in the number.

Technique 2: let the compiler report every frame

GCC can write each function's frame size to a file. Compile with -fstack-usage and every object gets a .su file:

s.c:3:5:leaf    80      static
s.c:4:5:mid     144     static
s.c:5:5:top     144     static

Each line gives the function, its frame size in bytes and a qualifier. static means a fixed size; dynamic means the frame depends on run-time values, from a variable-length array or alloca, which you should treat as a red flag in firmware; bounded means dynamic with a known maximum. Notice that mid and top are 144 bytes each here, not the sum of their callees: at -O2 GCC inlined the smaller functions, so their locals moved into the callers' frames. Always analyse the build you ship.

Frame sizes alone are not enough; you need the call graph. GCC 10 and later can write it with -fcallgraph-info=su, which produces a .ci file per object listing each function, its frame size and its callees. A short script can then find the most expensive path from each entry point (main, each interrupt handler, each task function). -Wstack-usage=N additionally warns about any single function whose frame exceeds N bytes.

Static analysis gives an upper bound that testing cannot, but it has blind spots: calls through function pointers, recursion, and assembly code. List those by hand and justify each bound, or forbid them in code that runs on small stacks.

Technique 3: make overflow fail loudly

Even with good numbers, guard the boundary so that an overflow stops the system at the moment it happens, instead of corrupting data.

Three ways to build the guard, from cheapest to strongest:

  • Place the stack at the bottom of RAM. Put the stack region below .data and .bss in the linker script, so that it grows down towards the start of RAM. On many parts, an access below the RAM base hits unmapped address space and raises an access fault, so overflow faults instead of overwriting variables. Check what lies below RAM on your chip first.
  • A canary word. Write a known value at the stack's lowest address and check it periodically or at every context switch. It detects overflow after the fact, and misses a frame that jumps over the canary, but it costs almost nothing. Zephyr's CONFIG_STACK_SENTINEL works this way.
  • A hardware guard. On RISC-V, a physical memory protection (PMP) entry can make a small region at the bottom of the stack inaccessible. Note that in machine mode, PMP entries only apply when they are locked, unless the core implements the extension that changes that, so read your core's documentation. Zephyr offers PMP-based guards on RISC-V through CONFIG_PMP_STACK_GUARD. The guard must be larger than the biggest single frame, or a function with a large local array can step over it entirely.

A sizing procedure

  1. Compute the worst path from each entry point with -fstack-usage and the call graph; add interrupt frames for every nesting level your priorities allow.
  2. Paint, run the heaviest tests, and compare the high-water mark with the computed bound. A measurement larger than the bound means the analysis missed something.
  3. Set the stack to the computed bound plus a margin you can justify, and keep a guard in place in every build, including release.

Try it yourself

  1. Compile your firmware with -fstack-usage, sort all .su lines by size, and look at the five largest frames. Explain each one.
  2. Add painting to a program running on QEMU's RISC-V virt machine, call a recursive function with increasing depth, and print the high-water mark after each call.
  3. On the same QEMU machine, align the stack bottom to 64 bytes and make it a locked PMP region with no permissions: write (_stack_bottom >> 2) | 7 to pmpaddr0 and 0x98 (lock bit plus naturally aligned power-of-two mode) to pmpcfg0. Recurse until the stack overflows and check that the trap handler reports mcause = 7, a store access fault, with mtval inside the guard. Give the trap handler its own stack, or it will fault on the guard too.
