Portable Stimulus in plain terms: one test intent, many platforms

Verification Advanced 27 Nov 2026 5 min read By Ketuna

Portable Stimulus describes what a test scenario must achieve as an abstract model, and lets a tool generate concrete tests for block simulation, SoC simulation and silicon. Here is the idea, with a small Python sketch.

In this article

  5. Try it yourself

A system-on-chip is verified on several platforms over its life: block-level simulation with a SystemVerilog or Python testbench, full-chip simulation with firmware running on the embedded processor, FPGA prototypes or emulation, and finally real silicon on a bench. Each platform has its own way of writing tests, so the same scenario, "capture a buffer, process it, send it out over DMA while the processor sleeps", gets rewritten three or four times by different people. Portable Stimulus is an attempt to write the scenario once, as intent, and generate the platform-specific tests from it.

What "test intent" means

A conventional test is a script: do this, then this, then check that. It mixes three things that change at different rates:

  • what the scenario must achieve: data produced by one block must be consumed by another, while some resource is held
  • which legal variations exist: buffer sizes, addresses, which engine is used, what runs in parallel
  • how each step is performed on a given platform: a bus transaction in a testbench, a C function call in firmware, a register poke over a debug link

Portable Stimulus keeps the first two in an abstract model and pushes the third into small per-platform mappings. A tool reads the model, solves the constraints to pick a legal scenario, and emits concrete code for the chosen target.

The Portable Test and Stimulus Standard (PSS) from the Accellera standards organisation defines a language for these models, with a syntax close to SystemVerilog and C++.

The building blocks

A PSS model is built from a few concepts. You do not need the syntax to grasp them.

  • Actions are units of behaviour, such as "capture frame", "filter", "DMA transfer". They have random fields and constraints, like a high-level sequence item.
  • Flow objects connect actions. A buffer is produced by one action and consumed by a later one; a stream has producer and consumer running together; a state object represents persistent system state such as a power mode.
  • Resources model shared hardware, such as DMA channels. An action can lock one exclusively or share it. If there is one channel, two actions that lock it cannot run in parallel.
  • Activities schedule actions inside a larger action: in sequence, in parallel, as a choice, repeated, or in an order the solver picks.
  • Exec blocks map each action to code for a target: a SystemVerilog task call for block simulation, a C function call for firmware.

The most distinctive feature is inference. If you ask for a "DMA out" action that consumes a processed buffer, and nothing in your activity produces one, the tool infers the chain of actions that must happen first, capture then filter, and fills in their parameters consistently. You state the goal; the tool works out a legal path to it.

A sketch of the model, in PSS-style notation:

buffer frame_b { rand int addr; rand int len; }

action capture  { output frame_b out; constraint { out.len in [64..1024]; } }
action filter   { input frame_b in; output frame_b out;
                  lock dma_chan ch; constraint { out.len == in.len; } }
action dma_out  { input frame_b in; lock dma_chan ch; }

action scenario { activity { do dma_out; } }   // capture, filter inferred

A Python sketch of the idea

Commercial tools implement full PSS solving. You can see the principle in a few lines of Python: an abstract scenario, constrained randomisation, and two back ends that render it for different platforms.

import random

def plan_scenario(seed):
    rng = random.Random(seed)
    n = rng.randrange(64, 1025)
    src = rng.choice([0x1000, 0x8000])
    dst = src + 0x4000                     # keep regions apart
    return [("capture", {"addr": src, "len": n}),
            ("filter",  {"src": src, "dst": dst, "len": n}),
            ("dma_out", {"addr": dst, "len": n})]

def render_cocotb(steps):
    return [f"await env.{a}(**{p})" for a, p in steps]

def render_c(steps):
    out = []
    for a, p in steps:
        args = ", ".join(f"0x{v:x}" for v in p.values())
        out.append(f"{a}({args});")
    return out

steps = plan_scenario(seed=7)
print("\n".join(render_cocotb(steps)))
print("\n".join(render_c(steps)))

The same plan becomes testbench calls for a block or subsystem simulation and C calls for firmware on the SoC's processor. Each back end assumes a library of matching functions on its platform: env.capture() driving the block's interfaces in cocotb, and capture() programming registers from C. Those libraries are the per-platform work that Portable Stimulus does not remove; it reduces how often the scenario itself has to be rewritten.

Where it pays off, and where it does not

Portable Stimulus is aimed at SoC-level scenarios with many interacting blocks, shared resources and concurrency, where hand-writing every combination is impractical and the same scenarios must run before and after silicon. Its strengths there:

  • Reuse across platforms. One scenario model serves block, SoC and lab bring-up, so behaviour verified in simulation can be re-checked on silicon with the same intent.
  • Coverage of scenario space. The solver can enumerate or randomise legal combinations of concurrent actions and resource usage, which is hard to do by hand.
  • Consistency by construction. Inference ensures generated tests are legal: every buffer consumed has been produced, every resource conflict is respected.

It does not help much for single-block verification with a rich protocol, where a UVM or cocotb environment with constrained random sequences already does the job well. It also adds a modelling layer that someone must own and debug. When the solver reports a scenario as unsatisfiable, that is useful information, since it means the scenario as written is impossible, but working out whether the model or the design is at fault takes skill.

Open-source tool support for full PSS is limited at the time of writing, so most students meet the ideas through the standard document and small home-made generators like the one above.

Try it yourself

  1. Extend the Python sketch with a second DMA channel as a resource, and generate scenarios where two transfers run in parallel only when they use different channels.
  2. Write a tiny cocotb environment with stub capture, filter and dma_out coroutines that print what they would drive, and run the generated calls on Icarus Verilog against an empty top level.
  3. Write matching C stubs, compile the generated C with GCC, and run it on your host to confirm both back ends execute the same steps with the same parameters.
  4. Add a constraint that cannot be met, such as a length below the minimum, and make the generator report that the scenario is impossible instead of producing a test.
