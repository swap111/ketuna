Running a model with TensorFlow Lite Micro: the interpreter, arena and operators

Edge AI Intermediate 27 Nov 2026 6 min read By Ketuna

What happens between handing TensorFlow Lite Micro a model array and getting scores back - how it reads the model in place, plans memory in the arena, calls kernels, and how to link only the operators you use.

In this article
  1. The model is read in place
  2. Operators and the op resolver
  3. The arena and memory planning
  4. Invoke is a loop over kernels
  5. Reference and optimised kernels
  6. Try it yourself

TensorFlow Lite Micro (TFLM) is an open-source runtime that runs quantized neural networks on microcontrollers with no operating system, no file system and no heap allocation after start-up. The example code is short enough that it is tempting to copy it and move on. But when something goes wrong, such as an allocation failure, a missing operator or a model that silently gives nonsense, you need a picture of what the runtime is doing underneath. This article walks through that picture in the order the calls happen.

The model is read in place

A trained model is converted to a .tflite file, which is a FlatBuffer: a binary format designed so that a program can read fields straight out of the buffer without unpacking or copying it. Inside are a list of tensors (shape, type, quantization scale and zero point), a list of buffers holding the constant data such as weights, and a list of operators in execution order, each naming its input and output tensors and an opcode.

On a microcontroller there is no file to open, so you turn the file into a C array and compile it in:

xxd -i model.tflite > model_data.cc

Mark the array const so the linker places it in flash, and align it as the TFLM examples do. At run time, tflite::GetModel(g_model) does not parse anything; it returns a typed view onto the array. The weights stay in flash for the whole life of the program, and the kernels read them from there.

Operators and the op resolver

Each opcode in the model (for example a 2-D convolution or a fully connected layer) must be matched to a kernel: the C++ code that implements it for the given data types. A kernel is registered as a small set of functions, chiefly one to prepare (check shapes, precompute constants such as requantization multipliers, request scratch memory) and one to invoke (do the arithmetic).

The op resolver is the lookup table from opcode to kernel. The usual choice is a mutable resolver sized for exactly the operators your model uses:

static tflite::MicroMutableOpResolver<4> resolver;
resolver.AddConv2D();
resolver.AddMaxPool2D();
resolver.AddReshape();
resolver.AddFullyConnected();

This is a flash-saving device as much as a lookup table. Only the kernels you register are referenced, so the linker can drop all the others. If you forget one, the program builds fine but allocation fails at start-up and the runtime logs an error naming the operator it could not find. To get the list right the first time, inspect the converted model rather than the training code, because the converter may fuse or insert operators. In Python:

import tensorflow as tf
tf.lite.experimental.Analyzer.analyze(model_path="model.tflite")

The output lists every operator in the graph with its tensors, so you can register exactly that set.

The arena and memory planning

TFLM never calls malloc. You give it one static array, the tensor arena, and everything it needs at run time comes out of that block:

constexpr int kArenaSize = 16 * 1024;
alignas(16) static uint8_t tensor_arena[kArenaSize];

static tflite::MicroInterpreter interpreter(
    tflite::GetModel(g_model), resolver, tensor_arena, kArenaSize);

if (interpreter.AllocateTensors() != kTfLiteOk) {
  // arena too small or an operator missing: check the log
}

AllocateTensors() is where the real set-up work happens, once:

  1. It runs each kernel's prepare step in graph order, which fixes output shapes and records any scratch buffers the kernel asks for.
  2. It works out the lifetime of every intermediate tensor, from the operator that writes it to the last one that reads it.
  3. A memory planner assigns each tensor an offset in the arena so that tensors whose lifetimes do not overlap reuse the same bytes.
  4. Data that must survive between inferences, such as per-tensor bookkeeping and constants the kernels computed in prepare, is placed in its own region of the arena that is not reused.

The planner is why the arena needed is close to the largest set of simultaneously live tensors rather than the sum of all of them. After a successful allocation, interpreter.arena_used_bytes() tells you what was actually used. The practical recipe is to start with a generous arena, read that number on the target build, then shrink the arena to it plus a margin.

Invoke is a loop over kernels

Once allocated, running an inference is simple:

TfLiteTensor* in = interpreter.input(0);
for (int i = 0; i < n; i++) in->data.int8[i] = features[i];

if (interpreter.Invoke() != kTfLiteOk) { /* handle error */ }

TfLiteTensor* out = interpreter.output(0);
int8_t score = out->data.int8[1];

Invoke() walks the operator list in order and calls each kernel's invoke function with pointers into the arena for activations and into flash for weights. There is no scheduling, threading or dynamic decision; the same sequence of kernels runs every time. That makes timing very repeatable, so you can measure it once with a cycle counter around Invoke() and trust the result.

Two details about the input and output tensors trip people up. First, the input is int8 with its own scale and zero point, stored in in->params. Your features must be quantized with exactly those values; copying raw sensor counts in produces wrong answers without any error. Second, the output scores are int8 too. If you only need the top class, compare the int8 values directly, because the dequantization is monotonic. If you need probabilities or a threshold in real units, apply out->params.scale and out->params.zero_point.

Reference and optimised kernels

TFLM ships portable reference kernels written in plain C++. They are easy to read and correct everywhere, but slow, because they make no use of the target's SIMD or DSP instructions. Optimised kernel libraries exist for several processor families and plug in behind the same operator names. The model, the resolver code and the results stay the same; only the speed changes. When you port to a new core, first get the reference kernels running and bit-exact against your Python reference, then switch to optimised kernels and check that the outputs have not changed.

Common mistakes:

  • copying unquantized features into an int8 input tensor
  • registering operators from the training code instead of the converted model
  • sizing the arena by guesswork and never reading arena_used_bytes()
  • placing the model array in RAM by forgetting const, which wastes RAM equal to the model size

Try it yourself

  1. Clone the open-source TFLM repository and build and run the hello_world example's host test with its Makefile, as described in the example's README.
  2. Convert a small model of your own to int8, run the Analyzer on it, and write a resolver with exactly the operators it lists.
  3. Deliberately leave one operator out and read the error log, then put it back.
  4. Print arena_used_bytes() and compare it with a hand estimate of the peak live activation bytes.
