Giving and receiving code review without bruised egos

Careers & skills Intermediate 27 Nov 2026 5 min read By Ketuna

Code review goes well when changes are small, comments are specific, reviewers ask questions instead of issuing verdicts, and authors respond to every point. Practical habits for both sides of a pull request.

In this article

  3. Things to avoid as a reviewer

Every change that reaches main on a well-run team has been read by someone other than its author. That review catches bugs, spreads knowledge of the codebase and keeps style consistent. It also involves one person criticising another person's work, often in short written comments without tone of voice. Handled carelessly, reviews turn into slow, tense exchanges that people avoid. Handled well, they become the place where most engineers learn fastest.

Small changes make good reviews possible

The quality of a review depends first on the size of the change. A reviewer looking at 50 lines can understand every one of them. A reviewer looking at 2,000 lines skims, approves and hopes. Large changes do not get more careful reviews; they get shallower ones.

As an author, keep each pull request to one logical change:

  • Separate refactoring from behaviour. Renaming signals across a module and fixing a bug in it are two pull requests. Mixed together, the fix is invisible in the rename noise.
  • Split big features into steps that each stand alone. For example: add the register interface with tests; then add the datapath behind a parameter; then enable it.
  • Write a description that saves the reviewer time. What changed, why, how you tested it, and where you want particular attention.

A description like this makes the reviewer's job a check, not a puzzle:

Fix FIFO full flag when read and write happen together

When the FIFO was full and rd_en and wr_en were both high, the
write was accepted and the count overflowed. The spec (v0.4, 3.2)
says a simultaneous read and write when full is accepted and the
count stays at DEPTH.

- rtl/sync_fifo.v: compute full from the next count
- tb/test_fifo.py: new test_full_rw_same_cycle (fails before fix)
- Lint clean; cocotb 10 seeds pass

Please check the next-count logic; I am not sure about the
empty case when DEPTH is a power of two.

Writing review comments

A useful comment is specific, explains its reason and leaves room for the author to know something you do not. Three habits help most.

Point at the exact place and the consequence. "This is confusing" gives the author nothing to act on. "On line 42, cnt is 4 bits but compares against DEPTH, which is 16; the comparison is never true" does.

Ask questions instead of issuing verdicts. A question invites an explanation, and sometimes the author has a reason you missed. "What happens here if valid drops in the middle of a burst?" works better than "This breaks on a dropped valid", and if it does break, the author discovers it themselves, which sticks.

Label the weight of each comment. Not every comment is a blocker. A common convention is a short prefix:

Prefix Meaning
blocking: Must change before merge (bug, spec violation, missing test)
suggestion: Better in your view; author decides
nit: Small style point; fine to ignore
question: You want to understand, not necessarily change

Without labels, an author cannot tell whether twenty comments mean "almost ready" or "start again".

Also say what is good. One line such as "the new test is exactly what this needed" is not flattery; it tells the author which habits to keep.

Things to avoid as a reviewer

  • Comments about the person. "You always forget resets" is about the author. "This register has no reset; is that intended?" is about the code.
  • Rewriting the change in your own style. If the code is correct, clear and consistent with the project, your preference for a different structure is a nit at most.
  • Dropping fifty comments at once on a beginner. Pick the important ones; mention patterns once ("several registers lack resets, for example lines 30 and 55") rather than on every line.
  • Sitting on reviews. A pull request waiting three days blocks the author and makes the eventual review feel like an obstacle. Review promptly, even if only to say when you will look properly.

Receiving review

The author's half of the work is just as important. The goal is not to win; it is to merge correct code and learn something.

  • Respond to every comment. Either change the code, or reply explaining why not. Silence leaves the reviewer guessing whether you saw it.
  • Assume good intent. Short written comments read colder than they were meant. Read "why is this here?" as a real question, not an accusation.
  • Separate yourself from the code. A bug found in review is a bug that did not reach silicon or a customer. That is the system working.
  • Ask when you disagree, with evidence. "I kept the blocking assignment because this block is combinational; the lint run is clean. Does that address it?" moves the discussion to facts. If it stays stuck, a short conversation is faster than ten comments.
  • Push fixes as new commits during review. The reviewer can see exactly what changed since their last look. Squash afterwards if your project prefers a clean history.

Common mistakes on both sides

  • Approving without running anything. If the change has tests, check that CI ran them and that a new test would fail without the fix.
  • Treating review as a gate to get past. Authors who argue every point teach reviewers to stop raising points, and quality drops.
  • Never reviewing others. Reviewing is one of the fastest ways to learn a codebase. New engineers can review too; their questions often find unclear code.

Try it yourself

  1. Take a recent change of your own and split it into two pull requests: one pure refactor, one behaviour change. Notice how much easier the second is to read.
  2. Write a pull request description for it using the template above: what, why, how tested, where to look.
  3. Review a classmate's lab repository. Write at least five comments, each with a prefix (blocking, suggestion, nit, question) and at least two in question form. Run their tests locally with Icarus Verilog or cocotb before you approve.
  4. When you receive comments, reply to every one, and push fixes as separate commits so the reviewer can follow them.
