AXI's five channels and why reads and writes are separate

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

Why AXI splits a transaction into five handshaked channels, what the valid/ready rules prevent, how bursts and wrap addresses work, and how many outstanding transactions it takes to hide memory latency.

Simple buses tie a transfer's address, data and response together in one sequence: nothing else happens until the current transfer ends. That is fine for register access and wasteful for memory, where a request may take tens of cycles to answer. AXI takes the opposite approach. It breaks every transaction into independent channels, each with its own flow control, so that requests, data and responses can all be in flight at once. Understanding why the split is drawn where it is, and what rules make it safe, is the key to designing and verifying AXI blocks.

The five channels

A read uses two channels and a write uses three:

  • AR (read address): the manager sends the address, burst length, size, type and an ID.
  • R (read data): the subordinate returns the data beats, each tagged with the ID and a response, with RLAST on the final beat.
  • AW (write address): the manager sends the write's address and burst information.
  • W (write data): the manager sends the data beats with byte strobes (WSTRB), WLAST on the last.
  • B (write response): the subordinate sends one response per write burst, after it has accepted all the data.

Why reads and writes are separate

Reads and writes have opposite data directions. On a shared bus, a long read burst blocks every write behind it, and turning the bus around costs time. With separate channels, a DMA engine can read a source buffer and write a destination buffer at the same time, and a processor's write-back of a dirty cache line does not delay the read that caused the eviction.

Splitting address from data inside each direction matters just as much. A manager can send several addresses before any data returns, so the memory controller sees requests early and can schedule them. The write data channel is even allowed to run ahead of its address: a subordinate must cope with W beats arriving before the matching AW. The separate B channel exists because a write is not complete when the data has been sent; the subordinate confirms it, including errors, only after it has accepted everything.

The valid/ready rules

Every channel uses the same handshake: the source drives VALID with the payload, the destination drives READY, and a transfer happens on a rising clock edge where both are high. Three rules keep the system from deadlocking or corrupting data:

  1. Once VALID is asserted, it stays asserted, with the payload unchanged, until the handshake. The destination may sample whenever it is ready, so the source must not withdraw or change an offer.
  2. The source must not wait for READY before asserting VALID. If both sides waited for the other, nothing would ever move.
  3. The destination may wait for VALID before asserting READY, and may assert READY early if it likes.

Rule 1 is the one most often broken in new RTL, and it is easy to check with an assertion in SystemVerilog:

// AR channel: an offered request must be held until accepted.
property ar_stable;
  @(posedge aclk) disable iff (!aresetn)
    (arvalid && !arready) |=>
      (arvalid && $stable({araddr, arlen, arsize, arburst, arid}));
endproperty
assert property (ar_stable);

The same property, with different signals, belongs on all five channels in every AXI block you verify.

Bursts and their address rules

One address handshake can move many data beats. The burst type decides how the address advances:

  • INCR: the address increases by the beat size each beat. AXI4 allows up to 256 beats.
  • WRAP: the address increases and wraps at a boundary equal to the total burst size. Lengths are 2, 4, 8 or 16 beats. This exists for cache refills, which want the critical word first.
  • FIXED: the address stays the same, for a FIFO-style register.

Work a WRAP burst by hand: 4 beats of 8 bytes starting at 0x1018. The total is 32 bytes, so the wrap boundary is the 32-byte block containing the start, 0x1000 to 0x101F. The beats go to 0x1018, then wrap to 0x1000, 0x1008 and 0x1010. The word the processor missed on arrives first.

A second rule bites in DMA design: a burst must not cross a 4 KB address boundary. An INCR burst of 8 beats of 4 bytes starting at 0x1FF0 would cover 0x1FF0 to 0x200F and is illegal. The manager must split it into a 4-beat burst ending at 0x1FFF and a 4-beat burst starting at 0x2000. The rule lets interconnects decode a burst once, since no burst can wander into the next 4 KB region and a different subordinate.

Outstanding transactions and IDs

Separate channels pay off only if the manager keeps several requests in flight. Little's law gives the number needed: outstanding requests = latency × request rate. Suppose (illustrative numbers) a memory returns the first beat 40 cycles after the request and you want the R channel busy every cycle with 8-beat bursts. One burst occupies the data channel for 8 cycles, so you need 40 / 8 = 5 bursts outstanding. A manager limited to one outstanding read would use the channel only 8 cycles in every 48.

IDs make this manageable. Transactions with the same ID must complete in order; transactions with different IDs may complete out of order, so a fast on-chip SRAM response need not wait behind a slow DRAM one. The cost lands in the interconnect and the manager, which must track every outstanding ID and reorder or route responses correctly.

Failure modes worth testing

  • Combinational VALID that depends on READY. Breaks rule 2 and can deadlock when two such blocks meet.
  • A subordinate that needs AW before accepting W. Legal behaviour, but it deadlocks with a manager that sends all data first and has no buffering.
  • Bursts crossing 4 KB. Common in DMA engines that compute burst lengths from transfer size alone.
  • Lost IDs under back-pressure. Out-of-order responses expose tracking bugs only when several transactions are outstanding.

Try it yourself

  1. Write the stability property above for all five channels and bind it to an open-source AXI subordinate model; simulate with Verilator using --assert (it supports a subset of SystemVerilog assertions, so check the constructs against your version).
  2. Prove the same rules with SymbiYosys on a small AXI-Lite register block. With the open-source Yosys front end, write them as immediate assertions using $past inside an always @(posedge aclk) block.
  3. Write a Python function that splits any (address, length) request into legal INCR bursts with no 4 KB crossing, and test it against random inputs.
