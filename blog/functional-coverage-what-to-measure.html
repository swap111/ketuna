Functional coverage: deciding what to measure before you measure it

Verification Intermediate 27 Nov 2026 6 min read By Ketuna

Build a coverage model from verification plan items into coverpoints, bins and crosses for a small timer, and see why writing that model is really a design review of the specification.

Functional coverage answers a question your checkers cannot: did the situations we care about actually happen during simulation? A scoreboard with zero mismatches only tells you that whatever happened was correct. If the interesting case never occurred, it was never checked. The hard part of coverage is not the syntax of a covergroup. It is deciding, before you run anything, which situations deserve to be counted.

Start from the plan, not from the signals

A common first attempt is to point a coverpoint at every input and let the tool create automatic bins. On a 32-bit data bus that produces a large number of bins, almost none of which mean anything, and coverage never closes. Worse, it measures the stimulus generator rather than the design's behaviour.

Coverage should be derived from the verification plan. Each plan item that says "the design must handle situation X" gets at least one bin that is hit only when X happens. If a bin cannot be traced to a plan item, ask why it exists. If a plan item has no bin, ask how you will know it was exercised.

A worked example: a down-counting timer

Take a small timer peripheral with these spec lines (a simplified version of a typical bus timer):

  • CTRL has enable, irq_en and auto_reload bits
  • Writing LOAD sets the reload value and restarts the count
  • When the count reaches zero, STATUS.pending is set; software clears it by writing 1
  • With auto_reload, the timer reloads from LOAD; without it, the timer stops
  • If a clear and a new zero event land on the same cycle, the event wins

Here are the plan items and the coverage they imply.

Plan item What must be seen Coverage construct
Reload values LOAD = 0, 1, mid-range, maximum Coverpoint on LOAD with four bins
Both modes reach zero Zero event with auto_reload 0 and 1 Coverpoint on mode, sampled at zero
Clear/event collision Clear write and zero event on one cycle Single bin on a combined condition
Mode × reload Each mode with each LOAD class Cross of the two coverpoints
Interrupt gating Zero event with irq_en 0 and 1 Coverpoint on irq_en at zero

Writing this table already raised two questions the spec did not answer. What does LOAD = 0 mean with auto_reload set: an event every cycle, or no events at all? And what happens if software writes LOAD on the same cycle the count reaches zero: does the old event still fire? Those are not coverage questions. They are specification holes, and the coverage model found them because it forced someone to list the cases that matter. That is why a coverage model is best treated as a review of the spec, done with the designer in the room.

The covergroup

Here is that model in SystemVerilog, sampled by the monitor once per zero event rather than every clock. Sampling only on meaningful events keeps idle cycles from inflating the numbers.

covergroup cg_timer_zero with function sample(
    bit [15:0] load, bit auto_rl, bit irq_en, bit clr_same_cycle);
  cp_load : coverpoint load {
    bins zero = {0};
    bins one  = {1};
    bins mid  = {[2:16'hFFFE]};
    bins max  = {16'hFFFF};
  }
  cp_mode : coverpoint auto_rl { bins one_shot = {0}; bins reload = {1}; }
  cp_irq  : coverpoint irq_en  { bins masked = {0}; bins enabled = {1}; }
  cp_clr  : coverpoint clr_same_cycle { bins collision = {1}; }
  x_mode_load : cross cp_mode, cp_load;
endgroup

A few choices are worth explaining:

  • Explicit bins for boundaries. zero, one and max are separate because counters break at their edges. The whole middle range is one bin because the logic treats every mid value the same way.
  • cp_clr has only the interesting bin. We do not need to count the common case where no collision happened; it will occur constantly.
  • The cross is deliberate. Mode and reload value interact in the spec (reload uses LOAD), so their combinations matter. irq_en gates only the output, so crossing it with LOAD would add bins without adding meaning.

The cross has 2 × 4 = 8 bins. Add the four cp_load bins, two mode bins, two interrupt bins and one collision bin, and the whole model is a handful of targets you can read in one screen. That readability is part of the point: a reviewer can check the model against the plan.

Illegal and ignored combinations

Some combinations should never occur, and some do not matter. Mark them explicitly rather than leaving them as permanent holes.

  • illegal_bins flags a combination the spec forbids. If it is ever hit, the simulation reports an error, so it doubles as a lightweight check.
  • ignore_bins removes combinations that are legal but uninteresting, so they do not drag the percentage down.

Each one deserves a comment that cites the spec line justifying it. A reviewer should never have to guess why a bin was ignored.

The same model in Python

If your testbench is in cocotb, a coverage model can be a dictionary of bin names to hit counts. The logic is the same: a sample() function called on each event, and a report of bins with zero hits.

from collections import Counter
from itertools import product

hits = Counter()

def load_class(v):
    return {0: "zero", 1: "one", 0xFFFF: "max"}.get(v, "mid")

def sample(load, auto_rl, irq_en, clr_same_cycle):
    lc = load_class(load)
    mode = "reload" if auto_rl else "one_shot"
    hits[f"load.{lc}"] += 1
    hits[f"cross.{mode}.{lc}"] += 1
    hits[f"irq.{irq_en}"] += 1
    if clr_same_cycle:
        hits["collision"] += 1

def holes():
    wanted = [f"cross.{m}.{l}" for m, l in
              product(["one_shot", "reload"], ["zero", "one", "mid", "max"])]
    wanted += ["irq.0", "irq.1", "collision"]
    return [b for b in wanted if hits[b] == 0]

Pitfalls

  • Coverage without checking. A bin being hit means nothing if no checker was watching. Make sure every plan item has both.
  • Not merging across seeds. Each random run alone looks low. Merge the results before deciding which holes are real.
  • Treating 100% as done. It means the model is satisfied, not that the model is complete. Review the model against the plan as carefully as the RTL.

Try it yourself

  1. Write the timer spec above as a one-page plan with item IDs, and give each item a bin name before writing any RTL or testbench.
  2. Implement the Python coverage model in a cocotb testbench for a simple timer of your own on Icarus Verilog, calling sample() from the monitor on every zero event.
  3. Run random tests with five seeds, merge the hit counts, and list the holes; decide for each whether to add a constraint, a directed test or a reasoned waiver.
  4. Take the two spec questions raised above to a classmate acting as designer, and record the answers in the spec.
