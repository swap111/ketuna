Debouncing a push button in RTL, and why a counter beats a delay chain

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

A mechanical button bounces for milliseconds when pressed. Learn why you synchronize the input first, how a small counter-based debouncer filters the bounce, and how to size the counter.

Your first FPGA project counts button presses on an LED display. You press once and the count jumps by three, or seven, or one, depending on the press. The logic is fine. The button is the problem: a mechanical contact does not close cleanly, it bounces. Filtering that bounce is a small design problem that teaches two habits you will use for the rest of your career: synchronize every asynchronous input, and use time measured by a counter rather than by gate delays.

What bounce looks like

Inside a push button, a metal contact springs onto another. On impact it rebounds, touches again, rebounds again, and settles after a short time. On an oscilloscope, a single press shows a burst of pulses before the line settles, and a release often does the same. How long the bouncing lasts depends on the switch type, its age and how it is pressed; it is commonly in the range of a few milliseconds. If you do not have a datasheet figure for your button, measure it with an oscilloscope or a logic analyser and design with margin.

A digital circuit clocked at tens of megahertz samples the button tens of thousands of times during that burst. Every bounce looks like a separate press.

Step one: synchronize

The button is an asynchronous input. It can change at any moment relative to your clock, so the first flop that samples it can go metastable. Before doing anything else with it, pass it through a two-flop synchronizer.

This is not optional just because the debouncer will "filter it anyway". A metastable value fed to the debouncer's comparison and counter logic can make different flops in that logic see different values on the same edge, which can corrupt the counter state. The synchronizer ensures the debouncer sees a clean, single-valued signal every cycle, even if it bounces.

Step two: a counter-based debouncer

The idea is simple: accept a new button level only after the synchronized input has held that level, without a single change, for a fixed time T. Any bounce restarts the timer.

module debounce #(
  parameter CLK_HZ = 50_000_000,
  parameter T_MS   = 10
) (
  input  wire clk,
  input  wire rst_n,
  input  wire btn_async,     // raw pin
  output reg  btn_clean,     // debounced level
  output wire press          // one-cycle pulse on each press
);
  localparam integer N = CLK_HZ / 1000 * T_MS;  // cycles to wait
  localparam integer W = $clog2(N + 1);

  reg       s1, s2;          // two-flop synchronizer
  reg [W-1:0] cnt;
  reg       btn_prev;

  always @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      s1 <= 1'b0; s2 <= 1'b0;
      cnt <= 0; btn_clean <= 1'b0; btn_prev <= 1'b0;
    end else begin
      s1 <= btn_async;
      s2 <= s1;
      if (s2 == btn_clean)
        cnt <= 0;                  // input agrees: nothing pending
      else if (cnt == N - 1) begin
        btn_clean <= s2;           // stable for N cycles: accept
        cnt <= 0;
      end else
        cnt <= cnt + 1'b1;         // disagreeing: keep timing
      btn_prev <= btn_clean;
    end

  assign press = btn_clean & ~btn_prev;
endmodule

Whenever the synchronized input s2 matches the current output, the counter is held at zero. When it differs, the counter runs. If the input bounces back before the count completes, the counter resets on that cycle. Only an input that differs continuously for N cycles changes the output.

The press output is an edge detector on the clean level: one clock-cycle pulse per real press, which is what a counter or a state machine downstream usually wants.

Sizing the counter

Choose T longer than the worst bounce you expect and shorter than a human would notice as lag; values around 10 ms are a common starting point, but base your choice on measurement. With a 50 MHz clock and T = 10 ms:

N = 50,000,000 × 0.010 = 500,000 cycles

A 19-bit counter covers it, since 219 = 524,288. The parameters compute this automatically, so the same module works on a board with a different clock. A 19-bit counter and a comparator are a few dozen cells: tiny.

If you have many buttons, you can share a single prescaler that produces a tick every millisecond, and give each button a small counter that advances on ticks. That trades a little timing precision for much less area per button.

Why not a delay chain

A tempting alternative is to "wait until the signal settles" with a chain of buffers, or by sampling the input through a long shift register clocked directly by the system clock and requiring all bits to agree.

  • A buffer chain delays by gate delays, which are nanoseconds and vary with process, voltage and temperature. Reaching milliseconds would take an absurd number of cells, and synthesis tools treat pure buffer chains as removable logic unless you force them to keep it. The delay would not be predictable anyway.
  • A shift register on the fast clock needs one flop per clock cycle of filter time: 500,000 flops for 10 ms at 50 MHz. Even with a slow sampling clock, it costs a flop per sample, while a counter needs only log2 of that many.

A counter measures time in clock cycles, which are exact and set by a crystal. It scales logarithmically with the filter time, and it is described entirely in synchronous logic that every tool understands. That combination is why counters are the default way to measure any interval longer than a few cycles in RTL.

Common mistakes

  • Debouncing the raw input without a synchronizer in front
  • Detecting edges on the raw or synchronized input instead of on the debounced level
  • Picking T without measuring the switch, or with no margin
  • Using a separate slow clock for the debouncer, creating an unnecessary clock domain crossing
  • Simulating with the real 10 ms timing, which makes tests extremely slow; override T_MS or CLK_HZ in the testbench

Try it yourself

  1. Write a testbench in Icarus Verilog that generates a bouncy press as a burst of random-width pulses before settling, and instantiate debounce with CLK_HZ = 1_000_000 and T_MS = 1 so the simulation runs quickly. Check that press fires exactly once per press.
  2. Count the flip-flops after synthesis with Yosys (synth -top debounce, then stat) and compare with the number a shift-register filter of the same duration would need.
  3. If you have a board, wire the button to a counter and an LED display, try it with and without the debouncer, and capture the raw bounce on an oscilloscope or a low-cost logic analyser with open-source capture software.
