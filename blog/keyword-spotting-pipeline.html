A keyword-spotting pipeline from microphone to decision

Edge AI Intermediate 27 Nov 2026 5 min read By Ketuna

How an always-listening device turns a microphone stream into a yes or no - framing audio, computing features incrementally, running a small convolutional network on a sliding window, and smoothing decisions over time.

A keyword spotter listens all the time and must answer one question many times a second: was the wake word just spoken? The neural network is the part everyone talks about, but it is one stage in a pipeline, and most field failures come from the stages around it: frames that do not line up with training, features computed slightly differently on the device, or a decision rule that fires on a single noisy window. This article follows the audio from the microphone to the decision and explains what each stage must get right.

The pipeline at a glance

The rates in the figure are a common choice for this task and are used throughout as an example: 16 kHz sampling, a feature frame every 20 ms, a 1 s window of frames for the network, and an inference every 200 ms.

Capturing and framing the audio

A digital microphone or an ADC delivers samples continuously, and DMA moves them into a buffer in RAM without the processor touching each sample. Using two halves of the buffer (ping-pong) lets the processor work on one half while DMA fills the other; an interrupt marks each half as ready.

The processor then cuts the stream into short, overlapping frames. Speech changes over tens of milliseconds, so a frame of 30 ms (480 samples at 16 kHz) is short enough to treat the sound as steady, and a hop of 20 ms (320 samples) gives overlap so that no sound falls into a gap. Over one second, the number of complete frames is (16,000 − 480) / 320 + 1, rounded down: 49 frames.

Each frame becomes a small vector of features, typically 10 to 40 numbers describing how energy is spread over frequency. How those features are computed is a topic of its own (see audio features for edge AI). For the pipeline, two points matter: features are computed incrementally, one new frame every 20 ms, rather than recomputing the whole second; and the device code must reproduce the training code's features exactly, down to window shape, scaling and quantization.

A sliding window into a small network

The network sees a 49 × 10 grid: 49 frames of 10 features. Treated as a one-channel image, it is a natural fit for a small convolutional network: a couple of convolution layers find local patterns in time and frequency, pooling shrinks the grid, and one or two dense layers map the result to class scores. Typical outputs are the keyword, silence and unknown (any other speech or noise). The unknown class matters: without it, the model only knows how to say "keyword" or "silence", and everyday speech gets forced into one of them.

The feature grid is kept as a circular buffer of the last 49 frames. Every 200 ms, ten new frames have arrived; the oldest ten are dropped and the network runs on the updated grid. A spoken word therefore appears in several overlapping windows, shifted a little each time. That is deliberate, and the next stage relies on it.

Timing has to fit. If one inference takes, say, 30 ms on the processor, running every 200 ms keeps it busy 15 % of the time, leaving room for features and sleep. Measure it on the target with a cycle counter rather than assuming.

Smoothing decisions over time

A single window can produce a high keyword score by accident: a door slam, a word that sounds similar, a cut-off syllable. Acting on every raw output gives frequent false triggers. Because a real keyword appears in several consecutive windows, you can demand agreement over time:

from collections import deque
import numpy as np

class Detector:
    def __init__(self, n_avg=4, threshold=0.8, refractory=5):
        self.hist = deque(maxlen=n_avg)   # last n_avg score vectors
        self.threshold = threshold
        self.refractory = refractory      # inferences to ignore after a hit
        self.hold = 0

    def update(self, probs):              # probs: scores for one window
        self.hist.append(np.asarray(probs, dtype=float))
        if self.hold > 0:
            self.hold -= 1
            return None
        avg = np.mean(self.hist, axis=0)
        k = int(np.argmax(avg))
        if k >= 2 and avg[k] >= self.threshold:  # 0 silence, 1 unknown
            self.hold = self.refractory
            self.hist.clear()
            return k                       # index of the keyword heard
        return None

Averaging the last four windows (800 ms) suppresses one-off spikes. The threshold trades misses against false triggers. The refractory period stops one utterance from firing several times as it slides through successive windows. The same logic ports to C in a few lines using int8 scores directly, since averaging and comparing do not need real-valued probabilities.

Measuring what matters

Accuracy on a test set of one-second clips is a starting point, not the product metric. An always-listening device is judged on two numbers measured on long, realistic recordings: how often it misses the keyword when spoken (false rejects), and how often it fires when nobody said it (false accepts, usually counted per hour of background audio). Tune the threshold and averaging length on a validation recording, then report both numbers on a separate test recording.

Common mistakes:

  • training on clips that are perfectly centred on the word, when the device sees it at every offset
  • leaving out an unknown class, so ordinary speech triggers the keyword
  • computing features in floating point during training and in a different fixed-point form on the device without comparing them
  • tuning the threshold on the same recordings used to report results

Try it yourself

  1. Record a few minutes of your own voice and background noise at 16 kHz, cut it into 30 ms frames with a 20 ms hop in numpy, and confirm you get 49 frames per second of audio.
  2. Train a small CNN on a public speech-commands dataset in PyTorch, using the same framing.
  3. Run the trained model over a long recording window by window, feed the scores through the Detector, and count false accepts per hour for a few thresholds.
  4. Quantize the model to int8 and check that the detections on the long recording barely change.
