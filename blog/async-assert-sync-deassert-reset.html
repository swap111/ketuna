Synchronous vs asynchronous reset, and why "assert async, release sync" wins

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

Entering reset is easy; leaving it is a timing event. See why asynchronous reset release can break a design, and how a two-flop reset synchronizer makes it safe.

Reset looks like the least interesting signal in a design: hold it low, everything goes to zero, release it, the chip starts. Most reset bugs live in that last word. Releasing reset is a change of state that happens relative to a running clock, and like any other signal it can arrive in the wrong place in the clock cycle. "Assert asynchronously, de-assert synchronously" is the standard answer, and the reason is worth understanding properly.

Two kinds of reset

Synchronous reset is just another data input. The flop only looks at it on a clock edge:

always_ff @(posedge clk)
  if (!rst_n) q <= '0;
  else        q <= d;

The reset is a mux in front of D. It is timed like any other path, it cannot cause a glitch on the flop, and it filters short pulses on the reset line. But it needs a running clock to take effect, and the extra mux sits in the data path.

Asynchronous reset uses a flop with a dedicated reset pin that acts immediately:

always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) q <= '0;
  else        q <= d;

The flop resets the moment rst_n goes low, clock or no clock. That matters at power-up, when clocks may not be stable yet, and for putting outputs into a safe state before anything else happens. The data path stays clean.

Why release is the dangerous part

Asynchronous assertion is harmless: every flop goes to its reset value, whatever the clock is doing. Release is different. The reset pin of a flop has its own timing requirements, called recovery and removal, which are the reset pin's equivalent of setup and hold:

  • Recovery time: reset must be released at least this long before the clock edge, for the flop to leave reset on that edge.
  • Removal time: reset must stay asserted at least this long after the edge, for the flop to stay in reset on that edge.

If the external reset is released inside that window, the flop may leave reset on this edge, on the next one, or go metastable. In a design with thousands of flops spread across the chip, the reset net reaches each one at a slightly different time. Some flops come out of reset one cycle earlier than others.

Picture a state machine whose state register is one-hot with IDLE = 0001 as its reset value. If bit 0 leaves reset a cycle late while the other bits start running, the machine can see 0000 for one cycle and never recover. Or a counter starts counting one cycle before the logic that reads it. These bugs depend on exact release timing, so they appear on some boards or some power-ups and not others.

The reset synchronizer

The fix keeps async assertion and makes release synchronous to the clock that the flops use:

module reset_sync (
  input  logic clk,
  input  logic rst_n_async,   // from pin or reset controller
  output logic rst_n_sync     // to the flops in this domain
);
  logic meta_q;
  always_ff @(posedge clk or negedge rst_n_async)
    if (!rst_n_async) begin
      meta_q     <= 1'b0;
      rst_n_sync <= 1'b0;
    end else begin
      meta_q     <= 1'b1;     // a constant 1 shifts in
      rst_n_sync <= meta_q;
    end
endmodule

Walk through it:

  1. When rst_n_async goes low, both flops clear immediately. rst_n_sync goes low at once, without waiting for a clock. Assertion stays asynchronous.
  2. When rst_n_async goes high, a constant 1 is shifted in. The first flop might see the release inside its recovery window and go metastable, exactly like the first flop of a data synchronizer.
  3. The second flop gives it one full clock period to resolve. rst_n_sync therefore rises cleanly, just after a clock edge, one or two cycles after the external release.

Now every flop in the domain sees its reset released by a signal that was launched from a flop on a clock edge. That release is an ordinary timed path, and static timing analysis checks recovery and removal on every flop, just as it checks setup and hold on data paths.

Practical rules that follow

  • One reset synchronizer per clock domain. A reset synchronized to one clock is asynchronous to every other clock.
  • The synchronized reset is a high-fanout net. It reaches every flop in the domain, so it is buffered as a tree during physical design, and its timing must close like any other path. If it cannot close in one cycle at your clock speed, the reset tree may need pipelining, which adds cycles of latency.
  • Order the release where it matters. If block B must not start before block A, release A's reset first, or let A tell B it is ready.
  • Filter glitches on the async input. A short noise pulse on an external reset pin will asynchronously reset part of the chip. Board-level filtering, or a reset controller that requires the input to be low for a minimum time, is common.
  • Not every flop needs reset. Datapath registers whose contents are overwritten before use often do not need one. Leaving reset off saves area and routing, but control flops (state machines, valid bits, counters) almost always need it.

Common mistakes

  • Using the raw external reset directly as the asynchronous reset of every flop, with no synchronizer on release
  • Sharing one synchronized reset across two unrelated clocks
  • Putting logic between the two synchronizer flops, or using the first flop's output anywhere
  • Mixing reset polarities without a clear naming convention (rst_n for active-low)
  • Assuming simulation proves reset works: zero-delay RTL simulation releases all flops on the same delta, so it cannot show uneven release

Try it yourself

  1. Simulate reset_sync in Icarus Verilog and release rst_n_async at a random time between clock edges. Confirm in GTKWave that rst_n_sync drops instantly and rises only on a clock edge, one to two cycles later.
  2. Synthesise it with Yosys against a sky130 standard-cell library and check that it maps to flops with an asynchronous reset pin.
  3. In OpenSTA, load the netlist, create a clock, and run report_checks on the paths ending at the reset pins of downstream flops to see recovery and removal checks reported.
