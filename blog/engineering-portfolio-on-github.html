Building an engineering portfolio on GitHub that reviewers will read

Careers & skills Beginner 27 Nov 2026 5 min read By Ketuna

A reviewer gives your profile a few minutes. Show fewer, finished projects, each with a clear README, tests that pass, checked results and an honest note on which parts you did yourself.

In this article
  1. What a reviewer actually looks at
  2. Fewer, finished projects
  3. Evidence over claims
  4. An honest note on what you did

When you list a GitHub link on an application, someone opens it, usually for a few minutes, between other tasks. In that time they want to answer one question: can this person build something real and show that it works? A profile with twenty half-started repositories answers that question badly. Three finished projects with evidence answer it well. This article is about choosing, finishing and presenting those few projects.

What a reviewer actually looks at

Put yourself in the reviewer's chair. They open your profile and look at the pinned repositories first, because that is what the page shows at the top. They click one, read the top of the README, glance at the folder structure, maybe open one source file and one test. If something looks interesting, they check the commit history to see whether the work was done steadily or pasted in one go.

So the reviewer judges:

  • Finish. Does the project do what its README says, end to end?
  • Evidence. Are there tests, results, waveforms, timing reports or measurements that show it works?
  • Clarity. Can they understand what it is in under two minutes?
  • Honesty. Is it clear what you built and what came from a tutorial, a template, a teammate or an AI tool?
  • Habits. Small, well-described commits, no build junk, code a colleague could maintain.

Notice what is missing: the number of repositories, the green contribution squares and the list of languages. Volume is not evidence.

Fewer, finished projects

Pick two to four projects and finish them properly. "Finished" does not mean large. A synchronous FIFO with a scoreboard testbench, formal properties and a synthesis report is finished. A RISC-V core that boots halfway is not.

A useful mix for a core electronics role:

Project type What it shows Example
A design with verification You can build and prove a block FIFO or UART with self-checking tests and coverage
A flow project You can take a design through tools Small block through Yosys and OpenROAD to a layout with clean DRC
A firmware project You can work close to hardware Interrupt-driven driver tested on QEMU or Renode
A tool or script You can automate Python parser that summarises a regression log

Choose projects that point at the role you want. A physical design applicant gains more from one clean layout with a timing report than from a web app.

Archive or make private the experiments you will not finish. Unpinned repositories still exist, but a tidy profile tells the reviewer where to look.

Evidence over claims

A README that says "fully verified" is a claim. A test log that says 2,000 random transactions passed on 10 seeds with every FIFO state reached is evidence. Wherever you can, replace an adjective with something the reviewer can check:

  • a make test (or similar) command that runs the tests, and the output it prints
  • a coverage summary, a synthesis cell count or a timing slack, with the tool and settings named
  • a waveform image of one normal transaction, labelled
  • continuous integration that runs the tests on every push, so the badge or the run history shows they still pass

Also show the limits. "Not tested with back-to-back reads across a clock-domain crossing" is a sign of maturity, not weakness. Reviewers trust a project more when it says where it stops.

An honest note on what you did

Many portfolio projects start from a course lab, a template, a teammate's code or AI-generated drafts. That is normal and not a problem. Hiding it is. A reviewer who later finds that the clever part came from elsewhere will distrust everything else.

Add a short section near the end of each README, for example:

## What I did
- Wrote the RTL for the FIFO and the scoreboard testbench
- Started from the course Makefile; added the coverage target
- Used an AI assistant to draft the cocotb test skeleton; reviewed
  and rewrote the checker (see AI_LOG.md)
- The UART receiver in rtl/uart_rx.v is from a classmate, with credit

This section protects you in interviews too. When someone asks "walk me through your scoreboard", you are talking about work you actually did, and you can go as deep as they like.

Common mistakes

  • Forked repositories pinned as your own work. A fork with no commits of yours shows nothing. Pin only what you changed meaningfully.
  • Build outputs committed. Waveform dumps, simulation folders and layout run directories bloat the repository and hide the source. Use a .gitignore.
  • One giant commit. "Initial commit" with 4,000 lines looks pasted. Commit as you work, with messages that explain why.
  • Broken instructions. If the run command fails on a clean clone, the reviewer stops there. Test it.
  • Coursework copied word for word. If many students submit the same lab, yours does not stand out. Extend it: add a feature, a formal proof or a better test.

Try it yourself

  1. Pick your best two projects. Clone each one into a fresh folder and follow your own README exactly. Fix everything that breaks.
  2. Add one piece of checkable evidence to each: a test command with its output, a coverage summary or a timing report, with the tool named (Icarus Verilog, Verilator, cocotb, Yosys or OpenSTA).
  3. Add a "What I did" section with honest credit, and a .gitignore that keeps build outputs out.
  4. Ask a classmate to open your profile cold and tell you, after two minutes, what you built and how you showed it works. If their answer is vague, your top README needs work.
