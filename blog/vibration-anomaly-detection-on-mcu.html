Detecting machine anomalies from vibration on a microcontroller

Edge AI Intermediate 27 Nov 2026 6 min read By Ketuna

Spectral band energies, a baseline learned from normal running and a simple distance score catch many machine faults on a microcontroller. Build that first, then decide whether a neural network adds anything.

A motor, pump or fan that is starting to fail usually tells you through its vibration before it stops: a bearing develops a new frequency, an imbalance grows the component at running speed, a loose mount raises the overall level. A small accelerometer and a microcontroller on the machine can watch for these changes continuously. The difficulty is that you rarely have recordings of faults to train on, because machines do not fail on request. So the practical question is not "which fault is this?" but "is this different from normal?", and that question has simple, explainable answers that should be tried before any neural network.

Features that describe a vibration

Raw accelerometer samples change constantly even on a healthy machine, so you compare features computed over a frame of samples. Take, as an illustrative setup, an accelerometer sampled at 3,200 Hz and frames of 1,024 samples, about 0.32 s each.

  • RMS (root mean square) of the frame measures overall vibration energy. Rising RMS is the oldest warning sign there is.
  • Spectral band energies. Window the frame, take an FFT and add up the power in a handful of frequency bands. With these numbers each FFT bin is 3,200 / 1,024 = 3.125 Hz wide. Bands might separate the running speed (a machine at 1,500 rpm turns at 25 Hz) and its first harmonics from higher bands where bearing and gear defects tend to show up.
  • Shape statistics such as crest factor (peak divided by RMS) or kurtosis respond to short impacts, which early bearing damage produces, even when RMS barely moves.

Taking the logarithm of band energies keeps them on a comparable scale, since vibration power varies over a wide range.

A baseline of normal behaviour

Record the machine while it is known to be healthy, over the conditions it normally sees: different loads, speeds, temperatures, times of day. Compute the features for every frame and store, for each feature, its mean μ and standard deviation σ. That is the baseline, and on a microcontroller it is a few dozen numbers.

For a new frame, express each feature as a z-score, how many standard deviations it is from normal: z = (x − μ) / σ. Then combine them into one anomaly score. Two simple choices:

  • the largest |z| across features, which points straight at the feature that moved
  • the sum of squares of the z-scores, which notices several features drifting together

Choose the alarm threshold from data, not by guessing: compute the score on normal frames that were not used to build the baseline and set the threshold just above nearly all of them, for example at their 99.9th percentile. Then require the score to stay above threshold for several consecutive frames before raising an alarm, because a door slamming next to the machine is not a fault.

The whole method in numpy

The script below uses synthetic data, a 25 Hz running tone plus its harmonic plus noise, and simulates a fault as a new tone at 410 Hz of growing strength.

import numpy as np

FS, N = 3200, 1024                          # sample rate (Hz), frame
EDGES = [0, 50, 100, 200, 400, 800, 1600]   # band edges in Hz
rng = np.random.default_rng(0)

def frame(fault=0.0):
    t = np.arange(N) / FS
    x = np.sin(2*np.pi*25*t) + 0.3*np.sin(2*np.pi*50*t)
    x += fault * np.sin(2*np.pi*410*t)      # a new tone appears
    return x + 0.2 * rng.standard_normal(N)

def features(x):
    p = np.abs(np.fft.rfft(x * np.hanning(N))) ** 2
    f = np.fft.rfftfreq(N, 1 / FS)
    bands = [p[(f >= lo) & (f < hi)].sum()
             for lo, hi in zip(EDGES, EDGES[1:])]
    rms = np.sqrt(np.mean(x ** 2))
    return np.log10(np.array(bands + [rms]) + 1e-12)

base = np.array([features(frame()) for _ in range(500)])
mu, sd = base.mean(axis=0), base.std(axis=0) + 1e-9

def score(x):
    return np.max(np.abs((features(x) - mu) / sd))

normal = np.array([score(frame()) for _ in range(500)])
thr = np.percentile(normal, 99.9)

for a in [0.0, 0.05, 0.2]:
    s = np.array([score(frame(a)) for _ in range(200)])
    print(f"fault={a}: flagged {np.mean(s > thr):.0%}")

On this synthetic data the weakest fault goes unnoticed and the stronger one is flagged in every frame, and because the score is the largest z-score, you can also report which band moved, which is exactly what a maintenance engineer wants to know. Real machines are messier, so treat the output of a script like this as a way to understand the method, not as an estimate of how well it will do on your machine.

Fitting it on the microcontroller

Everything here maps onto a small processor:

  • a 1,024-point FFT per frame, using an integer or single-precision FFT library, or a hardware FFT block if one is available
  • a sum per band and a log, which can be a lookup table or the position of the highest set bit plus a small correction
  • a subtraction, a multiplication by a precomputed 1/σ and a comparison per feature

Memory is the frame buffer (1,024 samples), the FFT working space and the baseline. Compute is dominated by the FFT, and at one frame every few seconds the processor sleeps nearly all the time. The baseline can even be learned on the device during commissioning: run Welford's online algorithm for mean and variance over the first hours of operation, then freeze it.

When to reach for a neural network

Simple scores work well when faults show up as changes in a few known bands. A model earns its place when normal behaviour itself is complicated, for example a machine whose spectrum changes a lot with load, so that one mean and standard deviation per band describes it badly. Then options include a baseline per operating condition, or an autoencoder trained only on normal frames, whose reconstruction error becomes the anomaly score. Either way, keep the simple detector running beside it as a reference, and compare both against the same held-out data. If the model does not catch something the simple score misses, it is not worth its flash.

Common mistakes:

  • building the baseline from a single afternoon, so the first change of load raises an alarm
  • setting the threshold on the same frames used to build the baseline
  • alarming on a single frame instead of requiring persistence
  • training a classifier on simulated faults and assuming it recognises real ones

Try it yourself

  1. Run the script and add a fault amplitude of 0.1 to see where detection starts.
  2. Change the fault to a change in the 25 Hz amplitude instead of a new tone and check which feature responds.
  3. Mount a phone or a small accelerometer board on a desk fan, record normal running at two speeds, and build a baseline from real data; then, with the fan unplugged, tape a small weight securely to one blade, keep the guard on, and score the new recording.
  4. Port the feature and score code to C for a microcontroller and compare its scores with numpy on the same recorded frames.
