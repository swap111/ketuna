Scoreboards and reference models: checking outputs you did not predict by hand

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Pair a Python reference model with a scoreboard so random tests check themselves. Covers in-order matching with a queue, out-of-order matching by tag, and the end-of-test checks that stop silent passes.

Once stimulus is random, you can no longer write the expected output next to each input by hand. Something must compute the right answer automatically and compare it with what the design produced. That is the job of two cooperating pieces: a reference model that predicts outputs from inputs, and a scoreboard that pairs each prediction with the matching actual output and decides pass or fail. Getting the pairing right is most of the work, and it changes depending on whether the design keeps its outputs in order.

Where the pieces sit

The scoreboard never touches pins. Monitors watch the design's input and output interfaces and turn pin activity into transactions. The input monitor feeds the model, the model produces expected transactions, and the scoreboard compares them with what the output monitor saw.

Keeping the model separate from the comparison matters. The model knows the spec; the scoreboard knows how to match. You can swap a simple model for a more detailed one, or reuse the scoreboard on another block, without rewriting both.

Writing the reference model

A reference model should be the most obviously correct statement of the spec you can write, at the transaction level, with no clocks or pins. For a block that adds a 16-bit saturating offset to each sample, the model is a few lines:

def sat_add_model(sample, offset):
    """Signed 16-bit saturating add, as the spec describes it."""
    s = sample + offset
    return max(-32768, min(32767, s))

Two rules keep a model useful. First, write it from the spec, not from the RTL. If you read the RTL and transcribe it into Python, you copy its bugs and the comparison always agrees. Second, keep it simpler than the design. The RTL may pipeline, share hardware and use clever bit tricks. The model should not; its value is that a reviewer can check it against the spec in a minute.

In-order matching with a queue

If the design produces outputs in the same order as inputs, which is true of most pipelines and FIFOs, the scoreboard is a queue. Predictions go in at the back; each actual output is compared with the front.

from collections import deque

class InOrderScoreboard:
    def __init__(self, name):
        self.name = name
        self.expected = deque()
        self.matched = 0
        self.errors = []

    def add_expected(self, txn):
        self.expected.append(txn)

    def add_actual(self, txn):
        if not self.expected:
            self.errors.append(f"unexpected output {txn}")
            return
        exp = self.expected.popleft()
        if txn == exp:
            self.matched += 1
        else:
            self.errors.append(f"expected {exp}, got {txn}")

    def final_check(self):
        assert not self.errors, self.errors[:5]
        assert not self.expected, f"{len(self.expected)} never came out"
        assert self.matched > 0, "scoreboard saw nothing"

The pipeline latency does not appear anywhere, which is deliberate. Because the queue absorbs any delay, the same scoreboard works whether the design takes one cycle or twelve, and keeps working when someone adds a pipeline stage.

Out-of-order matching by tag

Some designs return results out of order: a memory controller that serves a hit before an earlier miss, or a bus fabric with several outstanding transactions identified by an ID. A single queue would report false mismatches. Instead, keep one queue per tag, or a dictionary keyed by whatever identifies a transaction.

from collections import defaultdict, deque

class TaggedScoreboard:
    def __init__(self):
        self.pending = defaultdict(deque)   # tag -> expected data
        self.errors = []

    def add_expected(self, tag, data):
        self.pending[tag].append(data)

    def add_actual(self, tag, data):
        q = self.pending.get(tag)
        if not q:
            self.errors.append(f"tag {tag}: response with no request")
            return
        exp = q.popleft()
        if exp != data:
            self.errors.append(f"tag {tag}: expected {exp}, got {data}")

    def final_check(self):
        left = {t: len(q) for t, q in self.pending.items() if q}
        assert not self.errors, self.errors[:5]
        assert not left, f"outstanding requests: {left}"

Within one tag, order is still checked, because most protocols promise in-order responses for the same ID. Across tags, any order is allowed. Match the scoreboard to exactly the ordering rule the spec promises: looser than the spec hides reordering bugs; stricter produces false failures.

The end-of-test checks

The three assertions in final_check prevent the most embarrassing class of bug, the silent pass.

  • Errors list empty. The obvious one.
  • Nothing left pending. If the design swallowed a transaction, the scoreboard never saw a mismatch, only a missing output. Without this check the test passes.
  • At least one match. If the output monitor is wired to the wrong signal and never fires, there are zero mismatches and zero matches. Only the count reveals it.

Call final_check after the stimulus finishes and the design has drained, for example after waiting enough cycles for the deepest pipeline to empty.

When model and design disagree

A mismatch does not automatically mean the RTL is wrong. There are three suspects, and you should rule each one in or out deliberately:

  1. The design does not follow the spec. This is the bug you were hoping to find.
  2. The model misreads the spec. Models are code, and code has bugs. Re-read the spec line the model implements before blaming the RTL.
  3. The spec is ambiguous, and the designer and the model author read it differently. Neither is wrong yet; the spec needs a sentence added.

The third case is more common than beginners expect, and it is valuable: the scoreboard has found a place where two careful engineers understood the same document in two ways. Settle it with the designer, update the spec, and then fix whichever side lost the argument.

Make mismatch messages easy to act on. Print the input that produced the expectation, the simulation time, and both values in the same number base. A message that says only "mismatch" sends you to the waveform viewer for every failure; one that says "sample 32760 + offset 20: expected 32767, got −32756" often names the bug outright.

Try it yourself

  1. Write a small pipelined saturating adder in Verilog with two or three register stages, and a cocotb testbench with an input monitor, the model above and InOrderScoreboard.
  2. Drive 1,000 random samples on Icarus Verilog, including values near ±32767, and check final_check passes.
  3. Break the design three ways (wrong saturation limit, a dropped output, the output monitor watching the wrong valid signal) and confirm each is caught, noting which assertion fired.
  4. Add a fourth pipeline stage and confirm the scoreboard needs no changes.
