Inside a standard-cell library: Liberty, LEF and what the numbers mean

Physical design & tape-out Intermediate 27 Nov 2026 5 min read By Ketuna

A cell library is several files that describe the same cells for different tools. Learn what Liberty timing tables and LEF footprints contain, what drive strengths mean, and how a tool looks up one delay.

Every step of the digital flow leans on the standard-cell library, but most people only meet it as a path in a configuration file. Open the files and you find the cells described several times over, each view written for a different tool: one for timing and power, one for placement and routing, one for the layout itself, one for simulation. Knowing what is in each view, and which tool reads it, makes synthesis results, placement problems and timing reports far easier to interpret.

One cell, several views

Take a two-input NAND gate. The library describes it in at least these forms:

View File type Read by Contains
Timing and power Liberty (.lib) Synthesis, STA, power analysis Function, pin capacitance, delay and power tables, area
Abstract layout LEF Placement, routing Cell size, pin shapes and layers, blockages
Full layout GDS Final layout merge, DRC, LVS Every polygon of the cell
Simulation Verilog model Simulators Logic behaviour, sometimes with timing checks
Transistor netlist SPICE LVS, characterisation The transistors and their sizes

Each view must agree with the others: the same pin names, the same function, the same size. The library provider ensures that, and a mismatch between views is one of the rare cases where a "tool bug" really is a data problem.

The Liberty file: timing as tables

A Liberty file describes each cell under one set of operating conditions, a process, voltage and temperature corner. That is why a library comes as several Liberty files, one per corner.

For each cell it gives:

  • Area, in the library's area unit (square micrometres for open PDKs).
  • Function of each output, as a Boolean expression, which synthesis uses for mapping.
  • Input pin capacitance, the load each input presents to whatever drives it.
  • Timing arcs from each input to each output, with delay and output transition tables for rising and falling outputs.
  • Constraint tables for sequential cells: setup and hold times as functions of the data and clock transitions.
  • Power: leakage per input state, and internal switching energy tables.

The delay of a cell is not one number. It depends on how fast its input changes (the input transition or slew) and how much capacitance its output drives (the load). The most common model, the non-linear delay model (NLDM), stores delay as a two-dimensional table indexed by those two values. A simplified, illustrative fragment:

cell (nand2_1) {
  area : 3.75;
  pin (A) { direction : input; capacitance : 0.0024; }
  pin (Y) {
    direction : output;
    function : "!(A & B)";
    timing () {
      related_pin : "A";
      cell_fall (delay_template) {
        index_1 ("0.01, 0.05, 0.20, 0.80");      /* input slew, ns */
        index_2 ("0.0005, 0.002, 0.008, 0.032"); /* load, pF */
        values ("0.020, 0.032, 0.075, 0.240", \
                "0.028, 0.041, 0.085, 0.251", ...);
      }
    }
  }
}

The numbers are made up for illustration; real files have more points, more arcs and both rise and fall tables.

How a tool reads one delay

When the timing tool needs the delay of this NAND for an input slew of 0.10 ns and a load of 0.005 pF, neither value is in the table. It finds the surrounding grid points and interpolates. This Python sketch does the bilinear interpolation:

from bisect import bisect_right

slews = [0.01, 0.05, 0.20, 0.80]          # ns, index_1
loads = [0.0005, 0.002, 0.008, 0.032]     # pF, index_2
delay = [                                  # ns, rows = slew
    [0.020, 0.032, 0.075, 0.240],
    [0.028, 0.041, 0.085, 0.251],
    [0.050, 0.068, 0.115, 0.284],
    [0.110, 0.135, 0.196, 0.380],
]

def lookup(x, y):
    i = min(max(bisect_right(slews, x) - 1, 0), len(slews) - 2)
    j = min(max(bisect_right(loads, y) - 1, 0), len(loads) - 2)
    tx = (x - slews[i]) / (slews[i + 1] - slews[i])
    ty = (y - loads[j]) / (loads[j + 1] - loads[j])
    d00, d01 = delay[i][j], delay[i][j + 1]
    d10, d11 = delay[i + 1][j], delay[i + 1][j + 1]
    return (d00 * (1 - tx) * (1 - ty) + d01 * (1 - tx) * ty
            + d10 * tx * (1 - ty) + d11 * tx * ty)

print(f"{lookup(0.10, 0.005):.4f} ns")

It prints 0.0725 ns. By hand: the slew sits a third of the way from 0.05 to 0.20 ns, and the load halfway from 0.002 to 0.008 pF. Halfway along the load axis gives 0.063 ns in the 0.05 ns row and 0.0915 ns in the 0.20 ns row; a third of the way between those is 0.0725 ns.

The tool does the same for the output transition, which becomes the input slew of the next cell, and so the calculation ripples along the path. Values outside the table are extrapolated, which is less accurate; that is one reason libraries set maximum transition and capacitance limits, and why violating them matters even when slack is positive.

Drive strengths

Cells come in several drive strengths, usually marked by a suffix such as _1, _2, _4. A stronger version uses wider transistors, so it has lower output resistance and drives a large load faster. The cost is a larger input capacitance (it loads its own driver more), more area and more power. Looking at the tables, the _4 version's delay grows much more slowly with load than the _1 version's, while its delay at very small loads is similar or slightly worse.

This is why sizing is an optimisation, not a rule: upsizing a cell helps the net it drives and hurts the net that drives it. Synthesis and placement tools resize cells constantly to balance the two.

The LEF file: what the router needs to know

The LEF view hides the transistors and keeps only what placement and routing need:

  • Size and site. Every cell's width is a whole number of placement sites and its height is one row (or a multiple). The tech LEF defines the site and the layers.
  • Pins. The shape and metal layer of each pin, so the router knows where to connect.
  • Obstructions. Metal inside the cell that routes must avoid.
  • Symmetry, which tells the placer whether the cell may be flipped.

If routing struggles to reach certain cells, their LEF pin shapes are worth a look: pins that are small or crowded on the lowest metal are harder to access.

Try it yourself

  1. Open a sky130 Liberty file for the sky130_fd_sc_hd library in a text editor and find a NAND2 cell. Read its area, pin capacitances and one delay table.
  2. Copy the table into the Python script above and look up the delay at a slew and load of your choice. Then check the same arc in OpenSTA with report_dcalc on a small netlist.
  3. Compare the _1 and _4 versions of an inverter: input capacitance, area, and delay at small and large loads.
  4. Open the cell's LEF and GDS in KLayout and match the pins in the LEF to the polygons in the layout.
