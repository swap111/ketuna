RTL to GDS in one page: what each step of the flow takes in and hands out

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

The RTL-to-GDS flow is a chain of steps, each reading files and writing files you can open. Learn what goes in and comes out of synthesis, floorplan, placement, clock tree, routing and sign-off.

In this article
  1. The chain at a glance
  2. What each step reads and writes
  3. Two files carry most of the story
  4. How to use this picture when something fails
  5. Try it yourself

The first time you run a physical design flow, it looks like one long command that prints thousands of lines and either ends with a layout or does not. That view makes failures mysterious. A better picture is a relay race: each step takes a small set of files, does one job, and hands a new set of files to the next step. If you know what each step reads and writes, you can stop the flow anywhere, open the hand-off and check it with your own eyes.

The chain at a glance

There are six big steps between your Verilog and the GDS file a foundry turns into masks. Every one of them also reads the PDK (process design kit): the standard-cell library, the technology rules and the layer definitions.

What each step reads and writes

Step Takes in Hands out
Synthesis RTL, timing constraints (SDC), cell library timing (Liberty) Gate-level netlist, area and cell-count report
Floorplan Netlist, target utilisation or die size, pin order Die and core outline, placement rows, I/O pins, power grid
Placement Floorplan database, cell footprints (LEF) Every cell at a legal row position, congestion estimate
Clock tree Placed design, clock definitions Buffered clock network, skew and latency report
Routing Clocked design, metal layer rules Wires and vias on real metal layers
Sign-off Routed design, rule decks GDS, DRC and LVS reports, multi-corner timing, power checks

A few words on what happens inside each box.

Synthesis turns behavioural Verilog into a network of real library cells such as NAND2, inverter and D flip-flop. The netlist is still plain Verilog, so you can read it. The report tells you how many of each cell you used and their total area.

Floorplan decides the shape of the block. It draws the die and the core area, fills the core with rows that cells will sit in, places the I/O pins on the edges and lays down the power rings and straps. Nothing logical changes here, only geometry.

Placement gives each cell an x and y position inside the rows. Global placement spreads cells to minimise wire length, then legalisation snaps them onto row sites with no overlaps. Tools also resize cells and insert buffers at this point to fix early timing problems.

Clock tree synthesis replaces the single ideal clock net with a tree of buffers, so the clock edge reaches thousands of flip-flops at nearly the same time. Before this step, timing assumes an ideal clock; after it, the real clock delays are known.

Routing draws every connection as metal wires and vias. Global routing plans which regions each net passes through; detailed routing draws the exact shapes, obeying spacing and width rules.

Sign-off extracts the real resistance and capacitance of the wires, reruns timing at every corner, and checks the layout against the foundry rules (DRC) and against the netlist (LVS). Only when all of these pass is the GDS ready to send.

Two files carry most of the story

Two kinds of hand-off show up again and again:

  • A netlist (Verilog) says what is connected to what. It comes out of synthesis and is updated whenever a later step adds buffers or clock cells.
  • A physical database (DEF or OpenROAD's ODB) says where everything is. It grows at every step: outline, then rows, then cell positions, then clock buffers, then wires.

The GDS at the end is simply that physical database written as polygons on mask layers. It has no idea about logic, which is exactly why LVS exists: to prove the polygons still implement the netlist.

How to use this picture when something fails

Because each step has inputs and outputs, a failure can be traced to the step that produced bad data, not just the step that noticed it.

  • Routing fails with congestion. Look back at the placement density map and the floorplan utilisation. The router is usually the victim, not the culprit.
  • Timing fails after routing but passed after placement. Real wire parasitics replaced estimates. Compare the same path in both reports.
  • LVS fails. Compare the netlist that went into routing with the one LVS extracted from the layout; a missing power connection or a renamed pin is common.

A useful habit is to write down, before each run, what you expect each hand-off to look like: roughly how many cells, how full the core will be, which path will be critical. Then check. The flow is fast enough to run many times, so the learning comes from comparing your prediction with the files.

Try it yourself

  1. Install the open PDK sky130 and LibreLane (the Docker image is the simplest route) and harden a small registered design such as an 8-bit ALU with a configuration that sets DESIGN_NAME, VERILOG_FILES, CLOCK_PORT and CLOCK_PERIOD.
  2. Open the run directory under runs/. Each step has its own numbered folder; find the synthesised netlist, the floorplan DEF and the final GDS.
  3. Open the GDS in KLayout and the routed database in the OpenROAD GUI. Match what you see to the table above, step by step.
