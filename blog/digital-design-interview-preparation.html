Preparing for digital design interviews: the topics that recur and how to practise

Careers & skills Intermediate 27 Nov 2026 6 min read By Ketuna

Digital design interviews keep returning to timing, FSMs, clock domain crossing, FIFOs and Verilog. Here is what each topic tests and how to practise by drawing, explaining and coding aloud.

In this article
  1. The five topics and what each one tests
  2. A model reasoning path for one question
  3. Practise by drawing, explaining and coding aloud
  4. Common mistakes
  5. Try it yourself

Digital design interviews look varied from the outside, but the questions cluster around a small set of ideas: timing, state machines, clock domain crossing, FIFOs and the Verilog that describes them. Interviewers return to these because they reveal whether you understand hardware as hardware, with clocks, delays and parallel behaviour, rather than as a program that happens to be written in Verilog. Preparing well means knowing these topics deeply and practising the way you will be tested: at a whiteboard, out loud, with someone asking "why?".

The five topics and what each one tests

Each recurring topic probes a different part of your understanding. Knowing what the interviewer is really checking helps you aim your answer.

Topic Typical question What it really tests
Timing Find the maximum clock frequency of this path Can you reason about delay, setup and hold with numbers
FSMs Design a detector for the pattern 1011 Can you turn a behaviour into states and transitions
CDC Pass a counter value to another clock domain Do you know why naive crossings fail
FIFOs Design a synchronous FIFO; how is "full" derived Pointer arithmetic, corner cases, simultaneous read and write
Verilog Blocking vs non-blocking; how a latch is inferred Do you know what hardware your code describes

Timing questions almost always end in a number, so practise the setup equation (clock period at least clock-to-Q plus logic delay plus setup time, adjusted for skew) until you can work one in under a minute. Be ready to explain why a hold violation cannot be fixed by slowing the clock: the clock period does not appear in the hold check.

FSM questions reward a clean method more than speed. Decide Moore or Mealy, draw the states as circles, label every transition, and check what happens on overlapping inputs. For a 1011 detector, the interesting case is the input 1011011, where the last 1 of one match starts the next.

CDC questions test whether you know that a two-flop synchronizer is for single-bit signals only. A multi-bit bus synchronized bit by bit can be captured with some bits old and some new. The fixes are a handshake, an asynchronous FIFO, or Gray coding for counters, where only one bit changes per step, so a sample is either the old value or the new one.

A model reasoning path for one question

Here is how a strong candidate might work through a common question: "In a synchronous FIFO with 8 entries, how do you generate full and empty?"

  1. Restate and clarify. "Eight entries, one clock, one read port and one write port. Should a write when full be ignored? I will assume yes."
  2. Name the difficulty. "If read and write pointers are both 3 bits, equal pointers could mean empty or full. I need one more bit of information."
  3. Offer the standard fix. "Use 4-bit pointers. The low 3 bits address memory. Empty is when all 4 bits match. Full is when the low 3 bits match and the top bit differs, meaning the write pointer has wrapped once more than the read pointer."
  4. Check a corner case aloud. "Simultaneous read and write when full: the read frees a slot, but my write enable is gated by full, so the write is dropped this cycle. If the spec wants it accepted, I would gate on full && !rd_en instead."
  5. Write it.
// AW = 3 for 8 entries; pointers are AW+1 bits wide
wire empty = (wr_ptr == rd_ptr);
wire full  = (wr_ptr[AW-1:0] == rd_ptr[AW-1:0]) &&
             (wr_ptr[AW]     != rd_ptr[AW]);

Notice what the interviewer hears: a clarified spec, a named problem, a standard solution, a corner case found without prompting, and only then the code. Even if you made a small slip in the code, steps 1 to 4 show the thinking they are hiring for.

Practise by drawing, explaining and coding aloud

Reading answers is not preparation. In an interview you must produce the answer while someone watches, and that is a separate skill. Practise it in three modes.

  • Draw. For every topic, draw the circuit or waveform from memory on paper: a two-flop synchronizer, a rising-edge detector (one flop and an AND gate with the delayed copy inverted), an FSM diagram, a FIFO with its pointers. If you cannot draw it, you do not yet know it.
  • Explain. Say each answer out loud, alone or to a friend, as if to an interviewer. You will notice gaps the moment you try to say "and then…" and cannot continue. A phone recording played back is uncomfortable and very effective.
  • Code. Write small modules by hand, without an editor's help, then simulate them. A counter, an edge detector, a sequence detector, a FIFO. Typing them in afterwards and running a simulation catches the mistakes your eyes skipped.

A good weekly rhythm is two or three questions a day, each done in all three modes, with one mock interview at the end of the week where a peer picks the questions. Ask them to interrupt with "why?" and "what if the input glitches?", because real interviewers will.

Common mistakes

  • Starting to code immediately. Without clarifying the spec, you may solve a different problem. Spend the first minute asking questions.
  • Memorising answers without mechanisms. "Use Gray code" is not an answer until you can say why one changing bit makes the sample safe.
  • Going silent. Interviewers cannot give credit for thinking they cannot hear. Narrate, even when unsure.
  • Bluffing. Saying "I don't know that, but here is how I would find out" is far better than a confident wrong answer that the follow-up exposes.
  • Ignoring reset and corner cases. What happens at reset, on back-to-back inputs, and on simultaneous events is where most designs break and most follow-ups go.

Try it yourself

  1. Write the 1011 overlapping sequence detector as a Moore FSM by hand, then simulate it with Icarus Verilog (iverilog -o det det.v det_tb.v, then vvp det) on the stream 1011011 and check it fires twice.
  2. Build the 8-entry FIFO above, add a testbench that fills it, overfills it and drains it, and confirm full and empty assert exactly when expected.
  3. Run Verilator in lint mode (verilator --lint-only -Wall fifo.v) on your FIFO and fix every warning, then explain each fix out loud as if to an interviewer.
  4. Pick three timing questions, work them on paper, and have a peer quiz you with follow-ups for fifteen minutes.
