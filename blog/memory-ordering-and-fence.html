Memory ordering and FENCE: why a store may not be visible yet

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

Write buffers and relaxed ordering let a RISC-V core make memory operations visible out of program order. See where that breaks device drivers and multi-hart code, and which FENCE fixes each case.

Within a single thread, a processor always appears to run your loads and stores in program order: a load after a store to the same address sees the stored value. That guarantee says nothing about what another observer sees: a second hart, a DMA engine, or a peripheral reading its own registers. To those observers, a RISC-V core may make memory operations visible in a different order from the program's. Most of the time nobody can tell. In device drivers and lock-free code, it is the source of bugs that appear once in a million runs. FENCE instructions are how software states the ordering it needs.

Why hardware reorders

Reordering is not a design flaw; it is a consequence of making memory fast.

  • Write buffers. A store that misses in the cache would stall the pipeline while the line is fetched. Instead the core parks the store in a buffer and carries on. A later load to a different address that hits in the cache completes first. To an outside observer, the load happened before the store.
  • Multiple paths to memory. Normal memory and device registers often sit behind different parts of the interconnect, with different latencies. A store to a peripheral can arrive before an earlier store to SRAM.
  • Out-of-order and non-blocking caches. Larger cores keep several misses outstanding, and they complete in whatever order memory returns them.

The RISC-V memory model, called RVWMO (weak memory ordering), allows these reorderings between accesses to different addresses unless software asks otherwise. It defines precisely which orders are preserved, for example dependent accesses and accesses to the same address, and which need a fence. There is also an optional Ztso extension for cores that provide the stronger total store order; portable code should not assume it.

The FENCE instruction

fence takes two sets, a predecessor set and a successor set, each a combination of four access kinds: I (device input, reads from I/O regions), O (device output, writes to I/O regions), R (memory reads) and W (memory writes). The fence guarantees that every access of the predecessor kinds before it is visible to other observers before any access of the successor kinds after it.

fence rw, rw orders all memory accesses; fence iorw, iorw orders everything. Narrower fences say exactly what you need and let the hardware keep the rest of its freedom. On a small in-order core without a write buffer, a fence may cost nothing at all; on a large core it may have to drain buffers and wait.

A separate instruction, fence.i from the Zifencei extension, orders stores against instruction fetches on the same hart. It is needed after writing code into memory, for example a bootloader copying a program or a JIT compiler, because the instruction cache and fetch path are not required to see recent stores.

Case 1: handing a buffer to a DMA engine

A driver fills a descriptor in normal memory and then writes a "go" bit in the DMA engine's register:

#include <stdint.h>

#define fence_w_o()  __asm__ volatile ("fence w, o" ::: "memory")

struct desc { uint32_t src, dst, len, flags; };

void dma_start(volatile struct desc *d, volatile uint32_t *doorbell,
               uint32_t src, uint32_t dst, uint32_t len)
{
    d->src = src;
    d->dst = dst;
    d->len = len;
    d->flags = 1u;          /* descriptor valid */
    fence_w_o();            /* memory writes before device write */
    *doorbell = 1u;         /* device starts reading d now */
}

Without the fence, the doorbell write may reach the DMA engine before the descriptor writes reach memory, and the engine reads a half-written descriptor. Note that volatile is not enough: it stops the compiler from reordering or removing the accesses, but says nothing to the hardware. The "memory" clobber stops the compiler moving memory accesses across the asm statement, and the fence instruction stops the hardware.

Case 2: reading data after a status bit

The reverse direction: a peripheral finishes writing a buffer by DMA, sets a "done" bit in its status register, and the driver reads the buffer.

while ((*status & DONE) == 0) { }
__asm__ volatile ("fence i, r" ::: "memory");   /* device read before memory reads */
process(buffer);

Without the fence, the core may read the buffer speculatively or from a stale line before the status read completes. If the buffer is cacheable and the system has no hardware coherence for DMA, the driver must also invalidate the cache lines first; a fence orders accesses, it does not make stale cached data fresh.

Case 3: passing a message between harts

Two harts share a data word and a flag, both in normal memory, initially zero:

hart 0                          hart 1
  sw   t0, 0(a0)   # data = 42     loop: lw  t1, 0(a1)   # flag
  fence w, w                             beqz t1, loop
  sw   t2, 0(a1)   # flag = 1            fence r, r
                                         lw  t3, 0(a0)   # data

Without the producer's fence, the flag store may become visible first. Without the consumer's fence, the data load may be satisfied before the flag load. Either way, hart 1 can see flag = 1 and the old data. Each side needs its own fence: ordering is a property of both the writer and the reader.

In C you would normally not write these fences by hand. C11 atomics with release and acquire ordering express exactly this pattern, and the compiler emits the right instructions, which may be fences or the A extension's ordered atomic instructions with their .aq and .rl bits.

Common mistakes

  • Relying on volatile for hardware ordering. It constrains only the compiler.
  • Fencing on one side only. Message passing needs ordering at the writer and the reader.
  • Using a fence instead of cache maintenance. Fences order; they do not invalidate or clean cache lines.
  • Assuming the core you test on reorders. A simple in-order core may never show the bug, and the same code fails on a larger core with the same ISA.
  • Forgetting fence.i after loading code. The fetch path may still see the old bytes.

Try it yourself

  1. Read the "memory ordering" chapters of the RISC-V unprivileged specification and work through its litmus-test examples for message passing.
  2. Write the message-passing pattern above in C11 with atomic_store_explicit(..., memory_order_release) and atomic_load_explicit(..., memory_order_acquire), compile with a RISC-V GCC cross-compiler and -O2 -S, and see which instructions appear.
  3. Run a two-hart version on QEMU with -smp 2. It will probably pass even without fences, because the emulator rarely reorders, which is exactly why reasoning, not testing alone, is required here.
