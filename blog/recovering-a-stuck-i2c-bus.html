Why an I2C bus gets stuck low, and how firmware recovers it

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

If the controller resets in the middle of a read, a target can hold SDA low forever, waiting for clocks that never come. Clocking out the rest of the byte and sending a STOP releases the bus.

A board works for days, then after a watchdog reset the I2C sensor stops answering. Every transfer fails with "bus busy" or an arbitration error, and only unplugging the power fixes it. The sensor is not broken and neither is the driver. The bus is stuck, and the reason lies in a small detail of how I2C targets transmit data. Once you understand it, a dozen lines of start-up code make the problem go away.

How a target ends up holding SDA

I2C lines are open drain: any device can pull a line low, and the pull-up resistor brings it high when nobody pulls. The controller drives SCL. During a read, the target drives SDA, one data bit per clock: it puts a bit on SDA while SCL is low and keeps it there until the next falling edge of SCL.

Now suppose the controller is reset in the middle of a read, by a watchdog, a brown-out or a debugger. The target does not know. It is partway through a byte, perhaps presenting a 0 bit, and it will keep presenting it until it sees the next clock. But the controller has just restarted and is not clocking anything. The target therefore holds SDA low indefinitely.

When the controller's I2C peripheral comes up again, it checks the bus before starting a transfer. A START condition is SDA falling while SCL is high, which is impossible when SDA is already low. The peripheral reports the bus as busy, or it tries and detects arbitration loss because SDA does not follow what it drives. Resetting the microcontroller again does not help, because the target is the one stuck. Cutting power to the target does, which is why the power cycle "fixes" it.

The fix: give the target the clocks it is waiting for

The target is not hung; it is waiting. If the controller supplies more clock pulses, the target shifts out the remaining bits of its byte. At some point it reaches either a 1 bit, when it releases SDA, or the acknowledge slot, when it releases SDA to let the controller answer. Either way SDA goes high.

A byte is 8 data bits plus one acknowledge bit, so at most 9 clocks are enough to reach the end of whatever the target was doing. Once SDA is high, the controller generates a STOP: SDA rising while SCL is high. A STOP resets the bus state machine in every target, so the next START is seen cleanly.

There is a second benefit. While the controller clocks with SDA released, the ninth clock in the acknowledge slot sees SDA high, which a transmitting target reads as "not acknowledged". That tells it the controller wants no more bytes, so it stops transmitting instead of starting the next byte.

In the figure, firmware pulls SDA low again while SCL is low, then releases it after SCL goes high. That low-to-high transition with SCL high is the STOP.

The recovery routine

Most I2C peripherals cannot generate bare clocks, so the usual approach is to switch the two pins to GPIO in open-drain mode, bit-bang the recovery, and then hand the pins back to the peripheral. The GPIO helpers here stand for your board's pin functions; od_release lets the pull-up take the line high, od_low pulls it low.

#include <stdbool.h>

#define I2C_HALF_PERIOD_US 5u   /* 100 kHz: 10 us per clock */

/* Returns true if the bus is free afterwards. */
bool i2c_bus_recover(void)
{
    pins_to_gpio_open_drain();          /* detach the peripheral */
    od_release(SDA);
    od_release(SCL);
    delay_us(I2C_HALF_PERIOD_US);

    if (!read_pin(SCL)) {               /* SCL stuck low: clocks cannot fix */
        pins_to_i2c_peripheral();
        return false;
    }

    for (int i = 0; i < 9 && !read_pin(SDA); i++) {
        od_low(SCL);
        delay_us(I2C_HALF_PERIOD_US);
        od_release(SCL);
        delay_us(I2C_HALF_PERIOD_US);   /* also allows clock stretching */
    }

    /* STOP: SDA low while SCL low, raise SCL, then raise SDA */
    od_low(SCL);
    delay_us(I2C_HALF_PERIOD_US);
    od_low(SDA);
    delay_us(I2C_HALF_PERIOD_US);
    od_release(SCL);
    delay_us(I2C_HALF_PERIOD_US);
    od_release(SDA);
    delay_us(I2C_HALF_PERIOD_US);

    bool ok = read_pin(SDA) && read_pin(SCL);
    pins_to_i2c_peripheral();           /* then re-initialise it */
    return ok;
}

Use a slow clock for recovery. You do not know what state the target is in, and a gentle 100 kHz works with every device on the bus. Never drive the lines high with push-pull outputs: if a target is pulling low at the same moment, you create a short circuit between two drivers.

When to run it

  • At every start-up, before the I2C peripheral is enabled. Check whether SDA reads low; if it does, recover. This handles the common case of a reset during a transfer, because a reset is exactly when the bus gets stuck.
  • After a transfer times out. Every I2C transaction in your driver should have a timeout. On timeout, reset the peripheral, run the recovery, and retry a limited number of times before reporting a fault.
  • Never in an interrupt. The routine takes around a couple of hundred microseconds; run it in task or main-loop context.

What clocking cannot fix

  • SCL held low. A target that is stretching the clock forever, or that has latched up, will not respond to clocks you cannot send. The only cures are that device's reset pin or switching its power supply, so on boards where this matters, design in a way to power-cycle the sensor from a GPIO.
  • A damaged or missing pull-up. If SDA reads low because nothing pulls it up, no firmware will help; measure the line with a meter or scope.
  • A device that needs its own reset sequence. Some parts document an interface reset; follow the datasheet. The system management bus (SMBus) variant of I2C also defines a clock-low timeout after which devices reset their interface; check whether your parts support it.

Try it yourself

  1. On a real board, start a long read from a sensor and reset the microcontroller mid-transfer with the debugger, many times. Note how often the bus comes up stuck, measured by SDA low at start-up.
  2. Capture the event with a logic analyser and sigrok PulseView: you should see SDA stay low with SCL idle high. Then capture the recovery and count the clocks before SDA rises.
  3. Add the recovery to start-up, repeat step 1, and confirm the sensor answers every time. Write a host unit test for the routine with a fake GPIO layer that simulates a target releasing SDA after a chosen number of clocks.
