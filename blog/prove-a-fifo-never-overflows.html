Proving a FIFO never overflows with SymbiYosys

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Write assertions, a reset assumption and covers for a small FIFO, run a SymbiYosys proof, and read the counterexample trace step by step when an undersized counter breaks the full flag.

A random simulation of a FIFO might run a million cycles and still never hit the one sequence that breaks the full flag. A formal tool does not sample; it considers every possible input on every cycle and either proves your properties hold or hands you the shortest sequence that breaks one. For a block as small as a FIFO, the open-source flow of Yosys and SymbiYosys does this in seconds. This walk-through writes the properties, runs the proof, and then reads a real counterexample from a classic sizing bug.

The design

A four-entry FIFO with a separate occupancy counter. Four entries is plenty for a proof: the control logic is the same at depth 4 as at depth 1,024, and a small depth keeps the state space tiny.

module fifo4 #(parameter W = 8) (
  input  wire         clk, rst,
  input  wire         wr_en, rd_en,
  input  wire [W-1:0] din,
  output wire [W-1:0] dout,
  output wire         full, empty
);
  reg [W-1:0] mem [0:3];
  reg [1:0]   wp, rp;
  reg [2:0]   count;              // must hold 0..4

  wire do_wr = wr_en && !full;
  wire do_rd = rd_en && !empty;
  assign full  = (count == 3'd4);
  assign empty = (count == 3'd0);
  assign dout  = mem[rp];

  always @(posedge clk) begin
    if (rst) begin
      wp <= 0; rp <= 0; count <= 0;
    end else begin
      if (do_wr) begin mem[wp] <= din; wp <= wp + 1'b1; end
      if (do_rd) rp <= rp + 1'b1;
      count <= count + do_wr - do_rd;
    end
  end

The properties go at the bottom of the same module, inside ifdef FORMAL so that simulation and synthesis never see them.

Assumptions, assertions and covers

Three kinds of statement do three different jobs.

  • An assumption restricts what the tool may try. Here the only one we need is "the design starts in reset". Without it, the solver begins from arbitrary register contents and reports failures no real chip could reach.
  • An assertion is the claim to prove.
  • A cover asks the tool to show that a situation can happen. If a cover is unreachable, the proof may be passing for the wrong reason.

For "never overflows", we keep a shadow count of accepted operations that is independent of the design's own counter, and tie the flags to it.

`ifdef FORMAL
  reg f_init = 1'b1;
  always @(posedge clk) f_init <= 1'b0;
  always @(*) if (f_init) assume (rst);

  reg [3:0] f_count;
  always @(posedge clk)
    if (rst) f_count <= 0;
    else     f_count <= f_count + do_wr - do_rd;

  always @(*) if (!f_init) begin
    assert (f_count <= 4);
    assert (full  == (f_count == 4));
    assert (empty == (f_count == 0));
    assert (count == f_count);        // helper invariant
  end

  always @(*) if (!f_init) begin
    cover (full);
    cover (full && wr_en && rd_en);
  end
`endif
endmodule

The second cover asks for a write and read together while full, the case where the write is refused and the read proceeds. If a wrong assumption ever made that unreachable, the cover would report it.

Running the proof

The job file tells SymbiYosys what to read, which mode to run and which engine to use.

[tasks]
prove
cover

[options]
prove: mode prove
prove: depth 8
cover: mode cover
cover: depth 12

[engines]
smtbmc

[script]
read -formal fifo4.v
prep -top fifo4

[files]
fifo4.v

Run sby -f fifo4.sby. The prove task runs a bounded check from reset and an induction step; if both succeed, the properties hold on every reachable state, for any length of run. The cover task produces one short trace per cover statement, which you can open to see the situations really occur.

The helper invariant count == f_count is there for the induction step. Induction starts from any state where the assertions held for a few cycles, including states the design could never reach. Tying the design's counter to the shadow counter rules those out.

Breaking it: an undersized counter

Now introduce a bug that happens in real code. Someone sizes the counter with the address width, as reg [1:0] count;, reasoning that four entries need two bits. Two bits hold 0 to 3. The value 4 does not exist, so count == 3'd4 is never true and full never asserts.

Run the proof again and the base case fails. SymbiYosys prints which assertion failed and writes a trace into the task directory (look in fifo4_prove/engine_0/ for the .vcd file). Open it in GTKWave. A trace like this is what you will find:

Step rst wr_en count f_count full empty
0 1 x x x x x
1 0 1 0 0 0 1
2 0 1 1 1 0 0
3 0 1 2 2 0 0
4 0 1 3 3 0 0
5 0 x 0 4 0 1

Reading the counterexample

Read a trace from the failure backwards, one question at a time.

  1. Which assertion failed, and at which step? At step 5, full == (f_count == 4) is false: four entries are stored, but full is 0. The empty assertion fails at the same step.
  2. What did the inputs do? Reset, then four writes in a row. No reads. The solver found the shortest path: you cannot reach four entries in fewer writes.
  3. Where do the design's state and the shadow model first disagree? At step 5, count drops from 3 to 0 while f_count goes to 4. That is the wrap of a two-bit register.
  4. Is the scenario legal? Four writes to an empty four-entry FIFO is exactly what it is for, so this is a real bug, not a missing assumption.

The failure also tells you how bad the bug is. With count back at 0, empty asserts while the FIFO is full, so the consumer stops reading and a fifth write overwrites the oldest entry. A random simulation would hit this only if it happened to write four times without a read, and then only if a checker noticed.

Pitfalls

  • No reset assumption. The solver starts from garbage and reports failures from impossible states.
  • Asserting during the reset cycle. Guard assertions so they check only after reset has taken effect.
  • Skipping covers. A proof that passes because an assumption forbids all writes is worthless. Covers expose it.
  • Full-size parameters. Prove at depth 4; the same RTL at a larger depth has the same control logic.

Try it yourself

  1. Install Yosys and SymbiYosys with a solver such as Yices, save the design and properties as fifo4.v with the job file, and run sby -f fifo4.sby.
  2. Open the cover traces in GTKWave and confirm the "write and read while full" case does what you expect.
  3. Apply the two-bit counter bug, rerun, and fill in the table above from your own trace.
  4. Restore the design, delete the helper invariant, and see whether induction still passes at depth 8; explain the result.
