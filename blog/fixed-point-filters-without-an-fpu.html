Fixed-point filters on a microcontroller without an FPU

Embedded systems Advanced 27 Nov 2026 6 min read By Ketuna

A second-order IIR filter in integer C with Q15 samples and Q14 coefficients, checked bit-exactly against a Python model, plus the accumulator, rounding and limit-cycle problems that floating point hides.

On a core without a floating-point unit, every float multiply becomes a call into a software library, many instructions long. A filter running at a few kilohertz can consume most of a small microcontroller that way. Fixed-point arithmetic does the same job with integer instructions, but it moves responsibility from the hardware to you: you choose where the binary point sits, how many bits the accumulator needs, how to round, and what happens on overflow. This article builds a second-order IIR low-pass filter in integer C, verifies it against a model, and shows a real defect that only appears in fixed point.

Q formats in one paragraph

A Q format is an integer with an agreed scale. In Q15, an int16_t represents value / 215, covering −1.0 to just under +1.0 in steps of about 3.05 × 10−5. ADC samples map naturally onto it. Multiplying two Q15 numbers gives a Q30 result in 32 bits; shifting right by 15 returns to Q15. The general rule: multiplying Qm by Qn gives Q(m+n), and adding requires both operands to have the same Q.

Filter coefficients often do not fit Q15. A second-order low-pass has a feedback coefficient near −2 when the cutoff is low, so this design stores coefficients in Q2.14 (written Q14 below): an int32_t scaled by 214, covering −2.0 to just under +2.0.

The filter and its coefficients

The biquad difference equation in direct form I is:

y[n] = b0·x[n] + b1·x[n−1] + b2·x[n−2] − a1·y[n−1] − a2·y[n−2]

A second-order Butterworth low-pass with a 50 Hz cutoff at a 1 kHz sample rate, designed in Python with SciPy, has b = [0.020083, 0.040167, 0.020083] and a = [1, −1.561018, 0.641352]. Multiplying by 214 and rounding gives the integers b = [329, 658, 329] and a1 = −25576, a2 = 10508. As a sanity check, the quantized DC gain is (329 + 658 + 329) / (16384 − 25576 + 10508) = 1316 / 1316 = 1, so a constant input should pass through unchanged. Hold on to that expectation.

The integer C

#include <stdint.h>

#define COEF_Q 14                      /* coefficients in Q2.14 */

typedef struct {
    int32_t b0, b1, b2, a1, a2;        /* a0 is 1.0, not stored */
    int16_t x1, x2, y1, y2;            /* Q15 history */
} biquad_t;

static int16_t sat16(int64_t v)
{
    if (v > INT16_MAX) return INT16_MAX;
    if (v < INT16_MIN) return INT16_MIN;
    return (int16_t)v;
}

int16_t biquad_step(biquad_t *f, int16_t x)
{
    int64_t acc = (int64_t)f->b0 * x
                + (int64_t)f->b1 * f->x1
                + (int64_t)f->b2 * f->x2
                - (int64_t)f->a1 * f->y1
                - (int64_t)f->a2 * f->y2;     /* Q15 x Q14 = Q29 */
    acc += (int64_t)1 << (COEF_Q - 1);        /* round to nearest */
    int16_t y = sat16(acc >> COEF_Q);         /* back to Q15 */

    f->x2 = f->x1;  f->x1 = x;
    f->y2 = f->y1;  f->y1 = y;
    return y;
}

/* biquad_t lp = { 329, 658, 329, -25576, 10508, 0, 0, 0, 0 }; */

Each decision has a reason:

  • Accumulator width. Each product is up to about 215 × 215 = 230, and five of them are summed, so a 32-bit accumulator can overflow in the worst case. A 64-bit accumulator removes the question at the cost of a few extra instructions on a 32-bit core. If you need the speed, prove headroom with the sum of absolute coefficients and use 32 bits.
  • Rounding. Adding half an LSB before the shift rounds to nearest. A bare arithmetic shift rounds towards minus infinity and adds a small negative bias to every output.
  • Saturation. If the output exceeds the Q15 range, clamp it. Wrapping around turns a slightly too-large positive value into a large negative one, which in a feedback filter can ring for a long time.
  • Direct form I. It keeps the input and output histories at sample precision, so the internal values cannot exceed the output range by much. Direct form II uses fewer state variables but its internal node can grow larger than the output, which is harder to manage in fixed point.

Testing against a model, bit for bit

Write the same arithmetic in Python with integers, and compare two things. First, the integer Python model against SciPy's floating-point lfilter on a test signal: here a 10 Hz tone, a 200 Hz tone and some noise, 2000 samples. The fixed-point output differed from floating point by at most about 3.8 LSB, with an RMS difference of about 1.2 LSB, which is the expected cost of 16-bit samples and 14-bit coefficients.

Second, and more important, the C code against the integer model. Pipe the same input samples through a host build of biquad_step and compare the outputs exactly. They should be identical, not close. Bit-exactness is what makes the test useful: any difference at all means the C code does something the model does not, such as a different rounding or a missing cast, and you find it on the laptop rather than in a field recording.

The bug floating point never shows

Now feed the filter an impulse and then zeros. In floating point the output decays to zero. In this fixed-point version it decays to 6 and stays there forever. A constant input of 10,000 settles at 10,002, not 10,000, despite the exact DC gain computed above.

This is a limit cycle or dead band, caused by rounding inside the feedback loop. With y[n−1] = y[n−2] = 6 and zero input, the accumulator is 25576 × 6 − 10508 × 6 = 90,408. Adding the rounding constant 8192 gives 98,600, and 98,600 >> 14 = 6. The rounding error exactly sustains the output. Poles close to the unit circle, here at radius about 0.80, make it worse, and filters with lower cutoffs have poles closer still.

A common fix is error feedback: keep the bits that the shift discards and add them back into the next sample's accumulator, so the rounding errors cancel over time instead of feeding the loop:

    acc += f->err;                       /* int64_t err in biquad_t */
    int64_t y_full = acc >> COEF_Q;
    f->err = acc - (y_full << COEF_Q);   /* remainder, carried over */
    int16_t y = sat16(y_full);

Replace the rounding line with this (and drop the half-LSB addition). In the integer model, the impulse response then decays to 0 and the constant input settles at exactly 10,000. Other remedies are more fractional bits in the stored state, or truncation towards zero. Whichever you choose, test zero input and constant input explicitly, for every coefficient set you ship.

Pitfalls

  • Shifting a negative number right is implementation-defined in C; GCC documents an arithmetic shift, but check your compiler before relying on it
  • Quantizing coefficients for very low cutoff frequencies moves the poles noticeably; check the quantized filter's response, not the designed one
  • Mixing Q formats in one addition without aligning them first
  • Testing only with tones, which never reveal dead bands or saturation

Try it yourself

  1. Design the filter with scipy.signal.butter, quantize the coefficients, and write the integer model in Python as described.
  2. Compile biquad_step with host gcc, feed it the same samples, and confirm with diff that the outputs are identical to the model.
  3. Reproduce the stuck output of 6 with an impulse followed by zeros, apply error feedback, and confirm it decays to zero. Then cross-compile for RV32 without the M extension and count the instructions per sample to see what the multiplies cost.
