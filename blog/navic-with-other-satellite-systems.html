Using NavIC alongside other satellite systems in one receiver

India's electronics ecosystem Advanced 27 Nov 2026 6 min read By Ketuna

Why multi-constellation receivers track more satellites, how they cope with different signal structures and bands, and how one extra unknown per system absorbs the offset between their time references.

A receiver that listens only to NavIC works well inside its service region, but it sees a limited number of satellites, and in a city street or under a tree canopy some of them will be blocked. Adding a global system such as GPS, Galileo or BeiDou raises the satellite count and spreads the visible satellites across the sky. That sounds like simply adding more channels, yet each system brings its own signal design, its own bands and, most importantly, its own clock. This article explains what changes inside the receiver when it combines them.

Why more satellites help

A position fix is a least-squares fit. With four satellites the receiver has exactly enough equations for its four unknowns (three coordinates and a clock bias), so any error in one pseudorange flows straight into the answer and nothing tells you it is wrong. With more satellites the fit is overdetermined: residuals reveal a bad measurement, and the receiver can drop it. This is the basis of integrity checks such as receiver autonomous integrity monitoring.

Geometry matters as much as count. If all visible satellites sit in one part of the sky, small range errors stretch into large position errors along the poorly constrained direction. The usual figure of merit is dilution of precision (DOP), computed from the geometry matrix of the fit. NavIC's geostationary and geosynchronous satellites sit at fixed parts of the sky over the region, while the global systems' satellites move, so together they tend to fill gaps that either would leave on its own. When buildings block half the sky, the extra satellites are often the difference between a fix and no fix.

Different signals, shared hardware

The systems do not transmit identical signals. They differ in carrier frequency, ranging code length and chipping rate, modulation, and navigation message format. Some overlap helps a great deal: NavIC's L5 signal shares its centre frequency with signals of other global systems in the same band, and newer NavIC satellites add a signal in the L1 band used by most consumer receivers. Where bands coincide, one RF front end and one ADC can serve several systems.

Part of the receiver Shared across systems Specific to each system
Antenna, LNA, front end Yes, if the bands overlap Extra paths for bands that do not
ADC and sample clock Usually Sample rate chosen to suit the widest signal
Correlator channels Hardware can be generic Code generator, code rate, modulation
Message decoding No Frame format, ephemeris model, time scale

The practical lesson for a digital designer is to make correlator channels configurable rather than hard-wired: a programmable code generator (or a code memory), a programmable code rate through a numerically controlled oscillator, and support for the subcarrier modulations some modern signals use. Firmware then assigns channels to satellites of whichever system is visible.

Each system keeps its own time

Every constellation runs its own system time, steered towards universal time but maintained by its own ground segment. The offsets between these time scales are small, but light covers about 30 cm per nanosecond, so even tens of nanoseconds matter for positioning. A receiver that ignored the offset would see one constellation's pseudoranges consistently too long or too short, and the fit would bend to accommodate them.

There are two standard ways to handle this:

  1. Estimate it. Add one clock-bias unknown per system. With NavIC plus one global system the receiver now solves for five unknowns, and so needs at least five satellites, with at least one from each system.
  2. Use a broadcast offset. Some systems broadcast the offset between their time and another system's time, or to universal time, in the navigation message. The receiver can apply it and keep a single clock unknown, at the cost of trusting the broadcast value's accuracy.

Many receivers estimate the offset when enough satellites are visible and fall back on the broadcast value when they are short of satellites, because spending one satellite on an extra unknown hurts most exactly when satellites are scarce.

The other parts of each system also need care. Each system defines satellite orbits in its own reference frame and broadcasts its own ephemeris parameters. Differences between the frames are small for most uses, but a receiver aiming at high accuracy must apply the published transformations. There are also small hardware delays that differ between signals of different frequencies inside the receiver itself, which show up as part of the per-system bias and are another reason to estimate it rather than assume it.

A worked example: two clocks in one fit

The script below builds a made-up scene with four satellites from system A and three from system B, gives each system a different clock bias, adds 2 m of range noise and solves for five unknowns by Gauss-Newton iteration. All numbers are illustrative and the geometry is random, not real orbits.

import numpy as np

rng = np.random.default_rng(7)
def sats(n):                       # unit vectors above the horizon
    v = rng.normal(size=(n, 3)); v[:, 2] = abs(v[:, 2])
    return 2.2e7 * v / np.linalg.norm(v, axis=1, keepdims=True)

sv = np.vstack([sats(4), sats(3)])         # 4 from system A, 3 from B
sys_b = np.array([0, 0, 0, 0, 1, 1, 1])    # which system each belongs to
pos = np.array([120.0, -45.0, 30.0])       # true position, metres
bias_a, bias_b = 3000.0, 3040.0            # clock bias per system, metres
rho = (np.linalg.norm(sv - pos, axis=1)
       + np.where(sys_b == 1, bias_b, bias_a) + rng.normal(0, 2.0, 7))

x = np.zeros(5)                            # x, y, z, bias A, bias B
for _ in range(6):                         # Gauss-Newton iterations
    r = np.linalg.norm(sv - x[:3], axis=1)
    pred = r + np.where(sys_b == 1, x[4], x[3])
    H = np.zeros((7, 5))
    H[:, :3] = (x[:3] - sv) / r[:, None]
    H[sys_b == 0, 3] = 1.0
    H[sys_b == 1, 4] = 1.0
    x += np.linalg.lstsq(H, rho - pred, rcond=None)[0]
print(np.round(x, 1), round(x[4] - x[3], 1))

It prints a position within a few metres of the truth and an inter-system offset of about 41 m against the 40 m that was put in. Now change the solver to use a single bias column for all seven satellites and run it again: the position error grows, because the fit has to spread a 40 m inconsistency across the coordinates.

Pitfalls in multi-system designs

  • Mixing time scales in firmware. Keep every timestamp tagged with the system it belongs to; converting late and in one place avoids subtle bugs.
  • Weighting all signals equally. Signals differ in chipping rate, power and multipath behaviour. Weight measurements by their expected noise, or one noisy signal type will dominate.
  • Assuming the extra band is free. A second band means another filter, mixer path or wider ADC bandwidth, which costs power and area. Decide which bands earn their place from the use case.
  • Testing only in open sky. The benefit of multiple systems shows up in obstructed conditions. Test there, with recorded data you can replay.

Try it yourself

  1. Run the script, then remove satellites from system B one at a time. Note when the five-unknown fit fails and why the geometry matrix becomes rank-deficient.
  2. Compute DOP from H (the square roots of the diagonal of the inverse of H.T @ H) with and without system B's satellites.
  3. Read how an open-source software receiver such as GNSS-SDR configures channels for different signals, and trace where it handles per-system time.
