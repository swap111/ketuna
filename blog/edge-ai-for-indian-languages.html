Edge AI for Indian languages: keyword spotting across languages and accents

India's electronics ecosystem Advanced 27 Nov 2026 5 min read By Ketuna

How to build an on-device keyword spotter that works across Indian languages and dialects, from consent-based data collection and small multilingual models to evaluation that reports the worst group, not the average.

In this article
  1. Why multilingual keyword spotting is harder
  2. Collecting data that represents users
  3. Small multilingual models
  4. Fair evaluation: report the worst group
  5. Pitfalls
  6. Try it yourself

A voice interface on a low-cost device, such as a pump controller, a kiosk or an appliance, must recognise a handful of command words without sending audio to the cloud. That is keyword spotting on a microcontroller, a well-studied problem when the users all speak one language with a narrow range of accents. In India the same product may be used by speakers of several languages, each with many dialects, who code-switch freely and speak in noisy kitchens, fields and streets. A model that scores well on a clean benchmark can fail badly for whole groups of users. This article covers what changes in data, models and evaluation when you design for that reality.

Why multilingual keyword spotting is harder

A keyword spotter listens continuously and fires when it hears one of a few target words. Its two failure modes have different costs: a false reject ignores a user who spoke the word, and a false accept triggers on unrelated speech or noise. Both get worse when speech varies more than the training data did.

Variation comes from several directions at once. Different languages may use different words for the same command, or share a borrowed word pronounced differently. Within one language, dialects shift vowels, stress and speed. Microphones, rooms and background noise vary from one product to another. Speakers differ in age, gender and voice quality. The model has a tiny memory budget, typically tens to hundreds of kilobytes, so it cannot simply memorise all of this.

Collecting data that represents users

Data is the real work, and it is where most projects cut corners. A useful collection effort:

  • Defines the command set with users, including the words people actually say for each command in each language, not translations chosen by the engineering team
  • Recruits speakers across languages, dialect regions, ages and genders, in proportions that reflect intended users, and records metadata for each group
  • Records on the target hardware or similar microphones, in realistic rooms and with realistic noise
  • Collects negative data: hours of ordinary speech in each language, including words that sound similar to the keywords, plus everyday noise
  • Obtains informed consent, explains how recordings will be used and stored, and protects speakers' privacy; voice is personal data

Split the data by speaker, so no person appears in both the training and test sets. Otherwise the model learns individual voices and the test score is inflated. Keep a separate test set for every group you care about, collected the same way.

Small multilingual models

The usual pipeline extracts log-mel or MFCC features from short frames of audio, then feeds a window of frames to a compact network such as a depthwise-separable convolutional network, quantized to 8-bit integers to fit the microcontroller. Two design choices matter specifically for multiple languages.

Shared or separate models. One shared model with outputs for every keyword in every language is simplest to deploy and lets languages share acoustic knowledge, but its fixed capacity is split across them. Separate per-language models, selected by a setting, give each language the full budget but need the user or installer to choose. A middle path is a shared feature extractor with small per-language output heads.

Keywords as classes or as sounds. Treating each keyword as a class is accurate for a fixed set. Models that recognise smaller sound units, then match sequences, can add new keywords without retraining, at some cost in accuracy and compute.

Augmentation helps: adding recorded noise, room reverberation, speed and pitch changes and gain variation. It does not replace real speakers from under-represented groups; augmentation can stretch the data you have, but it cannot invent a dialect you never recorded.

Fair evaluation: report the worst group

A single accuracy figure hides the problem. Report false reject rate and false accepts per hour for every group, at the operating threshold you will ship. The made-up counts below show why:

# made-up evaluation counts per language and accent group
groups = {
    # group: (keyword clips, missed, hours of other speech, false wakes)
    "lang A, region 1":  (400, 12, 20.0, 4),
    "lang A, region 2":  (300, 27, 15.0, 6),
    "lang B, region 1":  (350, 14, 18.0, 3),
    "lang B, region 2":  (250, 40, 12.0, 9),
}

worst = None
for name, (n, miss, hrs, fa) in groups.items():
    frr = miss / n
    fa_h = fa / hrs
    print(f"{name:16s} FRR {frr:6.1%}  false wakes/h {fa_h:.2f}")
    if worst is None or frr > worst[1]:
        worst = (name, frr)

n_all = sum(g[0] for g in groups.values())
miss_all = sum(g[1] for g in groups.values())
print(f"pooled FRR {miss_all / n_all:.1%}, worst group {worst[0]}")

The pooled false reject rate is 7.2 percent, which might pass a review. But one group sees 16 percent, more than five times the best group's 3 percent, and also the most false wakes. For those users the product simply does not work well. Set acceptance criteria on the worst group, not the average, and on both error types together, because lowering the threshold to help one group usually raises false accepts for everyone.

Pitfalls

  • Test sets that share speakers with training data
  • Collecting most data from the team's own region and calling it multilingual
  • Reporting accuracy on balanced test clips instead of false accepts per hour on long recordings
  • Tuning the threshold on the test set
  • Shipping a quantized model without re-evaluating it per group after quantization

Try it yourself

  1. Record ten speakers saying two command words and ten minutes of ordinary conversation, with consent, and split them by speaker.
  2. Compute log-mel features with numpy and train a small convolutional model, then quantize it to 8-bit integers and compare per-group results before and after.
  3. Extend the script above to sweep the detection threshold and plot false reject rate against false accepts per hour for each group with matplotlib.
  4. Run the quantized model on a microcontroller with Zephyr and measure inference time and memory use.
