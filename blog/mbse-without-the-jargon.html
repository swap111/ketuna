Model-based systems engineering without the jargon

Systems & product engineering Beginner 27 Nov 2026 5 min read By Ketuna

Model-based systems engineering keeps what a system must do, how it is split up and how the parts connect in one linked model instead of scattered documents. Here is the idea in plain words, with an example.

On a typical small project the description of the system lives in many places: a requirements spreadsheet, a block diagram in a slide deck, a pin list in another spreadsheet, and a few decisions in someone's email. Each was correct on the day it was written. Three months later they disagree, and nobody knows which one is right. Model-based systems engineering (MBSE) is a name for a simple remedy: keep one connected description, the model, and treat documents and diagrams as views generated from it.

Documents versus a model

A document is a picture of the system frozen at one moment. If the radio changes from one interface to another, you have to find every document that mentions it and edit each by hand. Miss one and the team now has two truths.

A model stores each fact once, as an element with properties and links. "The radio module" is a single element. The block diagram, the interface table and the power budget all refer to that element. Change its interface once and every view that shows it changes too. That is the whole idea. The jargon around MBSE (languages, methods, tools) is about how to store and draw such a model, not about a different way of thinking.

Four questions the model answers

Most MBSE methods describe a system from several angles, called views. You can think of them as four questions, asked in order:

  1. Operational: what do the people around the system do with it? A farmer checks soil moisture on a phone each morning.
  2. Functional: what must the system do, independent of parts? Sense moisture, filter the reading, package it, transmit it.
  3. Logical: what abstract building blocks perform those functions? A sensor interface, a processing block, a radio link.
  4. Physical: what real things implement the blocks? A probe and an ADC, a microcontroller, a radio module, an antenna.

The valuable part is the links between the layers, called allocations: "filter the reading" is allocated to the processing block, which is realised by the microcontroller firmware. With those links in place, you can ask the model questions that are tedious to answer from documents, such as "which physical parts are involved in sending a reading?"

Why functions come before parts

Beginners often start at the physical row: "we will use this microcontroller and that radio". It feels productive, but it quietly fixes the design before anyone has listed what the system must do. Starting from functions has two benefits. First, it exposes forgotten functions, such as "report low battery" or "recover after a brown-out", while they are still cheap to add. Second, it keeps alternatives open: "filter the reading" could live in firmware or in a small hardware block, and a trade study can decide which, with the function's requirements in hand.

Interfaces are part of the model

Every arrow between blocks is an interface, and most integration problems happen at interfaces. In a model, an interface is an element in its own right, with properties: the signals, the protocol, voltage levels, timing, units and the team that owns it. When the sensor interface is described as "SPI, mode 0, up to 1 MHz, 3.3 V, 16-bit reading in units of 0.1 % volumetric moisture, owned by the hardware team", the firmware engineer can write the driver without waiting for the board, and a mismatch is caught at review rather than at bring-up.

You can start without a big tool

MBSE has standard languages and tools. SysML is a widely used open modelling language for systems, and Eclipse Capella is an open-source modelling tool built around a method called Arcadia. These are worth learning, and on large programs they earn their keep. But the habit matters more than the tool. On a student project you can get most of the benefit with plain text:

  • a CSV of functions, each with an ID and the logical block it is allocated to
  • a CSV of blocks, each with the physical part that realises it
  • a CSV of interfaces, each with endpoints, signals, units and owner
  • a short Python script that checks every function is allocated, every interface has an owner, and draws the diagram from the data

Because the diagram is generated from the tables, it cannot drift away from them. That is the model-based idea in its smallest form.

Common mistakes

  • Drawing pictures and calling them a model. If changing a block means editing three diagrams by hand, it is still a set of documents.
  • Boxes without interface definitions. An arrow labelled "data" hides every question that will matter at integration.
  • Modelling everything. Model what the team needs to reason about; a model nobody reads is overhead.
  • Letting documents and the model diverge. Generate documents from the model, or the team will stop trusting either.

Try it yourself

  1. For a device you know, such as a digital thermometer, write the four rows: one operational scenario, four or five functions, three logical blocks and the physical parts.
  2. Put the functions, blocks and allocations into CSV files and write a Python script that reports any function without an allocation.
  3. Install Eclipse Capella, which is free and open source, and redraw the same system with its functional and physical views. Compare how a change propagates in the tool with how it propagates in your CSV files.
