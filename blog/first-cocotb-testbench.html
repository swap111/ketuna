Your first cocotb testbench: clock, reset, drive and check a counter

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Build a complete self-checking cocotb testbench in Python for a 4-bit counter, and learn what await, the clock task, reset and ReadOnly actually do in simulation time.

A testbench that only produces waveforms makes you the checker: you scroll, squint and decide whether the design looks right. That works once. It does not work on the fiftieth change to the RTL, at midnight, in a regression with two hundred tests. cocotb lets you write the testbench in Python so that it drives the design and checks every result itself, and it runs on free simulators such as Icarus Verilog and Verilator.

The design under test

We will test a 4-bit counter with a synchronous active-high reset and an enable. It is small, but it has the three things every block has: a clock, a reset and behaviour that depends on an input.

module counter4 (
  input  wire       clk,
  input  wire       rst,     // synchronous, active high
  input  wire       en,
  output reg  [3:0] count
);
  always @(posedge clk) begin
    if (rst)     count <= 4'd0;
    else if (en) count <= count + 4'd1;
  end
endmodule

Before writing any test, write down what "correct" means: after reset the count is 0; with en high it adds one per clock and wraps from 15 to 0; with en low it holds.

How cocotb and the simulator take turns

The simulator owns time. Your Python code runs only in between simulator events, and every await hands control back until the thing you are waiting for happens. When you write await RisingEdge(dut.clk), cocotb asks the simulator to call back when clk rises, the simulator advances time and evaluates the RTL, and then your test resumes.

Two details trip up almost everyone:

  • Writes are scheduled. dut.en.value = 1 takes effect at the end of the current time step, not instantly. Reading dut.en.value on the next line still shows the old value.
  • Registered outputs update just after the edge. At the moment RisingEdge resumes your test, the flip-flops may not have updated yet. await ReadOnly() waits until every signal in the current time step has settled, which makes it the safe point to read outputs.

The complete testbench

Save this as test_counter4.py. It uses cocotb 2.x names.

import cocotb
from cocotb.clock import Clock
from cocotb.triggers import RisingEdge, ReadOnly, ClockCycles

async def reset(dut, cycles=2):
    dut.rst.value = 1
    dut.en.value = 0
    await ClockCycles(dut.clk, cycles)
    dut.rst.value = 0

async def check_after_edge(dut, expected):
    await RisingEdge(dut.clk)
    await ReadOnly()
    got = int(dut.count.value)
    assert got == expected, f"count={got}, expected {expected}"

@cocotb.test()
async def test_reset_value(dut):
    cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())
    await reset(dut)
    await ReadOnly()
    assert int(dut.count.value) == 0

@cocotb.test()
async def test_counts_and_wraps(dut):
    cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())
    await reset(dut)
    dut.en.value = 1
    model = 0
    for _ in range(40):              # 40 > 16, so it wraps twice
        model = (model + 1) % 16
        await check_after_edge(dut, model)

@cocotb.test()
async def test_enable_low_holds(dut):
    cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())
    await reset(dut)
    dut.en.value = 1
    await ClockCycles(dut.clk, 5)
    dut.en.value = 0
    await ReadOnly()
    held = int(dut.count.value)
    for _ in range(8):
        await check_after_edge(dut, held)

And a Makefile next to it:

SIM ?= icarus
TOPLEVEL_LANG = verilog
VERILOG_SOURCES = $(PWD)/counter4.v
COCOTB_TOPLEVEL = counter4
COCOTB_TEST_MODULES = test_counter4
include $(shell cocotb-config --makefiles)/Makefile.sim

Run make. cocotb compiles the Verilog, runs each @cocotb.test() in turn, and prints a pass/fail table. It also writes results.xml, which a CI system can read.

Reading the testbench line by line

The clock. Clock(dut.clk, 10, unit="ns") describes a 10 ns period clock (100 MHz). .start() returns a coroutine that toggles the pin forever, and cocotb.start_soon runs it in the background. If you forget this line, the first await RisingEdge waits forever and the test hangs.

The reset. The helper holds rst high for two rising edges with en low, then releases it. Putting it in a function means every test resets the same way, and a change to the reset sequence happens in one place.

The model. model = (model + 1) % 16 is the reference model: the simplest possible statement of what the counter should do. The test compares the design against it on every cycle, not just at the end. Checking every cycle means a failure message names the first cycle that went wrong, which is where debugging should start.

The checks. int(dut.count.value) raises an exception if any bit is X or Z. That is helpful: if you forget the reset, the test fails loudly instead of comparing garbage.

Mistakes worth avoiding

  • Calling a coroutine without await. reset(dut) on its own creates a coroutine object and never runs it. Always await it or start_soon it.
  • Reading outputs right at the edge. Without ReadOnly(), you can read the pre-edge value of count and see an off-by-one that is not in the design.
  • Writing during ReadOnly(). Signals cannot be changed in the read-only phase; await the next edge first. In the hold test, the write to en happens before ReadOnly() for that reason.
  • One giant test. Separate tests for reset, counting and holding mean a failure tells you which behaviour broke.

Reading a failure

When a check fails, cocotb stops that test, prints the assertion message with the simulation time, and moves on to the next test. The time tells you where to look in the waveform; the message tells you what was expected. Write messages that include both the observed and the expected value, as the helper does, so that most failures can be understood without opening a waveform at all.

All the tests in a module run one after another in the same simulation, so simulation time and the design's state carry over from one test to the next. That is why every test above starts the clock and applies reset itself: a test that relies on the previous one's leftovers passes or fails depending on test order.

To convince yourself the bench can fail, break the RTL on purpose: change the wrap or invert the enable, and confirm a test reports it. A testbench that has never failed has not been tested.

Try it yourself

  1. Install Icarus Verilog and cocotb in a Python virtual environment (pip install cocotb), save the two files above with counter4.v, and run make.
  2. Add WAVES=1 to the make command line to dump waveforms, and open them in GTKWave to see where the test sampled each value.
  3. Add a load input with a load_value to the RTL, write the plan item first, then a test that loads 14 and checks the wrap two cycles later.
  4. Switch to Verilator with make SIM=verilator and confirm the same tests pass unchanged.
