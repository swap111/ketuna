Sequencing an ADC array from RTL: sample scheduling, channel muxing and buffering

Digital & VLSI design Advanced 27 Nov 2026 5 min read By Ketuna

A sensor-fusion controller needs many channels sampled at known instants. Design the digital sequencer that schedules several multiplexed ADCs, respects settling time, timestamps each sample and buffers the results.

A sensor-fusion controller combines readings from many sources, such as accelerometer axes, current sensors and temperature probes, and the fusion algorithm assumes it knows when each reading was taken. The converters do the analog work, but the digital sequencer around them decides which channel each converter looks at, when it samples, how long the input mux is given to settle, and how each result is tagged and stored. Getting that logic right is what turns a box of ADCs into a measurement system.

The architecture

Take an illustrative array: four successive-approximation (SAR) ADCs, each with a 4-to-1 analog input multiplexer, giving 16 channels. Each ADC has a simple digital interface: a start pulse begins a conversion by sampling the input, and done with data reports the result some cycles later.

The sequencer's jobs:

  • step each ADC's mux through its channels in a programmed order;
  • wait for the mux and the sampling capacitor to settle before each start;
  • start conversions so that channels which must be compared are sampled together;
  • capture each result with its channel number and the time it was sampled;
  • push tagged results into a buffer that software or a DMA engine drains.

Building the schedule

Use these numbers, made up for illustration: each conversion takes 1.0 µs, and after switching the mux the input needs 0.25 µs to settle to within the required accuracy. One slot is therefore 1.25 µs, and each ADC visits its four channels in 5 µs, so every channel is sampled at 200 kS/s.

The key design choice is simultaneous sampling across converters. All four ADCs start on the same clock cycle, each on its own channel. Channels that the fusion algorithm compares directly, for example the three phase currents of a motor, should be placed on different ADCs in the same slot, so they are sampled at the same instant. Channels on the same ADC are sampled 1.25 µs apart, which matters for fast signals.

Rather than hard-coding the order, store the schedule in a small table that software writes: one entry per slot, holding the mux setting for each ADC and flags such as "end of sequence" or "repeat". Then firmware can sample a fast channel twice per sequence and a slow one once, or skip unused channels, without an RTL change.

The sequencer state machine

typedef enum logic [1:0] {IDLE, SETTLE, CONVERT, STORE} seq_t;
seq_t st;

always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) begin
    st <= IDLE; slot <= '0; tmr <= '0; start <= 1'b0;
  end else begin
    start <= 1'b0;                          // one-cycle pulse
    case (st)
      IDLE:    if (run) begin
                 mux_sel <= sched[0]; tmr <= settle_cyc; st <= SETTLE;
               end
      SETTLE:  if (tmr == '0) begin
                 start  <= 1'b1;            // all ADCs together
                 ts_hold <= timebase;       // time of sampling
                 st     <= CONVERT;
               end else tmr <= tmr - 1'b1;
      CONVERT: if (&adc_done) st <= STORE;  // wait for all four
      STORE:   begin                        // results pushed this cycle
                 slot    <= next_slot;
                 mux_sel <= sched[next_slot];
                 tmr     <= settle_cyc;
                 st      <= (run) ? SETTLE : IDLE;
               end
    endcase
  end

Three details deserve attention:

  • The mux switches as early as possible. It changes in STORE, right after the previous conversion is done, so the settle time starts immediately. In many SAR converters the sampling capacitor is disconnected from the input once a conversion begins, so switching the mux during the previous conversion is often allowed too, which hides the settle time entirely. Whether that is legal depends on the converter; check its timing requirements.
  • Settle time is a counter, not a guess. settle_cyc is a register, so it can be tuned after silicon is measured.
  • The timestamp is taken at the sampling instant. A sample's time is when the input was captured, not when the result appeared. ts_hold latches a free-running timebase counter on the same cycle as start. Tagging with the time of done would add the conversion latency to every timestamp and, if latency varies, add jitter to the data.

Tagging and buffering

Each result is packed with its channel number and timestamp, for example a 64-bit word holding the 12-bit sample, a 4-bit channel ID and a 32-bit timestamp. With 16 channels at 200 kS/s, that is 3.2 million words per second, or 25.6 MB/s, so the downstream bus and the software that consumes it must be checked against that rate. A FIFO absorbs the burst of four results produced at the end of each slot and the variable latency of whoever drains it. Report overflow with a sticky flag and an interrupt; silently dropped samples are the worst outcome for a fusion algorithm, because it cannot tell a gap from a steady signal.

Grouping the four simultaneous samples under one shared timestamp saves buffer space, at the cost of a more complex format.

Pitfalls

  • Channel crosstalk through the mux. Switching from a channel near full scale to one near zero needs more settling. Order the schedule so large jumps are rare, or give those slots extra settle time.
  • Clock domain crossings. ADC done and data may come from the converter's own clock. Synchronize them properly; a multi-bit result needs a handshake or a qualified capture, not per-bit synchronizers.
  • Timebase wrap. A 32-bit counter at 50 MHz wraps after about 86 seconds. Software must handle the wrap, or use a wider counter.
  • Changing the schedule while running. Use a shadow copy that takes effect at the end of a sequence, so one sequence never mixes old and new entries.

Try it yourself

  1. Draw the slot timeline for your own channel list on paper, mark which channels are sampled together, and compute each channel's sample rate.
  2. Write a behavioural ADC model in SystemVerilog that returns a sine wave value per channel after a fixed latency, and simulate the sequencer with Verilator or Icarus Verilog.
  3. Dump the tagged words to a file, load them with numpy, and plot each channel against its timestamp. Check that simultaneous channels share exactly the same timestamp.
