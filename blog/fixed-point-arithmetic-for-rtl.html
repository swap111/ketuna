Fixed-point arithmetic for RTL designers: Q formats, rounding and saturation

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

Convert a filter coefficient to Q1.15, track how bits grow through a multiply and an accumulate, and choose between truncation, rounding and saturation when you shrink the result back down.

A filter designed in Python uses floating-point coefficients like 0.3141. Hardware that filters a sensor signal thousands of times per second usually cannot afford a floating-point unit, so those numbers become integers with an implied binary point. Done carefully, fixed-point arithmetic gives results within a known, tiny error of the floating-point model. Done carelessly, it gives a filter that works on test vectors and wraps around to full-scale noise on a loud input.

Q formats

A fixed-point number is a two's complement integer with an agreed position for the binary point. The Qm.n notation says how the bits are split: m integer bits (including the sign bit, in the convention used here) and n fraction bits. The value is the integer divided by 2n.

Format Width Range Resolution (1 LSB)
Q1.15 16 bits −1 to just under +1 2−15 ≈ 3.05 × 10−5
Q4.12 16 bits −8 to just under +8 2−12 ≈ 2.44 × 10−4
Q2.30 32 bits −2 to just under +2 2−30

With a fixed width you trade range against resolution: every bit moved to the integer side doubles the range and halves the precision. Note that some texts count the sign bit separately and call 16-bit Q1.15 "Q15"; check which convention a document uses before you trust its widths.

Converting a coefficient

To put 0.3141 into Q1.15, multiply by 215 = 32768 and round to the nearest integer:

0.3141 × 32768 = 10292.4 → 10292 (hex 2834)

The stored value represents 10292 / 32768 = 0.3140869. The error is about −1.3 × 10−5, inside the bound of half an LSB, 2−16 ≈ 1.5 × 10−5, as it must be for rounding. If you had truncated instead, the error could be up to a full LSB. For a filter with many taps, these coefficient errors shift the frequency response slightly, so check the quantized response against the specification, not only the floating-point one.

Tracking bit growth

Every arithmetic operation can need more bits than its inputs:

  • Multiply: a Qa.b times a Qc.d gives a Q(a+c).(b+d). Two Q1.15 numbers give a Q2.30 result of 32 bits. The extra integer bit exists for one case only: −1 × −1 = +1, which Q1.15 cannot represent.
  • Add: adding two numbers of the same format needs one extra integer bit to hold the carry. Adding 2k numbers needs k extra bits in the worst case.

For a 16-tap filter with Q1.15 samples and coefficients, each product is Q2.30, and summing 16 of them needs 4 more integer bits: a Q6.30 accumulator of 36 bits can never overflow. That is a guarantee, not an estimate, and it means the accumulator needs no saturation logic.

In RTL, size the accumulator from this calculation and write the sign extension explicitly:

logic signed [15:0] x, c;        // Q1.15
logic signed [31:0] prod;        // Q2.30
logic signed [35:0] acc;         // Q6.30, 16 taps

assign prod = x * c;             // both operands signed
always_ff @(posedge clk)
  if (clear)      acc <= '0;
  else if (en)    acc <= acc + 36'(prod);  // sign-extends prod

Shrinking the result: truncation vs rounding

At the end you usually want a Q1.15 output again, so you must drop 15 fraction bits and some integer bits. Dropping fraction bits is a choice between:

  • Truncation: an arithmetic shift right. It costs nothing, but it always rounds toward minus infinity, so the average error is about −0.5 LSB. In a filter, that bias appears as a small DC offset; in an accumulating loop, it can build up.
  • Round half up: add half an output LSB (214 here) before shifting. The error stays within ±0.5 LSB, and the bias almost disappears. It costs one adder.
  • Convergent (round half to even): like rounding, but exact halves go to the even neighbour, removing the last bit of bias. Worth it when the same value is requantized repeatedly.

Here is a worked case, made up for illustration, with a short model you can run:

def to_q15(x):
    """Real number to Q1.15 integer, rounded, saturated."""
    v = round(x * (1 << 15))
    return max(-32768, min(32767, v))

def q30_to_q15(acc, mode="round"):
    """Drop 15 fraction bits from a Q.30 value, then saturate."""
    if mode == "round":
        acc += 1 << 14             # add half an output LSB
    v = acc >> 15                  # arithmetic shift (floor)
    return max(-32768, min(32767, v))

c = to_q15(0.3141)
x = to_q15(0.7)
p = c * x                          # Q2.30 product
print(c, x, p)                     # 10292 22938 236077896
print(q30_to_q15(p, "trunc"), q30_to_q15(p, "round"))  # 7204 7205

The exact product in output LSBs is 7204.53. Truncation gives 7204; rounding gives 7205, the nearer value.

Saturation instead of wrap-around

Dropping integer bits is where overflow happens. If the true result is 1.2 and the output is Q1.15, simply keeping the low 16 bits wraps it to a large negative number: a full-scale jump in the output. Saturation clamps instead: any value above the maximum becomes 0x7FFF, any value below the minimum becomes 0x8000.

// acc_r: rounded Q6.30 value shifted to Q6.15 (21 bits)
// top 6 bits must all equal the sign bit, or it overflowed
always_comb begin
  if (acc_r[20:15] == {6{acc_r[20]}}) y = acc_r[15:0];
  else if (acc_r[20])                 y = 16'sh8000;  // most negative
  else                                y = 16'sh7FFF;  // most positive
end

A saturated sample sounds or looks like clipping; a wrapped one looks like a spike of the wrong sign. For signal processing, saturation is almost always the right choice at the output, while wide internal accumulators avoid the need for it inside.

Common mistakes

  • Mixing signed and unsigned operands, which makes Verilog zero-extend a negative value
  • Forgetting that rounding can itself overflow: adding half an LSB to the largest value pushes it over, so saturate after rounding
  • Losing track of the binary point across modules; write the Q format in a comment next to every declaration
  • Verifying against a floating-point model with a tolerance instead of a bit-exact fixed-point model

Try it yourself

  1. Convert five coefficients of your own to Q1.15 by hand, then check them with the to_q15 function above.
  2. Extend the Python model into a bit-exact 16-tap FIR using numpy integer arrays, and compare its output with a floating-point version on a sine wave. Measure the error in LSBs.
  3. Write the FIR in SystemVerilog, simulate it in Verilator or Icarus Verilog with the same input, and compare against the Python model sample by sample. Any difference is a bug in one of them.
