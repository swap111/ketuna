Switching between two clocks without a glitch

Digital & VLSI design Advanced 27 Nov 2026 5 min read By Ketuna

A plain mux between two clocks can emit a runt pulse when its select changes. See how the cross-coupled glitch-free clock mux used for low-power modes works, and the assumptions it quietly relies on.

Low-power chips routinely change their clock source at run time: a fast oscillator or PLL while there is work to do, a slow low-power oscillator while waiting for the next sensor sample. The switch must happen while the logic downstream keeps running, and the clock it receives during the switch must contain no pulse shorter than either source's. A combinational mux cannot promise that. The standard circuit that can is small, but every flop and gate in it is there for a reason, and it depends on assumptions that are easy to violate at the system level.

What goes wrong with a plain mux

assign clk_out = sel ? clk1 : clk0; switches the instant sel changes. If sel changes while clk0 is high and clk1 is low, the output falls early, chopping a clk0 pulse short. If it changes while clk0 is low and clk1 is high, the output rises immediately, partway through a clk1 pulse, producing a short high pulse. Either way the downstream flops see a runt pulse: an edge that no timing analysis accounted for, or a pulse narrower than the flops' minimum pulse width. The result can be corrupted state or metastability in flops all over the clock domain.

The select usually comes from a register clocked by one of the two clocks, or from a third domain entirely, so it has no fixed relationship to both clocks at once. No amount of timing closure on sel fixes this.

The cross-coupled structure

The glitch-free mux gives each clock its own enable, and enforces two rules: an enable may only change while its own clock is low, and a clock may only be enabled after the other has been disabled.

module clk_mux_gf (
  input  logic clk0, clk1,
  input  logic rst_n,
  input  logic sel,           // 0 selects clk0, 1 selects clk1
  output logic clk_out
);
  logic en0_m, en0, en1_m, en1;

  always_ff @(negedge clk0 or negedge rst_n)
    if (!rst_n) begin en0_m <= 1'b0; en0 <= 1'b0; end
    else begin
      en0_m <= ~sel & ~en1;   // request clk0 only if clk1 is off
      en0   <= en0_m;
    end

  always_ff @(negedge clk1 or negedge rst_n)
    if (!rst_n) begin en1_m <= 1'b0; en1 <= 1'b0; end
    else begin
      en1_m <= sel & ~en0;    // request clk1 only if clk0 is off
      en1   <= en1_m;
    end

  assign clk_out = (clk0 & en0) | (clk1 & en1);
endmodule

Walking through a switch

Start with sel = 0, en0 = 1, en1 = 0: the output follows clk0. Now sel rises.

  1. On the next falling edge of clk0, en0_m captures 0, and on the one after that, en0 goes to 0. Both changes happen while clk0 is low, so the AND gate's output is already low and does not glitch. The last clk0 pulse at the output is a complete one.
  2. en1_m has been waiting on ~en0. Once en0 is 0, it crosses into the clk1 domain through the two clk1 flops, and en1 rises on a falling edge of clk1, while clk1 is low. The first clk1 pulse at the output is complete too.
  3. Between the two, the output stays low for a short gap. A gap is harmless: it is just a longer-than-usual low phase.

The two flops per branch serve a second purpose. The other branch's enable, and sel itself, are asynchronous to this branch's clock, so the first flop can go metastable. The second flop is a synchronizer. The falling-edge clocking is what keeps the enable changes inside the low phase.

The cost of the switch is latency: roughly two falling edges of the old clock plus two of the new. When switching to a slow clock, that can be a long time in absolute terms, and logic waiting for the switch must allow for it.

The assumptions it relies on

Both clocks must be running during the switch. If you switch away from a clock that has already stopped, its branch's flops never see a falling edge, en0 never drops, and en1 waits forever. The output is stuck. Power-management sequences must therefore keep the old clock alive until the switch completes, start the new clock and let it stabilise first, and only then gate or power down the old one. Some designs add a timeout or a forced-switch path for a failed oscillator, which needs its own careful analysis.

Reset must leave a defined state. With both enables reset to 0, the output is quiet until sel propagates through one branch. If logic needs a clock during reset, reset the appropriate enable to 1 instead, and check that the other branch cannot also start.

Implement it with real cells. The AND and OR gates are on the clock path. Synthesis may restructure them or merge them with other logic, reintroducing hazards. Use dedicated clock-gating or clock-mux cells from the library, mark the instances so optimisation leaves them alone, and check the netlist.

Timing tools need to be told. The output carries either clock. In STA, define both clocks at the mux output and declare them logically exclusive, so the tools do not try to time paths between them. Check scan test, too: test usually requires a way to force one clock through.

Common mistakes

  • Using a combinational clock mux and relying on software to switch "when it is safe"
  • Clocking the enable flops on the rising edge, which lets enables change while the clock is high
  • Turning off the old oscillator before the switch has completed
  • Letting synthesis optimise the clock-path gates

Try it yourself

  1. Simulate clk_mux_gf in Icarus Verilog with clocks of 10 ns and 34 ns periods and toggle sel at random times. Measure the narrowest high and low pulse on clk_out with a small checker in the testbench.
  2. Replace it with a plain mux and repeat. Count the runt pulses.
  3. Stop clk0 just before switching away from it and watch the output stick. Then write down, as a list, the power-management sequence that avoids it.
