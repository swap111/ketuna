Partitioning a NavIC receiver SoC between hardware correlators and firmware

Computer architecture & RISC-V Advanced 27 Nov 2026 6 min read By Ketuna

Count the operations in acquisition, tracking, data decoding and position solution for a NavIC receiver, and see why correlators belong in hardware while loop filters and navigation run comfortably in firmware.

A satellite navigation receiver is a classic hardware-software partitioning problem. Some of its work runs millions of simple operations per second on every sample from the ADC; some runs a few thousand times a second with real control logic; some runs once a second and involves matrix algebra. Putting each piece on the right side of the line decides the chip's area, power and flexibility. NavIC, India's regional navigation system, is a good concrete case, and the reasoning carries over to any receiver for GPS, Galileo or other systems.

The processing chain in brief

After the RF front end has amplified, filtered and down-converted a band (NavIC's L5 band is centred at 1176.45 MHz and its S band at 2492.028 MHz), an ADC delivers a stream of low-resolution samples, often only a few bits each. The digital receiver then performs four jobs for every satellite it uses:

  1. Acquisition: find whether the satellite is visible, and estimate its code phase and Doppler frequency.
  2. Tracking: keep the local replica code and carrier aligned with the incoming signal as both move.
  3. Data decoding: recover the navigation message bits (orbit and clock parameters).
  4. Navigation solution: compute position, velocity and time from the measurements of four or more satellites.

The open Standard Positioning Service signal on L5 uses a 1023-chip spreading code at 1.023 Mchip/s, so one code period is 1 ms, as with the GPS C/A code. Check the current NavIC interface control document for the exact signal definitions before you design to them; the numbers below use these values only to size the work.

Acquisition: a large, regular search

Acquisition correlates the incoming samples against a local code at every candidate code phase and Doppler offset, and looks for a peak. The work is easy to count. Use illustrative figures: 4.092 MHz sampling (four samples per chip), 1 ms of coherent integration (4092 samples), code phases in half-chip steps (2046 candidates), and Doppler bins 500 Hz apart over ±5 kHz (21 bins).

That is 2046 × 21 = 42,966 search cells, each needing 4092 complex multiply-accumulates: about 176 million complex MACs to search one satellite over one millisecond of data. Real receivers integrate longer for weak signals, which multiplies the work again.

No small embedded core does that in a useful time. Acquisition is therefore built as hardware: either a bank of parallel correlators that test many code phases at once, or an FFT-based engine that computes the correlation for all code phases in one transform per Doppler bin. Either way, the datapath is narrow (a few bits per sample), regular and highly parallel, which is exactly what silicon does efficiently.

The regional design helps a little. NavIC satellites are in geostationary and inclined geosynchronous orbits, so they move slowly relative to a receiver on the ground and their Doppler shift is much smaller than that of satellites in medium Earth orbit. The search width is then dominated by the receiver's own oscillator error: a 1 ppm reference at 1176.45 MHz is off by up to about 1.18 kHz. With a good reference and a narrower ±2 kHz search, the same grid needs only 9 Doppler bins instead of 21, cutting acquisition work by more than half. A satellite-specific search range is a firmware decision that changes how hard the hardware has to work.

Tracking: hardware correlators, firmware loops

Once acquired, each satellite is assigned to a tracking channel. A channel generates the local carrier and code, wipes the carrier off the incoming samples, and correlates against early, prompt and late copies of the code. Counting two real MACs (I and Q) per correlator per sample, that is 3 × 2 × 4092 = 24,552 MACs per millisecond per channel, about 24.6 million per second. Twelve channels need roughly 295 million MACs per second, running continuously on every sample.

That inner part goes in hardware, for the same reason as acquisition. But look at what the correlators produce: one set of early, prompt and late I/Q sums per channel per millisecond. The tracking loops that consume them, a delay-locked loop for the code and a phase- or frequency-locked loop for the carrier, run once per integration period. At 1 kHz for twelve channels, that is 12,000 loop updates per second, each a discriminator and a small filter of perhaps a few hundred instructions. A microcontroller-class core handles that comfortably.

Putting the loops in firmware is valuable, not just possible. Loop bandwidths, discriminator types, integration times, and the logic for detecting loss of lock and re-acquiring are where receiver designers keep experimenting. In firmware they can change after tape-out; in hardware they cannot.

Decoding and the navigation solution

Data decoding runs at the navigation symbol rate, tens to hundreds of symbols per second per satellite. Symbol synchronisation, forward error correction decoding, frame synchronisation and parity checks are well within the reach of firmware. A design might add a small hardware decoder if many channels and several systems must be decoded at once on a very slow core, but that is an optimisation, not a necessity.

The navigation solution runs at the output rate, typically one to ten times a second. It solves a small least-squares or Kalman filter problem with four unknowns (position and clock bias) or more. The arithmetic is floating point or wide fixed point with matrix operations and many special cases (satellite selection, ionospheric correction, integrity checks), which is software's natural territory. A core with a floating-point unit helps here more than any accelerator would.

The resulting partition

Function Rate Where
Sample handling, carrier and code generation Every sample (MHz) Hardware
Acquisition search Millions of correlations per attempt Hardware engine, driven by firmware
Tracking correlators Every sample, per channel Hardware
Tracking loops, lock detection About 1 kHz per channel Firmware
Data decoding Symbol rate Firmware (optional hardware assist)
Position, velocity and time 1 to 10 Hz Firmware

The interface between the two halves is a set of channel registers: firmware writes code and carrier numerically controlled oscillator settings, and reads correlator sums once per integration, usually triggered by an interrupt or collected by DMA. Defining that interface carefully, including timestamps that tie each measurement to the receiver's clock, is as important as either side.

Common mistakes

  • Putting tracking loops in hardware. It freezes the most tuned part of the design at tape-out.
  • Underestimating the correlator interrupt load. One interrupt per channel per millisecond adds up; batch the readout.
  • Sizing for one system only. Adding a second band or system later multiplies channels and correlators.
  • Ignoring the oscillator. Its error and stability drive the acquisition search width and loop design.

Try it yourself

  1. In Python with numpy, generate a 1023-chip spreading code, delay it, add a Doppler shift and noise, and write an FFT-based acquisition that finds the delay and Doppler.
  2. Add a second-order phase-locked loop and a delay-locked loop that update once per simulated millisecond and track a slowly changing Doppler.
  3. Count the multiply-accumulates in your Python model per simulated second and compare them with the estimates above.
