Gesture recognition from an IMU: data, features and a small model

Edge AI Intermediate 27 Nov 2026 6 min read By Ketuna

From recording wrist or handheld gestures to running a classifier on a microcontroller - defining classes, windowing six-axis motion data, compact features, a tiny network and the streaming loop on the device.

In this article
  1. Define the gestures and the "none" class
  2. Record and label
  3. Windows and features
  4. A small model
  5. Running it on the device
  6. Try it yourself

A six-axis inertial measurement unit (IMU), an accelerometer plus a gyroscope, costs little and draws little power, and it is enough to recognise a handful of deliberate hand gestures: a flick, a twist, a circle, a shake. That makes it a good first end-to-end edge AI project, because every stage is small enough to understand completely: you record your own data, design features you can reason about, train a model of a few hundred weights and run it on a microcontroller in real time. The steps below follow that path and point out where such projects usually go wrong.

Define the gestures and the "none" class

Start on paper. Pick three to five gestures that are physically distinct: different axes, different directions, different rhythms. "Flick up" and "flick down" differ only in sign and are easy; "draw a 2" and "draw a Z" are much harder.

Then add the most important class: none. In real use, the device spends almost all its time seeing motion that is not a gesture: walking, typing, picking up a cup. A model trained only on the gestures has no way to say "nothing happened", so it will label every movement as one of them. Recording plenty of ordinary activity as none is what makes the system usable.

Write a short protocol for each gesture: start position, how fast, how large, which hand, how the device is held. Variation is good, but it should be the variation users will produce, not confusion about what the gesture is.

Record and label

Sample the IMU at a fixed rate; 100 Hz is ample for hand motion. Record each gesture many times, by several people, across sessions on different days, with the device worn or held the way the product will be. Labelling is easiest if the recording tool marks gestures as they happen, for example with a button press or a prompt that tells the subject when to perform the gesture.

Keep the raw data and the labels in simple files (CSV is fine) with the sensor settings, the person and the session recorded alongside. You will want to re-cut windows and recompute features many times, and you cannot do that from features alone.

Windows and features

A gesture takes roughly a second, so the model looks at a window of motion, for example 1.5 s (150 samples at 100 Hz). To catch gestures whenever they happen, windows slide forward with a hop of, say, 0.25 s, so consecutive windows overlap.

You can feed the raw window, 150 × 6 numbers, to a small 1-D convolutional network. For a first version, compact hand-designed features are simpler and often enough. For each of the six axes, compute the mean (which captures orientation relative to gravity), the standard deviation (how much it moved), the minimum and maximum (direction and size of the peak), and the mean absolute difference between samples (how jerky the motion was). That gives 6 × 5 = 30 numbers per window.

import numpy as np

FS, WIN, HOP = 100, 150, 25          # 100 Hz, 1.5 s windows, 0.25 s hop

def windows(rec):
    """rec: (n_samples, 6) array of ax, ay, az, gx, gy, gz."""
    for start in range(0, len(rec) - WIN + 1, HOP):
        yield rec[start:start + WIN]

def features(w):
    d = np.diff(w, axis=0)
    return np.concatenate([w.mean(0), w.std(0), w.min(0), w.max(0),
                           np.abs(d).mean(0)])           # 30 values

Before training, split by person or session, not by window. Overlapping windows from one recording on both sides of the split would leak test data into training and inflate your score. Then compute feature normalisation (mean and standard deviation per feature) on the training set only and apply it everywhere.

A small model

With 30 inputs and, for example, 4 gestures plus none, a dense network of 30 → 16 → 5 with ReLU is a sensible starting point. It has 30 × 16 + 16 × 5 = 560 weights and 21 biases, about 644 bytes in int8 with int32 biases, and 560 MACs per inference. On any microcontroller that is a few microseconds to tens of microseconds; the feature computation will cost more than the network.

Train it in PyTorch or Keras on the training split, check per-class results on the validation split, and look at the confusion matrix: which gestures get confused with each other, and how often none is mistaken for a gesture. False triggers usually matter more to users than occasional misses, so tune for that. Then quantize to int8 and check that the quantized model's results on the test split are close to the float model's.

Before committing to the network, it is worth building a rule-based version too, such as "flick up if peak vertical acceleration exceeds a threshold and gyro roll stays small". If the rules perform almost as well, they are easier to explain, tune and test. The model earns its place when gestures differ in ways that are hard to write as rules.

Running it on the device

On the microcontroller the pipeline streams:

  1. A timer or the IMU's data-ready interrupt reads six values at 100 Hz into a circular buffer of the last 150 samples.
  2. Every 25 samples (0.25 s), the main loop computes the 30 features over the buffer, normalises them with the stored training statistics, and quantizes them with the model's input scale and zero point.
  3. The network runs and produces five scores.
  4. A decision rule requires the same gesture to win in two consecutive windows, above a threshold, and then ignores further detections for about a second so one gesture does not fire repeatedly.

The features can be computed incrementally (running sums for the mean and variance) to save cycles, but compute them in the simplest way first and check them against the Python output on the same recorded data, value by value. Feature mismatches between training and device are the most common cause of a model that works on the laptop and fails on the board.

Common mistakes:

  • no none class, so ordinary movement triggers gestures
  • recording one person in one session and testing on the same person
  • splitting windows randomly, which leaks overlapping data into the test set
  • device features that differ subtly from training features, for example in units or axis order

Try it yourself

  1. Log six-axis IMU data at 100 Hz from a phone app or a development board to CSV, with a button or keypress marking each gesture.
  2. Use the windowing and feature code above, train the 30 → 16 → 5 network, and report per-class recall with a person-wise split.
  3. Write the rule-based alternative for one gesture and compare it with the model on the same test data.
  4. Port the feature code and an int8 dense layer to C, run them on recorded data on your PC, and confirm the outputs match Python before flashing a board.
