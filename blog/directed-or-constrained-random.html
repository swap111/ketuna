Directed tests or constrained random? Using each where it pays off

Verification Beginner 27 Nov 2026 6 min read By Ketuna

Directed tests pin down the corners you know about; constrained random stimulus explores the ones you did not imagine. Learn when to use each, how to bias random towards corners, and why seeds matter.

Every testbench has to answer one question before it checks anything: what inputs do we send? There are two broad answers. A directed test sends a sequence you chose by hand to provoke a specific behaviour. A constrained random test lets the computer pick inputs from a set of legal values you describe. Students often treat these as rival schools. In practice every serious verification effort uses both, because each is strong exactly where the other is weak.

What directed tests are good at

A directed test encodes a known concern. "Reset in the middle of a transfer." "Write to the FIFO on the same cycle it becomes full." "Add 0x7F and 0x01 and check the overflow flag." You know the exact corner, so you write the exact stimulus and the exact expected result.

Directed tests are:

  • Cheap to understand. A reviewer reads the test and sees what it proves.
  • Fast to hit rare cases. One test gets you straight to a corner that might take random stimulus a very long time to reach.
  • Good as regression anchors. Once a bug is found, a directed test that reproduces it guarantees it never returns.

Their weakness is that they test only what you thought of. Bugs, by definition, often live where nobody thought to look: two features interacting, an event on an unusual cycle, an odd ordering of operations.

What random stimulus is good at

Constrained random stimulus explores combinations you did not list. You describe the legal input space ("address is one of four registers, data is any 32-bit value, a write is followed by a read about half the time") and the generator samples from it. Run enough samples and you reach interleavings no one wrote down.

Random stimulus needs two partners to be useful:

  1. A self-checking reference. You cannot hand-write the expected output for a random input, so a model or scoreboard must compute it.
  2. Coverage. Random tests do not tell you what they exercised. Coverage counters tell you whether the interesting cases actually happened.

The arithmetic of rare corners

Consider an 8-bit ALU with two operands, so 65,536 operand pairs. Suppose one bug only shows when both operands are 0xFF. Uniform random stimulus hits that pair with probability 1/65,536 per vector. The chance of hitting it at least once in N vectors is 1 − (1 − 1/65,536)N:

Vectors N Chance of hitting 0xFF, 0xFF at least once
1,000 about 1.5%
10,000 about 14%
65,536 about 63%
200,000 about 95%

For an 8-bit ALU the honest answer is to test all 65,536 pairs exhaustively. But widen the operands to 32 bits and exhaustive testing is impossible, while uniform random almost never lands on all-ones or on the boundary values that matter. That is why random stimulus must be constrained and biased, not uniform.

Biasing random towards corners

A good generator spends a share of its samples on values you suspect are special and the rest on the whole range. Here is a sketch in Python, as you would use in a cocotb test.

import random

CORNERS = [0x00, 0x01, 0x7F, 0x80, 0xFE, 0xFF]

def operand(rng):
    """Mostly corner values, sometimes anything."""
    if rng.random() < 0.3:
        return rng.choice(CORNERS)
    return rng.getrandbits(8)

def make_vectors(seed, n):
    rng = random.Random(seed)       # private generator, fixed seed
    return [(operand(rng), operand(rng)) for _ in range(n)]

print(make_vectors(seed=1234, n=3))

With 30% of each operand drawn from six corner values, the chance that both operands are 0xFF on one vector is (0.3 × 1/6)2 = 0.0025, plus a tiny contribution from the uniform part. That is about 1 in 400 instead of 1 in 65,536, and the remaining 70% of samples still roam the full range. The weights here are illustrative; you choose them from your plan and adjust them when coverage shows a hole.

Constraints also keep stimulus legal. If the protocol forbids a read while a write is pending, the generator must never produce one; otherwise every "failure" it finds is a testbench bug, and the team stops trusting the results.

Seeds make random reproducible

Random does not have to mean unrepeatable. A pseudo-random generator started from the same seed produces the same sequence every time. That gives you two habits:

  • Print the seed at the start of every run. cocotb prints the seed it gives Python's global random module and lets you set it through an environment variable (COCOTB_RANDOM_SEED in cocotb 2.x, RANDOM_SEED in older releases); if you create your own generator, as in the sketch above, print its seed too.
  • Rerun a failure with its seed. A failing nightly run is useless if you cannot reproduce it. With the seed you get the same stimulus and the same failure on your own machine.

Use a private random.Random(seed) object instead of the module-level functions when several components draw random numbers. Then adding a new random call in one component does not shift the sequence seen by another, and old seeds keep reproducing old failures for longer.

A practical split

A sensible small project ends up with roughly this shape:

  • Directed tests for reset values, each documented corner in the plan, and every bug ever fixed
  • Constrained random tests with a self-checking model, run with many seeds, for the bulk of the state space
  • Coverage to decide when the random runs have done enough, and to point at holes that a new directed test or a new constraint should close

The order matters too. Write a directed smoke test first: it proves that the clock, reset and basic path work, so that random failures later mean something.

Try it yourself

  1. Write an 8-bit adder with a carry output and a cocotb test that checks it exhaustively over all 65,536 pairs on Icarus Verilog.
  2. Widen it to 32 bits, replace the exhaustive loop with the biased generator above, and count how often each corner value appears in 10,000 vectors.
  3. Seed a deliberate bug that only triggers when both operands are all-ones, and compare how many vectors uniform and biased stimulus need to find it.
  4. Rerun the failing case with the printed seed and confirm the same vector fails.
