Contributing to open-source hardware and EDA projects

Careers & skills Advanced 27 Nov 2026 6 min read By Ketuna

How to make a first useful contribution to an open-source EDA tool or hardware project: pick a suitable issue, reproduce it, write a focused change with a test, and work with maintainers patiently.

In this article
  1. Choosing where to start
  2. Reproduce before you touch anything
  3. Writing a focused change
  4. Working with maintainers
  5. Common mistakes
  6. Try it yourself

The open-source silicon flow, from Yosys and Verilator to OpenROAD, Magic, KLayout and the open PDKs, is maintained by small groups of people with more issues than time. A good contribution helps them, deepens your understanding of a tool you rely on, and leaves a public record of engineering work that anyone can inspect. A poor one costs a maintainer an evening and gets closed. The difference is almost entirely in how you approach it, not in how clever the code is.

Choosing where to start

Start with a tool you already use. You know its behaviour, you have hit its rough edges, and you can judge whether a change is an improvement. Contributing to a project you have never run is guesswork.

Within that project, look for work that is small, well defined and wanted:

  • Issues labelled for newcomers, if the project uses such labels
  • Bugs you hit yourself and can reproduce reliably
  • Documentation that was wrong or missing when you needed it
  • Missing regression tests for behaviour that is already correct
  • Error messages that confused you and could say what went wrong

Avoid large features as a first contribution, and avoid anything that changes a core data structure or an output format other tools depend on. Those need design discussion with maintainers, and a newcomer rarely has the context to get them right. Before writing code, read the contributing guide, the code of conduct and a handful of recently merged pull requests. They show you the expected style, test layout and level of detail in descriptions, which is often stricter than the written guide.

Reproduce before you touch anything

A bug report from a stranger is a hypothesis. Your first job is to turn it into a fact on your own machine, with a build of the current main branch, not the packaged version you installed months ago.

Then shrink it. EDA bugs often arrive attached to a large design. Cut the input down until any further removal makes the bug disappear: delete modules, remove ports, simplify expressions, drop constraints. For synthesis and simulation tools, a test case of ten to twenty lines of Verilog is common and is far easier for everyone to reason about. Write down the exact command, tool version and commit hash. A note on the issue might look like this (an invented example, not a real bug):

Reproduced on main @ <commit>, built from source.

Input (min.v, 12 lines, attached).
Command:
  yosys -p "read_verilog min.v; synth -top top; stat"

Expected: one $_DFF_P_ cell; output follows input
          one cycle later.
Observed: no flip-flop; output tied to constant 0.

Removing the reset branch makes it pass, so the
problem seems to be in how this reset pattern is
handled. Investigating; happy to take this issue.

Posting a minimal reproduction on the issue is itself a valuable contribution, even if you never write the fix. It also tells others you are working on it, which avoids two people fixing the same bug.

Writing a focused change

Find the cause, not just a place where a patch makes the symptom vanish. In a large tool this means reading code you did not write, adding temporary debug output and following the data. The project's own test suite and history help: git log -p on the file you suspect, and git blame on the suspicious lines, often show why the code looks the way it does. Look for the commit that introduced the behaviour; if a passing older version exists, git bisect can find it.

When you understand the cause, make the smallest change that fixes it properly. A focused pull request:

  • Fixes one thing; unrelated cleanups go in a separate PR
  • Follows the existing code style, even where you would choose differently
  • Adds a regression test that fails before your change and passes after it
  • Runs the project's full test suite locally, not only your new test
  • Explains in the description what was wrong, why, how you fixed it, and how you tested it

The regression test matters most. Maintainers can review a three-line fix with a test confidently. They cannot review a three-line fix without one, because they have no evidence that it works or that it will keep working.

If you used an AI assistant to help understand the code or draft the fix, check its output as carefully as your own and follow the project's policy on AI-assisted contributions where it has one. Some projects ask contributors to disclose it.

Working with maintainers

Maintainers are often volunteers or are paid to work on other parts of the project. Reviews may take days or weeks. Be patient, and make each review cycle easy for them.

  • Respond to every review comment, either with a change or a short reason
  • Push follow-up commits rather than rewriting history mid-review, unless the project asks for squashed or rebased branches
  • Keep CI green; fix failures before asking for another look
  • Accept "no" gracefully. A maintainer may decline a correct change because it does not fit the project's direction, and they will have to support it long after you have moved on
  • After a quiet spell of a week or two, one polite reminder is fine; repeated pings are not

Disagreements happen. Argue with evidence, such as a test case, a reference to a standard or a measurement, not with persistence. If a maintainer explains a design constraint you did not know, that knowledge is part of what you came for.

Common mistakes

  • Opening a large PR without discussion. Ask on the issue first whether the approach is welcome.
  • Fixing against an old release. The bug may already be fixed on main, or the code may have moved.
  • Mixing formatting changes with logic changes. The diff becomes unreadable and the review stalls.
  • No test. It forces the maintainer to write one or to trust you blindly.
  • Disappearing. An abandoned PR is worse than none; if you cannot finish, say so on the PR.

Try it yourself

  1. Build one open-source tool you use from source, for example Yosys or Verilator, following its README, and run its test suite.
  2. Browse its open issues and pick one you can reproduce. Shrink the input to a minimal case and post it on the issue with the exact commit and command.
  3. Find a small documentation gap or a missing test in the same project and open a pull request for it, following the contributing guide exactly.
  4. Read three recently merged pull requests end to end, including review comments, and note what reviewers asked for that the authors had not provided.
