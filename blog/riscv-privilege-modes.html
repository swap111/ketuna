Machine, supervisor and user mode: why RISC-V has privilege levels

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

What machine, supervisor and user mode may each do, which kinds of systems need which combination, and how traps, delegation and the return instructions move execution between them.

In this article

  2. Which systems need which modes
  3. How traps move between levels
  4. Common mistakes
  5. Try it yourself

On a tiny sensor node, all the code runs with full access to the hardware, and that is fine: one team wrote all of it and it does one job. On a smart meter or a phone, some code must not be able to touch the key storage, reprogram the clock or read another application's memory. Privilege levels are the hardware mechanism that makes that separation enforceable rather than a convention. RISC-V defines three of them and lets a core implement only the ones its product needs.

Three levels, three jobs

  • Machine mode (M) is the most privileged and the only mandatory level. Code in M-mode can access every CSR and all of physical memory (subject only to locked protection entries). Every trap starts life aimed at M-mode. On a simple microcontroller, M-mode is where everything runs.
  • Supervisor mode (S) is for an operating system kernel. It has its own set of CSRs (sstatus, stvec, sepc, scause, satp and others) and controls virtual memory through page tables. It cannot touch machine-level CSRs.
  • User mode (U) is for applications. It can execute ordinary instructions and access the memory it has been given, and nothing else. Any attempt to read a privileged CSR or touch protected memory raises an exception that a more privileged level handles.

The current level is not visible in any user-readable register. It lives inside the core and changes only on a trap (up) or a return instruction (down).

Which systems need which modes

The specification allows three common combinations, and each matches a class of product:

Modes Typical system Why
M only Small microcontroller, bare metal or a simple RTOS One trust domain; no need to pay for separation
M + U Secure embedded device, RTOS with protected tasks Keeps application code away from drivers and keys, without virtual memory
M + S + U Linux-class processor The kernel needs virtual memory and its own trap handling; firmware stays below it

In an M + U system, protection comes from physical memory protection (PMP) rather than page tables. M-mode code programs a small number of PMP entries, each describing a region and its read, write and execute permissions for lower levels. User code that steps outside its regions gets an access fault.

For example, to give U-mode read and write access, but not execute, to a 64 KiB buffer at 0x2000_0000, you can use one PMP entry in naturally aligned power-of-two (NAPOT) mode. The address register holds the base and size together: (base + size / 2 − 1) >> 2 = (0x2000_0000 + 0x8000 − 1) >> 2 = 0x0800_1FFF. The configuration byte has R = 1 and W = 1 (bits 0 and 1), X = 0, and the address-matching field set to NAPOT (value 3 in bits 4 to 3), giving 0x1B.

static inline void pmp_buffer_rw(void)
{
    __asm__ volatile ("csrw pmpaddr0, %0" :: "r"(0x08001FFFu));
    __asm__ volatile ("csrw pmpcfg0,  %0" :: "r"(0x1Bu));
}

Real firmware usually reads, modifies and writes pmpcfg0 so it does not disturb the other three entries packed in the same register, and adds further entries for code and peripherals. Remember that on a core that implements PMP, U-mode accesses that match no entry fail, so U-mode needs explicit entries for everything it uses.

How traps move between levels

By default, every trap, from any level, goes to M-mode. That is simple but wasteful in a Linux system: a page fault in a user program is the kernel's business, and bouncing it through firmware costs time. So M-mode can delegate selected exceptions and interrupts to S-mode using two CSRs, medeleg and mideleg. A delegated trap taken from U-mode or S-mode goes to stvec, updates sepc, scause and sstatus, and the kernel returns with sret. A trap is never delegated to a lower level than the one it was taken in.

The ecall instruction is the deliberate way to ask a higher level for a service, and its cause code says where it came from: 8 for an ecall from U-mode, 9 from S-mode, 11 from M-mode. A user program's system call arrives in the kernel as cause 8 (delegated). The kernel's own call to firmware, for example to set a timer or start another hart, arrives in M-mode as cause 9. The interface for those kernel-to-firmware calls is standardised as the RISC-V Supervisor Binary Interface (SBI), and OpenSBI is a widely used open-source implementation of the M-mode side.

Going down is the job of mret and sret. Each restores the PC from its exception PC register and the privilege level from the saved previous-privilege field (MPP or SPP). That is also how a system starts a lower level for the first time: M-mode code sets MPP to U or S, writes the entry address into mepc, and executes mret. There is no other instruction that lowers privilege.

Common mistakes

  • Assuming S-mode exists. Many microcontroller cores implement only M, or M and U; check before porting code that touches s* CSRs.
  • Forgetting PMP entries for U-mode code. With PMP active, U-mode cannot even fetch its own instructions without an entry allowing execute.
  • Delegating everything. Some traps, such as those signalling firmware-level faults, must stay in M-mode.
  • Treating privilege as security by itself. Separation only helps if the more privileged code validates what lower levels ask it to do.

Try it yourself

  1. Write a bare-metal M-mode program that configures one PMP region, sets MPP to U, and uses mret to jump to a user function. Run it on QEMU's virt machine.
  2. From the user function, read mstatus with csrr and confirm that you get an illegal-instruction trap (mcause = 2) in your M-mode handler.
  3. Make the user code call ecall and check that mcause is 8; then access memory outside the PMP region and check for a load or store access fault.
