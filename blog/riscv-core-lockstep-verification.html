Verifying a RISC-V core against a reference model in lockstep

Verification Advanced 27 Nov 2026 5 min read By Ketuna

Compare a core's architectural state with an instruction set simulator after every retired instruction, and handle the hard parts - traps, interrupts, counters and device reads - without false mismatches.

Self-checking test programs tell you that a processor got the right answer at the end. They do not tell you where it first went wrong, and they cannot catch an error that a later instruction happens to overwrite. Lockstep comparison does both. An instruction set simulator (ISS) executes the same program alongside the RTL, and after every instruction the core retires, the testbench compares the architectural effects. The first mismatch names the exact instruction, its program counter and the register that differs. The idea is simple; making it robust against traps, interrupts and non-deterministic state is where the engineering lies.

What gets compared

The comparison is at the level of the instruction set architecture, not the microarchitecture. A pipelined core with forwarding and a single-cycle ISS look nothing alike inside, but every retired instruction must have the same architectural effect in both:

  • the program counter of the instruction, and the instruction word
  • the destination register and the value written, if any
  • for stores, the address, data and byte mask
  • for traps, the cause, the faulting PC and the new PC
  • selected control and status registers (CSRs) after instructions that change them

The retirement interface

The RTL side needs a clean way to report what it retired. Add a set of monitor-only output signals at the writeback stage: a valid bit per retired instruction, plus the PC, instruction word, destination register, write data, memory access details and trap information. The riscv-formal project defines an open interface of this kind (RVFI), and following it, or something close, means your core can also be used with formal checking tools that understand it.

The interface must report retirement, not issue. Instructions flushed by a branch misprediction or a trap never retire and must never appear. Getting this signal right is itself a useful check of the pipeline's flush logic.

The comparison loop

Here is the core of a lockstep checker. The RTL monitor produces one record per retired instruction, and the ISS is stepped once per record.

def lockstep(rtl_records, iss, max_report=1):
    """Compare RTL retire records with an ISS stepped in lockstep."""
    for n, r in enumerate(rtl_records):
        if r.intr_taken:                       # see the interrupt section
            iss.take_interrupt(r.intr_cause)
        e = iss.step()                         # executes one instruction
        diffs = []
        for field in ("pc", "insn", "rd", "rd_wdata", "trap"):
            if getattr(r, field) != getattr(e, field):
                diffs.append(f"{field}: rtl={getattr(r, field):#x} "
                             f"iss={getattr(e, field):#x}")
        if r.rd == 0 and r.rd_wdata != 0:
            diffs.append("write to x0 reported with non-zero data")
        if diffs:
            raise AssertionError(
                f"mismatch at retire #{n}, pc={r.pc:#010x}: " +
                "; ".join(diffs))
    return n + 1

Comparing the PC first, before the data, matters. If the PCs differ, the two models have taken different paths, and every later difference is a consequence. The first PC mismatch usually points at a branch, jump or trap.

Traps, interrupts and other false mismatches

Traps: synchronous and deterministic

Exceptions such as illegal instructions, misaligned accesses and environment calls are caused by the instruction itself. The ISS will raise the same trap on the same instruction if both models implement the specification the same way. Compare the trap cause, the saved exception PC, and the PC of the next instruction retired, which should be the trap handler's entry.

Two details commonly cause mismatches. First, decide how a trapping instruction appears in the trace: as a retired record with a trap flag, or not at all. Both models must agree. Second, some behaviour is legitimately implementation-defined, such as whether misaligned loads trap or are handled in hardware. Configure the ISS to match your core's documented choices.

Interrupts: asynchronous and not predictable

An external interrupt arrives when the testbench raises a pin, at a moment that depends on pipeline timing. The ISS, which has no pipeline, cannot know at which instruction boundary the RTL will take it. Trying to predict it produces endless false mismatches.

The standard solution is to let the RTL decide and make the ISS follow. The retirement record carries a flag saying "an interrupt was taken before this instruction", with its cause. The checker tells the ISS to take the same interrupt at the same point, as the loop above does, and then compares as usual. The ISS still checks that the interrupt was allowed, for example that it was enabled and not masked, so a core that takes interrupts while they are disabled is still caught.

Other sources of false mismatches

Some state differs between models for legitimate reasons:

  • Cycle and time counters. mcycle and time depend on pipeline timing. Either skip comparison for instructions that read them, or copy the RTL's value into the ISS when they are read.
  • Device reads. A load from a memory-mapped peripheral returns whatever the peripheral holds, which the ISS does not model. Feed the RTL's load data into the ISS for addresses in device regions, and compare only addresses and sizes.
  • Unspecified values. Some fields have no defined value after certain events. Compare them only where the specification defines them.

Each of these exceptions should be narrow and documented. A broad "ignore all CSRs" rule makes the checker quiet and blind.

Choosing programs

Lockstep makes any program a test, because the checking comes from the comparison, not from the program. Use the official instruction-group tests for coverage of each instruction, random instruction-sequence generators for interleavings no one wrote by hand, and real software such as a small operating system boot for long, realistic sequences.

Try it yourself

  1. Add retirement monitor signals to a simple RV32I core (your own, or an open-source teaching core), reporting PC, instruction, destination register and write data.
  2. Write a small RV32I ISS in Python and drive it from a cocotb test with the loop above. (An open-source ISS such as Spike can log every committed instruction instead; comparing that log with the RTL's retire log offline is a simpler first step than true lockstep.)
  3. Assemble a test program with the RISC-V GNU toolchain, run it on Icarus Verilog in lockstep, and confirm it completes with no mismatches.
  4. Plant a bug in the core, such as a wrong sign extension on one load type, and check that the first mismatch names the faulty instruction's PC.
