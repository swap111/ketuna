Designing a centre-aligned PWM block with dead time for a BLDC controller

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

Build a centre-aligned PWM from an up/down counter, insert dead time so the high and low switches of a half-bridge are never on together, and update the duty cycle without glitches.

A brushless DC (BLDC) motor is driven by three half-bridges, each a high-side and a low-side power switch in series across the supply. A PWM block decides, many thousands of times a second, which switch is on. Two details separate a PWM block that works on a bench LED from one that can drive a power stage: centre alignment, which keeps the switching edges of the three phases apart, and dead time, which stops both switches of one leg from conducting at once. Both are simple to build in RTL once you see what they are for.

Edge-aligned vs centre-aligned

An edge-aligned PWM uses a counter that counts up and wraps. Every phase's output turns on at the wrap, so all three legs switch at the same instant each period. That concentrates current transients and electrical noise at one moment, and it makes the effective voltage ripple worse.

A centre-aligned PWM uses an up/down counter that rises from 0 to TOP and falls back to 0. Each output is high while the counter is below that phase's compare value. Because the counter is symmetric, each pulse is centred on the counter's valley, and phases with different duty cycles switch at different times. The pulses are also symmetric in time, which simplifies sampling motor currents at a known point in the period, typically the centre.

The cost is that a full period takes 2 × TOP clock cycles instead of TOP, so for a given clock the PWM resolution is halved.

Choosing TOP

For a 20 kHz PWM from a 50 MHz clock, numbers chosen for illustration:

TOP = fclk / (2 × fpwm) = 50,000,000 / 40,000 = 1250

The duty cycle is then duty / TOP, in steps of 1/1250, which fits in an 11-bit register. 20 kHz is a common choice because it sits at or above the upper limit of human hearing, so the motor windings do not whine audibly; the right frequency for a real drive depends on the motor, the switches and the losses, and is a system decision.

Why dead time is necessary

Power transistors do not switch instantly, and turning one off often takes longer than turning one on, partly because charge must be removed from its gate. If the controller turns the high side off and the low side on in the same clock cycle, there is an interval in which both conduct. That connects the supply straight to ground through two transistors, a condition called shoot-through, which wastes power at best and destroys the switches at worst.

Dead time is a short interval after one switch turns off and before the other turns on, during which both are off. Its length comes from the power devices' and gate driver's datasheets, plus margin; take it from the hardware designer, never guess it. Assume 500 ns here for illustration, which is 25 cycles at 50 MHz.

The RTL

module pwm_ca #(parameter int W = 11) (
  input  logic         clk, rst_n,
  input  logic [W-1:0] top,       // half-period in cycles
  input  logic [W-1:0] duty_in,   // written by firmware at any time
  input  logic [W-1:0] dead,      // dead time in cycles
  output logic         hi, lo     // gate commands for one leg
);
  logic [W-1:0] cnt, duty, dt_cnt;
  logic         up, pwm, pwm_q;

  // up/down counter with a shadow duty register loaded at the peak
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      cnt <= '0; up <= 1'b1; duty <= '0;
    end else if (up) begin
      if (cnt == top) begin
        up <= 1'b0; cnt <= cnt - 1'b1;
        duty <= duty_in;             // safe point: output is low
      end else cnt <= cnt + 1'b1;
    end else begin
      if (cnt == '0) begin up <= 1'b1; cnt <= cnt + 1'b1; end
      else cnt <= cnt - 1'b1;
    end

  assign pwm = (cnt < duty);

  // dead-time insertion: both off for 'dead' cycles after any change
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      pwm_q <= 1'b0; dt_cnt <= '0; hi <= 1'b0; lo <= 1'b0;
    end else begin
      pwm_q <= pwm;
      if (pwm != pwm_q) begin
        hi <= 1'b0; lo <= 1'b0; dt_cnt <= dead;
      end else if (dt_cnt != '0) begin
        dt_cnt <= dt_cnt - 1'b1;
      end else begin
        hi <= pwm_q; lo <= ~pwm_q;
      end
    end
endmodule

The outputs hi and lo come straight from flops, so they cannot glitch. Every change of pwm forces both off first and only then turns on the new side, so the two are never high in the same cycle.

Glitch-free duty updates

Firmware writes duty_in whenever its control loop finishes, at an arbitrary point in the period. If the comparator used that value directly, a write in the middle of a pulse could create an extra edge or a pulse that is too short or too long. The shadow register duty copies duty_in only at the counter's peak, where the output is low for any duty below 100 %. Each period therefore uses one consistent compare value. Three phases sharing the counter all update at the same peak, so the motor sees a coherent new voltage vector.

Pitfalls

  • Dead time eats pulse width. The high side is on for the PWM pulse minus the dead time, so small duty cycles shrink or vanish, and the average voltage is slightly lower than commanded. Control software often compensates for this.
  • Minimum pulse width. A pulse shorter than the dead time never turns either switch on in this design. That is safe, but it creates a dead zone near 0 % and 100 % duty.
  • Reset and fault states. Both outputs must be off in reset and when a fault input is asserted. In a real controller, a hardware fault input that forces both off without waiting for software is standard.
  • Safety. Motor drives involve high currents and, often, high voltages. Test new PWM logic on a low-voltage, current-limited setup first, and have anyone working on a mains-powered drive supervised by someone qualified.

Try it yourself

  1. Simulate pwm_ca in Icarus Verilog with small values (for example top = 20, dead = 2) and check in GTKWave that the pulse is centred and the gaps appear on both edges.
  2. Add an assertion that hi && lo is never true, and run it in simulation and with SymbiYosys to prove it for all inputs.
  3. Change duty_in at random cycles in the testbench and confirm that each period's pulse width matches the value held at the previous peak.
