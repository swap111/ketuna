Timers in practice: PWM output, input capture and the prescaler arithmetic

Embedded systems Beginner 27 Nov 2026 5 min read By Ketuna

How a hardware timer turns a clock into PWM and pulse measurements, how to pick prescaler and period values for a target frequency and resolution, and how to measure a pulse that spans a counter wrap.

Dimming an LED, driving a servo, spinning a fan and reading an ultrasonic range sensor all use the same peripheral: a hardware timer. It is a counter with a few comparators attached, and nearly everything it does follows from two numbers you choose, the prescaler and the period. Getting those numbers right is simple arithmetic, but there is a "+1" in it that catches almost everyone once.

The counter and its two dividers

A typical timer takes its input clock, divides it by a prescaler, and uses the result to increment a counter. When the counter reaches the period value (often called the auto-reload value, ARR), it wraps to zero and starts again. Each wrap is an update event, which can raise an interrupt.

Most timers store "value minus one" in both registers, so a prescaler register of 0 means divide by 1 and a period register of 999 means 1000 counts. The update frequency is therefore:

fupdate = fclk / ((PSC + 1) × (ARR + 1))

Check your part's reference manual, because a few timers store the plain value. Writing the formula with the "+1" every time, and checking it against the manual once, avoids an error that is small enough to miss on a scope and large enough to break a protocol.

PWM: one compare register more

For pulse-width modulation, the timer compares the counter with a compare register (CCR). In the common edge-aligned mode, the output is high while the counter is below CCR and low after it:

duty cycle = CCR / (ARR + 1)

The period also sets the resolution: ARR + 1 counts per period means ARR + 1 possible duty values. For a fixed timer clock, a higher PWM frequency leaves fewer counts per period. That is the main trade-off in every PWM design.

Choosing PSC and ARR

Assume a 48 MHz timer clock; the number is made up for illustration.

A 20 kHz motor or fan PWM (above the audible range). With PSC = 0, ARR + 1 = 48,000,000 / 20,000 = 2400, so ARR = 2399. That gives 2400 duty steps, about 11.2 bits of resolution. Any larger prescaler would only reduce the resolution, so for PWM you usually want the smallest prescaler that keeps ARR within the counter's range.

A 50 Hz hobby-servo signal. A servo reads a pulse between roughly 1 and 2 ms in a 20 ms frame. The direct way is PSC = 47, giving a 1 MHz tick, and ARR = 19,999. Now CCR is the pulse width in microseconds: CCR = 1500 means 1.5 ms. The alternative PSC = 14 gives a 3.2 MHz tick and ARR = 63,999, which uses the full 16-bit range for finer steps. Both are correct; choose readable units unless you need the extra resolution.

A small script avoids mistakes when the numbers are less round:

def psc_arr(f_clk, f_target, max_count=65536, tol=1e-3):
    """Smallest prescaler (most PWM steps) that hits f_target."""
    for psc in range(65536):
        steps = round(f_clk / ((psc + 1) * f_target))
        if steps < 2:
            break
        if steps > max_count:
            continue
        f = f_clk / ((psc + 1) * steps)
        if abs(f - f_target) / f_target < tol:
            return psc, steps - 1, f
    return None

print(psc_arr(48e6, 20_000))   # (0, 2399, 20000.0)
print(psc_arr(48e6, 50))       # (14, 63999, 50.0)

If no exact pair exists, the function returns nothing, which is your cue to accept a small frequency error or change the clock.

Updating the duty cycle without glitches

If firmware writes a new CCR in the middle of a period, and the counter has already passed the new value, the output can miss a transition and produce one wrong-length pulse. Timers solve this with preload (shadow) registers: writes go to a buffer that is copied into the active register only at the next update event. Enable preload for CCR and ARR, and force one update after configuration so the first period starts with your values.

Input capture: measuring pulses in hardware

Input capture runs the other way. On a selected edge of an input pin, the hardware copies the counter value into a capture register. Two captures, one on the rising edge and one on the falling edge, give the pulse width in timer ticks. Because hardware latches the count, the result does not depend on how quickly the interrupt runs; the ISR only has to read the register before the next edge.

Counters wrap, so compute the difference with unsigned arithmetic of the counter's width:

#include <stdint.h>

/* 16-bit counter at 1 MHz: one tick = 1 us. */
uint16_t pulse_width_us(uint16_t rise, uint16_t fall)
{
    return (uint16_t)(fall - rise);   /* correct across one wrap */
}

With a rising capture at 0xFF00 and a falling capture at 0x0100, the result is 0x0200, 512 µs, even though the counter wrapped in between. This works as long as the pulse is shorter than one full counter cycle, 65.536 ms at this tick rate. For longer pulses, lower the timer clock with the prescaler or count update events in software.

Common mistakes

  • Forgetting the "+1" in PSC or ARR, giving a small frequency error
  • Choosing a large prescaler for PWM and losing resolution for no reason
  • Writing CCR without preload and seeing an occasional wrong pulse
  • Measuring pulse widths by reading a free-running counter in a GPIO interrupt, which adds the interrupt latency as jitter
  • Forgetting that the timer clock may not equal the core clock; check the clock tree

Try it yourself

  1. Use the Python function above for three targets on your board's actual timer clock, and confirm each result by hand with the formula.
  2. On a board, generate a 1 kHz PWM at 25 % duty and measure it with a logic analyser and sigrok PulseView. Change CCR in a loop, with and without preload, and look for short pulses.
  3. Feed the PWM back into an input-capture pin on the same chip and print the measured width. Compare it with CCR; any difference beyond one tick needs an explanation.
