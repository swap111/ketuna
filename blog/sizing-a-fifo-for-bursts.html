How deep should a FIFO be? Sizing it from burst length and rate mismatch

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

A FIFO only has to hold the backlog that builds up while a burst arrives faster than it drains. Work out that backlog for a sensor burst, add margin for synchronizer latency, and check the idle-time condition.

"Make it 1024 deep to be safe" is a common answer to FIFO sizing, and it wastes area on silicon where memory is expensive. "Make it 16 deep, that seems enough" is the other common answer, and it loses data the first time a burst is longer than someone assumed. The right depth falls out of a short calculation, as long as you know three things about the traffic: how long a burst is, how fast it arrives and how fast it drains.

What a FIFO is really absorbing

A FIFO does not fix a rate mismatch on average. If the producer writes faster than the consumer reads, forever, any finite FIFO eventually overflows. What a FIFO can do is absorb a burst: a limited run of data that arrives faster than the consumer can take it, followed by idle time in which the consumer catches up.

So the depth question becomes: during the worst burst, how many words pile up that the consumer has not yet removed? That pile, the backlog, is the minimum depth. Then you add margin for the latency of the control signals.

The basic calculation

Let the burst be B words, written one word per write clock at fw, and let the consumer read one word per read clock at fr, which is slower.

  • Time to write the burst: t = B / fw
  • Words read during that time: t × fr
  • Backlog at the end of the burst: B − B × fr / fw

depth ≥ B × (1 − fr / fw) + margin

If the consumer does not read on every clock, for example because it reads one word every other cycle, replace fr with its effective rate.

A worked example: a sensor burst

Here is a scenario, with numbers made up for illustration. A sensor interface captures a block of 256 samples and pushes them into a FIFO at 48 MHz, one sample per clock. A processing block on a separate 30 MHz clock pops one sample per clock whenever the FIFO is not empty. Between blocks, the sensor is idle.

Burst duration: 256 / 48 MHz = 5.33 µs.

Read during the burst: 5.33 µs × 30 MHz = 160 samples.

Backlog: 256 − 160 = 96 samples.

That is the storage needed if the consumer started reading at the very instant the first sample was written. It does not, and that is where the margin comes from.

Margin for synchronizer latency

The two clocks are unrelated, so this is an asynchronous FIFO. The write pointer reaches the read side through a two-flop synchronizer plus a register for the empty flag, so the reader sees "not empty" about three read clocks after the first write. During those three read cycles, 100 ns at 30 MHz, the writer keeps writing:

100 ns × 48 MHz = 4.8, which rounds up to 5 more samples.

The same delay applies in the other direction to the full flag: the writer learns that space has been freed a few write cycles late. In this scenario the writer never stalls, so that delay costs nothing, but in a design with backpressure it reduces the usable depth near full by a few entries.

Total: 96 + 5 = 101 entries. A simple asynchronous FIFO with Gray-coded pointers needs a power-of-two depth, so the answer is 128. The extra 27 entries are not waste; they are your safety margin against a slightly longer burst or a slower start than modelled.

Turning it into a script

Write the arithmetic once, by hand, then let a script check it and explore the corners:

import math

def fifo_depth(burst, f_wr, f_rd, rd_per_clk=1.0, sync_cycles=3):
    """Words of storage needed for one burst, plus synchronizer margin."""
    t_burst = burst / f_wr                  # seconds to write the burst
    drained = t_burst * f_rd * rd_per_clk   # words read meanwhile
    backlog = burst - drained
    # reader sees 'not empty' only after the pointer is synchronized
    margin = math.ceil(sync_cycles / f_rd * f_wr)
    need = math.ceil(backlog) + margin
    return need, 1 << (need - 1).bit_length()

print(fifo_depth(256, 48e6, 30e6))          # (101, 128)
print(fifo_depth(256, 48e6, 30e6, 0.5))     # reader takes every other clock

The second line asks what happens if the consumer can only take a sample every other cycle. The backlog grows to 176, the requirement to 181, and the depth doubles to 256. A small change in the consumer's behaviour has a large effect on area, which is why it pays to pin down the consumer's real rate before choosing the depth.

The idle-time condition

The depth calculation assumes the FIFO is empty when each burst starts. That is only true if the gap between bursts is long enough to drain it. In this example the consumer needs 256 / 30 MHz = 8.53 µs to remove one full block, plus the few cycles of flag latency. If a new block can start less than about 8.5 µs after the previous one started, the average input rate exceeds the output rate, the backlog carries over, and no finite depth is enough. State that requirement in the design documentation, and if the sensor can violate it, add an overflow flag so the failure is visible instead of silent.

Common mistakes

  • Sizing from average rates. The average tells you whether the system can keep up at all. The depth comes from the burst.
  • Forgetting the consumer's duty cycle. A reader that pauses for a header, a handshake or a pipeline stall reads less than one word per clock.
  • Ignoring flag latency. In an asynchronous FIFO both flags are a few cycles stale. Add those cycles' worth of writes to the margin.
  • Using clock frequencies without tolerance. Real oscillators have frequency tolerance; if two clocks are nominally equal, assume the writer can be slightly faster and size for a long-enough burst at that worst ratio.
  • No overflow detection. Even a well-sized FIFO should report overflow, so a violated assumption shows up in testing.

Try it yourself

  1. Redo the worked example on paper with your own numbers, then run the Python function above and compare.
  2. Extend the script into a cycle-by-cycle model: step both clocks with numpy time arrays, track occupancy, and record the maximum. Check that it agrees with the formula.
  3. In Icarus Verilog or with cocotb, drive a FIFO with the same burst pattern and add a check that fires if full is ever asserted while a write is pending. Shrink the depth until it fires, and see how close that is to your calculation.
