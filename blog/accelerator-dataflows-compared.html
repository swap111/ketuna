Weight-stationary, output-stationary and row-stationary dataflows compared

Edge AI Advanced 27 Nov 2026 6 min read By Ketuna

An accelerator dataflow is named for the data that stays put in each processing element. Counting buffer accesses for one matrix multiply shows how that choice, and the loop order behind it, sets traffic and energy.

Two accelerators with the same number of MAC units and the same clock can differ several-fold in energy per inference. The difference is rarely in the multipliers. It is in how often each operand is fetched from a large memory versus reused from a register next to the multiplier. The design choice that controls this is the dataflow: which of the three tensors, weights, inputs or partial sums, each processing element (PE) holds still while the others move past. Getting it right for your target layers is one of the first architecture decisions on an accelerator, and it is hard to change later.

The three tensors and their reuse

Write a layer as C = A · W, with A of size M × K (inputs), W of size K × N (weights) and C of size M × N (outputs). For a convolution, M is the number of output positions, K is kernel height × width × input channels and N is the number of output channels. Every MAC touches one element of each tensor, and each tensor has its own natural reuse:

  • each weight is used M times, once per output position
  • each input is used N times, once per output channel
  • each output accumulates K products, so its partial sum is read and written K times

Off-chip memory, the global on-chip buffer, small local buffers and PE registers form a hierarchy in which each level is far cheaper per access than the one above it. The goal of a dataflow is to serve as many of those uses as possible from the bottom of the hierarchy. No dataflow can keep all three tensors stationary at once, so each one picks.

Weight-stationary and output-stationary

Weight-stationary (WS): a P × P block of W is loaded into a P × P array, one weight per PE, and stays there while all M input rows stream through. Each weight is fetched from the buffer once and used M times. Partial sums flow through the array and leave at the edge, but because each PE only sees a P-element slice of the K dimension, the partial sums leaving one weight tile are incomplete. They must be stored and added to the results of the next K tile.

Output-stationary (OS): each PE owns one output element and keeps its accumulator in place for the whole K reduction. Inputs and weights both stream through, and the finished output leaves once, already complete, ready for requantization at the array edge.

Counting buffer accesses

Take M = K = N = 64 on a 16 × 16 array and count accesses to the global buffer, assuming the simplest loop order for each dataflow and that the buffer holds the whole layer. This is a model, not a measurement, but it shows the shape of the trade-off.

def traffic(M, K, N, P):
    ws = dict(A=M * K * (N // P),          # inputs re-streamed per N tile
              W=K * N,                     # each weight loaded once
              psum_wr=M * N * (K // P),    # partial sums out per K tile
              psum_rd=M * N * (K // P - 1))
    os_ = dict(A=M * K * (N // P),
               W=K * N * (M // P),         # weights re-streamed per M tile
               psum_wr=M * N,              # each output written once
               psum_rd=0)
    return ws, os_

print(traffic(64, 64, 64, 16))
Accesses Weight-stationary Output-stationary
Inputs (int8) 16,384 16,384
Weights (int8) 4,096 16,384
Partial-sum writes (int32) 16,384 4,096
Partial-sum reads (int32) 12,288 0

Weight-stationary wins on weights, as its name promises, by a factor of M / P = 4. But it pays with 28,672 partial-sum accesses, and partial sums are 32-bit, so in bytes that is 114,688 bytes against output-stationary's extra 12,288 bytes of weights. Counting every access as bytes, WS moves 135,168 bytes and OS 49,152 bytes for this layer.

That does not make output-stationary the universal answer. It makes where the partial sums live the deciding detail. Real weight-stationary designs place a dedicated accumulator memory right beside the array, sized for M × P partial sums, and loop over K tiles innermost. Then the partial-sum traffic goes to a small, cheap memory next to the adders instead of the global buffer, and the weight saving is kept. The dataflow name tells you what sits in the PE; the loop order and the buffer next to the array tell you the rest.

Some patterns that follow from the counts:

  • Large M (many output positions, as in early convolution layers on big feature maps) gives each weight many uses, so weight-stationary pays off well.
  • Large K (long reductions, as in deep layers with many input channels) multiplies partial-sum traffic unless outputs are held stationary or accumulated locally.
  • M = 1 (a batch-1 dense layer) leaves nothing to reuse weights across. Weight-stationary loads a full tile of weights to use each once; output-stationary uses one row of PEs. Either way the layer is limited by weight bandwidth, which is why small edge accelerators often run dense layers on a separate 1-D lane array.

Row-stationary for convolutions

Matrix-multiply dataflows treat a convolution after flattening it, which throws away its sliding-window structure: neighbouring outputs share most of their inputs. Row-stationary dataflow, introduced in research on energy-efficient convolution accelerators, keeps that structure. Each PE computes a 1-D convolution: it holds one row of filter weights in a small register file, slides along one row of the input feature map, and produces one row of partial sums. The PEs are arranged so that:

  • filter rows are reused horizontally across PEs working on different output rows
  • input rows are reused diagonally, because input row r contributes to several output rows
  • partial sums are accumulated vertically, so a column of PEs adds up the rows of one 2-D convolution

Instead of maximising the reuse of one tensor, row-stationary balances all three at the register-file level, which is why it does well on convolutions of many shapes. The cost is complexity: a PE needs a register file and control for its sliding window, the mapping of a layer onto the array is a search problem for the compiler, and dense layers fit it poorly.

Choosing for a real product

A dataflow is judged on the actual model, not on one layer. The process is the same each time:

  1. List every layer's M, K, N (or the full convolution shape) and its MAC share.
  2. For each candidate dataflow and loop order, count accesses at each memory level, as above, and weight them by relative access cost for your memory sizes and process.
  3. Add utilisation: a dataflow that saves traffic but leaves half the PEs idle on common shapes loses in latency and leakage.
  4. Check what the compiler can map. A dataflow that needs a hand-tuned schedule per layer is a maintenance cost.

Common mistakes:

  • comparing dataflows by their names without fixing the loop order and buffer sizes
  • forgetting that partial sums are wider than operands, so they cost more bytes per access
  • optimising for the largest layer and ignoring the dense layers that dominate latency at batch 1
  • counting MACs and ignoring accesses, which is where most of the energy goes

Try it yourself

  1. Extend the traffic function with a weight-stationary variant whose partial sums go to a local accumulator, and report global-buffer and local traffic separately.
  2. Run it over the layer shapes of a small convolutional network you have trained and plot bytes moved per layer for each dataflow.
  3. Write a cycle-accurate Python model of a 4 × 4 weight-stationary array and check its output against numpy, as you would for any golden model.
  4. Explore the open-source Timeloop and Accelergy tools, which model dataflows and energy across mappings, and compare their counts with yours.
