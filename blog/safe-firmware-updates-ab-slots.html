Bootloaders and safe firmware updates: A/B slots, verification and rollback

Embedded systems Advanced 27 Nov 2026 6 min read By Ketuna

A firmware update must survive power loss at any instant and a new image that boots but misbehaves. How A/B slots, signed images, a trial boot and a confirm step give you that, and where designs usually go wrong.

In this article

A device in the field that receives a broken update is no longer a device; it is a support visit. Two failure modes matter. The first is mechanical: power fails halfway through writing flash, and nothing valid is left to boot. The second is logical: the new image is complete and correctly signed, but it hangs on this particular hardware revision or cannot reach the network to receive a fix. A good update design handles both without anyone touching the device, and it does so with surprisingly little code if the states are chosen carefully.

The flash layout

The standard arrangement divides flash into four areas:

  • Bootloader: at the reset address, small, rarely or never updated, and write-protected
  • Slot A and slot B: each large enough for a complete application image
  • Boot record: a small area, ideally two flash sectors, holding which slot is active and in what state

The running application always lives in one slot. An update is downloaded into the other slot while the device keeps working normally. Nothing about the running image changes until the new one is complete and verified, so a power cut during download costs only the download.

There are two ways to run the new image. In a swap design, the bootloader copies or swaps the new image into a fixed primary slot, so every image is linked for one address; the swap must be resumable after power loss, which is where most of the complexity lives. In a direct design, the bootloader jumps to whichever slot is active, so images are either built twice, once per slot address, or made position-independent. Direct designs avoid the copy at the cost of the double build. The open-source MCUboot bootloader supports both styles and is worth reading even if you write your own.

What the bootloader verifies

Each image carries a header and a trailer. The header holds a magic number, the image size, a version and a security counter; the trailer holds a cryptographic hash of header and body and a signature over that hash.

Before jumping to any image, the bootloader checks, in order:

  1. the magic number and that the size fits the slot (cheap, catches empty or erased slots);
  2. the SHA-256 hash of the image (catches corruption from an interrupted write);
  3. the signature with a public key stored in the bootloader (catches images that did not come from you; Ed25519 and ECDSA P-256 are common choices);
  4. the security counter against a value stored in the device, so an attacker cannot install an older, correctly signed image with a known vulnerability.

A plain CRC catches corruption but not tampering. If anyone other than you can deliver bytes to the device, use a signature, and protect the bootloader's flash and the debug port so the key and the checks cannot be replaced.

Trial boot and confirmation

Verification proves the image is intact and authentic, not that it works. That is the job of the trial boot: the new image runs once, provisionally, and must explicitly confirm itself after passing a self-test. If the device resets for any reason before confirmation, the bootloader goes back to the previous image.

The bootloader's decision is a few lines once the record is in hand:

enum { ST_CONFIRMED = 1, ST_PENDING = 2, ST_TRIAL = 3 };

struct boot_rec {
    uint32_t magic, seq;         /* seq: highest valid copy wins */
    uint8_t  active, state, pad[2];
    uint32_t crc;                /* over the fields above */
};

int choose_slot(struct boot_rec *r)
{
    int other = 1 - r->active;

    if (r->state == ST_PENDING) {           /* first boot of new image */
        if (image_valid(r->active)) {
            r->state = ST_TRIAL;
            record_write(r);                /* before jumping, always */
            return r->active;
        }
        r->active = other;                  /* bad image: fall back */
        r->state = ST_CONFIRMED;
        record_write(r);
    } else if (r->state == ST_TRIAL) {      /* reset before confirm */
        r->active = other;
        r->state = ST_CONFIRMED;
        record_write(r);
    }
    return image_valid(r->active) ? r->active : -1;  /* -1: recovery */
}

The order matters: the record moves to TRIAL before the jump. If the new image then hangs, the watchdog resets the chip, the bootloader finds TRIAL and rolls back. If it wrote TRIAL after the image confirmed, a hang would leave the device rebooting into the bad image forever. The application's confirm() writes the record with state CONFIRMED; it should be called only after the checks that matter for this product, for example that the device has reached the update server, so that a broken network stack cannot confirm itself.

Surviving power loss in the record itself

The boot record is the single point of truth, so updating it must be atomic. Flash cannot be rewritten in place; a sector must be erased first, and power can fail between the erase and the write. Keep two copies in two sectors, each with a sequence number and a CRC. To update, erase and write the copy with the lower sequence number, giving it the next sequence number. At boot, read both and use the valid copy with the highest number. A power cut at any point leaves at least one valid copy, either the old state or the new one, never garbage.

Where designs go wrong

  • Confirming too early. An image that confirms itself in its first line of main() has turned the trial into a formality.
  • No watchdog during the trial. A new image that hangs with interrupts disabled never resets, so it never rolls back. Start the watchdog in the bootloader, before the jump.
  • Bootloader that cannot be trusted. If the application can rewrite the bootloader region, a bug or an attacker can remove every check. Lock it.
  • Forgetting the vector table and stack pointer. When jumping to an application, set the trap or vector base and the stack pointer from the application's image, not the bootloader's.
  • Testing only the happy path. The update path is the code most likely to be exercised for the first time in the field.

Try it yourself

  1. Implement choose_slot() and the two-copy record on your laptop, with flash simulated as a byte array whose writes can be cut off at any byte. Loop over every possible cut point in an update and assert that a valid image always boots.
  2. Sign and verify a test binary with Python's hashlib and an Ed25519 implementation, and flip one bit to confirm verification fails.
  3. On a board you own, build a Zephyr application with MCUboot (Zephyr's sysbuild can build both together) following the project's documentation, and walk a test update through the pending, trial and confirmed states. Pull the power once in each state and write down what boots.
