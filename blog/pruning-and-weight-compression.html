Pruning and weight compression for tiny models

Edge AI Advanced 27 Nov 2026 6 min read By Ketuna

Zeroing small weights only saves memory and time if the storage format and the hardware can exploit it. Unstructured versus structured pruning, index overhead, weight clustering, and checking what accuracy you gave up.

In this article

  2. Structured pruning that any hardware can use
  3. Weight clustering

After int8 quantization, a model that still does not fit, or still runs too slowly, invites the next step: remove weights. Trained networks are usually over-parameterised, and many weights end up close to zero, so pruning them often costs little accuracy. But a zero weight still occupies a byte and a multiply unless something in the storage format, the kernel or the hardware knows to skip it. The engineering question is not "how many weights can I zero?" but "what do the zeros buy on this target?", and the answer differs sharply between unstructured and structured pruning.

Unstructured pruning and the index tax

Magnitude pruning sets the weights with the smallest absolute values to zero, until a target fraction, the sparsity, is reached. Done gradually during fine-tuning, with the network retraining between steps, it can reach high sparsity on many models. The zeros are scattered with no pattern: that is unstructured sparsity.

To save memory you must store only the non-zero values plus enough information to know where they go. That information costs bytes. For an int8 layer with n weights and nnz non-zeros, compare three formats:

  • Dense: n bytes.
  • Value + 8-bit index: each non-zero stores its value and its position within a row (rows up to 256 wide): 2 × nnz bytes.
  • Bitmap: one bit per weight slot marks non-zeros, followed by the packed values: n / 8 + nnz bytes.

For a 64 × 64 layer (n = 4,096), with nnz = (1 − sparsity) × n:

Sparsity Dense Value + index Bitmap
50 % 4,096 4,096 2,560
75 % 4,096 2,048 1,536
90 % 4,096 about 820 about 922

With 8-bit indices you need more than 50 % sparsity just to break even, because each surviving weight now costs two bytes. The bitmap pays off earlier and stays ahead until nnz falls below n / 8, that is above 87.5 % sparsity, where the per-slot bitmap starts to cost more than the indices. With int8 weights, the metadata is the same order of size as the data, a much worse ratio than for 32-bit floats, where pruning was first popularised.

Speed is harder still. A sparse dot product on a microcontroller loads an index, computes an address and loads the matching input, so each useful MAC costs several instructions, and memory access becomes irregular. On a simple core it may need quite high sparsity before it beats the dense loop, and on SIMD kernels or a systolic array, scattered zeros save nothing unless the hardware was built to skip them. Measure on the target before counting on a speed-up.

Structured pruning that any hardware can use

Structured pruning removes whole units: an output channel of a convolution, a neuron of a dense layer, sometimes a whole layer. The result is simply a smaller dense network, which every kernel and accelerator already runs efficiently.

The savings also compound. Removing an output channel from one layer removes the matching input channel from the next. Take an illustrative pair of 3 × 3 convolutions, 16 → 32 → 64 channels. Pruning 8 of the 32 middle channels:

  • the first layer's weights go from 3 × 3 × 16 × 32 = 4,608 to 3 × 3 × 16 × 24 = 3,456
  • the second layer's go from 3 × 3 × 32 × 64 = 18,432 to 3 × 3 × 24 × 64 = 13,824
  • the activation tensor between them shrinks by a quarter, which lowers peak RAM

Both layers lose 25 % of their weights and MACs with no index overhead at all. Channels are usually ranked by the size of their weights (for example the L1 norm of each filter) or by how much the loss changes when they are removed, and then the network is fine-tuned to recover.

Between the two extremes sit semi-structured patterns, such as keeping exactly 2 of every 4 consecutive weights. Hardware with matching support can skip the zeros with a tiny fixed-size index; without that support they are just unstructured zeros.

Weight clustering

Clustering (or weight sharing) runs k-means on a layer's weights and replaces each weight with the nearest of k centroid values. Store a small codebook of k values and, per weight, an index of log2(k) bits. With 16 clusters, each weight needs 4 bits: a dense layer with 122,880 weights drops from 122,880 bytes in int8 to 61,440 bytes of indices plus a 16-entry codebook.

The cost is a lookup per weight before the MAC, which a microcontroller does in software and an accelerator can do with a small table next to each lane. Clustering combines well with pruning (zero becomes one of the clusters) and with standard compression of the packed indices for storage.

A small numpy experiment

import numpy as np

def prune_magnitude(w, sparsity):
    """Zero the smallest |w| so that `sparsity` of entries are zero."""
    k = int(sparsity * w.size)
    thr = np.sort(np.abs(w).ravel())[k - 1] if k else -1
    return np.where(np.abs(w) > thr, w, 0).astype(w.dtype)

def sizes(w):
    n, nnz = w.size, int(np.count_nonzero(w))
    return {"dense": n,                     # 1 byte per int8 weight
            "index8": 2 * nnz,              # value + 8-bit index
            "bitmap": (n + 7) // 8 + nnz}   # 1 bit per slot + values

rng = np.random.default_rng(0)
w = rng.integers(-127, 128, (64, 64), dtype=np.int8)
for s in [0.5, 0.75, 0.9]:
    print(s, sizes(prune_magnitude(w, s)))

Ties in integer weights make the achieved sparsity differ slightly from the target, so the sizes printed differ a little from the table. That is a useful reminder to measure what you produced rather than what you asked for.

Checking what you gave up

Pruning changes the model, so the evaluation has to be as careful as for the original:

  1. Per-layer sensitivity first. Prune one layer at a time and measure validation accuracy. The first and last layers are often sensitive; large dense layers often tolerate a lot.
  2. Fine-tune after pruning, gradually if you aim high, and re-quantize afterwards: pruning changes weight ranges, so scales computed before pruning may no longer fit.
  3. Look beyond the average. A pruned model may keep its overall accuracy while losing a rare class. Compare per-class recall, not just one number.
  4. Measure the deployed result: flash bytes from the build, RAM from the runtime, cycles from the target. A "90 % sparse" model that runs slower is not a win.

Common mistakes:

  • reporting sparsity as a saving without counting index storage
  • expecting unstructured zeros to speed up dense kernels or a systolic array
  • pruning a quantized model and keeping the old scales
  • comparing pruned and original models on different test sets

Try it yourself

  1. Run the script, then add a 4-bit clustered format to sizes() and find where it beats the bitmap.
  2. Train a small convolutional network in PyTorch, apply torch.nn.utils.prune.l1_unstructured to one layer, fine-tune briefly and record accuracy at several sparsities.
  3. Repeat with torch.nn.utils.prune.ln_structured on output channels, then actually rebuild the smaller layers and measure parameters and MACs.
  4. Export both variants to int8 and compare flash size and cycles per inference on a microcontroller or in an instruction-set simulator.
