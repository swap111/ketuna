Python for hardware engineers: the parts you will use every day

Careers & skills Intermediate 27 Nov 2026 5 min read By Ketuna

Hardware engineers use Python to parse tool reports, generate test vectors, plot results and write small reference models. Here are the parts of the language that matter, with working examples.

In this article
  1. Parsing tool reports

  3. Plotting results

Hardware engineers rarely write large Python applications, but most of them write Python every week. It is the glue around the tools: pulling numbers out of a timing report, generating thousands of test vectors, plotting a coverage trend, or modelling what a block should do so a testbench can check it. You do not need the whole language for this. A handful of features, used well, cover almost all of it: regular expressions, lists and dictionaries, file input and output, a plotting library, and simple classes. Everything below uses only the standard library plus matplotlib.

Parsing tool reports

Tool reports are text written for people, so the first job is usually to turn them into numbers. Regular expressions from the standard re module do most of the work. Suppose a timing report contains lines like these (format made up for illustration):

Path 1: slack -0.042 ns  start a_q[3]  end sum_q[8]
Path 2: slack  0.118 ns  start b_q[0]  end sum_q[1]

A short function extracts every path and its slack:

import re

PATH_RE = re.compile(
    r"Path\s+(\d+):\s+slack\s+(-?\d+\.\d+)\s+ns\s+"
    r"start\s+(\S+)\s+end\s+(\S+)"
)

def read_paths(filename):
    paths = []
    with open(filename) as f:
        for line in f:
            m = PATH_RE.search(line)
            if m:
                num, slack, start, end = m.groups()
                paths.append((int(num), float(slack), start, end))
    return paths

paths = read_paths("timing.rpt")
failing = [p for p in paths if p[1] < 0]
print(f"{len(failing)} of {len(paths)} paths violate setup")
for num, slack, start, end in sorted(failing, key=lambda p: p[1]):
    print(f"  {slack:+.3f} ns  {start} -> {end}")

Three habits make parsers like this trustworthy. Compile the pattern once and keep it readable by splitting it across lines. Convert to numbers immediately so comparisons are numeric, not alphabetical. And count what you did not match: if the report format changes after a tool update, a parser that silently finds zero paths is worse than one that crashes.

Generating test vectors

Testbenches often read stimulus and expected results from a file. Python makes it easy to produce both, including the corner cases a human would forget. For an 8-bit adder with a 9-bit sum:

import random

random.seed(1)  # same vectors every run, so failures reproduce

corners = [(0, 0), (255, 255), (255, 1), (128, 128), (1, 254)]
randoms = [(random.randrange(256), random.randrange(256))
           for _ in range(1000)]

with open("vectors.hex", "w") as f:
    for a, b in corners + randoms:
        f.write(f"{a:02x} {b:02x} {a + b:03x}\n")

A Verilog testbench can load this file with $readmemh into an array and compare the design's output with the third column. Fixing the seed is important: when a vector fails, you need the identical file again tomorrow to debug it. Putting the corner cases first means the most likely failures appear at the top of the log.

Plotting results

A plot often shows in seconds what a table hides: a slack distribution with a long negative tail, power rising faster than expected with frequency, a coverage curve that has flattened. The matplotlib library, with numpy for the numbers, is the usual open-source choice.

import matplotlib.pyplot as plt

slacks = [p[1] for p in read_paths("timing.rpt")]
plt.hist(slacks, bins=40)
plt.axvline(0.0, linestyle="--")
plt.xlabel("setup slack (ns)")
plt.ylabel("number of paths")
plt.title("Setup slack distribution")
plt.savefig("slack_hist.png", dpi=150)

Save plots to files rather than only showing them on screen, so they can go into a report or a review and be regenerated when the data changes. Label the axes with units every time; an unlabelled plot invites the wrong conclusion.

Writing small reference models

The most valuable Python a hardware engineer writes is often a reference model: a simple, obviously correct description of what a block should do. A testbench drives the same inputs into the model and the design and compares the outputs. Simplicity is the point, because the model must be easier to trust than the RTL.

A model of a small synchronous FIFO, matching a spec that ignores writes when full and reads when empty:

from collections import deque

class FifoModel:
    def __init__(self, depth):
        self.depth = depth
        self.q = deque()

    def step(self, wr_en, wr_data, rd_en):
        """One clock cycle; returns data read, or None."""
        out = None
        can_read = rd_en and len(self.q) > 0
        can_write = wr_en and len(self.q) < self.depth
        if can_read:
            out = self.q.popleft()
        if can_write:
            self.q.append(wr_data)
        return out

Notice that the model decides the full and empty conditions from the state at the start of the cycle, before the read. That is a design decision your spec must state, because it determines whether a simultaneous read and write on a full FIFO is accepted. Writing the model forces those questions into the open, often before the RTL exists. In a cocotb testbench, the same class can be called once per clock alongside the real design.

Making scripts usable by the team

A script that only works on your machine, with a file name typed into the code, will be rewritten by the next person who needs it. A few small habits make it a shared tool instead.

import argparse
import sys

def main():
    ap = argparse.ArgumentParser(description="Summarise setup slack")
    ap.add_argument("report", help="timing report file")
    ap.add_argument("--limit", type=float, default=0.0,
                    help="flag paths with slack below this (ns)")
    args = ap.parse_args()
    bad = [p for p in read_paths(args.report) if p[1] < args.limit]
    for p in bad:
        print(p)
    return 1 if bad else 0

if __name__ == "__main__":
    sys.exit(main())

Command-line arguments with argparse give the script a --help message for free. The if __name__ == "__main__" guard lets another script or a test import read_paths without running everything. And returning a non-zero exit code on failure means a make target or CI job can stop the flow automatically, instead of relying on someone to read the output.

Common mistakes

  • Comparing strings instead of numbers. "10.5" < "9.1" is True; convert with float() first.
  • Unseeded random stimulus. A failure you cannot reproduce is a failure you cannot debug.
  • Parsers that fail silently. Check that the expected number of items was found.
  • Copying RTL logic into the model. If the model mirrors the RTL's structure, it repeats its bugs. Model from the spec.
  • Clever one-liners. Code your teammates cannot read in a review will not be trusted.

Try it yourself

  1. Write the vector generator above, build an 8-bit adder in Verilog, and have an Icarus Verilog testbench read vectors.hex with $readmemh and report any mismatch.
  2. Run OpenSTA on a small synthesised netlist, save the output of report_checks to a file, and adapt the regular expression to its real format.
  3. Plot a histogram of the slacks with matplotlib, then tighten the clock constraint and plot again to see the distribution shift.
  4. Connect FifoModel to a FIFO design in a cocotb test and plant a bug in the full flag to confirm the comparison catches it.
