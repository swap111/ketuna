How to read the RISC-V specification without getting lost

Computer architecture & RISC-V Beginner 27 Nov 2026 6 min read By Ketuna

A reading order for the RISC-V manuals, how extension names like RV32IMAC_Zicsr are built, how to read the encoding tables, and the handful of specification words that change what you must implement.

The RISC-V specification is open, free to download and unusually readable for a standard. It is also long, split into volumes, and full of extensions with names like Zicsr and Sstc. Students who open it at page one and read straight through often give up somewhere around floating point. You do not need to read it that way. With a reading order, a way to decode extension names and a few key terms, you can find what you need in minutes and read the rest when a project calls for it.

Two volumes, two audiences

The ISA is published as two main documents, maintained in the open by RISC-V International (the official copies and their source are on the organisation's website and public repositories):

  • Volume I, the Unprivileged ISA. Everything an application programmer sees: the base integer instruction sets (RV32I, RV64I and the reduced RV32E), the standard extensions (M, A, F, D, C, bit manipulation, vectors and many more), the memory model, and the instruction listings.
  • Volume II, the Privileged Architecture. What operating systems, firmware and core designers need: privilege modes, the control and status registers (CSRs), traps and interrupts, physical memory protection, and virtual memory schemes such as Sv32 and Sv39.

Further specifications cover topics outside the ISA itself: the debug specification, the platform-level interrupt controller, the Supervisor Binary Interface, the ELF psABI (calling convention) and others. Know they exist; open them when a task needs them.

A reading order that works

  1. Volume I introduction. It explains the design goals, the base-plus-extensions model, and terms used throughout. Read it fully once.
  2. The RV32I base chapter. The registers, the six formats, and every base instruction. This is the chapter you will return to most.
  3. The instruction listings chapter near the end of Volume I, which gathers every encoding into tables. Keep it open as a reference.
  4. The ISA naming conventions chapter, which tells you how to read strings like RV32IMAC_Zicsr_Zifencei.
  5. The extension you need now, usually M and C for a microcontroller core, or Zicsr for CSR access.
  6. Volume II, machine-level chapter, when you write trap handlers or design a core: mstatus, mtvec, mepc, mcause, mie, mip, and the machine timer.

Save the memory model, floating point, vectors and supervisor mode for when a project requires them. They are long, and they make far more sense after you have built or programmed something simpler.

Decoding extension names

An ISA string lists the base and then the extensions, in a canonical order:

  • RV32 or RV64 gives the register width. I is the base integer set; E is the reduced base with 16 registers for very small cores.
  • Single letters are the original standard extensions: M multiply/divide, A atomics, F and D single and double floating point, C compressed instructions. G is shorthand for IMAFD plus Zicsr and Zifencei.
  • Multi-letter names starting with Z are standard unprivileged extensions, grouped by a following letter that hints at the closest single-letter category: Zicsr (CSR instructions), Zifencei (instruction fence), Zba, Zbb and Zbs (bit manipulation), Zmmul (multiply only).
  • Names starting with S are privileged-architecture extensions, such as Sstc (supervisor timer compare).
  • Names starting with X are non-standard, vendor-specific extensions.
  • Multi-letter names are separated by underscores.

So RV32IMAC_Zicsr_Zifencei is a 32-bit core with the base integer set, multiply and divide, atomics, compressed instructions, CSR instructions and the instruction fence. The same string, in lower case, is what you pass to GCC's -march option, so understanding it also tells you how to build for the core.

Extensions also have a status. Ratified extensions are stable and safe to design to. Others may be frozen or still drafts, and their encodings can change. Check the status on the official list before you implement one.

Reading an encoding table

Encoding tables show each instruction as a row of bit fields, high bits on the left. Take the branch "less than, unsigned", bltu, from the listings:

Bits 31 to 25 24 to 20 19 to 15 14 to 12 11 to 7 6 to 0
bltu imm[12, 10:5] rs2 rs1 110 imm[4:1, 11] 1100011

Read it right to left. The opcode 1100011 says "branch". The funct3 value 110 says "unsigned less than". The register fields are in their usual places. The immediate notation imm[12, 10:5] means "bit 12, then bits 10 to 5 of the offset", which is the B-type scrambling. Every other branch has the same row with a different funct3: 000 for beq, 001 for bne, 100 for blt, 101 for bge, 111 for bgeu. Once you see that pattern, the listings become a quick lookup rather than a wall of bits.

The words that change what you build

The specification uses a few terms precisely. Misreading them causes real bugs:

  • Reserved: not defined now, may be defined later. Hardware must usually treat reserved encodings as illegal; software must not use them.
  • Custom: set aside for non-standard extensions; standard extensions will not use it.
  • WARL (write any values, reads legal values): software may write anything to the field; hardware returns only values it supports. Software discovers support by writing and reading back.
  • WLRL (write legal values, reads legal values): software must write only legal values; what happens otherwise is not guaranteed.
  • WPRI (reserved writes preserve values, reads ignore values): software must preserve these bits when it writes the register.
  • Implementation-defined: the core chooses, and should document the choice.
  • Commentary: the manuals include non-normative explanation, set apart from the normative text, that explains why a rule exists. It is often the most educational part. Read it, but remember it is not a requirement.

Common mistakes

  • Reading a draft as if it were ratified. Encodings can still change.
  • Ignoring the privileged volume. Trap and CSR behaviour lives there, not in Volume I.
  • Treating commentary as normative. It explains; the rules are in the main text.
  • Building to a string you did not decode. A mismatch between -march and the core shows up as illegal-instruction traps.

Try it yourself

  1. Download the current Volume I, find the instruction listings chapter, and decode 0x0062E663 by hand using only the tables. Then check your answer with riscv64-unknown-elf-objdump on a one-instruction object file.
  2. Take the ISA string of any open-source RISC-V core you are interested in and write one line per extension saying what it adds and which chapter defines it.
  3. Find one WARL field in Volume II, such as the mode bits of mtvec, and write a short bare-metal test for QEMU that writes and reads it back.
