Writing a README that explains your project in two minutes

Careers & skills Beginner 27 Nov 2026 5 min read By Ketuna

A README should answer five questions in order, what it is, why it matters, how to run it, what the results are and where it stops, so a stranger understands your project in two minutes.

The README is the first file anyone opens in your project, and often the only one. A reviewer, a new teammate or you in six months will read the top of it and decide whether to keep going. If they cannot tell what the project is and whether it works within a couple of minutes, they move on. A good README is not long; it answers the right questions in the right order.

Five questions, in this order

A reader arrives with questions, and they arrive in a predictable sequence. Answer them in that sequence:

  1. What is it? One or two sentences, in plain words.
  2. Why does it matter? The problem it solves or what it demonstrates.
  3. How do I run it? Exact commands, from a clean clone.
  4. What are the results? Evidence that it works: test output, numbers, a picture.
  5. What are the limits? What is not done, not tested or known to be wrong.

Everything else, such as design notes, file layout, credits and history, comes after these five. A reader who stops after question 1 should still know what your project is. A reader who stops after question 4 should know whether to trust it.

What is it, and why it matters

The first lines carry most of the weight. Compare two openings:

Weak: This repository contains my project work for the digital design course. It was a very interesting learning experience.

Strong: A 16-entry by 8-bit synchronous FIFO in Verilog, with a cocotb scoreboard testbench and formal checks of the full and empty flags. It is the receive buffer for a UART that runs at 115,200 baud.

The strong version names the thing, its size, the language, how it is checked and where it is used. It does not say "interesting", because that tells the reader nothing about the project.

For "why", one short paragraph is enough. Say what problem the design solves or what you wanted to learn and show. If it is a course lab, say so; then say what you added beyond the lab.

How to run it

This section fails more often than any other. The author runs the project from a folder full of leftover state and never tries a clean clone. Write the commands as a reader would type them:

git clone <your-repo-url>
cd sync-fifo
make sim        # directed testbench, Icarus Verilog
make cocotb     # random scoreboard test, 10 seeds
make lint       # Verilator lint

List the prerequisites just above, with versions you tested: for example "Icarus Verilog 12, Verilator 5, Python 3.12 with cocotb". Then do the one thing that makes this section trustworthy: clone the repository into a new folder and run every command exactly as written. If it fails for you, it will fail for the reader.

Results and limits

Results are where the reader decides to believe you. Show what the tests print, and add one or two numbers with their context:

make cocotb
  test_random_traffic  PASS  (10 seeds, 2,000 transactions each)
  test_full_empty      PASS  (full reached 37 times, empty 41 times)
  TESTS=2 PASS=2 FAIL=0

If the project goes through synthesis or layout, add the cell count, the clock period it meets and the tool that reported it. A waveform screenshot of one normal transaction, with the signals labelled, helps a reader see the behaviour in seconds. (These sample figures are made up for illustration; use your own.)

Then state the limits plainly. For example:

  • Only tested in simulation; not run on an FPGA
  • Simultaneous read and write when full drops the write by design (see spec section 3)
  • Formal checks cover the flags, not the data ordering

A limits section does not make the project look weaker. It shows that you know where the edges are, which is exactly what a reviewer wants to see in an engineer.

Keep it current

A README that was right in March and wrong in June is worse than a short one, because readers trust it and act on stale instructions. Update it in the same commit that changes what it describes: a new make target, a renamed folder, a new result. If you keep a status line near the top ("complete", "in progress: formal checks not finished"), change it when the status changes. Reviewing a pull request is a good moment to ask whether the README still matches the code.

A template you can copy

# <Project name>
<One or two sentences: what it is.>

## Why
<The problem, or what this demonstrates.>

## Run it
Prerequisites: <tools and versions tested>
<exact commands from a clean clone>

## Results
<test output, key numbers with tool names, one picture>

## Limits
<what is not done, not tested or known wrong>

## Layout
<three to six lines: which folder holds what>

## What I did / credits
<your part, starting points, AI use, other people's code>

Common mistakes

  • Starting with history. "First I tried X, then Y" makes the reader hunt for the point. History, if it matters, goes at the end.
  • Instructions that need your machine. Absolute paths, a tool you installed by hand and forgot, a file you never committed.
  • Claims without numbers. "Efficient", "robust" and "fully tested" are untestable. Replace each with a result.
  • A wall of auto-generated text. A README that lists every file and function is a reference manual, not an introduction.
  • No date or status. Say whether the project is complete, in progress or abandoned.

Try it yourself

  1. Pick one of your projects and rewrite its first two sentences so a stranger knows what it is, its size and how it is checked.
  2. Clone it into an empty folder and follow your own run instructions literally. Fix every step that fails.
  3. Add a results block with real test output from Icarus Verilog, Verilator or cocotb, and a limits list with at least two honest entries.
  4. Give the README to a classmate, set a two-minute timer, then ask them what the project does and whether it works. Every question they ask is a gap to fill.
