From single-cycle to a five-stage pipeline: what changes and why

Computer architecture & RISC-V Intermediate 27 Nov 2026 5 min read By Ketuna

Cutting a single-cycle core into five stages adds pipeline registers, raises the clock and creates hazards. Work out the real speed-up, what each register must carry, and what new logic you inherit.

  5. Common mistakes
  6. Try it yourself

A single-cycle core is easy to understand and slow, because its clock period must fit the longest instruction from fetch to write-back. The classic fix is to cut the datapath into five stages and let five instructions be in flight at once. The idea is simple; the consequences are not. The cuts add registers, every control signal has to travel with its instruction, and new hazards appear that the single-cycle design never had. This article walks through what changes, and puts numbers on the gain.

Where the cuts go

The classic RISC pipeline splits the work at its natural boundaries:

  • IF: fetch the instruction at PC, compute PC + 4.
  • ID: decode, read the register file, build the immediate.
  • EX: ALU operation, address calculation, branch comparison.
  • MEM: data memory read or write.
  • WB: write the result into the register file.

A pipeline register sits between each pair of stages, clocked by the same clock as everything else. At each edge, every stage hands its work to the next and picks up new work from the one before. In steady state, one instruction enters and one leaves every cycle.

What the pipeline registers must carry

In the single-cycle core, the decoded control signals drive the whole datapath in the same cycle. In a pipeline the instruction that was decoded is three stages further on by the time it writes memory, and the decoder is already working on a different instruction. So everything an instruction needs later must ride along with it in the pipeline registers.

For the ID/EX register that means the two operand values, the immediate, the destination register number rd, the source numbers rs1 and rs2 (needed later for forwarding), the PC (for branches and auipc), and every control bit for EX, MEM and WB. Each later register drops what has been used and keeps the rest.

always @(posedge clk) begin
  if (rst || flush_ex) begin
    idex_regwrite <= 1'b0;      // a bubble: no side effects
    idex_memwrite <= 1'b0;
    idex_memread  <= 1'b0;
  end else if (!stall) begin
    idex_rs1v     <= rf_rs1v;
    idex_rs2v     <= rf_rs2v;
    idex_imm      <= imm;
    idex_rd       <= ifid_ins[11:7];
    idex_rs1      <= ifid_ins[19:15];
    idex_rs2      <= ifid_ins[24:20];
    idex_pc       <= ifid_pc;
    idex_regwrite <= dec_regwrite;   // control rides along
    idex_memwrite <= dec_memwrite;
    idex_memread  <= dec_memread;
  end
end

Two details in this snippet are new compared with a single-cycle core. A flush clears the side-effect bits so a squashed instruction becomes a harmless bubble. A stall holds the register. Neither exists in a single-cycle design, because there was never more than one instruction to manage.

The speed-up, worked out honestly

Use these stage delays, made up for illustration: IF 200 ps, ID 100 ps, EX 200 ps, MEM 200 ps, WB 100 ps, and 20 ps of overhead per pipeline register (clock-to-Q plus setup).

Single-cycle: the period must fit a load through every stage: 200 + 100 + 200 + 200 + 100 = 800 ps, one instruction per cycle.

Pipelined: the period is set by the slowest stage plus overhead: 200 + 20 = 220 ps. That is 1 / 220 ps, about 4.5 GHz in this imaginary technology, against 1.25 GHz before.

The ideal speed-up is 800 / 220, about 3.6, not 5. Two things ate the rest: the stages are unbalanced (ID and WB use only half the cycle), and each register adds overhead. If hazards then add stalls so that the average is 1.25 cycles per instruction, the time per instruction is 1.25 × 220 = 275 ps, and the speed-up is 800 / 275, about 2.9.

Notice also that the latency of a single instruction gets worse: it now takes five cycles of 220 ps, 1100 ps, against 800 ps before. A pipeline improves throughput, not the time any one instruction takes.

The hazards you just created

Overlapping instructions break assumptions the single-cycle core relied on:

  • Data hazards. add x3, x1, x2 followed by sub x5, x3, x4: the subtract reads x3 in ID while the add is still in EX. Forwarding paths fix most of these, as described in data hazards and forwarding; a load followed by a use still needs one stall, covered in the load-use hazard.
  • Control hazards. The branch outcome is known in EX, but IF has already fetched two more instructions. If the branch is taken they must be flushed, costing two cycles unless the core predicts well.
  • Structural hazards. If IF and MEM shared one memory port, a load and a fetch would collide in the same cycle. Separate instruction and data memories, or caches, remove this.

Each fix is more logic and, more importantly, more cases to verify. A pipelined core can pass every single-instruction test and still fail on a particular sequence of three instructions.

Common mistakes

  • Using a control signal from the decoder in a later stage. The decoder now belongs to a younger instruction; take the bit from the pipeline register.
  • Stalling some stages but not others. If the PC advances while IF/ID is held, an instruction is skipped.
  • Forgetting to clear side-effect bits on a flush. A flushed store that still writes memory is a real bug.
  • Expecting five times the speed. Balance and overhead set the period; hazards set the CPI.

Try it yourself

  1. Take a small single-cycle RV32I core, insert the four pipeline registers without any hazard logic, and run a program where every instruction is independent (insert nops between dependent ones). It should pass.
  2. Remove the nops, run again in Icarus Verilog or Verilator, and find the first wrong register value in GTKWave. That failure is your first data hazard.
  3. Synthesise both versions with Yosys and compare the flip-flop counts reported by stat: the difference is the cost of the pipeline registers.
