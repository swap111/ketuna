Draw the circuit before you write the Verilog: the habit that prevents most RTL bugs

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

Sketch the registers, muxes and logic first, write code that matches the drawing line for line, then check the code with AI and the tools. A moving-average filter shows the whole loop.

Verilog looks like software, so beginners write it like software: start typing, add an if here, a variable there, simulate, patch. The result usually simulates and often synthesises into something nobody intended: an extra register, a missing one, a latch, a mux chain three times longer than needed. Experienced designers do something that looks slower and is much faster: they draw the hardware first, then write code that describes the drawing. This article walks through that habit on a small example, and shows where AI assistance fits.

Why the drawing comes first

RTL stands for register-transfer level. The code describes registers and the combinational logic that moves data between them on each clock. If you cannot say where every register is, you do not yet know what circuit you are describing, and the synthesis tool will decide for you.

A drawing forces the decisions that matter:

  • How many registers, and how wide. Every flop costs area and power, and every one adds a cycle of latency.
  • What is combinational between them. That sets the critical path and the clock speed.
  • Where the muxes are. Every if and case becomes a mux; seeing them makes priority and defaults explicit.
  • What happens on reset and when the block is idle.

Ten minutes with a pencil answers these. Discovering them later in a waveform takes hours.

The example: a 4-sample moving average

The task: an 8-bit sensor sample arrives with an en strobe. Output the average of the last four samples, updated on each new sample. The output may lag by one clock.

Step 1: list the storage. The average needs the current sample and the three before it, so three 8-bit delay registers hold the older samples, x1, x2 and x3. The output is registered, as the specification allows a cycle of lag and a registered output is clean for whoever uses it. That is four registers in total.

Step 2: draw the logic between them. Four values are summed. As a tree, that is two adders in parallel and one after them: x0 + x1 and x2 + x3, then the sum of those. Each addition can grow by one bit, so the first adders are 9 bits wide and the final one 10 bits.

Step 3: draw the divide. Dividing by four is a right shift by two: just wiring, taking bits [9:2] of the sum. No divider is needed, which is one reason designers like powers of two.

Step 4: mark the enable and reset. All four registers load only when en is high. On reset they clear to zero, so the output ramps up over the first four samples, which you should note in the documentation.

On paper this is a row of three boxes for the delay line, two adders feeding a third, a label "[9:2]" on the final wire, and one more box for the output register. Count the flops on the drawing: 3 × 8 + 8 = 32.

Write the code to match the drawing

Now each part of the drawing becomes a few lines, and nothing else gets written:

module mavg4 (
  input  wire       clk, rst_n, en,
  input  wire [7:0] x0,          // new sample
  output reg  [7:0] avg
);
  // drawing: three delay registers
  reg [7:0] x1, x2, x3;
  // drawing: adder tree, widths grow by one bit per level
  wire [8:0] s01 = x0 + x1;
  wire [8:0] s23 = x2 + x3;
  wire [9:0] sum = s01 + s23;

  always @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      x1 <= 8'd0; x2 <= 8'd0; x3 <= 8'd0; avg <= 8'd0;
    end else if (en) begin
      x1  <= x0;
      x2  <= x1;
      x3  <= x2;
      avg <= sum[9:2];           // drawing: divide by 4 is wiring
    end
endmodule

Read it against the drawing: four registers in one clocked block, three adders as continuous assignments with the widths from the sketch, the shift as a part-select. If the code has something the drawing does not, or the drawing has something the code does not, one of them is wrong.

Then check it with AI and with the tools

Once the drawing and the code exist, an AI assistant is a useful second reviewer, not a replacement for the first two steps. Describe the circuit in words, paste the code, and ask specific questions: "How many flip-flops will this infer? Are the adder widths enough to avoid overflow? What does the output do in the first four samples after reset?" Compare its answers with your drawing. Where they disagree, find out who is right by checking the tools, not by trusting either side.

The tools give you ground truth:

  • Lint with Verilator flags width mismatches and unused signals.
  • Synthesis with Yosys reports the flop count. If it says 32, the drawing and the code agree. If it says 40, something is registered that you did not draw.
  • A schematic view of the synthesised design shows the structure, which you can hold next to your sketch.
  • Simulation against a Python model of a moving average confirms the numbers.

The order matters. Drawing first means you have an independent expectation to check the AI and the tools against. Starting from an AI-generated module and then trying to understand it reverses that, and you lose the ability to tell whether it is right.

Common mistakes the drawing catches

  • Accidental extra registers, from assigning an intermediate value inside a clocked block when you meant a wire
  • Missing width growth, such as an 8-bit sum that overflows
  • Latches, from a combinational block that does not assign an output on every path
  • A long chain of adders where a tree was intended, because the code was written as x0 + x1 + x2 + x3 without thinking about structure (synthesis may rebalance it, but you should know what you asked for)

Try it yourself

  1. Draw mavg4 yourself before reading the code again, including every width, and count the flops.
  2. Run yosys -p "read_verilog mavg4.v; synth -top mavg4; stat" and check the flip-flop count against your drawing. Then run show after proc to see the structure as a diagram (it needs Graphviz installed).
  3. Simulate it in Icarus Verilog with a short sequence of samples, compare against a three-line Python moving average, and explain the first four outputs after reset from your drawing.
