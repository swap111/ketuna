Superloop or RTOS? Deciding with timing requirements, not fashion

Embedded systems Beginner 27 Nov 2026 6 min read By Ketuna

A superloop with interrupts is enough more often than people think. Work out the worst-case loop time against each deadline, and you will see exactly which requirement, if any, calls for a preemptive scheduler.

"Should we use an RTOS?" is often answered by habit: one team always does, another never does. Both habits produce working products and both produce painful ones. The question has a better answer, and it comes from writing down your timing requirements and doing a little addition. This article shows the calculation for a superloop, the techniques that stretch a superloop further, and the specific requirements that make a real-time operating system worth its cost.

What a superloop is, and how it behaves in time

A superloop is the simplest firmware structure: initialise, then run every job in turn, forever. Interrupts handle the urgent hardware events and hand data to the loop through flags or buffers.

int main(void)
{
    init_all();
    for (;;) {
        sensor_job();      /* worst case  2 ms */
        control_job();     /* worst case  1 ms */
        comms_job();       /* worst case  3 ms */
        display_job();     /* worst case 15 ms */
        log_job();         /* worst case 25 ms (flash write) */
    }
}

The timing property that matters is the worst-case loop time: the sum of every job's worst case, plus the time stolen by interrupts. Here, with made-up but realistic numbers, it is 2 + 1 + 3 + 15 + 25 = 46 ms before interrupts. Any event that the loop notices by checking a flag may wait up to one full loop before it is handled, so the worst-case response time for anything handled in the loop is about 46 ms.

Now compare with the requirements:

Requirement Deadline Superloop result
React to a button 100 ms 46 ms: met
Answer a host command 50 ms 46 ms plus interrupts: marginal
Run the control law every 10 ms, jitter under 1 ms 10 ms Fails: runs once per loop, up to 46 ms apart

The superloop is not "too slow" in general. It fails one specific requirement, because a periodic job is stuck behind two long ones. That tells you what to fix.

Stretching the superloop

Before reaching for a scheduler, three techniques often solve the problem.

Move the strict periodic job into a timer interrupt. If control_job is short (1 ms) and does not block, run it from a 10 ms timer interrupt. Its jitter is now the interrupt latency, microseconds rather than tens of milliseconds. This only works for short, non-blocking jobs; a long job in an interrupt delays every other interrupt.

Break long jobs into small steps. The 25 ms log write is mostly waiting for the flash to finish programming. Turn it into a state machine that starts a page write, returns, and checks for completion on the next pass:

typedef enum { LOG_IDLE, LOG_WRITING } log_state_t;
static log_state_t log_state = LOG_IDLE;

void log_job(void)                       /* each call: a few us */
{
    switch (log_state) {
    case LOG_IDLE:
        if (log_has_page()) {
            flash_start_page_write(log_next_page());
            log_state = LOG_WRITING;
        }
        break;
    case LOG_WRITING:
        if (flash_done())
            log_state = LOG_IDLE;
        break;
    }
}

Do the same to the display update by redrawing a few lines per pass. If every job returns within about 1 ms, the loop time drops to a few milliseconds and the marginal host-command deadline becomes comfortable. This is cooperative multitasking: each job promises to give the CPU back quickly.

Run jobs at their own rates. Use a millisecond tick from a timer and run each job only when its period has elapsed, so slow jobs stop consuming every pass.

Many shipping products are exactly this: interrupts, a tick, and a set of small state machines. It uses little RAM, is easy to reason about, and has no scheduler to configure.

When the superloop stops being the simple option

Cooperative designs have a weakness: every job must be written to yield, forever, including code you did not write. These requirements are the honest signals that a preemptive RTOS will be simpler overall:

  • Several independent deadlines, some long jobs that cannot be split. A compression routine, a cryptographic operation or a large FFT that takes 30 ms of pure computation cannot yield without being rewritten. With preemptive priorities, a 10 ms control task interrupts it whenever it is due.
  • Blocking software stacks. Network stacks, USB stacks and file systems are usually written to wait for events. In a superloop you must turn each into a state machine; with an RTOS, each runs in its own thread and simply blocks.
  • Many timeouts. "Wait for a reply for at most 200 ms, retry three times" in several protocols at once becomes a tangle of timers in a superloop and a single blocking call with a timeout in an RTOS.
  • You need to analyse response times formally. With fixed priorities and preemption, a standard calculation gives each task's worst-case response time, as shown in Will every task meet its deadline? Response-time analysis worked by hand.

What an RTOS costs

The scheduler is not free, and the costs should be in the decision too:

  • RAM for stacks. Each task needs its own stack, sized for its worst case plus interrupts. Five tasks with modest stacks can use more RAM than the entire superloop program.
  • New classes of bugs. Shared data between tasks needs mutexes or queues, which bring deadlock and priority inversion. A superloop has none of these between jobs, only between jobs and interrupts.
  • Configuration and learning. Priorities, stack sizes, tick rate, which calls are allowed from interrupts. Open-source RTOSes such as Zephyr bring drivers and networking with them, which can tip the balance even for a simple product.

A short decision procedure

  1. List every deadline and period, with the source of each number.
  2. Estimate or measure each job's worst-case time.
  3. Add up the loop time and compare with each deadline, as in the table above.
  4. Try the three stretching techniques on paper. If every requirement is met with margin, stay with the superloop.
  5. If a requirement still fails because work cannot be split, or because you are integrating blocking stacks, choose an RTOS, and write down which requirement made you do it.

Try it yourself

  1. Take a project you know and fill in the requirements table for it. Show it to a colleague and ask them to challenge every worst-case number.
  2. In the Ketuna track D labs on QEMU, lab D4 is an interrupt-driven superloop and lab D5 adds a small preemptive kernel. Run the same periodic job in both and compare its measured jitter under QEMU's instruction-count clock (-icount), remembering that QEMU timing is repeatable but not that of real silicon.
  3. Rewrite a blocking job as a state machine, then ask an AI assistant to do the same, and compare the two for missed states and timeouts.
