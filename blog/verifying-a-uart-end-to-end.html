Verifying a UART end to end: framing, baud error and coverage closure

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Check every field of a UART frame, work out how much baud mismatch a receiver must tolerate and test it with a fractional-rate driver, then close coverage on parity, framing and glitch errors.

A UART is often the first protocol block students design, and most UART testbenches stop at a loopback test: send a byte, receive the same byte, pass. That test exercises the happy path at exactly the right baud rate with perfect frames. Real receivers face transmitters whose clocks are a little fast or slow, lines that glitch, and frames with bad parity or a missing stop bit. Verifying a UART properly means checking each part of the frame, deliberately sending imperfect traffic, and proving with coverage that every error case was exercised.

The frame and where the receiver samples

An asynchronous serial frame has no clock. The line idles high; a falling edge marks the start bit; data bits follow least significant first; an optional parity bit comes next; and one or more stop bits return the line high. The receiver finds the start edge, waits half a bit to reach the middle of the start bit, checks the line is still low, then samples once per bit time in the middle of each following bit.

The data pattern drawn here is 0x5A (bits 0, 1, 0, 1, 1, 0, 1, 0 from D0 to D7), with even parity, so the parity bit is 0.

How much baud error a receiver can tolerate

The receiver resynchronises only at the start edge. After that, any difference between the transmitter's bit time and the receiver's bit time accumulates across the frame. The last sample, in the stop bit, is where error is largest.

For a frame with 8 data bits and parity, the stop-bit sample lands 10.5 bit times after the start edge. The sample stays inside the correct bit as long as the accumulated drift is less than half a bit:

|relative baud error| × 10.5 < 0.5, so |error| < 0.5 / 10.5 ≈ 4.8%

Without parity the last sample is at 9.5 bit times and the limit is 0.5 / 9.5 ≈ 5.3%. A receiver that detects the start edge with a 16× oversampled clock can be up to one sixteenth of a bit late finding it, which eats into the margin: (0.5 − 1/16) / 10.5 ≈ 4.2% with parity. These limits are for the combined mismatch between both ends, and real designs keep a good share of the margin for the other device's clock error.

Clock division adds its own error. With an illustrative 50 MHz clock and 16× oversampling at 115,200 baud, the ideal divisor is 50,000,000 / (16 × 115,200) ≈ 27.13. Rounding to 27 gives 115,741 baud, about 0.47% fast, before any oscillator tolerance is counted.

A driver that can send at any rate

To test tolerance, the testbench must transmit at rates the design's own transmitter never produces. A cocotb driver with a bit time in picoseconds can do that directly.

from cocotb.triggers import Timer

async def send_frame(line, byte, baud, error_pct=0.0,
                     parity="even", stop_val=1):
    bit_ps = round(1e12 / (baud * (1 + error_pct / 100)))
    bits = [(byte >> i) & 1 for i in range(8)]
    frame = [0] + bits
    if parity is not None:
        p = sum(bits) % 2
        frame.append(p if parity == "even" else 1 - p)
    frame.append(stop_val)
    for b in frame:
        line.value = b
        await Timer(bit_ps, unit="ps")
    line.value = 1                       # back to idle

error_pct skews the rate, parity can be made wrong by passing the opposite setting, and stop_val=0 produces a framing error. A short low pulse on an idle line, shorter than half a bit, tests start-bit glitch rejection.

Checks for each part of the frame

A scoreboard compares received bytes and error flags with what the driver sent. Each plan item needs its own check:

Item Stimulus Expected
Data order All 256 byte values Received byte equals sent byte
Parity Correct and inverted parity Error flag only on inverted
Stop bit stop_val = 0 Framing error, no valid byte
Glitch Low pulse under half a bit No frame started
Back to back Next start bit right after stop No byte lost
Baud skew −4% to +4% in steps Correct bytes inside the design's stated tolerance

The baud-skew row needs a stated tolerance from the spec. If the spec does not give one, that is the first finding of the verification effort.

Closing coverage on the error cases

Random tests at nominal baud will hit all data values quickly and almost never produce errors, because the driver produces perfect frames unless told otherwise. Coverage makes that visible.

A reasonable coverage model samples once per received frame or detected error, with bins for data corners (0x00, 0xFF, 0x55, 0xAA, other), error type (none, parity, framing, glitch rejected), baud skew class (slow edge, nominal, fast edge), and the gap before the frame (zero idle, short, long). Cross error type with skew class, because a parity error at the edge of tolerance exercises different sample timing from one at nominal rate.

Closing it is then deliberate work: weight the random generator so a fraction of frames carry each error, sweep skew at the boundaries, and add directed tests for the combinations that stay empty. When a bin will not close, ask whether the case is truly reachable and, if not, waive it with a written reason.

Try it yourself

  1. Write a UART receiver in Verilog with a two-flop input synchronizer, mid-bit sampling and parity and framing error outputs.
  2. Build a cocotb testbench on Icarus Verilog with the driver above and a scoreboard, and run all 256 byte values at nominal baud.
  3. Sweep error_pct from −6 to +6 in 0.5% steps, find where the receiver starts failing, and compare it with the limit you calculated for your sampling scheme.
  4. Add a Python coverage dictionary for the bins described, and keep adjusting stimulus weights until every error bin and every cross bin is hit.
