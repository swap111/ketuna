RV32I in one sitting: every instruction format and why it is laid out that way

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

RV32I packs every instruction into one of six 32-bit formats. See each format field by field, decode real instructions by hand, and learn why fixed register positions keep the decoder small.

In this article
  1. The six formats at a glance
  2. Why the register fields never move
  3. Opcode, funct3 and funct7
  4. Decoding two instructions by hand
  5. Common mistakes
  6. Try it yourself

When you look at a RISC-V core in a waveform viewer, the instruction bus shows a stream of 32-bit hex numbers. Reading them by hand is a basic skill, and it is easier than it looks because the base integer set, RV32I, uses only six layouts. Once you know the six formats and the reasoning behind them, you can decode most instructions in your head and see why the decoder in the RTL is so short.

The six formats at a glance

Every RV32I instruction is 32 bits wide. The lowest seven bits, [6:0], are always the opcode, which says which family the instruction belongs to. The other fields depend on the format:

  • R-type (register–register): add, sub, and, sll, slt and friends. Two source registers, one destination.
  • I-type (immediate): addi, andi, the shift-immediates, all loads, and jalr. One source register, a 12-bit immediate, one destination.
  • S-type (store): sb, sh, sw. Two source registers (the base address and the data) and a 12-bit offset, but no destination.
  • B-type (branch): beq, bne, blt and so on. Like S-type, but the immediate is a branch offset in multiples of 2 bytes.
  • U-type (upper immediate): lui and auipc. A 20-bit immediate and a destination.
  • J-type (jump): jal. A 20-bit jump offset and a destination for the return address.

Why the register fields never move

Look down any column in the diagram. Wherever rs1 exists, it is in bits [19:15]. Wherever rs2 exists, it is in [24:20]. rd is always [11:7], and funct3 is always [14:12].

This is the single most important design decision in the encoding. Because the source register numbers are always in the same place, the core can start reading the register file before it knows what the instruction is. In a pipelined core, the decode stage wires bits [19:15] and [24:20] straight to the register file's read ports while the opcode logic works out the instruction type in parallel. If an instruction does not actually use rs2, the value read is simply ignored. Reading a register you do not need costs nothing; waiting for decode before reading would add delay to one of the busiest paths in the core.

Look at S-type and you see the price of this rule. A store has no destination register, so bits [11:7] are free. Rather than move rs2 into that space, the designers split the 12-bit offset into two pieces, [31:25] and [11:7], so that rs2 stays where it always is. A split immediate costs a few wires in the decoder, which are cheap. A moved register field would cost a multiplexer in front of the register file, on the critical path.

Opcode, funct3 and funct7

Decoding happens in up to three steps:

  1. The opcode picks the family: 0110011 is register–register arithmetic, 0010011 is immediate arithmetic, 0000011 is loads, 0100011 is stores, 1100011 is branches, 0110111 is lui, 0010111 is auipc, 1101111 is jal and 1100111 is jalr.
  2. funct3 picks the operation within the family: for arithmetic, 000 is add, 111 is and, 110 is or; for loads and stores it gives the size (000 byte, 001 half, 010 word); for branches it gives the comparison.
  3. funct7 separates the few pairs that share a funct3. For R-type, add and sub differ only in bit 30, and so do logical and arithmetic right shifts.

In RV32I the two lowest opcode bits are always 11. Other values in those two bits are used by the compressed (C) extension for its 16-bit instructions, which is how a core with C tells the two lengths apart from the first halfword.

Decoding two instructions by hand

0x002081B3. In binary, the low seven bits are 0110011, so this is R-type arithmetic. Bits [11:7] give rd = 3, [14:12] give funct3 = 0, [19:15] give rs1 = 1, [24:20] give rs2 = 2, and [31:25] are all zero. Funct3 0 with funct7 0 means add: this is add x3, x1, x2. Change bit 30 to 1 and you get 0x402081B3, which is sub x3, x1, x2.

0x00512423. The opcode is 0100011, a store. Funct3 is 010, a word, so it is sw. rs1 = 2 and rs2 = 5. The immediate is bits [31:25] (all zero) joined above bits [11:7] (01000), which is 8. The instruction is sw x5, 8(x2): store x5 at address x2 + 8.

A short Python helper makes the slicing mechanical and is a good habit when you debug a waveform:

def fields(ins):
    return {
        "opcode": ins & 0x7F,
        "rd":     (ins >> 7) & 0x1F,
        "funct3": (ins >> 12) & 0x7,
        "rs1":    (ins >> 15) & 0x1F,
        "rs2":    (ins >> 20) & 0x1F,
        "funct7": (ins >> 25) & 0x7F,
    }

print(fields(0x002081B3))   # add x3, x1, x2
print(fields(0x00512423))   # sw x5, 8(x2): rd field holds imm[4:0]

It slices every field for every instruction, exactly as hardware does. Interpreting which fields matter is the decoder's job.

Common mistakes

  • Reading the S-type "rd" field as a register. In a store it holds the low five bits of the offset.
  • Forgetting the sign. All immediates are sign-extended from bit 31, so 0xFFF in an I-type immediate means −1, not 4095.
  • Treating branch and jump offsets as instruction counts. They are byte offsets, always even.
  • Ignoring funct7. A decoder that checks only opcode and funct3 turns every sub into an add.

Try it yourself

  1. With a RISC-V GCC toolchain, assemble a few lines (add, sw, beq, lui) and run riscv64-unknown-elf-objdump -d on the object file. Decode each hex word by hand before reading the disassembly.
  2. Extend the Python helper to print the instruction name for the R-type and I-type arithmetic families.
  3. Write the same decoder in Verilog as a combinational module, simulate it in Icarus Verilog against your Python results, and check that the register fields are just wires.
