Career paths in embedded systems: firmware, drivers, board support and test

Careers & skills Beginner 27 Nov 2026 6 min read By Ketuna

What application firmware, device driver, board support and embedded test engineers work on, the tools each one uses every day, and how people move from one role to another as their skills grow.

"Embedded engineer" covers a wide range of jobs. One person writes the logic that decides when a motor turns on; another makes a new sensor talk over I²C; a third gets a brand-new board to boot for the first time; a fourth builds the rig that tests a thousand units. All of them write C, read datasheets and use a debugger, but their days look quite different. Knowing the differences helps you choose a first role and plan the next one.

The layers of an embedded product

Most embedded software sits in layers. At the bottom is the hardware: a microcontroller or processor, memory, peripherals and the board that connects them. Above it sits board support, the code that starts the chip, sets up clocks and memory and describes what is on the board. Next come drivers, which give each peripheral a clean interface. On top is application firmware, the product behaviour, often running on a real-time operating system such as Zephyr. Test cuts across all layers and checks that each one does its job.

The roles below map onto these layers. Small teams merge them, and one engineer may do all four. Larger teams separate them.

Application firmware

Application firmware engineers implement what the product does: read sensors, run control loops or state machines, handle user input, manage power modes, talk to a phone or a server. A typical day involves writing C (sometimes C++ or Rust), structuring work into tasks and interrupts, and testing behaviour on a development board.

The hard parts are timing and resources. A task that must respond within 2 ms, a buffer that must fit in a few kilobytes of RAM, a battery that must last months: these constraints shape every design decision. Good firmware engineers think in terms of state machines, worst-case response time and what happens when two events arrive at once.

Daily tools: an editor, GCC or Clang for the target, a debug probe with GDB, a serial terminal, an RTOS, and a unit-test framework that runs on the host computer.

Device drivers

Driver engineers make hardware usable. Given a peripheral, such as a UART, an SPI flash chip, an analog-to-digital converter or a display controller, they read its datasheet, write the register-level code, handle interrupts and direct memory access, and expose a simple interface to the layers above.

A typical day is spent with the datasheet in one window, the code in another and a logic analyser on the bench. Most bugs are a mismatch between what the code believes and what the hardware does: a bit set in the wrong order, a missing delay after reset, a status flag that clears on read. Drivers reward careful reading and a habit of checking every assumption with a measurement.

Board support and bring-up

Board support engineers own the boundary between a new board and the software. They write or adapt startup code and linker scripts, configure clocks and memory, write device tree or board configuration files, port a bootloader or an RTOS to new hardware, and lead bring-up: the first days when a fresh board is powered on and nothing works yet.

Bring-up is detective work. The board may not boot because of a firmware bug, a wrong strap resistor, a power rail that comes up in the wrong order or a solder fault. Board support engineers work closely with hardware designers, read schematics fluently and use an oscilloscope as often as a debugger. This role gives you the widest view of the whole system.

Embedded test and validation

Test engineers make sure firmware and hardware work together, repeatably. They write unit tests that run on a host, integration tests that run on real boards, and hardware-in-the-loop setups where a computer drives inputs and measures outputs. They also maintain continuous integration so every change is tested before it merges, and they write test plans that trace back to requirements.

A good test engineer thinks like an attacker: what happens on a brown-out, a full buffer, a corrupted packet, a sensor that returns garbage? Python is the main language, alongside C for test firmware, plus emulators such as QEMU and Renode that run firmware without hardware.

Comparing the roles

Role Main question Daily tools
Application firmware Does the product behave correctly under its timing and memory limits? C, RTOS, GDB, host unit tests
Device drivers Does the code match what the hardware actually does? Datasheets, C, logic analyser
Board support Does this new board boot and run the software stack? Linker scripts, schematics, oscilloscope
Test and validation Can we prove it works and keeps working after every change? Python, QEMU, Renode, CI, test rigs

How people move between roles

The roles share a base: C, the memory model of a microcontroller, interrupts, a debugger and the ability to read a datasheet. Because of that base, moves between them are common.

  • Test to firmware. Writing tests teaches you the product's behaviour in detail and where it breaks. Many engineers move from test into feature work with that knowledge.
  • Firmware to drivers. When the application needs a peripheral that has no driver yet, the firmware engineer often writes it, and discovers a taste for register-level work.
  • Drivers to board support. Driver experience plus schematic reading is most of what board bring-up needs.
  • Any role to embedded Linux or systems roles. Experience with drivers and board support transfers to kernel drivers and boot flows on larger processors, though that is a deeper area with its own learning curve.

The common mistake is staying only at the top layer. An application engineer who has never looked at a driver struggles when the bug is underneath. Spending some time one layer below your job makes you better at your job.

Try it yourself

  1. Write a bare-metal "hello" over UART for an RV32 target, build it with a RISC-V GCC toolchain and run it on QEMU's virt machine. You have just done board support: startup code, a linker script and a minimal driver.
  2. Add an interrupt-driven receive path with a ring buffer and test it under load. That is driver work.
  3. Port the same behaviour to a Zephyr sample application and run it in QEMU or Renode. That is application firmware on an RTOS.
  4. Write a Python script that sends input to the emulated UART and checks the output automatically. That is test, and it ties the other three together.
