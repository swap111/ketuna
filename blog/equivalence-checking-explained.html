Equivalence checking: proving synthesis did not change your design

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

How combinational and sequential equivalence checking compare a netlist with its RTL, what compare points and miters are, and why retimed flops, re-encoded state machines and X assignments need help.

You spent weeks verifying the RTL. Then synthesis rewrote it into thousands of gates, the place-and-route tool added buffers and resized cells, and someone applied a late fix directly to the netlist. Is the netlist still the design you verified? Re-running every simulation on the gate-level netlist would be slow and would still only cover the tests you have. Equivalence checking answers the question directly and completely: it proves, for every possible input, that two representations of the design behave the same.

Golden, revised and the miter

An equivalence check always compares two designs. The golden design is the trusted reference, usually the verified RTL. The revised design is the new version: the synthesised netlist, a netlist after a fix, or an RTL refactor that should not change behaviour.

The idea underneath is the miter. Feed both designs the same inputs, XOR each pair of corresponding outputs, and OR all the XORs together. The two designs are equivalent exactly when no input can make the miter output 1. That turns "are these the same?" into a satisfiability question a solver can answer: either it proves the miter is always 0, or it returns an input that makes the outputs differ.

Combinational equivalence: cut at the flops

Building one miter over a whole chip and many clock cycles would be hopeless. Combinational equivalence checking avoids time altogether. It assumes that every flip-flop in the golden design has a matching flip-flop in the revised one, and treats each matched pair as both an output (its D input is compared) and an input (its Q output is a shared free variable). The design breaks into many small logic cones, each ending at a primary output or a flop's D pin, called compare points or key points.

For each cone, the tool asks whether the golden and revised logic compute the same Boolean function of the cone's inputs. Each question is a small SAT problem. Because cones are checked independently, the method scales to whole chips. If every cone matches, and the flops are matched correctly, the two designs produce identical outputs on every cycle from any matching state.

Most of the effort goes into matching. Synthesis renames registers, adds suffixes for bits of a bus, and sometimes merges duplicate flops or removes constant ones. Tools match by name first, then by structure and function. Every unmatched point must be explained before the result means anything; an unmatched flop is a cone nobody compared.

Sequential equivalence: when the flops do not line up

Some legitimate transformations break the one-to-one flop correspondence:

  • Retiming moves registers across logic to balance paths, so the golden and revised flops hold different intermediate values.
  • State re-encoding turns a binary FSM into a one-hot one; three flops become five.
  • Clock gating replaces an enable mux with a gated clock, so a flop no longer loads on every edge.
  • Pipeline changes add or remove a stage while keeping the interface timing equivalent under some conditions.

Here no cone-by-cone mapping exists. Sequential equivalence compares the designs over time, from matching reset states, using model checking or induction. It is far more expensive and is typically run on the blocks where those transformations happened, not on the whole chip.

A small open-source check

Yosys includes equivalence commands. This script compares an RTL module against its own synthesised netlist.

read_verilog alu.v
prep -top alu
rename alu gold
design -stash gold

read_verilog alu.v
synth -top alu
rename alu gate
design -stash gate

design -copy-from gold -as gold gold
design -copy-from gate -as gate gate
equiv_make gold gate equiv
hierarchy -top equiv
equiv_simple
equiv_induct
equiv_status -assert

equiv_make builds the combined circuit and matches signals by name. equiv_simple proves cones combinationally; equiv_induct uses induction for the cases that need a little sequential reasoning. equiv_status -assert exits with an error if anything stays unproven, which makes the script usable in a regression. For larger designs, the eqy front end partitions the problem and runs these steps per partition.

Where the tools need help

An equivalence failure is not always a bug, and a pass is not always meaningful. The common trouble spots:

  • X assignments in RTL. default: out = 'x; tells synthesis it may choose any value. The netlist picks one; a strict comparison against the RTL's X then fails or passes depending on how the tool treats don't-cares. Know which mode you are in.
  • Test logic. Scan insertion changes the netlist's behaviour in test mode. Tie scan-enable to its functional value during the check.
  • Black boxes. Memories and analog macros have no gate-level logic to compare; they are black-boxed, and only their pins are checked. Anything inside them needs separate verification.
  • Removed or merged flops. A flop synthesis proved constant has no partner. Confirm that the constant really is constant in your RTL, not a sign of a missing connection.
  • Aborted cones. Large arithmetic, such as multipliers, can be too hard for a plain SAT check. Tools need hints, partitioning or special datapath methods.

What it does not tell you

Equivalence checking proves the two designs match. If the golden RTL has a bug, the netlist faithfully has the same bug. It also says nothing about timing, power or clock-domain crossings. It replaces "re-simulate everything on the netlist" for functional sameness, and nothing more.

Try it yourself

  1. Write a small 8-bit ALU in Verilog, save the script above as eq.ys, and run yosys -s eq.ys; confirm equiv_status reports everything proven.
  2. Edit one gate in the synthesised netlist by hand (write it out with write_verilog, change an AND to an OR, read it back as the gate design) and rerun; find the unproven signal in the report.
  3. Add an FSM to the design, run synth with and without -nofsm, and compare how the equivalence check behaves when state encoding changes.
