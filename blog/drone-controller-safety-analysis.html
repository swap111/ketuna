Safety analysis for a drone controller: failure modes and fail-safe behaviour

Systems & product engineering Advanced 27 Nov 2026 5 min read By Ketuna

What a multirotor flight controller should do when it loses the control link, its position fix, a sensor or its supply, how to rank simultaneous failures, and why a reset in flight is a hazard in its own right.

A multirotor has no glide. If its controller stops commanding the motors for even a fraction of a second, it falls. That single fact shapes the whole safety analysis of a flight controller: every failure has to be answered by a defined, tested behaviour, and "reset and try again" is often the most dangerous response of all. This article works through the main failure modes of a small multirotor controller and how to design the safe response to each.

Drones can injure people and damage property. Operation in India is governed by the national civil aviation regulator's rules, which cover registration, permitted zones and operator requirements; check the current rules before any flight, and test fail-safes only in a safe, permitted area.

Start from hazards and states

A safety analysis begins with what can hurt someone: an uncontrolled descent onto people, a fly-away beyond the operator's control, a crash into an obstacle, a battery fire after impact. Then it asks, for each failure, which hazard it leads to and what response minimises it.

Fail-safe responses for multirotors usually come from a short menu, in rough order of how much the vehicle still needs to work:

  • Hold: stop and hover in place. Needs attitude, altitude and position sensing.
  • Return to launch: fly back to the take-off point and land. Needs a position fix and enough battery.
  • Land in place: descend at a controlled rate where it is. Needs attitude and some altitude estimate.
  • Controlled descent without position: level attitude, slow descent, accept drift. Needs only attitude.
  • Motor stop: only appropriate on the ground or after a crash is detected.

The right response to a failure is the most capable one whose requirements are still met.

Failure modes and responses

Here is a partial analysis for a small multirotor. The responses are typical choices, not the only correct ones; open-source autopilots such as PX4 and ArduPilot make many of them configurable, which is itself a hint that the right answer depends on the mission.

Failure Detection Typical response
Control link lost No valid frame for a timeout Hold briefly, then return to launch if position is good, else land
Position fix lost or degraded Satellite count, accuracy estimate, innovation checks Switch to altitude hold; land if the operator link is also lost
One inertial sensor faulty Disagreement with a redundant sensor, range checks Switch to the healthy sensor; land
Compass disturbed Disagreement with expected field, heading innovations Inhibit position modes that rely on heading; land
Battery low / critical Voltage under load, estimated remaining energy Return to launch at low; land at critical
Motor or speed controller failure Commanded versus achieved attitude, telemetry Controlled descent; on hexacopters and larger, reallocate to remaining motors
Firmware hang Hardware watchdog Fast restart that resumes flight control (see below)

Two design details turn this table into safe behaviour. Timeouts need hysteresis: a link that drops for 200 ms and returns should not trigger a return-to-launch, but one that drops repeatedly should not keep resetting the timer either. Responses need priorities, because failures arrive together: a weak link often coincides with distance, which coincides with low battery.

Combining failures

A simple, reviewable way to combine failures is to evaluate every condition each control cycle and pick the most conservative applicable response. The state can only become more conservative automatically; going back to normal needs the operator.

In code, the selection can be a small, pure function that is easy to unit test exhaustively:

typedef enum { FS_NORMAL, FS_HOLD, FS_RETURN, FS_LAND } fs_state_t;

typedef struct {
    unsigned link_lost_ms;   /* time since last valid control frame */
    int      pos_ok;         /* position estimate trusted */
    int      batt_low;       /* enough for return, but low */
    int      batt_critical;  /* land now */
} fs_inputs_t;

#define LINK_HOLD_MS    500u
#define LINK_RETURN_MS 3000u

static fs_state_t fs_wanted(const fs_inputs_t *in)
{
    if (in->batt_critical) return FS_LAND;
    if (!in->pos_ok && in->link_lost_ms >= LINK_HOLD_MS) return FS_LAND;
    if (in->batt_low) return in->pos_ok ? FS_RETURN : FS_LAND;
    if (in->link_lost_ms >= LINK_RETURN_MS) return FS_RETURN;
    if (in->link_lost_ms >= LINK_HOLD_MS) return FS_HOLD;
    return FS_NORMAL;
}

fs_state_t fs_update(fs_state_t current, const fs_inputs_t *in)
{
    fs_state_t wanted = fs_wanted(in);
    return (wanted > current) ? wanted : current;  /* never relax */
}

The timeouts are illustrative. Because fs_wanted has no side effects, a test can enumerate every combination of inputs and check that the result matches the table agreed in review.

Brown-out and reset are hazards

On the ground, a brown-out reset is an inconvenience. In flight, it stops the motors. Even a fast restart costs height: in free fall a vehicle drops ½gt2, so 0.5 s of no thrust is about 1.2 m, and real recovery also needs time to re-level and arrest the descent. Design to prevent the reset rather than to survive it:

  • Separate, well-filtered supply for the controller, so motor current surges cannot pull its rail down. Add hold-up capacitance sized for the worst dip.
  • Brown-out detector thresholds set so the controller resets only when it truly cannot run, and an early warning interrupt above that threshold to log the event and start a landing.
  • Watchdog recovery that resumes flight, not a cold boot: on a watchdog reset with the vehicle armed, skip calibration and self-tests, restore the last attitude estimate if valid, and resume stabilisation as fast as possible. Record the event for analysis.
  • Never disarm automatically in the air because of a sensor fault. Disarming is a ground action.

Verifying fail-safe behaviour

Fail-safes that are never exercised do not work when needed. Test them in software-in-the-loop simulation first; both PX4 and ArduPilot support simulation, so you can inject link loss, position loss and sensor failures repeatedly. Then hardware-in-the-loop with the real controller, and only then in flight, at low height, in a permitted, empty area, one failure at a time, with a safety pilot able to take over.

Common mistakes

  • Return to launch without checking position quality. A return on a bad fix is a fly-away.
  • Timeouts with no hysteresis. Marginal links cause oscillating behaviour.
  • Treating reset as recovery. In flight, prevent resets; if one happens, resume control immediately.
  • Fail-safes configured but never tested.

Try it yourself

  1. Write a unit test in C that enumerates combinations of the inputs to fs_wanted and compares the result against a table you write by hand. Compile it with GCC.
  2. Run a PX4 or ArduPilot software-in-the-loop simulation, trigger a control-link loss in flight, and record which fail-safe triggers and when.
  3. Measure your controller's reset-to-first-motor-command time on the bench with a logic analyser and compute how far the vehicle would fall in that time.
