Lint warnings that point at real RTL bugs

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

Width mismatches, multiple drivers, combinational loops and unused signals are the lint warnings most worth reading. Here is what each one usually means in real RTL, with examples and fixes.

In this article
  1. Width mismatches
  2. Multiple drivers
  3. Combinational loops
  4. Unused and undriven signals
  5. A habit for reading lint output
  6. Try it yourself

The first time you run a lint tool on your Verilog, it prints dozens of warnings, and the temptation is to switch most of them off. That throws away the cheapest bug-finding you will ever get. A linter reads your code without simulating it and flags patterns that are legal but suspicious. Most warnings in a beginner's code fall into a few families, and each family usually points at a specific, real mistake. Learning to read them takes an afternoon and saves days of waveform debugging.

Width mismatches

Verilog silently extends or truncates values when the widths on the two sides of an assignment differ. The linter does not.

reg [7:0] cnt;
always @(posedge clk)
  if (cnt == 300) cnt <= 8'd0;     // 300 needs 9 bits
  else            cnt <= cnt + 8'd1;

The designer wanted a counter that wraps after 300. An 8-bit cnt can never reach 300, so the comparison is never true and the counter wraps at 256 instead. Nothing fails to compile, and a short simulation that never runs 256 cycles will not show it. The linter warns that the two sides of the comparison have different widths. What width warnings usually mean:

  • A counter or register that is too narrow for the value it is compared with or must hold, as above.
  • A missing carry or sign bit, where a 9-bit sum is assigned to an 8-bit target. Widen the target, or take the bits you want explicitly.
  • An unsized constant such as 0 or 1, which Verilog treats as 32 bits. Some linters flag cnt + 1 for this reason. Write 1'b1 or 8'd1.

When a truncation is intentional, make it explicit, for example assign low = full[7:0];, so the next reader and the linter both know you meant it.

Multiple drivers

A signal driven from two places has no defined value when the two disagree.

always @(posedge clk) if (load)  count <= din;
always @(posedge clk) if (inc)   count <= count + 1;

Each block alone looks fine. Together they describe two registers fighting over one output. In simulation, whichever block runs last on a given edge wins, so the behaviour depends on scheduling order. Synthesis may reject it or build something you did not intend. What it usually means:

  • Logic split across blocks that belongs in one. Merge it into a single always block with an explicit priority: if (load) … else if (inc) ….
  • A copy-paste error, where a second block was meant to drive a different signal.
  • Two assign statements on one wire, often from connecting two module outputs to the same net.

Genuine multiple drivers exist only for tri-state buses, which are rare inside modern chips.

Combinational loops

A combinational loop is a path from a signal, through logic, back to itself, with no flip-flop in between.

assign ready_out = valid_in & ready_in;
assign ready_in  = ~busy | ready_out;   // depends on ready_out

Such a loop can oscillate, latch up in one state, or have a value that depends on gate delays. Static timing tools cannot time it properly, and simulators may hang or report that they cannot settle. Verilator, for example, warns about signals involved in circular logic. What it usually means:

  • A handshake signal wired back on itself, often across two modules, each of which looks fine alone. This is common with valid/ready interfaces.
  • A Mealy output of one state machine feeding the input of another, whose Mealy output feeds back to the first.
  • A missing register where you intended one stage of delay.

The fix is almost always to break the loop with a flop, or to restructure so one side's output does not depend combinationally on its input. Loops spanning modules are easiest to find by drawing the signals between blocks on paper.

Unused and undriven signals

A signal that is assigned but never read, or read but never assigned, is the linter's way of finding typos and broken connections.

wire overflow_flag;      // declared
assign overfow_flag = (count == MAX);  // typo creates a new wire

With implicit nets allowed, which is the Verilog default, the typo silently creates a new 1-bit wire. overflow_flag is now never driven, and overfow_flag is never used. The linter reports both. What these warnings usually mean:

  • A typo in a name. Adding `default_nettype none at the top of each file turns implicit nets into errors, which catches this at compile time.
  • A port left unconnected at an instance, so an input floats or an output goes nowhere.
  • Leftover logic from an earlier version that synthesis will remove, which is harmless but hides real warnings in the noise.
  • Unused bits of a bus, for example the low bits of an address that is always aligned. These are often fine; acknowledge them explicitly, with a lint waiver comment or by naming them as unused, so they stop cluttering the report.

A habit for reading lint output

  • Run lint early and often, on every file, before simulation. A clean module stays clean if you check it each time you edit.
  • Fix, do not filter. Turn a warning off only for a specific line, with a comment explaining why it is intentional.
  • Read the first warning first. One typo can cause a cascade of later warnings; fixing it often clears many.
  • Ask why before you fix. A width warning fixed by widening a target hides the bug if the real mistake was the wrong operand.

Verilator reports these families under names such as WIDTH (split into more specific names in newer versions), MULTIDRIVEN, UNOPTFLAT, UNUSED and UNDRIVEN. The exact names differ by tool and version, so check the documentation of the tool you use. The meaning is what matters.

Try it yourself

  1. Put each of the four examples in its own file and run verilator --lint-only -Wall on it. Write down what you expect it to say before you run it, then compare.
  2. Add `default_nettype none to the unused-signal example and run Icarus Verilog (iverilog -g2012) on it to see the typo become an error.
  3. Run Yosys on the multiple-driver example with read_verilog, proc and check, and compare its report with the Verilator output.
