Running firmware without a board: QEMU and Renode in CI

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

Emulators let every commit boot the real firmware binary, run its self-tests and check its output. How to make firmware report pass or fail to the emulator, script the run, and know what still needs hardware.

Host unit tests check your logic, but they never run the startup code, the linker script, the interrupt vectors or the drivers as compiled for the target. Those break too: a changed compiler flag moves a section, a new interrupt handler is never registered, a stack grows into data. Catching that on every commit used to require a rack of boards. Emulators such as QEMU and Renode run the same binary you would flash, on a laptop or a CI server, with no hardware at all. This article shows how to turn an emulator run into an automated test, and where the emulator stops telling the truth.

What an emulator gives you

QEMU and Renode both execute the target's instructions and model a set of peripherals: interrupt controllers, timers, UARTs and more, depending on the machine. The firmware cannot tell the difference for anything that is modelled. So an emulator run checks:

  • that the image boots: reset vector, stack, .data copy, .bss zeroing;
  • that interrupts are wired: trap vector, controller configuration, handler dispatch;
  • that drivers talk to the modelled peripherals correctly;
  • that integration works: the scheduler, the protocol stack and the application together.

QEMU is fast and widely packaged, with machines such as the RISC-V virt board used throughout the Ketuna track D labs. Renode focuses on modelling whole microcontroller boards and multi-node systems, describes platforms in its own text files, and comes with a Robot Framework integration for writing tests.

Step 1: let the firmware report a result

A CI job needs a pass or fail, not a human reading a console. The firmware must therefore be able to end the emulation with a status.

QEMU's RISC-V virt machine has a small "test finisher" device. Writing 0x5555 to it exits QEMU with status 0; writing (code << 16) | 0x3333 exits with status code:

#include <stdint.h>

#define TEST_FINISHER 0x00100000u

void test_finish(int code)
{
    volatile uint32_t *fin = (volatile uint32_t *)TEST_FINISHER;
    *fin = (code == 0) ? 0x5555u : (((uint32_t)code << 16) | 0x3333u);
    for (;;) { }                      /* not reached on QEMU */
}

Firmware built for CI runs its self-tests and calls test_finish(0) or test_finish(n) with a failure number. Keep this in a test build only; production firmware should never write to an address that does nothing on real hardware. On machines without such a device, semihosting or simply a final "PASS" line on the UART does the same job.

Step 2: script the run with a timeout

Firmware that hangs must fail the job, not block it forever. Wrap the emulator in timeout, capture the UART output, and compare it with an expected file:

#!/usr/bin/env bash
# run_fw_test.sh ELF EXPECTED: boot firmware on QEMU and check its output
set -euo pipefail
elf=$1
expected=$2
log=$(mktemp)

status=0
timeout 20 qemu-system-riscv32 -M virt -bios none -nographic \
    -monitor none -icount shift=3 -kernel "$elf" > "$log" || status=$?

if [ "$status" -eq 124 ]; then
    echo "FAIL: timed out"; cat "$log"; exit 1
fi
if [ "$status" -ne 0 ]; then
    echo "FAIL: firmware reported status $status"; cat "$log"; exit 1
fi
if ! diff -u --strip-trailing-cr "$expected" "$log"; then
    echo "FAIL: output differs from $expected"; exit 1
fi
echo "PASS: $elf"

timeout returns 124 when it had to kill the process, which separates a hang from a reported failure. The -icount shift=3 option makes virtual time advance by a fixed amount per instruction, so timer-driven output is identical on every run and every machine. Without it, QEMU's clocks follow the host and a busy CI server can change what timer-based firmware prints. Keep expected output free of anything that legitimately varies, or compare only the lines that matter.

With Renode, the same idea is written as a Robot Framework test: load the platform and binary, create a terminal tester on the board's UART, and wait for an expected line with a timeout. The renode-test command runs such files and produces the pass or fail result for CI.

Step 3: arrange the pipeline

Order jobs by cost, so that cheap failures stop expensive work:

  1. Host unit tests of the pure logic, in seconds.
  2. Cross-build of every target configuration with warnings as errors. Keep the ELF, the map file and the size report as artefacts; the map file of a failed build is the first thing you will want.
  3. Emulator tests, one script call per firmware test image.
  4. Hardware-in-the-loop on a few real boards, nightly or before a release.

Each stage should be a script that runs identically on a developer's laptop and on the CI server. If a test can only run in CI, people stop running it before they push.

What still needs a real board

An emulator models behaviour, not physics, and its device models are simplified. Plan for these on hardware:

  • Timing. Emulators have no pipeline, cache or bus timing that matches silicon. Instruction counts are meaningful; microseconds are not.
  • Overruns and back-pressure. QEMU's UART, for example, holds host input back when its receive buffer is full, so bytes are delayed rather than lost. A real UART drops them.
  • Analog, power and RF. ADC noise, brown-outs, current draw, radio links.
  • Peripheral details and silicon errata. A model implements the documented behaviour; the real chip may differ, and the model may not implement every mode you use.
  • Electrical problems. Pull-ups, signal integrity, connectors, clock tolerance.

A useful habit: whenever a bug is found on hardware, ask whether an emulator test could have caught it. If yes, add one. If not, write down why, which tells you what your hardware tests must cover.

Try it yourself

  1. Install qemu-system-misc and gcc-riscv64-unknown-elf, build a minimal bare-metal program for the virt machine that prints one line and calls test_finish(0), run it with the QEMU command from the script, and check echo $?.
  2. Write the script above for one of your own images, make the firmware call test_finish(3) on purpose, and check that the job fails with status 3.
  3. Add an infinite loop to the firmware and confirm the script reports a timeout rather than hanging.
  4. Install Renode, run one of its bundled demo scripts, then write a Robot test that waits for your firmware's start-up banner on the UART.
