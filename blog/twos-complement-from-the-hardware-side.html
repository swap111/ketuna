Two's complement from the hardware side: why one adder does signed and unsigned

Digital & VLSI design Beginner 27 Nov 2026 6 min read By Ketuna

The same binary adder adds signed and unsigned numbers; only the interpretation and the overflow check differ. Learn the overflow rules, sign extension and the Verilog signed traps.

In this article

  3. Two different overflow checks
  4. Sign extension

A processor has one adder, yet it adds both unsigned int and int correctly. There is no separate signed adder hiding somewhere. Two's complement is the encoding that makes this possible, and once you see it from the hardware side, overflow flags, sign extension and the odd behaviour of Verilog's signed keyword all make sense.

One bit pattern, two meanings

An 8-bit register holds a pattern of eight bits. Read as unsigned, the bits have weights 128, 64, 32, 16, 8, 4, 2, 1, so the range is 0 to 255. Read as two's complement signed, the top bit has weight −128 instead of +128, and the range is −128 to +127.

Bits Unsigned Signed
0000_0101 5 5
0111_1111 127 127
1000_0000 128 −128
1111_1101 253 −3
1111_1111 255 −1

Notice that the signed and unsigned values of any pattern differ by exactly 256, or not at all. That is the key fact. An 8-bit adder computes the sum modulo 256, discarding the ninth bit. Since both interpretations are equal modulo 256, a sum that is correct modulo 256 is correct for both, as long as the true result fits in the range.

To negate a number, invert all the bits and add 1. Inverting gives 255 − x; adding one gives 256 − x, which is −x modulo 256. Subtraction is then a + ~b + 1, so the hardware reuses the adder with an inverter on one input and the carry-in set to 1.

A worked addition

Add 1111_1101 and 0000_0101:

    1111_1101      unsigned 253   signed -3
  + 0000_0101      unsigned   5   signed  5
  -----------
  1 0000_0010      8-bit result 2, carry-out 1

As signed numbers, −3 + 5 = 2: correct. As unsigned numbers, 253 + 5 = 258, which does not fit in 8 bits; the 8-bit result 2 is 258 − 256. The adder did the same thing in both cases. What differs is how you decide whether the answer is valid.

Two different overflow checks

  • Unsigned overflow is the carry-out of the top bit. In the example above, carry-out is 1, so the unsigned sum overflowed.
  • Signed overflow happens when two operands of the same sign give a result of the other sign. Adding two positives cannot give a negative, so if it does, the true answer was above 127.

In hardware, signed overflow is the XOR of the carry into the top bit and the carry out of it. Try 0111_1111 + 0000_0001: the result is 1000_0000, a carry goes into bit 7 but none comes out, so the XOR is 1. As signed numbers, 127 + 1 has overflowed to −128. As unsigned numbers, 127 + 1 = 128 is perfectly fine and the carry flag is 0.

This is why processors provide both a carry flag (C) and an overflow flag (V). The adder sets both every time; the program picks the one that matches how it is treating the numbers.

The same idea gives you comparisons for free. To compare a and b, the hardware computes a − b as a + ~b + 1 and looks at the flags, not at the result itself:

  • Unsigned: a is less than b when the subtraction produces no carry-out. A carry-out of 1 means "no borrow was needed", so a was at least b.
  • Signed: a is less than b when the sign bit of the result (N) differs from the overflow flag (V). If there was no overflow, a negative result means a is less than b. If there was overflow, the sign bit is wrong, so you flip the answer.

Check it with a = −3 (1111_1101) and b = 5. The subtraction gives 1111_1000 with a carry-out of 1 and no signed overflow. Unsigned, 253 is not less than 5, which matches the carry. Signed, N = 1 and V = 0, so −3 is less than 5. One subtractor, two different answers, both right for their interpretation.

Sign extension

To widen a signed value, copy its top bit into all the new upper bits. −3 in 8 bits is 1111_1101; in 16 bits it is 1111_1111_1111_1101. Padding with zeros instead would turn it into 253. Unsigned values are widened with zeros. Getting this wrong is one of the most common sources of arithmetic bugs in RTL, because the result looks plausible for positive inputs and only fails for negative ones.

The Verilog signed traps

Verilog decides whether an expression is signed by looking at all its operands. If any operand is unsigned, the whole expression is evaluated as unsigned, and smaller operands are zero-extended.

module sx_demo (
  input  wire signed [7:0] a,
  input  wire        [7:0] b,      // unsigned
  output wire signed [15:0] y_bad,
  output wire signed [15:0] y_ok
);
  // b is unsigned, so a is zero-extended: -3 becomes 253
  assign y_bad = a + b;
  // $signed treats b's bits as signed; a sign-extends correctly
  assign y_ok  = a + $signed(b);
endmodule

With a = -3 and b = 5, y_bad is 258 and y_ok is 2. Other traps worth knowing:

  • Part-selects are unsigned. a[7:0] is unsigned even when a is declared signed, so it will not sign-extend.
  • Unsized literals and concatenations. {a, 1'b0} is unsigned. Wrap it in $signed() when you need it signed.
  • Comparisons. A less-than comparison with one unsigned operand compares the bit patterns as unsigned, so −1 is "greater than" 5.
  • $signed on a 1-bit value. $signed(1'b1) is −1, not +1. Zero-extend first if you mean +1.

A safe habit is to make every operand in a signed expression explicitly signed and of the result width, and to read the elaborated widths in a lint report rather than assuming.

Common mistakes

  • Checking the carry flag for signed overflow, or the overflow flag for unsigned results
  • Forgetting to grow the result by one bit when you want the full sum instead of a wrapped one
  • Mixing signed and unsigned operands and expecting signed behaviour
  • Sign-extending an unsigned quantity, such as an ADC code that is offset binary rather than two's complement

Try it yourself

  1. Work the five rows of the table by hand, then write a Python loop that prints each 8-bit pattern with its unsigned and signed values (x - 256 if x > 127 else x) and check your answers.
  2. Simulate sx_demo in Icarus Verilog with iverilog -g2012 and print y_bad and y_ok using %d for several negative values of a.
  3. Add a signed-overflow output computed as the XOR of the carries into and out of bit 7, and test it on 127 + 1, −128 + −1 and −3 + 5.
