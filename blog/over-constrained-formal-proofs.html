How over-constrained assumptions make formal proofs lie

Verification Advanced 27 Nov 2026 5 min read By Ketuna

An assumption that is too strong can make a formal proof pass while checking nothing. Learn how vacuous passes and conflicting assumptions arise, and how cover statements and assumption reviews expose them.

In this article

  2. Three ways a proof ends up lying
  3. Covers are the antidote
  4. Checking and reviewing assumptions
  5. Try it yourself

A formal proof is only as honest as its assumptions. Every assume statement removes behaviour from the set the solver explores, and the solver does not know which removals reflect the real environment and which reflect an engineer's impatience. Remove too much and the proof passes because the failing scenario has been ruled out, not because the design handles it. The tool reports PASS in the same colour either way. This article shows how proofs end up lying, and the cheap habits that catch it.

What an assumption really does

To a model checker, an unconstrained input can take any value on any cycle. An assumption narrows that. assume (!(wr_en && full)) says: consider only input sequences in which the producer never writes while the FIFO is full. If the real producer obeys that rule, the assumption is a faithful model of the environment and the proof is meaningful. If the real producer can write when full, the proof has excluded exactly the case that matters.

Assumptions are not checked by the proof that uses them. They are taken as true. That is the root of every problem below.

Three ways a proof ends up lying

Assuming away the bug

The simplest lie is an assumption that forbids the situation where the bug lives. It usually starts innocently. A proof fails with a counterexample that looks "unrealistic", so someone adds an assumption to suppress it.

// Counterexample showed a write on the cycle after reset.
// "That never happens", so:
always @(posedge clk) if (f_past_valid && $past(rst)) assume (!wr_en);

Perhaps it never happens with today's producer. But the counterexample may also have been pointing at a real reset bug, such as a pointer that is not cleared until a cycle after rst falls. The assumption hides it permanently. Every assumption added in response to a counterexample should be traced to a written rule in the interface spec. If there is no such rule, the counterexample is a question for the designer, not a nuisance for the verifier.

A related trap is assuming on an output of the design. assume (!full) looks like it constrains the environment but actually constrains the design: it tells the solver to consider only runs in which the FIFO never fills. Every property about full behaviour then passes trivially. As a rule, assume only on inputs, or on relationships between inputs and outputs that the spec assigns to the environment.

Vacuous passes

An implication a |-> b passes on every cycle where a is false. If the assumptions make a impossible, the assertion passes on every cycle without ever checking b. That is a vacuous pass.

// Environment assumption, slightly too strong:
always @(*) assume (!(req0 && req1));      // never two requests at once

// The property we care about:
always @(posedge clk)
  if (f_past_valid && $past(req0 && req1))
    assert (gnt0 ^ gnt1);                  // exactly one grant on contention

The assertion exists to check arbitration under contention, and the assumption forbids contention. The proof passes. It has verified nothing about the one behaviour an arbiter exists for. Nobody wrote anything obviously wrong: the assumption was added for a different property, perhaps months earlier, and its interaction with this one went unnoticed.

Conflicting assumptions

If two assumptions contradict each other, no input sequence satisfies both. Then there are no traces at all, and every assertion holds over the empty set. The proof passes in seconds.

Conflicts are rarely as blunt as assume(a) and assume(!a). More often they involve time:

// From the protocol spec: valid stays high until ready
always @(posedge clk)
  if (f_past_valid && $past(valid && !ready)) assume (valid);

// Added later to "speed up the proof": valid is a single-cycle pulse
always @(posedge clk)
  if (f_past_valid && $past(valid)) assume (!valid);

Together these allow valid only on cycles where ready is also high. If a third assumption says ready is low during the first cycles after reset, the reachable behaviour shrinks further, possibly to nothing within the proof depth. Whether the conflict is total or partial, the result is the same kind of lie.

Covers are the antidote

A cover statement asks the solver for a trace that reaches a condition, under the same assumptions as the proof. If a cover is unreachable, something in the assumptions is ruling out behaviour you believe should be possible. That is precisely the signal the assertions cannot give you.

always @(*) if (f_past_valid) begin
  cover (req0 && req1);              // contention can happen
  cover (full);                      // the FIFO can fill
  cover (full && wr_en);             // a write arrives while full
end
always @(posedge clk) if (f_past_valid) cover ($past(valid && !ready) && valid);

Write at least one cover for the antecedent of every important assertion, and for every interesting state in the plan. Run cover mode as a separate task in the same job, and treat an unreached cover as a failed test, not a warning. In the arbiter example, cover (req0 && req1) would come back unreachable and point straight at the over-strong assumption.

A cheap sanity check catches total conflicts: add a cover for a condition that should be trivially reachable a few cycles after reset, such as the reset having been released. If even that is unreachable, the assumptions admit no traces.

Checking and reviewing assumptions

Checking them on the other side

An assumption about a block's inputs is a claim about its neighbour's outputs. That claim can be checked. In simulation of the larger system, compile the same property module with assumptions turned into assertions, so the real neighbour is held to the rule. In formal, prove the neighbour satisfies it as an assertion. This assume-guarantee split means every assumption is either proven somewhere else or explicitly documented as an external requirement.

A review checklist

When you review someone's formal setup, or your own, ask these for every assume:

  • Which spec line justifies it? Is it quoted in a comment?
  • Does it constrain only inputs, or relationships the spec assigns to the environment?
  • Was it added to suppress a counterexample? If so, was that counterexample discussed with the designer?
  • Is there a cover showing that the behaviour it permits still includes the interesting cases?
  • Is it checked as an assertion on the neighbouring block or the system?

Try it yourself

  1. Write a two-requester round-robin arbiter, an assertion that exactly one grant is given under contention, and the over-strong !(req0 && req1) assumption; run SymbiYosys in prove mode and watch it pass.
  2. Add cover (req0 && req1) in a separate cover task and confirm it is reported as unreached.
  3. Remove the assumption, plant a bug that grants both requesters on contention, and confirm the proof now fails with a short trace.
  4. Add the two conflicting valid assumptions to a small valid/ready block and find the simplest cover that exposes the conflict.
