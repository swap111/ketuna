Computing a CRC in hardware: from the polynomial to an LFSR and a parallel form

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

Turn a CRC polynomial into a serial shift-register circuit, check it against a known test vector, then let a short script unroll it into XOR equations that process a whole byte per clock.

A low-power sensor node sends short packets over a noisy radio or a long cable, and the receiver needs to know whether a packet arrived intact. A cyclic redundancy check (CRC) is the usual answer: a few check bits computed from the packet that change if any bit is corrupted in common ways. In software a CRC is a loop or a lookup table. In hardware it is one of the most elegant small circuits you can build: a shift register with a few XOR gates, which you can then unroll to handle a whole byte every clock.

The polynomial as a recipe

A CRC treats the message as a long binary polynomial and computes the remainder after dividing it by a fixed generator polynomial, using arithmetic in which addition and subtraction are both XOR and there are no carries. The remainder is the CRC.

For this article we use the 8-bit generator x8 + x2 + x + 1, a common choice for short packets, written in hex as 0x07 (the x8 term is implied). The details that define a complete CRC variant are the polynomial, the initial register value, whether bits are processed most-significant first, whether the result is inverted, and whether input or output bits are reflected. Here: initial value 0, most-significant bit first, no inversion, no reflection. With those settings, the standard check is that the ASCII string 123456789 gives 0xF4. Always pick your parameters from the specification of the protocol you implement, and test against its check value.

What does the receiver gain? Two properties follow from the algebra. Any CRC whose generator has degree n and a nonzero constant term detects every error burst of length n bits or less, so this one catches any burst of up to 8 bits. And because x8 + x2 + x + 1 has x + 1 as a factor (set x = 1 and the terms sum to 0 under XOR), it detects every error that flips an odd number of bits. A CRC detects errors; it does not correct them, and it is not protection against deliberate tampering.

The serial circuit: an LFSR

Long division by the generator, one message bit at a time, maps directly onto a linear feedback shift register (LFSR). Each clock:

  1. The feedback bit is the register's top bit XORed with the incoming message bit.
  2. The register shifts left by one.
  3. If the feedback is 1, the polynomial is XORed in, which means XOR gates in front of every bit position where the polynomial has a 1 (bits 0, 1 and 2 for 0x07).
module crc8_serial (
  input  wire       clk, rst_n,
  input  wire       init,      // load the initial value
  input  wire       en,        // one message bit this clock
  input  wire       din,       // message bit, MSB of each byte first
  output reg  [7:0] crc
);
  wire fb = crc[7] ^ din;
  always @(posedge clk or negedge rst_n)
    if (!rst_n)    crc <= 8'h00;
    else if (init) crc <= 8'h00;
    else if (en)   crc <= {crc[6:0], 1'b0} ^ (fb ? 8'h07 : 8'h00);
endmodule

Eight flops and three XOR gates. It processes one bit per clock, so a byte takes eight clocks. For a slow serial link that is fine; for a byte-wide bus it is eight times too slow.

Unrolling to a byte per clock

The circuit is linear: every next-state bit is an XOR of some current-state bits and some input bits. So eight serial steps can be collapsed into one combinational step, in which each of the 8 new CRC bits is an XOR of current CRC bits and the 8 data bits. Working out which ones by hand is tedious and error-prone. A script does it by simulating the serial circuit symbolically, tracking for each bit the set of inputs it is an XOR of:

POLY = 0x07                      # x^8 + x^2 + x + 1

def crc8_symbolic():
    crc = [{f"c{i}"} for i in range(8)]
    data = [{f"d{i}"} for i in range(8)]
    for i in range(7, -1, -1):              # MSB of the byte first
        fb = crc[7] ^ data[i]               # set XOR = symmetric diff
        crc = [set()] + crc[:7]             # shift left
        for b in range(8):
            if (POLY >> b) & 1:
                crc[b] = crc[b] ^ fb
    return crc

for b, terms in enumerate(crc8_symbolic()):
    print(f"next[{b}] =", " ^ ".join(sorted(terms)))

The set XOR (symmetric difference) is exactly right because anything XORed twice cancels. The script prints, for example, next[0] = c0 ^ c6 ^ c7 ^ d0 ^ d6 ^ d7. Notice that every equation contains ci and di in pairs. For this CRC, the byte-wide update only depends on crc ^ data, which halves the inputs:

wire [7:0] x = crc ^ data;   // data is one byte, bit 7 = first bit
wire [7:0] nxt = {
  x[5]^x[6]^x[7],             // bit 7
  x[4]^x[5]^x[6],             // bit 6
  x[3]^x[4]^x[5],             // bit 5
  x[2]^x[3]^x[4],             // bit 4
  x[1]^x[2]^x[3]^x[7],        // bit 3
  x[0]^x[1]^x[2]^x[6],        // bit 2
  x[0]^x[1]^x[6],             // bit 1
  x[0]^x[6]^x[7]              // bit 0
};
always @(posedge clk) if (en) crc <= nxt;

Each output is an XOR of three or four bits, a single shallow level of logic. The same script approach works for 32-bit CRCs or wider data paths; the equations get longer and you should generate the RTL from the script rather than typing it.

Verifying it

Never trust a CRC implementation without a known answer. Feed 123456789 one byte per clock and check for 0xF4. Then cross-check thousands of random bytes against a bit-serial model. The parallel equations above were checked this way against a bit-by-bit Python model for random CRC and data values.

Common mistakes

  • Processing bits LSB-first when the protocol specifies MSB-first, or the reverse
  • Forgetting the initial value or the final inversion that some CRC variants use
  • Hand-typing long parallel equations instead of generating them
  • Testing only with all-zero data, which gives a zero CRC for many variants and proves nothing

Try it yourself

  1. Run the Python script, then write a bit-by-bit software CRC and confirm crc8("123456789") == 0xF4 before writing any RTL.
  2. Simulate crc8_serial and the byte-wide version in Icarus Verilog on the same packet and confirm they agree with each other and with Python.
  3. Synthesise the byte-wide version with Yosys (synth, then stat) and count the XOR cells; compare with the number of terms in the equations.
