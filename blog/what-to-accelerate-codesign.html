Hardware/software co-design: deciding what to accelerate

Edge AI Intermediate 27 Nov 2026 6 min read By Ketuna

Profile the software first, use Amdahl's law to bound the gain, then move a hot loop into hardware only when the cost of starting it and moving its data is small next to the work it saves.

In this article
  1. Profile before you partition
  2. Bound the gain with Amdahl's law
  3. Count the interface cost
  4. Choose the granularity
  5. Try it yourself

When a sensing product is too slow or drains its battery too fast, the hardware engineer's instinct is to design an accelerator. Sometimes that is right. Often the accelerator speeds up something that was never the bottleneck, or it is so awkward to start and feed that the processor spends as long talking to it as it would have spent doing the work. Co-design is the discipline of deciding, with measurements, which parts of a system become hardware and which stay as software, and how the two talk. The order matters: measure first, then partition, then design the interface.

Profile before you partition

Start with a complete software version running on the target processor, or on an instruction-set simulator with a cycle model. It is the reference for correctness and the baseline for every speed-up claim. Then measure where the cycles go. On a bare-metal RISC-V core the simplest tool is the cycle counter:

#include <stdint.h>

static inline uint32_t cycles(void)
{
    uint32_t c;
    __asm__ volatile ("csrr %0, mcycle" : "=r"(c));
    return c;
}

/* usage */
uint32_t t0 = cycles();
fft_1024(buf);
uint32_t t_fft = cycles() - t0;   /* unsigned subtraction handles wrap */

Wrap each stage of the processing chain, run it over realistic input many times, and record the cycles per stage. Measure energy too if you can, because a stage that is short but keeps a large memory busy may still matter for battery life.

Here is a profile for a vibration-monitoring node that processes one frame of accelerometer data per period. The numbers are made up for illustration, but the shape is typical of signal-processing firmware.

Stage Share of cycles
Sample handling and filtering 30 %
1,024-point FFT 45 %
Spectral features 10 %
Small classifier 5 %
Radio, logging, control 10 %

Before any design, notice what is not in the top two: the classifier. If the team had started from "it is an AI product, so build a neural network accelerator", they would be accelerating 5 % of the work.

Bound the gain with Amdahl's law

If a fraction p of the run time is made s times faster, the overall speed-up is:

speed-up = 1 / ((1 − p) + p / s)

The untouched fraction 1 − p sets a hard ceiling of 1 / (1 − p), however fast the hardware is.

  • Accelerating only the FFT 20× (p = 0.45): 1 / (0.55 + 0.0225) ≈ 1.75×. Even an infinitely fast FFT block gives at most 1 / 0.55 ≈ 1.82×.
  • Accelerating the FFT and the filtering 20× (p = 0.75): 1 / (0.25 + 0.0375) ≈ 3.48×, with a ceiling of 4×.

That calculation takes a minute and already tells you that a filter-plus-FFT front end is worth twice as much as the FFT alone. It also tells you when to stop: if the requirement is a 1.5× speed-up, an FFT block, or even a few custom instructions for the FFT butterfly, will do.

Count the interface cost

Amdahl's law assumes the accelerated part simply takes p / s of the time. Real hardware has to be started, fed and read back, and that time is spent on the processor. Suppose the FFT is 450,000 cycles per frame in software, and the accelerator does it in 450,000 / 20 = 22,500 cycles. But the driver copies 1,024 samples into the accelerator's buffer with the CPU, about 4 cycles each, so 4,096 cycles, plus about 200 cycles of register writes and interrupt handling. The effective time is 26,796 cycles, an effective s of about 16.8 instead of 20.

That is still a good result, because the overhead is small next to the work. The same arithmetic can go the other way. Consider a checksum computed on 16-byte packets: suppose software takes 120 cycles per packet and a hardware block 10, but each call needs register writes, a start, and polling for done, about 40 cycles. Hardware wins, 50 against 120. If the packets were 2 bytes and software took 24 cycles, the same 40-cycle overhead makes the accelerator slower than the code it replaced.

So the rule is: offload only when overhead + hardware time is well below software time, and look for ways to shrink the overhead:

  • let the accelerator read from shared memory, or use DMA, instead of copying with the CPU
  • give it a whole frame or a whole layer per start, not one item
  • signal completion with an interrupt so the CPU can sleep, rather than polling

Choose the granularity

There are two broad shapes of hardware help, and they suit different profiles.

  • Fine-grained: a custom instruction in the processor, for example a multiply-accumulate on packed bytes or an FFT butterfly step. Call overhead is essentially zero because it is just an instruction, but each call does little work and the CPU stays busy. Good for hot inner loops that are spread through the code.
  • Coarse-grained: a memory-mapped accelerator that processes a whole buffer per start. Setup costs tens to hundreds of cycles, but it can do a lot of work in parallel while the CPU sleeps. Good for large, regular kernels such as the filter-and-FFT front end above.

Also ask what will change. Hardware is fixed at tape-out; firmware is not. Filtering and transforms are stable mathematics and make good hardware. Thresholds, classifier structure and decision rules change as you learn from field data and belong in software, or at most on a general-purpose engine that software programs.

Common mistakes:

  • building the accelerator before a software baseline exists to profile and to check results against
  • quoting the accelerator's speed-up on its kernel instead of the end-to-end speed-up
  • ignoring driver and data-copy cycles, which can cancel the gain on small jobs
  • hard-wiring parameters that the product team will want to tune later

Try it yourself

  1. Write the processing chain for a small signal task in C, wrap each stage with the cycles() function, and run it under a RISC-V simulator such as Spike or Renode, or on a board.
  2. Fill in a profile table like the one above from your measurements and compute the Amdahl ceiling for each candidate.
  3. For the best candidate, write down the driver steps (copy, configure, start, wait, read back) and estimate their cycles before you design any RTL.
  4. Explain your partition to a colleague in one page; if you cannot justify a block with numbers, leave it in software for now.
