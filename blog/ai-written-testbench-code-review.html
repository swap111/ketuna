Using AI to write testbench code without trusting it blindly

Verification Beginner 27 Nov 2026 5 min read By Ketuna

Write the first test by hand, then let an AI assistant draft more, and review every generated check against the spec. A worked review shows the flaws that make generated tests pass while checking nothing.

In this article

AI assistants are good at producing testbench code quickly: drivers, loops, random generators, boilerplate around a simulator. That speed is real and worth using. But a testbench has an unusual property. Its job is to fail when the design is wrong, and code that never fails looks exactly like code that works. A generated test that checks nothing will pass, and so will the next fifty. The habit that makes AI useful here is simple to state: write the first test yourself, then use AI for more, and review every generated check against the specification rather than against your sense that it looks plausible.

Why the first test should be yours

Writing the first test by hand does three things no assistant can do for you.

  • You learn the interface. Reset polarity, when outputs are valid, how a handshake completes. Without that, you cannot judge whether generated code drives or samples correctly.
  • You build a known-good reference. A small test you understand line by line, and have seen fail against a deliberately broken design, becomes the yardstick for anything generated later.
  • You read the spec closely. Writing even one check forces you to decide what "correct" means, which is the knowledge you need for every review afterwards.

Once that test exists and you have watched it catch a planted bug, an assistant can extend it far faster than you could, and you can tell when its output is wrong.

Give it the spec, not the RTL

What you put into the prompt decides what the output can check. If you paste the RTL and ask for tests, the assistant will tend to describe what the RTL does, and tests derived from the RTL agree with the RTL, bugs included. Paste the relevant part of the specification instead: the register table, the protocol rules, the error behaviour. Then any disagreement between generated tests and the design is a real question.

Follow your organisation's rules about what may be shared with external tools; design data is often confidential.

A worked review

Suppose you ask for a cocotb test for a saturating 8-bit accumulator: each cycle with en high adds din to acc, which sticks at 255 instead of wrapping. Here is the kind of draft you might get back, with problems typical of generated test code.

@cocotb.test()
async def test_accumulate(dut):
    cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())
    dut.rst.value = 1
    await Timer(20, unit="ns")
    dut.rst.value = 0
    total = 0
    for _ in range(50):
        v = random.randint(0, 20)
        dut.din.value = v
        dut.en.value = 1
        await RisingEdge(dut.clk)
        total = int(dut.acc.value)            # (1)
        assert int(dut.acc.value) == total    # (2)
    try:
        assert total <= 255                   # (3)
    except AssertionError:
        dut._log.warning("overflow?")         # (4)

Read it as a reviewer, checking each line against the spec.

  1. The expected value comes from the design. total is read from acc, so the model is the DUT itself.
  2. The check is a tautology. Comparing acc with a value just read from acc can never fail.
  3. The range check is meaningless. An 8-bit signal is always ≤ 255.
  4. A failure is swallowed. Catching the assertion and logging a warning turns a failure into a pass.

There are quieter problems too. Fifty values up to 20 sum to at most 1,000, so saturation is likely to happen, but the test never checks that acc stops at 255 rather than wrapping. en is never low, so "hold when disabled" is untested. Reset is released on a timer instead of a clock edge. And it samples acc right at the edge, where a registered output may still show its old value.

Here is the reviewed version, with a model written from the spec.

@cocotb.test()
async def test_accumulate_saturates(dut):
    cocotb.start_soon(Clock(dut.clk, 10, unit="ns").start())
    dut.rst.value, dut.en.value, dut.din.value = 1, 0, 0
    await ClockCycles(dut.clk, 2)
    dut.rst.value = 0
    model, saturated = 0, False
    for _ in range(200):
        v, en = random.randint(0, 40), random.random() < 0.8
        dut.din.value, dut.en.value = v, int(en)
        await RisingEdge(dut.clk)
        await ReadOnly()
        if en:
            model = min(255, model + v)       # spec: stick at 255
        saturated |= model == 255
        assert int(dut.acc.value) == model, \
            f"acc={int(dut.acc.value)} expected {model}"
        await FallingEdge(dut.clk)            # leave read-only phase
    assert saturated, "test never reached saturation"

The model is independent of the design, en is randomised, the check runs every cycle at a safe sampling point, and the final assertion proves the interesting case actually happened.

A review checklist for generated test code

  • Where does each expected value come from? It must be the spec or a model, never the DUT's own outputs.
  • Can each assertion fail? Imagine a broken design and trace whether the check would notice.
  • Are any failures caught, logged and ignored?
  • Is every signal name real, and does every API call exist in the tool version you use?
  • Are outputs sampled at a defined point, such as after ReadOnly()?
  • Does the stimulus reach the corners in the plan, and is there a check that it did?
  • Is there an end-of-test check that something was actually compared?

Then run the generated test against a design with a planted bug. If it passes, it is not finished.

Keep a record

Note in a short log what you asked for, what came back, what was wrong, and how you found it: by review, by a planted bug, or by a test failure. Over a few weeks the log shows you where generated code needs the closest reading, and it lets a reviewer see how the testbench was built and checked.

Try it yourself

  1. Write a saturating accumulator in Verilog, and write one cocotb test for it by hand on Icarus Verilog; plant a wrapping bug and confirm your test catches it.
  2. Paste only the spec sentence into an AI assistant and ask for three more tests; review each with the checklist above before running anything.
  3. Run the generated tests against the buggy design; for any that pass, write down which checklist item explains why.
  4. Fix the tests, rerun against both versions of the design, and record what review caught and what only the planted bug revealed.
