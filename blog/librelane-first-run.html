Hardening your first block with LibreLane: a guided first run

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

Take a small registered design from Verilog to GDS with LibreLane on sky130. Write a minimal configuration, run the flow, and learn which reports and views to open first and what to look for in each.

In this article

  2. A minimal configuration
  3. Running the flow
  4. What to open first

LibreLane is an open-source flow that takes Verilog and produces a layout, by running Yosys, OpenROAD, OpenSTA, Magic, KLayout and Netgen as a sequence of configurable steps. Your first run will print a lot and finish with a GDS file. The harder part is knowing what to look at afterwards, so that "the flow completed" becomes "I understand this layout and I know whether it is good". This guide walks through one run on a small design.

Pick a design worth hardening

Choose something small, synchronous and already verified: an 8-bit ALU with registers on its inputs and outputs is ideal. It has a clock, real logic between flip-flops, and a few hundred cells, so a run takes minutes on a laptop.

module alu8_reg (
  input  wire       clk, rst_n,
  input  wire [7:0] a, b,
  input  wire [1:0] op,
  output reg  [7:0] y
);
  reg [7:0] a_q, b_q;
  reg [1:0] op_q;
  always @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      a_q <= 0; b_q <= 0; op_q <= 0; y <= 0;
    end else begin
      a_q <= a; b_q <= b; op_q <= op;
      case (op_q)
        2'b00: y <= a_q + b_q;
        2'b01: y <= a_q - b_q;
        2'b10: y <= a_q & b_q;
        default: y <= a_q ^ b_q;
      endcase
    end
endmodule

Simulate it first with Icarus Verilog or Verilator. Physical design does not find functional bugs; it faithfully builds whatever you give it.

A minimal configuration

LibreLane reads a JSON or YAML configuration. For a first run you need very little:

{
  "DESIGN_NAME": "alu8_reg",
  "VERILOG_FILES": ["dir::src/alu8_reg.v"],
  "PDK": "sky130A",
  "STD_CELL_LIBRARY": "sky130_fd_sc_hd",
  "CLOCK_PORT": "clk",
  "CLOCK_PERIOD": 10,
  "FP_SIZING": "relative",
  "FP_CORE_UTIL": 40,
  "PL_TARGET_DENSITY_PCT": 50
}

What each line does:

  • DESIGN_NAME is the top module name. It must match the Verilog exactly.
  • VERILOG_FILES lists the sources; dir:: means "relative to this configuration file".
  • PDK and STD_CELL_LIBRARY choose the process and the cell library. The high-density library is the usual default.
  • CLOCK_PORT and CLOCK_PERIOD (in ns) let LibreLane write a basic timing constraint for you. Here 10 ns, a relaxed 100 MHz, so the first run should close timing easily.
  • FP_SIZING set to relative sizes the core from the synthesised cell area, and FP_CORE_UTIL sets the target utilisation in percent.
  • PL_TARGET_DENSITY_PCT tells global placement how tightly to pack cells locally. Keep it a little above the utilisation.

Leave every other variable at its default for now. Copying long configurations from older projects is a common source of trouble, because variable names changed between flow generations. Use the current LibreLane variable reference when you add anything.

Running the flow

Install LibreLane following its official documentation (a Nix environment or the published container image are the usual routes), and make sure the PDK version matches the one your LibreLane version expects. A mismatched PDK is the most common reason for a first run to stop in its first few steps.

From the directory containing the configuration:

librelane --run-tag first config.json

The flow creates runs/first/. Each step gets its own numbered folder, in the order it ran, holding that step's logs, reports and output views. The final/ folder collects the finished views: the netlist, DEF and ODB databases, SPEF parasitics, the GDS, and a metrics.json summary.

What to open first

Resist the urge to open the GDS straight away. Go in this order:

  1. The metrics summary in final/metrics.json. Check worst setup and hold slack (timing__setup__ws, timing__hold__ws), the detailed routing DRC count (route__drc_errors), the LVS error count and antenna violations. Any red number tells you which step's reports to read next.
  2. The synthesis report. Find the cell count and area. Count the flip-flops: this design has 8 + 8 + 2 + 8 = 26. If the number differs, find out why before going further.
  3. The timing reports from the sign-off STA step. Read the worst setup path line by line: launch clock, cells, arrival, required, slack. At 10 ns there should be plenty of slack.
  4. The floorplan and placement views. Open the final ODB in the OpenROAD GUI. Look at the core outline, the rows, the power straps, the placed cells and the pins. Does the core look as full as 40% suggests? Remember that tap cells, buffers and fillers are added after sizing.
  5. The GDS in KLayout. Now look at the layout, layer by layer. Find a flip-flop, a clock buffer, a power strap and a pin.

Then change one thing

The run becomes a lesson when you change one variable and predict the effect first.

  • Lower CLOCK_PERIOD until setup slack turns negative, and find the step where it first failed.
  • Raise FP_CORE_UTIL to 70 and watch routing congestion and DRC.
  • Change FP_ASPECT_RATIO and compare wire length.

Keep each run under its own tag so you can compare them side by side. Write your prediction down before each run; checking it afterwards is where the understanding comes from.

Common first-run problems

  • The flow stops in synthesis. Check that DESIGN_NAME matches the module and that every file in VERILOG_FILES exists. Then check the PDK and LibreLane versions match.
  • Timing fails at a generous clock. Usually the clock port name is wrong, so the design is effectively unconstrained or the clock is not recognised.
  • Every run looks identical. You may be editing a different configuration file from the one you pass on the command line.

Try it yourself

  1. Save the ALU above, simulate it in Icarus Verilog, then harden it with the configuration shown.
  2. Open final/metrics.json and write down setup slack, hold slack, die area and cell count.
  3. Rerun with --run-tag fast -c CLOCK_PERIOD=3 (the -c option overrides one configuration variable), compare the two metrics files, and find the worst path in the new timing report.
  4. Open both GDS files in KLayout and note any visible difference.
