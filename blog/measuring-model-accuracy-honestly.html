Measuring model accuracy honestly: test sets, leakage and confusion matrices

Edge AI Beginner 27 Nov 2026 6 min read By Ketuna

One accuracy number can hide a model that misses the class you care about. How to keep test data truly separate, spot leakage, and report per-class results from a confusion matrix.

In this article
  1. Three sets, three jobs
  2. How leakage sneaks in
  3. Reading a confusion matrix
  4. What an honest report contains
  5. Try it yourself

The first number most people report for a model is its accuracy: the fraction of test examples it got right. It is easy to compute and easy to fool yourself with. A model can score well because the test data secretly overlaps the training data, or because one class is so common that guessing it every time looks good. On an edge device, where the model will meet a different sensor, different users and different conditions, an over-optimistic number becomes a product that disappoints in the field. Measuring honestly takes a little discipline and no special tools.

Three sets, three jobs

Split your labelled data into three parts before you train anything:

  • Training set: the model learns its weights from this.
  • Validation set: you use this to make choices, such as the network size, the learning rate, the number of training epochs or a decision threshold.
  • Test set: you look at this once, at the end, to report how the finished model performs.

The validation set exists so that the test set stays untouched. Every time you change something because of a result, that data has influenced the model. If you tune on the test set, its score stops being an estimate of performance on new data and becomes a measure of how well you tuned to those particular examples. Keep the test set locked away until the end; if you have to change the model after looking at it, admit that the test set has become a validation set and collect a fresh one.

How leakage sneaks in

Leakage means information from the test set reaches training, so the score is better than the model deserves. In sensor projects it usually comes from one of these:

  • Overlapping windows. Motion or audio data is cut into windows that overlap, for example 1 s windows every 0.5 s. If you split the windows randomly, a test window shares half its samples with a training window. The model has effectively seen the test data. Split recordings first, then cut each recording into windows.
  • The same person, device or session on both sides. A model can learn the quirks of one person's walk, one microphone or one afternoon's background noise. If the same person appears in training and test, the score measures recognition of familiar people. Split by person (or device, or day): everyone in the test set should be someone the model has never seen.
  • Preprocessing fitted on all the data. Normalising features with a mean and standard deviation computed over the whole dataset lets test statistics leak into training. Compute them on the training set only and apply the same numbers everywhere else.
  • Duplicates. Copied files, or the same event recorded by two sensors, end up on both sides of a random split.

A useful smell test: if the score is surprisingly high for a small model on a hard task, look for leakage before celebrating.

Reading a confusion matrix

Suppose an activity model classifies windows from a wrist sensor as idle, walk or fall, and the test set has 600 windows. The numbers are made up for illustration. A confusion matrix counts, for each true class (row), how often each class was predicted (column):

True \ predicted idle walk fall
idle (400) 390 8 2
walk (150) 12 130 8
fall (50) 10 15 25

Accuracy is the diagonal over the total: (390 + 130 + 25) / 600 = 545 / 600 ≈ 90.8 %. That sounds good until you look at the fall row. Of 50 real falls, the model found 25. Half of the events that matter most were missed.

Two per-class numbers make this visible:

  • Recall (also called sensitivity): of the true examples of a class, the fraction the model found. Fall recall = 25 / 50 = 0.50.
  • Precision: of the times the model predicted a class, the fraction that were right. Fall precision = 25 / (2 + 8 + 25) = 25 / 35 ≈ 0.71.

Also compare with a trivial baseline. A "model" that always says idle scores 400 / 600 ≈ 66.7 % on this test set without learning anything. Accuracy should always be read against that number, especially when classes are unbalanced.

import numpy as np

labels = ["idle", "walk", "fall"]
cm = np.array([[390,   8,  2],      # rows: true class
               [ 12, 130,  8],      # columns: predicted class
               [ 10,  15, 25]])

accuracy = np.trace(cm) / cm.sum()
recall = np.diag(cm) / cm.sum(axis=1)      # of each true class, found
precision = np.diag(cm) / cm.sum(axis=0)   # of each prediction, right
print(f"accuracy {accuracy:.3f}")
for name, r, p in zip(labels, recall, precision):
    print(f"{name:5s} recall {r:.2f} precision {p:.2f}")

Which number matters depends on the product. For a fall alarm, a miss may be far worse than a false alarm, so you would tune for high fall recall and accept lower precision. For a wake word, false triggers annoy users, so precision matters more. Write down which errors are costly before tuning, so the choice is driven by the product and not by whichever number looks best.

What an honest report contains

A report another engineer can trust has:

  1. how the data was split, and by what (person, device, day, location)
  2. the size of each set and the count of each class
  3. the confusion matrix, plus recall and precision per class
  4. the trivial baseline for comparison
  5. the result of the quantized model running the deployed code, not just the float model in training
  6. the conditions the test data does not cover, such as untested users, temperatures or mounting positions

For small test sets, also remember that each example moves the percentage a lot: with 50 falls, one more or one fewer detection changes fall recall by two percentage points. Do not read meaning into small differences between models evaluated on a small test set.

Common mistakes:

  • splitting overlapping windows randomly instead of splitting recordings
  • tuning thresholds or architecture on the test set
  • reporting accuracy alone on unbalanced classes
  • evaluating the float model and shipping the int8 one without re-measuring

Try it yourself

  1. Run the script above, then change the fall row to [2, 3, 45] and see how accuracy and fall recall change differently.
  2. Take a dataset of sensor recordings and split it twice: randomly by window, and by recording or person. Train the same small model on each and compare test scores; a large gap points to leakage.
  3. Use sklearn.metrics.confusion_matrix and classification_report from scikit-learn on your own model's predictions and check them against the numpy version.
  4. Write the six-point report above for your last model and see which items you cannot yet fill in.
