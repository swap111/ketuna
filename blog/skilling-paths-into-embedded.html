Skilling paths into embedded systems in India: from college lab to product team

India's electronics ecosystem Intermediate 27 Nov 2026 5 min read By Ketuna

A project ladder that takes you from blinking an LED to firmware a product team would accept, with what each rung teaches and how to show it, from register-level drivers to an RTOS, tests and field updates.

Most engineering students have made a microcontroller board blink an LED, read a sensor and print to a serial terminal. Product teams hire people who can write firmware that runs for years in the field, survives brown-outs and bad inputs, can be updated safely and can be understood by the next engineer. The gap between those two is large, but it is crossable with a deliberate sequence of projects. This article describes that sequence and what each step should teach you.

The gap between a lab project and product firmware

A typical lab project works once, on the bench, when the person who wrote it is watching. Product firmware has to keep working when nobody is watching. The differences are concrete:

Lab project Product firmware
Runs on a vendor library you have not read You understand what the library does at register level
Polling loops and delay() calls Interrupts, timers, low-power sleep and scheduling
Crashes are fixed by pressing reset A watchdog recovers, and logs say what happened
Tested by trying it Unit tests, hardware-in-the-loop tests, test reports
Updated by plugging in a programmer Secure field updates with rollback
Code in one file Modules with clear interfaces, version control, reviews

None of the right-hand column is exotic. It is learned by building projects that force each skill, one at a time.

Rung 1: understand the hardware under the library

Pick one microcontroller and write a GPIO, timer and UART driver yourself, directly against the reference manual's registers, without the vendor's library. Then compare your code with the library's.

This teaches you to read a reference manual and a datasheet, to understand clocks, memory-mapped registers and reset values, and to use a debugger to inspect registers. Once you have done it for one chip, every other chip is easier.

Rung 2: interrupts, buffers and timing

Make your UART receive with interrupts into a ring buffer, and drive a periodic task from a timer interrupt. Measure timing with a logic analyser or by toggling a pin and watching it on an oscilloscope.

Here you learn about shared data between interrupt and main code, the volatile keyword and its limits, critical sections and how long an interrupt handler may take. Most real firmware bugs live in exactly this area, so it is worth getting right before moving on.

Rung 3: an RTOS and a real application

Port the same application to an RTOS such as Zephyr. Split it into tasks, communicate with queues and add a low-power idle mode. Build something with a purpose, for example a sensor node that samples every few seconds, filters the data, stores it and sends it over a radio.

This teaches you scheduling, priorities, stack sizing, power modes and the habit of measuring current consumption rather than guessing.

Rung 4: make it robust

Now try to break it. Pull the power during a flash write. Send malformed packets. Disconnect the sensor. Let it run for a week. Then fix what you find:

  • Watchdog that resets the system if the main loop stalls
  • Brown-out handling so a dying supply does not corrupt stored data
  • Input validation on everything that comes from outside
  • Fault logging so a reset leaves a record of why

A short example of the kind of habit this rung builds: recording the reset cause at boot so field failures leave evidence. The register names below are placeholders; use your chip's reset-cause register.

#include <stdint.h>

#define RST_CAUSE_REG   (*(volatile uint32_t *)0x40001000u) /* example */
#define RST_WDT         (1u << 0)
#define RST_BROWNOUT    (1u << 1)

extern void log_event(const char *msg);

void record_reset_cause(void)
{
    uint32_t cause = RST_CAUSE_REG;
    if (cause & RST_WDT)      log_event("reset: watchdog");
    if (cause & RST_BROWNOUT) log_event("reset: brown-out");
    RST_CAUSE_REG = cause;    /* write-1-to-clear on many chips */
}

Rung 5: test, update and document like a team

Finally, add what a product team expects around the code:

  • Unit tests for logic that does not touch hardware, run on your PC with GCC
  • Simulation or emulation with QEMU or Renode for parts of the system
  • Continuous integration that builds and tests every commit
  • A bootloader with field update and rollback, so a bad update cannot brick the device
  • A README and design notes a new engineer could follow

At this point your project looks like real product work, and you can talk about it the way product engineers do.

Showing the work

Keep each rung in version control with honest commit history. Write a short note for each project: what you built, how you tested it, what broke and what you changed. Record a short video of the device working and include current measurements and test results. An interviewer who can see your interrupt handler, your test report and your notes on a power-loss bug learns more than any certificate can tell them.

College labs, short focused programs and self-study can all get you up this ladder. What matters is that someone reviews your code at some point. Firmware written alone tends to carry the same blind spots from project to project.

Try it yourself

  1. Write a register-level UART driver for a board you own, and compile it with GCC for your target using -Wall -Wextra with no warnings.
  2. Run the same firmware in Renode or QEMU if your board is supported, and script a test that sends input and checks output.
  3. Port the application to Zephyr and use its logging subsystem to record the reset cause at boot.
  4. Pull the power during a flash write fifty times and record what happens, then fix it.
