Pipelining a datapath step by step: latency, throughput and the cost of registers

Digital & VLSI design Intermediate 27 Nov 2026 5 min read By Ketuna

Cut a multiply-accumulate path into balanced stages, see how the clock period, latency and register count change, and carry a valid bit alongside the data so the pipeline knows which results are real.

In this article

A multiply-accumulate (MAC) unit sits at the heart of every digital filter and neural-network accelerator. Written as one line of RTL, it is also usually the longest path in the block, and it sets the clock speed for everything around it. Pipelining is how you break that path into pieces, and doing it well is mostly bookkeeping: balancing the pieces, counting the registers, and keeping track of which data is valid.

The unpipelined MAC

always @(posedge clk)
  if (en) acc <= acc + a * b;

Between the input registers and acc there is a multiplier followed by an adder. Use these delays, made up for illustration: the 16 × 16 multiplier takes 4.0 ns, the 40-bit adder 2.0 ns, and each register adds 0.4 ns of overhead (clock-to-Q plus setup).

Tclk ≥ 0.4 + 4.0 + 2.0 = 6.4 ns, about 156 MHz

One MAC completes every cycle, so throughput is 156 million MACs per second, and each result is ready one cycle after its inputs.

First cut: register the product

Put a register between the multiplier and the adder. The two halves are now separate paths:

  • multiplier stage: 0.4 + 4.0 = 4.4 ns
  • accumulate stage: 0.4 + 2.0 = 2.4 ns

The clock is set by the slower stage, 4.4 ns, or about 227 MHz. That is better, but the accumulate stage now idles for 2 ns of every cycle. The lesson: a pipeline is only as fast as its slowest stage, so the gain from a cut depends on how evenly it splits the delay.

Balanced cut: split the multiplier

A hardware multiplier has a natural internal seam. It first reduces its partial products to two numbers (a carry-save form) and then adds those two in a final adder. Suppose each half takes 2.0 ns. Cutting there gives three stages of equal logic:

Stage Logic Period needed
1 Partial-product reduction 2.4 ns
2 Final multiplier add 2.4 ns
3 Accumulate 2.4 ns

Now Tclk = 2.4 ns, about 417 MHz. Throughput rose by 6.4 / 2.4 ≈ 2.67 times. It did not triple, because the 0.4 ns register overhead is paid in every stage. That overhead is why pipelining has diminishing returns: as the logic per stage shrinks, the fixed register cost takes a larger share of each cycle.

What it costs

Latency. A result now appears three cycles after its inputs: 3 × 2.4 = 7.2 ns, slightly longer than the 6.4 ns of the unpipelined version. Pipelining raises throughput, not speed for a single operation. If the consumer needs one answer as soon as possible, pipelining can make it worse.

Registers. Each cut adds a register as wide as the data crossing it. The carry-save cut carries two wide vectors, so it is the most expensive. Registers cost area, clock power on every edge, and clock-tree load. Count them before you cut, and prefer seams where the data is narrow.

The feedback loop. Notice that the accumulator adder and its register stay together in one stage. The accumulate depends on its own previous result, so you cannot insert a register inside that loop without changing what the circuit computes: with two registers in the loop you would have two interleaved accumulators. Loops set a hard floor on the clock period; only the feed-forward part of a path can be pipelined freely.

Carrying a valid bit

Once data takes three cycles to flow through, the accumulator must know which cycles hold real data. The standard method is a valid bit that travels in a parallel register chain, one flop per stage:

module mac3 (
  input  wire               clk, rst_n,
  input  wire               in_valid,
  input  wire signed [15:0] a, b,
  output reg  signed [39:0] acc
);
  reg               v1, v2;
  reg signed [31:0] p1, p2;   // stand-ins for the two multiplier halves
  always @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      v1 <= 1'b0; v2 <= 1'b0; acc <= 40'sd0;
    end else begin
      v1 <= in_valid;
      v2 <= v1;
      if (v2) acc <= acc + p2;
    end
  end
  always @(posedge clk) begin   // data needs no reset
    p1 <= a * b;    // in a real design, stage 1 is PP reduction
    p2 <= p1;
  end
endmodule

The valid flops are reset so the pipeline starts empty; the data flops are not, because their contents are ignored whenever the matching valid bit is low. That saves reset routing on the widest registers. The accumulator only updates when v2 says the product beside it is real, so bubbles in the input stream are harmless.

Common mistakes

  • Pipelining the data but not the control. Every signal that qualifies the data, such as valid, last, or a channel number, must be delayed by the same number of stages.
  • Unbalanced stages. One long stage wastes the gains of all the others.
  • Cutting inside a feedback loop. It changes the function, not just the timing.
  • Forgetting downstream latency. Any logic waiting for the result now waits longer; update its counters and testbench expectations.

Try it yourself

  1. Draw the three-stage pipeline on paper with every register and its width, and add up the flip-flops before writing any code.
  2. Simulate mac3 in Icarus Verilog with in_valid toggling randomly and compare acc against a Python model that accumulates only the valid products.
  3. Synthesise the unpipelined and pipelined versions with Yosys against a sky130 library, then compare the critical path in OpenSTA with report_checks and the flip-flop count with stat.
