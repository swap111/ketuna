Debugging a failing test systematically: from the first mismatch to root cause

Verification Beginner 27 Nov 2026 5 min read By Ketuna

A repeatable method for hardware test failures - reproduce, find the first divergence, narrow in time and hierarchy, and write down each hypothesis - with a script that finds where two traces first disagree.

In this article

  2. Step 2: find the first divergence
  3. Step 3: narrow in time and hierarchy

  5. Step 5: fix, then prove the fix
  6. Try it yourself

A failing hardware test usually reports its problem far from where the problem began. The scoreboard complains at cycle 9,000 that a byte is wrong; the byte went wrong at cycle 4,100 when a pointer skipped; the pointer skipped because a flag was one cycle late. Beginners open the waveform at cycle 9,000 and start scrolling. That can take an afternoon. A systematic method takes a fraction of the time and, more importantly, works every time.

Step 1: reproduce it exactly

You cannot debug a failure you cannot repeat. Before anything else, rerun the failing test with the same seed, the same build options and the same simulator version, and confirm it fails the same way at the same time.

If it does not reproduce, that is the first finding, and a serious one. Common causes are an unrecorded random seed, a test that depends on what an earlier test left behind, or a race between testbench and design at a clock edge. Fix reproducibility first; otherwise every later step is guesswork.

Then make the failure as small as you can. Shorten the test until it still fails. A failure at cycle 300 is much easier to read than one at cycle 9,000.

Step 2: find the first divergence

The reported mismatch is a symptom. What you want is the first moment the design's behaviour differs from what it should be. Everything after that is consequence.

The fastest way to find it is to compare traces, not to scroll waveforms. If your reference model can log its internal state per transaction or per cycle, and your monitor can log the design's observable state in the same format, a few lines of Python find the first line where they disagree.

import sys

def first_divergence(model_log, dut_log):
    with open(model_log) as m, open(dut_log) as d:
        for n, (exp, got) in enumerate(zip(m, d), start=1):
            if exp.strip() != got.strip():
                return n, exp.strip(), got.strip()
    return None

result = first_divergence(sys.argv[1], sys.argv[2])
if result:
    n, exp, got = result
    print(f"line {n}: expected '{exp}'\n        got      '{got}'")
else:
    print("logs agree")

If each line carries a cycle number, the output tells you exactly where to open the waveform. Logging a few extra internal values, such as FIFO occupancy or FSM state, at every transaction makes this far more powerful, because internal state usually diverges before outputs do.

Step 3: narrow in time and hierarchy

Open the waveform at the first divergence, not before. Now walk backwards through the logic, one level at a time.

  1. Which signal is wrong at this time? Name it precisely, for example "count is 3, should be 4".
  2. What drives it? Find the always block or assignment. Add its inputs to the waveform.
  3. Which input is wrong, or are they all correct and the logic is wrong? If an input is wrong, it becomes the new signal of interest, and you repeat from step 1, usually a cycle or two earlier.
  4. Stop when the inputs are right and the output is wrong. That block contains the bug.

This is a search through the cone of logic feeding the failure, and each step moves you closer. It also stops you wandering: at every moment you are looking at one signal and one driver.

When the failing behaviour is buried deep in a large design, you can narrow the hierarchy first instead: check the outputs of each major sub-block at the divergence time, find the first sub-block whose outputs are wrong while its inputs are right, and descend into it.

Step 4: write down each hypothesis

The biggest time sink in debugging is not slow tools. It is chasing the same wrong idea twice, or forgetting what you already ruled out. Keep a short log as you go:

# Hypothesis Test Result
1 Scoreboard drops an item on simultaneous read and write Log scoreboard queue length per cycle Queue length correct; ruled out
2 FIFO full asserts one cycle late Check full vs occupancy at divergence full low with 8 entries; confirmed
3 Comparator uses old count value Read RTL for full Compares registered count before update; root cause

Each hypothesis must make a prediction you can check. "Something is wrong with the FIFO" predicts nothing. "full asserts one cycle late" predicts exactly what the waveform will show at the divergence. Writing it down also makes it easy to ask a colleague for help: they can read what you tried instead of starting over.

Step 5: fix, then prove the fix

When you find the cause, resist the urge to patch and move on.

  • Explain the whole failure. Your root cause should account for every symptom, including the cycle at which the test failed. If it does not, there may be a second bug.
  • Add a test that fails without the fix. A directed test aimed at the exact condition makes sure the bug never returns.
  • Rerun the original seed and the full regression. A fix that breaks something else is not a fix.
  • Ask why existing checks missed it for so long. Often an assertion near the root cause would have fired at the first divergence. Add it.

Try it yourself

  1. Take a small FIFO and a cocotb test with a scoreboard on Icarus Verilog, and plant a bug that makes full assert one cycle late.
  2. Make the model and monitor each write one line per transaction with cycle number and occupancy, and use the script above to find the first divergence.
  3. Open the waveform in GTKWave at that cycle and walk back through the cone, keeping a hypothesis table as you go.
  4. Add an assertion that would have fired at the first divergence, and confirm it does.
