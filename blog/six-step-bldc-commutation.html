Six-step BLDC commutation in firmware: Hall sensors, PWM and timing

Embedded systems Advanced 27 Nov 2026 6 min read By Ketuna

How firmware turns three Hall sensor signals into the six switch patterns that spin a brushless DC motor, how to change PWM outputs without shoot-through, how to compute speed, and how to detect a stall.

A brushed DC motor commutates itself with brushes and a split ring. A brushless DC (BLDC) motor has no brushes, so the controller must switch current between its three windings at the right moments as the rotor turns. Six-step (trapezoidal) commutation with Hall sensors is the simplest way to do it, and it is a good piece of firmware to study, because it combines a lookup table, interrupt timing, PWM peripherals and fault handling, all with real consequences when something is wrong.

A word on safety first. A motor drive switches substantial currents, a stalled motor can overheat windings and transistors within seconds, and a wrong switch pattern can short the supply through a bridge leg. Develop with a current-limited bench supply, a hardware overcurrent cut-off, and the rotor clamped or guarded. Mains-powered drives need qualified supervision.

The bridge and the six steps

The three windings, called phases A, B and C, connect to a three-phase bridge: each phase has a high-side switch to the supply and a low-side switch to ground. In six-step drive, at any moment:

  • one phase is driven high, with PWM on its high-side switch setting the effective voltage;
  • one phase is held low, with its low-side switch on;
  • the third phase floats, with both switches off.

Current flows from the high phase through two windings to the low phase. There are six such pairs, and stepping through them in order rotates the magnetic field in 60° electrical steps:

Step High (PWM) Low Floating
1 A B C
2 A C B
3 B C A
4 B A C
5 C A B
6 C B A

The rotor follows the field. To keep it turning with maximum torque, the step must change as the rotor reaches each 60° boundary, which is exactly what the Hall sensors report.

Reading the Hall sensors

Three Hall sensors placed 120° electrical apart produce a 3-bit code that changes every 60°. Six codes appear in normal operation; 000 and 111 never do with 120° spacing, so either of them means a disconnected sensor or a wiring fault.

The mapping from Hall code to step depends on how the sensors are mounted relative to the windings, so it comes from the motor's documentation or from a calibration run: drive each step slowly at a low, current-limited duty, let the rotor settle, and record the Hall code. The table below is illustrative only:

#include <stdint.h>

enum { PH_A, PH_B, PH_C };
typedef struct { uint8_t hi, lo; } step_t;

static const step_t steps[6] = {
    { PH_A, PH_B }, { PH_A, PH_C }, { PH_B, PH_C },
    { PH_B, PH_A }, { PH_C, PH_A }, { PH_C, PH_B },
};

/* Hall code (C:B:A bits) -> step index; -1 = invalid. Illustrative:
 * the real table comes from the motor data or a calibration run. */
static const int8_t hall_to_step[8] = { -1, 5, 3, 4, 1, 0, 2, -1 };

Following the Hall sequence 5, 4, 6, 2, 3, 1 through this table gives steps 1 to 6 in order, one direction of rotation. For the opposite direction, a common approach is to apply the step three positions ahead, (k + 3) % 6, which reverses the current in the windings and therefore the torque.

Commutating in the Hall interrupt

Each Hall edge raises an interrupt. The handler reads the code, validates it, applies the new switch pattern and records the time for speed measurement. It must be short and predictable, because late commutation costs torque and causes current spikes.

#include <stdbool.h>

static volatile uint8_t  last_hall;
static volatile uint32_t last_edge_ticks, edge_period_ticks;
static volatile bool     motor_fault;
static volatile bool     reverse;              /* set by the application */

void hall_isr(void)
{
    hall_clear_flags();
    uint8_t code = hall_read();                 /* 3 GPIO bits */
    int8_t  k    = hall_to_step[code];

    if (k < 0) {                                /* 000 or 111 */
        bridge_all_off();
        motor_fault = true;
        return;
    }
    if (reverse)
        k = (int8_t)((k + 3) % 6);

    bridge_apply(steps[k].hi, steps[k].lo);     /* see below */

    uint32_t now = timer_capture();             /* input capture */
    edge_period_ticks = now - last_edge_ticks;
    last_edge_ticks = now;
    last_hall = code;
}

A stricter handler also checks that code is the expected next code after last_hall. A code that jumps two steps usually means electrical noise on a sensor line, and acting on it applies the wrong pattern.

Changing the outputs without shoot-through

The most dangerous moment is the change itself. If a high-side and a low-side switch on the same leg are on at the same time, even for a few nanoseconds, the supply is shorted through them. That is called shoot-through, and it can destroy the transistors.

Three precautions, in hardware wherever possible:

  • Dead time. Motor-control timers insert a programmable delay between turning one switch of a leg off and the other on. Set it from the gate driver's and transistors' switching times, never zero.
  • Atomic pattern changes. Writing the six outputs one register at a time creates intermediate patterns. Many motor-control timers let you preload the next output configuration and apply all of it at once on a commutation event, which the Hall interrupt can trigger. Use that rather than sequential writes.
  • A hardware break input. Wire the overcurrent comparator to the timer's emergency-stop input, so the outputs turn off within the hardware's response time, without waiting for an interrupt.

Speed from the Hall period

Six Hall edges make one electrical revolution, and a motor with p pole pairs makes p electrical revolutions per mechanical one:

rpm = 60 / (6 × Tedge × p)

For example, with edges 1 ms apart, the electrical period is 6 ms, about 166.7 Hz. For a motor with 4 pole pairs that is about 41.7 mechanical revolutions per second, or 2500 rpm. Measuring with timer input capture rather than reading a counter in software keeps interrupt latency out of the result. Averaging over six edges removes the error from imperfect sensor placement.

Detecting a stall

If the rotor stops while current is applied, Hall edges stop, the pattern stays fixed, and full current flows continuously through two windings. A periodic check catches it:

void control_tick(void)                         /* e.g. every 1 ms */
{
    uint32_t idle = timer_now() - last_edge_ticks;
    if (duty_cmd > 0 && idle > STALL_TIMEOUT_TICKS) {
        bridge_all_off();
        motor_fault = true;                     /* restart needs a reset */
    }
}

Choose the timeout from the slowest speed you need to run at, with margin, and handle start-up separately, since a motor starting from rest has no recent edge. Latch the fault rather than retrying automatically, so that a jammed mechanism is not repeatedly heated.

Try it yourself

  1. Write the table and the Hall handler as plain C, and test them on your laptop with gcc: feed the Hall sequence in both directions and check the step sequence, then feed 0 and 7 and check that the bridge is switched off.
  2. Simulate a rotor in Python with numpy: generate Hall codes from an angle that advances at a chosen speed, call the commutation logic, and confirm the rpm calculation.
  3. On real hardware with a current-limited supply, do the calibration run described above to build the true Hall table before you ever run the motor at speed. Have someone else review the dead-time setting.
