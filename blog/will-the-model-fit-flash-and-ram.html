Will the model fit? Estimating flash and RAM for TinyML

Edge AI Intermediate 27 Nov 2026 6 min read By Ketuna

Weights go in flash, activations go in RAM, and the tensor arena holds the live ones. A worked estimate for a small audio network shows how to size both before you write any firmware.

The most common way a TinyML project stalls is not low accuracy. It is a link error saying the image overflows flash, or a model that converts fine and then fails at start-up because its memory arena is too small. Both can be predicted from the network description with a spreadsheet's worth of arithmetic. Doing that estimate before you choose a microcontroller, or before you add one more layer, saves a lot of rework.

Two memories, two kinds of data

A quantized model has two kinds of data with very different needs.

  • Weights and biases are constants. They are written once when you build the firmware and only read afterwards, so they can live in flash. On many microcontrollers the processor reads flash directly, so they never need copying to RAM.
  • Activations, the intermediate tensors that each layer produces, are created and overwritten during every inference. They need RAM.

On top of the model, flash also holds the inference runtime, the kernels for each operator, your application and its libraries. RAM also holds the sensor buffers, feature arrays, the stack and any runtime bookkeeping. The model is only part of each budget.

A worked example network

Take a small keyword-spotting style network. The input is a 49 × 10 grid of audio features (49 time frames, 10 coefficients each), quantized to int8. The layers are illustrative but typical in shape:

Layer Output shape Weights (int8) Biases (int32)
Conv 3 × 3, 8 filters, same padding 49 × 10 × 8 72 8
Max pool 2 × 2 24 × 5 × 8 0 0
Conv 3 × 3, 16 filters, same padding 24 × 5 × 16 1,152 16
Flatten 1,920 0 0
Dense 64 64 122,880 64
Dense 4 4 256 4

The convolution weights are kernel height × width × input channels × output channels: 3 × 3 × 1 × 8 = 72 and 3 × 3 × 8 × 16 = 1,152. The first dense layer has 1,920 inputs and 64 outputs, so 1,920 × 64 = 122,880 weights.

Flash for the model: 124,360 weight bytes plus 92 biases × 4 bytes = 368, so 124,728 bytes, about 125 kB. Per-channel scales and the model's structure add a little more.

Look at where that came from: almost 99 % of the weights are in one dense layer. That is a typical surprise. Adding a 2 × 2 pool after the second convolution shrinks its output to 12 × 2 × 16 = 384 values, the dense layer to 384 × 64 = 24,576 weights, and the whole model to about 26 kB of weights. A small architectural change often saves more than any compression trick.

Activations and the tensor arena

Activations do not all need RAM at the same time. A tensor is alive from the layer that writes it until the last layer that reads it. While a layer runs, its input and output must both exist; everything earlier can be overwritten. Using int8 activations, the live bytes per layer are:

Running Live tensors Bytes
Conv 1 input 490 + output 3,920 4,410
Max pool 3,920 + 960 4,880
Conv 2 960 + 1,920 2,880
Dense 64 1,920 + 64 1,984
Dense 4 64 + 4 68

Flatten is a reshape: the same bytes reinterpreted, so it needs no new memory.

A runtime such as TensorFlow Lite Micro gives the model one static block of RAM, the tensor arena, and a memory planner assigns each activation an offset inside it so that tensors whose lifetimes do not overlap share the same bytes. The lower bound for the arena is therefore the peak, 4,880 bytes, not the 7,358 bytes of all activations added up. The real arena is somewhat larger: kernels may need scratch buffers, the planner may not find a perfect packing, and the runtime keeps per-tensor bookkeeping in the arena too. Treat the peak as a starting estimate, then measure.

The rest of the RAM budget

The model is often not the biggest RAM user. For this audio example:

  • Audio buffer. One second of 16-bit audio at 16 kHz is 16,000 × 2 = 32,000 bytes. That is more than six times the activation peak. Computing features incrementally, one frame at a time, avoids keeping the whole second of raw audio.
  • Feature array. The 49 × 10 int8 input is 490 bytes, and it can sit in the arena as the input tensor.
  • DMA buffers, stack and the rest of the application. These are fixed costs you measure from your build, not from the model.

A small script keeps the arithmetic honest as the network changes:

acts = [490, 3920, 960, 1920, 64, 4]   # bytes, int8; flatten aliases
peak = max(a + b for a, b in zip(acts, acts[1:]))
weights = 72 + 1152 + 122880 + 256
biases = (8 + 16 + 64 + 4) * 4
print("arena lower bound:", peak, "B")         # 4880
print("model flash:", weights + biases, "B")   # 124728

For a real model, write the shapes once in a list and generate both tables from it.

Turning the estimate into a decision

Add up each budget with margin, and compare with the part you are considering.

  1. Flash = model bytes + runtime and kernel code + application. Get the code size from your own build with the size tool or the linker map file, because it depends heavily on which operators you include and on compiler options.
  2. RAM = arena + sensor and feature buffers + stack + application data.
  3. Margin. Leave room for the next model version. Models grow; flash and RAM on a chosen part do not.

Common mistakes:

  • summing all activations instead of finding the peak, and buying a larger part than needed
  • forgetting the raw sensor buffer, which can dwarf the model
  • assuming weights must be copied to RAM when the processor can read them from flash
  • guessing the arena size instead of reading the runtime's reported usage after allocation

Try it yourself

  1. Build the example network in PyTorch or Keras and print each layer's output shape and parameter count; check them against the tables above.
  2. Write the shape list for your own model and generate the flash and peak-activation numbers with a script.
  3. Convert the model to an int8 .tflite file, run it in TensorFlow Lite Micro on the host, and compare arena_used_bytes() after AllocateTensors() with your lower bound.
  4. Move the flatten later (add a pool) and see how much flash you save for how much accuracy.
