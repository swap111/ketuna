Preparing for embedded interviews: C, interrupts and debugging stories

Careers & skills Intermediate 27 Nov 2026 5 min read By Ketuna

Embedded interviews test pointers, bit manipulation, interrupt design and how you debug. Here is how to prepare each area, with worked questions and a structure for telling a bug story clearly.

In this article
  1. Pointer and bit-manipulation questions
  2. Designing an interrupt service routine
  3. Telling a clear debugging story
  4. Common mistakes
  5. Try it yourself

Embedded interviews have a recognisable shape. You will be asked to read or write C that touches memory directly, to reason about what happens when an interrupt arrives at the wrong moment, and to describe a bug you found on real hardware. Each part checks something different: whether you know what the compiler and the processor actually do, whether you can design for concurrency, and whether you debug with a method rather than luck.

Pointer and bit-manipulation questions

These questions are short, and the interviewer watches how carefully you read. A classic one: "Set bit 5, clear bit 2 and toggle bit 0 of a register, without touching the other bits."

#include <stdint.h>

#define REG (*(volatile uint32_t *)0x40021000u) /* address made up */

void update(void)
{
    REG |=  (1u << 5);   /* set bit 5   */
    REG &= ~(1u << 2);   /* clear bit 2 */
    REG ^=  (1u << 0);   /* toggle bit 0 */
}

Talk through the details as you write. The u suffix keeps the shift unsigned, which matters for bit 31 because shifting a signed 1 into the sign bit is undefined behaviour. The volatile qualifier tells the compiler that every access must really happen, because the hardware can change the register and the write has side effects. Then add the follow-up before they ask: each line is a read-modify-write, so if an interrupt handler also writes this register between the read and the write, its change is lost. On many microcontrollers, separate set and clear registers or bit-banding exist to avoid exactly this.

Pointer questions test whether you can read declarations. Be ready for these:

Declaration Meaning
const uint8_t *p Pointer to constant data; you may move p, not write *p
uint8_t *const p Constant pointer; you may write *p, not move p
volatile uint32_t *p Every access through p is performed as written
uint8_t (*f)(uint8_t) Pointer to a function taking and returning uint8_t

Also practise counting set bits, checking whether a number is a power of two (x && !(x & (x - 1))), swapping byte order, and extracting a bit field with a shift and a mask. Write them on paper first, then compile them and test the edge cases: zero, all ones, the top bit.

Designing an interrupt service routine

ISR questions often begin with "what should and shouldn't go in an interrupt handler?". The reasoning matters more than the list. An ISR runs while other code is suspended and, depending on priorities, while other interrupts wait. Every microsecond spent inside it adds latency to everything else.

A good answer covers:

  • Keep it short. Read the hardware, clear the interrupt flag, store the data, set a flag or push to a queue, and leave. Processing happens in the main loop or a task.
  • No blocking calls. No waiting on a peripheral, no printf, no heap allocation, because they can take unbounded time or are not re-entrant.
  • Share data safely. Variables shared with the main loop must be volatile. Multi-byte values that the processor cannot read in one access need protection, such as briefly disabling interrupts or using a single-producer, single-consumer ring buffer where each side owns one index.
  • Clear the cause. Forgetting to clear the flag means the ISR re-enters immediately and the system appears to hang.

Interviewers often follow with a scenario: "A 16-bit timer count is updated in an ISR and read in main on an 8-bit processor. What can go wrong?" The model reasoning: the read takes two instructions; if the ISR fires between them, main combines the low byte of one value with the high byte of another. For a count rolling from 0x00FF to 0x0100, that can produce 0x01FF or 0x0000. Fix it by disabling the interrupt around the read, or by reading twice until two consecutive reads agree.

Telling a clear debugging story

"Tell me about a bug you found" is nearly certain. Many candidates ramble through the history of the project. Use a tight structure instead:

  1. Symptom: what was observed, and how often.
  2. Hypotheses: two or three possible causes you considered.
  3. Experiments: what you measured or changed to separate them, one variable at a time.
  4. Root cause: what it actually was, in one sentence.
  5. Fix and prevention: the change, and what you did so it would not recur.

For example: "Our sensor board printed garbage on the serial console after a firmware update, but only sometimes. I suspected a baud mismatch, a clock configuration change, or a wiring fault. A scope on the TX line showed the bit time was off by several percent compared with the expected value at 115200 baud. The update had changed the system clock source, and the UART divisor was still computed for the old frequency. I derived the divisor from the clock configuration instead of a constant, and added a start-up check that prints the measured clock."

Notice what makes it work: a scope measurement instead of guesses, a single root cause, and a fix that prevents the whole class of bug. If you have only lab or project experience, a lab bug told this way is perfectly good.

Common mistakes

  • Forgetting volatile, or treating it as a lock. It prevents the compiler from removing accesses; it does not make a read-modify-write atomic.
  • Signed shifts and integer promotion. uint8_t values are promoted to int before arithmetic; ~ on a small type gives a wide result.
  • Long ISRs. Doing the work inside the handler is the most common design flaw interviewers probe for.
  • A story without measurements. "I tried things until it worked" tells the interviewer you were lucky.

Try it yourself

  1. Write the bit-manipulation helpers above in a small C file, compile them with GCC (gcc -Wall -Wextra -O2 bits.c), and test edge cases with assert.
  2. Build a bare-metal UART receive ring buffer for a RISC-V target and run it on QEMU or Renode, with the ISR pushing bytes and the main loop pulling them.
  3. Simulate the torn 16-bit read: in a host program, split a counter read into two byte reads with a deliberate update between them, observe the wrong value, then apply the read-twice fix.
  4. Write your own debugging story in the five-part shape, under 150 words, and practise telling it in two minutes.
