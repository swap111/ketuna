Designing a skid buffer to break a ready path without losing throughput

Digital & VLSI design Advanced 27 Nov 2026 5 min read By Ketuna

A skid buffer registers the ready signal of a valid/ready interface and adds one spare slot to catch the word already in flight. Here is the design, traced cycle by cycle through a stall.

In a valid/ready pipeline, data and valid flow forward through registers, but ready usually flows backward through combinational logic. A long pipeline, or one whose stages sit far apart on the die, ends up with a ready path that crosses many stages in one cycle and fails timing. You cannot fix it with a plain flop on ready, because the sender would act on stale information and push a word the receiver cannot hold. The skid buffer is the standard answer: register ready, and keep exactly enough storage to absorb the consequence.

Why one extra slot is enough

Suppose the downstream receiver drops out_ready at some edge. If our in_ready is a flop output, the upstream sender does not see the stall until the next cycle. During the cycle in between, it still sees in_ready = 1, and it is allowed to complete a transfer. So one more word arrives after the stall began, and we must store it somewhere other than the output register, which is still holding the word the receiver refused.

That word is the "skid": like a car that keeps sliding a short distance after the brakes go on. Because in_ready is late by exactly one cycle, exactly one extra word can arrive, so one extra register is enough. With that, the skid buffer has two slots: the output register, which drives out_data, and the skid register, which only fills during a stall.

The RTL

module skid_buf #(parameter int W = 32) (
  input  logic         clk, rst_n,
  input  logic         in_valid,
  output logic         in_ready,
  input  logic [W-1:0] in_data,
  output logic         out_valid,
  input  logic         out_ready,
  output logic [W-1:0] out_data
);
  logic         skid_valid;
  logic [W-1:0] skid_data;

  assign in_ready = !skid_valid;          // a flop output, no logic

  wire take = in_valid && in_ready;        // word accepted this edge
  wire move = out_ready || !out_valid;     // output slot frees up

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      out_valid  <= 1'b0;
      skid_valid <= 1'b0;
    end else if (take && !move) begin      // stalled: catch the skid
      skid_valid <= 1'b1;
    end else if (move) begin
      if (skid_valid) begin                // drain skid first
        out_valid  <= 1'b1;
        skid_valid <= 1'b0;
      end else begin
        out_valid  <= take;
      end
    end

  always_ff @(posedge clk) begin
    if (take && !move)                skid_data <= in_data;
    if (move) out_data <= skid_valid ? skid_data : in_data;
  end
endmodule

Note that take and skid_valid cannot both be true, because in_ready is low whenever the skid is full. That is why the move branch can choose between the skid and the input without ever losing one of them. in_ready depends only on a flop, so the upstream sender sees no combinational path from out_ready at all. The forward path from in_data through the mux into the output register is the only logic added.

Tracing a stall cycle by cycle

The sender always has data (words A, B, C …). The receiver accepts on every cycle except cycles 2 and 3. Each row shows the signals during that cycle, before the edge at its end.

Cycle out_ready in_ready / skid Edge result
0 1 1 / empty A accepted into out reg
1 1 1 / empty A leaves; B into out reg
2 0 1 / empty B held; C accepted into skid
3 0 0 / C B held; sender holds D
4 1 0 / C B leaves; C moves to out reg
5 1 1 / empty C leaves; D into out reg
6 1 1 / empty D leaves; E into out reg

Cycle 2 is the skid itself: the receiver stalled, but in_ready was still 1 from the previous edge, so C arrived and went into the skid register. In cycle 3, in_ready has caught up and the sender holds D. In cycle 4 the receiver takes B, and C moves from the skid into the output register on the same edge. From cycle 5 on, words again flow one per cycle.

The output side never idles while the receiver is ready: every cycle with out_ready = 1 moves a word. The input is stalled only for the cycles the receiver itself stalled. That is what "no throughput loss" means here.

Trade-offs and variants

  • Cost. One extra data register of width W, a mux on the output path, and two control flops. For a wide bus that is real area, so use skid buffers where timing needs them, not at every stage.
  • Latency. Data passes through one register, the same as a plain pipeline stage.
  • Registering both directions. This design registers ready backward and data forward. Placing skid buffers every few stages along a long pipeline bounds both paths, at the cost of the extra registers.
  • Verification. Skid buffers are a classic place for subtle bugs, such as losing the skid word when out_ready and in_valid change on the same edge. Random stall testing with a scoreboard finds many; formal property checking can prove that no word is lost or duplicated.

Common mistakes

  • Deriving in_ready from out_ready "just a little", which brings back the combinational path the buffer exists to remove
  • Draining the skid register and accepting a new word into the output register on the same edge, which drops one of them
  • Letting the output register load from the input while the skid is full, so the newer word overtakes the older one and the order is lost
  • Testing only with out_ready held high, where the skid register never fills and the interesting logic never runs

Try it yourself

  1. Reproduce the trace table by hand from the RTL, then write a short Python model of the same two registers and check it prints the same rows.
  2. Simulate skid_buf in Verilator or Icarus Verilog with a cocotb test that toggles out_ready and in_valid randomly, and score every word in and out.
  3. Write properties for "a word accepted is eventually output, once and in order" in a small formal harness and check them with SymbiYosys.
