Writing a small device driver: the layers between a register and an API

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

Build an I2C sensor driver in four layers: a register map, a replaceable bus interface, a checked initialisation sequence and an interrupt-backed API with clear units that you can test on a laptop.

The first driver most people write is a single function that pokes registers and returns a number. It works on the bench, then grows: a retry here, a delay there, a global flag set by an interrupt. Six months later nobody can change it without breaking something. A small driver does not need a framework, but it does need layers with clear jobs. This article builds one for a sensor, layer by layer, and explains what each layer protects you from.

The four layers

The sensor in this example is made up so that the code stands on its own: an I2C temperature sensor with an identity register, a control register with a self-clearing reset bit, a data-ready interrupt output, and a signed 16-bit result in units of 1/128 °C.

Layer 1: the register map

Start by copying the register table from the datasheet into a header, using the datasheet's own names so that a reviewer can check it line by line:

/* tmp_regs.h: register map of a made-up I2C temperature sensor */
#define TMP_REG_ID       0x0Fu  /* reads TMP_ID_VALUE              */
#define TMP_REG_CTRL     0x10u
#define TMP_CTRL_RESET   (1u << 7)  /* self-clearing soft reset   */
#define TMP_CTRL_DRDYIE  (1u << 1)  /* data-ready pin enable      */
#define TMP_CTRL_RUN     (1u << 0)  /* continuous conversion      */
#define TMP_REG_DATA_H   0x12u  /* then DATA_L; 1/128 degC per LSB */
#define TMP_ID_VALUE     0xA5u

Nothing else goes in this file. When the next revision of the part moves a bit, there is exactly one place to change.

Layer 2: a bus interface you can replace

The driver should not call the I2C controller directly. It calls three functions through a small structure, and whoever creates the driver decides what they point to:

#include <errno.h>
#include <stdint.h>

struct tmp_bus {
    int  (*read)(void *ctx, uint8_t reg, uint8_t *buf, unsigned len);
    int  (*write)(void *ctx, uint8_t reg, uint8_t val);
    void (*delay_ms)(unsigned ms);
    void *ctx;                  /* for example: controller + address */
};

struct tmp_dev {
    const struct tmp_bus *bus;
    volatile int data_ready;    /* set by the data-ready interrupt */
};

On the board, read and write wrap the real I2C driver with the sensor's bus address. On a laptop they point at a fake that stores registers in an array. The driver logic is identical in both, which is the whole point.

Layer 3: initialisation that checks everything

A good initialisation sequence never assumes the hardware is there. It waits for power-up, confirms the part's identity, resets it to a known state with a bounded wait, configures it, and reads the configuration back:

static int rd8(struct tmp_dev *d, uint8_t reg, uint8_t *v)
{
    return d->bus->read(d->bus->ctx, reg, v, 1);
}

int tmp_init(struct tmp_dev *d, const struct tmp_bus *bus)
{
    uint8_t v;
    int rc;

    d->bus = bus;
    d->data_ready = 0;
    bus->delay_ms(2);                          /* power-up time  */

    if ((rc = rd8(d, TMP_REG_ID, &v)) != 0)
        return rc;                             /* bus error      */
    if (v != TMP_ID_VALUE)
        return -ENODEV;                        /* wrong part     */

    if ((rc = bus->write(bus->ctx, TMP_REG_CTRL, TMP_CTRL_RESET)) != 0)
        return rc;
    for (int i = 0; ; i++) {                   /* bounded wait   */
        bus->delay_ms(1);
        if ((rc = rd8(d, TMP_REG_CTRL, &v)) != 0)
            return rc;
        if (!(v & TMP_CTRL_RESET))
            break;
        if (i == 10)
            return -ETIMEDOUT;
    }

    const uint8_t cfg = TMP_CTRL_RUN | TMP_CTRL_DRDYIE;
    if ((rc = bus->write(bus->ctx, TMP_REG_CTRL, cfg)) != 0)
        return rc;
    if ((rc = rd8(d, TMP_REG_CTRL, &v)) != 0)
        return rc;
    return (v == cfg) ? 0 : -EIO;              /* verify         */
}

Each check turns a confusing failure into a specific error. A wrong identity means the wrong part was fitted, or the address is wrong. A reset that never completes means a dead or unpowered chip. A read-back mismatch catches a write that did not take. The loop limit means a missing sensor cannot hang the boot.

Layer 4: the interrupt path and the API

The sensor raises its data-ready pin when a conversion finishes. The GPIO interrupt handler does the minimum: it records the event. The bus transfer happens later, in the caller's context, because an I2C transaction is far too slow for an interrupt handler.

void tmp_drdy_isr(struct tmp_dev *d)        /* from the GPIO ISR */
{
    d->data_ready = 1;
}

/* Returns 0 and the temperature in millidegrees Celsius,
 * -EAGAIN if no new sample is ready, or a negative bus error.
 * Call from thread or main-loop context only. */
int tmp_read_mdegc(struct tmp_dev *d, int32_t *mdegc)
{
    uint8_t b[2];
    int rc;

    if (!d->data_ready)
        return -EAGAIN;
    d->data_ready = 0;
    if ((rc = d->bus->read(d->bus->ctx, TMP_REG_DATA_H, b, 2)) != 0)
        return rc;
    int16_t raw = (int16_t)(((uint16_t)b[0] << 8) | b[1]);
    *mdegc = (int32_t)raw * 1000 / 128;
    return 0;
}

The comment above tmp_read_mdegc is part of the API, not decoration. It states the units (millidegrees, an integer, so no floating point is needed), every return code, and the context the function may be called from. A raw value of 0x0C80 (3200) gives 25,000 m°C; 0xFF00 (−256) gives −2000 m°C. Those two cases, positive and negative, are the first unit tests to write.

With an RTOS, the flag becomes a semaphore given by the ISR, and the read function can wait on it with a timeout instead of returning -EAGAIN. If two threads can use the sensor, add a mutex around the bus transfer.

Testing it without the board

Because the driver only sees struct tmp_bus, a fake bus of a dozen lines lets you run every path on a laptop in milliseconds. The fake keeps the sensor's registers in an array and, to model the self-clearing reset bit, clears it after it has been read twice:

static uint8_t regs[256];
static int reset_reads;

static int fake_read(void *ctx, uint8_t reg, uint8_t *buf, unsigned n)
{
    (void)ctx;
    for (unsigned i = 0; i < n; i++)
        buf[i] = regs[(uint8_t)(reg + i)];
    if (reg == TMP_REG_CTRL && (regs[reg] & TMP_CTRL_RESET) &&
        ++reset_reads >= 2)
        regs[reg] &= (uint8_t)~TMP_CTRL_RESET;
    return 0;
}

A matching fake_write stores into regs and fake_delay does nothing. Now the hard cases are one line each: put 0x5A in the identity register and tmp_init must return -ENODEV; make the fake never clear the reset bit and it must return -ETIMEDOUT after its bounded wait rather than looping forever. These are exactly the cases that are awkward to create on real hardware, which is why they so often go untested until a field failure.

Review checklist

  • Every register name and bit position matches the datasheet table
  • Every wait has a limit, and every limit returns an error code
  • Units are stated in the API and stored as integers
  • No bus transfers, delays or printing inside the interrupt handler
  • The driver contains no global state, so two sensors are two tmp_dev structures
  • Errors from the bus layer are passed up, not swallowed

Try it yourself

  1. Compile the driver on your laptop with gcc together with a fake bus whose read and write use a 256-byte array. Write tests for a wrong identity, a reset bit that never clears, a read-back mismatch, and the two temperature values above.
  2. Add a fake write that fails on the third call and confirm the error reaches the caller unchanged.
  3. Port the bus layer to a real I2C driver on a board, or to Zephyr's i2c_write_read_dt(), without changing the driver logic. Ask a colleague to review the register header against the datasheet before you power it up.
