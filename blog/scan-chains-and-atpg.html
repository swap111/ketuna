Scan chains and ATPG: how chips are tested after manufacturing

Physical design & tape-out Beginner 27 Nov 2026 5 min read By Ketuna

Every manufactured chip must be tested for defects in seconds. Learn how scan turns flip-flops into a shift register, how ATPG generates patterns, and what fault coverage really measures.

Verification proves that your design is correct. It does not prove that each chip coming off the wafer was built correctly. A speck of dust, a slightly thin wire or a missing via can break one gate in one die while its neighbours on the same wafer work perfectly. Every die must therefore be tested on a tester, quickly, and the test has to reach logic buried deep inside the chip with only a few pins. Scan design and automatic test pattern generation (ATPG) are how that is done.

The problem: buried logic is hard to reach

Imagine trying to test one AND gate in the middle of a processor using only the normal input pins. To set its inputs, you would have to drive the whole chip through a sequence of states that happens to put the right values there. To see its output, you would have to wait until that value affects a pin. For a design with thousands of flip-flops, finding such sequences is impractical.

Two properties capture the difficulty: controllability (how easily can you set a node to 0 or 1) and observability (how easily can you see its value). Scan design makes every flip-flop both directly controllable and directly observable.

The trick: turn flip-flops into a shift register

A scan flip-flop is an ordinary D flip-flop with a two-input multiplexer in front of it. In normal mode, the mux passes the functional data d. In scan mode, it passes scan_in, which comes from the previous scan flop.

module scan_dff (
  input  wire clk,
  input  wire scan_en,  // 1: shift, 0: normal
  input  wire d,        // functional data
  input  wire scan_in,  // from previous flop in chain
  output reg  q         // also drives next scan_in
);
  always @(posedge clk)
    q <= scan_en ? scan_in : d;
endmodule

Chain these flops together, q of one feeding scan_in of the next, and in scan mode the whole set of flip-flops becomes one long shift register between a scan_in pin and a scan_out pin.

How a scan test runs

One test pattern goes through three phases:

  1. Shift in. With scan_en = 1, clock the chain once per flop to load a chosen value into every flip-flop. You now control every state bit directly.
  2. Capture. Set scan_en = 0 and pulse the clock once. Each flop captures the output of the logic in front of it, which is the logic's response to the values you shifted in.
  3. Shift out. Set scan_en = 1 again and clock the chain to read every captured value at scan_out. The tester compares them with the expected values.

The shift-out of one pattern overlaps with the shift-in of the next, so the cost per pattern is roughly one chain length of shift cycles plus a capture cycle. As an illustrative example, with one chain of 100 flops and 200 patterns, the test takes about 200 × (100 + 1) + 100 = 20,300 clock cycles, the final 100 being the last unload. Real chips split flops into many shorter parallel chains to keep this small.

ATPG: letting a tool choose the patterns

Which values should you shift in? ATPG tools work from a fault model, an abstract description of what a defect does. The most common is the stuck-at model: any net may be permanently stuck at 0 or at 1. Every net gives two faults.

For each fault, the tool searches for a pattern that does two things:

  • Excites the fault: drives the net to the opposite of its stuck value, so a good chip and a faulty chip differ there.
  • Propagates the difference to a scan flop or output pin, by setting other gate inputs so the difference is not masked.

Because scan makes every flop a controllable input and an observable output, ATPG only has to reason about the combinational logic between flops, which is a much easier problem. One pattern usually detects many faults at once, so the pattern count is far smaller than the fault count.

Other fault models extend this. Transition faults model a node that switches too slowly and need a launch and capture at speed. Bridging faults model two nets shorted together.

What fault coverage means

Fault coverage is the fraction of modelled faults that the pattern set detects. As an illustrative example, if a design has 10,000 stuck-at faults and the patterns detect 9,850, coverage is 98.5%.

Read the number carefully:

  • It is coverage of the model, not of all possible defects. High stuck-at coverage does not guarantee that timing-related defects are caught.
  • Some faults are untestable by design, for example in redundant logic, and are often reported separately.
  • Undetected faults point to logic that scan cannot reach well: non-scan flops, asynchronous resets, memories, and analog blocks. These need their own approaches, such as memory built-in self-test.

Try it yourself

  1. Write a small design with a few registers. Replace each with the scan_dff module above, chain them, and simulate shift, capture and shift out in Icarus Verilog.
  2. Inject a stuck-at fault by forcing one internal net to 0 in the testbench (force), and confirm that one of your patterns shows a different value at scan_out.
  3. Work out by hand a pattern that excites and propagates a stuck-at-1 fault on one AND gate input, then check it in simulation.
  4. Use Yosys to synthesise the design and count the nets, which gives you twice that number of stuck-at faults to think about.
