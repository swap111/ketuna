Bounded proof or full proof? Model-checking depth and k-induction explained

Verification Advanced 27 Nov 2026 6 min read By Ketuna

Why a bounded model check can pass while the induction step fails on a correct design, how unreachable states cause it, and when to raise k versus write an invariant that makes the unbounded proof go through.

  2. The induction step and unreachable states

The first surprise in formal verification usually arrives like this: the bounded check passes at depth 20, you switch to prove mode, and the induction step fails with a trace that starts from a state your design can never reach. Nothing is wrong with the RTL. The tool is telling you that your properties are true but not yet inductive. Understanding why separates people who use formal tools from people who fight them.

What a bounded check actually establishes

Bounded model checking (BMC) unrolls the design from its reset state for k cycles, with every input free, and asks a solver whether any assertion can fail within those cycles. If the answer is no, you have learned something precise: no input sequence of length k or less, starting from reset, violates the property.

That is a strong statement about short behaviour and no statement at all about cycle k+1. For a design whose interesting behaviour takes longer to reach than k cycles, such as a 16-bit timeout, a deep FIFO or a counter that must reach a high value, a BMC pass may never have exercised the logic you care about. Bounded results are excellent for finding bugs quickly. They are not proofs.

The induction step and unreachable states

k-induction adds a second question to make the result unbounded. The base case is BMC to depth k. The induction step asks: starting from any state at all, if the assertions hold for k consecutive cycles, can they fail on the next one? If the base case passes and the step cannot fail, the property holds forever: from reset it holds for k cycles, and every window of k good cycles is followed by another good one.

The catch is in "any state at all". The step does not start from reset. It may start from states the design can never reach, and if some unreachable state satisfies your assertions for k cycles and then breaks one, the step fails.

A small example that fails induction

Two 32-bit counters reset to zero and always increment together. An assertion claims they never show the pair (3, 5).

reg [31:0] a, b;
always @(posedge clk)
  if (rst) begin a <= 0; b <= 0; end
  else     begin a <= a + 1; b <= b + 1; end

`ifdef FORMAL
  always @(*) if (!f_init) assert (!(a == 3 && b == 5));
`endif

The property is obviously true: from reset, a == b on every cycle, so the pair (3, 5) is unreachable. BMC passes at any depth you try.

The induction step fails. The solver picks a start state with a = b − 2, for example (1, 3), which satisfies the assertion. One cycle later it is (2, 4), still fine, and the next cycle is (3, 5), which fails. For k = 1 the counterexample is (2, 4) → (3, 5). Raising k does not help much: in the unreachable family where a − b is fixed at −2, the counters cycle with a period of 232 and pass through (3, 5) once per period. So the solver can always find a run of good states of any length below 232 that ends at the bad state, and the step keeps failing until k reaches 232, about 4.3 billion. No solver will unroll that far.

The fix is an invariant

The real reason the property holds is a fact you did not state: a == b. Add it as an assertion.

always @(*) if (!f_init) begin
  assert (a == b);                     // helper invariant
  assert (!(a == 3 && b == 5));
end

Now the step must start from a state where both assertions hold, which rules out every state with a != b. From any state with a == b, the next state also has a == b, so the invariant is inductive by itself at k = 1, and the original property follows from it. The proof completes immediately.

This is the general pattern. An induction failure on a correct design means some relationship between registers is true in every reachable state but not written down. Your job is to find it and assert it. Typical helper invariants:

  • a counter equals the difference of two pointers
  • a one-hot state register is one-hot
  • a shadow model in the formal block matches the design's state
  • a "busy" flag is set exactly when a transaction counter is non-zero

Each helper is itself proven, so a wrong one fails rather than silently weakening the result.

When raising k is the right answer

Sometimes the gap is short, and raising k is cheaper than finding an invariant. Consider a three-stage shift register whose input is tied to zero, with an assertion that the last stage is always zero.

always @(posedge clk)
  if (rst) {s0, s1, s2} <= 3'b000;
  else begin s0 <= 1'b0;  s1 <= s0;  s2 <= s1; end

`ifdef FORMAL
  always @(*) if (!f_init) assert (!s2);
`endif

With k = 1 the step starts with s2 = 0 but s1 = 1, and fails a cycle later. With k = 2 it can still start with s0 = 1. With k = 3 the three good cycles force s1 and s0 to have been flushed to zero, and the step passes. The required depth equals the pipeline depth, which is small and known.

A rule of thumb follows. If the unreachable states are flushed out after a bounded number of cycles, as in a pipeline, raise k. If they can persist indefinitely, as with counters that drift apart or pointers that disagree, no practical k will do and you need an invariant.

Reading an induction trace

When the step fails, open the trace and ask, at the first cycle:

  1. Is this state reachable from reset? If it is, you have a real bug the base case has not reached yet; increase the BMC depth to confirm.
  2. If not, which registers are inconsistent with each other? That inconsistency is the invariant you are missing.
  3. After adding it, rerun. Repeat until the step passes. Each round usually teaches you something true about the design.

Engines based on IC3/PDR, such as abc pdr in SymbiYosys, construct inductive invariants automatically and often succeed where plain k-induction stalls. They are worth trying, but writing the invariant yourself also documents why the design is correct.

Try it yourself

  1. Put the two-counter example in a module with a reset assumption and run SymbiYosys in mode prove with the smtbmc engine; read the induction trace and confirm a != b in its first state.
  2. Add the a == b invariant and rerun; note how quickly it completes.
  3. Shrink the counters to 4 bits, remove the invariant, and find the smallest depth at which induction passes; explain the number from the cycle length.
  4. Try the same job with the abc pdr engine and compare the result.
