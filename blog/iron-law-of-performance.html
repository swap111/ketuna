The iron law of performance: instructions, CPI and clock period

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

Execution time is instruction count times cycles per instruction times clock period. Learn where each factor comes from, compute CPI from an instruction mix, and see how compilers, caches and pipelines move each one.

"This core runs at a higher clock, so it is faster." "This one does more instructions per second, so it wins." Both claims are common, and both can be wrong, because they look at one factor of a product of three. The time a program takes depends on how many instructions it executes, how many cycles each takes on average, and how long each cycle is. That relationship is often called the iron law of performance. Once you use it, you stop comparing processors by a single number and start asking which factor a design change actually moves.

The equation and its three factors

Execution time = instruction count × CPI × clock period

  • Instruction count (IC) is the number of instructions the program actually executes, not the number in the binary. A loop of 5 instructions that runs 1000 times counts as 5000. It depends on the algorithm, the compiler and the instruction set.
  • CPI (cycles per instruction) is the average number of clock cycles each executed instruction takes. It depends on the microarchitecture (pipelining, stalls, branch prediction) and on the memory system (cache misses add cycles).
  • Clock period is the length of one cycle, the inverse of clock frequency. It depends on the circuit design, the pipeline depth and the silicon process.

The units make the equation easy to check: instructions × (cycles / instruction) × (seconds / cycle) = seconds.

Computing CPI from an instruction mix

Different instruction types take different numbers of cycles, so CPI is a weighted average. Suppose a profile of a program on some core shows the following (numbers made up for illustration):

Class Fraction of instructions Average cycles
ALU 50% 1
Load 25% 2 (some cache misses)
Store 10% 1
Branch 15% 1.5 (some mispredictions)

CPI = 0.50 × 1 + 0.25 × 2 + 0.10 × 1 + 0.15 × 1.5 = 0.50 + 0.50 + 0.10 + 0.225 = 1.325.

If the program executes 2 million instructions at 100 MHz (a 10 ns period), the time is 2,000,000 × 1.325 × 10 ns = 26.5 ms.

A few lines of Python make it painless to try changes:

def cpi(mix):
    return sum(frac * cycles for frac, cycles in mix.values())

def run_time_ms(ic, mix, f_hz):
    return ic * cpi(mix) / f_hz * 1e3

base = {"alu": (0.50, 1), "load": (0.25, 2),
        "store": (0.10, 1), "branch": (0.15, 1.5)}
print(cpi(base), run_time_ms(2e6, base, 100e6))   # 1.325 26.5

How design changes move each factor

Now apply three different improvements, one at a time, to the same program.

A better compiler. Optimisation removes redundant instructions and cuts the instruction count by 20%, to 1.6 million, with the same mix. Time = 1.6 M × 1.325 × 10 ns = 21.2 ms. Only IC moved.

A better cache. Fewer misses bring the average load from 2 cycles down to 1.4. CPI becomes 0.50 + 0.35 + 0.10 + 0.225 = 1.175. Time = 2 M × 1.175 × 10 ns = 23.5 ms. Only CPI moved.

A deeper pipeline. Splitting stages raises the clock from 100 to 130 MHz, but the longer pipeline makes stalls costlier: loads now average 2.3 cycles and branches 2.0. CPI rises to 0.50 + 0.575 + 0.10 + 0.30 = 1.475. Time = 2 M × 1.475 / 130 MHz ≈ 22.7 ms. The clock period improved by 23%, but the run time improved by only about 14%, because CPI got worse at the same time.

Change IC CPI Clock Time
Baseline 2.0 M 1.325 100 MHz 26.5 ms
Better compiler 1.6 M 1.325 100 MHz 21.2 ms
Better cache 2.0 M 1.175 100 MHz 23.5 ms
Deeper pipeline 2.0 M 1.475 130 MHz 22.7 ms

The lesson is not that one change is best; with other numbers the ranking flips. The lesson is that every change should be evaluated on all three factors, because most changes improve one and cost another.

Why single-number comparisons mislead

Clock frequency alone ignores CPI and IC. The deeper pipeline above has a 30% higher clock but is nowhere near 30% faster.

MIPS (millions of instructions per second, which is frequency divided by CPI) ignores IC. Suppose a different compiler produces 2.6 million simpler instructions with a CPI of 1.15. Its MIPS rating is 100 / 1.15 ≈ 87, better than the baseline's 100 / 1.325 ≈ 75. But its run time is 2.6 M × 1.15 × 10 ns = 29.9 ms, slower than the baseline's 26.5 ms. More instructions per second is worthless if you need more instructions.

Instruction count alone ignores how hard each instruction is to execute. An instruction set with complex instructions may need fewer of them, but if each takes many cycles or forces a slower clock, the program is not faster.

The only reliable comparison is the time to run your workload. The iron law tells you why one design is faster and which factor to work on next.

Common mistakes

  • Counting static instructions. IC is what executes; a loop body counts once per iteration.
  • Using a CPI measured on a different program. CPI depends heavily on the workload's mix and memory behaviour.
  • Forgetting memory stalls. Cache misses belong in CPI; a "CPI of 1" pipeline is rarely 1 in practice.
  • Comparing chips by frequency across different microarchitectures. Only within one design does frequency translate directly into speed.

Try it yourself

  1. Compile a small benchmark with a RISC-V GCC cross-compiler at -O0 and at -O2, run both on Spike or QEMU, and count executed instructions (Spike's instruction log is one way). That is the IC change from the compiler.
  2. Run the same binaries on a small RISC-V core in Verilator with a cycle counter in the testbench, and compute CPI = cycles / instructions for each.
  3. Use the Python functions above to predict the run time from your measured IC and CPI, then check the prediction against the simulated cycle count.
