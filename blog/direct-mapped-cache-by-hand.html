Caches from scratch: a direct-mapped cache worked by hand

Computer architecture & RISC-V Beginner 27 Nov 2026 5 min read By Ketuna

Split an address into tag, index and offset, then trace hits and misses for a short program in a tiny direct-mapped cache. One shifted array turns a 0% hit rate into 75%.

A processor can execute an instruction in a cycle or so, but fetching a word from main memory takes many cycles. A cache is a small, fast memory close to the core that keeps copies of recently used data, so most accesses never have to wait for main memory. Caches can look like magic in a textbook diagram. They stop looking like magic once you work one by hand, with real addresses, on paper. That is what this article does, with a cache small enough to fit in a table.

Lines, not bytes

A cache does not store individual bytes. It stores lines (also called blocks): aligned chunks of memory, typically 32 or 64 bytes in real designs. When the core asks for one byte that is not in the cache, the cache fetches the whole line containing it. This bets on spatial locality: if a program reads one array element, it will probably read the next one soon. Keeping the line around bets on temporal locality: data used now is likely to be used again.

In a direct-mapped cache, each line of memory can live in exactly one place in the cache. That makes the hardware simple: to check whether an address is cached, you look in one slot and compare one tag.

Splitting the address

Our example cache is tiny, so the tables stay readable: 128 bytes of data, 16-byte lines, which gives 128 / 16 = 8 lines. Addresses are 32 bits. The cache splits every address into three fields:

  • Offset: which byte inside the line. 16 bytes per line needs log2(16) = 4 bits, address bits 3 to 0.
  • Index: which of the 8 cache lines to look in. log2(8) = 3 bits, address bits 6 to 4.
  • Tag: everything else, bits 31 to 7, 25 bits. It is stored with the line so the cache can tell which of the many memory lines that share an index is currently present.

Take address 0x0000_0104. In binary its low byte is 0000 0100 and bit 8 is set. The offset (bits 3 to 0) is 4. The index (bits 6 to 4) is 0. The tag is the address shifted right by 7, which is 2. So this address lives in cache line 0, byte 4, and the line must hold tag 2 to be a hit.

Tracing a short program

Here is a loop that reads two arrays of 32-bit words in turn, the kind of thing a dot product does:

int a[4], b[4], sum = 0;
for (int i = 0; i < 4; i++)
    sum += a[i] * b[i];

Suppose the linker places a at 0x100 and b at 0x180. The loads alternate: a[0], b[0], a[1], b[1] and so on, with the cache empty at the start.

Access Address Tag Index Offset Result
a[0] 0x100 2 0 0 miss
b[0] 0x180 3 0 0 miss
a[1] 0x104 2 0 4 miss
b[1] 0x184 3 0 4 miss
a[2] 0x108 2 0 8 miss
b[2] 0x188 3 0 8 miss
a[3] 0x10C 2 0 12 miss
b[3] 0x18C 3 0 12 miss

Every access misses. Both arrays map to index 0, because their addresses differ by 0x80, exactly the cache size. Each load of b evicts the line holding a, and the next load of a evicts b. The data needed is tiny, the cache has seven idle lines, and still nothing hits. This is a conflict miss: not caused by the cache being too small, but by two hot lines competing for one slot.

One shift changes everything

Move b by one line, to 0x190. Its index becomes 1 while a stays at index 0.

Access Address Index Result
a[0] 0x100 0 miss (fetch line)
b[0] 0x190 1 miss (fetch line)
a[1] to a[3] 0x104 to 0x10C 0 hit
b[1] to b[3] 0x194 to 0x19C 1 hit

Two misses in eight accesses: a 75% hit rate. The first two are compulsory misses, unavoidable on first touch; after that, spatial locality pays off.

Put a cost on it with the average memory access time: AMAT = hit time + miss rate × miss penalty. With a 1-cycle hit and a 20-cycle miss penalty (made up for illustration), the first layout gives 1 + 1.0 × 20 = 21 cycles per access, the second 1 + 0.25 × 20 = 6 cycles. Same code, same cache, three and a half times faster, purely from where the data sits.

Common mistakes

  • Forgetting the valid bit. At reset the tags hold garbage; without a valid bit, a random match is a false hit.
  • Using bytes where bits belong. Index and offset widths are log2 of the number of lines and of the line size in bytes.
  • Blaming capacity for conflict misses. If the working set is far smaller than the cache, look at the indices first.
  • Ignoring the store side. Writes need a policy (write-through or write-back) as well; that is a separate design choice.

Try it yourself

  1. Write a 20-line Python model of this cache that takes a list of addresses and prints tag, index, offset and hit or miss. Check it against both tables above.
  2. Change the line size to 8 bytes and the number of lines to 16 (same capacity) and rerun both traces. Predict the result before you run it.
  3. Write the lookup in Verilog (tag array, valid bits, comparator) and simulate it in Icarus Verilog with the same address list, comparing against your Python output.
