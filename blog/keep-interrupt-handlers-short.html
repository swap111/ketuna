Keeping interrupt handlers short: what belongs in an ISR and what does not

Embedded systems Beginner 27 Nov 2026 5 min read By Ketuna

A good interrupt handler acknowledges the hardware, captures the data that would otherwise be lost, and defers everything else. Here is why, with the arithmetic and the patterns for deferring work.

An interrupt handler runs when the hardware decides, not when your program is ready, and while it runs, other interrupts at the same or lower priority wait. Every microsecond you spend inside it is a microsecond added to the response time of everything else. That is the whole reason behind the advice "keep ISRs short", and once you see the arithmetic, deciding what goes in and what comes out stops being a matter of taste.

Three jobs, in order

A well-written interrupt service routine (ISR) does three things and then returns:

  1. Acknowledge. Clear the condition that raised the interrupt, usually by writing a flag or reading a data register, as the reference manual describes. If you return without clearing a level-triggered source, the interrupt fires again immediately and the main program never runs.
  2. Capture. Save anything the hardware will overwrite soon: a received byte, a timer capture value, an ADC result, a timestamp. If you do not take it now, it is gone.
  3. Defer. Tell the rest of the program that something happened, using a flag, a queue or an operating-system signal, so the real work runs outside the interrupt.

Parsing a message, updating a display, writing to flash, logging, retrying a bus transfer: all of that is deferred work.

The cost of a long handler, in numbers

Take a board with two interrupt sources at the same priority: a UART receiving at 115200 baud with the common 8N1 format, and a periodic timer. Each byte on the wire is 10 bits, so a new byte can arrive every 10 / 115200 s, about 86.8 µs. Suppose the UART has a receive holding register that keeps one byte. The firmware then has roughly 86.8 µs to read each byte before the next one overwrites it.

Now someone adds a debug message to the timer ISR: a 40-character printf sent out on a second, polled UART at the same baud rate. Sending 40 characters takes 40 × 86.8 µs, about 3.5 ms. While the timer ISR busy-waits on that output, the receive interrupt cannot run, and up to 40 incoming bytes arrive. With one byte of buffering, about 39 of them are lost. The bug is in the timer ISR, but the symptom appears in the UART protocol code, which is why these problems take so long to find.

The general rule: the worst-case delay for any interrupt is at least as long as the longest handler that can block it, plus any section of code that runs with interrupts disabled. Short handlers keep that number small and predictable.

A worked case: a sensor's data-ready line

An external accelerometer pulls a GPIO pin low when a new sample is ready. Reading the sample takes an I2C transaction of several bytes. At 400 kHz each byte with its acknowledge bit takes 9 clock periods, 22.5 µs, so a six-byte read with address and register bytes costs a few hundred microseconds even before any bus retries. That transfer does not belong in the GPIO interrupt.

Here is the tempting version:

void gpio_isr(void)                     /* do not do this */
{
    gpio_clear_flag(ACCEL_INT_PIN);
    i2c_read(ACCEL_ADDR, REG_DATA, buf, 6);  /* blocks on the bus */
    filter_update(buf);                      /* maths in the ISR  */
    printf("x=%d\n", x);                     /* slow output       */
}

And the short version, which acknowledges, captures a timestamp and defers:

#include <stdbool.h>
#include <stdint.h>

static volatile bool     accel_ready;
static volatile uint32_t accel_stamp;

void gpio_isr(void)
{
    gpio_clear_flag(ACCEL_INT_PIN);     /* 1. acknowledge */
    accel_stamp = timer_now();          /* 2. capture     */
    accel_ready = true;                 /* 3. defer       */
}

int main(void)
{
    init_all();
    for (;;) {
        if (accel_ready) {
            accel_ready = false;
            uint8_t buf[6];
            if (i2c_read(ACCEL_ADDR, REG_DATA, buf, 6) == 0)
                filter_update(buf, accel_stamp);
        }
        /* other work */
    }
}

The timestamp is captured in the ISR because it is the one piece of information that changes meaning if you read it later. The data itself stays safely in the sensor until the main loop asks for it.

Ways to defer

  • A flag. One volatile bool per event, as above. Fine when the main loop is fast compared with the event rate and missing a repeat event does no harm, because two events between checks look like one.
  • A queue. When every event carries data that must not be lost, such as received bytes, the ISR pushes into a single-producer, single-consumer ring buffer; see Writing an interrupt-safe ring buffer for UART receive.
  • An RTOS signal. With a scheduler, the ISR gives a semaphore or submits a work item, and a task blocked on it wakes and does the work. In Zephyr, k_sem_give() and k_work_submit() may be called from an ISR. Use only the calls the RTOS documents as ISR-safe, and never wait on anything inside a handler.

What does not belong in an ISR

  • Formatted printing, logging to flash, or anything that waits for a slow peripheral
  • Blocking waits, delays and polling loops
  • Taking a mutex or calling malloc
  • Long loops whose length depends on data
  • Heavy floating-point work on cores where the handler must save extra registers for it

Try it yourself

  1. The Ketuna track D lab D4 runs a timer interrupt and a UART receive interrupt on QEMU's RISC-V virt machine. Add a busy-wait of a few milliseconds to the timer handler, then type into the console and record, with the mtime counter, the largest gap between entering the timer handler and the next entry into the UART handler. QEMU holds input back when its UART is full, so bytes arrive late rather than being lost; the latency number is what tells you a real board would drop them.
  2. Move the work out with a flag, repeat the measurement, and compare the worst-case delay with the 86.8 µs byte period.
  3. On a real board, toggle a spare GPIO at the start and end of each ISR and watch it with a logic analyser and the open-source PulseView. The pulse widths are your handler times; compare them with the byte period you calculated.
