Zephyr devicetree for beginners: describing hardware so drivers can find it

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

How Zephyr uses devicetree nodes, properties, overlays and bindings to tell drivers where a peripheral lives and which pins it uses, all resolved at build time into C macros.

In this article

  2. An overlay for one sensor

In bare-metal firmware, the address of the I2C controller, the sensor's bus address and the pin for its interrupt line are usually #defines scattered through the code. Move to a new board and you hunt for every one of them. Zephyr takes a different approach: the hardware is described once, in a devicetree, and drivers and applications ask the build system for the values. This article explains the pieces, using a temperature sensor on an I2C bus as the running example.

A tree that describes hardware, not behaviour

A devicetree is a text description of the hardware as a tree of nodes. Each node is a device or a bus: the SoC, its I2C controller, a sensor on that controller. Each node has properties: its register address, its interrupt number, the GPIO it uses, its clock frequency.

The tree is assembled from layers:

  • the SoC file (.dtsi) describes what is inside the chip: every peripheral, its base address and interrupts, mostly with status = "disabled";
  • the board file (.dts) includes the SoC file and enables what the board uses, sets pins and adds the parts soldered on the board;
  • your overlay file adds or changes nodes for your application without editing either of the above.

Unlike Linux, Zephyr does not parse the devicetree at run time. At build time, a script turns the final merged tree into a generated C header full of macros. Your code reads properties through those macros, and a wrong node name is a compile error, not a crash in the field.

An overlay for one sensor

Suppose a board's I2C controller is labelled i2c0 in the board file, and you have connected a temperature sensor at bus address 0x48 with an alert output on a GPIO pin. You describe that in app.overlay, in the application folder, which the build picks up automatically (a file boards/<board>.overlay takes its place for a specific board):

&i2c0 {
    status = "okay";
    clock-frequency = <I2C_BITRATE_FAST>;

    temp0: temp-sensor@48 {
        compatible = "vnd,demo-temp";
        reg = <0x48>;
        alert-gpios = <&gpio0 7 GPIO_ACTIVE_LOW>;
        conversion-ms = <100>;
    };
};

Read it piece by piece:

  • &i2c0 { ... } refers to an existing node by its label and adds to it. Here it also switches the controller on.
  • temp0: is a new label for the sensor node, so C code can find it. temp-sensor@48 is the node name; the part after @ is the unit address, which matches reg.
  • compatible says what kind of device this is. It is the key that connects the node to a binding and a driver. The vnd vendor prefix is the placeholder Zephyr uses in examples and tests; a real part uses its manufacturer's prefix.
  • reg = <0x48> is the address on the parent bus, so for a node under an I2C controller it is the 7-bit I2C address.
  • alert-gpios is a phandle-array: a reference to the GPIO controller node, then the pin number and flags.

Bindings: the schema for a compatible

Zephyr will not accept arbitrary properties. Every compatible needs a binding, a YAML file that lists the allowed properties and their types. For an application-specific device, put it in dts/bindings/ inside your application folder, which is searched automatically:

# dts/bindings/vnd,demo-temp.yaml
description: Demo I2C temperature sensor with an alert output

compatible: "vnd,demo-temp"

include: i2c-device.yaml

properties:
  alert-gpios:
    type: phandle-array
    description: Active alert output from the sensor
  conversion-ms:
    type: int
    default: 100
    description: Time between conversions, in milliseconds

include: i2c-device.yaml brings in the standard properties for any I2C device, such as reg. If the overlay misspells conversion-ms or gives it a string, the build fails with an error naming the node and property, which is much better than discovering it on the bench.

Reading the tree from C

The generated macros take a node identifier and a property name. Property names are written with underscores instead of hyphens:

#include <zephyr/kernel.h>
#include <zephyr/device.h>
#include <zephyr/drivers/i2c.h>
#include <zephyr/drivers/gpio.h>

#define TEMP_NODE DT_NODELABEL(temp0)

static const struct i2c_dt_spec temp_i2c = I2C_DT_SPEC_GET(TEMP_NODE);
static const struct gpio_dt_spec temp_alert =
    GPIO_DT_SPEC_GET(TEMP_NODE, alert_gpios);
static const int conv_ms = DT_PROP(TEMP_NODE, conversion_ms);

int temp_init(void)
{
    if (!device_is_ready(temp_i2c.bus) ||
        !gpio_is_ready_dt(&temp_alert))
        return -ENODEV;
    return gpio_pin_configure_dt(&temp_alert, GPIO_INPUT);
}

int temp_read_raw(uint8_t out[2])
{
    uint8_t reg = 0x00;                  /* made-up result register */
    return i2c_write_read_dt(&temp_i2c, &reg, 1, out, 2);
}

I2C_DT_SPEC_GET bundles the controller device and the bus address; GPIO_DT_SPEC_GET bundles the GPIO controller, pin and flags, including the active-low setting. Nothing in this code mentions 0x48, pin 7 or a controller address. Move the sensor to another bus or another board, change the overlay, and the C code is unchanged.

A real Zephyr driver goes one step further: it defines DT_DRV_COMPAT for its compatible and uses the DT_INST_* macros to create one driver instance for every enabled node with that compatible. That is how one driver serves three identical sensors on two buses.

Common mistakes

  • Node present but status not "okay". Disabled nodes generate no device. Many SoC peripherals are disabled by default and must be enabled in the board file or overlay.
  • Devicetree right, Kconfig missing. The driver for a subsystem is compiled only if its Kconfig option is also enabled, for example CONFIG_I2C=y. Both halves are needed.
  • Using a device without checking readiness. Initialisation can fail at boot. Always check device_is_ready() or the matching *_is_ready_dt() helper.
  • Guessing what the build saw. The final merged tree is written to build/zephyr/zephyr.dts. When something is not found, read that file before anything else.

Try it yourself

  1. Install Zephyr with west following the project's getting-started guide, build samples/hello_world for qemu_riscv32, and open build/zephyr/zephyr.dts. Find the UART node and check its address against the QEMU virt memory map (0x10000000).
  2. Add a node under the root (/ { ... };) in an overlay with a vnd,demo-config compatible and an integer property, write its binding, and print the value with DT_PROP from main().
  3. Misspell the property name in the overlay and read the build error. Then remove the binding file and read that error too, so you recognise both later.
