Verifying an ML accelerator against a numpy golden model

Edge AI Advanced 27 Nov 2026 5 min read By Ketuna

An ML accelerator is verified like any datapath, against a bit-exact integer reference. Writing that numpy golden model, choosing random and corner tensors, and comparing layer by layer to localise bugs.

In this article
  1. The golden model must be integer and bit-exact
  2. Random tensors, then corners
  3. Compare layer by layer, and inside the layer
  4. A cocotb test skeleton
  5. Try it yourself

An ML accelerator has an unusual property for a piece of hardware: small arithmetic bugs barely show at the system level. A requantization that rounds the wrong way, or an accumulator that wraps on one rare tile, may cost a fraction of a percent of model accuracy, which looks like noise. Teams that verify by "the model still classifies the test images" ship those bugs. The fix is to treat the accelerator as the integer datapath it is and verify it the way any datapath is verified: against a reference model that defines every bit of every output, with stimulus designed to reach the corners.

The golden model must be integer and bit-exact

A float model of the network is the wrong reference. Quantized hardware is supposed to differ from float, so a float comparison needs a tolerance, and any tolerance large enough to accept correct rounding also accepts many bugs. The reference has to compute the same integer arithmetic the hardware computes, and agree exactly.

That forces you to write down the arithmetic precisely, which is valuable in itself: operand widths, how zero points are applied, accumulator width and what happens on overflow, the rounding mode of requantization, the clamp limits with and without a fused ReLU. In numpy, with 64-bit intermediates so the model itself cannot overflow:

import numpy as np

def dense_ref(x, w, b, zx, m0, shift, zy, relu):
    """Bit-exact integer reference for one dense layer."""
    acc = (b.astype(np.int64)
           + (x.astype(np.int64) - zx) @ w.T.astype(np.int64))
    assert np.all(np.abs(acc) < 2**31), "accumulator overflow"
    y = (acc * m0 + (1 << (shift - 1))) >> shift
    lo = zy if relu else -128
    return acc.astype(np.int32), np.clip(y + zy, lo, 127).astype(np.int8)

Two choices here pay off later. The function returns the accumulator as well as the output, so a mismatch can be located before or after requantization. And the overflow check makes the reference refuse inputs the specification does not cover, instead of silently agreeing with hardware that wraps.

Use one reference for everyone. The same Python model generates expected values for the RTL testbench, checks the firmware driver, and is compared against the training framework's own integer export. If the RTL team and the firmware team each write their own reference, they will eventually disagree and the bug will hide in the gap.

Random tensors, then corners

Constrained-random stimulus is the workhorse: random layer shapes within the supported range, random int8 inputs and weights, random biases, and random quantization parameters (zero points, multipliers and shifts) within their legal ranges. Fix the seed per run and log it, so a failure can be replayed exactly.

Random data rarely reaches extremes, though. Sums of random products cluster near zero, so accumulators almost never approach their limits, and outputs almost never saturate. Add directed corner cases:

  • inputs and weights at their extremes, chosen so that every product has the same sign and the sum is as large as possible
  • outputs pushed to both clamp limits, with and without ReLU
  • accumulator values that land exactly on a rounding half, to pin down the rounding mode
  • shapes that are not multiples of the array or tile size, including a single row, a single column and the largest legal layer
  • zero points at both ends of their range

The zero point deserves special attention. The hardware multiplies (x − zx), which spans −255 to 255 and needs 9 bits, not 8. A classic bug is a subtractor that truncates the difference to 8 bits. It passes every test with zx = 0, which is exactly what a lazy test uses. Choose corners in the (x − zx) domain: with zx = −128, an input of −128 contributes nothing, and the stressful input is 127.

Compare layer by layer, and inside the layer

A whole network is a poor unit for debugging: if the final logits differ, the bug could be in any layer, and errors propagate and mix. Verify in stages:

  1. Single operations (one dense layer, one convolution, one pooling) against the reference, with all the stimulus above.
  2. Internal taps: compare the accumulator values before requantization as well as the final int8 outputs. A mismatch in accumulators points at the MAC array, operand fetch or tiling; matching accumulators with mismatched outputs point at requantization.
  3. Whole models layer by layer: run a real quantized network, dump every intermediate tensor from hardware and reference, and report the first layer and first element that differ.

A scoreboard that prints "layer 3, output channel 7, position (2, 5): got 41, expected 42, accumulator matched" turns an afternoon of waveform staring into a five-minute fix.

A cocotb test skeleton

With cocotb, the testbench is Python, so the golden model plugs in directly. The two helpers that load tensors and read results back depend on your accelerator's interface (registers, memory model or a bus driver), so they are named here but not shown:

import cocotb
import numpy as np
from cocotb.clock import Clock

@cocotb.test()
async def dense_random(dut):
    cocotb.start_soon(Clock(dut.clk, 10, units="ns").start())
    seed = int(cocotb.RANDOM_SEED)
    rng = np.random.default_rng(seed)
    for trial in range(200):
        n_in = int(rng.integers(1, 257))
        n_out = int(rng.integers(1, 65))
        x = rng.integers(-128, 128, n_in, dtype=np.int8)
        w = rng.integers(-127, 128, (n_out, n_in), dtype=np.int8)
        b = rng.integers(-2**15, 2**15, n_out, dtype=np.int32)
        zx = int(rng.integers(-128, 128))
        m0 = int(rng.integers(2**30, 2**31))
        shift = int(rng.integers(32, 48))
        exp_acc, exp_y = dense_ref(x, w, b, zx, m0, shift, 0, False)
        await load_layer(dut, x, w, b, zx, m0, shift)   # design-specific
        got_acc, got_y = await read_results(dut, n_out) # design-specific
        bad = np.flatnonzero(got_y != exp_y)
        assert bad.size == 0, (
            f"seed {seed} trial {trial}: first mismatch at {bad[0]}, "
            f"acc got {got_acc[bad[0]]} exp {exp_acc[bad[0]]}")

Run it in a regression with many seeds, add the corner-case tests beside it, and collect functional coverage on what matters: shapes at and around tile boundaries, saturation hit at both limits, ReLU on and off, every legal shift.

Common mistakes:

  • comparing against the float model with a tolerance
  • testing only with zero points of zero
  • verifying only whole-network accuracy, so rare arithmetic bugs average out
  • separate reference models for RTL and firmware that drift apart
  • random stimulus without directed corners, so accumulators never approach overflow

Try it yourself

  1. Write dense_ref and a matching conv2d_ref in numpy, and check both against a float computation on data where the quantization parameters make the result exactly representable.
  2. Build a small MAC-lane engine in Verilog, simulate it with Icarus Verilog or Verilator under cocotb, and run the random test above with your own load_layer and read_results.
  3. Introduce the 8-bit zero-point subtraction bug on purpose and confirm which of your tests catch it.
  4. Export a small int8 model, run it layer by layer through your reference, and compare every intermediate tensor with the inference framework's output.
