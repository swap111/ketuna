Interrupt controllers in RISC-V SoCs: what the core-local and platform-level units do

Computer architecture & RISC-V Advanced 27 Nov 2026 5 min read By Ketuna

Timer and software interrupts stay local to each hart; external interrupts pass through a platform-level controller with priorities, thresholds and claim/complete. How the pieces fit and where they bite.

In this article

A RISC-V hart has exactly three machine-level interrupt inputs: timer, software and external. A real SoC has dozens of interrupt sources, from UARTs and DMA channels to GPIO pins, and possibly several harts that could serve them. Two kinds of controller bridge that gap. A core-local unit provides the timer and software interrupts for each hart, and a platform-level controller funnels every peripheral interrupt into each hart's single external interrupt input, with priorities and a handshake that keeps sources from being lost or served twice. Knowing how they divide the work explains most interrupt latency and most interrupt bugs.

Two units, two jobs

The core-local unit (historically called the CLINT; the newer ACLINT specification splits it into timer and software-interrupt devices) holds a free-running 64-bit mtime counter shared by the platform, one mtimecmp register per hart, and one msip bit per hart. The timer interrupt of a hart is pending while mtime ≥ its mtimecmp. Writing 1 to a hart's msip raises its software interrupt, which is how one hart pokes another. These signals go straight into the hart's mip register with no arbitration, because each belongs to exactly one hart.

The platform-level controller (the PLIC in its standard form) handles everything else. Each interrupt source gets a number from 1 upwards (0 means "none") and a programmable priority. For each context, typically one per hart per privilege mode that takes interrupts, it has an enable bit per source and a priority threshold. The controller asserts a context's external interrupt line when at least one enabled source is pending with a priority above that context's threshold.

The claim/complete handshake

The heart of the platform controller is a two-step handshake that serves each interrupt exactly once, even with several harts competing:

  1. Claim. The handler reads the context's claim register. The controller returns the ID of the highest-priority pending, enabled source and atomically clears its pending bit. If another hart claims at the same moment, only one gets the ID; the other gets the next one, or 0.
  2. Service. The handler deals with the peripheral and clears the cause in the peripheral itself.
  3. Complete. The handler writes the same ID back to the complete register (the same address as the claim register). Until then, the controller's gateway for that source will not forward a new request from it.

The gateway also converts the source's signalling: a level-triggered source is re-sampled after completion, so if the peripheral still holds its line high, a new request appears; an edge-triggered source is latched once per edge.

With the register layout from the PLIC specification, an M-mode external interrupt handler for context ctx looks like this:

#include <stdint.h>

#define PLIC_BASE      0x0C000000u
#define PLIC_CLAIM(c)  (*(volatile uint32_t *) \
                        (PLIC_BASE + 0x200004u + 0x1000u * (c)))

typedef void (*irq_fn)(void);
extern irq_fn irq_table[];   /* indexed by source ID */

void external_irq(uint32_t ctx)
{
    uint32_t id;
    while ((id = PLIC_CLAIM(ctx)) != 0u) {   /* drain all pending */
        irq_table[id]();                      /* clears the source */
        PLIC_CLAIM(ctx) = id;                 /* complete */
    }
}

The loop matters. Each trap costs entry and exit overhead, so serving every pending source per trap reduces work when interrupts arrive in bursts.

Where the latency goes

The platform-level approach is flexible and scales to many sources and harts, but it adds steps to every external interrupt: the trap entry, a register save, a read of the claim register across the bus (often several cycles, and serialising), a table dispatch, and a write to complete. All sources share one trap vector, so software must find the handler. Priority between harts and nesting are managed in software through thresholds.

For microcontrollers that need fast, deterministic, nested interrupts, a separate core-local interrupt controller specification (CLIC) adds per-interrupt levels, hardware vectoring per source and preemption. For large systems with many harts and virtualisation, the Advanced Interrupt Architecture defines message-signalled interrupts delivered to per-hart interrupt files. Check the current ratification status of each before committing a design to it; the choice depends on whether you need determinism, scale, or simplicity.

The 64-bit timer on a 32-bit hart

mtime and mtimecmp are 64 bits even on RV32, so software writes mtimecmp in two halves. Writing the low half first can momentarily form a value smaller than mtime and fire a spurious interrupt. A safe sequence writes all ones to the low half, then the new high half, then the new low half, so the intermediate value is never below the target. For a 1 ms tick with mtime counting at 10 MHz (an illustrative frequency), each tick adds 10,000 to the previous compare value. Add to the last compare value, not to the current mtime, or the tick period drifts by the handler latency every time.

Common mistakes

  • Forgetting to complete. The source is never forwarded again, and that peripheral appears dead.
  • Completing before clearing the peripheral. A level-triggered source immediately raises a new, spurious request.
  • Leaving priority at 0. Priority 0 means "never interrupt"; enabled sources still do nothing.
  • Confusing contexts. Enabling a source for the S-mode context of hart 0 does nothing for hart 0's M-mode handler.

Try it yourself

  1. Run a bare-metal program on the QEMU virt machine, which includes a standard core-local timer and PLIC, and take a UART receive interrupt through the claim/complete loop above.
  2. Set the context threshold above the UART's priority and confirm that the interrupt is masked; lower it and confirm it arrives.
  3. Implement a tiny PLIC model with two sources and one context in Verilog, and verify the claim/complete rules with assertions in SymbiYosys.
