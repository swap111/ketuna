Using AI tools responsibly in engineering: by hand first, then check

Careers & skills Beginner 27 Nov 2026 6 min read By Ketuna

Do a task yourself first so you can judge what an AI assistant gives you, then verify generated code with the same tests, lint and review you would apply to any other code. Here is why, and how.

  2. Generated code is just code
  3. How much checking each output needs
  4. A worked example of reviewing AI output

AI assistants can draft a testbench, explain an unfamiliar script or suggest corner cases in seconds. They are also confidently wrong in ways that look exactly like correct answers: a FIFO whose full flag is off by one, a register address that does not exist, a clock-domain crossing with no synchronizer. In software, a bug like that may be caught in the next release. In hardware it can be fabricated into silicon. So the question is not whether to use these tools, but how to use them without losing the ability to tell good output from bad.

Why "by hand first" comes before the tool

You can only review what you understand. If you have never written a synchronous FIFO, an AI-generated one looks plausible: it compiles, the signal names make sense, the comments are confident. You have no way to notice that the pointers are one bit too narrow to tell full from empty.

Once you have built one yourself, with your own mistakes and your own debugging, you know where the traps are. You know to check the pointer width, the behaviour on a simultaneous read and write when full, and what happens on reset. The same AI output now gets a sharp review instead of a nod.

This is why a sensible learning order is: do it by hand, then do it with AI, then compare. The by-hand pass builds the judgement; the AI pass shows you where the tool helps and where it misleads; the comparison teaches you both. Later, on familiar tasks, you can start with the AI draft, but only because your earlier hand work gave you the means to check it.

Generated code is just code

A useful mental rule: code from an AI assistant gets exactly the same checks as code from a new colleague you have not worked with yet. Not fewer because it looks polished, and not a special ritual either. For hardware and firmware, that means:

  • Read it before running it. Predict where it might be wrong. Write the predictions down; it trains your eye.
  • Lint it. verilator --lint-only -Wall for RTL, compiler warnings turned up for C (gcc -Wall -Wextra).
  • Test it against the spec, not against itself. A reference model or expected values that you wrote or reviewed independently.
  • Plant a bug to confirm the test can fail. A test that passes on broken code proves nothing.
  • Review it with a person in the normal pull request flow, with AI use stated openly.

Compiling proves syntax. Passing a test written by the same tool that wrote the design proves only that both share the same understanding, which may be the same misunderstanding.

How much checking each output needs

Not every output deserves the same scrutiny. Two questions decide it: how easy is it to verify, and how much does an error cost?

Output Easy to verify? Cost of error Checking needed
Regex or log-parsing script Yes: run it on known input Low Quick test on sample data
Documentation draft Yes: read it Low to medium Read for accuracy against the design
Testbench scaffolding Mostly Medium Review, and confirm it can fail
Register map or driver code Partly: needs the datasheet High Check every address and bit field against the source
Protocol or CDC logic Hard: bugs are rare and timing-dependent Very high Independent tests, formal checks, expert review

The pattern is that AI output needs the most checking exactly where it is most tempting to trust it: subtle concurrency, protocol corner cases and numbers that should come from a datasheet. Treat any address, timing value or bit position from an AI tool as unverified until you have found it in the real source.

A worked example of reviewing AI output

Suppose you ask an assistant for a debounce module for a push button, and it returns a design that counts 20 ms of stable input at a 50 MHz clock. Before simulating, a quick review:

  • Counter width. 20 ms at 50 MHz is 50,000,000 × 0.020 = 1,000,000 cycles. That needs 20 bits, because 220 = 1,048,576. If the generated counter is 16 bits wide, it wraps at 65,536 and never reaches the threshold. This is a common class of AI error: the arithmetic in the comment is right and the declared width is not.
  • Synchronizer. A button is asynchronous to the clock. Does the input pass through two flip-flops before the counter? If not, add them.
  • Reset value. Does the output start in a defined state?

Three checks, a few minutes, and two of them need knowledge you only have if you have built something similar by hand. Then simulate with a test that holds the input stable for just under and just over the threshold, and confirm the output changes only in the second case.

Responsibility and confidentiality

The engineer who commits the code is responsible for it, whoever drafted it. "The AI wrote it" is not an answer in a design review or an incident report.

Two more rules apply in any workplace or course:

  • Follow the policy on what you may paste. Many organisations restrict which tools may see their designs or customer data. Never paste confidential material into a tool that is not approved for it.
  • Be open about AI use. State it in the pull request or the lab report. Reviewers judge risk better when they know which parts were generated and how you checked them.

Common mistakes

  • Skipping the hand-work stage and then being unable to explain your own submission in a review or interview.
  • Accepting code because it compiles or because the comments sound right.
  • Letting the tool write both the design and its tests with no independent check.
  • Trusting numbers (addresses, timing parameters, register fields) without finding them in the datasheet or spec.

Try it yourself

  1. Write a small block by hand, such as a debounce circuit or an 8-bit counter with enable, and a self-checking testbench for it in Icarus Verilog or cocotb.
  2. Ask an AI assistant for the same block from the same spec. Before running anything, write down three places you expect it to be wrong.
  3. Run verilator --lint-only -Wall on it and run it against your own testbench. Record which problems your review caught, which only the test caught, and which neither caught.
  4. Plant a deliberate bug in the generated version and confirm your testbench fails. If it does not, improve the testbench before trusting either design.
