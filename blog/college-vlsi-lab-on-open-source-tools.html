Setting up a college VLSI lab on open-source EDA tools

India's electronics ecosystem Intermediate 27 Nov 2026 5 min read By Ketuna

How to set up a college VLSI lab that runs on open-source tools, with suitable machines, a containerised and version-pinned toolchain, open PDKs and lab exercises that need no licence server.

Many college VLSI labs depend on a licence server that is shared, rationed, expired or only reachable from the lab. Students cannot practise at home, labs stall when the server is down and the skills stop at the edge of the campus network. Open-source EDA tools and open PDKs remove that dependency. A lab built on them lets every student run the same flow on a lab machine, a personal laptop or a cloud runner. Doing it well is mostly an exercise in configuration management, and this article walks through the choices.

What the lab needs to cover

Decide the learning outcomes first, then pick tools. A typical undergraduate and early postgraduate sequence maps neatly onto open tools:

Topic Tools
RTL simulation and waveforms Icarus Verilog, Verilator, GTKWave
Python testbenches cocotb
Synthesis Yosys
Formal checks SymbiYosys
Place and route, timing OpenROAD, OpenSTA, orchestrated by LibreLane
Layout and physical verification Magic, KLayout, Netgen
Analog schematic and simulation Xschem, ngspice
FPGA flows Yosys with open place-and-route tools for supported boards

All of these can share one installation, and one open PDK such as sky130, gf180 or IHP SG13G2 ties the digital and analog exercises to a real process.

Machines: modest for most, more for some

RTL simulation, synthesis of small blocks and analog simulation run comfortably on ordinary lab desktops and student laptops. Place and route of a small block is heavier: it wants several cores and a generous amount of memory, and a full chip-level run more still. A practical lab plan:

  • Lab desktops running Linux natively, or dual-boot, for everyday work
  • Student laptops using the same container, so practice at home matches the lab
  • One or two larger shared machines, or a continuous integration service, for full physical design runs that would be slow on desktops

Linux is the natural host. On Windows laptops, students can use a Linux subsystem or a virtual machine with the container inside; test this path yourself before term starts, because graphics for layout viewers is where it most often breaks.

Containers and a pinned toolchain

The single most important decision is to pin versions. Open tools move quickly, and a flow that works with one combination of tool and PDK versions may fail with the next. If each machine installs "the latest", lab exercises break mid-semester and students get different results for the same design.

Package the tools in a container image and give it an explicit version tag. Community-maintained images bundling many open tools exist, and LibreLane documents its own supported environments; you can use one directly or build your own from a recipe kept in version control. Record exactly what is inside:

# lab-toolchain.txt  (kept in the course repository)
image:    <registry>/<image>:<tag>     # never "latest"
pdk:      sky130, version <commit or release id>
librelane: <version>
checked:  <date>, by <name>, on the exercise suite

Students start every session the same way. The mount puts their work on the host, so nothing is lost when the container exits:

docker run --rm -it -v "$PWD":/work -w /work <registry>/<image>:<tag> bash

A short smoke test, run on every machine at the start of term, confirms that the tools are present and report the expected versions:

iverilog -V | head -n 1
verilator --version
yosys -V
ngspice --version | head -n 3
klayout -v

Upgrade between semesters, not during one, and only after rerunning the whole exercise suite against the new image.

Open PDKs and their versions

The PDK is versioned too. Install it once into a shared location, or bake it into the image, and pin it the same way. Use the version manager or install method that the flow's documentation recommends, so the PDK version and the flow agree. When a student reports that their design passes design rule checks on one machine and fails on another, the first thing to check is whether both machines use the same PDK version.

Lab exercises without licence servers

Design exercises so they run unattended and grade themselves where possible. That keeps feedback fast and makes the lab robust to staff shortages:

  1. Self-checking testbenches in cocotb or Verilog that print a clear pass or fail
  2. Synthesis exercises where students report cell counts and explain warnings
  3. Timing exercises on a small block with an SDC file, reading OpenSTA reports
  4. A physical design run with LibreLane on a small block, with students explaining the timing, DRC and LVS results
  5. An analog exercise in Xschem and ngspice, such as an inverter's transfer curve across process corners

Keep exercise templates in a version-controlled repository. A continuous integration job can run every student's submission through the same container, so "it worked on my machine" stops being an argument. Ask students to write a short report for each exercise, explaining their result rather than pasting it; drawing the circuit or waveform by hand before running the tool, and checking AI-generated code against their own reasoning, are habits worth grading.

Common mistakes

  • Installing tools by hand on each machine, so no two are alike
  • Upgrading tools in the middle of a semester
  • Choosing exercises too large to finish on lab machines in a session
  • Forgetting to pin the PDK along with the tools
  • Testing the setup only on Linux desktops, then discovering laptops fail on the first day

Try it yourself

  1. Pull a community open-tool container image, pin it by tag, and run the smoke test above.
  2. Write a three-exercise mini lab: an Icarus Verilog testbench, a Yosys synthesis report and an OpenSTA timing check, all on the same small design.
  3. Set up a continuous integration job that runs those exercises in the same container on every commit to the lab repository.
