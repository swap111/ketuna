Setting up a hardware regression in CI: seeds, triage and flaky tests

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

Structure a hardware regression as fast per-commit smoke runs and broad nightly random runs, record every seed, group failures by signature, and treat a flaky simulation as a bug in its own right.

In this article
  1. Two tiers: per-commit and nightly
  2. Record every seed, and everything else
  3. Triage: group failures by signature
  4. Flaky tests are bugs
  5. Keeping the regression trusted
  6. Try it yourself

A testbench that only runs when someone remembers to run it protects nothing. A regression runs every test automatically, on every change, and reports the result where the whole team sees it. Hardware regressions have their own wrinkles compared with software: simulations are slow, many tests are random, and a failure is only useful if anyone can reproduce it next week. Getting the structure right early saves a project from the slow drift where the regression is "mostly green" and nobody trusts it.

Two tiers: per-commit and nightly

One regression cannot be both fast and thorough. Split it.

The smoke tier runs on every push and must finish in minutes. It includes lint with warnings treated as errors, every directed test, and a few random tests with fixed seeds. Fixed seeds matter here: if the smoke tier used fresh seeds, a pull request could fail on a bug it did not introduce, and people would learn to rerun until green. A red smoke run should always mean "this change broke something".

The nightly tier runs every test with many fresh random seeds, collects coverage, and takes as long as the compute budget allows. Its job is to explore. Its failures are expected and valuable, and they go to triage rather than blocking anyone's work.

Record every seed, and everything else

A random failure is worthless if nobody can reproduce it. For every run, record enough to rerun it exactly: the test name, the seed, the commit hash, the simulator and its version, and any options. A one-line CSV per run is plenty.

#!/usr/bin/env bash
# run_seeds.sh TEST N : run TEST with N fresh seeds, log one line per run
set -u
test=$1; n=$2
commit=$(git rev-parse --short HEAD)
mkdir -p logs
for i in $(seq 1 "$n"); do
  seed=$(od -An -N4 -tu4 /dev/urandom | tr -d ' ')
  log="logs/${test}_${seed}.log"
  if make COCOTB_TEST_FILTER="$test" COCOTB_RANDOM_SEED="$seed" \
       > "$log" 2>&1 && ! grep -q "FAIL=[1-9]" "$log"; then
    status=PASS
  else
    status=FAIL
  fi
  echo "$test,$seed,$commit,$status" >> logs/results.csv
done

The exact variable names depend on your cocotb version and Makefile; the point is that the seed goes in from outside and comes out in the log. A failure then becomes a one-line command for whoever picks it up.

Triage: group failures by signature

A night of random runs might produce dozens of failures, almost always from far fewer distinct causes. Reading them one by one wastes the morning. Group them by signature: the first error message with the variable parts (times, values, seeds) stripped out.

import re
from collections import defaultdict

def signature(log_text):
    for line in log_text.splitlines():
        if "Error" in line or "AssertionError" in line:
            line = re.sub(r"0x[0-9a-fA-F]+|\d+", "N", line)
            return line.strip()[:120]
    return "no error message (timeout or crash?)"

def triage(failing_logs):
    groups = defaultdict(list)
    for path in failing_logs:
        with open(path) as f:
            groups[signature(f.read())].append(path)
    for sig, paths in sorted(groups.items(), key=lambda kv: -len(kv[1])):
        print(f"{len(paths):4d}  {sig}")
        print(f"      e.g. {paths[0]}")

Each group then gets one owner and one verdict: a new design bug, a known bug already filed, or a testbench problem. Pick the shortest failing run in each group to debug; it is usually the easiest to read. Once fixed, turn the failing seed into a directed test or a fixed-seed entry in the smoke tier, so the fix stays fixed.

Flaky tests are bugs

In software, a flaky test often comes from network timing or thread scheduling outside the program's control. A digital simulation with a fixed seed, the same build and the same simulator should be completely deterministic. If the same seed passes on one run and fails on the next, something is wrong, and it is worth hunting down. Typical causes:

  • the testbench reads its seed from the clock or another source that changes between runs
  • tests share output files or directories and overwrite each other when run in parallel
  • a test depends on state left by a previous test in the same simulation
  • a race between testbench and design at a clock edge, resolved differently after an unrelated code change
  • uninitialised memory in a C model linked into the simulation

Never fix flakiness with automatic reruns. That hides the race until it becomes a real bug in a run nobody can reproduce.

Keeping the regression trusted

  • Green means green. If a known failure must stay in the regression, mark it as an expected failure with a bug reference, so new failures stand out and a surprise pass is noticed too.
  • Watch the run time. When the smoke tier creeps past a few minutes, people stop waiting for it. Move slow tests to nightly.
  • Publish results where people look, with the reproduction command beside each failure.
  • Track coverage over time from the nightly runs. A drop is often the first sign that a constraint changed and some stimulus stopped happening.
  • Pin your tool versions. A simulator or cocotb upgrade can change scheduling details or default options. Record the versions in the repository, upgrade them deliberately in their own change, and rerun the nightly tier before and after so any difference is traced to the upgrade rather than to the design.

Try it yourself

  1. Put a small design and a cocotb testbench in a Git repository, and write a make smoke target that runs Verilator lint plus your directed tests with fixed seeds.
  2. Adapt run_seeds.sh to your setup and run 50 seeds of a random test; check that a seed from the CSV reproduces its result exactly.
  3. Plant two different bugs, collect the failing logs, and confirm the triage script groups them into two signatures.
  4. Hook make smoke into whatever CI service your team uses, so it runs on every push.
