Five assertion patterns that catch real bugs early

Verification Intermediate 27 Nov 2026 5 min read By Ketuna

One-hot state, stable-until-accepted, no overflow, eventual response and no X on outputs. For each pattern, the SVA you write, the bug it catches and the mistake that makes it useless.

In this article
  1. 1. One-hot state
  2. 2. Stable until accepted
  3. 3. No overflow, no underflow
  4. 4. Eventual response
  5. 5. No X on outputs

Most assertions that find bugs in real projects are not clever. They are the same handful of patterns, written once per interface or state machine, placed close to the RTL and left running in every simulation and every formal job. Each pattern below encodes a rule that designers break by accident, and each catches the bug at the cycle it happens, not hundreds of cycles later when a corrupted value reaches an output. Learn these five well and you will have useful checks on almost any block you touch.

All the examples assume a property module with a default clock and reset:

default clocking cb @(posedge clk); endclocking
default disable iff (!rst_n);

1. One-hot state

Many state machines are encoded one-hot: one flip-flop per state, exactly one of them set. A one-hot machine with two bits set, or none, is in a state the designer never imagined, and its outputs are whatever the logic happens to produce.

a_state_onehot: assert property ($onehot(state));

What it catches: a missing default assignment in the next-state logic, a transition that sets the new state bit without clearing the old one, or a reset that does not reach every state flop.

Watch out for: encodings that legitimately allow all-zero (an idle state represented by no bit set). Use $onehot0 there, and write down in a comment why zero is allowed. For binary-encoded machines, the equivalent pattern is "state is one of the legal codes", written with inside.

2. Stable until accepted

In valid/ready style interfaces, the sender raises valid with a payload and must hold both unchanged until the receiver takes it with ready. A sender that drops valid or changes data while stalled loses or corrupts a beat, and the bug appears only under back-pressure.

a_valid_held:  assert property (valid && !ready |=> valid);
a_data_stable: assert property (valid && !ready |=> $stable(data));
c_backpressure: cover property (valid && !ready ##1 valid && ready);

What it catches: skid buffers and pipeline stages that overwrite their output register while the downstream is not ready. These are among the most common bugs in streaming designs, because a test with ready held high never exercises them.

Watch out for: the cover. If your testbench never deasserts ready, both assertions pass vacuously. The cover proves at least one stall happened.

3. No overflow, no underflow

Any storage with a count has two edges where things go wrong. Writing to a full FIFO or reading from an empty one either corrupts data or silently drops it, depending on the design.

// On the FIFO's own ports: the design must refuse illegal operations
a_full_holds:  assert property (wr_en && full && !rd_en |=> count == $past(count));
a_count_range: assert property (count <= DEPTH);

// On the producer side: the environment must never write when full
a_no_write_when_full: assert property (full |-> !wr_en);

What it catches: off-by-one full flags (asserting at DEPTH−1 or DEPTH+1), pointer comparisons that wrap incorrectly, and producers that ignore the flag.

Watch out for: which side owns the rule. If the spec says the FIFO ignores writes when full, the first assertion belongs to the FIFO. If the spec says the producer must never write when full, the third one belongs to the producer, and in a formal proof of the FIFO alone it becomes an assume. Writing the wrong one hides the real contract.

4. Eventual response

Requests must be answered. A request that is never acknowledged, a transaction that never completes, or an arbiter that starves one requester can hang a whole system, and a functional test will just time out without saying why.

// Bounded: a response within 16 cycles of each new request
a_resp_bounded: assert property ($rose(req) |-> ##[1:16] resp);

// Unbounded liveness, for formal tools that support it
a_resp_eventual: assert property (req |-> s_eventually resp);

What it catches: deadlocks, lost requests, and arbitration that never grants a low-priority requester.

Watch out for: two things. First, the bound must come from the spec or from a deliberate design decision, not from whatever the current RTL happens to achieve. A bound picked to make the assertion pass checks nothing. Second, an unbounded property can never fail in a finite simulation; it can only be left pending at the end. It is meaningful in formal, where the tool reasons about infinite traces, and also needs a fairness assumption that the environment eventually lets the design make progress.

5. No X on outputs

An X on an output means some state was never initialised, some signal was never driven, or some mux select was undefined. In RTL simulation, X values can be hidden by if and case statements that pick one branch, so the X disappears inside the block and only causes trouble on silicon.

a_valid_known: assert property (!$isunknown(valid));
a_data_known:  assert property (valid |-> !$isunknown(data));

What it catches: missing reset on control flops, undriven outputs after a refactor, and read data from uninitialised memory leaking out.

Watch out for: qualification. Data buses are often legitimately X when nothing valid is being sent, which is why the second assertion only checks data while valid is high. Control signals such as valid, ready and interrupt lines should never be X outside reset, so check them unconditionally.

Making the patterns stick

A few habits turn these from good intentions into checks that run every day.

  • Put them in a separate module and bind it to the design. The RTL stays clean, and the same property module attaches to every instance.
  • Name each assertion after the rule it checks, and refer to the spec section in a comment. A failure called a_data_stable tells the reader exactly what went wrong.
  • Pair every important assertion with a cover. A pattern whose antecedent never fires is decoration.
  • Run them in both simulation and formal. The same text checks your tests' traffic in simulation and all possible traffic in a formal tool.

Try it yourself

  1. Write a two-entry skid buffer with valid/ready on both sides and bind patterns 2 and 5 to its input and output ports.
  2. Drive it from a cocotb testbench on Verilator with --assert, first with ready always high, then with random back-pressure; check that the cover only hits in the second run.
  3. Introduce a bug where the output register loads while ready is low, and confirm a_data_stable fires on the first stalled cycle.
  4. Write a SymbiYosys job for the same buffer and see whether the formal tool finds the bug in fewer cycles than your random test needed.
