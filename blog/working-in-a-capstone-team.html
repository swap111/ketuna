Working in a capstone team: roles, milestones and disagreements

Careers & skills Intermediate 27 Nov 2026 6 min read By Ketuna

How a small capstone team avoids the usual failures: agree interfaces and owners in week one, track milestones by what is tested, and settle technical disagreements with data instead of volume.

In this article
  1. Agree interfaces before anyone writes code
  2. Give every deliverable an owner
  3. Track milestones by what is tested
  4. Settle disagreements with data
  5. Common mistakes
  6. Try it yourself

A capstone project is usually the first time you build something with three or four other people against a fixed date. The technical work is rarely what goes wrong. Teams fail because two blocks do not fit together, because nobody owned the integration, because "almost done" meant different things to different people, or because a design argument dragged on for a week. Each of these has a known remedy, and most of them have to be applied in the first week.

Agree interfaces before anyone writes code

Suppose a team is building a small sensor node: an RTL block that filters samples, a bus interface, firmware on a RISC-V core and a host script that plots the data. Four people can work in parallel only if the boundaries between their parts are fixed early. Those boundaries are the interfaces: signal names and widths, clock and reset, register addresses and bit fields, packet formats, function signatures.

Write them down in a short interface document before the first line of RTL. For each boundary, record:

Item Example
Signals or fields sample_valid, sample_data[15:0], signed, two's complement
Timing and handshake Valid for one cycle; no backpressure; one sample per 1,000 clocks at most
Clock and reset clk 50 MHz, active-low synchronous reset rst_n
Registers 0x00 CTRL (bit 0 enable), 0x04 STATUS (bit 0 overflow, write 1 to clear)
Owner The person who decides changes to this interface

The last row matters most. Every interface needs one owner, and any change goes through them with a note to everyone affected. Without that rule, someone widens a bus "just for now", the firmware still reads the old width, and the bug surfaces at integration two days before the demo.

It is also worth building a skeleton in week one: every block present as a stub that obeys the interface, connected end to end, so a trivial value flows from sensor model to host plot. The skeleton finds mismatched assumptions while they are cheap to fix.

Give every deliverable an owner

Roles in a small team are about ownership, not hierarchy. Each block, the test plan, integration, the build and CI setup, and the final report each need one named person who is responsible for it being finished. Others can help; one person answers for it.

Two roles are often forgotten:

  • Integration owner: keeps the top level building, runs the full regression, and is the first to notice when parts stop fitting
  • Documentation owner: keeps the README, interface document and decisions log current, rather than leaving them for the last night

Ownership does not mean working alone. Pair on difficult pieces, and make sure at least two people understand each block, so an illness or an exam does not stop the project.

Track milestones by what is tested

Capstones have fixed dates: a design review, a mid-point demo, the final presentation. Plan backwards from them into milestones, and define each milestone by evidence, not effort.

M1  end of week 2   Skeleton runs end to end in simulation;
                    interface doc v1.0 reviewed
M2  end of week 4   Filter block passes its scoreboard test
                    with random stimulus; firmware reads
                    STATUS over the bus in simulation
M3  end of week 6   Full system on FPGA; host plots live data;
                    regression runs in CI on every push
M4  end of week 7   Demo rehearsed twice; known limits written

A milestone is met when its evidence exists, such as a passing test, a CI run or a reviewed document, not when someone says it is "mostly working". Agree a team definition of done for any task: code written, tested, reviewed by one teammate, merged, and documented where needed.

Identify the critical path: the chain of tasks where any slip moves the final date. In the example, integration on the FPGA depends on the filter, the bus and the firmware all being ready, so those dependencies need the earliest attention. Work off the critical path, such as plotting polish, has slack and can wait.

Check progress weekly in a short meeting: what is done, with evidence; what is next; what is blocked. If a milestone is going to slip, say so in that meeting and cut scope there, while there are still options. Moving stretch goals out in week 4 is a decision; discovering in week 7 that they never happened is a failure.

Settle disagreements with data

Technical disagreements are normal and often useful: should the filter be fixed-point or use a small multiplier, should the firmware poll or use interrupts, should you buy time by dropping a feature or by working weekends. They turn harmful when they are decided by whoever argues longest.

A simple process keeps them productive:

  1. State the question precisely, including what "better" means: latency, area, effort, risk.
  2. List the options and what each would cost.
  3. Agree what evidence would decide it, before collecting it: a quick synthesis run for area, a ten-line simulation for latency, an hour-long spike to test feasibility.
  4. Time-box it. If the evidence is not conclusive by the deadline, the owner of that block decides, and the reason goes in the decisions log.
  5. Commit together. Once decided, everyone supports the choice; reopen it only if new evidence appears.

This separates the idea from the person. Nobody loses face when a measurement decides, and the decisions log means the same argument does not restart a week later.

Common mistakes

  • Starting to code before interfaces are agreed. Integration week becomes rewrite week.
  • No integration owner. Everyone assumes someone else is running the full system.
  • Milestones defined by effort. "Worked on firmware" says nothing about whether it works.
  • Silently uneven workload. Raise it early and rebalance; resentment in week 6 is harder to fix.
  • Hiding a slip. The team can only re-plan around problems it knows about.

Try it yourself

  1. For your next team project, write a one-page interface document with an owner per interface before any code exists, and review it together.
  2. Build the end-to-end skeleton in the first week: stub modules in Verilog simulated with Icarus Verilog or Verilator, or stub firmware running on QEMU.
  3. Write your milestones in the evidence-based form above, and set up a CI job, for example with a make target that runs your tests, so "done" can be checked automatically.
  4. Next time the team disagrees, run the five-step process, and record the decision and its evidence in a DECISIONS.md file in the repository.
