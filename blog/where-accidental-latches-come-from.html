Where accidental latches come from, and how to read the synthesis warning

Digital & VLSI design Beginner 27 Nov 2026 5 min read By Ketuna

A combinational block that does not assign every output on every path makes synthesis infer a latch. Learn to spot the cause, read the warning, and prevent it with defaults and always_comb.

In this article

  2. The usual suspects
  3. Why it matters even when simulation passes

You write what you believe is a simple multiplexer, run synthesis, and the log says something like "latch inferred for signal y". The design may even simulate correctly. The warning is still almost always a bug, and it comes from one specific habit that is easy to fix once you understand what the tool is reasoning about.

What the tool is telling you

A combinational block describes logic whose outputs depend only on its present inputs. An always @* block in Verilog, or always_comb in SystemVerilog, is how you describe that logic in procedural code.

Now suppose some path through the block does not assign an output. What should the output be on that path? Verilog's answer is: it keeps whatever value it had before. A variable that "keeps its value" when not assigned is, by definition, storage. Since the block has no clock, the storage the tool builds is a level-sensitive latch, transparent while the assigning condition is true and holding when it is false.

So the warning is the tool saying: "your description requires memory here, and I built it." It did exactly what the code said. The bug is that the code said something you did not mean.

The usual suspects

An if without an else:

always @* begin
  if (sel)
    y = a;      // when sel is 0, y is not assigned
end

When sel is 0, y must hold its old value. The tool builds a latch on y enabled by sel.

A case that does not cover every value:

always @* begin
  case (op)            // op is 2 bits: four possible values
    2'b00: y = a + b;
    2'b01: y = a - b;
    2'b10: y = a & b;
  endcase              // 2'b11 leaves y unassigned
end

An output assigned in some branches but not others:

always @* begin
  case (state)
    IDLE: begin busy = 1'b0; done = 1'b0; end
    RUN:  begin busy = 1'b1;              end  // done missing
    FIN:  begin busy = 1'b0; done = 1'b1; end
    default: begin busy = 1'b0; done = 1'b0; end
  endcase
end

The third one is the most common in real designs. The case is complete and has a default, so it looks safe, but done is not assigned in the RUN branch. Each output is checked separately. Covering every case value is not enough; you must cover every output in every branch.

Why it matters even when simulation passes

A latch in the middle of a synchronous design causes three kinds of trouble:

  • Timing. Static timing analysis handles latches through a mechanism called time borrowing, which is harder to constrain and review. An accidental latch is not designed for this, so its timing is whatever the tools happen to produce.
  • Glitches. The latch is transparent while its enable is high. If the enable is itself a decoded combinational signal, a glitch on it can open the latch briefly and capture a wrong value.
  • Simulation mismatch. If the sensitivity list or the coding style differs slightly from what synthesis assumes, the RTL simulation and the gate-level netlist can behave differently, and your tests no longer describe the chip.

There are designs that use latches on purpose, such as some clock gating cells and some high-speed pipelines. Those are deliberate, reviewed and usually instantiated as library cells, not inferred from a missing else.

Two habits that prevent it

Assign defaults at the top of the block. Give every output a value on the first lines, then override it where needed. Every path now assigns every output, because the defaults run on every path.

always_comb begin
  busy = 1'b0;          // defaults first
  done = 1'b0;
  case (state)
    RUN: busy = 1'b1;
    FIN: done = 1'b1;
    default: ;          // defaults already cover IDLE and others
  endcase
end

This style is shorter, and adding a new output later cannot create a latch as long as you add its default line.

Use always_comb instead of always @*. In SystemVerilog, always_comb states your intent: this block is combinational. Tools are expected to warn when the code inside implies storage, and simulators evaluate it once at time zero so outputs start defined. It also builds its own sensitivity list, so you cannot forget an input. Where you do want a latch, always_latch documents that intent instead.

For case statements, a default branch covers values you did not list, including X and Z in simulation. In SystemVerilog, unique case additionally asks tools to check that the listed items do not overlap and that one always matches.

Reading the warning

Synthesis logs differ between tools, but a latch warning usually names three things: the signal, the source file and line of the always block, and sometimes the enable condition. To fix it:

  1. Go to the block and list every output it assigns.
  2. For each output, trace every path through the if and case structure and check it is assigned on all of them.
  3. Add defaults at the top rather than patching the one missing branch, so the next edit cannot reintroduce the problem.
  4. Re-run synthesis and confirm the warning is gone and the cell report contains no latch cells.

Do not silence the warning with a tool option. If a latch is truly intended, write it with always_latch and get it reviewed.

Try it yourself

  1. Save the three "usual suspects" in a file and run Yosys with yosys -p "read_verilog -sv bad.v; proc; stat". Look for $dlatch cells in the statistics and the messages printed by the proc step.
  2. Run verilator --lint-only -Wall bad.v and compare its messages with the Yosys output.
  3. Rewrite each block with defaults and always_comb, rerun both tools and confirm the latch cells are gone. Draw the intended mux on paper first, then check that the netlist matches it.
