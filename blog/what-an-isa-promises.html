What an instruction set promises, and what it leaves to the hardware

Computer architecture & RISC-V Beginner 27 Nov 2026 6 min read By Ketuna

An instruction set is a contract. Learn exactly what it guarantees to software, what it deliberately leaves open, and why that freedom lets one binary run on very different cores.

A compiled program for a small RISC-V microcontroller core can also run, unchanged, on a much larger RISC-V core with a deep pipeline and caches. The two chips share almost no circuits, yet both produce the same answer. That works because both honour the same contract: the instruction set architecture, or ISA. Knowing what the contract says, and what it does not say, tells a hardware engineer which parts of a design are free to change and which must never move.

The contract in one sentence

The ISA defines the architectural state of the machine and how each instruction changes it. Architectural state is everything software can observe: the program counter (PC), the integer registers, memory, and the control and status registers (CSRs). An instruction such as add x3, x1, x2 is defined purely as a state change: read x1 and x2, write their sum into x3, and advance the PC by 4.

Notice what is missing from that definition. It says nothing about how many clock cycles the add takes, which adder circuit does the work, or whether the result sits in a pipeline register for a while before reaching the register file. Those choices belong to the microarchitecture, the particular way one chip implements the ISA.

The sequential illusion

The strongest promise is this: the result must look as if instructions ran one at a time, in program order, each finishing before the next begins. A pipelined core overlaps five instructions; an out-of-order core may execute a later instruction before an earlier one. Both are allowed, as long as software can never tell.

This is why pipelines need forwarding and stall logic. If add x3, x1, x2 is followed by sub x5, x3, x4, the subtract must see the new x3 even though the add has not reached the register file yet. The hazard logic exists only to keep the sequential promise.

The same promise covers traps. When an instruction faults, for example a load from a misaligned address on a core that does not support it, the ISA requires a precise trap: every older instruction has completed, the faulting one and every younger one have had no effect, and a CSR (mepc in RISC-V machine mode) records exactly which instruction faulted. A core that speculatively ran three younger instructions must throw their results away before the handler starts.

A worked example: one loop, two cores

Take a short loop that sums an array of 100 words. The compiler produces the same five instructions per iteration whichever core you buy:

loop: lw   t1, 0(a0)      # load a word
      add  t0, t0, t1     # accumulate
      addi a0, a0, 4      # next address
      addi a1, a1, -1     # count down
      bnez a1, loop       # repeat while count != 0

That is 500 instructions for the loop body. Now compare two imaginary cores (numbers made up for illustration):

Core A: multi-cycle Core B: 5-stage pipeline
Clock 50 MHz (20 ns) 200 MHz (5 ns)
Average cycles per instruction 4.0 1.3
Time for 500 instructions 500 × 4.0 × 20 ns = 40 µs 500 × 1.3 × 5 ns = 3.25 µs

The architectural result is identical: the same sum in t0, the same final values of a0 and a1, the same memory contents. Only the time differs, and time is not part of the contract. That is precisely the freedom that lets one core be tiny and another fast.

The freedom the ISA leaves on purpose

Good ISAs leave more open than you might expect, because every guarantee costs hardware somewhere. RISC-V is a useful example because its specification is open and explicit about these choices.

  • Optional extensions. The base integer set (RV32I) is small. Multiply and divide (M), atomics (A), compressed 16-bit instructions (C) and floating point (F, D) are optional. A core declares what it implements, and the toolchain is told the same through the -march option.
  • Misaligned accesses. A core may handle a word load from an odd address in hardware, or it may trap and let software emulate it. Both are legal. Software that wants to be portable avoids misaligned accesses.
  • Fields with legal-value rules. Many CSR fields are specified as "write any value, read back a legal one". A core that supports only one interrupt-vector mode can hard-wire the mode bits, and software discovers this by writing and reading back.
  • Timing. The ISA never promises how long anything takes. Code that relies on a delay loop taking a fixed time is relying on the microarchitecture, not the contract, and will break on the next core.
  • Memory ordering. RISC-V uses a relaxed memory model. A core may let a later load overtake an earlier store to a different address, so software that needs ordering (for device registers or for other cores) must ask for it with a fence instruction.

Why the line matters to engineers

For a hardware designer, the contract is a licence: change anything below the line, as long as the architectural behaviour is unchanged. Adding a cache, deepening a pipeline or replacing a slow divider are all invisible to software if done correctly.

For a verification engineer, the contract is the reference. A common technique is to run the same program on the RTL and on an instruction set simulator, and compare the architectural state after every retired instruction. Cycle counts are expected to differ; register and memory values are not.

For a firmware engineer, the contract says what is portable. Code written to the ISA and its standard calling convention (the ABI, which says which register holds arguments, return address and stack pointer) moves between cores. Code that depends on cycle counts or undocumented behaviour does not.

Common mistakes

  • Treating a particular core's timing as part of the ISA. Cycle-counted delays work on one chip and fail on the next.
  • Confusing ISA and ABI. The ISA says x1 is a register; the ABI says it holds the return address. Hand-written assembly must follow both.
  • Assuming every extension is present. Code built for RV32IMC raises illegal-instruction traps on an RV32I core.
  • Leaking microarchitecture into behaviour. If a design returns a different result depending on pipeline state, it has broken the contract, even if the test suite happened to pass.

Try it yourself

  1. Install a RISC-V GCC cross-compiler and compile a small C function twice, with -march=rv32i -mabi=ilp32 and with -march=rv32imc -mabi=ilp32, adding -S to see the assembly. Note which instructions change and why.
  2. Run the binary on an instruction set simulator such as Spike or QEMU (qemu-riscv32 in user mode) and confirm the result.
  3. If you have a small open-source RV32I core in Verilog, run the same program in Icarus Verilog or Verilator and compare the final register values with the simulator. Count cycles in both and notice that only the time differs.
