Associativity, replacement and write policies: cache design choices compared

Computer architecture & RISC-V Intermediate 27 Nov 2026 6 min read By Ketuna

Set associativity removes conflict misses, replacement picks a victim, and the write policy decides when memory is updated. Compare each choice with its hardware cost, including a pseudo-LRU tree worked by hand.

In this article
  1. Associativity: more than one place per line
  2. Replacement: choosing the victim
  3. Write policies: when memory sees the store
  4. Common mistakes
  5. Try it yourself

A direct-mapped cache is simple and fast, but two busy addresses that share an index evict each other on every access, even when the rest of the cache sits empty. Real cache designs answer three questions beyond capacity and line size: how many places may a line go (associativity), which line leaves when a set is full (replacement), and when does a store reach the next level of memory (write policy). Each answer buys hit rate or bandwidth with area, power or timing. This article compares them with the hardware cost in view.

Associativity: more than one place per line

In an N-way set-associative cache, the index selects a set of N lines, and an incoming line may go into any of them. A lookup reads all N tags of the set at once and compares them in parallel; if one matches and is valid, it is a hit and a multiplexer selects that way's data.

Associativity attacks conflict misses. Two arrays whose addresses differ by a multiple of the cache size collide in a direct-mapped cache, but in a 2-way cache both lines fit in the same set.

The cost is real, and you can count it. Take a 4 KiB cache with 32-byte lines and 32-bit addresses. There are 4096 / 32 = 128 lines and the offset is 5 bits.

Direct-mapped 4-way set-associative
Sets 128 32
Index bits 7 5
Tag bits per line 32 − 7 − 5 = 20 32 − 5 − 5 = 22
Total tag storage 128 × 20 = 2560 bits 128 × 22 = 2816 bits
Tag comparators 1 4
Data path after compare none 4-to-1 way multiplexer

Fewer sets mean fewer index bits, so every tag grows. More importantly for timing, the way multiplexer sits after the tag compare, on the hit path. That is why level-1 caches, which must answer in a cycle or two, tend to have modest associativity, while larger and slower caches further out can afford more ways. A fully associative cache, one set containing every line, removes conflict misses entirely but needs a comparator per line, so it is used only for small structures such as TLBs.

Replacement: choosing the victim

When a set is full and a new line arrives, one way must be evicted. A direct-mapped cache has no choice to make. With N ways there are several policies:

  • Least recently used (LRU). Evict the way not touched for longest. It matches temporal locality well. Exact LRU for 4 ways must remember an ordering of 4 items, and there are 4! = 24 orderings, so at least 5 bits per set, plus update logic that rewrites the order on every hit.
  • Pseudo-LRU (tree PLRU). Approximate LRU with a binary tree of N − 1 bits per set: 3 bits for 4 ways. Each bit points toward the half that was used less recently.
  • Random. A free-running counter or LFSR picks the way. No per-set state at all, and surprisingly competitive for higher associativity, but harder to reason about when you need predictable timing.
  • FIFO / round-robin. Evict in order of arrival; one small counter per set.

Work it by hand. Start with all bits 0. Access ways 0, 1, 2, 3 in turn; each access sets the bits along its path to point to the other side. After way 3, the bits are b0 = 0, b1 = 0, b2 = 0, so the victim is way 0, which agrees with true LRU. Now access way 0 again: b0 becomes 1 and b1 becomes 1. The tree now points to the right pair and then, by b2 = 0, to way 2. True LRU would evict way 1, which has not been used since the start of the sequence. PLRU forgot that ordering because the left subtree's history was overwritten. That is the approximation you accept for 3 bits instead of 5 and much simpler update logic.

Write policies: when memory sees the store

A store that hits in the cache updates the cached line. The question is what happens to the next level.

  • Write-through. Every store is also sent to the next level, usually via a small write buffer so the core need not wait. The next level is always up to date, which simplifies coherence with DMA and other masters. The cost is traffic: every store becomes a bus write.
  • Write-back. The store updates only the cache and sets a dirty bit. The line is written to the next level only when it is evicted. Repeated stores to the same line cost one write-back at the end.

Consider a loop that increments a counter in memory 1000 times. With write-through, 1000 writes cross the bus. With write-back, the line stays dirty in the cache and costs one 32-byte write when it is eventually evicted. The price of write-back is a dirty bit per line, eviction logic that must write a line out before refilling, and the fact that memory can be stale, which matters to any other master reading it.

A second choice applies to store misses: write-allocate fetches the line into the cache and then updates it; no-write-allocate sends the store straight to the next level and leaves the cache alone. Write-back caches usually allocate; write-through caches often do not.

Common mistakes

  • Counting only data storage. Tags, valid, dirty and replacement bits add a significant fraction of the area of a small cache.
  • Putting a slow way multiplexer on a one-cycle hit path. Check timing before adding ways.
  • Choosing write-back without planning for DMA. Stale memory needs either hardware coherence or software clean and invalidate operations.
  • Assuming PLRU equals LRU. It agrees often, but not always, as the example shows.

Try it yourself

  1. Extend a Python cache model with an associativity parameter and LRU, PLRU and random replacement, and replay the same address trace through each.
  2. Count bus writes in the model for write-through and write-back while replaying a trace with repeated stores.
  3. Write a 4-way tag array with PLRU in Verilog, simulate it in Verilator against the Python model, and compare its area to a direct-mapped version with Yosys stat.
