Making decisions on a soil sensor node: thresholds, rules or a model?

Edge AI Beginner 27 Nov 2026 5 min read By Ketuna

Start a sensor node's decision logic with a threshold and hysteresis, add readable rules as needs appear, and bring in a model only when logged data shows the simple logic failing, using a soil moisture node.

In this article
  1. Step 1: a threshold
  2. Step 2: hysteresis
  3. Step 3: a few readable rules
  4. Step 4: a model, if the data says so
  5. Try it yourself

A soil sensor node in a field has a simple job: measure moisture and decide whether to open a valve, raise an alert or just report. It is tempting to put machine learning on it from the start, because "smart irrigation" sounds like a model. But every layer of cleverness costs battery, flash, testing effort and, most importantly, explainability to the farmer who has to trust it. The better path is to begin with the simplest logic that could work, find out from real data where it fails, and add complexity only to fix those specific failures.

Step 1: a threshold

The simplest decision is a threshold: if soil moisture falls below a set point, irrigate. The node reads its capacitive moisture sensor, converts the raw reading to a moisture value using a calibration for that soil (measured once, in dry and saturated soil), and compares.

This already captures most of the value. It is a few lines of code, uses almost no energy, and anyone can understand and adjust it: "the valve opens when moisture drops below 25 %." The numbers here and below are illustrative; the right values depend on the soil and the crop, and come from the agronomist or the farmer's experience.

A single threshold has one flaw, which shows up on the first day: chatter. Near the set point, sensor noise makes the reading cross back and forth, and the valve opens and closes repeatedly, wearing it out and wasting the battery.

Step 2: hysteresis

The fix is hysteresis: two thresholds instead of one. Start irrigating when moisture falls below the lower one; stop only when it rises above the upper one. Between them, keep doing whatever you were doing.

As long as the gap between the thresholds is larger than the sensor noise, the valve switches once per cycle. It is the same idea as a thermostat, and it remains the core of the node's logic in every later step.

Step 3: a few readable rules

Once the node is in the field and its decisions are logged, specific problems appear, and each can be fixed by a rule that a person can read:

  • It rained, but the node irrigated anyway, because the sensor responds a little later than the rain arrives. Rule: if a rain gauge (or a sudden rise in moisture) shows rain in the last few hours, wait.
  • It irrigated at midday, losing water to evaporation. Rule: if irrigation is needed between late morning and afternoon and moisture is not critically low, defer to the evening.
  • A broken sensor read zero and opened the valve indefinitely. Rule: if the reading is outside the physically possible range, or has not changed at all for a day, stop and raise a sensor-fault alert. A maximum valve-open time guards against any failure.
#include <stdbool.h>
#include <stdint.h>

#define START_BELOW   25.0f   /* % moisture, illustrative */
#define STOP_ABOVE    32.0f
#define CRITICAL      15.0f
#define MAX_OPEN_MIN  60

typedef struct {
    bool valve_on;
    bool fault;               /* latched until a person clears it */
    uint16_t open_min;        /* minutes the valve has been open */
} ctrl_t;

/* Called every minute with a calibrated moisture reading. */
bool decide(ctrl_t *c, float moisture, bool sensor_ok,
            bool rained_recently, bool midday)
{
    if (!sensor_ok || c->open_min >= MAX_OPEN_MIN)
        c->fault = true;                     /* raise an alert */
    if (c->fault) {
        c->valve_on = false;                 /* fail safe: close */
    } else if (c->valve_on) {
        if (moisture > STOP_ABOVE)
            c->valve_on = false;             /* upper threshold */
    } else if (moisture < START_BELOW && !rained_recently &&
               (!midday || moisture < CRITICAL)) {
        c->valve_on = true;                  /* lower threshold */
    }
    c->open_min = c->valve_on ? c->open_min + 1 : 0;
    return c->valve_on;
}

The fault flag is latched on purpose: after a sensor failure or an over-long irrigation, the node keeps the valve closed until someone has looked, rather than reopening on the next reading. Each rule is one condition with a reason, and every decision can be explained in a sentence: "did not irrigate because it rained two hours ago." That explanation is what lets a farmer trust the node, or correct it.

Step 4: a model, if the data says so

A model becomes worth considering when the logs show a pattern the rules cannot capture well, and when you have the data to learn it. For example:

  • the best irrigation time depends on how fast each field dries, which varies with soil, crop stage and weather in a way that is hard to write as rules, and you have months of moisture logs to learn drying rates from
  • several sensors at different depths interact, and hand-written rules for every combination become unmanageable

Even then, the model often does not replace the logic; it feeds it. A small regression model might predict moisture six hours ahead, and the existing hysteresis rule acts on the prediction instead of the current reading. The fail-safe rules stay exactly as they are, outside the model, because a model should never be the only thing standing between a fault and an empty water tank.

To justify the step, compare against the simple logic on the same logged data: how much water would each have used, and how often would moisture have dropped below the critical level? If the model does not clearly win on numbers that matter to the farmer, keep the rules.

Common mistakes:

  • starting with a model before logging what the simple logic does
  • a single threshold without hysteresis, so actuators chatter
  • no limit on valve-open time or check for impossible sensor readings
  • thresholds copied from elsewhere instead of calibrated for the soil
  • letting a model override safety rules

Try it yourself

  1. Simulate the node in Python: moisture falls by a small amount per step, rises while the valve is on, plus random noise. Compare a single threshold with hysteresis and count valve switches.
  2. Add a rain event to the simulation and implement the rain rule.
  3. Port decide() to a microcontroller with a capacitive soil sensor, log every decision with its reason over a week, and review the log.
  4. From the logs, fit a simple drying-rate model per day with numpy.polyfit and check whether predicting ahead would have changed any decisions.
