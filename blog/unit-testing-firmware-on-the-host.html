Unit testing firmware on your laptop: separating logic from hardware

Embedded systems Intermediate 27 Nov 2026 5 min read By Ketuna

Most firmware bugs are in ordinary logic, not in register writes. Split the two, swap registers for a fake array on the host, and a plain gcc build can test your code in seconds with sanitizers switched on.

Testing firmware on the board is slow: build, flash, reset, poke at buttons, read a serial log. So it gets done rarely, and mostly for the happy path. Yet when you look at the bugs that reach the field, most are not in the register writes. They are in plain logic: a parser that mishandles an empty line, an off-by-one in a buffer, a percentage that overflows at full scale. That logic does not need the board at all. Separate it from the hardware, and your laptop can run hundreds of tests in the time it takes to flash once.

Two kinds of code in every driver

Look at almost any firmware function and you find two things mixed together:

  • Decisions and arithmetic: parsing, clamping, scaling, state machines, checksums, timeouts. These are pure C. Given the same inputs they produce the same outputs.
  • Hardware access: reading and writing registers, waiting for flags. This is the part that needs the chip.

The design rule is to keep the second kind as thin as possible: functions that only move values between registers and the logic, making no decisions of their own. Then the logic can be compiled and tested anywhere, and the thin layer is simple enough to check by review and a short test on the board.

A worked example

Here is an LED brightness function for a PWM peripheral, split in two. The register addresses are made up for illustration:

/* reg.h */
#include <stdint.h>
#define PWM_BASE    0x40001000u
#define PWM_ARR     (PWM_BASE + 0x00u)
#define PWM_CCR     (PWM_BASE + 0x04u)
#define PWM_CTRL    (PWM_BASE + 0x08u)
#define PWM_CTRL_EN (1u << 0)

#ifdef HOST_TEST
extern uint32_t fake_pwm[4];
#define REG32(a) (fake_pwm[((a) - PWM_BASE) / 4u])
#else
#define REG32(a) (*(volatile uint32_t *)(uintptr_t)(a))
#endif

/* led.c */
#include "reg.h"

/* Logic: percent (0..100) to a compare value for a period. */
uint32_t duty_to_ccr(uint32_t percent, uint32_t period)
{
    if (percent > 100u)
        percent = 100u;
    return (uint32_t)(((uint64_t)percent * period + 50u) / 100u);
}

/* Thin hardware layer: no decisions, just register traffic. */
void led_set_brightness(uint32_t percent)
{
    uint32_t period = REG32(PWM_ARR) + 1u;
    REG32(PWM_CCR) = duty_to_ccr(percent, period);
    REG32(PWM_CTRL) |= PWM_CTRL_EN;
}

On the target, REG32 is the usual volatile pointer to a fixed address. When the file is compiled with -DHOST_TEST, REG32 becomes an element of an ordinary array. The production source is identical in both builds; only one macro changes. That array is a fake: a stand-in for the hardware that the test can preload and inspect.

The tests

You do not need a framework to start. A ten-line check macro is enough, and open-source frameworks such as Unity add reporting and fixtures when the suite grows.

/* test_led.c */
#include <stdio.h>
#include <stdint.h>
#include "reg.h"

uint32_t duty_to_ccr(uint32_t percent, uint32_t period);
void led_set_brightness(uint32_t percent);

uint32_t fake_pwm[4];
static int failures;

#define CHECK_EQ(got, want) do {                                  \
    unsigned long g_ = (got), w_ = (want);                        \
    if (g_ != w_) {                                               \
        printf("%s:%d: %s = %lu, want %lu\n",                    \
               __FILE__, __LINE__, #got, g_, w_);                 \
        failures++;                                               \
    } } while (0)

static void test_duty_edges(void)
{
    CHECK_EQ(duty_to_ccr(0, 2400), 0);
    CHECK_EQ(duty_to_ccr(100, 2400), 2400);
    CHECK_EQ(duty_to_ccr(150, 2400), 2400);           /* clamped  */
    CHECK_EQ(duty_to_ccr(33, 1000), 330);
    CHECK_EQ(duty_to_ccr(50, 0xFFFFFFFFu), 2147483648u); /* no wrap */
}

static void test_led_writes_registers(void)
{
    fake_pwm[0] = 999;           /* ARR: 1000 counts per period */
    fake_pwm[2] = 0x10;          /* an unrelated CTRL bit is set */
    led_set_brightness(25);
    CHECK_EQ(fake_pwm[1], 250);  /* CCR */
    CHECK_EQ(fake_pwm[2], 0x11); /* EN set, other bit kept */
}

int main(void)
{
    test_duty_edges();
    test_led_writes_registers();
    printf("%s\n", failures ? "FAIL" : "PASS");
    return failures != 0;
}

Build and run it with the host compiler:

gcc -DHOST_TEST -Wall -Wextra -g -fsanitize=address,undefined \
    led.c test_led.c -o test_led && ./test_led

Each test targets a case that is tedious on hardware: full scale, out of range, a period so large that percent * period would overflow 32 bits (the reason for the 64-bit multiply), and a check that the read-modify-write on CTRL preserves bits it does not own. A version of duty_to_ccr that multiplies in 32 bits passes every other case and fails that one.

Fakes, stubs and mocks

The array behind REG32 is one kind of test double, and it helps to know the others, because each answers a different question:

  • A stub returns fixed answers and records nothing. Use it when the code under test only needs something back, such as a status register that always reads "ready".
  • A fake behaves like a simplified version of the real thing, like the register array above, or a flash driver backed by a byte buffer. Use it when the test checks the end state.
  • A mock records every call or access in order and lets the test check the sequence: "wrote the divisor, then enabled the FIFO, then set the line control register". Use it when the order of register accesses is itself the requirement, as it often is in a peripheral's initialisation sequence.

Start with fakes; they keep tests short and readable. Reach for a mock when a datasheet says "write A before B" and you want a test that fails if someone reorders the code.

Why the host build finds extra bugs

Running on a laptop is not just faster. It gives you tools the microcontroller lacks:

  • Sanitizers. -fsanitize=address reports out-of-bounds reads and writes and use of freed memory; -fsanitize=undefined reports signed overflow, bad shifts and misaligned access. On the target, the same bugs silently corrupt memory.
  • Coverage. Compile with --coverage and run gcov to see which branches your tests never reached.
  • Debuggers and printing without any effect on real-time behaviour.

What host tests cannot tell you

Be honest about the limits:

  • Type sizes and alignment can differ. On a 64-bit laptop, long is 64 bits; on a 32-bit microcontroller it is 32. Use stdint.h types everywhere so the logic means the same thing on both.
  • Timing, interrupts and real peripherals are not exercised. A fake register does not raise flags by itself, enforce write-1-to-clear behaviour, or delay. Those need emulator tests and some testing on hardware.
  • Compiler differences. Build the same sources with the cross-compiler too, with warnings on, so nothing compiles only on the host.

The practical split is a large number of host unit tests for logic, a smaller number of emulator tests for integration, and a few hardware tests for timing and electrical behaviour.

Try it yourself

  1. Compile the example above, then break duty_to_ccr by removing the 64-bit cast and watch the overflow test fail.
  2. Take one function from your own firmware that mixes logic and register access, split it as shown, and write tests for its edge cases.
  3. Lab D8 in the Ketuna track D labs runs host tests with register mocks against a seeded set of driver bugs, and uses mutation testing to check that the tests notice deliberate changes to the code. Run it and see which seeded bug your first tests miss.
