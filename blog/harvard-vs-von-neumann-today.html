Harvard vs von Neumann in microcontrollers today

Computer architecture & RISC-V Beginner 27 Nov 2026 6 min read By Ketuna

Textbooks present Harvard and von Neumann as rivals. Real microcontrollers use separate instruction and data paths for speed and one shared address space for flexibility. Here is why both ideas survive.

Most architecture courses introduce two machine organisations. In a von Neumann machine, instructions and data live in one memory reached by one path. In a Harvard machine, they live in separate memories with separate paths. Exam questions then ask which is better. Real microcontrollers answer "both": nearly every modern core mixes the two ideas, and understanding why explains a lot about how chips are built and how firmware behaves.

The two pure models

In a pure von Neumann organisation, a program is just data that the processor happens to execute. One memory, one bus. This is flexible: the same memory can hold any mix of code and data, a program can load another program and run it, and the address space is simple. The cost is a bottleneck. Every instruction must be fetched over the same bus that loads and stores use, so an instruction that accesses memory competes with the fetch of the next instruction.

In a pure Harvard organisation, instruction memory and data memory are physically separate, with separate buses, and often separate address spaces. The processor can fetch an instruction and access data in the same cycle, so the bottleneck disappears. The cost is rigidity: data cannot easily be read from instruction memory, code cannot be loaded into data memory and run, and each memory must be sized for the worst case of its own kind.

Putting a number on the bottleneck

Take a short loop of five instructions, one of which is a load, on a simple core that can do one memory access per cycle. Ignore everything else for a moment.

  • With one shared memory port, each iteration needs five instruction fetches plus one data access: six memory accesses, so at least six cycles.
  • With separate instruction and data ports, the load's data access happens in the same cycle as a fetch, so the iteration can complete in five cycles.

That is a 20% difference on this loop, and it grows with the fraction of loads and stores. In a pipelined core the conflict is worse: a load in the memory stage and a fetch in the fetch stage want the bus in the same cycle every time, which is called a structural hazard. That is why a classic five-stage pipeline, and even a simple single-cycle teaching core, is drawn with separate instruction and data memories.

What real microcontrollers do

Modern microcontroller cores take Harvard's separate paths and von Neumann's single address space at the same time. This is usually called a modified Harvard architecture.

  • Separate buses at the core. The core has an instruction port and a data port, sometimes a third for peripherals. Fetches and loads proceed in parallel. On larger cores, the same split appears as separate level-1 instruction and data caches.
  • One address space behind them. Flash, SRAM and peripherals all have addresses in the same memory map. Both buses can reach most regions through a bus matrix. A pointer is just an address, whatever it points to.

The single address space gives back the flexibility of von Neumann:

  • Constants in flash. A const lookup table stays in flash and is read with ordinary load instructions through the data bus.
  • Code in RAM. Firmware can copy a time-critical function into SRAM and run it from there, or a bootloader can load an application into RAM and jump to it.
  • One kind of pointer. C compilers need no special qualifiers or instructions to read program memory.

Some older 8-bit microcontroller families are closer to strict Harvard: program memory has its own address space, and reading a constant table from flash needs special instructions or compiler extensions. If you have used one, you have felt the cost of the pure model.

Consequences you will meet in firmware

Mixing the two models leaves a few traces that matter in practice.

  • Code that writes code must say so. When a program writes instructions into memory and then executes them, the instruction path (a fetch buffer or instruction cache) may still hold old bytes. RISC-V requires a fence.i instruction between writing and executing on the same hart, precisely because the instruction and data paths are separate.
  • Bus contention depends on placement. If code runs from SRAM and data also lives in the same SRAM bank, the two buses meet again at that bank and the Harvard advantage shrinks. Linker scripts that put hot code and hot data in different memories recover it.
  • Flash wait states hurt fetches. Flash is often slower than the core, so fetches from flash stall unless a prefetch buffer or small cache hides the latency, while data in SRAM is fast. Benchmarks can change significantly depending on where code is placed.

Common mistakes

  • Treating "Harvard" as a property of the ISA. It describes how a chip connects memory, not the instruction set; one ISA can be implemented either way.
  • Forgetting fence.i after loading code. The data path saw the new instructions; the fetch path may not have.
  • Assuming code in RAM is always faster. It can be, but it then competes with data for the same bank.
  • Answering exam questions with "Harvard is faster". Separate paths remove a bottleneck; the right answer explains which one and at what cost.

Try it yourself

  1. Write a linker script for a RISC-V microcontroller memory map that places .text in flash and copies one function into SRAM (.data-style), build it with a RISC-V GCC cross-compiler, and check the addresses with riscv64-unknown-elf-objdump -h.
  2. Simulate a small RV32I core in Icarus Verilog twice: once with separate instruction and data memories, and once with an arbiter in front of a single memory. Count cycles for the same program.
  3. Draw the loop example above as a cycle-by-cycle table for both organisations before running anything, and compare your prediction with the simulation.
