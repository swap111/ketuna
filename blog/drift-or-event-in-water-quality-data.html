Telling sensor drift from real events in water quality data

Edge AI Beginner 27 Nov 2026 5 min read By Ketuna

A water quality reading can change because the water changed or because the sensor did. Moving statistics, reference checks and a few explainable rules separate slow drift from genuine events.

In this article
  1. Two different shapes of change
  2. Moving statistics: short against long
  3. Reference checks expose drift directly
  4. Small, explainable rules first
  5. Try it yourself

A sensor node in a tank, canal or treatment plant reports pH, conductivity, dissolved oxygen or turbidity every few minutes. When a reading moves, someone has to decide whether the water changed, which may need action, or whether the sensor changed, which needs maintenance. Electrochemical and optical water sensors drift as their membranes age, their electrodes foul and biofilm grows on their windows. A system that cannot tell the two apart either raises false alarms until people ignore it, or slowly absorbs real problems into a drifting baseline. Simple, explainable methods handle most of this before any neural network is needed.

Two different shapes of change

Drift and events usually differ in speed, and that is the most useful clue.

  • Sensor drift is slow and steady: a pH electrode reading creeps upward by a small amount each day, or a turbidity sensor rises as its window fouls. It continues in one direction for days or weeks.
  • A real event is usually fast: a discharge, a dosing fault or a storm runoff changes the water within minutes to hours, and often recovers when the cause passes.

Speed alone is not proof. A sensor can fail suddenly (a cracked electrode, an air bubble on an optical window), and real conditions can change slowly (seasonal temperature, gradual contamination). So you combine several clues, each simple enough to explain to the person who will act on the alert.

Moving statistics: short against long

Compare a short-window summary with a long-window baseline. The short window, say the mean of the last hour, follows the water quickly. The long window, say the median of the last day, changes slowly and, because it is a median, is barely moved by a few hours of unusual readings. A real event shows up as a large gap between them. Drift moves both together, so the gap stays small.

import numpy as np

rng = np.random.default_rng(0)
n = 30 * 24 * 4                               # 30 days, every 15 min
t_days = np.arange(n) / 96
ph = 7.2 + 0.02 * rng.standard_normal(n)      # water plus noise
ph += 0.01 * t_days                           # slow sensor drift
ph[1500:1524] -= 0.5                          # a 6-hour real event

def rolling(x, w, fn):
    out = np.full_like(x, np.nan)
    for i in range(w, len(x)):
        out[i] = fn(x[i - w:i])
    return out

short = rolling(ph, 4, np.mean)               # last hour
long_ = rolling(ph, 96, np.median)            # last day
event = np.abs(short - long_) > 0.15
print("flagged samples:", np.flatnonzero(event))

slope = np.polyfit(t_days, ph, 1)[0]
print(f"long-term slope: {slope:.4f} pH per day")

On this synthetic data, made up for illustration, the rule flags a continuous run of samples starting half an hour into the event and ending shortly after it, with no false alarms over the 30 days, even though the baseline drifted by 0.3 pH over the month. The fitted slope of about 0.01 pH per day recovers the drift that was built in. The numbers you choose (window lengths, the 0.15 threshold) should come from your own site's normal variability, measured over a period you know was quiet.

Reference checks expose drift directly

Statistics can suggest drift; a reference check measures it. Common approaches:

  • Calibration checks. At a fixed interval, a technician places the sensor in a standard solution of known value, or an automatic system flushes one past it. The difference between reading and known value is the drift, and it is logged.
  • A second sensor. Two sensors of the same kind side by side, or a portable instrument used during site visits. Water changes affect both; drift usually affects one.
  • Physical consistency. Some parameters are linked. A genuine pollution event often moves several readings together, such as conductivity and turbidity, while drift typically affects one sensor alone. A sudden change in one parameter with no movement in related ones is a hint to suspect the sensor.

Each check gives the decision a reason a human can verify, which matters when the alert might stop a pump or trigger a report.

Small, explainable rules first

Put the clues together as a short set of rules:

  1. If the short-long gap exceeds its threshold and a related parameter also moved: report a probable event.
  2. If the gap exceeds its threshold but no related parameter moved: report a possible sensor fault, and ask for a check.
  3. If the long-term slope since the last calibration exceeds a limit, or the last reference check was off by more than a tolerance: schedule maintenance for drift.
  4. Otherwise: normal.

Every alert then comes with its reason ("pH dropped 0.5 within an hour while conductivity also rose"), and every threshold can be tuned by someone who understands the site. A small decision tree trained on labelled history can refine the thresholds and stays just as readable. A neural network becomes worth considering only once you have plenty of labelled events and the simple rules demonstrably miss them.

All of this fits easily on a microcontroller at the sensor node: a few running sums for the short mean, a buffer of a day's readings for the median (or a cheaper running estimate), and some comparisons. Doing it locally means the node can send a short alert immediately and only summary data the rest of the time.

Common mistakes:

  • using a long-window mean instead of a median, so the event itself drags the baseline and hides
  • re-zeroing the baseline automatically and absorbing real slow contamination as "drift"
  • setting thresholds from a datasheet instead of the site's measured normal variability
  • skipping reference checks because the statistics look fine

Try it yourself

  1. Run the script, then make the event slower (spread the drop over two days) and see when the short-long rule stops catching it.
  2. Add a second, independent synthetic sensor that sees the event but not the drift, and implement rule 2.
  3. Find a public water quality dataset from a monitoring agency, plot one parameter over a year, and mark where you think calibrations happened from the jumps in the data.
  4. Port the short-mean and long-median logic to C with fixed-size buffers and compare its flags with the Python version on the same data.
